从 3.x 升上来之后页面某些地方不对劲，你打开升级指南想找"我这种情况在哪一条"。这一节一千三百多行，直接滚动找是低效的——它有固定结构，先拿到地图再定位。

## 七个章节

| `##` 章节 | 讲什么 |
| --- | --- |
| Upgrading Nuxt | 升到最新版（`nuxt upgrade`）与 nightly 渠道 |
| Testing Nuxt 5 | 用 `future.compatibilityVersion: 5` 提前试 Nuxt 5 的破坏性变更（**十九项清单**） |
| Moving to `nuxt/server` | Nuxt 4.6 起服务端代码改从 `nuxt/server` 显式导入，与 h3 的差异、`NUXT_E8012`、应用密钥一节 |
| Migrating to Nuxt 4 | **本体的 27 项变更**，前面挂着一节 Migrating Using Codemods |
| Nuxt 2 vs. Nuxt 3+ | 从 2 看 3+ 的概念差别 |
| Nuxt 2 to Nuxt 3+ | 2 → 3+ 的迁移路线 |
| Nuxt 2 to Nuxt Bridge | 走 bridge 的路线 |

也就是说，**这一节同时管着"升最新版"、"试下一大版本"、"3 到 4"和"2 到 3+"四类事情**，而它们的入口是同一页。

## 升级动作本身只有两条命令路径

**升到最新版**：那一节只给了一句话——"To upgrade Nuxt to the latest release, use the `nuxt upgrade` command."，然后按包管理器给了五条写法：

```bash
npx nuxt upgrade
yarn nuxt upgrade
pnpm nuxt upgrade
bun x nuxt upgrade
deno x nuxt upgrade
```

**指定装 4.0**：Migrating to Nuxt 4 开头那句 "First, upgrade to Nuxt 4:" 同样给了五条，只是把包名换进去（`npm install nuxt@^4.0.0`、`yarn add nuxt@^4.0.0`、`pnpm add nuxt@^4.0.0`、`bun add nuxt@^4.0.0`、`deno add npm:nuxt@^4.0.0`）。

装完之后这一节给了两句定性，是整个迁移策略的基调：

> After upgrading, most Nuxt 4 behaviors are now the default. However, some features can still be configured if you need to maintain backward compatibility during your migration.

意思是：**升上去后大部分东西已经按 4 的方式跑了，不需要逐个开关去打开**；需要保留旧行为时再回配置里找对应项。**这也是为什么不该先急着把配置改成 4 的形状**——先跑起来，看哪里坏。第三句承诺是："Breaking or significant changes are documented below along with migration steps and available configuration options."（下面的每一项都配迁移步骤与可用的配置项）。

## 27 项变更与它们的级别

Migrating to Nuxt 4 一节里，按 `###` 数下来是 **27 个变更小节**，顺序如下：

New Directory Structure、Singleton Data Fetching Layer、Corrected Module Loading Order in Layers、Deduplication of Route Metadata、Normalized Component Names、Unhead v2、New DOM Location for SPA Loading Screen、Parsed `error.data`、More Granular Inline Styles、Scan Page Meta After Resolution、Shared Prerender Data、Default `data` and `error` values in `useAsyncData` and `useFetch`、Removal of deprecated `boolean` values for `dedupe`、Respect defaults when clearing `data`、Respect defaults when clearing `useState`、Alignment of `pending` value、Key Change Behavior、Shallow Data Reactivity、Absolute Watch Paths in `builder:watch`、Removal of `window.__NUXT__` object、Directory index scanning、Template Compilation Changes、Default TypeScript Configuration Changes、TypeScript Configuration Splitting、Removal of Experimental Features、Removal of Top-Level `generate` Configuration、Normalized Page Component Names。

**级别标注的三处问题**（都是数出来的，可以自己复算）：

1. **27 项里只有 26 项写了 🚦 Impact Level。** 缺的那一条是 **Removal of `window.__NUXT__` object** —— 它只有 What Changed／Reasons for Change／Migration Steps 三段，**没有级别行**。
2. **级别词汇在同一页有两套写法**：Significant **1**、Moderate **3**、Medium **4**、Minimal **18**。Moderate 与 Medium 都夹在 Minimal 和 Significant 之间，**文档从没说过这两级是不是同一个东西**。
3. **级别与内容的重要性并不严格对齐**：唯一标 Significant 的是 New Directory Structure（目录结构），而 `useAsyncData`／`useFetch` 那一批数据获取行为的变更各自只标到 Moderate 或 Minimal——**但这些恰恰是最容易在业务代码里显形的**。读级别时要按"我的代码有没有碰到它"来判断，而不是按级别排序处理。

## 每一项的内部结构

三段模板在整页的出现次数是：**What Changed 27 次、Reasons for Change 14 次、Migration Steps 34 次**（第三段次数多于小节数，因为有的小节把它拆成了多段）。

这组数字的实际含义：**有 13 项变更没写"为什么改"**，只有"改了什么"和"怎么迁"。所以当你想判断"这条变更对我这个项目到底要不要紧"，而那一节又没有 Reasons for Change 时，**依据不足，只能到自己的代码里搜相关 API**。

三段之外还有两类常见元素：👉 指向 RFC issue 的链接（目录结构那条给的是 nuxt/nuxt **#26444**），以及 `::tip` 里给出的单项 codemod 命令——**六项变更有可自动化的命令**，这一部分下一篇单独数。

## 自查：怎么用这张地图

- 先确定你在哪一节：升小版本 → Upgrading Nuxt；试 5 → Testing Nuxt 5；服务端 import 报错 → Moving to `nuxt/server`；3 到 4 → Migrating to Nuxt 4；从 2 起步 → 最后三节。
- 在 Migrating to Nuxt 4 里定位时，**按 API 名字搜而不是按级别**：`useAsyncData`、`useState`、`builder:watch`、`window.__NUXT__`、`app/pages` 这些字符串命中率高。
- 看到级别先怀疑措辞：Moderate 与 Medium 在这一节没区分，`window.__NUXT__` 那条干脆没标。
- 没有 Reasons for Change 的那 13 项，别推测动机，只照 Migration Steps 改。
