  摘要：升级路上最容易撞到的三个配置类报错码，各占一页、各一页只有一段诊断加一段 Resolution。**B5001 "Missing compatibilityDate"**——没设这个日期，Nuxt 就无从决定套用哪套默认行为，**不写会静默采用新默认值**，Resolution 是补上**当天日期**。**B5003 "Reserved runtimeConfig.app namespace"**——把自定义键写进了 `runtimeConfig.app`，而这个命名空间**是 Nuxt 留给内部值的（原文举例 `baseURL` 与 `cdnURL`）**，Resolution 是给两个去向：`runtimeConfig.public`（暴露给客户端）或**顶层自定义命名空间（只在服务端）**。**B5004 "External config file not supported"**——`nuxt.config` 旁边还放着独立的 `vite.config` 或 `webpack.config`，Nuxt 自己管打包器、**会直接忽略这些文件**，Resolution 是搬进对应键再删掉外部文件，并列出了**四份**文件的对应关系。**这三节都不在官方主目录清单里，要直接拼 URL（`docs/4.x/errors/b5001`）才找得到。**

升级完构建通过，但终端里留着三行提示：一个缺 `compatibilityDate`、一个说 `runtimeConfig.app` 里的键冲突、一个说你旁边的 `vite.config` 被忽略了。这三条都有专属页面，而且都短到可以一次读完。

## 三节共用的形状

三节的结构完全一致：**一个编号标题、一段诊断句、一个 `## Resolution`、一条 read-more**。没有参数表、没有示例之外的额外说明。

还有一件事会影响你找到它们：**这三个错误码各自一页，且都不在官方主目录的链接列表里**，站内检索也经常搜不到——**直接拼地址最快**，形如 `https://nuxt.com/docs/4.x/errors/b5001`。

## B5001：缺 compatibilityDate

诊断原文：

> No `compatibilityDate` is set in your Nuxt configuration. Nuxt uses this date to decide which behaviour defaults to apply, so your project stays stable across Nuxt and Nitro updates instead of **silently picking up new defaults**.

Resolution 给的写法是"用你加这一行那天的日期"：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  // use the current date, e.g. the day you add this line
  compatibilityDate: 'YYYY-MM-DD',
})
```

三点要读准：**`'YYYY-MM-DD'` 是占位符不是字面值**；这一键**决定套用哪一套行为默认值**；后果的措辞是**"静默"捡到新默认值**——也就是说没有这条提示时你不会知道行为已经变了。那一节末尾的 read-more 指向升级那一节。

配置参考里 `## compatibilityDate` 那节**没有类型行也没有默认值行**，正面讲它的只有那一节与那一节两处。

## B5003：自定义键写进了保留命名空间

诊断原文：

> You have custom keys under `runtimeConfig.app`, a namespace Nuxt reserves for internal values (such as `baseURL` and `cdnURL`). **Custom keys here can collide with Nuxt's own config.**

Resolution 给两个去向，而且各自标了可见性：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  runtimeConfig: {
    // instead of runtimeConfig.app.myKey
    public: {
      myKey: 'value',
    },
  },
})
```

> Move custom keys to `runtimeConfig.public` (**exposed to the client**) or to a **top-level custom namespace (server-only)**.

这一条正好补上了 `runtimeConfig` 那节的空白：配置参考只说"`public` 与 `app` 之下的东西前端也拿得到"，**没说自定义键能不能写进 `app`**；B5003 明确答了——**`app` 是保留命名空间，别往那里放自己的键**。

结合两侧记载，可用的落点其实是两类：`public` 下（进客户端）、顶层或顶层自定义对象下（只在服务端）。想给值加类型，官方给的路子是扩展 `RuntimeConfig` 接口（在运行时配置那一节），不是写进 `app`。那一节末尾的 read-more 指向运行时配置那一节。

## B5004：旁边的独立配置文件被忽略

诊断原文：

> Nuxt found a standalone `vite.config` or `webpack.config` file next to your `nuxt.config`. **Nuxt manages the bundler internally and ignores these files**, so they are usually leftovers from a migration or a copied non-Nuxt project.

Resolution 是"搬进去、再删掉外部文件"，并列了**四条对应关系**：

| 独立文件 | 搬进 `nuxt.config` 的键 |
| --- | --- |
| `vite.config` | `vite` |
| `webpack.config` | `webpack` |
| `nitro.config` | `nitro` |
| `postcss.config` | `postcss` |

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  vite: {
    // your Vite config here
  },
})
```

**这里有一处前后宽度不同要留意**：诊断句只点名了 `vite.config` 与 `webpack.config` 两种，Resolution 的映射表却给了**四种**（多了 `nitro.config` 与 `postcss.config`）。也就是说**如果你项目里躺着的是后两种，报错文案可能不提它们，但处理方式是一样的**。

那一节的 read-more 指向入门的配置那一节——那一节有同一批映射的完整版（**它写的是 Nuxt 把 `nuxt.config.ts` 当作唯一真相源、"skips reading external configuration files"**）。

## 三条放一起的共同点

| | 触发点 | 危险等级 |
| --- | --- | --- |
| B5001 | 少写一个键 | **静默改变行为**（升级后最难查的那类） |
| B5003 | 键写错位置 | 可能与框架自身配置**相撞** |
| B5004 | 文件放错位置 | **整份配置被忽略**，不报错也不生效 |

三条都属于"改一处配置就解决"的类别，但**没有一条会导致构建失败**——这正是它们容易被长期忽略的原因。

## 自查

- 三个错误码页都要**直接拼 URL 去找**，不靠站内目录。
- B5001：补当天日期；`'YYYY-MM-DD'` 是占位符；不写的后果是静默采用新默认值。
- B5003：`runtimeConfig.app` 是保留命名空间；自定义键去 `public`（进客户端）或顶层自定义命名空间（只服务端）。
- B5004：`vite`／`webpack`／`nitro`／`postcss` 四份独立文件都要搬进对应顶层键**再删除外部文件**；诊断句只点了前两种，处理方式四种相同。
- 三条都不阻断构建，属于"看起来没事"的那类，值得在升级后专门搜一遍。
