写过一个 Nuxt 2 模块的人，升级时都会问同一句：能不能不改代码就先用起来？这一节给的答案是"有一点兼容层，但通常不够"，然后列出七件要做的事。

## 官方立场：兼容层有限，最佳路径是重写

> Nuxt 3 has a basic backward compatibility layer for Nuxt 2 modules using `@nuxt/kit` auto wrappers. But there are usually steps to follow to make modules compatible with Nuxt 3 and sometimes, using Nuxt Bridge is required for cross-version compatibility.

三个层次在这一句里：**有 basic 兼容层**（靠 `@nuxt/kit` 的自动包装）、**通常仍要做一些步骤**、**跨版本兼容有时必须走 Bridge**。

紧接着官方把推荐路径说得很直白：

> We have prepared a Dedicated Guide for authoring Nuxt 3 ready modules using `@nuxt/kit`. **Currently best migration path is to follow it and rewrite your modules.** Rest of this guide includes preparation steps if you prefer to avoid a full rewrite yet making modules compatible with Nuxt 3.

也就是说：**这一整页剩下的内容，定位是"不想重写时的准备步骤"**，不是推荐路线。页面还挂了一条 `::tip` 指向模块列表页（"Explore Nuxt 3 compatible modules."）。

## 两条兼容性判据

`### Plugin Compatibility` 只有一句：**"Nuxt 3 plugins are **not** fully backward compatible with Nuxt 2."**（外加一条指向插件目录页的 read-more。）

`### Vue Compatibility` 给的判据更实用：

> Plugins or components using the Composition API need exclusive Vue 2 or Vue 3 support.
>
> By using [vue-demi](https://github.com/vueuse/vue-demi) they should be compatible with both Nuxt 2 and 3.

拆开是两件事：**用了 Composition API 的插件或组件，只能声明支持 Vue 2 或 Vue 3 中的一边**；**要同时支持两边，官方给的手段是 vue-demi**（措辞是 "they should be compatible"，是预期而非保证）。

## 容器访问没了：Module Migration 的开场

> When Nuxt 3 users add your module, you will not have access to the module container (`this.*`) so you will need to use utilities from `@nuxt/kit` to access the container functionality.

这一句是模块侧最大的破坏点：**Nuxt 2 模块里 `this.nuxt`、`this.options` 这类 `this.*` 访问，在 Nuxt 3 用户加载你的模块时拿不到**，必须换成 `@nuxt/kit` 的工具函数。

下面四个 `###` 就是这一步的具体动作清单。

### 一、先用 @nuxt/bridge 试

> Migrating to `@nuxt/bridge` is **the first and most important step** for supporting Nuxt 3.

操作只有一句：如果你的模块有 fixture 或 example，把 `@nuxt/bridge` 包加到它的配置里（链接指向 Bridge 那一节的 "Update `nuxt.config`" 小节）。

### 二、CommonJS 转 ESM

这一节只有一句指路："Nuxt 3 natively supports TypeScript and ECMAScript Modules. Please check Native ES Modules for more info and upgrading." ——**具体怎么转在那一节，这里没写**。

### 三、注入的插件要有默认导出

> If you inject a Nuxt plugin that does not have `export default` (such as global Vue plugins), **ensure you add `export default () => { }` to the end of it.**

官方的前后对照是一个 vuelidate 插件：

```js [Before]
// ~/plugins/vuelidate.js
import Vue from 'vue'
import Vuelidate from 'vuelidate'

Vue.use(Vuelidate)
```

```js [After]
// ~/plugins/vuelidate.js
import Vue from 'vue'
import Vuelidate from 'vuelidate'

Vue.use(Vuelidate)

export default () => { }
```

**改动只有末尾那一行空默认导出**——这是给注入用的插件补形状，不是让它变得可执行。

### 四、别写运行时模块

> With Nuxt 3, Nuxt is now a build-time-only dependency, which means that modules shouldn't attempt to hook into the Nuxt runtime.

判据是那句 **"Your module should work even if it's only added to `buildModules` (instead of `modules`)"**，下面三条是要避开的：

- **不要在模块里更新 `process.env` 又让 Nuxt 插件去读**；改用 `runtimeConfig`。
- `(\*)` **不要依赖 `vue-renderer:*` 这类运行时钩子来做生产渲染**。
- `(\*)` **不要在模块里 import 的方式添加 `serverMiddleware`**；改为引用文件路径，使它独立于模块上下文。

带星号的两条有统一例外，写在列表外面：**"Unless it is for `nuxt dev` purpose only and guarded with `if (nuxt.options.dev) { }`."** ——**只为开发服务、并且用 `nuxt.options.dev` 守卫住的，可以保留。**

这一节末尾还有一条 `::tip` 再次指向模块作者指南。

**这里有一处文档缺陷要指出**：那句 `buildModules` 的链接，锚点指向的是 `api/nuxt-config#runtimeconfig`，**不是 `buildModules` 相关的位置**。照链接跳过去会看到运行时配置那一节，容易误读。**"Nuxt 3 里 `buildModules` 这一键本身是否还存在"这一节没有说**，要查得直接看配置参考的顶层节列表。

### 五、TypeScript 是可选的

最后一条 `### Use TypeScript (Optional)` 给了三句：**生态在往 TypeScript 迁移，建议考虑**；**可以先只把 `.js` 改名成 `.ts` 起步**（"TypeScript is designed to be progressive!"）；**在 Nuxt 2 与 Nuxt 3 的模块和插件里用 TS 语法不需要额外依赖**（两条都以 `::tip` 给出）。

## 自查

- 官方推荐是**按模块开发指南重写**；这一节其余七节是"不想重写时"的准备步骤。
- 两条判据：插件**不完全向后兼容**；Composition API 只能选一边，**跨边靠 vue-demi**。
- 容器 `this.*` 拿不到，改 `@nuxt/kit`；**先接 `@nuxt/bridge` 试**被列为第一且最重要的一步。
- 注入的插件要补 `export default () => { }`。
- 运行时依赖三避：`process.env` 跨端传递（改用 `runtimeConfig`）、`vue-renderer:*`、import 式加 `serverMiddleware`；**带 `nuxt.options.dev` 守卫的纯开发用法可保留**。
- 那一节 `buildModules` 的链接锚点指错（指向 `#runtimeconfig`）；`buildModules` 在 4.x 的地位这一节没讲。
