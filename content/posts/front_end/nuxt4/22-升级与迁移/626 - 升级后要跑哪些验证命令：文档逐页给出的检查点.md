升级最难的不是改代码，是判断"改完了没有"。文档没有给一张勾完就能上线的清单，但把检查点散在了各页里——这一篇按出处收拢。

## 七条有出处的检查点

| 检查点 | 命令或动作 | 出自哪一页 |
| --- | --- | --- |
| 装完新版先双验 | dev 与生产构建都要正常 | Bridge 的 Overview：`::note` "make sure both development and production builds are working as expected before proceeding" |
| 开完 Nitro 再试一次 | `nuxi dev` ＋ `nuxi build`（或 `nuxi generate`） | Bridge 的 Nitro：`## Ensure Everything Goes Well` 那句带 ✔️ |
| 测试前先补类型文件 | `nuxi prepare` | Bridge 的 TypeScript：**不跑就会 `TS5083: Cannot read file '~/.nuxt/tsconfig.json'`** |
| 生成 tsconfig 本体 | `npx nuxt prepare` | 迁移的 Configuration：TypeScript 三步里的第 2 步 |
| 类型检查 | `nuxt typecheck`（用 `vue-tsc`） | 迁移的 Configuration 的 `::note` |
| 跑测试 | `npm run test` / `npm run test:watch`；e2e 走 `nuxt test` | 测试那一节与 `nuxt test` 命令页 |
| 静态与服务端分开验 | `nuxi generate` 与 `nuxi build` | Bridge 的 Nitro 的 Static/Server Target 两节 |

## 前两条：双验的顺序有讲究

Bridge 的检查点其实是**两道**，而且分处两节：装完依赖升级后要确认 dev 与生产构建都正常（那一刻 Bridge 还没开），**开着 `bridge.nitro: true` 之后还要再试一次** `nuxi dev` 与 `nuxi build`。**两道之间隔着"换服务端产物"这一步**，所以只跑一道不能说明问题。

顺带一提：`nuxi build` 与 `nuxi generate` 的差别在产物形状（一个出可跑的服务端、一个出静态目录），**Bridge 的 Nitro 页把选择依据交给 `target: 'static'` 这个 Nuxt 2 键**，4.x 侧的对应做法是预渲染那套（本系列在部署分区里已单独讲过，此处不重复）。

## 第三条最容易被 CI 咬

> As `.nuxt/tsconfig.json` is generated and not checked into version control, you'll need to generate that file before running your tests. Add `nuxi prepare` as a step before your tests, otherwise you'll see `TS5083: Cannot read file '~/.nuxt/tsconfig.json'`

这条的实战含义：**本地能跑不代表 CI 能跑**——本地早就有过 `.nuxt`，CI 是干净检出。**把 `nuxi prepare` 放进测试之前的步骤**是官方给的解法，而不是把生成文件提交进仓库。

## 第四、五条：生成与检查是两件事

- `npx nuxt prepare` 的职责是**生成那些 tsconfig 文件**（配置侧三步里的第二步）。
- `nuxt typecheck` 的职责是**做类型检查**，官方 `::note` 写明它用 `vue-tsc`：`note` 原文是 "Nuxt can type-check your app using `vue-tsc` with `nuxt typecheck` command."

两条不要混：**跑 `typecheck` 之前得先有生成的配置**，否则报的就是上一条那个 `TS5083`。而在 4.x 侧，**这一节说的类型检查还需要显式开 `typescript.typeCheck`（默认 `false`）并把 `typescript` 与 `vue-tsc` 装成 dev 依赖**（配置参考里那一子项的原文要求）。

## 第六条：测试这一路的三条硬事实

- **单元测试环境目前只支持 vitest**：原文 "It currently *only has support for `vitest`* (although contribution to add other runtimes would be welcome)."
- **推荐安装的依赖是一串**：`@nuxt/test-utils vitest @vue/test-utils happy-dom playwright-core`（页首 code-group 给的就是这一行，四种包管理器写法）。
- **`@nuxt/test-utils/module` 是可选项**：加进 `modules` 只多一个 DevTools 里跑单元测试的集成，**不加也能用**。

`vitest.config.ts` 的官方示例把用例分成三个 project（`unit`／`e2e`／`nuxt`，第三份的 `environment: 'nuxt'`）——**这三类要分开跑**：`unit` 那份是 `environment: 'node'`，**测不到需要 Nuxt 运行时的东西**。

而 `nuxt test` 命令这一侧的公开契约是：**把 `process.env.NODE_ENV` 设为 `test`（if not already set）**，并支持 `--dev`（"Run in dev mode"）——**别把"跑测试"等同于"一定没有 dev 行为"**。

## 第七条：文档没写的部分

有一件很多人想问的事，**官方没有记载**：**codemod 跑完之后要不要复核、要复核什么**。相关的原文只有两句——"execute all codemods in sequence, with the option to deselect any that you do not wish to run" 与"Each codemod … can be executed independently"。**"改完要过一遍 diff"是常识，但不是文档承诺**；这一节不把它列成官方检查点。

同理，"要不要跑一次端到端冒烟"、"要不要比对产物体积"这类，**文档也都没有要求**——它们属于你自己的发布流程，不是升级指南的一部分。

## 自查

- 有出处的七条：**双验 → Nitro 后试跑 → `nuxi prepare` → `nuxt prepare` 生成 → `nuxt typecheck` → 测试（unit/e2e/nuxt 三类，vitest only）→ 静态与服务端分别验**。
- CI 里最先炸的是 `TS5083`，解法是**测试前加 `nuxi prepare`**。
- 4.x 侧要用 `typecheck` 还得开 `typescript.typeCheck` 并装 `typescript`＋`vue-tsc`。
- `nuxt test` 设的是 `NODE_ENV=test`，且有 `--dev` 选项。
- **codemod 后是否复核、冒烟与体积比对：文档未要求，属自定流程。**
