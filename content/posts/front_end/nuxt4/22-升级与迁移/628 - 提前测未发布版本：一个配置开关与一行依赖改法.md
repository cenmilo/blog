版本管理器里显示"已是最新"，但你想要的行为还没发。这时候能做的只有两件事，而且官方文档把它们写在了两个不同的页面：一个开关改的是**已经定型的默认值**，一个渠道改的是**今天刚合进去的代码**。混用会得出错误结论——比如以为某个变化不存在，其实它只在另一个渠道里。

## 先分清两个词

**发布渠道（release channel）**指的是同一个包对外提供的不同版本流。稳定渠道是你 `npm install nuxt` 拿到的那个；nightly 渠道是每天从源码最新提交打出来的那个。它们在 npm 上是**两个不同的包名**，`nuxt-nightly` 而不是 `nuxt`。

**兼容性版本（compatibility version）**是 `nuxt.config.ts` 里的一个键。它不换包，只是让当前这套代码**按下一个大版本的默认值来跑**。

一个是换货，一个是改预设。

## 第一条路：把默认值切成 Nuxt 5

升级页的 "Testing Nuxt 5" 一节开头就给了版本下限：Nuxt 5 仍在开发中，**从 Nuxt 4.2 起**可以测试它的许多 breaking changes。

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  future: {
    compatibilityVersion: 5,
  },
})
```

配置参考里 `future` 这一节只有类型和一句说明，**具体会改变什么都没写在那一节**。19 项清单在升级页。逐项如下，左边是原文的加粗小标题，右边是它实际改掉的默认行为。

| # | 变化 | 开关后的行为 |
| --- | --- | --- |
| 1 | Vite Environment API | `experimental.viteEnvironmentApi` 启用，Vite 插件的注册与配置方式随之改变 |
| 2 | 路由大小写敏感 | 页面路由严格按 URL 大小写匹配，与 Nitro 一致，`/About` 不再命中 `pages/about.vue` |
| 3 | 页面名归一 | 页面组件名与路由名一致，`<KeepAlive>` 行为稳定 |
| 4 | 可序列化的页面元数据 | `experimental.extractSerializablePageMeta` 在构建期抽出能静态分析的 `definePageMeta` 值 |
| 5 | 客户端 payload 抽取 | `experimental.payloadExtraction` 变成 `'client'`，预渲染页面的 HTML 内联 payload |
| 6 | `clearNuxtState` 重置为初始值 | 清状态时回到 `useState` 的初始值，而不是设成 `undefined` |
| 7 | 非异步的 `callHook` | `callHook` 可以返回 `void`，不再保证一定返回 `Promise` |
| 8 | `navigateTo` 提前返回 | `experimental.navigateToEarlyReturn` 让中间件重定向后不再继续往下执行 |
| 9 | 服务端专用 head composable | `useServerHead`、`useServerHeadSafe`、`useServerSeoMeta` **不再自动导入**；`unhead.legacy` 被忽略，Unhead 的 legacy 插件不再注册，Capo 排序常开 |
| 10 | PostCSS 默认关闭 | `autoprefixer` 与 `cssnano` 不再自动配置，除非你在 `postcss.plugins` 里自己开 |
| 11 | 带 key 的 composable 必须有 `source` | `optimization.keyedComposables` 里缺字符串 `source` 的条目不再通过自动导入匹配 |
| 12 | 注释节点占位 | client-only 组件的 SSR 占位改用注释节点而不是 `<div>` |
| 13 | 类型化页面 | `experimental.typedPages` 启用，路由带类型检查 |
| 14 | 错误响应格式 | `experimental.inlineErrorRendering` 启用：页面错误返回错误页、服务端路由错误返回 JSON，**且不看请求头** |
| 15 | 带类型的 `$fetch` | `experimental.routeTypedFetch` 用生成的路由类型为 `$fetch` 与 `useFetch` 补类型 |
| 16 | 关掉 Nitro 自动导入 | 服务端代码显式导入 Nitro 的助手，不再依赖自动导入兼容层 |
| 17 | 禁用 Vue Options API | Options API 从客户端 bundle 里编译出去，为的是减体积 |
| 18 | 更严的副作用导入 | 生成的 `tsconfig.json` 启用 `noUncheckedSideEffectImports` |
| 19 | 忽略 TypeScript `baseUrl` | 生成的 tsconfig 不再用 `compilerOptions.baseUrl` 解析 Nuxt 别名 |

第 7 项最阴。`callHook` 原本永远返回 `Promise`，切成 Nuxt 5 之后可以返回 `void`。如果你的模块里写着 `await nuxt.hook(...)` 之外的地方对返回值做了 `.then()`，**表现是运行到那一行才炸**，跟路由、渲染都没关系。

清单后面紧跟一句 `::note`，原文是：

> This list describes what the flag changes on Nuxt 4. Nuxt 5 itself carries further changes that no flag enables here, such as the upgrade to Nitro v3.

**这句话划了边界**：跑完 19 项都正常，不等于 Nuxt 5 上正常。Nitro v3 这类换引擎的变化，开关一个都不碰。每一项的迁移步骤在 Nuxt 5 的升级页（`docs/5.x/getting-started/upgrade`），4.x 这套文档里没有。

## 第二条路：nightly 渠道

升级页的 "Nightly Release Channel" 一节只有一句指向，具体机制在 going-further 那一节。

发布规则是：提交合进 `main` 分支、**并且通过全部测试**，GitHub Actions 就自动发一次版。也就是说 nightly 不是残缺的预览包，官方原话是构建与发布的方式和稳定版**完全相同**，区别只在"你要自己盯仓库更新"。风险他们也写了：review 和自动化测试都没抓到的回归，有**一点概率**存在，所以内部正是用这个渠道在每次正式发布前复核一遍。

进出都是改 `package.json` 里的一个依赖。

```diff [package.json]
{
  "dependencies": {
--    "nuxt": "^4.0.0"
++    "nuxt": "npm:nuxt-nightly@latest"
  }
}
```

改完必须**删掉锁文件再重装**。官方列出的锁文件名是五个：`package-lock.json`、`yarn.lock`、`pnpm-lock.yaml`、`bun.lock`、`bun.lockb`。不删的话解析器还按锁文件里的旧解析结果装，改的这行等于白写。退出渠道是反向的同一动作：改回 `^4.0.0`，删锁文件，重装。

还有一个带警告的当下状态：`latest` 这个标签**目前跟踪的是 Nuxt v4 分支**，所以"很可能有 breaking changes"。想试 3.x 分支的每日构建，用另一个标签：

```json
"nuxt": "npm:nuxt-nightly@3x"
```

CLI 也能单独走 nightly，不动项目的 `nuxt` 依赖：

```bash [Terminal]
npx @nuxt/cli-nightly@latest [command]
```

最后一条是文档的约定而不是坑：**只在 nightly 渠道才有的功能，官方文档里会挂一个标记**。看到那个标记就意味着这段行为你现在装的稳定版跑不出来。

## 两条路各自解决什么

| 你的目的 | 该用哪条 | 理由 |
| --- | --- | --- |
| 提前评估升级工作量 | `future.compatibilityVersion` | 19 项是已经定下来的默认值变化，结果可复现 |
| 验证某个昨天刚合并的修复 | nightly 渠道 | 开关不会引入新代码，只改预设 |
| 想知道某个未记载行为是否存在 | 都不够 | 开关与 nightly 都不能替代 5.x 的升级页 |

按官方口径，nightly 与 compatibilityVersion 是可以叠加的：一个改包，一个改预设。但文档没有给出"两者同时开"的示例，所以这条只能算作推断，真出问题两边都难定位——生产项目建议一次只动一个。

动手检查的顺序：先把依赖固定回稳定版跑一次基线，记录 dev 与 build 都通过；再只开 `compatibilityVersion`，看报错落在上表第几项；要试 nightly 就另起分支，删掉那五个锁文件名之一并重装。
