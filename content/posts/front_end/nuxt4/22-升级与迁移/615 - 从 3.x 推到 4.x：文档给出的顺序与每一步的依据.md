升级指南那一节有 27 个变更小节，迁移文档又有 11 个页面，读完很容易得结论："知道很多，但不知道第一步先敲哪条命令。" 这一篇就把已经写明的动作按顺序排一遍。

## 先说清一件事：顺序是谁给的

文档里没有"总流程"这一节。**下面的顺序是按各节自己的措辞拼的**：升级那一节用的是 "First, upgrade to Nuxt 4:" 与 "After upgrading, …"，目录结构那节写的是 "Nuxt now defaults to…"，配置那一节的 TypeScript 步骤自己带了 1-2-3 编号。**凡是文档没说先后的地方，我会写明"这一步与那一步顺序可换"，不替你编。**

## 第①步：把包升上去

两条路都在升级页，选一条：

```bash
npx nuxt upgrade
```

或者显式钉大版本（原文 "First, upgrade to Nuxt 4:"）：

```bash
npm install nuxt@^4.0.0
```

两边都给全了 npm／yarn／pnpm／bun／deno 五种写法。**`nuxt upgrade` 那节的定位是"升到 latest release"，安装那节是"明确装 4.0"**——**两者的差别文档没有进一步解释**，要按你的目标是"跟最新"还是"停在 4"来挑。

## 第②步：先跑一次，别急着改配置

> After upgrading, most Nuxt 4 behaviors are now the default. However, some features can still be configured if you need to maintain backward compatibility during your migration.

这句的实际操作含义是：**默认值已经是 4 的形状，不需要挨个开**；配置只在"要保留旧行为"时才动。所以顺序是先跑 dev、先跑 build，看真实报什么，再去 27 个变更小节里定位。

同页还有一句承诺可以用来对表："Breaking or significant changes are documented below along with migration steps and available configuration options."

## 第③步：决定要不要跑 codemod

要跑就跑总 recipe（**版本号是钉死的，注释写明因为 codemod/codemod #1710**）：

```bash
# Using pinned version due to https://github.com/codemod/codemod/issues/1710
npx codemod@0.18.7 nuxt/4/migration-recipe
```

它的行为官方写了两条：**按顺序执行全部 codemod**，并且**可以取消勾选不想跑的项**。

跑之前先看清范围：**27 项变更里只有 6 项有自动化命令**（`file-structure`、`default-data-error-value`、`deprecated-dedupe-value`、`shallow-function-reactivity`、`absolute-watch-path`、`template-compilation-changes`），**其余 21 项只能手改**。所以这一步的产出不是"迁移完成"，而是"其中 6 处机械改动做完了"。

## 第④步：目录结构（这一步可以整块跳过）

新版默认 `srcDir` 是 `app/`，但官方明确写了**不必迁移**：

- 如果 Nuxt 检测到你用的是旧结构（例如顶层就有页面目录），**新结构不会应用**。
- 想要强制旧布局，这一节直接给了配置：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  // This reverts the new srcDir default from `app` back to your root directory
  srcDir: '.',
  // This specifies the directory prefix for `router.options.ts` and `spa-loading-template.html`
  dir: {
    app: 'app',
  },
})
```

- **例外只有一个你已经知道**：原本就设了自定义 `srcDir` 的项目，`modules/`、`public/`、`shared/`、`server/` 会**从 `rootDir` 而不是从你的 `srcDir` 解析**；对策是显式设 `dir.modules`、`dir.public`、`serverDir`。
- 别忘了第三方配置：官方点名的例子是 `tailwindcss` 与 `eslint` 配置要自己更新，并补了一句 `@nuxtjs/tailwindcss` 应当会自动把 `tailwindcss` 配好。

**这一步与第⑤步的顺序可以换**：目录布局和类型配置互不影响，先做哪个都行。文档没有规定先后。

## 第⑤步：把类型这条路补上

迁移文档的 TypeScript 一节给的是三步编号，正好接在这里：

1. 在 `tsconfig.json` 里写四份 references：**`.nuxt/tsconfig.app.json`、`.nuxt/tsconfig.server.json`、`.nuxt/tsconfig.shared.json`、`.nuxt/tsconfig.node.json`**。
2. 跑 `npx nuxt prepare` 生成这些文件。
3. 按安装页说明装 Volar。

要做真正的类型检查再加两条：`nuxt typecheck` 走 `vue-tsc`，而配置项 `typeCheck` **默认是 `false`**，并且**官方写明前置条件是把 `typescript` 与 `vue-tsc` 装成 dev 依赖**。

这一节还有一句容易安抚人的话值得记住：**用 TypeScript 集成不等于要把应用全改写成 TS**，只是为了让编辑器有提示。

## 第⑥步：按 27 项逐条过

到这一步才是体力活。定位技巧有两条，都来自文档结构本身：

- **按 API 名字搜，不按标题搜**：`useAsyncData`、`useState`、`builder:watch`、`window.__NUXT__`、`app/pages` 这类字符串命中率高。
- **级别只当参考**：这一节同时用了 Moderate 与 Medium 两套措辞，而且**`window.__NUXT__` 那一节连影响级别都没标**。真正要判断的是"我的代码有没有碰到它"。

碰到需要保留旧行为的项目，用那 **10 处 `experimental` 回退/提前写法**之一（例如 `experimental.defaults.useState.resetOnClear`、`experimental.normalizePageNames: false`）。**`future.compatibilityVersion: 5` 不属于这一步**——它是"试 Nuxt 5"用的，而且要 Nuxt 4.2 以上。

## 第⑦步：补 compatibilityDate

如果构建或启动时弹出缺少 `compatibilityDate` 的提示（报错码 B5001），按它的 Resolution 补当天日期：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  // use the current date, e.g. the day you add this line
  compatibilityDate: 'YYYY-MM-DD',
})
```

这一键管的是 **Nitro／Nuxt Image 与其他模块里那些不升主版本也会变的 presets 行为**，官方在 B5001 里的措辞是"不写就会**静默采用新默认值**"。**它是升级后最容易"没报错但行为变了"的一处**，所以放在收尾而不是开头。

## 自查

- 七步里**只有目录结构与类型两步在文档里有明确编号顺序**，其余步骤之间的先后文档未规定。
- 第②步的"先跑"依据是 "most Nuxt 4 behaviors are now the default"。
- 第③步的自动化覆盖 **6/27**，跑完不等于迁完。
- 第④步可以整块退回旧布局（`srcDir: '.'` ＋ `dir.app`），**但设过自定义 `srcDir` 的项目必须检查四个目录的解析基准**。
- 第⑤步：四份 references ＋ `npx nuxt prepare` ＋ Volar；要检查还得装 `typescript`／`vue-tsc` 并开 `typeCheck`（默认 `false`）。
- 第⑥步用 `experimental` 单项回退；`compatibilityVersion` 是另一件事。
- 第⑦步 `compatibilityDate` 补当天日期（B5001 的 Resolution）。
