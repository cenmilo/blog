接手一个 `package.json` 里写着 `"nuxt": "^2.x"` 的项目，老板问"要不要升"。你可能想找一张能直接对比的表——官方文档里确实有一张，位置很靠后，而且它只陈述差异，**不回答"该不该"**。这一篇把这张表逐行落地，顺便说清它凭什么不能当选型依据。

## 这张表在页面的哪里

官方讲版本升级的那一页有 7 个大章节，顺序是：升级命令、测 Nuxt 5、搬到 `nuxt/server`、迁移到 Nuxt 4，然后才是 **Nuxt 2 vs. Nuxt 3+**、**Nuxt 2 to Nuxt 3+**、**Nuxt 2 to Nuxt Bridge**。

也就是说这张表排在全页最后，前面四章讲的都是 3→4 与 4→5 的事。**它是给还在 Nuxt 2 的人看的，而页的正文主体并不服务这批人**。

## 15 行照录

三列分别是 Nuxt 2、Nuxt Bridge、Nuxt 3+。原文用的是图标（对勾、叉、进度中等），下面换成文字，含义一一对应。

| 特性 | Nuxt 2 | Nuxt Bridge | Nuxt 3+ |
| --- | --- | --- | --- |
| Vue | 2 | 2 | 3 |
| 稳定性 | 稳定 | 稳定 | 稳定 |
| 性能 | 快 | 更快 | 最快 |
| Nitro 引擎 | 无 | 有 | 有 |
| ESM 支持 | 部分 | 更好 | 有 |
| TypeScript | 需手动开 | 部分 | 有 |
| Composition API | 无 | 部分 | 有 |
| Options API | 有 | 有 | 有 |
| 组件自动导入 | 有 | 有 | 有 |
| `<script setup>` 语法 | 无 | 部分 | 有 |
| 自动导入 | 无 | 有 | 有 |
| webpack | 4 | 4 | 5 |
| Vite | 不完整 | 部分 | 有 |
| Nuxt CLI | 旧 | nuxt | nuxt |
| 静态站点 | 有 | 有 | 有 |

## 先读三列相同的那五行

**稳定性**这一行三列都写"稳定"。这在选型上是硬信息：留在 2 不代表在用不稳定的东西，升级也不代表从"不稳"走向"稳"。

**性能**这一行三列都是形容词（快、更快、最快），没有数字、没有测试条件。它不能拿来做基准对比。

**Options API**、**组件自动导入**、**静态站点**三行也都是"有"。特别是最后一行：**如果你的升级理由里有一条是"要出静态站"，这张表说明 Nuxt 2 本来就能出**。

## 四行"无"是真正的工作量

Nuxt 2 那一列写"无"的四行：**Nitro 引擎**、**Composition API**、`<script setup>`**语法**、**自动导入**，再加上 **Nuxt CLI** 那行的"旧"。

这五行连起来读才是升级的实际内容：**服务端从 Nitro 换成另一套（2 用的是 webpack＋`nuxt start`）、`.vue` 文件的写法要换、composable 不用 import 就能用这件事是新引入的、命令行本身换代**。

另外两行容易看漏：

- **TypeScript** 在 2 是"需手动开"，在 Bridge 是"部分"，到 3+ 才是"有"。三列的词都不一样，说明这是个渐进过程而不是一次切换。
- **webpack** 两列都是 4，只有 Nuxt 3+ 是 5。这一行讲的是 webpack 版本，跟 Vite 那行是两件事：**3+ 仍然保留 webpack 这一列，只是版本号变了**。

## Bridge 那一列的定位

Bridge 列里有 5 个"部分"或"更好"：ESM、TypeScript、Composition API、`<script setup>`、Vite。它不是完整的新版，而是**在 Nuxt 2 上引入 Nuxt 3 特性、带 opt-in 机制的兼容层**——这是页面下一节的原话。

Bridge 也不是所有能力都到位。它的总览页明确写了限制，取数那一类组合式函数在 Bridge 下是用不了的，这一点在 Bridge 分篇里已经单独讲过。

## 表后面的两条路线

表格之后是两个小节，**每个小节正文只有一句话加一个跳转**。

**Nuxt 2 to Nuxt 3+**：说迁移指南提供了把 Nuxt 2 特性逐条对照到 Nuxt 3+ 的步骤与改造当前应用的指引，跳转目标是 migration 分区的总览页。

**Nuxt 2 to Nuxt Bridge**：说如果你更希望**逐步迁移**，可以用 Bridge；它是让你可以在 Nuxt 2 里使用 Nuxt 3+ 特性的兼容层，带 opt-in 机制。跳转目标是 bridge 分区的总览页。

页面到此结束。**没有任何一句给出"什么情况下选前者、什么情况下选后者"的判断条件**，也没写工期、风险或回滚方式。这两节的作用只是指路，判断得自己做。

## 那怎么判断

表里没有依据，只能把这张表当**工作量清单**用。做法是按项目实际用到的特性去数"无"和"部分"：

| 项目现状 | 从表里读到什么 | 结论方向 |
| --- | --- | --- |
| 全项目只用 Options API | Options API 三列都是"有" | 升级不会改写法，收益只在 Nitro 与 CLI |
| 用了 `@nuxt/typescript` 手动开 | TypeScript 在 2 是"需手动开" | 升级能去掉手动配置，但 Bridge 只到"部分" |
| 想直接上 `<script setup>` | Bridge 那一列是"部分" | 走 Bridge 不能全部拿到，别把计划排成两步等价 |
| 只需要静态输出 | 静态站点三列都是"有" | 这条不构成升级理由 |
| 依赖 webpack 4 的 loader | webpack 两列是 4，3+ 是 5 | 版本号那行是真差异，要单独验 |

第四行是最常见的一种：拿"要出静态站"当升级理由，而这张表恰恰显示这一项三列都支持。**要升级的理由得从"无"那一列里找**。
