改了 `buildDir` 之后生成的类型文件跑哪去了、改了 `server.builder` 之后内联样式怎么就不生效了——这类问题的答案不在单个配置项那一节里，而在另一节的某半句话里。

## 文档明确连起来的十四条

下面每一行都能在文档里指到原句，不是推断：

| 上游 | 下游 | 文档原句（要点） |
| --- | --- | --- |
| `app.baseURL` / `app.cdnURL` | `app.buildAssetsDir` | "The folder name for the built site assets, **relative to `baseURL` (or `cdnURL` if set)**." |
| `buildDir` | `typesDir` | "This defaults to your `buildDir`, and is separate from it so that the configurations referenced by your project `tsconfig.json` stay in place…" |
| `rootDir` | `typesDir`、`analyzeDir`、`buildDir`、`serverDir`、`vite.cacheDir`、`alias` 表 | 这些节的默认值都写成 `"/<rootDir>/…"` 形式；相对路径 "will be relative to your `rootDir`" |
| `builder` | `typescript.builder` | "By default Nuxt infers this based on your `builder` option (**defaulting to 'vite'**)" |
| `server.builder`（选 Vite） | `features.inlineStyles` | "Inlines styles when rendering HTML. **This is currently available only when using Vite.**" |
| `ssr` | `spaLoadingTemplate` | 定性句限定 "inserted into any HTML page **rendered with `ssr: false`**" |
| `ssr: false` | `experimental.spaLoadingTemplateLocation` | "When rendering a client-only page (**with `ssr: false`**), we optionally render a loading screen…" |
| `srcDir` | `dir.app` → `router.options.ts`、`spa-loading-template.html` | "a new `dir.app` is added, which is the directory we look for `router.options.ts` and `spa-loading-template.html` - **this defaults to `<srcDir>/`**" |
| `srcDir` | `watch` 的条目 | "Strings should be either absolute paths or **relative to the `srcDir`** (and the `srcDir` of any layers)" |
| `experimental.inlineRouteRules` | `defineRouteRules` | 该页标注：要用必须在配置里开 `experimental.inlineRouteRules` |
| `future.compatibilityVersion: 5` | 十九项默认（含 6 个 `experimental.*`、`unhead.legacy`、`postcss.plugins` 默认、`optimization.keyedComposables`） | "Defaults throughout your Nuxt configuration then change… **On Nuxt 4 this covers:**" 那份清单 |
| `compatibilityDate` | Nitro／Nuxt Image／其他模块的 presets 行为 | "used to control the behavior of **presets** in Nitro, Nuxt Image and other modules that may change behavior without a major version bump" |
| `nitro.envPrefix`（默认 `"NUXT_"`） | `runtimeConfig` 的环境变量覆盖 | 两份记载：覆盖句里用的是 `NUXT_` 前缀；默认值 JSON 里写着 `envPrefix: "NUXT_"` |
| `build.analyze` | `analyzeDir` | 默认 `filename` 写成 `"/<rootDir>/.nuxt/analyze/{name}.html"`，与 `analyzeDir` 默认同一目录 |
| `extensions` | 页面文件可用扩展名 | 页面目录那页把"合法扩展名"直接链到 `api/nuxt-config#extensions` |

## 三条值得单独看的链

**第一链：`rootDir` → 一串默认值。** `rootDir` 那节说明句写着"运行 `nuxt ./my-app/` 会把 `rootDir` 设成 `./my-app/` 的绝对路径"，而 `buildDir`、`typesDir`、`analyzeDir`、`serverDir`、`modulesDir`、`vite.cacheDir` 的默认值全是 `"/<rootDir>/…"` 形式。**改根目录会连带挪动这一整串**——这也是为什么"配置没改但产物位置变了"这类问题要先查启动命令的路径参数。

**第二链：`ssr` → 加载屏 → 加载屏的位置与元素。** `ssr: false` 是 `spaLoadingTemplate` 的生效前提，`experimental.spaLoadingTemplateLocation` 决定这块 HTML 渲染在 `#__nuxt` 内部还是旁边，而 `app.spaLoaderTag`（`"div"`）与 `app.spaLoaderAttrs`（`{"id":"__nuxt-loader"}`）决定那个元素本身。**四段记载分在两页三节，文档没有一处把它们并列过。**

**第三链：`future.compatibilityVersion` → `experimental.*` → 具体行为。** 十九项清单里至少六项落在实验开关上（`viteEnvironmentApi`、`extractSerializablePageMeta`、`payloadExtraction`、`navigateToEarlyReturn`、`typedPages`、`routeTypedFetch`），个别实验开关那节又写着"当 `future.compatibilityVersion` 设成 `5` **或更高**时启用，也可以显式开／关"。**方向只有一个：高档位改默认值；单项能不能改回来，文档是按开关分别说的，没有总表。**

## 没连起来的九组

这几处是"看着该有关系，但文档从没写过"的位置。**排查时不要拿它们当依据。**

| 两组东西 | 文档状态 |
| --- | --- |
| `esbuild.options` ↔ `vite.esbuild` ↔ `webpack.loaders.esbuild` | 三份默认值逐字相同，**同步与覆盖规则没写** |
| 顶层 `runtimeConfig` ↔ `nitro.runtimeConfig` | `nitro` 那份默认多一段 `nitro`，**两者关系官方未解释** |
| 顶层 `routeRules` ↔ `nitro.routeRules` | 两处都不列属性，官方示例全用顶层，**谁优先没写** |
| `appId` ↔ `future.multiApp` | 都在讲多应用，**没有任何一句互指** |
| `theme` ↔ `extends` | 说明句几乎同形，**同时写时谁生效、theme 的源算不算图层都没写** |
| `workspaceDir` ↔ `typescript.includeWorkspace` | 两处各讲各的 workspace，**没写是不是同一个目录** |
| `compatibilityDate` ↔ `future` ↔ `experimental` | 三套"控制默认行为"的机制，**没有一处给过优先级或分工表** |
| `spaLoadingTemplateLocation` ↔ `app.spaLoaderAttrs` | 一个管位置、一个管元素属性，**两者叠加后的 DOM 结构没有图示** |
| `imports.global` | 只有类型与默认值，**既没说明句，也没和任何键连起来** |

顺带一条与它同类的形状空白：`vue.propsDestructure` 在配置页默认是 `true`，而入门配置页却把它当"可能需要打开的 Vue 实验特性"来教；`optimization.treeShake` 与 `webpack`/`vite` 的关系也一样，两处从不互指——**同一份配置在两页口径不同，是这套文档的常见形态。**

## 用法：把这张表当排查顺序表

改一个键之前，按这三步走：

1. **在上表里查它是不是某个上游的默认值**。是的话，先确认上游有没有被动过（`rootDir`、`srcDir`、`builder`、`future.compatibilityVersion` 这四个最常牵连）。
2. **查它的生效前提**。例如加载屏相关的三个键，前提句都写着 `ssr: false`；`inlineStyles` 的前提句写的是构建器。
3. **落在"没连起来的九组"里时，不要推断**：把两处都写一遍跑一次，用构建产物与运行结果来定，而不是按名字猜优先级。

## 自查

- **十四条**带原句的因果链已逐条列出；**九组**看着相关但文档没连的位置也逐条列出。
- 牵连最广的四个上游：`rootDir`、`srcDir`、`builder`／`server.builder`、`future.compatibilityVersion`。
- 有生效前提的三个键：`spaLoadingTemplate`、`spaLoadingTemplateLocation`（都限定 `ssr: false`）、`features.inlineStyles`（限定 Vite）。
- 文档没有全局关系图；**所有跨节推断都必须实测**。
