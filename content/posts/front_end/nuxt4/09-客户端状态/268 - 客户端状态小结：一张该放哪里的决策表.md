新手面对"这段数据放哪儿"会有选择困难：ref 不行吗？全局变量不行吗？localStorage 呢？250-269 写到这里，其实答案的一条主轴已经浮出来了：**按"这个状态要在多大范围内活多久"来选容器，而不是按哪个 API 最熟。** 这篇把这一路收成一张表，动笔前先查它。

## 先问存活范围

useState 那页的定位句，把它的边界写得最清楚：

> [`useState`] is an SSR-friendly [`ref`] replacement. Its value will be preserved after server-side rendering (during client-side hydration) and shared across all components using a unique key.

关键词是 "during client-side hydration"——它保证的是**服务端渲染出来的值、在浏览器水合时接得上**，并且"同一次加载里、跨所有组件共享"。注意这句话里**没有**"刷新页面还在""关标签再开还在"——那些是 `useCookie`（255）的范围。所以第一个分岔就是：状态只要活"这一次页面加载（含水合）"，还是要活到"跨请求 / 刷新"？

## 决策表

| 你的状态是… | 放这儿 | 依据 / 注意 |
| --- | --- | --- |
| 一次加载内、跨组件共享的 UI 状态（弹层开关、筛选条件、当前颜色） | `useState(key, init)` | state-management：SSR-friendly ref 替代；值须可 JSON 序列化（264） |
| 要活过刷新 / 跨请求的小数据（草稿、偏好、token） | `useCookie` | 明文存 cookie，别放密钥；跨水合另论（255/257） |
| 会话 / 登录态 | 加密封装的 cookie（`nuxt-auth-utils` 之类） | 不是内存变量；服务端 `requireUserSession` 才护数据（259） |
| 前端要读、可响应式、构建期就定死的配置 | `app.config` + `useAppConfig`/`updateAppConfig` | 进客户端包，禁密钥；update 是深合并（265/266） |
| 部署后才能改、或含密钥的配置 | `runtimeConfig`（私有键 / `public`） | 私有只服务端可读；`NUXT_` 环境变量运行时覆盖（265） |
| 服务端取的、客户端导航时想复用的数据 | `useFetch`/`useAsyncData` 带显式 key，用 `useNuxtData` 读缓存 | 它进 payload；hydrate-never 组件可用开关剔出（267） |

一个提醒：这张表里"内存 ref"那一栏是空的——**模块级 `ref` / `export myState = ref({})` 恰恰是不该选的**。官方 state-management 的 best practice 把这条写成了 warning：

> Never define `const state = ref()` outside of `<script setup>` or `setup()` function.
> For example, doing `export myState = ref({})` would result in state shared across requests on the server and can lead to memory leaks.

它给的替代写法是 `const useX = () => useState('x')`——把状态收进函数、用 `useState` 承接。这就是 250 那一篇讲的"服务端共享实例串数据"的根因。

## localStorage 为什么不在表里

这是新手最常脱口而出的方案："那我存 localStorage 不就刷新还在？"问题在于它**只在浏览器存在**：服务端渲染时根本没有 `localStorage`，服务端读它是 `undefined`、浏览器读它有值——同一个组件两端读到不同的东西，就撞水合不匹配（263、264 一路的那个隐患）。要跨请求又两端一致地活，官方给的位置是 cookie（`useCookie`），不是 localStorage。localStorage 只在"纯客户端、且不参与 SSR 渲染"的场景才安全，那种场景也别当状态管理主力。

## 初始化：异步数据进 useState 用 callOnce

表里第一行"一次加载内共享"有个常见需求：状态初始值要靠异步接口拿。state-management 的 "Initializing State" 给的官方配方是 `useState` + `callOnce`：

```vue [app/app.vue]
<script setup lang="ts">
const websiteConfig = useState('config')

await callOnce(async () => {
  websiteConfig.value = await $fetch('https://my-cms.com/api/website-config')
})
</script>
```

`callOnce` 保证这段只跑一次、且结果进 payload、水合时不重复调用（262 讲过这三个出口的分界）。官方还点了句历史对照："This is similar to the `nuxtServerInit` action in Nuxt 2"——想给 store 填服务端初始状态的旧写法，对应到这套就是这个配方。

## 官方不替你选状态库

如果你需要比 `useState` 更结构化的全局状态（模块化的 store、devtools 时间旅行等），Nuxt 官方不站队。state-management 那句：

> Nuxt is not opinionated about state management, so feel free to choose the right solution for your needs.

它列的官方集成方向是 [Pinia](官方 Vue 推荐)、[Harlem](不可变)、[XState](状态机)，并说明 "Nuxt **used to rely** on the Vuex library"——Nuxt 2 迁过来的看迁移指南。用 Pinia 时的初始化和 `callOnce` 也接得上，官方示例是 `await callOnce(website.fetch)`。这张表到此为止覆盖的是 Nuxt 自带的原生容器；引入状态库是你在这之上的选择，不属于"必须"。

## 自查（收尾）

- 这个状态到底要活多久？活不过"这一次加载"→ useState；要活过刷新 → cookie；是配置 → 两个 config 容器；是密钥 → runtimeConfig 私有键。
- 有没有在 `<script setup>` 外面定义 ref、或者 `export` 一个 ref？按官方 warning 收进 `useState`。
- 有没有拿 localStorage 当跨水合状态？换成 `useCookie`。
- 需要更强的全局状态时，是你在 Pinia/Harlem/XState 之间主动选，而不是 Nuxt 默认给你塞了一个。
