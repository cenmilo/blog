从 250-269 开始讲状态。第一篇先解决一件事：**为什么"在文件最上面放一个 ref"这种在纯前端项目里最自然的做法，在有服务端的框架里会出事故。**

## 官方那条 warning 就是答案

这一节 Best Practices 小节的原文（连格式都照它给的）：

> Never define `const state = ref()` outside of `<script setup>` or `setup()` function.
> For example, doing `export myState = ref({})` would result in state shared across requests on the server and can lead to memory leaks.

配套那句替代写法也很短：

> Instead use `const useX = () => useState('x')`

我把这两句合起来读，规则是：**共享状态要挂在一个"每次请求都会重新创建的东西"上，而不是挂在模块上。**

## 为什么模块级 ref 会跨请求

官方没有在这一节展开原理，但在生命周期那一节给了足够的前提：

> The Vue and Nuxt instances are created first. Afterward, Nuxt executes its app plugins.

这条出现在"服务端对**每一次初始请求**执行的步骤"清单里（232 抄过整串）。也就是说**每个请求都会新建一次应用实例、重跑插件**——而 `app/plugins/` 里写的"每次请求都跑"这件事，恰恰说明服务端进程是**被复用的**。

于是两类东西的生命周期不是一回事：

| 东西 | 活多久 | 谁看得见 |
| --- | --- | --- |
| 模块顶层的 `const state = ref()` | 进程存活期间 | **所有请求**（同进程内共享） |
| `setup()` 里的 `const state = ref()` | 一次组件实例 | 该实例 |
| `useState('key', ...)` | 一次请求的应用实例 + payload 里的那份 | 本次 SSR 与它水合出来的客户端；同请求内跨组件共享 |

第三行是 `useState` 存在的理由，官方两句定位：

> [`useState`] is an SSR-friendly [`ref`] replacement. Its value will be preserved after server-side rendering (during client-side hydration) and shared across all components using a unique key.

"用唯一 key 在所有组件之间共享"这句正好对上 215 讲的 key 语义：**key 决定的是归属，而归属的单位是一次加载（一个 payload），不是一个进程。**

## 序列化是另一条硬边界

这一节和 `useState` 那一节都挂了同一条 important：

> Because the data inside [`useState`] will be serialized to JSON, it is important that it does not contain anything that cannot be serialized, such as classes, functions or symbols.

**三类东西不能放进去：类实例、函数、symbol。** 官方给的失败症状是一个具体报错，252 会连它的解法一起讲。

顺带一句 235 记过的差别：payload 本身用的是 `devalue`（能带 `Date`、`Map`、`ref` 等），而这两节对 `useState` 的说法是 "serialized to JSON"。**两处口径不同**，我的处理是按最严的写（类实例/函数/symbol 一律不放），并在需要复杂类型时走自定义序列化。

## 三块官方示例分别对应三种需求

### 一，组件间共享一个计数

```vue [app/app.vue]
<script setup lang="ts">
const counter = useState('counter', () => Math.round(Math.random() * 1000))
</script>

<template>
  <div>
    Counter: {{ counter }}
    <button @click="counter++">
      +
    </button>
  </div>
</template>
```

官方说明："In this example, we use a component-local counter state. **Any other component that uses `useState('counter')` shares the same reactive state.**" —— 共享的范围由 key 字符串决定。

### 二，用异步数据初始化全局状态

> Most of the time, you will want to initialize your state with data that resolves asynchronously. You can use the [`app.vue`] component with the [`callOnce`] util to do so.

```vue [app/app.vue]
<script setup lang="ts">
const websiteConfig = useState('config')

await callOnce(async () => {
  websiteConfig.value = await $fetch('https://my-cms.com/api/website-config')
})
</script>
```

官方给了一句历史对照（tip）："This is similar to the `nuxtServerInit` action in Nuxt 2, which allows filling the initial state of your store server-side before rendering the page."

这个组合我在 230 已经拆过：**`callOnce` 保证只跑一次（并且不返回任何东西），`useState` 保证结果能跨水合活着**。两者缺一都会出问题——只用 `callOnce` 会把值存在局部变量里，水合后是空的；只用 `useState` 不包 `callOnce`，就是服务端一次、客户端一次。

### 三，配 Pinia 模块

```ts [app/stores/website.ts]
export const useWebsiteStore = defineStore('websiteStore', {
  state: () => ({
    name: '',
    description: '',
  }),
  actions: {
    async fetch () {
      const infos = await $fetch('https://api.nuxt.com/modules/pinia')

      this.name = infos.name
      this.description = infos.description
    },
  },
})
```

```vue [app/app.vue]
<script setup lang="ts">
const website = useWebsiteStore()

await callOnce(website.fetch)
</script>
```

注意 `state: () => ({...})` **也是工厂写法**——和 `useState` 的 `init`、`default` 是同一个理由（每个实例求一次值）。安装方式官方单独用 important 提示："Make sure to install the Pinia module with `npx nuxt module add pinia`..."（模块添加的机制在 045）。

而 210 那条"别在 handler 里放副作用"的分界，在这一节有了正面写法：**action 由 `callOnce` 调，而不是塞进 `useAsyncData`**（官方在 data-fetching 那一节的 note 里明说"not triggering side effects like calling Pinia actions"，并给了 ❌ 例子）。

## 包装成一个 composable 是官方推荐的共享方式

Shared State 一节整段：

> By using [auto-imported composables] we can define global type-safe states and import them across the app.

```ts [composables/states.ts]
export const useColor = () => useState<string>('color', () => 'pink')
```

```vue [app/app.vue]
<script setup lang="ts">
const color = useColor() // Same as useState('color')
</script>
```

那句注释 "Same as `useState('color')`" 是官方自己点破的等价关系：**包装函数只是把 key 与类型固定下来，共享机制完全靠 key**。这也回答了 250 开头那条 tip 为什么够用——`const useX = () => useState('x')` 里没有模块级状态，**导出的是函数**。

## 官方对状态库的立场

> Nuxt **used to rely** on the Vuex library to provide global state management. If you are migrating from Nuxt 2, please head to the migration guide.
>
> Nuxt is not opinionated about state management, so feel free to choose the right solution for your needs. There are multiple integrations with the most popular state management libraries, including:
> - [Pinia] - the official Vue recommendation
> - [Harlem] - immutable global state management
> - [XState] - state machine approach with tools for visualizing and testing your state logic

我读到的取舍建议其实就藏在三个描述句里：**要官方 Vue 推荐的就 Pinia，要不可变状态的是 Harlem，要状态机与可视化的是 XState**。Nuxt 本身只保证 `useState` 这一条最小通路。

## 自查

1. `export const myState = ref({})` 为什么危险？（答：官方说它会造成"服务端跨请求共享状态"并可能导致内存泄漏，因为模块作用域的生命周期跟进程而不是跟一次请求。）
2. `useState` 的 key 与 `setup` 里的局部 `ref`，共享范围各是什么？（答：前者在同一个 key 下跨组件共享、并随 payload 跨水合保留；后者只在单个组件实例内。）
3. 哪些值不能放进 `useState`，为什么？（答：类实例、函数、symbol——它的内容要被序列化成 JSON。）
