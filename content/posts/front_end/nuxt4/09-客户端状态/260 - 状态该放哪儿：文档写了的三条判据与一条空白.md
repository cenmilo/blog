You can use the `app.vue` component with the `callOnce` util to do so."），而构建期就定的东西属于 `app.config`（055/073 讲过它不进运行时）。**剩下两个问题文档口径不一致或干脆没写**：一是"要不要用状态库"——官方明确不站队（"Nuxt is not opinionated about state management, so feel free to choose the right solution for your needs."）并列了 Pinia/Harlem/XState 三个模块，同时提醒 Nuxt "**used to rely** on the Vuex library"；二是 **`localStorage` 既没被推荐也没被禁用**——整套 4.x 语料里它只出现在两处：hydration 页把它当错配成因（"`localStorage` doesn't exist on the server!"）并给 `useCookie` 作解法，以及 `useFetch` 拦截器示例里的一次写入，**没有任何一句"可以用它存状态"或"不要用它存状态"**，所以我按空白处理，不引用旧文档里那句早已不在 4.x 的说法。

这一篇我只做一件事：**把"放哪儿"这个问题拆成文档真的回答过的部分和没回答的部分**。以前我按 Nuxt 2 的习惯想这件事，那套说法在 4.x 文档里找不到依据。

## 三条判据（都有原话）

| 这个值… | 放哪儿 | 官方依据 |
| --- | --- | --- |
| 只在一次加载里跨组件共享 | `useState` | "Nuxt provides the `useState` composable to create a reactive and SSR-friendly shared state across components." |
| 要跨请求活着（偏好、会话） | `useCookie` | "useCookie is an SSR-friendly composable to read and write cookies." |
| 服务端算出来、给首屏用 | `callOnce` + `useState` | "You can use the `app.vue` component with the `callOnce` util to do so." |
| 构建期就定死、只读 | `app.config` | 055/073 讲过的定位（它不是运行时可写的状态） |
| 需要被 URL 分享/刷新保留 | 路由 query | 见下一节 |

反向判据也有一条，是这一页最硬的 warning（250 抄过全句）：**别在 `setup` 外面定义 `ref`**——那会让状态跨请求共享。

## 路由 query：文档没叫你把状态放那儿，但机制支持

我翻完相关三页后的结论是：**"筛选状态放 URL"是一条社区惯例，不是 Nuxt 文档的推荐**——没有任何一句写"应该把状态放进 query"。但机制侧的记载是完整的，三条：

1. **query 能直接驱动取数**：`useFetch` 的 `query` 收响应式值，"Nuxt will automatically use the reactive value and re-fetch each time it changes."（239）
2. **参数能被校验**：`definePageMeta` 的 `validate`（返回 false 就是 404，111 讲过），所以脏参数有官方出口。
3. **query 会离开你的掌控**：官方在两个不同场景都写过同一句风险——服务端组件把 props 转成 GET query 时点名 "visible in logs/CDN/Referer"（170），`navigateTo`/外部跳转那节也提醒查询串可能被带出去（126）。

所以我的取舍是：**分页、排序、搜索词这类"可分享、无隐私"的放 query；带身份或敏感参数的不要放**——后半句是我按那两句风险推的判据，官方没写成规则。

## 状态库：官方只说"不站队"

> Nuxt is not opinionated about state management, so feel free to choose the right solution for your needs. There are multiple integrations with the most popular state management libraries, including:
> - Pinia - the official Vue recommendation
> - Harlem - immutable global state management
> - XState - state machine approach with tools for visualizing and testing your state logic

同节还有一句历史说明，值得知道免得照旧文写：**"Nuxt used to rely on the Vuex library to provide global state management."**，迁移去 `migration/configuration#vuex` 那页（070 系列里我没重引它）。

三个库的描述句本身就是选型依据：**要官方 Vue 的推荐路线选 Pinia，要不可变状态选 Harlem，要状态机与可视化测试选 XState**。除此之外官方没给比较表，我不会自己编一张。

用了状态库之后，取数那侧的分界仍然生效（254）：**store 的 action 不放进 `useAsyncData` 的 handler**，官方给的形状是 `callOnce(website.fetch)`。

## 那条空白：localStorage 在 4.x 文档里没被评价

我原以为文档里有"别用 localStorage 存响应式状态"这种句子，找了一遍没有。全库里 `localStorage` 只出现在两处，且都不是选型建议：

| 出现处 | 上下文 | 官方给的处理 |
| --- | --- | --- |
| `guide/best-practices/hydration` | 作为水合错配的第一类成因示例：`const userTheme = localStorage.getItem('theme') \|\| 'light'`，注释 "localStorage doesn't exist on the server!" | 换 `useCookie`："This works on both server and client" |
| `api/composables/use-fetch` | 拦截器示例里 `onResponse` 中 `localStorage.setItem('token', ...)` | 无（221 里我明确说这处不能照抄） |

**所以我能诚实说的只有**：文档从没说"可以用它存状态"，也从没说"禁止"；唯一成文的信号是——**在服务端会跑到的代码里读它会制造水合错配，而官方给那个场景的替代是 `useCookie`**。至于"隐私模式/容量上限"那类理由，我在 4.x 这几页里没找到，不写进结论。

要自己下判断的话，我建议按三条实测：

1. 这个值需要服务端看见吗？需要 ⇒ `useCookie`（服务端读得到，255）。
2. 它会被水合期读到吗？会 ⇒ 别在 `<script setup>` 顶层读它（199 那张表）。
3. 它要跨设备吗？要 ⇒ 都不适合，那是账号数据（官方会话配方的说法是"不用为会话建数据库"，但用户资料类数据仍是服务端的事，259）。

## 自查

1. 官方对状态管理库的立场原话是哪句？（答："Nuxt is not opinionated about state management, so feel free to choose the right solution for your needs."）
2. `localStorage` 在 4.x 文档里被推荐或被禁用了吗？（答：都没有；只出现在水合错配成因与 `useFetch` 拦截器示例里，前者给的替代是 `useCookie`。）
3. 一次性初始化为什么用 `callOnce` + `useState` 而不是 `useAsyncData`？（答：action/写状态属副作用，官方说 `useAsyncData` 是取数与缓存、不用于触发副作用；`useState` 负责让值跨水合活着。）
