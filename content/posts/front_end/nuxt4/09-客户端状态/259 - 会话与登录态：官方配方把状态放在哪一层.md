新手最容易把登录态想成一个"存在内存里的变量"：登录成功就把 `user` 塞进某个全局 ref，然后到处读。在 Nuxt 里这个做法会同时踩两个雷——服务端每个请求共享同一个实例（250 篇讲过），而且刷新页面就没了。官方那份 Sessions and Authentication 配方给出的答案完全不同：**登录态不是内存变量，是一个加密封装的 cookie**，谁读都从这一个地方读。

## 登录态存在哪儿：加密封装的 cookie

配方用的是 `nuxt-auth-utils` 这个模块。它的一句话定位是：

> The module uses secured & sealed cookies to store session data, so you don't need to setup a database to store session data.

拆开看两件事。第一，会话数据不放在服务端内存、也不放数据库，而是放在 cookie 里——所以它是"跨请求"的，刷新、换设备重启浏览器都还在。第二，这个 cookie 是 "secured & sealed"（加密封装）的，加解密用一把密钥，来自环境变量 `NUXT_SESSION_PASSWORD`：

> session cookies are encrypted using a secret key from the `NUXT_SESSION_PASSWORD` environment variable.

开发环境你没设它，它会被自动加进 `.env`；但官方有一句 important 直接提醒你部署前必须自己在生产环境补上：

> You'll need to add this environment variable to your production environment before deploying.

这把密钥和上一批 `useCookie`（255）里普通 cookie 的关系是这样的：普通 `useCookie` 存的是明文（JSON 序列化），而这里的会话 cookie 是被模块加密后再放进浏览器的。你自己用 `useCookie` 存 token 时要记住——那玩意儿在浏览器 DevTools 里是能看到的（除非你设 `httpOnly`，见 255 选项表）。

## 登录：服务端往会话里写，客户端只管提交表单

配方的登录接口是一个服务端 handler，用 `setUserSession` 把用户写进会话 cookie：

```ts [server/api/login.post.ts]
export default defineEventHandler(async (event) => {
  const { email, password } = await readValidatedBody(event, bodySchema.parse)

  if (email === 'admin@admin.com' && password === 'iamtheadmin') {
    // 把用户会话写进 cookie，这个服务端工具由 auth-utils 模块自动导入
    await setUserSession(event, {
      user: {
        name: 'John Doe',
      },
    })
    return {}
  }
  throw createError({
    status: 401,
    message: 'Bad credentials',
  })
})
```

登录页拿到成功之后，做的不是"把 user 存进本地变量"，而是**让客户端重新读一遍会话**再跳转：

```ts
const { loggedIn, user, fetch: refreshSession } = useUserSession()
// 提交 /api/login 成功后
await refreshSession()   // Refresh the session on client-side
await navigateTo('/')
```

这里 `useUserSession()` 返回的成员（`loggedIn, session, user, clear, fetch`）就是"读同一个会话"的统一入口。服务端 `setUserSession` 写、客户端 `useUserSession` 读，中间靠那枚加密 cookie 传递——没有一个环节是内存 ref。

## 守接口：服务端 requireUserSession

配方的"Protect API Routes"一节写了一句最容易被新手跳过的话，原文我原样放在这里，因为它是整个配方的安全基石：

> Protecting server routes is key to making sure your data is safe. Client-side middleware is helpful for the user, but without server-side protection your data can still be accessed.

也就是说：**你写在客户端路由中间件里的登录判断，只是给用户看的体验，不是数据保护**。真正的数据接口必须自己挡。模块提供了 `requireUserSession`：

```ts [server/api/user/stats.get.ts]
export default defineEventHandler(async (event) => {
  // 请求没有有效会话时这里直接抛 401
  const { user } = await requireUserSession(event)
  return {}
})
```

## 守页面：客户端中间件 + definePageMeta

数据安全靠上面那层，但体验上你不希望未登录用户看到一堆空数据或报错，于是配方再补一层客户端路由中间件：

```typescript [app/middleware/authenticated.ts]
export default defineNuxtRouteMiddleware(() => {
  const { loggedIn } = useUserSession()
  if (!loggedIn.value) {
    return navigateTo('/login')
  }
})
```

这一节有两句限定要一起读。第一句是官方对客户端中间件作用范围的提醒：

> Unlike on the server, client-side middleware is not automatically applied to all endpoints, and we'll need to specify where we want it applied.

第二句是"指定到哪儿"的具体做法——在页面里用 `definePageMeta` 点名这个中间件：

```vue [app/pages/index.vue]
<script setup lang="ts">
definePageMeta({
  middleware: ['authenticated'],
})
</script>
```

## 哪一层放什么

把这四段按"状态在哪"重新拼一遍，就是这个配方的核心结论：

| 要放的东西 | 放哪一层 | 官方用什么 |
| --- | --- | --- |
| 会话本体（用户是谁） | 加密封装的 cookie | `setUserSession`（写）、`requireUserSession`（服务端校验） |
| 读当前登录状态 | 组件/中间件里统一入口 | `useUserSession()` 的 `loggedIn/user` |
| 接口数据保护 | 服务端 handler | `requireUserSession(event)`，无会话抛 401 |
| 页面访问体验 | 客户端路由中间件 | `defineNuxtRouteMiddleware` + 页面 `definePageMeta` |

对照 250-262 那条主线：`useState` 管的是"一次加载内的共享状态"，cookie 管的是"跨请求"。登录态属于后者——它必须活过刷新，所以官方把它放进 cookie，而不是 `useState`。

## 自查

- 我是不是把登录态写成了模块级 `ref`？如果是，服务端会串用户、刷新会丢，得改成会话 cookie。
- 敏感接口有没有在服务端 `requireUserSession`？只有客户端中间件拦截 ≠ 数据安全。
- 客户端中间件是"不自动作用到所有端点"的，要保护的页面有没有各自用 `definePageMeta` 点名？
- `NUXT_SESSION_PASSWORD` 在生产环境有没有自己设上？
