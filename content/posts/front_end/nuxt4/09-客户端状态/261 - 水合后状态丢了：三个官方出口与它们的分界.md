  摘要：症状很统一：服务端算出来的东西，浏览器接手后变成空的或不一样。这一篇把官方给的三个出口摆在一起，因为它们解决的是同一段路上的三个不同问题。**出口一 `useState`**——定位句是 "Its value will be preserved after server-side rendering (during client-side hydration) and shared across all components using a unique key."，它管的是"一次加载内的共享状态"。**出口二 `callOnce`**——note 里连机制都写了："`callOnce` is a composable meant to be called directly in a setup function, plugin, or route middleware, **because it needs to add data to the Nuxt payload to avoid re-calling the function on the client when the page hydrates**."，它管的是"这段代码别在水合时再跑一遍"，而且明确 "doesn't return anything"。**出口三 `useHydration`**——定位句 "Allows full control of the hydration cycle to set and receive data from the server."，官方同时限定它是 "an advanced composable, primarily designed for use within plugins, mostly used by Nuxt modules."，并把"要全局响应式状态"的需求推给 `useState`：「`useHydration` is designed to **ensure state synchronization and restoration during SSR**. If you need to create a globally reactive state that is SSR-friendly in Nuxt, `useState` is the recommended choice.」。第四个选项其实是 `useCookie`（255），它管的是"跨请求"而不是"跨水合"。**还有一处空白必须说**：236 的 `purgeCachedData` 说明只点名 `useAsyncData` 与 `nuxtApp.static.data`，**没有任何一句说 `useState` 的值存在哪个对象、会不会被路由跳转清掉**，只有一句错误码侧的 "identifies the shared state across the app and in the hydration payload"（E7009）。

先把这条路画出来，三个出口分别站在不同位置：

```
服务端跑 setup ──► 渲染 HTML ──► 浏览器拿到 HTML ──► 水合：再跑一次 setup
                                  └── payload 带过去的数据
```

**"状态丢了"永远是这一句话**：第二次跑 setup 时，没有东西把第一次的结果交给它。

## 出口一：useState（最常见的那个）

官方两句定位：

> Nuxt provides the `useState` composable to create a reactive and SSR-friendly shared state across components.
> [`useState`] is an SSR-friendly [`ref`] replacement. Its value will be preserved after server-side rendering (during client-side hydration) and shared across all components using a unique key.

它给的是**响应式 + 跨水合 + 跨组件**，代价是寿命只到一次加载（250/260），以及那条序列化边界（类实例、函数、symbol 不放，251）。这也是 254 那个 `callOnce` + `useState` 组合的由来：

```vue [app/app.vue]
<script setup lang="ts">
const websiteConfig = useState('config')

await callOnce(async () => {
  websiteConfig.value = await $fetch('https://my-cms.com/api/website-config')
})
</script>
```

## 出口二：callOnce（问题不是"值丢了"，是"又跑了一遍"）

它的 note 把机制说得很直白：

> `callOnce` is a composable meant to be called directly in a setup function, plugin, or route middleware, because it needs to add data to the Nuxt payload to avoid re-calling the function on the client when the page hydrates.

所以它管的是**执行次数**，不管响应式。两个限制连在一起读才不会用错：

- "The default mode of `callOnce` is to run code only once. For example, **if the code runs on the server it won't run again on the client.**"
- **"Note that `callOnce` doesn't return anything."** You should use `useAsyncData` or `useFetch` if you want to do data fetching during SSR."

**这就是 230 那条分界的另一面**：想要"取数并把结果给模板用"，那是 `useAsyncData` 的活（它会缓存进 payload 并返回 `data`）；想要"这件事只做一次"，才轮到 `callOnce`，而值要靠别的容器（`useState`、store）承载。

## 出口三：useHydration（自己接管那一次传递）

定位句是 "Allows full control of the hydration cycle to set and receive data from the server."，用法上官方限定得比前两个都窄：

> This is an advanced composable, primarily designed for use within plugins, mostly used by Nuxt modules.

并且官方主动把常见需求指走：

> `useHydration` is designed to **ensure state synchronization and restoration during SSR**. If you need to create a globally reactive state that is SSR-friendly in Nuxt, `useState` is the recommended choice.

它到底做了什么，看官方那对示例最清楚（左边是它，右边是"不用它时你要自己写的两段钩子"）：

```ts [With useHydration]
export default defineNuxtPlugin((nuxtApp) => {
  const myStore = new MyStore()

  useHydration(
    'myStoreState',
    () => myStore.getState(),
    data => myStore.setState(data),
  )
})
```

```ts [Without useHydration]
export default defineNuxtPlugin((nuxtApp) => {
  const myStore = new MyStore()

  if (import.meta.server) {
    nuxt.hooks.hook('app:rendered', () => {
      nuxtApp.payload.myStoreState = myStore.getState()
    })
  }

  if (import.meta.client) {
    nuxt.hooks.hook('app:created', () => {
      myStore.setState(nuxtApp.payload.myStoreState)
    })
  }
})
```

**这张对照告诉我的本质是：`useHydration` 把"服务端在 `app:rendered` 写 payload、客户端在 `app:created` 读 payload"这一对时序收成一个调用。**所以真正要选它的场景是：**你已经有一个自己的 store 实例（非响应式对象），它不会自己进 payload**。262 细讲这对时序与它的所有约束。

## 三个出口的分界

| 我的问题 | 选 | 不选另一个的理由（官方句） |
| --- | --- | --- |
| 一次加载内跨组件共享响应式值 | `useState` | `useHydration` 那页明说这种需求推荐 `useState` |
| 某段代码不要在水合时再执行一遍 | `callOnce` | 它不返回值，也不管响应式 |
| 首屏要渲染这份数据 | `useAsyncData`/`useFetch` | `callOnce` 不返回任何东西 |
| 我自己的非响应式 store 要跨水合 | `useHydration` | 官方定位：advanced、主要在插件/模块里 |
| 值要活过刷新、要让服务端看见 | `useCookie` | 前四个都只在一次加载内 |

## 一处空白：状态存在哪、活多久，没写

`useState` 那页只说值会被 "preserved after server-side rendering"，E7009 补了一句 key "identifies the shared state across the app **and in the hydration payload**"——**能确认的只有"它进 payload"**。而 236 的清理机制说明是这么写的：

> Nuxt will automatically purge cached data from `useAsyncData` and `nuxtApp.static.data`.

**这份名单里没有 `useState`**。所以两个问题文档没答：状态是不是存在 `nuxtApp.static.data`、路由跳转会不会清它。我的测法（十分钟）：

1. 页面 A `useState('x', () => ({ hits: 0 }))`，把它 +1。
2. `navigateTo('/b')` 再回到 A，读 `x.value.hits`。
3. 同一个实验在 `experimental.purgeCachedData: false` 下重复一次，比较结果。

在结果出来之前，我不会把"状态会自动清掉"或"会一直留着"当成设计前提——**这两个假设都容易在改版时炸**。

## 自查

1. 官方推荐"全局响应式状态"用什么、把 `useHydration` 定位成什么？（答：`useState`；`useHydration` 是 advanced、主要在插件里、多被模块使用。）
2. `callOnce` 为什么能避免水合时重跑？（答：它需要往 Nuxt payload 写数据，所以必须直接在 `setup`、插件或路由中间件里调用。）
3. 值需要活过刷新时，前三个出口为什么都不够？（答：它们都只在一次加载内成立；跨请求要 `useCookie`。）
