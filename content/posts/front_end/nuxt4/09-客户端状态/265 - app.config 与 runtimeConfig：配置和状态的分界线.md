打开一个 Nuxt 项目，你可能会同时看到两个放配置的地方：一个文件叫 `app/app.config.ts`，另一个是 `nuxt.config.ts` 里的 `runtimeConfig` 这一段。名字里都有 config，新手常常分不清该往哪个里写。它们不是新旧版本的关系，是分工不同——一个偏"前端要读的、响应式的应用设置"，一个偏"分公私、能被环境变量在运行时改的配置和密钥"。这一篇把它们一次讲清。

## app.config.ts：响应式的应用配置

app.config 那一页的定位句：

> Expose reactive configuration within your application with the App Config file.

它写成这样，扩展名可以是 `.ts`/`.js`/`.mjs`：

```ts [app/app.config.ts]
export default defineAppConfig({
  theme: {
    primaryColor: '#ababab',
  },
})
```

页面里（以及插件、组合式里）用 `useAppConfig()` 读，服务端渲染时和浏览器里都能读到同一个 `theme`：

```vue [app/pages/index.vue]
<script setup lang="ts">
const appConfig = useAppConfig()
console.log(appConfig.theme)
</script>
```

三个要点：

- 它是**响应式**的——页首那句 "reactive configuration" 就是这个意思，值改了界面会跟着变。具体怎么改（`updateAppConfig`）下一篇讲。
- 它**会进客户端包**，所以那条 caution 要求别放密钥（264 篇已经引用过）："Do not put any secret values inside `app.config` file. It is exposed to the user client bundle."
- 如果你设了自定义 `srcDir`，它得放在那个新 `srcDir` 的根上（note 明写），位置错了读不到。

## runtimeConfig：分公私两半，私有只在服务端

runtimeConfig 写在 `nuxt.config.ts` 里，它把键按"要不要下发给前端"分成两层：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  runtimeConfig: {
    apiSecret: '123',        // 私有：只在服务端可读
    public: {
      apiBase: '/api',       // 公有：服务端和浏览器都能读
    },
  },
})
```

nuxt-config 那一页对它的定位正好和 app.config 相反：

> It mainly should hold *private* configuration which is not exposed on the frontend. This could include a reference to your API secret tokens.
> Anything under `public` and `app` will be exposed to the frontend as well.

读的时候两端表现不同，指南里写得很直白：

> - On client-side, only keys in `runtimeConfig.public` and `runtimeConfig.app` ... are available, and the object is both writable and reactive.
> - On server-side, the entire runtime config is available, but it is read-only to avoid context sharing.

服务端那份"整个 runtimeConfig 可读但只读"的理由是 "to avoid context sharing"——和 250 篇"服务端共享实例会串数据"是同一套顾虑。

## 关键差别：值从哪来

这是两者最容易被忽略的分界。

app.config 是**构建期就定死的**。它打进客户端包，你没法在部署后、不改代码重构建的情况下改它。

runtimeConfig 的价值在于它能在**运行时被环境变量覆盖**。指南原话：

> Runtime config values are **automatically replaced by matching environment variables at runtime**.

覆盖有两个硬性前提：

1. 键要先在 `nuxt.config` 里声明过（"This ensures that arbitrary environment variables are not exposed to your application code."）。
2. 环境变量名字必须是 `NUXT_` 开头、全大写、用下划线表示层级和大小写变化。

```ini [.env]
NUXT_API_SECRET=api_secret_token
NUXT_PUBLIC_API_BASE=https://nuxtjs.org
```

同一个键的公有版本要加 `PUBLIC`：`apiBase` 在 `public` 下，对应环境变量是 `NUXT_PUBLIC_API_BASE`。这一层"声明了才认、命名对上才覆盖"的规则，是 runtimeConfig 独有、app.config 没有的。也正因为这样，部署到不同环境时你可以只改环境变量、不动代码——app.config 做不到。

指南还提醒一句常见坑：把某个键的默认值指向"另一个名字"的环境变量（`myVar: process.env.OTHER_VARIABLE`）只在构建期有效、运行时会失效，因为运行时只认命名对得上的 `NUXT_` 变量。

## 类型谁推、能放什么

两个都做了类型自动推断，但边界不一样：

- **app.config**：Nuxt 会从你写的配置自动推出接口。全推断的类型只在应用代码（组件/组合式/插件）里有效；在服务端路由、`shared/` 和 `nuxt.config` 里，app.config 的键被当成 `unknown`——理由是"那些地方没有应用的自动导入上下文"。要跨边界都有类型，得扩展 `SharedAppConfig`。
- **runtimeConfig**：靠 unjs/untyped 自动生成接口，也能手动 declare `RuntimeConfig` / `PublicRuntimeConfig` 两个接口。

还有一个 app.config 特有的限制，来自它被 Nitro 共享（自 v3.3）：

> 1. You cannot import Vue components directly in `app.config.ts`.
> 2. Some auto-imports are not available in the Nitro context.

官方给的"绕法"（在 nitro 配置里塞 Vite 插件）自己都标了不推荐，说 "may lead to unexpected behavior and bugs"。

## 一句话选择

- 想让前端读一份可响应式、可在运行时随部署环境被改的配置/密钥 → runtimeConfig（私有放顶层、公有的放 `public`）。
- 想让前端读一份构建期就固定、纯给 UI 用的应用设置（主题色、开关列表等） → app.config。
- 任何时候：密钥不往 app.config 放，也不往 `useState` 放（264）。

## 自查

- 我要改的这个值，部署后还需不需要动？需要 → runtimeConfig + `NUXT_` 环境变量；不需要 → app.config。
- 这个值是公有的还是私有的？私有的放 runtimeConfig 顶层，别放 `public`、别放 app.config。
- 用 runtimeConfig 覆盖时，环境变量名对不对得上（大写、`NUXT_` 前缀、`PUBLIC` 对应 public 层），键有没有先在 nuxt.config 里声明？
- 有没有在 app.config 里 import Vue 组件？那条在 Nitro 上下文里不行。
