## 先看一段你屏幕上能翻出来的东西

打开 `/me`，滚到 HTML 最后，有这一段（下面是本轮从产物响应里原样抄回来的）：

```
<script type="application/json" data-nuxt-data="nuxt-app" data-ssr="true" id="__NUXT_DATA__">
[["ShallowReactive",1],{"data":2,"state":4,"once":10,"_errors":11,"serverRendered":13,"path":14},
["ShallowReactive",3],{},["Reactive",5],{"$scurrentUser":6},{"id":7,"email":8,"role":9},
"probe-u","probe@example.com","free",["Set"],["ShallowReactive",12],{},true,"\u002Fme"]
</script>
```

这一串就是所谓**负载**（payload）：服务端渲这一页时顺手写进 HTML 的一份数据，浏览器接手（水合：把这段 HTML 认下来并挂上事件）之后不再重新取一遍。

先标明这一段的来历：它是"让插件写一个人"那一趟抄下来的（后面有一节整节量的就是这次改动），匿名访客在同一格里看到的是 `null`，那一节的最后附着那一份原样读数。

形状值得说清，因为它和多数人的直觉不一样：**这不是一组嵌套对象，而是一张带下标的表**。`"state":4` 说的是"状态那一位在第 4 格"，第 4 格是 `["Reactive",5]`，第 5 格才是 `{"$scurrentUser":6}`。`$s` 是 `useState` 给键加的前缀（依据是装上的那份实现，`node_modules/nuxt/dist/app/composables/state.js` 里 `useStateKeyPrefix = "$s"`），所以第 6 格就是 `useState('currentUser')` 那一位——这一份里它指向一个对象，`id`、`email`、`role` 各自再指向更后面的格子。

## 那一位是谁写的

整个前端里只有一处把它写成一个"人"：

```ts
export default defineNuxtPlugin(() => {
  const event = useRequestEvent()

  useUser().value = (event?.context.user as CurrentUser | undefined) ?? null
})
```

`event.context.user` 是上一站那条服务端中间件挂上去的（`server/middleware/auth.ts`）。这个文件名带 `.server`，讲插件的那一节写得很短：「You can use `.server` or `.client` suffix in the file name to load a plugin only on the server or client side.」

后缀不是风格问题。装上的实现里 `useRequestEvent()` 第一行是 `if (import.meta.client) return;`（`node_modules/nuxt/dist/app/composables/ssr.js:13`）——**客户端调用它拿到的永远是 `undefined`**。所以如果哪天这个文件被改名成 `current-user.ts`，插件在浏览器里也会跑一遍，算出来的是 `undefined ?? null`，于是把负载里带回来的那份刚好的身份**覆盖成 null**。症状是水合之后页面从"显示邮箱"变成"显示未登录"，而服务端发出去的 HTML 是对的。

为什么这件事写在插件里、不写在页面里，上一站已经量过一面：路由中间件跑在页面 setup 之前，身份如果等页面来写，门永远读到初值。这一站补另一面——那一位到底从哪来。

## 页面里读不到初值：把这条规则量出来

`useState(key, init)` 的 `init` 那一节写着：「A function that provides initial value for the state **when not initiated**.」讲状态那一节还有一句：「Its value will be preserved after server-side rendering (during client-side hydration) and shared across all components using a unique key.」

翻译成人话：负载里已经有这一位时，你写的那个初值函数根本不参与。这一层量不出来（端到端那一趟负载总是服务端写好的），所以要靠第二层——不起服务、不连库、但跑真运行时的 `test/nuxt/`。四条读数：

```
[负载·工厂只在缺位时跑] {"inPayloadBefore":false,"value":"来自工厂","inPayloadAfter":true}
[负载·已有那一位] {"value":null,"值是null":true,"工厂跑了吗":false}
[工厂只在缺位时可见] {"删掉之后读到":null,"是null":true,"读完键又回来了":true}
[负载·同一个槽位] {"sameObject":false,"都是ref":true,"从另一处读到的":"slot@example.com","负载里那一位":"slot@example.com"}
```

第二行是这一站的核心：负载里那一位是 `null` 时，`init` 一次都没跑。第三行是把键删掉再读，工厂才显形。第四行说明"两处调用"的关系：`useUser()` 调两次拿到的是**两个 ref 对象**（`sameObject:false`），但它们都指向负载里同一个位置，所以门、页眉、页面读写的其实是同一格——这就是为什么插件写一次，全站都看得见。

还有两条判据盯的是页面本身：

```
[页面只读·无人写过] {"邮箱那段":"未登录","有登出按钮":false}
[页面只读·写过又清掉] {"写过之后":"outside@example.com","清掉之后":"未登录","写过时有按钮":true,"清掉后有按钮":false}
```

"清掉之后"那半句是登出那行 `user.value = null` 的依据：页面显示的不是渲染那一刻抄下来的一份值，改那一位，DOM 立刻跟着变。

## 让插件写一个假身份，看整条链怎么动

前面那些句子都在讲"值从哪来"，这一节把它变成能看到的差别。把插件那句改成写死一个人（临时改动，跑完就还原）：

```ts
  useUser().value = { id: 'probe-u', email: 'probe@example.com', role: 'free' }
```

三份规格一起跑（`E2E_PORT=3218`，仍然没有数据库）：

```
[console gate ssr] {"status":200,"location":"(没有这一位)","bytes":3287,"hasMarker":true,"hasRequestId":true}
[身份负载] {"status":200,"那段脚本在":true,"状态里的键":["$scurrentUser"],"下标":6,"下标在表里":true,"
  解出的值":{"id":7,"email":8,"role":9},"值是严格null":false,"含未登录":false,"登出按钮":true}
[console gate api] {"status":401,"code":"UNAUTHENTICATED"}
[baseline no-js] {"/me":{"status":200,"h1":1,"testids":6,"text":84,"inlineScript":4},
  "/console":{"status":200,"h1":1,"testids":12,"text":105,"inlineScript":4}}
  4 failed / 1 skipped
```

四条结论，一条读数各撑一条。

门真的读的就是这一位：状态从 302 变 200，`hasMarker` 从 `false` 变 `true`，正文从 89 字节涨到 3287 字节。页面那句"这一段只有登录用户才应该看得见"就这样发给了一个匿名访客——这正是上一站那句"门挡的是导航不是数据"的正面证据。

数据面纹丝不动：接口那道门仍然回 401 `UNAUTHENTICATED`。它查的是 cookie 里的会话号，不认负载里这个人。身份写得再漂亮，没有会话就是没有会话。

负载里的形状也换了：那一位不再是 `null`，而是指向一个对象格（`{"id":7,"email":8,"role":9}`），页面上"未登录"消失、登出按钮出现。

改动还原后同一批规格回到 `9 passed`／`1 skipped (27.2s)`（`E2E_PORT=3221` 那一趟），基线读数长这样：

```
[console gate ssr] {"status":302,"location":"/me","bytes":89,"hasMarker":false,"hasRequestId":true}
[身份负载] {"status":200,"那段脚本在":true,"状态里的键":["$scurrentUser"],"下标":6,"下标在表里":true,"解出的值":null,"值是严格null":true,"含未登录":true,"登出按钮":false}
[身份负载·无凭据] {"含sid字样":false,"含sess_字样":false,"含currentUser":true,"去标签后长度":735}
```

## 两种端到端量不出来的坏法

选判据层次的时候，这一站撞到两种"产物档全绿"的改动，都值得记下来。

**改初值工厂。** 把 `useUser()` 里那句改成 `() => ({ id: 'from-factory', email: 'factory@example.com', role: 'free' })`。产物档 6 条判据一条没红（`5 passed`／`1 skipped`），因为负载里那一位是 `null`，工厂根本不跑；同一改动在第二层立刻红：`[工厂只在缺位时可见] {"删掉之后读到":{"id":"from-factory","email":"factory@example.com","role":"free"},"是null":false}`，`1 failed | 5 passed (6)`。

**写 `undefined` 而不是 `null`。** 这一条更有意思：那份判据的注释里原本写着"负载那张表会把 `undefined` 那一位整个丢掉，所以键会消失"。把插件改成写 `undefined` 跑一遍，读数是 `{"下标":6,"下标在表里":true,"解出的值":null,"值是严格null":true}`、`2 passed`——**序列化把 `undefined` 落成了 `null`，键没消失**。那句断言是猜的，猜错了，判据注释随之改写：`?? null` 这一位是靠代码形状守住的，不是靠负载守住的。

两种坏法合起来给出一条选层规则：**凡是"只在没有负载时才生效"的逻辑，初值、降级、默认形状，都归第二层，端到端那一层量不到它。**

## "唯一写入口"那句话，现在有判据守着

插件文件头一直写着"唯一一处"，但仓库里没有任何判据守这句话。三种真实的坏法当时都不会红，所以补了一份静态判据（`test/unit/identity-surface.test.ts`，5 条）：除插件外谁都不许把身份写成对象（只许置空）；插件里只许有一处写入且兜的是 `null`；键名 `currentUser` 只许出现在定义处；前端不许从 cookie 推身份；插件必须带 `.server` 后缀并且被目录扫得到。基线打印：

```
[身份的用处] {"扫到的文件数":15,"用身份的文件":["app/app.vue","app/middleware/console-auth.ts",
  "app/pages/console/index.vue","app/pages/me.vue","app/plugins/current-user.server.ts"],"插件在册":true}
[身份的写入] [{"文件":"app/app.vue","写入":[]},{"文件":"app/middleware/console-auth.ts","写入":[]},
  {"文件":"app/pages/console/index.vue","写入":[]},{"文件":"app/pages/me.vue","写入":["null"]}]
[插件那一行] {"写入次数":1,"右值":"(event?.context.user as CurrentUser | undefined) ?? null","兜的是null":true}
[键名的出处] {"文件":["app/composables/use-user.ts"],"定义处":"app/composables/use-user.ts"}
[cookie 的用处] {"读sid的文件":[],"读csrf的文件":["app/pages/me.vue"],
  "原因":"sid 是 HttpOnly，页面脚本本来就读不到"}
```

第一行那份清单就是"这一位在前端被谁读、被谁写"的全部去处；第四行只有定义处一个文件；最后一行的 `读csrf` 那一项是正对照，说明同一套正则确实能在别处读到东西。

三条变异读数（都是先改坏再跑）：

- 把登出那句改成 `user.value = { id: 'u-x', email: 'self@example.com', role: 'admin' }` → 报 `expected [ { '文件': 'app/pages/me.vue', …(2) } ] to deeply equal []`，`1 failed | 4 passed (5)`。这一改在浏览器里就是"自己造一个身份"，上一站那道门会照样放行——它判的正是这一位。
- 在 `app/app.vue` 里绕过出口再抄一遍键名（`useState('currentUser')`）→ `[键名的出处] {"文件":["app/app.vue","app/composables/use-user.ts"]}`，红。抄第二遍的代价是两处不同步，症状是"服务端明明写了，页面还是未登录"。
- 把 `?? null` 改成兜 `undefined` → 打印变成 `[插件那一行] {"写入次数":1,"右值":"(event?.context.user as CurrentUser | undefined) ?? (undefined as unknown as null)","兜的是null":false}`，红（而产物档那两条照绿，见上一节）。

这份判据第一次跑没踩到新坑，因为它一开始就剥注释再读——上一站那两处假红（注释里的例子字样被当成声明）教的规矩直接用上了。

## 出问题时按这个顺序找

| 症状 | 先看哪一位 | 怎么确认 |
| --- | --- | --- |
| 服务端 HTML 里有邮箱，水合之后变成未登录 | 插件文件名是否还有 `.server` | `ls app/plugins/`，再跑 `test/unit/identity-surface.test.ts` |
| 页面一直显示未登录，接口却是 200 | 那一位有没有被写进去 | 看响应里 `__NUXT_DATA__` 那段第 6 格是什么 |
| 改了初值工厂，行为没变 | 正常，负载里已有那一位 | 跑 `npm run test:nuxt -- identity-source` |
| 匿名访客看到会员区正文 | 身份是不是被别处写成了对象 | `[身份的写入]` 那份点名 |
| 页面与门读的不是同一个人 | 键名被抄了两遍 | `[键名的出处]` 应当只有一处 |

## 你自己站上跑一遍

```
npm run test:unit -- test/unit/identity-surface.test.ts
npm run test:nuxt -- identity-source
E2E_PORT=3217 npm run test:e2e -- --project=site \
  test/e2e/identity-payload.spec.ts test/e2e/console-gate.spec.ts test/e2e/console-baseline.spec.ts
```

预期分别是 `Tests 5 passed (5)`、`Tests 6 passed (6)`、`9 passed / 1 skipped`。跑完单位层那一份，最好把 `[身份的用处]` 那行打印读一遍：它列出的五个文件就是"这一位在前端被谁读、被谁写"的全部清单，多出来的那一个写入者都是要问的。

`1 skipped` 是那条需要真会话的判据。这一站仍然没有可连的数据库，所以"真登录之后负载里长什么样"留给读者：连接串放在 `.env` 里，用你自己的库跑，别把它写进任何会被渲染或提交的文件。

本轮之后：单位层 32 文件／222 条，运行时层 6 文件／20 条，`npm run check` 八项全 ok。仓库里的永久改动是四份判据文件（`test/e2e/identity-payload.spec.ts`、`test/nuxt/identity-source.test.ts`、`test/unit/identity-surface.test.ts` 与上一站的三份仍在），应用代码改过六处、全部还原。
