## 名字一样，跑在两个不同的地方

`app/pages/console/index.vue` 第 5 到 7 行写着：

```vue
definePageMeta({
  middleware: ['console-auth'],
})
```

而 `app/middleware/console-auth.ts` 与 `server/middleware/auth.ts` 这两个文件名里都有 `middleware`，一个在 `app/` 下、一个在 `server/` 下。官方讲这一层的那一节把区别写得很直白：「Route middleware run within the Vue part of your Nuxt app. Despite the similar name, they are completely different from server middleware, which are run in the Nitro server part of your app.」

翻译成这一站的分工：

| 哪一层 | 跑在 | 输入 | 管的是 | 这一站的文件 |
| --- | --- | --- | --- | --- |
| 页面层 | Vue 那一侧，导航之前 | 内存里已经放着的那位身份 | 这次导航落不落到这一页 | `app/middleware/console-auth.ts` |
| 服务端层 | Nitro 那一侧，每个请求开头 | cookie 里那枚会话号 | 这次请求是谁 | `server/middleware/auth.ts` |

## 门里只有五行

```ts
export default defineNuxtRouteMiddleware(() => {
  if (useUser().value) {
    return
  }
  return navigateTo('/me')
})
```

读一位状态，然后放行或跳走。四个新手会撞上的点，官方那一节全有明文。

- 具名中间件不会自动生效。那一节分三种：页面里的匿名中间件、`app/middleware/` 里的具名中间件、文件名带 `.global` 的全局中间件。这一站用第二种，要有页面点名。讲会话的那一节配方一句到位：「client-side middleware is not automatically applied to all endpoints, and we'll need to specify where we want it applied.」
- 没有 `next()`。「a third `next()` argument is not passed, and redirect or route cancellation is handled by returning a value from the middleware」。返回值四种：什么都不返回（放行）、`navigateTo('/')`（重定向，服务端那一趟顺带把状态码定成 302）、带 `redirectCode: 301`、`abortNavigation()`。这一站用前两种。
- 名字归一成 kebab-case：`consoleAuth` 与 `console-auth` 是同一个门，第六节有用。
- 这里读不到"当前路由"。「There is no concept of a "current route" in middleware」，所以 `useRoute()` 在这里永远不准。这一站的门连 `to` 与 `from` 都没用——它判的不是路径。

## 未登录直取这一页，拿到的是什么

会员区那两份端到端规格一起跑（起的是 `nuxt build` 的产物服务，环境里没有数据库）：

```
E2E_PORT=3205 npm run test:e2e -- --project=site \
  test/e2e/console-gate.spec.ts test/e2e/console-baseline.spec.ts
```

```
[console gate ssr] {"status":302,"location":"/me","bytes":89,"hasMarker":false,"hasRequestId":true}
[baseline console route] {"consoleStatus":302,"location":"/me","consoleBytes":89,"hasMarker":false,"meStatus":200}
[console gate followed] {"url":"http://localhost:3205/me","status":200,"text":true}
[console gate api] {"status":401,"code":"UNAUTHENTICATED"}
  7 passed / 1 skipped (27.1s)
```

`bytes` 是 89：重定向那条响应的正文只够装一个跳转提示；`hasMarker` 判的是页面里那句"这一段只有登录用户才应该看得见"在不在响应里，读数是 `false`。`location` 是 `/me` 而不是 `/login`——这一站没有登录页那一支路由，跳去不存在的地址只会让 302 后面再跟一个 404。

`hasRequestId` 是关键的一位：请求号是服务端那层的中间件发的，它出现在响应上，说明**页面那层决定跳转之前，Nitro 侧已经跑过一遍**。第三行是接口那侧的对照，同一个匿名请求打会员区要用的接口拿到 401——页面这道门挡导航，接口那道挡数据，两道各有各的读数。

## 服务端那一层：什么时候一次库都不查

```ts
const sid = getCookie(event, SID_COOKIE)

if (!sid || !useRuntimeConfig().databaseUrl) {
  event.context.user = null
  return
}

event.context.user = await loadSessionUser(sid)
```

这一层只挂身份：不返回响应，也不判权限——"有没有登录"和"能不能做这件事"是两件事，后者归接口里那句 `requireUser()`。`if` 里第二个条件是整套端到端能跑的前提：环境里没有连接串时，带 cookie 的请求不该每个都去连一次库再抛错，而是按"没人登录"处理。

这一层之前一条判据都没有：端到端那趟跑在没配库的机器上，"查了几次"永远是 0，读不出区别。这里补一份单位层判据，把会话服务换成一枚计数器，不起 Nuxt、不连库，三种输入各量一次。

```
[身份·没带号] {"查了几次":0,"挂上的值":"null"}
[身份·没配库] {"查了几次":0,"挂上的值":"null"}
[身份·查成了] {"查了几次":1,"传进去的号":["sess_probe"],"挂的是同一个对象":true}
```

第二条就是那个降级。把 `if` 里那半句删掉复跑，这条立刻红：打印变成 `{"查了几次":1,"挂上的值":"null"}`，报 `AssertionError: expected 1 to be +0`。

另两条钉的是形状：库里没这个人时挂 `null` 而不是 `undefined`（`[身份·查不到] {"挂上的值":"null","挂成了undefined":false}`），中间件自己不返回值（`[身份·返回值] {"匿名":"undefined","有人":"undefined"}`）。必须是 `null`，因为前端那一位的初值就是它——一边 `undefined` 一边 `null`，服务端渲的那份与浏览器接手的那份就不是同一个形状。
## 把门的名字写错一位，会红在哪一层

把 `app/pages/console/index.vue` 第 6 行改成 `middleware: ['console-authx'],`，原命令再跑一次（`E2E_PORT=3211`）。`nuxt build` 一路绿灯、产物服务照常起来，直到有人真的打这一页：

```
[console gate ssr] {"status":500,"location":"(没有这一位)","bytes":2319,"hasMarker":false,"hasRequestId":true}
[console gate followed] {"url":"http://localhost:3211/console","status":500,"text":false}
[console gate api] {"status":401,"code":"UNAUTHENTICATED"}
  2 failed / 1 skipped / 1 passed (27.6s)
```

三件事同时成立。

第一，**构建不查这个名字**，坏处在运行时才露，而失败模式是 500 不是悄悄放行：2319 字节是那一页错误页，`hasMarker` 仍然 `false`，对用户是"整页打不开"，不是"看到了不该看的"。第二行那份对照得清楚：门没坏时落到 `/me` 拿 200，门坏了地址停在 `/console`、状态 500，一步都没多走。

第二，类型检查这一层是查的：

```
app/pages/console/index.vue(6,16): error TS2820: Type '"console-authx"' is not assignable
to type 'NavigationGuard | "console-auth"'. Did you mean '"console-auth"'?
```

`nuxt prepare` 生成的页面类型把 `middleware` 那一位写成"已注册门名"的枚举，所以名字写偏当场报，连建议名都给出来。前提是流水线真的跑它：本站那条聚合命令八项里含 `nuxt typecheck`，只跑构建的那一段拦不住。

第三，接口那位的 401 一个字没变：页面这道门坏了，数据那道照旧。这也是讲会话那一节配方的排序理由——先保住接口（「Protecting server routes is key to making sure your data is safe」），之后才补页面层的门，并且说明补门是为了未登录的人不至于看到一堆残留数据。顺序反过来，数据就只靠一道挡不住人的门。

改回 `['console-auth']` 再跑那两份规格（`E2E_PORT=3210`），回到 `7 passed`／`1 skipped (27.0s)`。

## 更安静的一种坏法：这一页忘了声明

写错名字至少会 500，类型检查也报得出来。**把那一行删掉**才是安静的：`definePageMeta({})` 完全合法，不声明门不是类型错误，`nuxt typecheck` 关于这一页一个字都没提，构建照绿。

端到端那层今天会红，但红的原因是这一页**碰巧**有判据在打它——条件不在规则里。以后在 `app/pages/console/` 下加第二条路由，比如一张报表页，忘了写 `definePageMeta`，没人打那条新地址，仓库里所有判据一条都不会红，而页面会带着会员区那段正文直接回给匿名访客。

这一站的改动因此是三份新判据、十五个用例：

| 文件 | 钉的是什么 |
| --- | --- |
| `test/unit/gate-surface.test.ts` | 会员区目录下每条路由都声明了那道门；声明的门名都在 `app/middleware/` 里注册着；落点是个真页面 |
| `test/unit/console-auth-middleware.test.ts` | 无身份时返回的就是 `navigateTo` 的返回值而非自己拼的字符串；落地参数逐字符是 `/me`；有身份时什么都不返回；两条路各读一次身份，不碰 cookie 也不发请求 |

| `test/unit/session-middleware.test.ts` | 上一节那三条：没带号不查、没配库不查、有号有库恰好查一次 |

名字对账那条与类型检查重叠而非替代：后者要 `nuxt prepare` 走一遍全项目，前者 171 毫秒，只跑单位层的那一档也堵得住。

四条变异读数，都是先把代码改坏再跑：

- 名字写成 `console-authx` → `[名字对不上的声明] {"查了":["app/pages/console/index.vue → console-authx"],"在册的门名":["console-auth"]}`，3 条红。
- 写成合法的驼峰 `consoleAuth` → 声明读出来是 `["console-auth"]`，5 条全绿。归一规则写进判据才是规则，否则合法写法变成假红。
- 把 `return navigateTo('/me')` 改成 `return '/me'` → `[门·未登录] {"返回值是那个哨兵":false,"落地参数":[],"读了身份几次":1}`，2 条红。
- 落点改成 `/login` → 单位层那两条之外，静态那条一起红：`[门的落点] {"读到的目标":"/login","那一页存在":false}`。同一处改坏，两层各查各的。

## 第一次跑，判据红在注释上

那份静态判据第一次跑是 `4 failed | 1 passed (5)`，两处原因都在注释里。`console/index.vue` 第三行的注释照抄了官方例子的写法，含 `middleware: ['auth']`，判据读整个文件，就认为这一页声明的门叫 `auth`；`console-auth.ts` 的注释里写着"不要用 `useRoute()`"，于是"这一层没用当前路由"那条也判成红。两个都是假红。

修法是判据先剥注释再读：块注释、HTML 注释、`//` 之后都清掉，才去找 `middleware:`。**扫的是文件，文件里不只有代码**。

第三处红不在测试里，在类型检查上：

```
test/unit/console-auth-middleware.test.ts(57,24): error TS2352: Conversion of type
'RouteMiddleware' to type '(to: string, from: string) => unknown' may be a mistake
```

单位层不起 Nuxt 运行时，但全项目共用一份生成的类型，那个模块的导出在类型眼里仍是 `RouteMiddleware`。桩换掉的只是运行时，所以要 `as unknown as` 把两头分开。**跑得起来不等于类型也过**，这是两道各自独立的闸门。

## 出问题时按这个顺序找

| 症状 | 先怀疑哪一层 | 怎么确认 |
| --- | --- | --- |
| 拿到 302 但 `location` 不是你要的那页 | 页面层的门 | 看 `navigateTo` 的参数 |
| 打会员区直接 500 | 门的名字没有对应文件 | 跑 `gate-surface` 那份，或列一下 `app/middleware/` |
| 匿名访客能看到会员区正文 | 那一页没声明门 | 看那一页 `definePageMeta` 里有没有 `middleware` |
| 页面过了门、接口还是 401 | 身份没挂上，多半没配库 | 看那个 `if` 的第二条是否命中 |
| 某条用例永远 skip | 环境缺数据库，属正常 | 判据自己写着需要什么 |

## 你自己站上跑一遍

```
npm run test:unit -- test/unit/gate-surface.test.ts \
  test/unit/console-auth-middleware.test.ts test/unit/session-middleware.test.ts
E2E_PORT=3205 npm run test:e2e -- --project=site \
  test/e2e/console-gate.spec.ts test/e2e/console-baseline.spec.ts
```

第一轮预期 `Test Files 3 passed (3)`／`Tests 15 passed (15)`；第二轮预期 `7 passed`／`1 skipped`。端口那位沿用上一线的规矩：Windows 会把 31xx 段发给出站连接，撞上就换一位，别去动别人的进程。

`1 skipped` 那条是「带上一枚有效会话：同一地址回 200，正文里才有那一段」。跳过不等于通过：它需要你自己建的那套库，连接串放在 `.env` 里，别写进任何会被渲染或提交的文件。这一站没有可连的数据库，"真会话能不能过门"因此是留给你的待跑步骤。

本轮之后单位层是 31 文件／217 条，运行时层 5 文件／14 条；仓库里的永久改动只有那三份判据文件，六处变异全部改回原状。
