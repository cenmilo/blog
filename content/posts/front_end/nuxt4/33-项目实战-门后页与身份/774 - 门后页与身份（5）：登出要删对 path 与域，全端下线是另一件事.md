## 症状不是"没删干净"，是"删不掉"

登出这一件事在本仓库里分两半：删掉库里那一行会话，再把浏览器里那两位 cookie 清掉。少做后一半，用户看起来还是登录着——而**后一半最容易出错的地方不是有没有回 `Set-Cookie`，是那一条里的 `Path` 长得对不对**。

cookie 的删除只有一种做法：回一条**同名、同 path、同域**、`Max-Age=0` 的 `Set-Cookie`。所以一枚 cookie 的 path 有两个现场：发它的那一处，和删它的那一处。原来的代码里，这两处各写了一遍字面量：

```ts
const shared = { sameSite: 'lax' as const, path: '/', secure, maxAge: SESSION_MAX_AGE_SEC }
// ……
deleteCookie(event, SID_COOKIE, { path: '/', secure })
deleteCookie(event, CSRF_COOKIE, { path: '/', secure })
```

改的时候只改一边，不会有任何地方报错：浏览器手里那条 cookie 的 path 与清除指令不同，它不归这条指令管，于是好好地留在那里；服务端每个请求都还能读出一个用户，界面上"登出"按钮点下去也确实回到了未登录的样子——**下一次刷新才露出来**。

先立判据，再动代码。判据是一条静态规则：这两个文件里 `path:` 后面不许再出现字符串字面量。它在旧代码上的第一次跑就是红的，并且直接点出现场在哪几行：

```
[path 的现场] {"会话那份":[40,56,57],"state那份":[106,115]}
[第二处字面量] {"offenders":["server/utils/http/session-cookie.ts:40,56,57","server/services/auth/oauth-state.ts:106,115"]}
```

五处，两个文件——OAuth 那对 state cookie 是同一个毛病（发与删各写一遍）。修法是给这一个值一个名字，五个现场全指向它：

```ts
export const SESSION_COOKIE_PATH = '/'
```

改完判据变绿，行为那两条也钉住了同一件事：

```
[path 同源] {"发了几条":2,"删了几条":2,"发出用的path":["/","/"],"清除用的path":["/","/"],"全部同源":true,
  "发出的maxAge":[2592000,2592000],"sid关窗csrf开窗":[true,false],"cookie名":["sid","csrf","sid","csrf"]}
[Secure 两态] {"本地发出的四条secure":[false,false],"本地返回":false,"tls发出":[true,true],"tls返回":true}
```

`cookie名` 那一位是"发哪两枚就得清哪两枚"：漏掉 `csrf` 就是留一枚读得到的旧值在浏览器里；`sid关窗csrf开窗` 是那一对着陆点的另一处细节（上一线量过：页面脚本读得到 `csrf`，读不到 `sid`）。

## 登出那一条响应里到底写了什么

`test/e2e/logout.spec.ts` 第一条不需要库，任何时候都跑。它读的是**原文**：

```
[logout set-cookie] ["sid=; Max-Age=0; Path=/","csrf=; Max-Age=0; Path=/"]
  6 passed / 3 skipped (27.4s)
```

三位各有含义：值为空、`Max-Age=0`、`Path=/`。没有 `Expires` 那一位也够——`Max-Age` 优先，浏览器按它过期。状态码是 200、体是 `{"ok": true}`，而且连打两次同形：**没登录也回 200**，这条幂等不是偷懒，是为了不把一个"登出"变成一个能试探别人会话还在不在的探测点，也为了同一个人开两个标签页时，在 A 里登出之后 B 里那个按钮不会一直报错。

## 这条判据原来是松的

收紧之前先问了一句：把 `SESSION_COOKIE_PATH` 改成 `'/app'`，端到端会红吗？跑出来的答案是**会红，但不是这条判据红的**：

```
[logout set-cookie] ["sid=; Max-Age=0; Path=/app","csrf=; Max-Age=0; Path=/app"]
  3 failed / 3 skipped
```

三条红的都在另一份规格里——`Path=/app` 之后，接口那侧读不到 `csrf` 那一位了（浏览器不再把它发给 `/api/…`）。而 `logout.spec.ts` 里那句 `expect(line).toContain('Path=/')` 从头到尾是绿的：**`Path=/app` 里含有子串 `Path=/`**。子串断言挡住了"漏写属性"，挡不住"写了一个别的值"。

改成按属性边界匹配之后，同一个变异直接把它打红：

```
Error: 这一条的 path 不是单独一位：sid=; Max-Age=0; Path=/app
```

改完复原再跑同一批（`E2E_PORT=3234`）：`6 passed`／`3 skipped (27.4s)`。这条判据本身值一句话：**判据要能被"改 path"这个坏法直接打红**，能被别的判据间接发现不叫守住。

## 顺手量到两条自动导入的边界

这一站的改动撞上了两条规则，都值得记下来，因为它们都会在"看起来无关的一步"上让构建停住。

**其一：services 层看不见这个新常量的自动导入。** 把 `oauth-state.ts` 里两处 path 换成常量之后，`nuxt typecheck` 报 `server/services/auth/oauth-state.ts(119,11): error TS2304: Cannot find name 'SESSION_COOKIE_PATH'`（128 行再一次）。这与 768 那站记的那条是同一族的边界：services 目录能看见项目自己扫进来的名字（比如 `useDb()`），看不见一部分别的名字——要显式 `import`。

**其二，这条是新的：一旦有调用方显式 import 某个 util，那个 util 自己的自动导入就不解了。** 加了那行 import 之后，报错的位置跑到了 `session-cookie.ts` 里，而且是四行：

```
server/utils/http/session-cookie.ts(39,10): error TS2304: Cannot find name 'getRequestProtocol'.
server/utils/http/session-cookie.ts(54,3): error TS2304: Cannot find name 'setCookie'.
server/utils/http/session-cookie.ts(55,3): error TS2304: Cannot find name 'setCookie'.
server/utils/http/session-cookie.ts(62,10): error TS2304: Cannot find name 'getCookie'.
server/utils/http/session-cookie.ts(71,3): error TS2304: Cannot find name 'deleteCookie'.
server/utils/http/session-cookie.ts(72,3): error TS2304: Cannot find name 'deleteCookie'.
```

改法同样直白：这个 util 也显式从 `h3` 引那四个名字。改完 `typecheck` 绿。

**它的连锁后果在判据里**：`session-cookie.ts` 之前用自动导入时，单测把 `setCookie`／`deleteCookie` 挂在 `globalThis` 上就能截住；显式 import 之后真函数被调起来，报的是 `TypeError: Cannot read properties of undefined (reading 'req')`（真 h3 在剥一个假 event）。桩必须换一层——`vi.mock('h3', …)`。**桩要跟着被测代码取名字的方式走**，取法一变，假绿就变成真崩，或者更糟：假绿继续绿着。

## 全端下线是另一件事

后台那条接口删的是**会话行**，一位 cookie 都不动：

```ts
const rows = await useDb().delete(sessions).where(eq(sessions.userId, userId)).returning({ id: sessions.id })
return rows.length
```

两件事的区别只在"下线几台"：登出关自己这一台，全端下线把这个用户的所有会话行一次删掉（一台设备一行）。返回的是删了几行——不先查列表再逐个删，因为逐条删中间崩一次会留下"下了一半线"的状态，而那正是这条接口要消灭的东西。

被下线的设备**不需要收到任何通知**：它手里那枚 cookie 还在、还会照发过来，但服务端按它查不到会话行，于是中间件挂 `null`、接口回 401（770 与 773 量的正是这一路）。这条链上"角色"那位来自登录那一刻的 JOIN，所以这里也不是靠重读角色生效的。

这一节本站只量到接口侧：`[鉴权先于参数]` 那三种非法形状对匿名请求全是 401（上一站读数）。**"删掉 N 行之后旧 sid 换回 401"这一条要真会话**，`logout.spec.ts` 里对应那三条现在是 `3 skipped`——用你自己的库跑（连接串放 `.env`，别写进会被渲染或提交的文件）。

## 出问题时按这个顺序找

| 症状 | 先看哪一位 | 怎么确认 |
| --- | --- | --- |
| 登出后刷新又登录着 | 清除指令的 `Path` 与写入时是否同一个值 | 看 `[logout set-cookie]` 原文与那个常量 |
| 接口读不到 `csrf` | 这一位的 `Path` 是不是被改成了子路径 | `[path 同源]` 的 `清除用的path` |
| 本地浏览器"没存 cookie" | `Secure` 写死了 true | `[Secure 两态]` 应当是 false／true 两态 |
| 单测里桩没生效、直接崩在 h3 | 被测文件改成显式 import 了 | 把桩从 globalThis 换成 mock 那个模块 |
| 全端下线后别人还在线 | 那是登出，只关一台 | 看这条接口删的是行还是 cookie |

## 你自己站上跑一遍

```
npm run test:unit -- test/unit/cookie-path-single-source.test.ts
E2E_PORT=3234 npm run test:e2e -- --project=site \
  test/e2e/logout.spec.ts test/e2e/session-cookie.spec.ts
```

预期 `Tests 4 passed (4)` 与 `6 passed`／`3 skipped`。想验证这一站那条收紧，就把常量临时改成 `'/app'` 再跑第二轮：现在它会红在 `logout.spec.ts` 第一条上，报的正是那句"这一条的 path 不是单独一位"。

本轮之后单位层是 35 文件／236 条，运行时层 6 文件／20 条。仓库里的永久改动是三份：新判据 `test/unit/cookie-path-single-source.test.ts`，`logout.spec.ts` 那一条收紧，以及把 path 收成单一来源（`session-cookie.ts` 导出常量、两处引用；`oauth-state.ts` 显式引它）。
