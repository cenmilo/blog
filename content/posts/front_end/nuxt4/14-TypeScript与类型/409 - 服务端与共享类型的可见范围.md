把接口响应类型写在 `server/types/` 里，页面中直接用就飘红；挪到 `shared/types/` 又突然好了——这不是玄学，是四个类型上下文各自的可见范围。这一篇把它一次讲清。

## 为什么会有"看见/看不见"

官方在 shared 那页给的是 bundle 层面的解释：

> Nuxt builds two separate bundles: the Vue app (client and server-side rendering) and the Nitro server (API routes, server middleware, server plugins). They are bundled independently and run in different contexts.

两个独立 bundle、跑在不同上下文，所以类型也是分上下文的（395 那四份 tsconfig：`tsconfig.app.json`、`tsconfig.node.json`、`tsconfig.server.json`、`tsconfig.shared.json`）。一个类型声明只对引用了它的上下文可见。

## 三个类型目录的可见范围

官方在 "Type-Only Imports" 之后给了明确分配：

> Types that are only used in one context can live next to that context instead: `app/types/` is auto-imported in the Vue app only, and `server/types/` is auto-imported in the Nitro server only. Use `shared/types/` when a type is needed in both.

| 放这里 | 谁能不 import 就用 |
| --- | --- |
| `app/types/` | 只有 Vue 应用侧 |
| `server/types/` | 只有 Nitro 服务端侧 |
| `shared/types/` | app 与 server **两侧都自动导入** |

于是"页面里用不到服务端目录下的类型"是正确行为，不是 bug——要在两端共用，就得放 `shared/types/`。

## `import type` 看着能用，但仍要放对

官方专门拆了"只引类型"这件事，先承认它能过：

> `import type` is erased at compile time and does not pull runtime code into the other bundle, so importing only types across the boundary may appear to work.

紧接着给理由要求仍按目录规矩来：

> Even so, keep shared types (such as API response types) in `shared/types/`, where they are auto-imported in both contexts. This keeps the boundary clear, avoids accidentally turning a type import into a value import later, and matches Nuxt's separate type contexts for app, server, and shared code.

三条理由值得记住：**边界清晰**、**防止日后把类型导入误改成值导入**（那就真违反 `::important` 了）、**与三套类型上下文一致**。所以别拿"`import type` 能用"当把共享类型留在 `server/` 下的借口。

## 硬约束：shared 里不能引 Vue 或 Nitro

shared 那页用 `::important` 定的规矩：

> Code in the `shared/` directory cannot import any Vue or Nitro code.

官方还分别说了两个方向的后果：

- 把组件/composable 引到服务端：它们需要 Vue app 运行时和常常需要 Nuxt 上下文（`useNuxtApp()`、`useRoute()`），Nitro 里都不存在；会引发构建或运行错误，还会把 app 依赖拖进服务端包。
- 把服务端专属代码（Node API、Nitro 工具、服务端路由 handler）引到应用：浏览器里跑不了，会破坏客户端构建、造成运行时错误，或把服务端逻辑泄进客户端包。

顺带版本口径：`::note` 说 `shared/` 目录**从 Nuxt v3.14+ 才有**。

## 服务端侧还有哪些可见性差别

类型可见性之外，运行时的导入面另有规矩（313 那条线）：`nuxt/server` 那套同名工具和 h3 的 helper 不是一回事、模块层用 `nuxt.options` 之外的地方拿到的是空对象、服务端片段里 `useRequestEvent()` 在浏览器返回 `undefined`。这些都跟"哪个上下文有什么"是同一类问题的不同面，配着记。

自动扫描的边界也别忘（413 会细讲）：只有 `shared/utils/` 与 `shared/types/` 会被自动导入，**这两个目录下的子目录不会**，除非你把目录同时加进 `imports.dirs` 与 `nitro.imports.dirs`；其它位置手动用 `#shared` 别名引。

## 自查

- 四个类型上下文（app/node/server/shared）决定一个类型声明谁能看见。
- 分法：`app/types` 只 app、`server/types` 只服务端、`shared/types` 两端都自动导入。
- `import type` 编译期擦除、跨边界"只引类型"能过，但官方仍要求共享类型放 `shared/types/`（边界清晰/防误改值导入/与上下文一致）。
- `shared/` 里不能 import 任何 Vue 或 Nitro 代码（`::important`）；两端各自方向的后果官方都列了。
- `shared/` 从 v3.14+ 才有；只有 `shared/utils` 与 `shared/types` 顶层被自动导入，嵌套要双配 `imports.dirs` + `nitro.imports.dirs`，其余用 `#shared`。
