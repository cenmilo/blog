这类报错很难查，因为它没有明确的错处：刚加的 `app/utils/format.ts` 页面里认不出来；`typescript.hoist` 加了包名还是找不到；增强写了却仍是 `unknown`。第一反应是配置没写对，但更常见的原因是**生成物还是旧的**。

## 为什么"重生成"是第一步

395 那条事实决定了排查顺序：类型是 `.nuxt` 里的生成物，dev/build/`nuxt prepare` 三个时机生成。既然是生成物，就会有"该重新生成而没生成"的窗口。

而 `.nuxt` 那页的 `::warning` 顺手解释了另一个常见错误行为：

> You should not touch any files inside since the whole directory will be re-created when running `nuxt dev`.

有人为了让报错消失去手改 `.nuxt` 里的声明文件——下一次 `nuxt dev` 整个目录重建，改动直接没了。这条和 395 的"别手改生成的 tsconfig"（`::warning`）是同一个道理：**生成物只能靠重新生成来修**。

同页还有 `::important`：`.nuxt` 要进 `.gitignore`，因为它是开发构建产物。

## 标准两步：cleanup 然后 prepare

`nuxt cleanup` 官方定义 "Remove common generated Nuxt files and caches."，删除清单逐项如下：

- your build directory, which is `.nuxt` unless `buildDir` says otherwise
- `.output`
- `dist`
- `node_modules/.vite`
- `node_modules/.cache`

命令形态很薄——只有一个参数和一个选项：

```bash
npx nuxt cleanup [ROOTDIR] [--cwd=<directory>]
```

| 项 | 说明 |
| --- | --- |
| `ROOTDIR` | 项目根目录，默认 `.` |
| `--cwd=<directory>` | 指定 Nuxt 项目根目录 |

注意第一条的措辞：它删的是**你的构建目录**，默认 `.nuxt`，但如果你配了 `buildDir`（356/357），被删的就是你指定的那个位置——搬过 `buildDir` 的项目要有心理准备。

删完接着生成：

```bash
npx nuxt prepare
```

`prepare` 会建 `.nuxt` 并生成类型（395/399）。这两步合起来就是"类型层面推倒重来"的安全组合——只删生成物和缓存，不动你的源码与配置。

## 判断到底是哪一类问题

"重生成"能修的和不带的，症状不一样：

| 症状 | 先试 | 为什么 |
| --- | --- | --- |
| 新加的 composable/util 认不出 | cleanup + prepare | 生成物没跟上 |
| 改了 `imports.dirs`/`hoist` 没生效 | prepare 后仍不行就 cleanup 再来 | paths 写在生成的 tsconfig 里 |
| 增强写了仍 `unknown` | 先查文件放对上下文目录（396/406），再重生成 | 位置不对不是生成问题 |
| 改了 `nuxt.config` 行为没变 | 确认它整重启完了（362） | 配置类文件是整重启不是热更 |
| 报错行对不上代码 | 开 sourcemap（408 下节） | 产物映射问题 |

最后一行提醒：类型报错位置奇怪，可能是 sourcemap 而不是类型本身。

## 看不清就开调试工具

debugging 那页给的三件在类型/构建类问题上也用得上：

```ts
export default defineNuxtConfig({
  // or sourcemap: true
  sourcemap: {
    server: true,
    client: true,
  },
})
```

服务端构建默认开 sourcemap、客户端在 dev 开，要精确控制就用这个对象。再加 `nuxt dev --inspect` 接 Chrome DevTools 看进程内部——官方限制照旧："the Node.js and Chrome processes need to be run on the same platform. This doesn't work inside of Docker."

## 一条容易忽略的连带：`.nuxt` 里有 VFS

`.nuxt` 那页还提到模块可以往这个目录加模板而**不落盘**：

> Nuxt also provides a Virtual File System (VFS) for modules to add templates to this directory without writing them to disk.
> You can explore the generated files by opening the Nuxt DevTools in development mode and navigating to the **Virtual Files** tab.

排错时有用：某个由模块贡献的声明"看不到文件"，不代表没生成——它可能只在 VFS 里。去 DevTools 的 Virtual Files 页看才是全貌。

## 自查

- 类型是 `.nuxt` 生成物，所以"新符号认不出/改了没生效"第一步是重生成，不是改配置猜。
- `nuxt cleanup` 删五样：构建目录（默认 `.nuxt`，配了 `buildDir` 就删那个）、`.output`、`dist`、`node_modules/.vite`、`node_modules/.cache`；只有 `ROOTDIR` 与 `--cwd` 两项。
- 然后 `nuxt prepare` 重建 `.nuxt` 与类型。
- 绝不手改 `.nuxt` 里的文件（`::warning`，dev 会整目录重建）；`.nuxt` 要进 `.gitignore`（`::important`）。
- 增强放错上下文、配置没重启这两类不是生成物问题，重生成治不了。
- 模块加的模板可能只在 VFS 里，用 DevTools 的 Virtual Files 页看。
