类型报错难查，是因为中间隔着一层看不见的加工：你写的是 `app/composables/useFoo.ts`，编辑器用的是 `.nuxt` 里生成的声明。中间任何一段没跑通，症状都只是"找不到这个名字"。这一篇把这条链摊开，逐段给核对动作。

## 链路全景

```
nuxt.config（imports / alias / typescript.* / buildDir / typesDir）
  +  目录结构（app/composables、app/utils、app/components、shared/…）
      ↓  触发时机：nuxt dev / nuxt build / nuxt prepare
.nuxt/
  ├─ tsconfig.app.json  tsconfig.server.json  tsconfig.node.json  tsconfig.shared.json
  └─ 自动导入声明（#imports 指向的就是这张表）
      ↓  根 tsconfig.json 用四条 references 接进来
编辑器语言服务 / nuxt typecheck
```

官方对前两段的原话："Nuxt projects rely on auto-generated types to work properly. These types are stored in the `.nuxt` directory and are generated when you run the dev server or build your application."（395）

## 第一段核对：生成到底跑没跑

先确认 `.nuxt` 存在且是新近的。三个触发时机里，**只要没跑过任何一个，这里就是空的**——刚 clone、刚 `nuxt cleanup`（408）之后都会这样。最快的补法是显式生成：

```bash
npx nuxt prepare
```

`.nuxt` 那页的定位句也印证了它是开发期产物："Nuxt uses the .nuxt/ directory in development to generate your Vue application."，并用 `::important` 要求它进 `.gitignore`——**正因为它是产物，仓库里不会有它**，队友 clone 下来必须自己生成一次。

## 第二段核对：四份 tsconfig 与 references

生成了，接着看生成的东西对不对。根 `tsconfig.json` 只有四条引用（395）：

```json
{
  "files": [],
  "references": [
    { "path": "./.nuxt/tsconfig.app.json" },
    { "path": "./.nuxt/tsconfig.server.json" },
    { "path": "./.nuxt/tsconfig.shared.json" },
    { "path": "./.nuxt/tsconfig.node.json" }
  ]
}
```

核对两件事：这四份文件在不在 `.nuxt` 里；报错的那个文件属于哪个上下文。`app/` 下的报错看 `tsconfig.app.json`、`server/` 下的看 `tsconfig.server.json`、`shared/` 看 `tsconfig.shared.json`、`nuxt.config.ts` 那批看 `tsconfig.node.json`。

这一步能拦住两个常见错误做法：
- 直接改 `.nuxt/tsconfig.*.json`（官方 `::warning`："the whole directory will be re-created when running `nuxt dev`"；另有 395 那条"别手改、要扩展走 nuxt.config"）；
- 把增强写在错误的上下文目录（396/409：`app/types` 只 app、`server/types` 只服务端、`shared/types` 两端）。

## 第三段核对：paths 里的别名

`#imports`、`~/`、`#build`、`#shared` 这些能跳转，靠的是生成 tsconfig 里的 `compilerOptions.paths`——官方原话是生成的配置"include **recommended basic TypeScript configuration** for your project, references to auto-imports, API route types, path aliases like `#imports`, `~/file`, or `#build/file`"。

alias 配错、或 monorepo 里某个包解析不到（403），症状就是"这个模块找不到"。这类要回查 `typescript.hoist`（给指定模块生成深别名，且官方注明**不支持子路径**）与 `workspaceDir` 检测结果。

还有一条要留在心里：`typescript.tsConfig` 里的 `types`、`paths`、`noEmit` **由 Nuxt 按上下文管理，设了不生效**（397）。在 tsConfig 里加 `paths` 试图修别名问题，是典型的"改了没用"。

## 第四段核对：不落盘的 VFS

翻 `.nuxt` 找不到某个声明，就断定"没生成"——这一步最容易错。`.nuxt` 那页给了另一套机制：

> Nuxt also provides a Virtual File System (VFS) for modules to add templates to this directory without writing them to disk.
> You can explore the generated files by opening the Nuxt DevTools in development mode and navigating to the **Virtual Files** tab.

模块贡献的模板可能**只存在于 VFS**，磁盘上没有对应文件。所以看全貌要去 DevTools 的 Virtual Files 页，而不是在资源管理器里翻 `.nuxt`。这一条对排查"装了某个模块之后类型才出现"特别关键。

## 第五段核对：报错来自谁

最后确认这条报错本身是谁给的：编辑器的红线来自语言服务读生成物，`nuxt typecheck` 的报错来自 `vue-tsc`/Golar 真跑了一遍检查（399）。而 `nuxt dev`/`nuxt build` **默认不做类型检查**（395），所以"构建过了"从来不代表类型对。

顺序就明确了：改代码后 IDE 没红 ≠ 类型没问题；IDE 红线和 `nuxt typecheck` 结论不一致时，先重生成（408），再比对上下文与 paths，最后才怀疑配置写错。

## 逐段排查表

| 段 | 看什么 | 修的位置 |
| --- | --- | --- |
| 生成 | `.nuxt` 在不在、新不新 | `nuxt prepare`；必要时 cleanup 再来（408） |
| 四份 tsconfig | 报错文件属于哪个上下文 | `typescript` 的四个 `*TsConfig`（397） |
| 增强位置 | 类型声明放对目录没 | `app/`、`server/`、`shared/`（396/409） |
| paths 别名 | `#imports`/`~/`/`#shared` 能不能跳 | `alias`、`typescript.hoist`、`workspaceDir`（403） |
| VFS | 磁盘上没有但可能存在 | DevTools 的 Virtual Files 页 |
| 报错来源 | IDE 还是 typecheck | 记住 dev/build 默认不查类型（399） |

## 自查

- 类型报错走一条可核对的链：配置+目录 → 生成 `.nuxt` 四份 tsconfig 与自动导入声明 → 根 tsconfig 四条 references → IDE/typecheck。
- `.nuxt` 是开发期产物、要进 `.gitignore`，所以 clone 后必须 prepare 才有类型。
- 绝不手改 `.nuxt` 里的文件（`::warning`，dev 重建）；要改走 `nuxt.config` 的 `typescript` 节。
- 翻磁盘找不到声明不等于没生成：模块模板可以只走 VFS，用 DevTools 的 Virtual Files 页看。
- `tsConfig` 里的 `types`/`paths`/`noEmit` 设了无效（397）；别名问题查 `hoist`/`workspaceDir`。
- dev/build 默认不做类型检查，"构建过了"≠"类型对了"。
