很多人以为用 Nuxt 写 TS 要维护一大堆声明文件，其实反过来：绝大多数类型 Nuxt 已经给好了，你要动手的地方很少，而且那少数几处的套路是同一个。

## 不用写的：生成物已覆盖

`guide/concepts/typescript` 那句总纲：

> Nuxt is fully typed and provides helpful shortcuts to ensure you have access to accurate type information when you are coding.

具体哪些"帮你弄好了"，官方在同页列了生成的 tsconfig 里包含的东西——**推荐的基础 TypeScript 配置**、对 **auto-imports** 与 **API route types** 的引用、以及 `#imports`、`~/file`、`#build/file` 这类**路径别名**（原句："include **recommended basic TypeScript configuration** for your project, references to auto-imports, API route types, path aliases like `#imports`, `~/file`, or `#build/file`, and more."）。

对照成清单：

| 你不用管的 | 靠什么给好 |
| --- | --- |
| `ref`/`computed`/`useFetch`/`useState` 等自动导入 | 生成的自动导入声明（`#imports`） |
| `app/composables`、`app/utils` 里的自有函数 | 同上，扫目录自动生成 |
| `app/components` 下的组件名（模板里不 import） | 组件类型生成 |
| `~/`、`@@`、`#build`、`#imports`、`#shared` 别名 | 生成的 `compilerOptions.paths` |
| 自家 `server/api` 的入参与返回类型 | Typed API Routes（`ServerRoutes`） |
| `lib`/`types`/`moduleResolution` 这些 tsconfig 项 | 四份生成的 tsconfig（别自己写） |

也就是说，只要 `.nuxt` 生成过（dev/build/`nuxt prepare` 任一），上面这些直接就有类型，编辑器还给补全。

## 要写的：三类具名接口增强

要自己动类型的地方，官方给的都是同一个动作——**augment 一个接口**。这三类本系列各自有专篇，这里只归位：

**① 自定义页面元数据**。`definePageMeta` 的类型里最后一条是 `[key: string]: unknown`，官方说：

> Apart from the above properties, you can also set **custom** metadata. You may wish to do so in a type-safe way by augmenting the type of the `meta` object.

所以像 393 例子里那句 `pageType: 'Checkout'` 想要有类型，就得增强 `PageMeta`。

**② `app.config`**。分两个方向：模块作者声明"合法输入"用 `AppConfigInput`；给 `useAppConfig()` 的输出定型用 `AppConfig`（app 代码内）；在 app 代码之外（服务端路由、`shared/`、`nuxt.config`）`useAppConfig()` 返回的是 `SharedAppConfig`，要增强它。三者的位置与后果见 055/348。

**③ `runtimeConfig`**。默认由 untyped 从你写的字面量自动推；要手动控制，就增强 `RuntimeConfig`（私有层）与 `PublicRuntimeConfig`（public 层）。**模块作者增强的是 `@nuxt/schema`，不是 `nuxt/schema`**——这条差异见 344。

三处模板都是同一个形状：

```ts [某个 .d.ts]
declare module 'nuxt/schema' {
  interface PageMeta {
    pageType?: string
  }
}

// 必须有一处 import/export，否则不是模块
export {}
```

## 写了还要放对目录

395 那条规则在这里落地：项目被切成四个类型上下文，增强放错目录就"认不出来"。官方的分配是：

- 增强 `app` 上下文的类型 → 文件放 `app/`
- 增强 `server` 上下文 → 放 `server/`
- app 与 server 共享的 → 放 `shared/`

`directory-structure/app/app-config` 那页也给了对应说法：**`shared/` 目录里的 `.d.ts` 覆盖 app 代码、共享代码与服务端路由**，所以要三处都可见的增强就写在那儿。

## 一个反直觉点：类型检查默认根本不开

不用写类型不代表不用管类型——但反过来也要知道：`nuxt dev`/`nuxt build` 默认**不做类型检查**（官方原句 "By default, Nuxt doesn't check types when you run `nuxt dev` or `nuxt build`, for performance reasons."）。所以类型写错了，构建照样过，只是 IDE 会划线、或你显式跑 `nuxt typecheck`（399）才炸。这是"类型没报错"和"类型是对的"之间的差别，别混。

## 自查

- 不用管：自动导入、自有 composables/utils/组件、路径别名、`server/api` 的入参与返回、tsconfig 本身——都由 `.nuxt` 生成物给。
- 要写的只有三类，动作都是 augment 具名接口：`PageMeta`（自定义 meta）、`AppConfig`/`AppConfigInput`/`SharedAppConfig`、`RuntimeConfig`/`PublicRuntimeConfig`（模块作者用 `@nuxt/schema`）。
- 增强必须放对上下文目录（app/server/shared），否则不被识别。
- dev/build 默认不检查类型；要显式 `nuxt typecheck` 或开 `typescript.typeCheck`。
