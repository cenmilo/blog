`app/utils/format.ts` 里导出一个 `formatDate`，页面里直接用没报错；换台机器、或刚 `git clone` 完打开项目，同一行代码红线一条："Cannot find name 'formatDate'"。代码没动，红的是编辑器——这条几乎每个 Nuxt 项目都会碰到。

## 类型从哪来：不是全局变量

自动导入常被误解成"往全局塞变量"。官方专门否认：

> Contrary to a classic global declaration, Nuxt preserves typings, IDEs completions and hints, and **only includes what is used in your production code**.

它保留了**类型、编辑器补全与提示**，并且生产包里只打进真正用到的部分。同一页还有一句使用说明："In the docs, every function that is not explicitly imported is auto-imported by Nuxt and can be used as-is in your code."

结论：这些名字的类型来自 `.nuxt` 里的**生成声明**（395）。生成物在不在，直接决定编辑器认不认。

## 成因一：生成物还没生成

刚 clone、刚 `nuxt cleanup`、CI 里没跑过任何命令时，`.nuxt` 是空的——所有自动导入都报找不到。官方给的动作就是手动生成：

> You can also generate these files manually by running `nuxt prepare`.

所以 `package.json` 里那条 `postinstall: nuxt prepare`（见 075）不是可选项，它是"clone 完就能有类型"的保障。CI 同理要先 prepare。

## 成因二：被开关关掉了

`imports` 侧有两个开关会拿掉可见性，而且行为不同（细节见 152）：

- `imports.scan: false`——不再扫 `app/composables`、`app/utils`，自有函数就没了自动导入；这条还会**破坏图层对同名的覆盖**。
- `autoImport: false`——整体关掉自动导入，但官方留了口子：**`#imports` 依然可用**，改成显式导入即可。

配了这两个开关后又出现红线，先确认是不是自己关的。

## 成因三：目录不在扫描范围

Nuxt 只从固定的几个目录自动导入：`app/components/`、`app/composables/`、`app/utils/`。放错位置就不扫——比如把工具函数丢在 `app/utils/helpers/date.ts` 这种嵌套子目录里，默认并不会被自动导入，需要把它同时加进 `imports.dirs` 与 `nitro.imports.dirs`（这条两边都要配的边界见 151）。

## 成因四：代码在 node_modules 里

这是发布模块时最常撞的一条：**`node_modules` 里不启用自动导入**，官方的理由是出于性能。所以你在自己项目里"不用 import 就能用 `useRuntimeConfig`"，把同样代码放进要发布的包就报找不到——模块的 runtime 代码必须显式写：

```ts
import { useRuntimeConfig } from '#imports'
```

`#imports` 这个别名是把所有自动导入项暴露出来的口子，官方原句："Nuxt exposes every auto-import with the `#imports` alias that can be used to make the import explicit if needed."。在应用代码里也可以用 `#imports` 显式导入来消歧义。

## 成因五：增强类型放错了上下文

若是你自己 `declare module` 增强的类型不生效（比如 `PageMeta` 的自定义字段、`app.config` 的键），按 395 那条规则检查位置——项目被切成 app/node/server/shared 四个上下文，官方说法是：

> TypeScript will not recognize augmentations placed outside these directories unless they are explicitly included in the appropriate context.

要增强 app 的类型就放 `app/` 下；server 的放 `server/`；两边共享的放 `shared/`。放错目录＝写了但认不到，症状就是"我明明声明了，怎么还是 unknown / 还是报错"。

## 还有一条容易误判：类型没错、只是没检查

反过来也有：代码里类型确实是错的，但 dev 和 build 一路绿灯。因为官方明写 "By default, Nuxt doesn't check types when you run `nuxt dev` or `nuxt build`, for performance reasons."。IDE 的补全/报错来自生成的类型与语言服务，跟构建有没有做类型检查是两回事。要真正把关，得跑 `nuxt typecheck` 或开 `typescript.typeCheck`（397/399）。

## 排查顺序

1. `.nuxt` 在不在？没有就 `nuxt prepare`。
2. 是不是自己关了 `imports.scan` / `autoImport`？
3. 文件在不在被扫的目录（顶层 `app/composables`、`app/utils`）？嵌套要配 `imports.dirs` + `nitro.imports.dirs`。
4. 代码在 `node_modules`（发布模块）？改成从 `#imports` 显式导入。
5. 自己写的增强有没有放对 app/server/shared？
6. 上面都对 yet 行为不对，`nuxt typecheck` 显式验一遍，别靠 dev 绿灯判断。

## 自查

- 自动导入的类型来自 `.nuxt` 生成声明，不是全局变量；官方强调保留类型/补全且只打包用到的。
- 五类成因：没生成（prepare）、被开关关（imports.scan / autoImport，后者 `#imports` 仍可用）、目录不在扫描范围（嵌套要双配）、在 node_modules（必须显式 import）、增强放错上下文。
- `#imports` 是显式化兜底与消歧义手段。
- dev/build 默认不做类型检查——"IDE 没报错"不等于"类型是对的"。
