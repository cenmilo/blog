中文资料里这三个词经常互相乱用："加个插件"其实指的是模块，"装个模块"其实做的是配置一个包。这一讲按官方原文把边界划清，你之后读文档就不会再串。

## 一张表先分清

| 名词 | 活在哪一期 | 官方定位原文 | 放哪里 / 怎么装 |
| --- | --- | --- | --- |
| 模块（module） | **构建期** | "Nuxt 提供一个模块系统来扩展框架核心并简化集成。" | `nuxt.config` 的 `modules` 数组；或 `modules/` 目录 |
| 插件（plugin） | **运行期**（应用创建时） | "`plugins/`：在 Nuxt 应用创建时使用 Vue 插件及更多内容" | `app/plugins/` 目录 |
| 图层（layer） | 项目结构级复用 | "`layers/` 目录允许你组织并共享可复用的代码、组件、组合式函数与配置。这个目录内的层会被自动注册进你的项目。" | `layers/` 目录 |

一句话记法：**模块改变的是"Nuxt 怎么构建我的应用"，插件改变的是"应用启动时能做什么"，图层复用的是"一整个项目结构"。**

## 模块：构建期依次执行的异步函数

官方对模块的定义很具体，注意里面几个词：

> Nuxt 模块是**异步函数**，它们在通过 `nuxt dev` 以开发模式启动 Nuxt、或通过 `nuxt build` 为生产构建项目时**顺序运行**。它们可以覆盖模板、配置 webpack loader、添加 CSS 库，并执行许多其它有用的任务。
>
> 最棒的是，Nuxt 模块可以作为 npm 包分发。这让它们能够跨项目复用并与社区共享，有助于创建一个高质量附加品的生态。

这段里有三条会直接影响你的行为：

1. **"顺序运行"**意味着模块之间有先后依赖关系。模块里能改模板、能改构建配置，那么后跑的模块看到的就是前面模块改过后的状态。所以"我的模块在另一个模块之后加载"是有意义的诉求（后面模块那几讲会讲怎么控制顺序）。
2. **它跑在构建期**，不是浏览器里。你在模块里 `console.log` 是打在终端，不是打在 DevTools。
3. **npm 包是它的分发形态**，所以官方才有那句"最棒的是"——模块生态是能被安装复用的。

## 为什么这么设计：官方给的理由很实在

> 在开发生产级的 Nuxt 应用时，你可能会发现框架的核心功能不够用。Nuxt 可以用配置选项与插件来扩展，但**在多个项目之间维护这些定制是乏味、重复且耗时的**。另一方面，把每个项目的需求都开箱支持，会让 Nuxt 变得极其复杂而难以使用。
>
> 这就是 Nuxt 提供模块系统的原因之一：它使得扩展核心成为可能。

这两句话值得记住，因为它给了你一个判断标准：

- 只在**一个项目**里需要的东西 → 配置 + 插件就够了。
- 要在**多个项目**间重复的东西 → 才是模块的场合。

顺便，这一节末尾还有一句鼓励：**"每个人都有机会开发模块，我们迫不及待想看到你会构建什么。"** 写模块本身在 Module Author Guide 那一块，本套教程后面会讲。

## 怎么加模块，以及一个已弃用的名字

官方的写法是把模块名放进 `modules`：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: [
    // 使用包名（推荐的用法）
    '@nuxtjs/example',

    // 加载一个本地模块
    './modules/example',

    // 以内联选项的方式添加模块
    ['./modules/example', { token: '123' }],

    // 内联模块定义
    async (inlineOptions, nuxt) => { },
  ],
})
```

四种形态都在 `modules` 这一个数组里：包名、本地路径、`[路径, 选项]` 元组、以及**直接写一个异步函数**。第三种和第四种是很多人不知道的能力——临时给模块传选项、或者干脆在项目里内联一个小模块。

然后是这条必须知道的警告：

> Nuxt 模块现在是**仅在构建期**的，Nuxt 2 里使用的 `buildModules` 属性已被 `modules` 取代而**弃用**。

看到旧教程写 `buildModules`，那是 Nuxt 2 时代的写法。

还有一条很实用的：

> **从 v4.3 起你可以把某个模块的配置键设为 `false` 来禁用它。** 当你想禁用从层继承来的模块时，这一点特别有用：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  // 禁用 `@nuxt/image` 模块
  image: false,
})
```

注意这条的指向正好是下面要说的"图层"：**层给你带来了模块，你可以选择关掉它。**

## 插件：应用创建时跑的东西

官方对 `app/plugins/` 的说明只有一句：

> **`plugins/`**：在 Nuxt 应用创建时使用 Vue 插件及更多内容

它的两个特征和模块正好相反：**运行在应用启动时**（服务端和/或客户端），**属于单个项目内部**（不是你安装的一个包）。

这里还有一个词义混淆值得提前拆：英文 plugin 在 Vue 生态里指 `app.use()` 那种 Vue 插件，而 Nuxt 的这一节说的是"文件放在 `app/plugins/` 里"这件事。官方用词是 "use Vue plugins **and more**"——那个 "and more" 就是它比你预期更宽的地方（后面 `defineNuxtPlugin` 那一讲会展开）。

## 图层：复用的是"项目结构"

官方在目录结构那一节给的是：

> **`layers/`** 目录允许你组织并共享可复用的**代码、组件、组合式函数与配置**。这个目录内的层会被自动注册进你的项目。

以及介绍里更完整的一句：

> `modules/` 目录包含这个 Nuxt 应用的本地模块。模块被用来**扩展 Nuxt 应用的功能**。

对比就出来了：

- 模块扩展的是**能力**（加一个功能、接一个服务）。
- 图层复用的是**一整套结构**（组件、组合式函数、配置一起给你）。
- 本地模块（`modules/` 目录）是模块的"项目内形态"，官方在目录结构那一节对它的说法是"模块被用来扩展 Nuxt 应用的功能"。

模块的四种添加形态里正好也演示了这个区别：`'@nuxtjs/example'` 是外部包（模块生态），`'./modules/example'` 是项目内的本地模块。

## 判断该用哪一个：三个问题

按顺序问自己：

1. **这件事只在这个项目里需要，且发生在应用启动/运行时？** → 写 `app/plugins/` 里的插件。
2. **这件事要在多个项目间重复，或者需要接一个第三方服务？** → 找现成模块装进 `modules`；没有现成的再考虑自己写。
3. **我要复用的是一整套界面与结构（组件 + 组合式函数 + 配置）？** → 用层（`layers/` 或 `extends`）。

三者并不互斥：一个模块可以给你注册组件、一个层可以带模块进来。但**"我到底该把这段代码放哪"这个问题，先按上面三问回答，比按直觉乱放省事得多。**

## 自查

- [ ] 你能一句话区分模块（构建期）与插件（应用创建时）吗？
- [ ] 知道 `buildModules` 已弃用、模块现在只在构建期运行吗？
- [ ] `modules` 数组的四种形态里，你知道可以写 `[路径, 选项]` 和内联异步函数吗？
