上一篇说了路线。这一篇给你一个能长期使用的模型：**把 Nuxt 拆成六层看。** 学框架最难受的不是记不住 API，而是出了问题不知道往哪找。有了这六层，"我该去哪一层查"就变成了一个可以回答的问题。

## 第一层：你写的 `.vue` 文件

官方对起点的描述很直接：

> 我们让一切变得如此：你从一开始就能写 `.vue` 文件，在开发中享受热模块替换，并在生产中得到一个高性能的应用，并且默认就是服务端渲染。

这一层的含义是：**框架不要求你先搭骨架。** 一个 `.vue` 文件里有 `<template>`、`<script setup>`、`<style>`，它就是应用的组成单元。官方也把这一点讲成了目录职责：`app/components/` 放"应用的 Vue 组件"，`app/pages/` 放"基于文件的路由"。

## 第二层：目录约定（最容易低估的一层）

这一层不是"帮你少写几行"，而是**框架读目录当配置**。官方列的自动化里，有四条直接落在这一层：

> - **基于文件的路由**：根据 `app/pages/` 目录的结构来定义路由。
> - **自动导入**：在各自目录里写 Vue 组合式函数与组件，然后不使用 import 就能用它们，同时享受 tree-shaking 与优化后的 JS 包。
> - **取数工具**：Nuxt 提供组合式函数来处理 SSR 兼容的数据取数。
> - **零配置 TypeScript 支持**：不用学习 TypeScript 就能写类型安全的代码，靠的是自动生成的类型与 `tsconfig.json`。

于是你会得到一批"看不见声明"的东西：路由表、组件名、`useXxx` 函数名、布局名、`error.vue`、`app.vue`。它们的共同特征是：**由位置产生，不由 import 产生。**

这也是本套教程把阶段三（目录结构）放在视图与路由之前的原因。这一层出问题时最骗人——代码语法完全正确，只是文件放错了位置，于是**静默不生效**。

还有一句必须同时记住：

> 配置文件仍然可以定制并覆盖它的默认行为。

约定不是死规矩。几乎每一条约定背后都有一个可改的配置项，后面讲到时我会点出来。

## 第三层：构建与打包

官方给的是两条：

> **代码分割**：Nuxt 自动把你的代码拆成更小的 chunk，这有助于减少应用的初始加载时间。
>
> **已配好的构建工具**：我们默认使用 Vite，以在开发中支持热模块替换（HMR），并在生产中打包你的代码，最佳实践已经内置。

这一层解决的是"我的代码变成什么文件"。它和第二层是连着的：正因为路由来自文件，每个页面天然成为一个可延迟加载的 chunk。你以后看到"首屏 JS 太大"这类问题，答案基本都在这一层（分包、按需加载、未使用的组件不进产物）。

## 第四层：服务端引擎 Nitro

"同时提供前端与后端"这句话的落点就在这里：

> Nuxt 的服务端引擎 Nitro 解锁了新的全栈能力。
>
> 在开发时，它为你的服务端代码使用 Rollup 与 Node.js worker，并做上下文隔离。它还通过从 `server/api/` 读取文件来生成你的服务端 API，并从 `server/middleware/` 生成服务端中间件。
>
> 在生产中，Nitro 把你的 app 与 server 构建进一个统一的 `.output` 目录。这个产物很轻：经过压缩并移除了任何 Node.js 模块（除 polyfill）。

请注意这一层也在**读目录**：`server/api/`、`server/middleware/`。也就是说第二层那套约定在服务端同样成立，只是换了目录树。这条认知在后面会救你一次：应用侧的路由中间件不会为 `/api/*` 运行，服务端有它自己的中间件层。

## 第五层：渲染方式

官方先给默认值，再给三个可改的方向：

> Nuxt 内置服务端渲染（SSR）能力，你不必自己配置一个服务器。

以及：

> 由于 Nuxt 是一个多面的框架，它给了你这些可能：用 `nuxt generate` 把整个应用静态渲染到一个静态托管、用 `ssr: false` 全局禁用 SSR，或者通过设置 `routeRules` 选项利用混合渲染。

这一层的关键认知是：**渲染方式不是项目级的全局开关，而是可以按路由分别决定的。** `routeRules` 就是干这件事的（后面专门讲）。很多"这个页面要 SEO、那个后台不要"的需求，答案都在这一层，而不是重构项目。

## 第六层：部署形态

最后一层只有两个官方说法：

> Nuxt 没有供应商锁定，可以把你的应用部署到任何地方，甚至边缘。
>
> 你可以把这个产物部署在任何支持 JavaScript 的系统上——从 Node.js、Serverless、Workers、边缘侧渲染，到纯静态。

外加一句"生产就绪"：

> 一个 Nuxt 应用可以部署在 Node 或 Deno 服务器上，预渲染后托管在静态环境，或部署到 Serverless 与边缘提供商。

这一层之所以值得单列，是因为它经常被人误当成"框架问题"。同一个 `.output` 在不同平台行为不同，那不是 Nuxt 出了 bug，是第四层的产物在换宿主。

## 六层连起来的一次完整链路

把六层按顺序串一遍，你会看到一次访问实际经过的路径：

1. 你写 `app/pages/index.vue`（第一层）。
2. 目录约定把它变成一条 `/` 的路由，并把 `app/components/` 里的组件按名字提供给你（第二层）。
3. 构建时它被切成单独的 chunk，未使用的组件不进产物（第三层）。
4. 同时 `server/api/` 里的文件被 Nitro 读成接口（第四层）。
5. 请求来了，按这一条 URL 的渲染方式决定：服务端渲染出 HTML，或静态产物直接给出，或只发骨架交给浏览器（第五层）。
6. 这套产物跑在你选的那个平台上（第六层）。

以后你排查任何问题的第一句话，建议就改成：**"这件事掉在第几层？"**
