这是全套教程里最该早点读透的一页。不是为了记住名词，而是因为**后面每一个"为什么会这样"都落在这里**：水合不匹配、`window is not defined`、中间件跑两次、静态托管 404、SEO 抓取不到内容。

## 先定义"渲染"

官方的开场两句，把术语钉死了：

> Nuxt 支持不同的渲染模式：同构渲染（universal rendering）、客户端渲染（client-side rendering），同时也提供混合渲染（hybrid-rendering）以及把应用渲染到 CDN 边缘服务器上的可能性。
>
> **浏览器和服务端都能解释 JavaScript 代码，把 Vue.js 组件变成 HTML 元素。这一步称为渲染。**

注意这个定义：**渲染不是"服务端做的事"**。同一个组件、同一份代码，浏览器也能渲染。所以 Nuxt 官方的措辞是"同构渲染（universal）"而不是简单叫 SSR——它强调的是**同一份代码两端都跑**。

然后是默认值与切换成本：

> 默认情况下，Nuxt 使用**同构渲染**，以提供更好的用户体验、性能并优化搜索引擎索引，但你可以**用一行配置**切换渲染模式。

那一行就是 `ssr: false`。

## 同构渲染的完整链路：HTML 先到，水合后到

官方把流程分成两步讲，第二段就是水合的定义：

> 当浏览器请求一个 URL 且同构渲染开启时，Nuxt 在服务端环境中执行 JavaScript（Vue.js）代码，并向浏览器返回一个完全渲染好的 HTML 页面。Nuxt 也可能从一个缓存中返回完全渲染好的 HTML 页面，如果这个页面是提前生成的。用户能立即得到应用的**全部内容**，这与客户端渲染相反。
>
> HTML 文档下载完成后，浏览器会解释它，Vue.js 接管这个文档。**曾经在服务端运行过的同一份 JavaScript 代码，在客户端（浏览器）再运行一次**，此时它负责启用交互性（因此称为**同构渲染**），把监听器绑定到 HTML 上。这一步称为**水合（Hydration）**。水合完成后，页面才能享受动态界面与页面过渡这类好处。

把这两段收成一个能背下来的链条：

1. 请求进来 → 服务端跑组件代码 → 返回**完整 HTML**（也可能来自缓存）。
2. 浏览器显示 HTML（此时内容已经可见）。
3. 同一份 JS 在浏览器**再跑一次** → 绑事件 → 这一步叫**水合** → 之后才有交互。

**"内容先到、交互后到"**就是这条链的本质。它同时解释了两种典型 bug：水合不匹配（第 1 步和第 3 步算出来的 HTML 不一样）、以及"看得见但点不动"（还没水合完）。

## 哪些代码在哪一侧跑：官方给的判定

这一段是官方专门回答"我的代码到底跑在哪"的，非常重要：

> 在同构渲染模式下，一个 Vue 文件里哪部分跑在服务端、哪部分跑在浏览器，是常见问题。

```vue [app/app.vue]
<script setup lang="ts">
const counter = ref(0) // 在服务端与客户端环境中都会执行

const handleClick = () => {
  counter.value++ // 只在客户端环境中执行
}
</script>

<template>
  <div>
    <p>Count: {{ counter }}</p>
    <button @click="handleClick">
      Increment
    </button>
  </div>
</template>
```

官方接着给出了它自己的解释：

> 在首次请求时，`counter` 这个 ref 在服务端被初始化，因为它在 `<p>` 标签内被渲染。`handleClick` 的内容在这里**从未被执行**。在浏览器水合期间，`counter` 被重新初始化。`handleClick` 这时才把自己绑定到按钮上；因此可以推断，`handleClick` 的函数体总会运行在浏览器环境里。

判定方法就一句话：**被渲染进 HTML 的会两端各执行一次；只在事件回调里的只在浏览器执行。**

再往下，官方给了一张"目录级别"的分布说明：

> [中间件]与[页面]在服务端以及水合期间的客户端都会运行。[插件]可以在服务端、客户端或两端都渲染。[组件]也可以被强制只在客户端运行。[组合式函数]与[工具函数]根据其使用上下文来渲染。

这一句直接预回答了后面几讲的好几个问题：为什么中间件在初始页会跑两趟（因为它在服务端和水合期间的客户端都跑）、为什么有 `.client`/`.server` 后缀（组件可强制单侧）、为什么 utils 里不能碰 `window`（它按使用上下文走）。

## 同构的两条代价，官方写得很坦白

**好处**是两条：

> - **性能**：用户可以立即访问页面内容，因为浏览器展示静态内容比展示 JavaScript 生成的内容快得多；同时 Nuxt 在水合过程中保留 Web 应用的交互性。
> - **搜索引擎优化**：同构渲染像传统服务端应用一样，把页面的整个 HTML 内容交付给浏览器。网络爬虫可以直接索引页面内容。

**代价**也是两条：

> - **开发约束**：服务端和浏览器环境提供的 API 不同，写出能两端无缝运行的代码可能很棘手。幸运的是，Nuxt 提供了指南与特定变量来帮助你判断一段代码在哪里执行。
> - **成本**：要有一台正在运行的服务器才能即时渲染页面。这会带来像传统服务器一样的月度成本。不过由于同构渲染在客户端导航时由浏览器接管，服务端调用被大幅减少。

这里给了两个后面一定会遇到的关键词：`import.meta.server`/`import.meta.client`（"Nuxt 提供的特定变量"），以及"客户端导航不再请求服务端"这个省钱机制（123 讲路由实例、145 讲预取都会用到）。

适用场景官方也点名了：

> 同构渲染非常多面，能适应几乎任何用例，尤其适合内容导向的网站：**博客、营销网站、作品集、电商站点与市场。**

## 纯客户端渲染：三条好处、三条坏处

官方的定义：

> 从一开始，一个传统 Vue.js 应用就是在浏览器（或**客户端**）渲染的。浏览器下载并解析所有 JavaScript 代码之后，Vue.js 才生成 HTML 元素。

好处三条：

- **开发更快**：完全在客户端工作时，不必担心代码的服务端兼容性，例如使用 `window` 这类仅浏览器可用的 API。
- **更便宜**：跑服务器有基础设施成本；纯客户端应用可以托管在任意静态服务器上，只有 HTML、CSS 与 JavaScript 文件。
- **可离线**：因为代码完全在浏览器里运行，它在断网时仍能继续工作。

坏处两条（性能和 SEO），和上一节正好互为反面。适用场景同样点名：

> 纯客户端渲染适合那些不需要被索引、或用户频繁访问的重度交互 Web 应用……例如 **SaaS、后台管理与在线游戏**。

开启方式与一个必须配套的提醒：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  ssr: false,
})
```

> 如果你使用了 `ssr: false`，你应当在 `~/spa-loading-template.html` 放一个 HTML 文件，写入你希望用来渲染加载屏的内容，它会在你的应用被水合之前一直显示。

这一句很重要：**关掉 SSR 之后白屏是必然的**，官方给的办法不是"忍着"，而是准备一个加载模板。

## 静态化：`nuxt generate` 与它的副作用

如果目标是"整个站点都是静态文件"，官方给的是命令而不是配置：

> 如果你用 `nuxt generate` 或 `nuxt build --prerender` 命令把应用部署到静态托管，那么默认情况下，Nuxt 会把每个页面渲染成单独的静态 HTML 文件。

紧接着是一条警告，属于新手必踩：

> 如果你用 `nuxt generate` 或 `nuxt build --prerender` 预渲染你的应用，那么你将**无法使用任何服务端接口**，因为你的输出目录里不会包含服务器。如果你需要服务端功能，请改用 `nuxt build`。

也就是说 `ssr: false` + `nuxt generate` 这条路，是把 002 讲那句"同时提供前端与后端"的后端拿掉了。想同时要静态页面和接口，就得回到 `nuxt build` 加按路由预渲染（`routeRules`），也就是混合渲染那一段。

纯客户端 + 静态托管还有一个文件层面的细节，官方写在这一节：

> 你可能只需要一个 `index.html` 文件，加上 `200.html` 与 `404.html` 两个兜底文件，然后告诉你的静态 Web 主机对所有请求都返回它们。

## 混合渲染与边缘渲染：现在只需记住名字

这一页还有两节属于进阶，本套教程各有专篇（`routeRules` 与边缘部署）。现在只要认住官方给的定位：

- **混合渲染**：允许**按路由**使用不同的缓存规则，并决定服务器对新请求如何响应（例如内容页静态生成、后台按需渲染）。
- **边缘渲染**：请求被最近的边缘服务器拦截并生成 HTML，官方提醒"ESR 更像一个部署目标，而不是真正的渲染模式"。
