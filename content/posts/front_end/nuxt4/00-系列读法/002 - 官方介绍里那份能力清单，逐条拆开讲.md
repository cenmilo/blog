上一篇我们把"一个 Web 应用要手工做哪些事"列了一遍（见 010 讲）。这一讲直接看官方那张清单——它写的正是"Nuxt 把这些事接过去了"。

先把定位读准，官方的原话是：

> Nuxt 是一个免费、开源的框架，用一种直观且可扩展的方式，让你能用 Vue.js 创建类型安全、高性能、生产级的全栈 Web 应用与网站。
>
> 我们让一切变得如此：你从一开始就能写 `.vue` 文件，在开发中享受热模块替换，在生产中得到一个高性能的应用，并且**默认就是服务端渲染**。
>
> Nuxt 没有供应商锁定，可以把你的应用部署到**任何地方，甚至边缘**。

一句话里塞了三个后面的大主题：`.vue` 文件即组件、HMR（`nuxt dev` 那一讲讲）、SSR 默认开（"同一份代码跑在两个地方"那讲讲）。这一讲不展开，只做一件事：**把名字对上。**

## 官方列的七条自动化与约定

这一节的开头有句重要的前提，先抄下来：

> Nuxt 使用约定和有主见的目录结构来自动化重复性工作，让开发者专注于推进功能。**配置文件仍然可以定制并覆盖它的默认行为。**

这句"仍然可以覆盖"很关键——约定不是强制。后面你会看到几乎每条约定都配着一个可关的选项。

然后是七条本身，每条我给一句"它到底替你省了什么"：

**一、基于文件的路由。**

> 根据 `app/pages/` 目录的结构来定义路由。这能让组织应用更容易，并避免手动配置路由的需要。

不用 Nuxt 时那张路由表就是要手写的。从这里开始，路由由文件名生成（细节在 `pages` 目录那两讲与路由篇）。

**二、代码分割。**

> Nuxt 自动把你的代码拆成更小的 chunk，这有助于减少应用的初始加载时间。

注意这条和"路由由文件生成"是一体的：每个页面组件天然是一个可延迟加载的单元。组件侧"只在使用时才导入"也属于这条的收益（没被用到的组件不进生产代码）。

**三、开箱即用的服务端渲染。**

> Nuxt 内置 SSR 能力，所以你不必自己搭一个单独的服务器。

自己写 SSR 服务器是 010 讲那份手工账单里最贵的一项，在这里变成默认行为，且**没有额外配置文件**。

**四、自动导入。**

> 在各自目录里写 Vue 组合式函数与组件，然后不使用 import 就能用它们，同时享受 tree-shaking 与优化后的 JS 包。

这一条会在组件与自动导入那一段整块展开。现在只需要记住它的定义方式：**目录决定名字**。

**五、取数工具。**

> Nuxt 提供组合式函数来处理 SSR 兼容的数据取数，以及不同的策略。

"SSR 兼容"这四个字是重点：在服务器上取过的数据，浏览器水合时要能复用，否则会重复请求。

**六、零配置 TypeScript 支持。**

> 不用学习 TypeScript 就能写类型安全的代码，靠的是我们自动生成的类型与 `tsconfig.json`。

这条最容易被误解成"自动做类型检查"。**不是**：类型是生成的，检查要另开（类型那一会明确写默认不检查类型）。

**七、已配好的构建工具。**

> 我们默认使用 Vite，以在开发中支持热模块替换（HMR），并在生产中打包你的代码，最佳实践已经内置。

开发服务器那讲讲 `nuxt dev`，构建那讲讲 `nuxt build`；构建器还能换成 webpack 或 rspack。

官方在这七条后面收了一句：

> Nuxt 处理了这些，并**同时提供前端与后端功能**，让你能专注于真正重要的事：**创建你的 Web 应用**。

"同时提供后端"指的就是 Nitro。

## SSR 默认开，官方给了五条理由

这一节值得慢慢读，因为它解释了"为什么不是纯客户端渲染"。官方的五条好处：

- **更快的初始页面加载时间**：Nuxt 把一个完全渲染好的 HTML 页面发给浏览器，它可以立即显示。这带来更快的感知加载时间与更好的体验，**在慢网络或慢设备上尤其明显**。
- **更好的 SEO**：搜索引擎能更好地索引 SSR 页面，因为 HTML 内容立即可得，而不需要 JavaScript 在客户端渲染出内容。
- **在低功率设备上表现更好**：它减少了客户端需要下载并执行的 JavaScript 量，对那些跑重 JS 应用吃力的设备有益。
- **更好的无障碍**：内容在初次加载时立即可得，这对依赖屏幕阅读器或其它辅助技术的用户是改善。
- **更容易缓存**：页面可以在服务端缓存，从而进一步减少生成与发送内容所需的时间。

最后一条直接连着按路由配缓存策略的那一讲。而第四条"无障碍"这条好处，你会在屏幕阅读器、换页播报那些内容里反复遇到——**SSR 与无障碍不是两件独立的事**。

官方还补了一句总的判断，以及**三个能改变渲染形态的开关**：

> 总的来说，服务端渲染能提供更快的、更有效的用户体验，并改善搜索引擎优化与无障碍。
>
> 由于 Nuxt 是一个多面的框架，它给了你这些可能：用 `nuxt generate` 把整个应用静态渲染到一个静态托管、用 `ssr: false` 全局禁用 SSR，或者通过设置 `routeRules` 选项利用混合渲染。

这三个开关就是整个渲染篇的骨架：静态站走 `nuxt generate` 与静态托管兜底文件，SPA 走 `ssr: false`，混合渲染走 `routeRules`。这里先把名字认住。

## Nitro：那句"同时提供后端"指的是它

> Nuxt 的服务端引擎 Nitro 解锁了新的全栈能力。
>
> 在开发时，它为你的服务端代码使用 Rollup 与 Node.js worker，并做上下文隔离。它还通过从 `server/api/` 读取文件来生成你的服务端 API，并从 `server/middleware/` 生成服务端中间件。
>
> 在生产中，Nitro 把你的 app 与 server 构建进**一个统一的 `.output` 目录**。这个产物很轻：经过压缩并移除了任何 Node.js 模块（除 polyfill）。你可以把这个产物部署在任何支持 JavaScript 的系统上——从 Node.js、Serverless、Workers、边缘侧渲染，到纯静态。

三个信息点：

1. **服务端 API 与中间件也是"文件生成"的**（`server/api/`、`server/middleware/`），和路由同一套思路。
2. **生产产物只有一个目录 `.output`**。
3. **部署面极宽**——官方给的顺序是 Node.js / Serverless / Workers / 边缘 / 纯静态。

## 架构：五个包，出问题该看哪一个

> Nuxt 由不同的核心包组成：
> - 核心引擎：`nuxt`
> - 打包器：`@nuxt/vite-builder`、`@nuxt/rspack-builder`、`@nuxt/webpack-builder`
> - 命令行工具：`@nuxt/cli`
> - 服务端引擎：`nitro`
> - 开发工具包：`@nuxt/kit`

官方在这份清单后面有一句建议，值得当学习路线用：

> 我们建议把每个概念都读一遍，以便对 Nuxt 的能力与各包的范围有一个完整的视野。

这个"谁负责什么"的分工在核心包那一讲展开；这一讲你只要能对上一个直觉：**改配置无效先想 `nuxt`、构建产物奇怪先想 builder、接口行为奇怪先想 `nitro`、写模块先想 `@nuxt/kit`**。
