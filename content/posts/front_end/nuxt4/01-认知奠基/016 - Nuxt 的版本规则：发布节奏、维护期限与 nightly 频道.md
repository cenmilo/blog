学框架的人很少在第一课想版本问题，但它决定两件事：**你敢不敢升、以及你的项目还能不能拿到安全补丁。** 这一讲把官方写死的规则列全。

## 发布节奏：一句话四条

> 自 2023 年 1 月起，我们为 Nuxt 采用了遵循 semver 的一致发布节奏。我们以**每年一次框架大版本**为目标，预期**每周一左右的补丁版本**与**每月左右的次要版本**。除了明确标记为 `experimental` 的选项之内，它们**不应包含破坏性变更**。

拆成可执行的判断：

- **`4.3.0` → `4.4.0`（次要）**：不该有破坏性变更。
- **`4.4.1` → `4.4.2`（补丁）**：更不该。
- **`4.x` → `5.0`（大版本）**：一定有迁移工作，看升级指南。
- **唯一例外**：`experimental.*` 里的东西，官方明确说破坏性变更只发生在这一类选项内。

最后这条对写教程和做技术选型都很重要：**依赖实验特性，等于接受"它随时可能改名或改行为"**。本系列每次提到实验特性我都会点名，原因就在这里。

## 维护期限：一个大版本至少活多久

> 我们承诺在每个 Nuxt 大版本发布之后，**至少支持它到下一个大版本发布后的六个月**，并在那时为现有用户提供升级路径。

配合官方那张时间表看：

| 版本 | 状态 | 初次发布 | 结束支持（EOL） |
| --- | --- | --- | --- |
| 5.x | scheduled（计划中） | Q4 2026（预估） | TBA |
| **4.x** | **stable** | 2025-07-16 | 5.x 发布后 6 个月 |
| 3.x | unsupported | 2022-11-16 | 2026-07-31 |
| 2.x | unsupported | 2018-09-21 | 2024-06-30 |
| 1.x | unsupported | 2018-01-08 | 2019-09-21 |

状态词官方也定义了，值得照抄进你的运维规范：

| 状态 | 含义 |
| --- | --- |
| Unsupported | 不再维护，**不会收到安全补丁** |
| Maintenance | **只会**收到安全补丁 |
| Stable | 正在被开发，会收到安全补丁 |
| Development | 可能不稳定 |
| Scheduled | 还不存在，但在计划中 |

再补一句官方原文提醒（对你的依赖规划很关键）：

> Nuxt 3 已于 2026 年 7 月 31 日结束生命周期，**不再接收 bug 修复或安全补丁**。如果你仍在 Nuxt 3 上，请遵循升级指南迁移到 Nuxt 4。

**看这张表的正确方式**：从你今天开始算，你的项目最迟要在 5.x 发布后 6 个月内处理一次大版本迁移。这不是坏消息，而是可规划的排期。

## 大版本之间：4 和 5 的特殊安排

官方对接下来两个版本说了一个"轻微变化"：

> 我们正为 Nuxt 4 与 Nuxt 5 计划这一节奏的一个轻微变化。**Nuxt 4 将是一个以稳定性为目标的发布，包含所有 `compatibilityVersion: 4` 的特性**，随后很快跟一个 **Nuxt 5**，它将包含升级到 Nitro v3 与更多变更。
>
> 这种方式把破坏性变更分离成可管理的阶段，从而允许更好的生态测试与更顺畅的迁移。

这一段解释了为什么你会在文档里看到 `future.compatibilityVersion` 这类键：**特性是先落地、再由大版本"转正"的**。本系列会遇到的两处就是它：`compatibilityVersion: 5` 下路由默认大小写敏感，以及 `normalizePageNames` 在 5 及以上才默认启用（类型那一段会讲）。

## nightly：抢先测试，但看清它跟的是哪条分支

> nightly 发布频道允许使用直接由仓库最新提交构建的 Nuxt。
>
> 当一个提交被合并进 `nuxt/nuxt` 的 `main` 分支并**通过全部测试**后，我们会用 GitHub Actions 触发一次自动的 npm 发布。

> 这些 nightly 发布的构建与发布方式和质量与稳定版相同。**唯一的差别**是你应当经常查看 GitHub 仓库以获取更新。评审过程与自动化测试都未必能捕获到的回归，存在很小的可能。因此我们内部用这个频道在每次发布前把一切再核一遍。

**怎么开（官方原样）：**

```diff [package.json]
{
  "dependencies": {
--    "nuxt": "^4.0.0"
++    "nuxt": "npm:nuxt-nightly@latest"
  }
}
```

> 移除 lockfile（`package-lock.json`、`yarn.lock`、`pnpm-lock.yaml`、`bun.lock` 或 `bun.lockb`）并重新安装依赖。

退出就是反向替换同样的两项，同样要删 lockfile 再装。

三条必须一起记住的提醒：

1. **只有 nightly 才有的特性，文档里会带一个提示标记**（"仅在 nightly 发布频道可用的特性会在文档中用 alert 标出"）。
2. **当前这条 latest 正在跟 v4 分支**，官方原话值得照抄：

> 当前 `latest` nightly 发布频道正在跟踪 Nuxt v4 分支，意味着**它此刻特别可能出现破坏性变更——小心！** 你可以用 `"nuxt": "npm:nuxt-nightly@3x"` 选用 3.x 分支的 nightly 发布。

3. 每个激活版本都有自己的 nightly（官方说法是"每个激活版本都有各自自动生成的 nightly 发布"）——所以别把 3.x 的 nightly 当 4.x 的新特性用。
