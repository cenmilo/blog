前两讲分别在算"手工活"和划"Nuxt 与 Vue 的分工"。这一讲换一个很具体的问题：**跑完构建，我手上到底多了什么东西？** 这个问题回答不清楚，上线时一定出事。

## 官方的那句话，说了三件事

> 在生产中，Nitro 把你的 **app 与 server** 构建进**一个统一的 `.output` 目录**。这个产物很轻：**经过压缩并移除了任何 Node.js 模块**（除 polyfill）。你可以把这个产物部署在**任何支持 JavaScript 的系统**上——从 Node.js、Serverless、Workers、边缘侧渲染，到纯静态。

拆开是三条：

1. **app 与 server 合成一个目录**。不是"前端一份、后端一份"两个产物，而是一个 `.output`。
2. **它不依赖宿主机的 Node 模块**——所以官方才敢说"部署到任何支持 JS 的系统"。
3. **同一个产物面向多种宿主**：Node、Serverless、Workers、边缘、纯静态。

## 三样东西分别从哪来

`.output` 里装的东西，对应 002 讲那七条能力中的三条：

**第一样：客户端包。** 来源是这两条承诺：

> **代码分割**：Nuxt 自动把你的代码拆成更小的 chunk，这有助于减少应用的初始加载时间。
>
> **已配好的构建工具**：我们默认使用 Vite，以在开发中支持热模块替换（HMR），并在生产中打包你的代码，最佳实践已经内置。

以及组件侧的那条：`app/components/` 里创建的组件"如果一个组件在任何地方都没有被使用，你的生产代码就不会包含它"。

**这一样就是浏览器下载的东西**，也是性能优化的主战场（首屏 JS、异步 chunk、按需水合）。

**第二样：服务端程序。** 来源是 Nitro 那一节：

> 在开发时，它为你的服务端代码使用 Rollup 与 Node.js worker，并做上下文隔离。它还通过**从 `server/api/` 读取文件来生成你的服务端 API**，并**从 `server/middleware/` 生成服务端中间件**。

也就是说：接口和中间件不是"你另外部署的一个后端"，而是**和前端同一次构建、同一个目录里的产物**。这是 009 讲那张分工表里"归位置决定"的一档——文件放对位置，产物里就有这条路由。

**第三样：静态 HTML 文件——注意它是可选的。** 官方给的是命令而不是默认行为：

> 如果你用 `nuxt generate` 或 `nuxt build --prerender` 命令把应用部署到静态托管，那么默认情况下，**Nuxt 会把每个页面渲染成单独的静态 HTML 文件**。

所以"静态文件"这一样**只有在预渲染时才有**。而跟着是一条必须读到的警告：

> 如果你用 `nuxt generate` 或 `nuxt build --prerender` 预渲染你的应用，那么**你将无法使用任何服务端接口**，因为你的输出目录里不会包含服务器。**如果你需要服务端功能，请改用 `nuxt build`。**

这一句是整篇最实用的判断依据：**接口在不在，取决于你用哪条命令，而不是你写没写 `server/api/` 文件。** 你写了、但用了 `nuxt generate`，产物里就没有服务器。

纯客户端渲染还有一档更小的形态：

> 你可能只需要一个 `index.html` 文件，加上 `200.html` 与 `404.html` 两个兜底文件，然后告诉你的静态 Web 主机对所有请求都返回它们。

这两个兜底文件的用途，在讲首页与 404 的那一领会完整展开（什么时候会用到 `404.html`、以及为什么 SSR 站点不需要它）。

## 一张表把三样东西钉住

| 产物 | 内容 | 谁用 | 想要它就必须 |
| --- | --- | --- | --- |
| 客户端包 | 拆分后的 JS/CSS chunk、入口与异步 chunk | 浏览器 | 有构建（`nuxt build` 或 `nuxt generate`） |
| 服务端程序 | Nitro 服务器 + 从 `server/api`、`server/middleware` 生成的路由与中间件 | 宿主（Node/Serverless/Workers/边缘） | 用 `nuxt build`（不是 `nuxt generate`） |
| 静态 HTML | 逐页预渲染的 HTML；纯客户端形态下是 `index.html` + `200.html`/`404.html` | 静态托管 / CDN | 用 `nuxt generate` 或 `nuxt build --prerender` |

这张表也解释了一个很容易混的现象：**同样一份代码，换一条命令，能力就少一块。** 004 讲说"渲染方式是可切换的"，切换的成本就体现在这张表上——`ssr: false` 省掉第二样的运行成本，但内容型站点就丢了首屏 HTML 与 SEO；`nuxt generate` 省掉第二样，但丢掉接口。

## `.output` 的三条使用规则

官方在产物目录那一页只写了三件事，但每件都要照做：

> Nuxt 在为生产构建你的应用时创建 `.output/` 目录。

> 这个目录应当被加入你的 `.gitignore` 文件，以避免把构建输出提交进你的仓库。

> 你不应该触碰里面的任何文件，因为在运行 `nuxt build` 时**整个目录会被重新创建**。

第三条尤其值得记住：**"在产物里改一行再上线"这种操作等于白改**——下次构建就没了。要改产物内容，改的是配置、代码，或者用构建期的钩子（进阶那一段会讲 `build:manifest` 这类钩子，官方说它"允许你自定义 Nitro 用来渲染最终 HTML 里 `<script>` 与 `<link>` 标签的清单"）。

顺带把另一个目录摆正，因为它经常被和 `.output` 混起来：**`.nuxt` 是开发/构建期的生成目录，`.output` 是生产产物**。007 讲说类型存在 `.nuxt` 里；052、053 两讲会分别把两个目录讲完。判断标准也很简单：**要部署的是 `.output`，要读类型的是 `.nuxt`。**
