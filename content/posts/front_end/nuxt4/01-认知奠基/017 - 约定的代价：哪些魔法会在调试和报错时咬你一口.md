summary:
  摘要：约定换来的是"少写代码"，代价是"错误不再出现在你写的那一行"。这一讲把官方文档里明确写出的静默失败与错位归因集中列一遍：配置项名字拼了不会报错（官方因此强烈建议 nuxt.config 用 .ts 以在 IDE 里获得提示避免拼写错误）；不在被扫描目录里的组件与函数不会自动导入、嵌套子目录里的文件不会被自动导入；自动导入的 ref 与 computed 在模板里不会被解包；组合式函数必须在正确上下文且同步调用，否则得到 Nuxt instance is unavailable；直接修改 tsconfig.json 的 compilerOptions.paths 会让 #imports 这类别名不再被识别；.output 整个目录会在 nuxt build 时重建，所以手改产物无效；nuxt generate 预渲染后产物里没有服务器因此服务端接口全部不可用；app.config.ts 里不能直接导入 Vue 组件且部分自动导入在 Nitro 上下文不可用。遇到这类现象，正确的排查顺序是先确认位置与命令，而不是先怀疑框架 bug。

前面几讲一直在讲约定多省事。这一讲讲它的账单。这类问题的共同特征是，不报错，只是不生效，而它们的解法也一样，先确认位置与命令，再怀疑框架。

账单一，配置写错了，不会告诉你。

官方在配置那一节给的那条建议，其实是在承认这件事。你不必使用 TypeScript 来构建 Nuxt 应用，不过我们强烈建议为 `nuxt.config` 文件使用 `.ts` 扩展名，这样你可以在编辑配置时在 IDE 里获得提示，以避免拼写错误和失误。

以及那句每个选项都描述在 Configuration Reference 里。为什么要这么强调，因为配置项拼错、或者把一个只在 `experimental` 下的键写在顶层，运行时不会报未知配置，它就是不生效。

排查动作，改完配置，去 `.nuxt` 里找它的痕迹，052 讲会讲里面有什么，或者对比改前改后的产物，而不是靠看起来应该生效了。

账单二，位置不对等于静默不存在。

这一类最常见，官方的措辞都很直白。组件在模板里用不了，官方依据是默认情况下只扫描 `~/components` 目录，扫描不到就不存在这个名字。函数不自动导入，自动导入只覆盖 `app/composables/` 和 `app/utils/`，服务端只覆盖 `server/utils/`，同理。子目录里的文件没被导入，官方的原话是 `shared/utils/` 与 `shared/types/` 里嵌套在子目录中的文件不会被自动导入，而 `server/types/` 只有直接存放的文件会被扫描，只扫顶层是设计。中间件放了却不跑，命名中间件在页面上使用时才通过异步导入加载，没被引用就不运行。布局名对不上，布局名会被规范化为 kebab-case，`someLayout` 会变成 `some-layout`，你引用的是没规范化的名字。

这条账单的价值，以后凡是我写了却没反应，第一句先问，这个文件在被扫描的位置吗，名字规范化之后是什么。

账单三，自动导入的两处反直觉。

一，模板里不解包。官方原话，自动导入的 `ref` 与 `computed` 在组件的 `<template>` 里不会被解包，这是因为 Vue 处理不是模板顶层的 ref 的方式所致。症状是模板里拿到的是对象，得写 `.value`，或者行为和你熟悉的 Vue 不一样。

二，上下文与同步性。这意味着除了极少数例外，你不能在 Nuxt 插件、Nuxt 路由中间件或 Vue setup 函数之外使用它们，而且必须同步使用。如果你得到类似 `Nuxt instance is unavailable` 的错误信息，那很可能意味着你在 Vue 或 Nuxt 生命周期的错误位置调用了某个 Nuxt 组合式函数。

这条最容易误判成 bug。模块顶层调用 `useRuntimeConfig()` 报错时，很多人会去查依赖版本。真正的原因是求值时没有上下文，011 讲那条分工的落地。

账单四，生成物不能碰，碰了就是白改。

`.output` 会被整体重建，官方原话是，你不应该触碰里面的任何文件，因为在运行 `nuxt build` 时整个目录会被重新创建。

`.nuxt` 是 Nuxt 依赖的配置源，Nuxt 依赖这份配置，而且 Nuxt 模块也可能扩展它，因此不推荐直接修改你的 `tsconfig.json` 文件，请改为通过 `nuxt.config.ts` 扩展它。以及更具体的一处，覆盖 `compilerOptions.paths` 会让 `#imports` 这类别名不再被识别，要用 `nuxt.config` 的 `alias`。

结论，想改行为，改输入，代码、配置、钩子，不要改输出，`.nuxt` 和 `.output`。

账单五，命令与开关改变能力，而不是改变 bug。

用 `nuxt generate` 或 `--prerender`，会少掉所有服务端接口，官方原话是你将无法使用任何服务端接口，因为你的输出目录里不会包含服务器。

用 `ssr: false`，会少掉首屏 HTML 与索引，官方建议同时放 `~/spa-loading-template.html` 做加载屏。

把值写进 `app.config.ts`，会少掉环境变量覆盖能力，官方原话是与 `runtimeConfig` 选项相反，这些不能被使用环境变量覆盖。

在 `app.config.ts` 里导组件或依赖自动导入，会少掉组件与部分自动导入，官方已知限制两条，不能在 `app.config.ts` 里直接导入 Vue 组件，以及部分自动导入在 Nitro 上下文中不可用。

这一格是看起来正常但功能缺一块的重灾区，代码没动，能力却少了一半，因为命令或开关换了。

账单六，报错来自另一个上下文。三类典型的错位归因。

ESM 报错看起来在你的组件里，实际是上游包的 `main` 和 `module` 发布方式与 Node 的解析规则冲突，015 讲，官方明确问题几乎肯定在上游库。

水合不匹配看起来是取数写错，实际可能是根作用域副作用、或模板里用了两侧算得不一致的值，013 讲。

服务端里同拼写函数行为怪异，实际是自动导入的是 h3 的 helper、而不是 `nuxt/server` 的那批，服务端那一段会细讲。

把代价换成三条纪律，你可以直接贴到项目 README。

没报错不等于生效。位置、扫描范围、名字规范化三件事，每次放了没用都先查。

改输入不改输出。`.nuxt` 和 `.output` 里的任何改动都会在下次构建消失。

命令与开关会改变能力集合。部署前用与线上完全一致的命令跑一次 `nuxt preview`，构建那段会讲为什么。

## 自查

- [ ] 上一次「没报错但不生效」，你是靠什么定位的（有没有查目录/扫描配置）？
- [ ] `nuxt.config` 是 `.ts` 吗？改配置后你验证过它生效了吗？
- [ ] 你的项目里有没有「手改过 `.output` 或 `.nuxt` 里的文件」这种习惯？
- [ ] 见到 `Nuxt instance is unavailable`，你会先检查调用位置吗？
- [ ] 部署用的命令，和你本地验证时用的是同一条吗？
- [ ] 自动导入的 `ref` 在模板里不解包这条，你踩过吗？
