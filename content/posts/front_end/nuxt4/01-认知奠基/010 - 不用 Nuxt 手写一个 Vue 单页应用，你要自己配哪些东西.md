这一篇是全系列最重要的一篇"反面论证"。我们不去说 Nuxt 好在哪，先算一件事：**如果只用 Vue，你要亲手做掉哪些活。** 算清楚了，之后每一条官方能力你都知道它在替你挡什么。

## 先把目标定死：我们要的是一个"能上线的站点"

如果只要一个 demo，写个 `index.html`、`<script>` 引 Vue、页面里挂个 `#app`，确实十分钟就能跑。但一个能上线的站点至少要求：

- 有好几个页面，地址要能进收藏夹、能被搜索引擎索引。
- 首屏不能是空白等 JS 跑完。
- 打包后的文件要能放到某种托管上。

下面五件事就是被这些要求逼出来的。

## 第一件：把 `.vue` 变成浏览器能执行的东西

`.vue` 是单文件组件，浏览器根本不认识它。官方对这一层的描述是：

> Vue 的单文件组件（SFC 或 `*.vue` 文件）封装了一个 Vue 组件的标记（`<template>`）、逻辑（`<script>`）与样式（`<style>`）。Nuxt 为 SFC 提供**零配置**体验，并带有热模块替换（HMR），带来顺畅的开发体验。

也就是说，你不用 Nuxt 时要自己搞定：

- 一个打包/构建工具，能把 `<template>` 编译成渲染函数；
- `<script setup>` 这种语法需要的编译步骤；
- `<style scoped>` 里的作用域处理；
- 开发时的热模块替换——否则你每改一行就手动刷一次整页。

这就是官方那句"已配好的构建工具"背后的活：

> 我们默认使用 Vite，以在开发中支持热模块替换（HMR），并在生产中打包你的代码，最佳实践已经内置。

**要点不是"Vite 好配"，而是"这件事必须有人做"**——不是你做，就是框架做。

## 第二件：一张手写的路由表

多页要导航，就需要路由。纯 Vue 的形态是：你建一个 `routes` 数组，逐条写清路径、组件、嵌套关系，再把它交给路由器。

官方对应的那条约定是：

> **基于文件的路由**：根据 `app/pages/` 目录的结构来定义路由。这能让组织应用更容易，并**避免手动配置路由的需要**。

目录那一节对 `pages/` 的一句话说明也是同一件事：

> `pages/`：基于文件的路由，用于在你的 Web 应用中创建路由。

差别体现在维护成本上：手写路由表时，**"文件"和"路由"是两处信息**，加页面要在两个地方改；忘改一处不会报错，只会得到一个打不开的路径。而由目录生成时，只有一处信息。

## 第三件：一台会渲染 HTML 的服务器，加上一条载荷通道

这是五件事里最贵的一件，也是纯 Vue 项目最容易低估的一件。

官方的流程描述里有两个动作：

> 当浏览器请求一个 URL 且同构渲染开启时，Nuxt 在服务端环境中执行 JavaScript（Vue.js）代码，并向浏览器返回一个完全渲染好的 HTML 页面。
>
> **曾经在服务端运行过的同一份 JavaScript 代码，在客户端（浏览器）再运行一次**，此时它负责启用交互性，把监听器绑定到 HTML 上。这一步称为**水合（Hydration）**。

你要自己做的是这三块：

1. **一个服务端进程**：能执行组件代码、把渲染结果拼成完整 HTML 发出去（`renderToString` 那一类）。
2. **一条数据通道**：服务端取到的数据要交给浏览器，否则水合时浏览器会重新取一遍——慢、贵，而且两侧数据不一致就直接水合不匹配。官方对这件事的定位是：
   > **取数工具**：Nuxt 提供组合式函数来处理 **SSR 兼容**的数据取数，以及不同的策略。
   以及"SSR 兼容"具体指什么：
   > 为确保水合正确，保持服务端与客户端数据一致很重要……这些方法确保服务端取到的数据在水合期间被复用，避免重复请求。
3. **一份状态约定**：什么放服务端、什么放客户端。官方在这一节给了个非常具体的例子：`<script setup>` 里的 `const counter = ref(0)` **在服务端与客户端都会执行**，而 `handleClick` 的函数体**只在浏览器执行**。自己搭 SSR 时，这类判断全是你手写规则。

顺带一提，官方也说了这件事的代价不会因为"用了框架"就消失：

> **开发约束**：服务端和浏览器环境提供的 API 不同，写出能两端无缝运行的代码可能很棘手。幸运的是，Nuxt 提供了指南与特定变量来帮助你判断一段代码在哪里执行。

**框架降低的是难度，不是消除约束。** 后面你会反复用到 `import.meta.server`/`import.meta.client` 这对"特定变量"。

## 第四件：产物的组织与代码分割

首屏不该把所有页面的代码都发出去。官方的那条是：

> **代码分割**：Nuxt 自动把你的代码拆成更小的 chunk，这有助于减少应用的初始加载时间。

自己配时你要处理：入口 chunk 与异步 chunk 的划分、chunk 文件名与哈希、以及服务端渲染时该为这条路由引入哪些资源。而这些和第二件是连着的——**正因为页面来自目录，每个页面天然成为一个可分割单元**，官方才敢把它做成默认行为。

## 第五件：部署形态与切换它的成本

最后你要决定这个应用怎么上线，并且要允许以后改主意：

- 有服务器 → 同构渲染，但要付一台在跑的机器的成本（官方明确列了这条代价）。
- 没有服务器、只有静态托管 → 必须把每个页面预渲染成 HTML 文件；官方给的命令是 `nuxt generate` / `nuxt build --prerender`，并警告"你将无法使用任何服务端接口"。
- 只要交互不要索引（后台类）→ 干脆关掉 SSR（`ssr: false`），但官方提醒此时"应当在 `~/spa-loading-template.html` 放一个加载屏 HTML"。

纯 Vue 项目里，这些决定意味着**换一套构建目标 + 换一套托管脚本**，而且往往要重做第三件事。官方的对应承诺是这一句：

> Nuxt 没有供应商锁定，可以把你的应用部署到任何地方，甚至边缘。

以及生产产物的形态：

> 在生产中，Nitro 把你的 app 与 server 构建进一个统一的 `.output` 目录……你可以把这个产物部署在任何支持 JavaScript 的系统上——从 Node.js、Serverless、Workers、边缘侧渲染，到纯静态。

## 把两边并排放：这张表才是本系列的大纲

| 你必须做的事 | 官方对应的能力 | 本系列的位置 |
| --- | --- | --- |
| 配打包器与 SFC 编译 | 已配好的构建工具（默认 Vite，含 HMR） | 环境与命令那一段 |
| 手写路由表 | 基于文件的路由 | 目录结构 + 路由与导航 |
| 一台渲染 HTML 的服务器 | 开箱即用的服务端渲染 | 渲染模式那几讲 |
| 数据两端一致 | 取数工具（SSR 兼容） | 取数与状态 |
| 组件/函数到处手动 import | 自动导入（含 tree-shaking 与优化后的包） | 组件与自动导入 |
| 拆 chunk 保首屏 | 代码分割 | 性能与构建 |

这张表就是全套教程的目录来源。**每一行都是"我不用帮你做，但你自己一定得做"的一件事。** 这也是为什么 002 讲我说这一讲的目的不是深入，而是把名字对上：以后每次学到一个"魔法"，你都应该能反问一句"那不用 Nuxt 时这活是谁干的"。
