你在搜索框里敲「Nuxt 性能优化」，翻几屏就会有人提 Vapor Mode。名字听着像某个「更快的渲染模式」，于是你打开 `nuxt.config.ts`，准备加一行开关。

先等一下。

我知道你搜这个词，多半不是好奇，是项目卡了，想找个开关一键提速。但这一节就干一件事，让你在按下保存之前，看清这一行到底开了什么。

它不是性能开关，是另一种编译策略。而且官方把它标成实验特性。

Vue 平时渲染一个组件，次序是这样的。数据变了，先算一棵新的虚拟 DOM 树，一个描述页面该长什么样的普通对象，再拿它跟上一棵逐点比对，最后把差异写进真实 DOM。中间那棵树，是这套流程能保持稳定、能把不同组件拼在一起的原因，也是它的成本。

打个比方。虚拟 DOM 像施工队的图纸，每次数据变了，先画一张新图纸，跟旧图纸逐行比对，再把改动誊到真墙上。稳是真的稳，不同工种照着同一张图纸也能协作，但每改一处，画图、比对、誊写，三步都逃不掉。

Vapor Mode 去掉的，就是中间那棵树。

编译器在构建阶段就知道哪个节点绑了哪个数据，于是直接生成「改这个节点」的代码。相当于施工队早就知道哪块砖动过，直接上去换砖，图纸和比对全省了。官方的原话是，Vue 3.6 引入的一种替代编译策略，在没有 Virtual DOM 的情况下渲染组件，从而降低内存占用并改善运行时性能。

插一嘴，前端框架这些年一直有条支线剧情，不靠虚拟 DOM 行不行。Svelte 走的是编译路线，Vapor 算是 Vue 拿出来的一个回应。

你想想看这个落点，收益在运行时。更新频繁的时候，差距才拉得开。

至于「首屏少下载一点东西」，那是另一条链上的事，分包、按需水合、`routeRules` 缓存，跟这一行配置没关系。010 和 012 讲过了，这里不展开。

官方在这一节开头就放了警告，三条都得读。

第一条，它是实验特性，需要 Vue 3.6 或更新版本，API 可能改变。

第二条，在一个更旧的 Vue 版本上启用 `vue.vapor`，Nuxt 会警告并把它关掉。注意，不是「没生效」，是当场关回去。

第三条，它要的是一个同时包含 Vapor 与互操作修复的 Vue 版本。3.6 还在预发布阶段的时候，官方给的 `package.json` 例子写的是 `^3.6.0-rc.2`。

第三条正好接 016 讲那句，破坏性变更只会发生在明确标记为 `experimental` 的选项之内。Vapor 就是这样一个选项。API 可能改变不是客套话，是免责条款。

配置就一个键。

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  vue: {
    vapor: true,
  },
})
```

它装的是 Vue 的 `vaporInteropPlugin`，名字里那个 interop 是关键。怎么说呢，这一行请进来的不是一套新渲染引擎，是一个互操作插件。装完之后，你的应用仍然按虚拟 DOM 渲染，你要在具体那个组件的 `<script setup>` 上加一个 `vapor` 属性，它才走新路径。

```vue [app/pages/index.vue]
<script setup vapor lang="ts">
const count = ref(0)
</script>
```

所以这一行配置不会把你的应用变成 Vapor，它只是允许你逐个标记。真正决定某个组件走哪条路的，是那个属性。

官方对这套设计的说法是渐进采用，路由、`useAsyncData`、布局以及大多数内置组件保持不变地继续工作。也正因为是渐进，官方给的使用建议很直接，在一个新项目里尝试，而不是加到已有项目上。

限制一共六条。官方把原因写在最前面，因为 Nuxt 以互操作模式运行 Vapor，一些依赖虚拟 DOM 的模式在 Vapor 组件里表现不同。逐条过。

完整 Vapor 应用还不支持。应用根仍然是虚拟 DOM，你按组件选入，官方说以后可能会支持整棵 Vapor 应用。

模板 ref 不暴露 `$el`。凡是靠它去够真实 DOM 的写法，在这个组件里当场失效。

一些内置组件读不到 Vapor 的插槽内容。这条最容易踩，也最好解决。`<ClientOnly>` 会跳过它的属性透传下沉，而 `<NuxtIsland>`、服务端组件，以及那几个往 head 里写东西的组件，`<Title>`、`<Style>`、`<Noscript>`，在你传 Vapor 插槽时会告警。官方给的解法是把值直接传进去，比如给 `<Title>` 传一个字符串。这些组件不是不能用，是传法要换。

Options API 在 Vapor 组件里不受支持。连带后果写得很具体，通过 `defineNuxtComponent` 使用 `asyncData` 与 `fetchKey` 都不可用，要改用 `<script setup>` 配 `useAsyncData`。这属于写法迁移，比改一行配置贵。

带 key 的 `onPrehydrate` 会退化成不带 key 的形式，并在开发环境告警，因为没有组件实例可以挂这个 key。

最后一条值得单独说。在 Vapor 的 `<script setup>` 里，`await` 之后调用的 Nuxt 组合式函数，可能丢失 Nuxt 上下文，官方建议尽可能在第一个 `await` 之前调用完。

它之所以要紧，是因为框架在另一处保证过相反的事。130 讲那份自动导入的说明里写的是，`<script setup>`、`defineNuxtComponent`、`defineNuxtPlugin`、`defineNuxtRouteMiddleware` 这四个位置里框架做了转换，`await` 之后上下文仍然在。到了 Vapor 组件里，这个保证被官方自己打了问号。

同一个 `await`，四个地方给你保证，到这里变成可能丢。。。

实验特性四个字的成本，具体就长这个样子。

官方的收尾判断也记一下，大多数其它 Nuxt 组合式函数与内置组件照常工作，因为它们依赖的是注入，而不是组件实例。

绕回一开始那个问题，现在要不要用它。

三个事实摆在一起就够决策了。官方说它是实验特性、API 可能改变，官方建议新项目才试，六条限制里有三条会推翻你已经写过的东西，Options API、`$el`、`await` 之后的上下文。

我的口径是这样，把它当成「以后要评估的性能选项」，不要当成默认工程实践。说真的，现阶段让我把它开在存量项目上，我是不敢的。

真遇到性能诉求，先按 010 和 012 那条链去看产物与取数，分包、按需水合、`routeRules` 缓存，这些是文档里成熟的路径，不需要你装候选版。Vapor 排在它们后面。

（这是我给的建议，官方给的是「建议在新项目尝试」，两句话的分量不一样。）
