summary:
  摘要：官方用"步骤"给出了完整顺序。服务端对每个初始请求依次是：Nitro 插件（只在服务端启动时执行一次，serverless 下每个请求都会重启并执行但不被 await）→ 服务端中间件（对每个请求执行；从中间件返回值会终止请求并把返回值当响应发出，官方说一般应避免）→ 应用插件（先创建 Vue 与 Nuxt 实例，再执行内置插件如 Vue Router 与 unhead 以及 app/plugins 下的自定义插件，之后调用 app:created 钩子）→ 路由校验（插件之后、中间件之前调用 definePageMeta 的 validate）→ 应用侧中间件 → 页面与组件（用 useFetch/useAsyncData 取数）→ HTML 输出（渲染后 app:rendered，发送前 Nitro 调用 render:html 可改 HTML）。浏览器侧依次是：应用插件 → 路由校验 → 应用中间件 → app.mount 与水合（挂载前 app:beforeMount、挂载后 app:mounted）→ 完整 Vue 生命周期。把这条顺序和构建期的 Nuxt 钩子表放在一起，就知道任何一段代码"应该写在哪、能在哪一步介入"。

013 讲回答这段代码在两侧各做什么，这一讲回答另一半，它排在第几步、以及框架在哪一步留了口子。有了这张顺序表，你就不需要靠试错来理解为什么我的代码没跑到。

服务端，一个初始请求的七步。官方这一节的标题就是每一次初始请求都会执行以下步骤，我按顺序列出，并给每步配一句能在这里做什么。

第 1 步，Nitro 插件，`server/plugins`。当 Nitro 启动时，它初始化并执行 `/server/plugins` 目录下的插件，这些插件可以捕获并处理应用级错误，注册在 Nitro 关闭时执行的钩子，注册请求生命周期事件的钩子，例如修改响应。

关键的那句是关于次数的，Nitro 插件只在服务端启动时执行一次，在无服务器环境里，服务端会在每次进来的请求上启动，Nitro 插件也随之启动，但它们不会被 await。

能做什么，跨请求的东西，全局错误处理、对外部资源的连接、往 `render:html` 这类事件挂钩。不能做，假设这里改的东西只影响当前用户，因为它本来就是进程级的。

第 2 步，服务端中间件，`server/middleware`。在初始化 Nitro 服务端之后，`server/middleware/` 下的中间件对每个请求执行，中间件可用于鉴权、日志或请求转换这类任务。

警告必须照抄，这是最容易写错的一步。从中间件返回一个值会终止请求并把返回的值作为响应发出，为确保正确的请求处理，这种行为通常应当避免。

能做什么，读或改 header、记日志、往 `event.context` 挂东西。不能做，返回响应体。

第 3 步，应用插件。首先创建 Vue 与 Nuxt 实例，随后 Nuxt 执行它的应用插件，这包括内置插件，例如 Vue Router 与 `unhead`，以及位于 `app/plugins/` 目录的自定义插件，包括没有后缀的与带 `.server` 后缀的。在这一步之后，Nuxt 调用 `app:created` 钩子，它可以用来执行额外的逻辑。

这里能确认一件事，`app/plugins/` 跑在第 5 步的中间件之前。所以中间件里想用一个插件提供的东西是成立的，反过来不行。

第 4 步，路由校验。在初始化插件之后、执行中间件之前，如果在 `definePageMeta` 函数里定义了 `validate`，Nuxt 会调用它，`validate` 方法可以是同步或异步的，它常用于校验动态路由参数。如果参数有效，`validate` 函数应当返回 `true`，如果校验失败，它应当返回 `false`，或返回一个包含 `status` 和/或 `statusText` 的对象来终止请求。

顺序含义，校验早于中间件。所以参数非法的 404 会先于鉴权重定向发生。

第 5 步，应用侧中间件。中间件让你能在导航到某个特定路由之前运行代码，Nuxt 在初始页面加载时，服务端与客户端都，执行所有全局中间件，然后在任何客户端导航之前再执行一次，命名与匿名中间件只在页面 meta 里指定的那些路由上执行。

还有一条关于重定向的关键补充，013 讲引过，这里给它的顺序位置。服务端的任何重定向都会导致一个 `Location:` 头被发送给浏览器，浏览器随后向这个新位置发起一次全新的请求，发生这种情况时，所有应用状态都会被重置，除非它被持久化在 cookie 中。

也就是说重定向会把请求弹回第 1 步重新开始，这就是中间件里塞的状态在下一趟读不到的原因。

第 6 步，页面与组件。Nuxt 渲染页面与其组件，并在这一步用 `useFetch` 与 `useAsyncData` 取所需数据，因为服务端没有动态更新、也不发生任何 DOM 操作，像 `onBeforeMount`、`onMounted` 以及之后的钩子在 SSR 期间不会执行。

第 7 步，HTML 输出。在所有需要的数据取完、组件渲染完之后，Nuxt 把渲染出的组件与 `unhead` 的设置结合，生成一个完整的 HTML 文档，这个 HTML 连同其相关数据一起被发回客户端，以完成 SSR 过程。在把 Vue 应用渲染成 HTML 之后，Nuxt 调用 `app:rendered` 钩子。在最终确定并发送 HTML 之前，Nitro 会调用 `render:html` 钩子，这个钩子允许你操纵生成的 HTML，例如注入额外的脚本或修改 meta 标签。

这是我要往 HTML 里塞点东西的正确位置，`render:html`，Nitro 侧，而不是去改产物文件，017 讲那条纪律。

浏览器，五步。官方说这一段无论你的 Nuxt 模式是哪一种，都在浏览器里完整执行。

应用插件，与服务端类似，包含内置与自定义插件，在客户端执行的是无后缀与带 `.client` 后缀的插件，之后调用 `app:created`。

路由校验，与服务端相同，包含 `definePageMeta` 里的 `validate`。

应用侧中间件，Nuxt 中间件在服务端和客户端都运行，如果你想让某些代码只在特定环境运行，考虑用 `import.meta.client` 与 `import.meta.server` 来拆分。

挂载 Vue 应用并水合，调用 `app.mount('#__nuxt')` 把 Vue 应用挂载到 DOM，如果应用使用 SSR 或 SSG 模式，Vue 会执行水合，水合期间 Vue 重建应用，不包括 Server Components，把每个组件匹配到其对应的 DOM 节点并附加 DOM 事件监听器。在挂载 Vue 应用之前，Nuxt 调用 `app:beforeMount` 钩子，挂载之后调用 `app:mounted`。

Vue 生命周期，与服务端不同，浏览器会执行完整的 Vue 生命周期。

构建期也有一张顺序表。上面是运行期，还有一张属于构建期，官方把它列成 Nuxt Hooks（Build Time）表，几行关键的按顺序排。

`ready`，参数 `nuxt`，在 Nuxt 初始化之后、实例准备就绪时调用。`modules:before`，在 Nuxt 初始化期间、安装用户模块之前调用。`app:resolve`，参数 `app`，在解析 `app` 实例之后调用。`app:templates`，参数 `app`，在生成 `NuxtApp` 期间调用，允许定制、修改或向构建目录添加新文件。`pages:extend`，参数 `pages`，在页面路由从文件系统扫描之后调用。`pages:resolved`，参数 `pages`，在页面路由被用扫描到的元数据增强之后调用。`build:manifest`，参数 `manifest`，由 Vite 与 webpack 在清单构建期间调用，允许自定义 Nitro 用来渲染最终 HTML 里 `<script>` 与 `<link>` 标签的清单。`nitro:config` 与 `nitro:init`，分别是初始化 Nitro 之前与之后。

两张表合起来是一条完整链路，构建期生成路由与产物，服务端启动，第 1 到 2 步，每个请求，第 3 到 7 步，浏览器，五步。

用顺序表定位问题的三个例子。

接口没被调用，它属于服务端第 2 步，中间件，或第 6 步，页面，但如果你用了 `nuxt generate`，产物里根本没有服务端。

中间件里 `useRoute()` 拿到怪值，看第 5 步，中间件里没有当前路由这个概念，必须用参数 `to` 和 `from`。

水合后 DOM 与你预期不一致，看浏览器第 4 步，水合是匹配已有节点，不是重新渲染，差异来自两侧计算结果不同。

页面首屏没数据、切回来却有，第 6 步的取数只在服务端渲染时进 payload，客户端导航会复用或另取，对应 `useFetch` 的响应式与缓存规则。
