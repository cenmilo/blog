  摘要：服务端渲染不是"另写一套服务端代码"，而是同一份组件代码在服务端跑一次生成 HTML、在浏览器水合时再跑一次绑定交互。官方对两侧的差别给了具体判定：initial 请求时 counter 这类被渲染进 HTML 的值在服务端初始化、handleClick 的函数体从不执行；水合期间 counter 被重新初始化、handleClick 才绑到按钮上。按目录看：中间件与页面在服务端和水合期间的客户端都运行，插件可以在服务端、客户端或两侧，组件可以强制只在客户端，组合式函数与工具函数按其使用上下文渲染。服务端这一侧还有三条硬事实：没有 DOM 操作、onBeforeMount 与 onMounted 及之后的钩子不会执行、默认情况下 Vue 在 SSR 期间暂停依赖追踪（服务端没有响应式，因为渲染是自上而下输出静态 HTML，无法回头改已渲染的内容）。

004 讲我给了渲染的名字，010 讲说了这件事的手工成本。这一讲回答那个最实际问题，我这段代码，在服务端跑不跑，在浏览器跑几次。答不上来，就会写出本地好好的、线上偶现错乱的代码。

心智模型，一次渲染，两次执行。

官方在生命周期那一节对服务端的定位是，对于你应用的每一个初始请求，会执行以下步骤，其中第六步就是这一段，Nuxt 渲染页面与其组件，并在这一步用 `useFetch` 与 `useAsyncData` 取所需数据。因为服务端没有动态更新、也不发生任何 DOM 操作，像 `onBeforeMount`、`onMounted` 以及之后的钩子在服务端渲染期间不会执行。

再配合渲染那一节的水合定义，HTML 文档下载完成后，曾经在服务端运行过的同一份 JavaScript 代码，在客户端再运行一次，此时它负责启用交互性。

于是模型很清楚，组件的 setup 会被执行两次，服务端一次、浏览器水合一次。差异全在这一次能做什么。

服务端那一侧的三个不能。

一，没有 DOM。上一句官方原文就写了不发生任何 DOM 操作。所以 `document`、`window` 在服务端不存在，这就是 `window is not defined` 的成因。

二，mounted 之后的钩子不执行。官方把它说成一个真实的坑，例子就是定时器，你应该避免在 `<script setup>` 的根作用域里产生需要清理的副作用。一个这样的例子就是用 `setInterval` 设置定时器。在纯客户端代码里，我们可以设置一个定时器然后在 `onBeforeUnmount` 或 `onUnmounted` 里把它拆掉。然而由于卸载钩子在 SSR 期间永远不会被调用，定时器会一直留着。要避免这一点，请把你的副作用代码移进 `onMounted`。

这段值得抄进笔记，因为它的因果链和直觉相反。不是 onMounted 没跑所以没启动定时器，而是根作用域跑了、清理钩子却没跑。

三，没有响应式。官方给的理由很硬，默认情况下，Vue 在 SSR 期间会暂停依赖追踪以获得更好的性能。服务端没有响应式，因为 Vue 的服务端渲染把应用作为静态 HTML 自上而下渲染，这使得无法回头修改已经渲染过的内容。

所以你在服务端改一个 `ref` 的值，不会看到界面变化，这是设计，不是 bug。要响应，代码得活到浏览器那一侧。

哪些代码在哪一侧，官方那份判定。

渲染那一节给了一个具体例子。

```vue [app/app.vue]
<script setup lang="ts">
const counter = ref(0) // 在服务端与客户端环境中都会执行

const handleClick = () => {
  counter.value++ // 只在客户端环境中执行
}
</script>

<template>
  <div>
    <p>Count: {{ counter }}</p>
    <button @click="handleClick">
      Increment
    </button>
  </div>
</template>
```

官方的解释是，在首次请求时，`counter` 这个 ref 在服务端被初始化，因为它在 `<p>` 标签内被渲染。`handleClick` 的内容在这里从未被执行。在浏览器水合期间，`counter` 被重新初始化。`handleClick` 这时才把自己绑定到按钮上。

判据一句话，会被写进 HTML 的，两侧各执行一次，只在事件回调里的，只在浏览器执行。

再往目录级别推，官方那张分布说明，中间件与页面在服务端以及水合期间的客户端运行。插件可以在服务端、客户端或两侧渲染。组件也可以被强制只在客户端运行。组合式函数与工具函数根据其使用上下文渲染。

换成表最直观。`app/pages/` 页面，服务端是，初始请求，浏览器也是，水合期间。`app/middleware/` 中间件，服务端是，初始页，浏览器也是，水合加后续导航。`app/plugins/` 插件，服务端可，客户端可，可单侧可两侧。`app/components/` 组件，服务端默认是，可强制只在客户端，浏览器是。`app/composables/` 和 `app/utils/`，服务端跟着调用它的东西走，浏览器同左。

最后一行是很多人踩坑的地方，utils 里写 `window.addEventListener` 不会有编译错误，它只在被服务端调用时才炸。

怎么知道自己现在在哪一侧。

官方在渲染那一节说的特定变量就是这两行，`import.meta.server` 与 `import.meta.client`。用法是显式分支。

```ts
if (import.meta.server) {
  // 只在服务端
}

if (import.meta.client) {
  // 只在浏览器
}
```

官方在讲中间件跑两趟时，给的正是这几种写法。这里只为看清哪一步跑在哪一侧，`defineNuxtRouteMiddleware` 的完整写法在 060 与 130，`nuxtApp.isHydrating`、`payload.serverRendered` 要到 274 与 279 才逐项讲，payload 就是服务端把那一次取到的数据打包随 HTML 一起交给浏览器的那份数据。这一段先别往项目里贴，照着往下读即可。

```ts
export default defineNuxtRouteMiddleware((to) => {
  // 在服务端跳过中间件
  if (import.meta.server) {
    return
  }
  // 完全在客户端跳过中间件
  if (import.meta.client) {
    return
  }
  // 或者只在初始客户端加载时跳过中间件
  const nuxtApp = useNuxtApp()
  if (import.meta.client && nuxtApp.isHydrating && nuxtApp.payload.serverRendered) {
    return
  }
})
```

这个例子还顺带回答了跑几次，初始页的中间件服务端一次、浏览器一次。

一次初始请求的完整顺序，服务端七步。把生命周期那一节的七步压缩成一张能贴在显示器边上的清单。

Nitro 插件，`server/plugins`，只在服务端启动时执行一次，serverless 下每个请求都会重启并执行，但它们不会被 await。

服务端中间件，`server/middleware`，对每个请求执行。官方警告，从中间件返回值会终止请求并把该值当响应发出，一般应避免。

应用插件，先创建 Vue 与 Nuxt 实例，然后执行 `app/plugins/`，内置插件如 Vue Router 与 `unhead` 也在内。之后调用 `app:created`。

路由校验，插件之后、中间件之前，若有 `definePageMeta` 里的 `validate` 就调用它。

应用侧中间件，全局中间件在初始页服务端与客户端都跑，之后每次客户端导航前再跑，命名或匿名只在被指定的路由上跑。

页面与组件，渲染并用 `useFetch` 或 `useAsyncData` 取数，本讲前三条不能就在这一步生效。

HTML 输出，与 `unhead` 的设置合并成完整文档，渲染后调用 `app:rendered`，发送前 Nitro 调用 `render:html`。

浏览器侧则是五步，应用插件、路由校验、应用中间件、挂载并水合，`app.mount('#__nuxt')`、完整 Vue 生命周期。

读这张表的正确方式不是背，而是用它定位问题。接口没被调用，看第 1 到 2 步，`useState` 拿不到值，看第 3 步，中间件不该跑却跑了，看第 5 步，数据重复请求，看第 6 步与 7 之间。
