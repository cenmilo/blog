插件里最常见的两个需求是"SSR 完事之后做点什么"和"浏览器里挂载之后再操作"。这两件事的差别就写在 Environment 列上——从这一组开始，那一列不再是清一色。

## 七行照录

| 钩子 | 参数 | 环境 | 描述 |
| --- | --- | --- | --- |
| `app:rendered` | `renderContext` | **Server** | SSR 渲染完成时调用 |
| `app:redirected` | - | **Server** | 在 SSR 重定向之前调用 |
| `app:beforeMount` | `vueApp` | **Client** | 挂载应用之前调用，**只在客户端调用** |
| `app:mounted` | `vueApp` | **Client** | Vue 应用被初始化并挂载到浏览器时调用 |
| `app:suspense:resolve` | `appComponent` | **Client** | 在 Suspense 的 resolved 事件上调用 |
| `app:manifest:update` | `{ id, timestamp }` | **Client** | 检测到你的应用有新版本时调用 |
| `app:data:refresh` | `keys?` | **Client** | `refreshNuxtData` 被调用时调用 |

## 两条只在服务端

**`app:rendered`** 的触发条件是"SSR 渲染完成"，参数是 `renderContext`。

**`app:redirected`** 的条件更窄：**在 SSR 重定向之前**，而且**参数列是 `-`（无参数）**。

这两条的实际含义：**它们只会在服务端那一次执行里出现**。如果你的插件是 `mode: 'server'`，能钩到这俩；写成客户端专用的插件就完全碰不到。

**`renderContext` 里有什么，这一节没有列**——**参数类型未给出**，要看内容只能自己打印一次。表里也没有说这两条的先后关系（一个讲渲染完成、一个讲重定向之前，**顺序文档未写**）。

## 五条只在客户端：三个时机层次

**挂载前后各一条，参数相同**：`app:beforeMount` 与 `app:mounted` **都是 `vueApp`**。两句描述的对比就是它们的用处：

| 钩子 | 时机 |
| --- | --- |
| `app:beforeMount` | 挂载应用之前 |
| `app:mounted` | Vue 应用已初始化**并挂载到浏览器** |

`app:beforeMount` 那句原文还重复了一次环境信息（"Called before mounting the app, **called only on client side**."）——**描述里写着"只在客户端"，而 Environment 列已经标了 `Client`**。两处一致，读的时候不用怀疑。

**要操作真实 DOM，得等 `app:mounted`**；要在挂载前给 `vueApp` 补东西（指令、全局组件、混入这类），是 `app:beforeMount` 的位置。前面讲插件时官方给的那个客户端示例用的正是 `app:mounted`：**在 `app:mounted` 里改 colorMode 偏好**。

**第三条是 Suspense**：`app:suspense:resolve`，参数 `appComponent`，描述是"在 Suspense 的 resolved 事件上调用"，**并直接链到 Vue 文档的 Suspense 一节**——这是运行时表里少见的"描述完全依赖另一个框架的概念"的行：**Nuxt 根组件被包在 Suspense 里，这个钩子对应它解析完成的那一刻**。

**第四条讲版本**：`app:manifest:update`，参数是 `{ id, timestamp }`，条件是"检测到你的应用有新版本"。**这两个键分别代表什么（哪个 manifest、时间戳是谁的）、检测到之后框架做了什么，页面一个字没写**——它只给了这一句。

**第五条最特殊**：`app:data:refresh`，**它是这一组里唯一一个由用户侧 API 直接带起来的**——描述是"**`refreshNuxtData` 被调用时调用**"。参数写作 `keys?`，即**一个可选的键列表**。

这条的实用形状很直接：**用户在页面里调 `refreshNuxtData(['user'])`，你的钩子就带着这组 key 被调用**，于是可以做"这些 key 刷过之后再做点别的"。

## 环境列的读法

到这里可以给出运行时表的读表规则：**`Server` 表示只在服务端跑、`Client` 表示只在浏览器跑、`Server & Client` 表示两侧都会跑**（前三组共 12 行的分布是 5 条两侧、2 条服务端、5 条客户端）。

| 环境值 | 这七行里的钩子 |
| --- | --- |
| Server | `app:rendered`、`app:redirected` |
| Client | `app:beforeMount`、`app:mounted`、`app:suspense:resolve`、`app:manifest:update`、`app:data:refresh` |

**要"只发生一次"的动作，应该挂在单侧钩子上**。两侧都跑的钩子（上一组那五条）做累加类操作会算两遍——这也是为什么表里要专门给一列 Environment。

## 选钩子的三个问句

1. **这个动作要在服务端还是浏览器？** 先看 Environment，**列里写 `Client` 的钩子在服务端根本不触发**，插件写得再对也不会跑。
2. **要不要真实 DOM 或已挂载的应用？** 要就 `app:mounted`，不要就可以在 `app:beforeMount` 或更早。
3. **是不是由某个用户 API 带起来的？** 像数据刷新这种，表里直接写了触发它的公开 API（`refreshNuxtData`），**顺着这句能找到"谁调用会让我的钩子跑"**。

这一组未记载的：`renderContext` 的字段、`app:manifest:update` 里 `id`/`timestamp` 的含义与后续动作、`app:data:refresh` 中 `keys` 缺省时传什么（是全部 key 还是 `undefined`）、以及 `app:suspense:resolve` 与页面级 Suspense（下一组里的 `page:start`/`page:finish`）的关系。
