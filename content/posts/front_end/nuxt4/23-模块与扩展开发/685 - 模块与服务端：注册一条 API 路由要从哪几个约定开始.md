## 先看用户自己写服务端时的那三条根约定

Nuxt 会扫描这几个目录并注册 API 与 server handler，带热更新：

```bash [Directory Structure]
-| server/
---| api/
-----| hello.ts      # /api/hello
---| routes/
-----| bonjour.ts    # /bonjour
---| middleware/
-----| log.ts        # log all requests
```

每个文件默认导出一个用 `defineEventHandler()` 或它的别名 `eventHandler()` 定义的函数。handler 可以直接返回 JSON 数据、返回一个 `Promise`，或者用 `event.node.res.end()` 自己把响应发出去。

这一页还有一条重要提醒，是模块作者最容易违反的：

> 不要在 server 路由或工具函数里 import Vue 应用的代码（组件、composables 或其他只有应用侧能用的工具），也不要在应用侧 import 只有服务端能用的代码。

原因是这两边跑在不同上下文里。要两边共用，官方给的位置是 `shared/` 目录。

## 路径前缀由目录决定，不由文件名决定

- 放在 `~~/server/api` 里的文件，路由会**自动加上 `/api` 前缀**。
- 想要不带 `/api` 前缀，就放 `~~/server/routes`。文档的例子是 `server/routes/hello.ts` 返回 `'Hello World!'`，访问地址是 `http://localhost:3000/hello`。
- 有一条限制写得很明确：服务端路由**目前不支持**像页面那样的完整动态路由功能。

中间件是第三种：`~~/server/middleware` 里的任何文件都会被读进来。文档对它的行为和边界都说了：

> 中间件 handler 会在任何其他 server 路由之前、在每个请求上运行，用来添加或检查请求头、记录请求，或者扩展事件上的请求对象。

> 中间件 handler 不应该返回任何东西（也不应该关闭或响应请求），只能检查或扩展请求上下文，或者抛出一个错误。

官方给的两个例子就是这两类用途：一个用 `getRequestURL(event)` 打日志，一个往 `event.context.auth` 里塞 `{ user: 123 }`。

第四种是插件：`~~/server/plugins` 里的文件会被自动注册成 Nitro 插件，用来扩展 Nitro 的运行时行为、挂生命周期事件，示例是 `defineNitroPlugin((nitroApp) => { ... })`。

第五种是工具：`~~/server/utils`。这一页明确说服务端路由由 [h3](https://github.com/h3js/h3) 驱动、自带一批 helper，你也可以在这里加自己的——示例定义了一个 `defineWrappedResponseHandler`，包一层原始 handler、前后做事、`try/catch` 里返回 `{ err }`，然后 `server/api/hello.get.ts` 里 `export default defineWrappedResponseHandler(event => 'hello world')`。

## 两个 v4.3 之后的新东西，模块作者要用

**`#server` 别名**：从 `server/` 目录里任意位置导入，与发起导入的文件位置无关。文档给的对照是——原本要写 `import { formatUser } from '../../../utils/formatUser'`，现在写 `import { formatUser } from '#server/utils/formatUser'`。它有一条硬边界：**只能在 `server/` 内部使用**，在客户端代码里从 `#server` 导入会直接报错。

**`server/types/`**：这里的类型只在服务端上下文自动导入，所以在服务端路由、中间件、插件、工具里可以直接引用而不用 import。但只扫 `server/types/` 这一层，嵌套子目录里的文件不会被自动导入（这一点与 `shared/types/` 的规则一致）。应用侧也要用的类型不属于这里，要放 `shared/types/`。

## 文件名里能写的三种后缀

**方法后缀**。文件名可以以 `.get`、`.post`、`.put`、`.delete` 等结尾来匹配请求方法。文档给的对照很干净：`server/api/test.get.ts` 返回 `Test get handler`，`server/api/test.post.ts` 返回 `Test post handler`，那么对 `/test` 的请求里 GET 拿前者、POST 拿后者、**任何其他方法返回 405 错误**。

另一种组织方式是目录里放 `index.[method].ts`，文档说这适合创建 API 命名空间，给了三个并列文件：`server/api/foo/index.get.ts`、`server/api/foo/index.post.ts`、`server/api/foo/bar.get.ts`。

**动态参数**。文件名里用方括号，例如 `/api/hello/[name].ts`，通过 `event.context.params` 读取，官方示例用 `getRouterParam(event, 'name')` 拼出 `Hello, ${name}!`；还补了一句可以用 `getValidatedRouterParams` 配 Zod 或 Valibot 做运行时与类型双重安全。

**catch-all**。`~~/server/api/foo/[...].ts` 会注册一条兜底路由，匹配所有没命中任何 handler 的请求（比如 `/api/foo/bar/baz`）；注释里写了两种读法：`event.context.path` 拿到完整路径，`event.context.params._` 拿到那段 `bar/baz`。想给这段起名字就用 `[...slug].ts`，通过 `event.context.params.slug` 读。

## 模块侧注册：一次一个 route

从模块里注册，走的是 `addServerHandler`。官方示例就是这个形状：

```ts
import { addServerHandler, createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options) {
    const { resolve } = createResolver(import.meta.url)

    addServerHandler({
      route: '/robots.txt',
      handler: resolve('./runtime/robots.get'),
    })
  },
})
```

对应的 runtime 文件 `runtime/robots.get.ts` 里 `export default defineEventHandler(() => ({ body: \`User-agent: *\nDisallow: /\` }))`，访问 `/robots.txt` 就得到那两行文本。

这里有几件事与目录约定不同，值得单独记：

- 路径必须用 `createResolver(import.meta.url)` 解析，不能写相对字符串——你的模块装在 `node_modules` 里，用户进程的当前目录跟你无关。
- `route` 是**精确匹配**，以 `/**` 结尾才把它下面的路径也一起匹配。这一页还有一条容易漏的规则：以 `/**` 结尾的路由**连它的基路径本身也匹配**，所以 `route: '/_fonts/**'` 会同时服务 `/_fonts` 和它下面的一切；而在 Nitro 2 那种只匹配基路径以下的主机上，Nuxt 会额外把基路径注册成第二条路由，好让一次注册在两边行为一致。
- `route` 传空字符串时，handler 被注册成**中间件**。
- 只在开发环境需要的路由用 `addDevServerHandler`，它会被排除在生产构建之外。文档给的实用例子是 Tailwind 配置查看器：先用 `joinURL(nuxt.options.app?.baseURL, '/_tailwind')` 拼出带 baseURL 的路径，再 `addDevServerHandler({ route, handler: viewerDevMiddleware })`。

`addServerHandler`、`addDevServerHandler` 两张参数表的逐项拆解，讲 Kit 服务端函数的两篇已经做过，这里不重复；只提一句 dev 那张表比正式的多一个 `meta`（路由元数据，例如 OpenAPI 操作信息），并且文档注明 Nitro v3 只在**非中间件**的 handler 上挂它。

## 想让模块的 server 目录按约定扫描

另一种做法是把整个目录交给 Nitro：`addServerScanDir(resolve('./runtime/server'))`，它会检查子目录，注册方式跟 `~~/server` 一样。这条有硬限制，文档写明了只有四个子目录会被扫：`~~/server/api`、`~~/server/routes`、`~~/server/middleware`、`~~/server/utils`。也就是说你在 `runtime/server/plugins/` 放东西，靠这个函数是不会被注册的。

还有一个相邻的函数是 `addServerImportsDir`（让 Nitro 扫描某个目录做自动导入），和 `addServerImports`（把指定名字注册进服务端的自动导入清单，示例是把 `@storyblok/vue` 的五个导出逐个加进去）。这一页对 `addServerImports` 挂了一条警告，讲的是跨上下文的共享：

> 如果你想提供一个在客户端和服务端都能用、并且能在 `shared/` 目录里使用的工具，那么这个函数必须被 `addImports` 和 `addServerImports` **从同一个源文件**导入，且签名完全一致。这个源文件不能导入任何上下文相关的东西（例如 Nitro 上下文、Nuxt 应用上下文），否则可能在类型检查阶段报错。

## 别忘了名字要带前缀

服务端路由是最容易撞车的一类导出。最佳实践那一页专门点了这一条：`/api/auth`、`/api/login`、`/api/user` 这类常见路径**很可能已经被应用自己用掉了**，模块要用自己模块名-derived 的前缀，两种写法是 `/api/_foo/...`（下划线前缀）和 `/_foo/...`（非 API 路由）。

## 注册之前把这四问答一遍

- 这条路由该落在 `api/`（要 `/api` 前缀）还是 `routes/`（不要）？模块侧则要看 `route` 写全了没有。
- 它是中间件吗？是的话，它不该返回值，而且 `addServerScanDir` 那种扫描方式与 `route: ''` 这种注册方式你要选一个。
- 需要按方法分开吗？文件名后缀 `.get`/`.post` 决定了未匹配方法是 405。
- 你的 runtime 目录准备让 Nitro 扫吗？只有那四个子目录会被扫，其他得逐个 `addServerHandler`。
