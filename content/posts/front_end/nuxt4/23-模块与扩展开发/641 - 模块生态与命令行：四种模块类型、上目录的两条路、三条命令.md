模块发出去之后有两件事决定它有没有人用：**别人能不能搜到它，以及装它要不要手改配置**。前者靠命名前缀，后者靠一条命令。这一篇把生态页与命令行页合起来讲。

## 先看规模那句话

生态页开场给的是一个数字：**Nuxt 模块生态代表每月超过 3500 万次 NPM 下载**，为各种工具提供扩展功能与集成。这句话的实际含义是：**你发出去的模块在一个已经有量级的分发面上，而那个面的入口就是命名规范**。

## 四种类型，四种前缀

| 类型 | 前缀或 scope | 谁做的 | 页面给的例子 |
| --- | --- | --- | --- |
| 官方模块 | `@nuxt/` | Nuxt 团队制作并由团队持续维护；像框架一样欢迎社区贡献 | `@nuxt/content` |
| 社区模块 | `@nuxtjs/` | **被验证过的（proven）**模块，由社区成员制作并维护，同样欢迎任何人贡献 | `@nuxtjs/tailwindcss` |
| 第三方与其他社区模块 | 通常是 `nuxt-` 开头 | 任何人都可以做；**用这个前缀能让它们在 npm 上被发现** | —— |
| 私有或个人模块 | 无要求 | 为你自己的场景或公司做的，**不需要遵守任何命名规则也能与 Nuxt 一起工作**，常见形态是挂在某个 npm 组织 scope 下 | `@my-company/nuxt-auth` |

三条值得单独读出：

**第一，`@nuxt/` 不等于"不接受外部贡献"**。原文说官方模块由团队制作与维护，但**像框架一样，非常欢迎社区贡献**。

**第二，`@nuxtjs/` 的门槛词是 "proven"**。这一档描述的是已被验证过的模块，不是"想用这个 scope 就能用"。

**第三，`nuxt-` 开头是给新想法准备的**。原文说这是"起草和试一个想法的最佳起点"——**它的收益是可发现性，而不是权威性**。

## 上目录只有一条路

任何社区模块都可以被列到模块清单上，**要上榜的动作是在 nuxt/modules 仓库开一个 issue**，用 `module_request.yml` 这个模板。页面还补了一句流程上的好处：**在你上榜之前，Nuxt 团队可以帮你把最佳实践应用到模块上**。

第二条路是转组织：**把模块移进 nuxt-modules 组织，就总有别人能帮忙，这样可以合力做出一个更完善的方案**。已经发布且能用的模块想转过去，同样是**在 nuxt/modules 开 issue**。

转过去能拿到两件东西，页面写得很具体：**模块可以被改名到 `@nuxtjs/` scope 下**，以及**文档可以拿到一个子域名**（形如 `my-module.nuxtjs.org`）。

## 使用侧的三条命令

### `nuxt module add`

```bash [Terminal]
npx nuxt module add <MODULENAME...> [--cwd=<directory>] [--logLevel=<silent|info|verbose>] [--skipInstall] [--skipConfig] [--dev] [--packageManager=<npm|pnpm|yarn|bun|deno|aube|nub|upm>]
```

一个参数：`MODULENAME...`——**可以一次给多个，用空格分隔**。

六个选项：

| 选项 | 默认 | 说明 |
| --- | --- | --- |
| `--cwd=<directory>` | `.` | 指定 Nuxt 项目根目录 |
| `--logLevel=<silent\|info\|verbose>` | | 指定构建期日志级别 |
| `--skipInstall` | | 跳过 npm 安装 |
| `--skipConfig` | | 跳过 `nuxt.config.ts` 更新 |
| `--dev` | | 把模块装成 dev 依赖 |
| `--packageManager=<...>` | | 用哪个包管理器安装 |

这条命令做的三件事按原文顺序：**用你的包管理器把模块装成依赖 → 把它加进 `package.json` → 更新你的 `nuxt.config`**。所以它是**三个动作而不是一个**，`--skipInstall` 与 `--skipConfig` 就是用来只保留其中一部分的。

```bash [Terminal]
npx nuxt module add pinia
```

**不写模块名直接跑，会进入选择列表，里面是与你当前 Nuxt 版本兼容的那些模块**。

一条 `::note`：`nuxt add` 是同一条命令，而且**它还接受分层（layers）**。

### `nuxt module remove`

```bash [Terminal]
npx nuxt module remove [MODULENAME...] [--cwd=<directory>] [--logLevel=<silent|info|verbose>] [--skipInstall] [--skipConfig]
```

选项是 add 的子集（四个，没有 `--dev` 与 `--packageManager`），**且 `--skipInstall` 这里的描述是"跳过依赖卸载"**。作用写得很清楚：**卸载包，并把它从 `nuxt.config` 的 `modules` 数组里删掉**。不带名字跑同样是进入选择列表，**这次列的是项目当前正在用的那些模块**。

### `nuxt module search`

```bash [Terminal]
npx nuxt module search <QUERY> [--cwd=<directory>] [--nuxtVersion=<3|4|4.2.0>] [--json]
```

| 选项 | 默认 | 说明 |
| --- | --- | --- |
| `--cwd=<directory>` | `.` | 指定 Nuxt 项目根目录 |
| `--nuxtVersion=<3\|4\|4.2.0>` | | 按 Nuxt 版本过滤、只列兼容的模块（**默认自动探测**） |
| `--json` | | 以 JSON 输出 |

参数 `QUERY` 是**要搜索的关键词**。搜索的行为描述里有两处细节：**结果是"与你的 Nuxt 版本兼容"的那些模块**，并且**每条会显示模块描述、把匹配到的文本高亮**。

`--json` 那句强调的是 **machine-readable**，也就是给脚本用的。

## 三条命令串起来的完整流程

在别人的项目里装一个模块，命令行这一侧的动线是：`nuxt module search 关键词` → `nuxt module add 名字`（它会同时改 `package.json` 与 `nuxt.config`）→ 不满意时 `nuxt module remove 名字`。

而"兼容"这件事在两节之间是闭环的：**搜索按你的 Nuxt 版本过滤、add 不带名字时只列兼容项**，这对应模块作者那一侧写在 `meta.compatibility` 里的 semver 约束——**版本不匹配时用户看到的是一条 WARN 并且模块被禁用**。生态页与前缀无关的那句话也在这里汇合：**写"for Nuxt"而不是"for Nuxt 3"，版本要求交给 `meta.compatibility`**。

## 两节都没写的部分

- **`--packageManager` 里 `aube`、`nub`、`upm` 三种没有任何解释**，页面只把枚举值列在选项签名里。
- **`nuxt module add` 具体往 `nuxt.config` 里写成什么形态**（包名字符串？还是带选项的元组？）文档未说明，只说"update your nuxt.config file"。
- **`search` 的数据源**是什么、多久更新一次，两节都没提。
- **模块上榜之后的展示顺序或分级**，生态页没写。
