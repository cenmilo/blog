## 交出去的第一个形态：一个虚拟文件

讲高级配方的那一页有个小节叫 Add Virtual Files，说法是：需要加一个可以被 import 进用户应用的虚拟文件时，用 `addTemplate`。示例是这样的形状：

```ts
import { addTemplate, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    // The file is added to Nuxt's internal virtual file system and can be imported from '#build/my-module-feature.mjs'
    addTemplate({
      filename: 'my-module-feature.mjs',
      getContents: () => 'export const myModuleFeature = () => "hello world !"',
    })
  },
})
```

注释那行就是用户侧的用法：**从 `#build/my-module-feature.mjs` 导入**。文档给的导出是一个普通函数，你要暴露的是一个组合式函数（比如名字里带 `use` 的那个），形状完全一样，只是 `getContents` 返回的那串代码内容不同。

服务端要另一个版本，文档紧接着给了 `addServerTemplate`：

```ts
import { addServerTemplate, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    // The file is added to Nitro's virtual file system and can be imported in the server code from 'my-server-module.mjs'
    addServerTemplate({
      filename: 'my-server-module.mjs',
      getContents: () => 'export const myServerModule = () => "hello world !"',
    })
  },
})
```

这两页在 `addServerTemplate` 的写法上并不完全一致，值得留意：讲 Kit 模板的那页示例把 `filename` 写成 `#my-module/test.mjs`，而它下面"在 runtime 文件里"的导入却写成 `import { test } from '#my-module/test.js'`，一个是 `.mjs` 一个是 `.js`。**文档没有解释这个差异**，实际要按哪个来，只能在自己的项目里两种都试一次再定。

## `addTemplate` 的七个字段，每个都影响你交出去的东西

模板对象或一个字符串路径都可以传；传字符串时会被转成对象并把 `src` 设成那个字符串值。

| 字段 | 类型 | 必填 | 文档说明 |
| --- | --- | --- | --- |
| `src` | `string` | 否 | 模板路径。不提供 `src` 就必须提供 `getContents` |
| `filename` | `string` | 否 | 模板文件名。不提供就由 `src` 路径生成，此时 `src` 是必需的 |
| `dst` | `string` | 否 | 目标文件路径。不提供就由 `filename` 和 Nuxt 的 `buildDir` 生成 |
| `options` | `Options` | 否 | 传给模板的选项 |
| `getContents` | `(data: Options) => string \| Promise<string>` | 否 | 会被 `options` 对象调用的函数，返回字符串或解析成字符串的 Promise。**如果提供了 `src`，这个函数会被忽略** |
| `write` | `boolean` | 否 | 设为 `true` 时模板写到目标文件，否则只存在于虚拟文件系统里 |
| `dependsOn` | `Array<'pages' \| 'plugins'> \| ((change: { event, path }, ctx: { nuxt, app, options }) => boolean)` | 否 | 除 `nuxt.options` 与应用结构之外，模板输出还依赖哪些被监视的输入 |

三行最实用：

- `write: true` 是把文件真落盘的那一个开关。
- `dependsOn: []` 的意思是这个模板从不读取被监视文件的内容，于是 dev 里文件改动时 Nuxt 可以不去重算它。文档在最后给了结论性的那句：**什么都没声明的模板，会在每一次改动时重新生成**。
- `getContents` 与 `src` 是互斥的两种来源，同时给了的话前者被忽略。

## 配置改了，虚拟文件怎么跟着改

高级配方那一页给的三行很短：在 `builder:watch` 里判断改动的路径是否包含某个配置文件，命中就调 `updateTemplates`：

```ts
nuxt.hook('builder:watch', (event, path) => {
  if (path.includes('my-module-feature.config')) {
    // This will reload the template that you registered
    updateTemplates({ filter: t => t.filename === 'my-module-feature.mjs' })
  }
})
```

讲 Kit 的那页给的完整示例多做了两件事，而这两件事是实际会踩到的：

```ts
nuxt.hook('builder:watch', async (event, relativePath) => {
  if (event === 'change') {
    return
  }

  const path = resolve(nuxt.options.srcDir, relativePath)
  if (updateTemplatePaths.some(dir => path.startsWith(dir))) {
    await updateTemplates({
      filter: template => template.filename === 'routes.mjs',
    })
  }
})
```

第一件是先对 `event === 'change'` 早退——也就是**只对新增和删除之类的动作重新生成，普通内容改动不重新生成**。第二件是把 `builder:watch` 给的相对路径先 `resolve(nuxt.options.srcDir, relativePath)` 再比较前缀，因为回调给的是相对路径，而你要比较的是绝对目录。

`updateTemplates` 只有一个选项 `filter`，不传 filter 就**重新生成所有模板**。这句话在开发时是有代价的：一个项目里的模板不止你模块那一个。

## 类型这一半：三个层次按需要选

第一层，`addTypeTemplate`。它的定位是：把模板渲染进项目的 buildDir，然后把它注册为类型。文档说得很具体——它既写盘，也会在生成的 `nuxt.d.ts` 里加一条指向它的引用。字段是 `addTemplate` 那五个（`src`、`filename`、`dst`、`options`、`getContents`），没有 `write` 和 `dependsOn`。

关键是第二个参数 `context`：

| 属性 | 类型 | 必填 | 文档说明 |
| --- | --- | --- | --- |
| `nuxt` | `boolean` | 否 | 设为 `true` 时，类型加进 Nuxt 上下文 |
| `nitro` | `boolean` | 否 | 设为 `true` 时，类型加进 Nitro 上下文 |

**省略 `context` 时，类型只会被加进 Nuxt 上下文。**这是模块类型"在应用里红、在服务端也红"最常见的来源：服务端要用，得写 `{ nitro: true }`。

第二层，`prepare:types` 钩子。需要更细的控制时，文档给的做法是注册一个回调去注入类型：

```ts
const template = addTemplate({ /* template options */ })
nuxt.hook('prepare:types', ({ references }) => {
  references.push({ path: template.dst })
})
```

注意这里用的是 `template.dst`，也就是 `addTemplate` 的返回值里那个目标路径。

第三层，直接改 TypeScript 配置。文档列了四种，形状完全一致：

```ts
// extend tsconfig.app.json
nuxt.options.typescript.tsConfig.include ??= []
nuxt.options.typescript.tsConfig.include.push(resolve('./augments.d.ts'))

// extend tsconfig.shared.json
nuxt.options.typescript.sharedTsConfig.include ??= []
nuxt.options.typescript.sharedTsConfig.include.push(resolve('./augments.d.ts'))

// extend tsconfig.node.json
nuxt.options.typescript.nodeTsConfig.include ??= []
nuxt.options.typescript.nodeTsConfig.include.push(resolve('./augments.d.ts'))

// extend tsconfig.server.json
nuxt.options.typescript.serverTsConfig.include ??= []
nuxt.options.typescript.serverTsConfig.include.push(resolve('./augments.d.ts'))
```

`??= []` 这一步不是可有可无的：`include` 可能本来就没有值，直接 push 会炸。

或者用钩子版本，按上下文分开加引用——`prepare:types` 的回调参数里有 `references`（应用上下文）、`sharedReferences`（shared）、`nodeReferences`（node）三个，服务端上下文则走 `nitro:prepare:types` 的 `references`。文档在这里补了一条：TypeScript 的 references 会把文件加进类型上下文，**不受 `tsconfig.json` 里 `exclude` 选项的影响**。

## 目录本身就已经在上下文里了

Augment Types 那一节说：Nuxt 会自动把模块的目录纳入相应的类型上下文，所以大多数情况下你只要把声明文件放对目录。三个对应关系：

- `my-module/runtime/` —— 应用类型上下文（`runtime/server` 目录除外）
- `my-module/runtime/server/` —— 服务端类型上下文
- `my-module/` —— node 类型上下文（`runtime/` 与 `runtime/server` 两个目录除外）

文档配的目录树就是这个意思：

```bash [Directory Structure]
-| my-module/   # node type context
---| runtime/   # app type context
------| augments.app.d.ts
------| server/ # server type context
---------| augments.server.d.ts
---| module.ts
---| augments.node.d.ts
```

## 那一条已知的限制，正好卡住服务端虚拟文件

文档专门列了一个"已知限制"：服务端路由除了用 `tsconfig.server.json` 检查，**还会再用 `tsconfig.app.json` 检查一遍**。原因是 Nuxt 要推断你服务端接口的返回类型，好在 `$fetch` 和 `useFetch` 里给出响应类型。

后果写在同一条 warning 里：如果一个模块用 `addServerTemplate` 造了一个只在服务端用的虚拟文件，并把它的类型声明放在 `tsconfig.server.json` 里，那么这些类型只在服务端上下文可见；等应用上下文去检查这些服务端路由文件时，它认不出这些"只在服务端"的类型，就会报错。文档给的解决办法只有一句：**很遗憾，这类类型也得在应用上下文里再声明一遍。**

所以一个模块要交出去的东西如果是服务端虚拟文件，`addTypeTemplate` 的 `context` 两个都设成 `true`（或者两次调用分别进两个上下文）才是完整做法。

## 交付前的三项自查

- 用户侧的导入路径写清楚了吗：应用侧是 `#build/文件名`，服务端是文档给的那个 specifier，两处示例不一致时以实测为准。
- 类型进了哪些上下文：`addTypeTemplate` 不给 `context` 就只进 Nuxt 上下文。
- dev 会不会太吵：模板没声明 `dependsOn` 就会每次改动都重新生成；`updateTemplates` 不带 filter 会重生成所有模板。
