## 两条前置规则，先定死目录和路径

基础配方那一页在讲组合式函数的小节末尾挂了一条 note，位置很靠后，但它管着前面所有小节：

> 所有本来应该放在你的 `app/` 目录里的组件、页面、组合式函数和其他文件，都需要放在 `runtime/app/` 里。这样它们才能被正确地进行类型检查。

另一条规则写在代码注释里：`// Create resolver to resolve relative paths`。所有指向 runtime 文件的路径都通过 `createResolver(import.meta.url)` 出来的 `resolve` 来写，而不是字符串相对路径——你的模块最终会装在 `node_modules` 里。

## 第一步：注册一个插件

插件是模块加运行时逻辑最常见的入口，文档的说法是"Plugins are a common way for a module to add runtime logic"，函数是 `addPlugin`：

```js
import { addPlugin, createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    // Create resolver to resolve relative paths
    const resolver = createResolver(import.meta.url)

    addPlugin(resolver.resolve('./runtime/plugin'))
  },
})
```

这里有一个和上面那条 note 冲突的细节值得留意：插件路径写的是 `./runtime/plugin`，**没有** `app/` 段，而组件示例写的却是 `runtime/app/components/...`。文档没有解释插件为什么不在 `runtime/app/` 下；`addPlugin` 的参数与 `order` 取值区间在讲 Kit 插件函数那篇已经逐项给过，这里不重复。

## 第二步：给一个组件

组件用 `addComponent`，把它作为自动导入交给 Nuxt 解析。文档给了两个并列的例子，区别只在来源：

```ts
import { addComponent, createResolver, defineNuxtModule, useRuntimeConfig } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    const resolver = createResolver(import.meta.url)

    // From the runtime directory
    addComponent({
      name: 'MySuperComponent', // name of the component to be used in vue templates
      export: 'MySuperComponent', // (optional) if the component is a named (rather than default) export
      filePath: resolver.resolve('runtime/app/components/MySuperComponent.vue'),
    })

    // From a library
    addComponent({
      name: 'MyAwesomeComponent', // name of the component to be used in vue templates
      export: 'MyAwesomeComponent', // (optional) if the component is a named (rather than default) export
      filePath: '@vue/awesome-components',
    })
  },
})
```

三个字段各自的含义都写在注释里：`name` 是**在模板里要用的那个名字**，`export` 可选、当组件是具名导出（而不是默认导出）时才需要，`filePath` 可以是 resolver 解析出来的路径，也可以直接是一个库的模块说明符。

组件多起来的时候用整目录的形式 `addComponentsDir`。目录形式的代价是名字由文件名决定，所以前缀这件事要在文件名上做——文档在最佳实践那页给的建议就是拿模块名当前缀（例如模块叫 `nuxt-foo` 时用 `<FooButton>` 而不是 `<Button>`）。

## 第三步：给一个组合式函数

`addImports` 负责把组合式函数加进自动导入清单：

```ts
import { addImports, createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    const resolver = createResolver(import.meta.url)

    addImports({
      name: 'useComposable', // name of the composable to be used
      as: 'useMyComposable', // optional alias that will be available for the consuming apps
      from: resolver.resolve('runtime/app/composables/useComposable'), // path of composable
    })
  },
})
```

三个字段里 `as` 是最容易被忽略的：它给**使用方项目**提供一个别名，也就是说用户那边叫 `useMyComposable`，而你文件里导出的叫 `useComposable`。多条可以传数组：

```ts
addImports([
  { name: 'useFirstComposable', from: resolver.resolve('runtime/composables/useFirstComposable') },
  { name: 'useSecondComposable', from: resolver.resolve('runtime/composables/useSecondComposable') },
])
```

整目录用 `addImportsDir(resolver.resolve('runtime/composables'))`。

注意这两段里路径是 `runtime/composables/...`，而上一段单条示例里是 `runtime/app/composables/...`，同一条 note 又要求应用侧文件放 `runtime/app/` 下。**这一页自己的示例路径就是不一致的**，文档没有说明哪一种是准。落地时按那条 note 走 `runtime/app/composables/`，然后确认可用：在 playground 里不写 import 直接调用一次，再看类型有没有报错——只跑通不报错不代表类型也对。

另外这一页对导出前缀又强调了一次，用词是 "highly recommended"：给你的导出加前缀，避免与用户代码或其他模块冲突。

## 第四步：需要跨服务端与客户端保持一致状态时

这一小节讲的是一个不太常见但很具体的问题：有些函数要在 SSR 和客户端水合之间保持状态一致，文档举的例子是 Nuxt 自带的 `useState` 和 `useAsyncData`。机制是这样的：**当一个函数被注册之后，Nuxt 的编译器会在它被调用时传入的参数少于指定个数时，自动注入一个额外的参数作为 key**，这个 key 在服务端渲染和客户端水合之间保持稳定。注入的 key 是**由文件路径和调用位置算出来的哈希**。

注册方式是把配置塞进 `nuxt.options.optimization.keyedComposables`：

```ts
import { createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    const resolver = createResolver(import.meta.url)

    nuxt.options.optimization.keyedComposables.push({
      name: 'useMyState',
      source: resolver.resolve('./runtime/composables/state'),
      argumentLength: 2,
    })
  },
})
```

这张配置表只有三行：

| 属性 | 类型 | 说明 |
| --- | --- | --- |
| `name` | `string` | 函数名。默认导出用 `'default'`（可调用的名字会从文件名按 camelCase 推出） |
| `source` | `string` | 函数定义所在文件的已解析路径，支持 Nuxt 别名（`~`、`@` 等） |
| `argumentLength` | `number` | 函数接受的最大参数个数。调用时参数少于这个数就会注入唯一 key |

`argumentLength` 这个字段决定注入与否：调用时给的参数比它少，编译器才补 key。

## 第五步：把模块选项交给运行时

配方页在这一节把理由说得很清楚：**模块不是应用运行时的一部分，所以模块选项也不是**。要在运行时读到它们，官方推荐走 Nuxt 的 `runtimeConfig`：

```js
import { defineNuxtModule } from '@nuxt/kit'
import { defu } from 'defu'

export default defineNuxtModule({
  setup (options, nuxt) {
    nuxt.options.runtimeConfig.public.myModule = defu(nuxt.options.runtimeConfig.public.myModule, {
      foo: options.foo,
    })
  },
})
```

这里用 `defu` 而不是直接赋值，文档专门解释了：**这样是扩展用户提供的 public 运行时配置，而不是覆盖它**。运行时侧读取跟读其他配置一样：

```js
import { useRuntimeConfig } from '@nuxt/kit'

const options = useRuntimeConfig().public.myModule
```

紧跟着的那条警告是这一步唯一的安全边界，原话值得贴在代码评审里：

> 注意不要把任何敏感的模块配置暴露在 public 运行时配置上，例如私有 API key，因为它们最终会进入公开打包产物。

## 改配置这件事也有对应写法

配方页的第一节给的是直接改 Nuxt 配置，例子是打开一个实验特性：

```js
nuxt.options.experimental ||= {}
nuxt.options.experimental.componentIslands = true
```

注释解释了第一行为什么要写：`experimental` 这个对象在用户配置里可能还不存在，先补上再赋值。改动更复杂的配置时，文档的建议是改用 `defu`。

## 填完这四类能力之后要验的三件事

- 目录：所有本该在 `app/` 下的东西确实在 `runtime/app/` 下；示例之间路径不一致时以 note 为准。
- 解析：每一处指向 runtime 的路径都过了 resolver，没有裸的相对字符串。
- 边界：`runtimeConfig.public` 里没有密钥；需要服务端私有的值放非 public 那一层。
