## 第一类：不会报错，但会把用户的项目拖慢或弄脏

这四条来自最佳实践那一页，反着读就是错误清单。

**一、把耗时逻辑留在 `setup` 里。**Nuxt 会等你的模块 setup 完成才继续下一个模块、才启动开发服务器与构建，超过 **1 秒** Nuxt 就发出警告。正确做法是把耗时的事推迟到钩子，把一次性的事放进 `onInstall` / `onUpgrade`。

**二、导出名字不加前缀。**配置、插件、API、组合式函数、组件、服务端路由这六类都要带模块名前缀。反面例子在这一页被点名了：`/api/auth`、`/api/login`、`/api/user` 这类路径**很可能已经被应用用掉了**。

**三、每次构建都重做初始化。**文档对生命周期钩子的定位就是"避免每次构建都做不必要的工作"。判断标准很朴素：同一个项目里连跑两次 dev，第二次不该再建一遍数据库结构或再写一遍配置文件。

**四、README 不回答三个问题。**为什么用、怎么用、它做了什么。顺带缺的还有可运行的 StackBlitz 最小复现——那不只是友好，它让用户能把复现直接发回给你。

另外三条（TypeScript 友好、原生 ESM、措辞不绑版本号并改用 `meta.compatibility`、沿用 starter 的默认工具与 ESLint 配置）在检查清单那篇已经逐条给了验证动作，这里不重复。

## 第二类：服务端兼容页列出的失败方式

这一页的前提写在开头：Nuxt 3 与 4 目标 Nitro v2（`nitropack`，用 `h3` v1），Nuxt 5 默认 Nitro v3（`nitro`，用 `h3` v2），还可以用基于 Web API 的自定义服务端运行时（`nuxt/server`），它到处都能跑。页面第一句 note 也界定了范围：**模块没有服务端代码，这一页全部不适用**。

下面十一个点，每一条都有原文对应。

**1. 注册了主机跑不了的 handler，会被跳过并警告。**原文：Nuxt 会根据用户用的服务端构建器挑最合适的 handler；**如果你注册的 handler 用户的构建器跑不了，它会被跳过，并附带一条警告**。所以表现不是报错而是"我的接口怎么 404 了"，要看构建输出里那条警告。

**2. 只给一个 variant，就永远测不到另一个。**在 `nitropack` v2 主机上 Nuxt 优先 `nitro2`，**只有当 `nuxt` 变体是唯一注册的那个时才会在那里跑**。文档因此明确要求：在 Nuxt 5 上测 `nuxt` 变体。要专门测 `nuxt` 变体，就在测试 fixture 里把 `server.builder` 设成非 Nitro 的构建器（例如 `@nuxt/vite-server`）——因为 `nitropack` v2 上永远优先 `nitro2`、`nitro` v3 上永远优先 `nitro3`。

**3. `handler` 的对象写法有依赖前提。**原文用重要提示框写着：对象形态需要 `@nuxt/kit@^4.6` 出现在模块的 **`dependencies`** 里（模块 starter 就是这么配的）。如果 `@nuxt/kit` 只是 devDependency 且在构建时留作 external，或者被放成 peerDependency，**跑的是应用侧那份版本，而低于 4.6 的版本会在对象 `handler` 上失败**。

**4. 类型检查需要额外的 devDependency。**要检查 `nuxt` 文件得装 `nuxt@>=4.6` 作为 devDependency；要检查 `nitro3` 文件还得装 `nitro`。少装的表现是运行正常但编辑器/CI 报类型。

**5. 在 Nuxt 5 的 playground 与测试 fixture 里，h3 自动导入的 `defineEventHandler` 不可用。**文档明写：那时要从 `nuxt/server` 导入它。

**6. dev handler 的 `nuxt` 变体不能从模块代码里 import `nuxt/server`。**`nuxt/server` 只给服务端代码用，而 dev handler 的每个变体是**模块代码里的函数、跑在 Nuxt 进程里**而不是在服务端构建里。文档要求：按 Web 的 `Request`/`Response` 写 handler、在 `setup` 里从 `nuxt.options` 读配置，再逐个适配各服务端 API。示例因此从 `h3` 导入 `defineEventHandler` 和 `toWebRequest`，并要求**把 `h3@^1` 加进模块的 `dependencies`**。

**7. dev handler 的路径匹配在各主机上不一样。**`nitropack` v2 主机上每个变体都按**路径前缀**匹配（Nitro v2 的行为），于是 `/_my-module` 连 `/_my-module/inter.woff2` 也会吃掉；Nitro v3 上 `nuxt` 与 `nitro3` 变体是精确匹配。要所有变体都覆盖下面的路径，路由以 `/**` 结尾——**而在 `nitropack` v2 主机上这条需要 `@nuxt/kit@^4.6.1` 进 `dependencies`**。同一节还有一条会影响读路径的代码：v2 主机上 `event.path` 是相对路由 base 的（请求 `/_my-module/assets/inter.woff2` 时它等于 `/inter.woff2`），完整 URL 要从 `toWebRequest()` 或 `nuxt` 变体的 `event.req.url` 拿。

**8. 工具函数的参数类型别写 `H3Event`。**如果模块暴露吃 event 的工具（通过别名、`addServerImports` 或类型模板），文档要求参数标成 `nuxt/server` 的 `RequestEvent`，或者只标它实际读的那部分。**写成 `H3Event` 就只能接受某一个 h3 大版本的 event，这个工具在 `nuxt/server` handler 里就调不了**。

**9. `getNitroVersion` 回答不了"主机跑的是哪套服务端 API"。**它报的是 Nitro 的大版本；而**换了 `server.builder` 的主机一个 Nitro 变体都不跑**。用它做兼容判断会判错方向。

**10. 判断不出来时按 `nitro2` 处理。**Nuxt 会读注册文件的 import 来决定它用哪套 API，所以你通常不需要声明；不够用时才写 `meta.compatibility.server`（例如 `server: 'nuxt'`）。原文那句底线是：**如果我们分辨不出来，代码会被当作 `nitro2`**。

**11. 有些领域根本没有 `nuxt` 变体。**基于服务端插件、storage 或缓存的模块**没有 `nuxt` 变体可注册**，因为 `nuxt/server` 不覆盖这些区域；文档的做法是现在就按 `nitro2` 注册，等移植时再加 `nitro3`。Tasks 也明确**不被 `nuxt/server` 支持**。

## 那张五行对照表，逐行落地

一个文件如果 import 了 `nitro/*`，就会被读成 **Nitro 3 代码**，所以 `nitro2` 文件必须改用 `h3` 与 `nitropack/*`。五行原文：

| 区域 | 在 `nitro2` 文件里 | 在 `nitro3` 文件里 |
| --- | --- | --- |
| Storage：`useStorage()` 及其驱动配置 | `nitropack/runtime` | `nitro/storage` |
| 缓存：`defineCachedEventHandler()`、`defineCachedFunction()` | `nitropack/runtime` | `nitro/cache` |
| 服务端插件 | `defineNitroPlugin()` from `nitropack/runtime` | `definePlugin()` from `nitro` |
| Nitro 自己的运行时钩子，例如 `request` 与 `error` | `useNitroApp().hooks` from `nitropack/runtime` | `useNitroHooks()` from `nitro/app` |
| 懒加载 handler：`lazyEventHandler()` | `h3` | `nitro/h3` |

顺带一条 tip：因为 `defineNitroPlugin` 是个恒等函数，**你可能可以把它换成一个类型注解**，从而写出对 `nitro2` 与 `nitro3` 都可移植的代码。

## `nuxt/server` 到底覆盖到哪

文档给了一份清单：请求与响应相关的工作都在内——handler、错误、路由参数、query 与 body 的读取和校验、请求头、CORS、cookies、会话、重定向、路由规则、运行时配置、应用配置、用 `serverFetch()` 的进程内 fetch、用 `useServerHooks()` 的运行时钩子。**但 Nitro 管的东西多得多**，需要这些区域时就得留在 Nitro 自己的导入里（放进 `nitro2` 或 `nitro3` 文件）。

类型侧也有对应分工：要给模块新增的运行时配置键做类型，就增强 `nuxt/schema` 的 `RuntimeConfig` 或 `PublicRuntimeConfig`，**这样 `nuxt`、`nitro2`、`nitro3` 三种文件里都能拿到类型**。而 `H3Event`（给 `useRequestEvent()`）和完整的 Nitro 配置这类构建器专属类型来自生成的 `.nuxt/nuxt.d.ts`；**没有它，它们会退化成与构建器无关的类型（`RequestEvent` 和缩减版的 Nitro 配置）**。

## 一次评审按这两组过

- 体验组四条：setup 有没有超过 1 秒、六类导出有没有前缀、初始化是否重复执行、README 三问是否齐。
- 兼容组：`@nuxt/kit` 是否在 `dependencies` 且版本够、变体是否在两代主机上都测过、dev handler 是否按 `Request`/`Response` 写、工具函数参数是否用了 `RequestEvent`、涉及 storage/缓存/插件/Tasks 的部分是否清楚它们没有 `nuxt` 变体。
