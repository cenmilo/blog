用了三层四层之后，最先撞上的问题不是"怎么装"，而是"这个组件到底是谁的那份"。这套规则一共三级，两处控制手段，还有一条关于路径解析的坑。

## 三级优先级

入门页与作者页各写了一份，**内容完全相同**：

> 1. **Your project files** - always have the highest priority
> 2. **Auto-scanned layers** from `~~/layers` directory - sorted alphabetically (Z has higher priority than A)
> 3. **Layers in `extends`** config - first entry has higher priority than second

翻译过来是：**你的项目文件永远最高**；**自动扫描到的层按字母序排，靠后的字母优先级更高**（Z > A）；**`extends` 里的层，第一项高于第二项**。

目录那一页给的是同一套，措辞略有差别："**当多个层定义了同一资源（组件、组合式函数、页面等）时，优先级高的层胜出**"，并补了一句"**层按字母序排序，靠后的字母优先级更高**"。

一个具体的推论值得单独看：**字母序意味着命名会决定行为**。`layers/a-base/` 与 `layers/z-theme/` 同时放 `Button.vue`，**用哪个不由语义决定，而由首字母决定**——这就是下一条控制手段存在的理由。

## 控制手段一：数字前缀

目录页给的写法是三个例子：`1.base/`、`2.features/`、`3.admin/`。

入门页把它展开成一张目录树，并**在注释里标出每一档的优先级**：

```bash [Directory structure]
layers/
  1.base/        # Lowest priority
  2.features/    # Medium priority
  3.admin/       # Highest priority (among layers)
```

配一句 `::tip`：**这个模式适合做出"带默认值的 base 层，被更具体的层逐步覆盖"**。

作者页给的是**同一件事的另一种举例，并且刻意把字母与数字反向配对**：

```
~/layers/1.z-layer、~/layers/2.a-layer
```

于是 **`2.a-layer` 的优先级高于 `1.z-layer`**——这个例子的价值就在于它证明了**数字前缀压过了字母本身**：一个叫 `a-layer` 的层，因为前缀是 2，赢过叫 `z-layer` 而前缀是 1 的那个。

## 控制手段二：不改名，用 `extends` 排序

入门页给的第二条路更省事：**从 `nuxt.config` 里控制 `~~/layers` 目录的顺序，而不重命名目录**，做法是把这些目录写进 `extends`：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: [
    '~~/layers/admin', // highest priority
    '~~/layers/features',
    '~~/layers/base', // lowest priority (among the listed layers)
  ],
})
```

这一句是三种写法里最容易被误用的部分，因为它把"自动扫描"变成了"显式声明"。规则写得很细：

> Both `~~/...` (recommended) and `~/...` alias forms as well as relative paths (`./layers/admin`) are supported. Any layer in `~~/layers` that you do not list keeps its alphabetical auto-scan order, ranked below the layers you list in `extends`.

三点：**`~~/` 是推荐写法，`~/` 与相对路径也支持**；**没被列出的层不会被忽略，它们保持字母序位置**；**但它们整体排在"你列出的那些"之下**。

也就是说：**一旦你开始用 `extends` 排序，"列出与否"本身就是一级优先关系**，比字母序更强。

目录页对同一件事的表述简短一些，并额外提到 `~~/layers/admin` 这种写法（**它给的例子用 `~~/` 前缀**），而入门页的例子用相对路径 `'../base'` 与 `~~/layers/...` 混合——**两处的路径写法并不一致，但都是被支持的形态**。

## 一个完整例子

入门页给了把两种来源混起来的那一种：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: [
    '../base', // Local layer outside project
    '@my-themes/awesome', // NPM package
    'github:my-themes/awesome#v1', // Remote repository
  ],
})
```

如果此时项目里还有一个 `~~/layers/custom`，最终顺序是：

- 你的项目文件（最高）
- `~~/layers/custom`
- `../base`
- `@my-themes/awesome`
- `github:my-themes/awesome#v1`（最低）

这一串里有两个信息：**自动扫描到的 `custom` 排在所有 `extends` 项之前**（即使它没被列出），以及 **`extends` 内部严格按数组顺序**。

作者页对此补了一句结论："**你的项目文件会覆盖任何层，而 `~~/layers/custom` 会覆盖 `extends` 里的任何东西**"——**这句话与上面那份列表一致，可以当成校验口径**。

入门页还有一个组件级的例子，讲的是"同名文件在多层里"的取舍：

```bash [Directory structure]
layers/
  1.base/
    app/components/Button.vue    # Base button style
  2.theme/
    app/components/Button.vue    # Themed button (overrides base)
app/
  components/Button.vue          # Project button (overrides all layers)
```

结论两句：**只有层存在时用 `2.theme/Button.vue`（字母/数字序更高）**；**项目里有 `app/components/Button.vue` 时它覆盖所有层**。

## 两条路径解析的坑

作者页的 Tips 一节讲了两件与"合并"直接相关的事，**它们的共同点是：层里的路径不是按层自己解析的**。

**第一条**：在层的组件与组合式函数里用全局别名（`~/`、`@/`）导入时，**这些别名相对的是用户项目的路径**。**官方给的对策是用相对路径，或者用命名层别名（`#layers/名字`）**。

**第二条**：层的 `nuxt.config` 里用相对路径时（**`extends` 的嵌套是例外**），**它们同样相对用户的项目而不是这个层**。对策是**在配置里用完整解析后的路径**：

```ts [nuxt.config.ts]
import { fileURLToPath } from 'node:url'
import { dirname, join } from 'node:path'

const currentDir = dirname(fileURLToPath(import.meta.url))

export default defineNuxtConfig({
  css: [
    join(currentDir, './app/assets/main.css'),
  ],
})
```

这三行 `node:url`／`node:path` 的组合是**唯一被官方给出的"让层引用自己的文件"的办法**，与模块那边用 `createResolver(import.meta.url)` 是同一思路的两种写法。

## 合并是怎么发生的

作者页最后一节把实现点名列出：**配置加载与 `extends` 支持由 unjs/c12 处理，合并使用 unjs/defu，远程 git 来源通过 unjs/giget 支持**，并附一个 GitHub issue 链接说明图层支持仍在持续开发。

这条链上还有一处**与"覆盖"不同的能力**：从 v4.3 起可以**把某个模块的配置键设成 `false` 来禁用它**，用途正是"层带了我不需要的模块"：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['./base-layer'],
  // Disable modules from the layer by setting their config key to false
  image: false, // Disables @nuxt/image
  pinia: false, // Disables @pinia/nuxt
})
```

页面补了三点：**配置键由各模块自己定义**（举了 `image`、`pinia`、`content` 三例，**要查模块文档确认它的键**）；**适用场景**（层里有你用不到的模块、你想换一种实现、特定环境要关掉分析类模块）；**以及一个副作用**——**设成 `false` 会让该模块的 setup 不运行，但仍然为它生成类型**，而且**这招对你自己项目里的模块同样有效，不只是层带来的**。

模块侧的"关掉它"这一句在两页各写一遍，措辞一致（配置键、类型仍生成、用于关层带来的模块）。

## 三条自查

1. 多层同名组件出问题，**先查是不是只靠字母序**在决定，然后再决定是加数字前缀还是改用 `extends` 排序。
2. 一旦开始用 `extends` 排 `~~/layers`，**检查是否有没列出的层被你默认当成"参与排序"了**——它们整体沉到已列出的下面。
3. 层里的配置或组件用了 `~/`、`@/` 或相对路径，**按上面那两条坑逐处替换**（组件里换相对/`#layers`，配置里换解析后的绝对路径）。

未记载的部分：**`extends` 与自动扫描同时存在且层数很多时，是否有第四级 tie-breaker**（没有写）；`shared/` 目录在层里出现时谁覆盖谁（清单只有一页提到它，规则部分没覆盖）；以及"资源类型不同（组件 vs 页面 vs 配置键）是否共用同一套优先级"——页面只对"同一资源"下了结论。
