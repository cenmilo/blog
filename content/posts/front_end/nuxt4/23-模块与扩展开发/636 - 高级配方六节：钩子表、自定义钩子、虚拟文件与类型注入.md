模块写到这里会出现两类新需求：**在框架的某个时刻做点什么**（钩子），以及**让用户的项目认识你造出来的东西**（文件与类型）。这两类都有静默失败的写法，这一页把它们分开了。

## 六节各解决什么

| 节 | 需求 | 用什么 |
| --- | --- | --- |
| Use Lifecycle Hooks | 挂到 Nuxt 的生命周期上 | 定义里的 `hooks` map 或 `nuxt.hook` |
| Create Custom Hooks（`###`） | 让别人能订阅你的模块 | 在 `modules:done` 里 `nuxt.callHook` |
| Add Virtual Files | 造一个用户能 import 的文件 | `addTemplate` / `addServerTemplate` |
| Update Virtual Files | 让虚拟文件重算 | `updateTemplates({ filter })` |
| Add Type Declarations | 给用户项目加类型 | `addTypeTemplate` 或 `prepare:types` |
| Extend TypeScript Config | 把文件塞进某个类型上下文 | 改 `nuxt.options.typescript.*` 或 references |
| Augment Types | 从模块自己的目录增强类型 | 按目录放置声明文件 |

页面自己是 6 个 `##`，其中 Create Custom Hooks 与 Known Limitations 各是一个 `###`，最后还挂了一个 `####`。

## 钩子有两条挂法

定性句：**生命周期钩子让你扩展 Nuxt 的几乎每一个方面，模块可以通过编程方式挂，也可以通过定义里的 `hooks` map 挂**。

```js
import { addPlugin, createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  // Hook to the `app:error` hook through the `hooks` map
  hooks: {
    'app:error': (err) => {
      console.info(`This error happened: ${err}`)
    },
  },
  setup (options, nuxt) {
    // Programmatically hook to the `pages:extend` hook
    nuxt.hook('pages:extend', (pages) => {
      console.info(`Discovered ${pages.length} pages`)
    })
  },
})
```

两种挂法在同一个示例里并存：`app:error` 走 map，`pages:extend` 走 `nuxt.hook`。**map 那种不需要等 setup 跑**，钩子名是带层级的字符串（`app:error`、`pages:extend`、`modules:done`）。

紧跟着一条 `::note`，标题就叫 **Module cleanup**：

> If your module opens, handles, or starts a watcher, you should close it when the Nuxt lifecycle is done. The `close` hook is available for this.

```ts
nuxt.hook('close', async (nuxt) => {
  // Your custom code here
})
```

三种动作都被点名了：**打开、持有、启动 watcher**。开发服务器反复重启时，没关的 watcher 会一份份叠上去，表现是内存和文件描述符一直在涨——**这类问题不在构建期暴露，只在长时间开着 dev 之后暴露**。

## 自定义钩子要在 `modules:done` 里调用

模块也可以定义并调用自己的钩子，页面称这是"让模块可扩展的有力模式"。条件句是本页最重要的一条时序规则：**如果你期望其他模块能订阅你的钩子，就应该在 `modules:done` 钩子里调用它**，理由写得很具体——**这确保了所有其他模块都有机会在自己的 `setup` 里完成设置、并向你的钩子注册监听器**。

```ts
// my-module/module.ts
import { defineNuxtModule } from '@nuxt/kit'

export interface ModuleHooks {
  'my-module:custom-hook': (payload: { foo: string }) => void
}

export default defineNuxtModule({
  setup (options, nuxt) {
    // Call your hook in `modules:done`
    nuxt.hook('modules:done', async () => {
      const payload = { foo: 'bar' }
      await nuxt.callHook('my-module:custom-hook', payload)
    })
  },
})
```

如果直接在 `setup` 里 `callHook`，**比你的模块后加载的那些还没注册监听，你的钩子就空跑了一次**。这里没有任何报错。示例同时给了类型侧的半边：用 `export interface ModuleHooks` 声明钩子名与载荷类型，钩子名带模块前缀加冒号（`my-module:custom-hook`）。

## 虚拟文件：客户端与服务端是两个工具

```ts
addTemplate({
  filename: 'my-module-feature.mjs',
  getContents: () => 'export const myModuleFeature = () => "hello world !"',
})
```

注释写明了导入面：**文件加入 Nuxt 的内部虚拟文件系统，可以从 `#build/my-module-feature.mjs` 导入**。

服务端要**换成 `addServerTemplate`**：

```ts
addServerTemplate({
  filename: 'my-server-module.mjs',
  getContents: () => 'export const myServerModule = () => "hello world !"',
})
```

注释同样给了导入面，但**这次是裸文件名：可以从 `'my-server-module.mjs'` 导入**（它进的是 Nitro 的虚拟文件系统）。两个函数的差别就是这两处：工具不同、导入前缀不同。

要更新已注册的文件，用 `updateTemplates`，官方给的是配合 `builder:watch`：

```ts
nuxt.hook('builder:watch', (event, path) => {
  if (path.includes('my-module-feature.config')) {
    // This will reload the template that you registered
    updateTemplates({ filter: t => t.filename === 'my-module-feature.mjs' })
  }
})
```

`filter` 拿到的是模板对象、按 `filename` 筛。**这是本页唯一一处"配置文件变了要让模板重算"的写法**。

## 类型：三个工具与一条目录规则

`addTypeTemplate` 的定位是**同时**写一份模板到磁盘、并在生成的 `nuxt.d.ts` 里加一条引用：

```js
addTypeTemplate({
  filename: 'types/my-module.d.ts',
  getContents: () => `// Generated by my-module
    interface MyModuleNitroRules {
      myModule?: { foo: 'bar' }
    }
    declare module 'nitropack/types' {
      interface NitroRouteRules extends MyModuleNitroRules {}
      interface NitroRouteConfig extends MyModuleNitroRules {}
    }
    export {}`,
})
```

要增强 Nuxt 管的类型就用这招：`declare module` 打开 Nitro 的类型模块，往 `NitroRouteRules` 与 `NitroRouteConfig` 两个接口上合。

需要更细的控制时改走钩子：

```ts
const template = addTemplate({ /* template options */ })
nuxt.hook('prepare:types', ({ references }) => {
  references.push({ path: template.dst })
})
```

注意这里引用的是 `template.dst`（模板的**目标路径**），不是 `filename`。

扩展 tsconfig 有两条路。**最简的**是直接改配置，四个上下文各一行：`nuxt.options.typescript.tsConfig`、`sharedTsConfig`、`nodeTsConfig`、`serverTsConfig`，写法都是 `include ??= []` 然后 push。**或者**用 `prepare:types` 与 `nitro:prepare:types` 两个钩子分别推 references：前者解构出 `references`、`sharedReferences`、`nodeReferences` 三个数组（依次是 app、shared、node 上下文），后者只管 server 上下文。

一条 `::note` 值得单独记：**TypeScript references 是把文件加进类型上下文，不受 `tsconfig.json` 里 `exclude` 的影响**。所以想用 exclude 排除掉某个被 reference 进来的文件是无效的。

## 目录决定类型上下文

增强类型最省事的做法是**不配置**，只放对位置。页面给的规则是三条：

- `my-module/runtime/` —— **app 类型上下文**（但 `runtime/server` 目录除外）
- `my-module/runtime/server/` —— **server 类型上下文**
- `my-module/` —— **node 类型上下文**（但 `runtime/` 与 `runtime/server` 除外）

```bash [Directory Structure]
-| my-module/   # node type context
---| runtime/   # app type context
------| augments.app.d.ts
------| server/ # server type context
---------| augments.server.d.ts
---| module.ts
---| augments.node.d.ts
```

**声明文件的名字是 `augments.*.d.ts` 这种形态，靠目录而不是靠配置来选上下文**；要从任意位置增强，才回去用上面那节改 tsconfig。

## 那条限制：服务端路由被检查两次

Known Limitations 下面只有一个 `####`：**服务端路由除了用 `tsconfig.server.json`，还会额外用 `tsconfig.app.json` 做类型检查**。原因写得明白：**Nuxt 要推断服务端端点的返回类型，才能在 `$fetch` 与 `useFetch` 里给出响应类型**。

`::warning` 说清了后果与解法：如果模块用 `addServerTemplate` 造了一个**仅服务端的虚拟文件**、又把它的类型声明放进 `tsconfig.server.json`，那么**app 上下文在类型检查你的服务端路由时认不出这些仅服务端类型，会报错**。原文给的对策带着一个 "unfortunately"：**这类类型需要也在 app 上下文里声明一份**。

这页没写的：`addTemplate` 其余入参、钩子的完整清单（跳去 api/advanced/hooks）、以及 `ModuleHooks` 接口如何被 Nuxt 读取（示例只 export 了它，没有注册步骤）。
