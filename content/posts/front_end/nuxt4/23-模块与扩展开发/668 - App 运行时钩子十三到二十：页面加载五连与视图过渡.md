想在切页面时显示进度条、或者想知道预取什么时候发生——这一组八行就是答案，而且**它们的触发条件里有两条明确写着"要开某个开关"**。

## 八行照录

| 钩子 | 参数 | 环境 | 描述 |
| --- | --- | --- | --- |
| `link:prefetch` | `to` | Client | 当一个 `<NuxtLink>` 被观察到将要被预取时调用 |
| `page:start` | `pageComponent?` | Client | 在 `NuxtPage` 内部 Suspense 的 pending 事件上调用 |
| `page:finish` | `pageComponent?` | Client | 在 `NuxtPage` 内部 Suspense 的 resolved 事件上调用 |
| `page:loading:start` | - | Client | 当一次路由导航开始（**在解析之前**）或页面 key 变化时调用。**页面被复用时（例如在 `definePageMeta` 里给了静态 `key`）它会触发而页面组件的 `setup()` 不会重跑** |
| `page:loading:end` | - | Client | 在 `page:finish` 之后调用 |
| `page:transition:finish` | `pageComponent?` | Client | 在页面过渡的 onAfterLeave 事件之后 |
| `dev:ssr-logs` | `logs` | Client | 当一组服务端日志已被传到客户端时带一个数组调用（**需要 `features.devLogs` 启用**） |
| `page:view-transition:start` | `transition` | Client | 当实验性的 viewTransition 支持启用时，**在 `document.startViewTransition` 被调用之后**调用；`transition` 参数是一个 `ViewTransition` 对象，它有一个可读可改的 `types` 属性（`ViewTransitionTypeSet`） |

**这一组八行没有一行标 `Server`**——**全部只在浏览器里跑**，服务端渲染阶段看不到它们。

## 页面加载那一串

四个 `page:` 开头的钩子构成一组，**能确定的顺序只有一条**：

| 关系 | 依据 |
| --- | --- |
| `page:loading:end` 在 `page:finish` **之后** | 描述原文就是一句 "Called after `page:finish`" |
| `page:start` 与 `page:finish` 成对 | 两条描述分别是同一个 Suspense 的 **pending** 与 **resolved** 事件 |
| `page:loading:start` 在"导航开始、解析之前" | 描述里的括号 "(before resolution)" |

**其余的先后关系文档没有给**——比如 `page:loading:start` 与 `page:start` 谁先到，**表里没有写过**，要顺序保证只能实测。

参数形状也值得注意：**`page:start`、`page:finish`、`page:transition:finish` 三条都是 `pageComponent?`（可选）**，而 **`page:loading:start`／`page:loading:end` 两条完全没有参数**（`-`）。

**所以想拿组件实例的进度逻辑应该挂在 `page:start`/`page:finish`，只想要"开始／结束"信号的是 `page:loading:*`。**

## `page:loading:start` 那句括号最有用

这一条的描述比别处长得多，多出来的部分是一条行为警告：**页面被复用时（例如在 `definePageMeta` 里给了静态 `key`），它会触发，而页面组件的 `setup()` 不会重跑。**

这解释了两种常见的困惑：

**第一种：进度条闪一下但数据没变。** 因为 `page:loading:start` 讲的是"导航开始了"，**不等于组件会重建**。

**第二种：以为换页就会重跑 setup。** 只要 `key` 不变，同一组件实例会被复用，**只有页面 key 变化才会带来新的加载周期**。

反过来用它也有价值：**要检测"用户点了链接但组件没换"这种情况，恰好就是这个钩子给了信号而 `setup()` 没跑**——这是文档在这一行里给出的唯一组合关系。

## 预取与两条需要开关的

**`link:prefetch`** 说的是**"`<NuxtLink>` 被观察到将要被预取的那一刻"**，参数是 `to`（要去的那个目标）。

它对应的是链接预取那套行为：**什么时候会预取（可见性、空闲、悬停这些策略）在链接与导航那一章讲，本表只说明这个钩子在被观察到预取时触发**。**要统计"预取实际发生了多少次"，这个钩子是唯一给到的信号点**。

**剩下两条各带一个前置开关**：

| 钩子 | 需要的开关 |
| --- | --- |
| `dev:ssr-logs` | **`features.devLogs` 启用**（否则服务端日志不会传到客户端，这个钩子也就不会有内容） |
| `page:view-transition:start` | **实验性的 viewTransition 支持启用**，且时机在 `document.startViewTransition` 被调用之后 |

`dev:ssr-logs` 只在开发形态有意义（名字里就写着 `dev`），参数 `logs` 是一个数组。

**注意 `dev:ssr-logs` 这个名字在运行时表和 Nitro 表里各有一行**：运行时这条是"客户端收到了一组服务端日志"（参数 `logs`），**Nitro 那条是"一个请求周期结束时产生这组日志"（参数 `{ path, logs }`）**。**同名不同侧，别把两个搞混**。

## 视图过渡那一行能改什么

`page:view-transition:start` 是这八行里唯一说明"参数可以被修改"的：**`transition` 是一个 `ViewTransition` 对象，它的 `types` 属性可读也可写**（类型是 `ViewTransitionTypeSet`），表里同时链到 MDN 的两个页面。

**这意味着在这里可以按页面调整过渡类型集合**——这是文档给出的能力边界，**其余的 View Transition API 行为都在 MDN，不在这张表里**。

它的前置条件也写在同一句里：**必须启用实验性的 viewTransition 支持**（表里链到过渡那一章的 "View Transitions (API experimental)" 一节）。

## 用法建议

| 想做的事 | 挂哪个 |
| --- | --- |
| 顶部进度条的开始与结束 | `page:loading:start` ＋ `page:loading:end`（无参数，够用） |
| 需要页面组件实例 | `page:start`／`page:finish`／`page:transition:finish` |
| 统计或拦截预取 | `link:prefetch` |
| 自定义过渡类型 | `page:view-transition:start`（**要先开实验开关**） |
| 把服务端日志搬到客户端展示 | `dev:ssr-logs`（**要先开 `features.devLogs`**） |

**过渡相关还有一条不在这一组**：`page:transition:finish` 对应的是 `onAfterLeave`，而"离开前"的那个时机**在这张表里没有对应行**——表里只给了 finish 这一个。

这一组未记载的还有：`page:loading:start` 与 `page:start` 的顺序、导航被中断（例如中间件重定向）时这几个钩子各自是否补齐"end"、以及 `link:prefetch` 与预取被跳过时的行为差别。
