## 发布前先看这一屏

模块的开发循环很短，出问题往往不是功能没做出来，而是它把别人的项目弄慢、弄脏、或者名字撞了。官方在两节里把这件事说全了：一页是作者实践，一页是怎么测。下面是逐条换成动作的版本。

## 九条实践，每条后面跟一个动作

**一、异步 setup 的耗时。**文档的规则是：Nuxt 会等你的模块 setup 完成，才继续下一个模块、才启动开发服务器和构建流程，所以要**把耗时的逻辑推迟到 Nuxt 钩子里**；配套那条警告是 setup 超过 **1 秒** Nuxt 就发出警告。发布前的动作就是打开一个装了你这模块的项目跑 `nuxt dev`，看终端里有没有那条超时警告——有就是这条没过。

**二、导出要带前缀。**这一条覆盖配置、插件、API、组合式函数、组件、服务端路由六类，理由是避免与其他模块、Nuxt 内部实现、用户自己的代码冲突，建议用模块名做前缀。组件、组合式函数、服务端路由的三行对照表在讲前缀那一节已经完整给过，服务端路由还额外给了 `/api/_foo/...` 与 `/_foo/...` 两种写法。发布前的动作：把模块注册出去的每个名字逐个列一遍，看有没有裸的 `Button`、`useData`、`/api/auth`。

**三、一次性工作放生命周期钩子。**文档给的分工很明确：生成配置文件、建数据库结构、装依赖这类**一次性的**任务用 `onInstall`，版本相关的迁移用 `onUpgrade`，`setup` 里只留每次构建都要做的（示例是 `addServerHandler({ /* ... */ })`）。这样"避免每次构建都做不必要的工作"。发布前的动作：在 playground 里连跑两次 `nuxt dev`，第二次不该重做初始化。

**四、TypeScript 友好。**原话是：Nuxt 对 TypeScript 是一等支持，模块暴露类型、用 TypeScript 开发，**即使用户不直接写 TypeScript 也能受益**。动作：确认包里有 `.d.ts`，且在 JS 项目里装上不报错。

**五、原生 ESM。**只有一句：Nuxt 依赖原生 ESM，并让你去读 Native ES Modules 那一节。动作：查 `package.json` 的 `type` 与导出格式，别留 CommonJS 的 `require`。

**六、README 要回答三个问题。**文档列的三问是：为什么用这个模块、怎么用这个模块、这个模块做了什么。它还补了一句：链接到集成站点和文档总是个好主意。动作：把 README 从头读一遍，三问是否各自有答案。

**七、给一个可运行的演示。**这条不只是"贴心"，文档写清了它的双重用途：用你的模块做一个最小复现，放到 [StackBlitz](https://nuxt.new/s/v4)，加进 README——它既让潜在用户能快速试验，**也让他们在遇到问题时能直接把最小复现发回给你**。动作：链接点得开、打开就能跑。

**八、措辞别绑版本号。**原话：Nuxt、Nuxt Kit 和其他新工具在设计时同时考虑了向前和向后兼容，所以请用"X for Nuxt"而不是"X for Nuxt 3"，以免生态分裂；版本约束改用 `meta.compatibility` 来表达。动作：搜一遍 README 和包描述里硬写的 "for Nuxt 3"。

**九、跟 starter 的默认约定。**文档的落脚点是：模块 starter 自带一套默认工具和配置（举例是 ESLint 配置），如果你打算把模块开源，**沿用这些默认值能让你的模块和其他社区模块保持一致的代码风格**，别人提 PR 更容易。动作：跑 starter 带的 lint，别带着自定义规则发布。

## 三类测试各自能验到哪

讲测试的那一节只分了三个小节，能力差别很大，得按实际情况预期。

**单元测试那一节其实没有内容。**它整节只有一条 tip：仍在讨论和探索如何简化 Nuxt 模块的单元测试与集成测试，并给了一个 RFC 链接让你参与讨论。**所以 4.x 文档没有官方推荐的模块单测写法**，这条要提前知道，别在发布计划里给它留工时。

**端到端测试是完整的一条路。**文档点名 Nuxt Test Utils 是做这件事的库，并给了五步工作流：

1. 在 `test/fixtures/*` 里建一个作为"fixture"的 Nuxt 应用
2. 在测试文件里把这个 fixture 配好并启动 Nuxt
3. 用 `@nuxt/test-utils` 提供的工具与 fixture 交互（例如抓一个页面）
4. 针对这个 fixture 做断言（例如"HTML 里包含……"）
5. 重复

fixture 侧的配置文件就是一个真的 `nuxt.config.ts`，从相对路径 import 你的模块源码：

```ts [test/fixtures/ssr/nuxt.config.ts]
// 1. Create a Nuxt application to be used as a "fixture"
import MyModule from '../../../src/module'

export default defineNuxtConfig({
  ssr: true,
  modules: [
    MyModule,
  ],
})
```

测试文件是文档原样的四步落地：

```ts [test/rendering.ts]
import { describe, expect, it } from 'vitest'
import { fileURLToPath } from 'node:url'
import { $fetch, setup } from '@nuxt/test-utils/e2e'

describe('ssr', async () => {
  // 2. Setup Nuxt with this fixture inside your test file
  await setup({
    rootDir: fileURLToPath(new URL('./fixtures/ssr', import.meta.url)),
  })

  it('renders the index page', async () => {
    // 3. Interact with the fixture using utilities from `@nuxt/test-utils`
    const html = await $fetch('/')

    // 4. Perform checks related to this fixture
    expect(html).toContain('<div>ssr</div>')
  })
})

// 5. Repeat
describe('csr', async () => { /* ... */ })
```

三个细节值得注意：`describe` 的回调本身是 `async`，`setup` 在里面被 `await`；断言的是**渲染出来的 HTML 字符串**包含某段标记；文档最后那句 tip 说这种流程的示例在模块 starter 的 `test/basic.test.ts` 里。

**手工测试那条路是"在别人项目里跑"。**文档给了两级：开发时直接用 starter 内置的 playground 应用；要测**不在你模块仓库里的项目**，就用 `npm pack`（或你包管理器等价的命令）从模块打一个 tarball，然后在测试项目的 `package.json` 里写成 `"my-module": "file:/path/to/tarball.tgz"`，装完之后就能像引用普通项目一样引用 `my-module`。

这一步很关键，因为它测的是发布产物而不是 `src` 目录——playground 里能跑、发布后跑不了，通常是这里的差异造成的。

## 发布前那一次过一遍

- dev 启动没有超过 1 秒的 setup 警告。
- 六类导出全部带前缀，服务端路由走了 `/api/_模块名/`。
- 一次性工作不在 `setup` 里，连跑两次 dev 不重做初始化。
- README 三问齐、演示链接可点、没有 "for Nuxt 3" 这类硬版本号。
- starter 的 lint 与测试全绿；E2E 至少一个 fixture 断言了 HTML。
- 用 `npm pack` 出的 tarball 在一个外部项目里装得上、跑得起来。
