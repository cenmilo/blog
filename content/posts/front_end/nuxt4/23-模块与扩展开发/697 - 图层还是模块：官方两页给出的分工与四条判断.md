## 两页各自怎么说自己

讲图层的那页第一句是：图层是一个强大的系统，让你能扩展默认文件、配置等等；它的目录结构**几乎与标准 Nuxt 应用相同**，所以容易写也容易维护。一个最小图层只需要有一个 `nuxt.config.ts` 表明自己是图层。

讲模块的那页第一句是：模块是一组**在启动 Nuxt 开发模式或构建生产项目时按顺序运行的函数**；有了模块，你可以把自定义方案封装起来、正式地测试它、并作为 npm 包分享出去，而不必往项目里加多余的样板，也不必要求 Nuxt 本身做改动。

一句话概括分工：**图层复用文件与配置，模块复用代码与构建行为。**

## 图层会被自动扫描的十类东西

作者指南那页把可继承的位置逐条列了出来：

- `app/components/*` 扩展默认组件
- `app/composables/*` 扩展默认组合式函数
- `app/layouts/*` 扩展默认布局
- `app/middleware/*` 扩展默认中间件
- `app/pages/*` 扩展默认页面
- `app/plugins/*` 扩展默认插件
- `app/utils/*` 扩展默认工具
- `app/app.config.ts` 扩展默认应用配置
- `server/*` 扩展默认服务端端点与中间件
- `nuxt.config.ts` 扩展默认 Nuxt 配置

这份清单本身就是答案的一半：**你要复用的东西如果落得进这十类，就不需要写模块**。入门那页给的用途清单也从同一个方向说话：共享配置预设（`nuxt.config` 与 `app.config`）、组件库、工具与组合式函数库、模块预设、跨项目的标准 setup、主题，以及大型项目里用分层架构落实领域驱动设计。

## 覆盖是图层独有的能力，也是它的风险

图层有三行优先级，从高到低：**你的项目文件** → **`~~/layers` 目录里自动扫描的图层（按字母序，Z 压过 A）** → **`extends` 里的图层（排在前的压过排在后的）**。可以用数字前缀控制自动扫描的顺序（`1.base`、`2.theme`、`3.admin`），也可以在 `extends` 里显式列出 `~~/layers/admin` 这样的路径而不改目录名——**没被列出的那些保持字母序，整体排在已列出的之下**。

模块没有这种"同名文件谁赢"的机制。模块注册组件用 `addComponent`/`addComponentsDir`，注册组合式函数用 `addImports`，冲突靠命名前缀和 `priority` 解决，而不是靠目录覆盖。

需要"基础层给默认、主题层改外观、项目层最终裁定"的时候，图层这条链是现成的。需要"根据配置决定生成什么"的时候，只有模块能写那段逻辑。

## 反过来，这四件事图层做不到

**一、执行任意代码。**图层能带 `nuxt.config.ts`，但那还是配置；要在构建期判断版本、读文件、按条件注册路由，得是模块函数。

**二、禁用继承来的模块之外的定制。**图层这一页给了 v4.3 的关闭方式：把模块的配置键设成 `false`（`image: false`、`pinia: false`、`content: false`），这会让 setup 不跑但**仍然生成该模块选项的类型**。这是"减法"，不是"改写"。

**三、可靠的相对路径。**这一页把坑写得很明白：图层里用 `~/`、`@/` 这类全局别名时，**它们是按用户项目的路径解析的**，绕开办法是用相对路径或命名图层别名；`nuxt.config` 里的相对路径同样按用户项目解析（嵌套 `extends` 例外），所以官方建议用完整解析后的路径：

```ts [nuxt.config.ts]
import { fileURLToPath } from 'node:url'
import { dirname, join } from 'node:path'

const currentDir = dirname(fileURLToPath(import.meta.url))

export default defineNuxtConfig({
  css: [
    join(currentDir, './app/assets/main.css'),
  ],
})
```

**四、远程图层的依赖可见性。**这页有一条 warning：如果你把远程源当图层继承，**图层自己的依赖在 Nuxt 之外是访问不到的**——它们装在 `node_modules/.c12/层名/node_modules/` 里，你的包管理器看不见它。举的例子很具体：远程图层依赖一个 eslint 插件，那个插件在你的 eslint 配置里就用不了。所以官方明确推荐**把图层内容发成 npm 包**（公开或私有都行），或者把远程 git URL 直接加成依赖。

## 命名别名：两页都在讲的那件事

`~~/layers` 里自动扫描的图层会自动得到别名，比如 `~~/layers/test` 可以从 `#layers/test` 访问（v3.16.0 起）。其他图层想要别名，就在自己的配置里写 `$meta.name`：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  $meta: {
    name: 'example',
  },
})
```

这会产生 `#layers/example`。也可以在 `extends` 的元组选项里给 `meta.name` 覆盖。

这个别名对模块作者同样有用：它给了一个跨层的稳定导入路径，绕开上面第三条的路径解析问题。

## 四条判断，按顺序问

- **要复用的是文件还是行为？**十个可扫描目录装得下，用图层；需要跑代码（读文件、判断版本、按配置注册）用模块。
- **需不需要"同名覆盖"？**需要就图层，优先级三行已经够表达基础层、主题层、项目层。
- **跨项目还是同一个仓库内？**同一个仓库内的局部图层可以直接放 `~~/layers`；跨项目要么发 npm 包（图层和模块都适用），要么接受远程图层带来的依赖不可见。
- **要不要改类型、构建配置或服务端行为？**这四样只能走模块：`addTemplate`/`addTypeTemplate` 造文件与类型、`extendViteConfig` 或 `addVitePlugin` 改打包、`addServerHandler` 一类注册服务端资产。

两条路也常常叠着用：**图层里放模块预设**是官方列出的用途之一——主题层负责外观与被覆盖的组件，模块负责构建期的接线。

## 这一组编号到此结束

模块这一段还剩最后一篇：调试那一页给了什么手段（sourcemaps 的默认状态、`--inspect`、两套 IDE 配置），以及模块自己为什么不在那些被调试的代码里。
