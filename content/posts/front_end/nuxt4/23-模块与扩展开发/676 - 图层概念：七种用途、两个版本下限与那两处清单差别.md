把三个项目共用的那套组件、配置和页面抽出来——这件事在 Nuxt 里不靠复制粘贴，靠图层。这一节先说清它是什么、能干什么，以及哪两个版本是分水岭。

## 两节各讲什么

两节的描述句**逐字相同**："Nuxt 提供了一个强大的系统，让你能扩展默认文件、配置以及更多内容"。所以从标题分辨：一节是入门里的 Layers，另一节是 **Authoring Nuxt Layers**。

**入门页**管四件事：能用它做什么、`~~/layers` 的自动注册、`extends` 的写法、优先级。**作者页**管另外四件：一个层最少要有什么、starter 命令、发布（git 或 npm）、两条路径解析的坑。

作者那一节开头还有一句互相引用：**先读入门那一节**。两节之间是循环链接，**从哪一节进来都会被告知另一节的存在**，这点比多数章节做得好。

## 一个层最少有什么

作者页给的下限是一句："**一个最小的 Nuxt 层目录应该包含一个 `nuxt.config.ts` 文件，用来表明它是一个层**"。

```ts [base/nuxt.config.ts]
export default defineNuxtConfig({})
```

**空的 `defineNuxtConfig({})` 就够**——这个文件的作用是"标记"，不是"配置"。

结构上的相似度是这套系统的卖点，原话是：**图层的结构与一个标准 Nuxt 应用几乎相同，这让它们很容易编写和维护**。

## 七种用途

入门页的 Use Cases 一节列了七条，逐条落地形态不同：

| 用途 | 原文给的形态 |
| --- | --- |
| 跨项目共享可复用的配置预设 | 用 `nuxt.config` 与 `app.config` |
| 做组件库 | 用 `app/components/` 目录 |
| 做工具与组合式函数库 | 用 `app/composables/` 与 `app/utils/` |
| 做 Nuxt 模块预设 | Create Nuxt module presets |
| 跨项目共享标准设置 | Share standard setup across projects |
| 做 Nuxt 主题 | Create Nuxt themes |
| 在大型项目里做代码组织 | **实现模块化架构并支持 Domain-Driven Design（DDD）** |

这七条里前四条是"把某类文件装进层"，后三条是"用一个层表达一整套约定"。**目录那一节还有一句同样的话，并且点明了它更适合的场景**：大代码库的 DDD、UI 库或主题、配置预设、把 admin 面板或功能模块分开。

## 两个版本下限

自动注册与别名各有各的版本号，都在 `::note` 里：

| 能力 | 起始版本 | 表现 |
| --- | --- | --- |
| `~~/layers` 目录自动注册为层 | **Nuxt v3.12.0** | 项目里 `~~/layers` 下的任何层**会被自动注册**，不用写进 `extends` |
| 命名层别名 | **Nuxt v3.16.0** | 为每个层的 `srcDir` 自动创建别名，**`~~/layers/test` 可以通过 `#layers/test` 访问** |

**这两条是分开的**：3.12 到 3.16 之间，层会被自动注册，但你**没有 `#layers/名字` 这个导入面**。目录那一节对同一件事再确认一遍（自动注册 v3.12.0+、命名别名 v3.16.0）。

想给"不在 `~~/layers` 里的层"也要一个别名，作者页给的办法是写 `$meta.name`：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  $meta: {
    name: 'example',
  },
})
```

这会产出 `#layers/example` 指向你的层。**`$meta` 这个键在配置参考里没有条目**（作者页也没解释它属于哪族配置），它只在这里出现。

## 最小可用的一对文件

作者页的基本示例是四份文件一起看的：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: [
    './base',
  ],
})
```

```vue [app/app.vue]
<template>
  <BaseComponent />
</template>
```

```ts [base/nuxt.config.ts]
export default defineNuxtConfig({
  // Extending from base nuxt.config.ts!
  app: {
    head: {
      title: 'Extending Configs is Fun!',
      meta: [
        { name: 'description', content: 'I am using the extends feature in Nuxt!' },
      ],
    },
  },
})
```

```vue [base/app/components/BaseComponent.vue]
<template>
  <h1>Extending Components is Fun!</h1>
</template>
```

这份例子里能读出三件事：**项目侧 `app.vue` 直接用了 `<BaseComponent />`，没有任何 import**（组件由层的 `app/components/` 自动进入）、**层里的组件路径写作 `base/app/components/`**（**层内部也是 `app/` 那一族目录**）、**层的 `nuxt.config.ts` 可以只做 head 这类配置**，与项目配置合并。

## 两份"哪些内容会被自动扫描"的清单

作者页列了会被自动扫描并用于"扩展默认值"的条目，一共 **10 项**：

- `app/components/*` —— 扩展默认组件
- `app/composables/*` —— 扩展默认组合式函数
- `app/layouts/*` —— 扩展默认布局
- `app/middleware/*` —— 扩展默认中间件
- `app/pages/*` —— 扩展默认页面
- `app/plugins/*` —— 扩展默认插件
- `app/utils/*` —— 扩展默认 utils
- `app/app.config.ts` —— 扩展默认 app config
- `server/*` —— 扩展默认服务端端点与中间件
- `nuxt.config.ts` —— 扩展默认 nuxt config

`layers/` 目录那一节也有一份，叫 Layer Content，**11 项**。两处差别有两点：

**第一，目录页多出一项 `shared/`**（"app 与服务端之间共享的代码"），作者页的清单里没有它。**而 `shared/` 是 4.x 新目录结构里被单独讲过的一个目录**，所以这不算矛盾，只是**作者页那份清单没跟上**——要确认层里能不能放 `shared/`，应以目录页那份为准。

**第二，同一个东西两处写法不同**：作者那一节写 `app/app.config.ts`，目录那一节写 `app.config.ts`（链接都指向 app-config 那一节）。**`app.config.ts` 到底该放在层根的 `app/` 里还是层根，两节的字面不一致**，这一处不做推断，放文件时以能生效的那个位置为准。

除这两点外，两份清单覆盖的内容一致，且都强调"auto-imported"这一族（组件、composables、utils）。

## 从零起一个层

作者页给的是一条命令：

```bash [Terminal]
npm create nuxt -- --template layer nuxt-layer
```

**模板名是 `layer`**，指向 nuxt/starter 的 layer 分支；后续步骤**页面让你去看那个模板自己的 README**，两节都没有列下一步。

## 什么时候用哪种写法

入门那一节对此只给了一句判据，而且**同一句话在两节的顺序是颠倒的**：

| 场景 | 用 |
| --- | --- |
| 属于你项目的一部分的本地层 | `~~/layers` 目录 |
| 外部依赖（npm 包、远程仓库）或项目目录之外的层 | `extends` |

（入门页把这个对比放在优先级一节里，作者页放在"When to Use Each"小节里，**两处内容一致、条目顺序相反**。）

这一节未记载的部分：`~~/layers` 的自动扫描深度（层里再套 `layers/` 会怎样，两节都没说）、`#layers/名字` 别名是否可用于运行时导入、以及 starter 的 layer 模板具体生成了哪些文件——**页面只给了命令，没给目录树**。
