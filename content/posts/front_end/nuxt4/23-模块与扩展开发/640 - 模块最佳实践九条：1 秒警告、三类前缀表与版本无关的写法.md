模块会装进别人的项目里，所以模块作者写的每一行都影响别人的构建时间。这一节九条规矩里，**能被验证的只有三条**——其余六条更像是约定。先说能验证的。

## 一、异步 setup 有一条 1 秒线

模块可以是异步的，页面举的例子是**要请求某个 API 或调用某个异步函数**。紧接着是这一节的核心警告：

> be careful with asynchronous behaviors as Nuxt will wait for your module to setup before going to the next module and starting the development server, build process, etc. Prefer deferring time-consuming logic to Nuxt hooks.

**等待是三重的**：等你的模块 setup 完 → 才轮到下一个模块 → 才起开发服务器或开始构建。所以 `setup` 里那一次网络请求，会串行加在每个人的冷启动上。给出的对策就一句：**耗时的逻辑推给 Nuxt 钩子**。

`::warning` 把这条量化了：

> If your module takes more than **1 second** to setup, Nuxt will emit a warning about it.

这条的实际用处是**自我检测**：起 dev 时看到那条警告，就说明该把 `setup` 里的东西挪进钩子回调了。挪到哪里、挪到哪个钩子，这一节没有给具体清单。

## 二、前缀表管三类东西

要求是：**任何暴露出去的 configuration、plugin、API、composable、component 或 server route 都要有一个显式前缀**，目的是避免与别的模块、Nuxt 内部实现或用户自己写的代码冲突。**理想情况下用模块自己的名字当前缀**，示例给的是模块叫 `nuxt-foo`：

| 类型 | ❌ 避免 | ✅ 推荐 |
| --- | --- | --- |
| 组件 | `<Button>`、`<Modal>` | `<FooButton>`、`<FooModal>` |
| 组合式函数 | `useData()`、`useModal()` | `useFooData()`、`useFooModal()` |
| 服务端路由 | `/api/track`、`/api/data` | `/api/_foo/track`、`/api/_foo/data` |

**列举的六类里只有三类进了表**，剩下三类（configuration、plugin、API）没有给出对应形态——不要以为只有这三类需要前缀。

### 服务端路由单独一节

`### Server Routes` 说这是**尤其重要**的一类，理由很具体：**`/api/auth`、`/api/login`、`/api/user` 这类常见路径很可能已经被应用自己用了**。推荐两种前缀形态：

- `/api/_foo/...`（用下划线开头的前缀）
- `/_foo/...`（非 API 的路由）

这与基础配方页那三条 tip 是同一个要求的两种表述——**配方页在组件、组合式函数、服务端路由三处各重复了一次"给导出加前缀"**。

## 三、一次性任务用生命周期钩子

场景列举是**生成配置文件、准备数据库、安装依赖**这类：

```ts
import { addServerHandler, defineNuxtModule } from 'nuxt/kit'
import { isLess } from 'verkit'

export default defineNuxtModule({
  meta: {
    name: 'my-database-module',
    version: '1.0.0',
  },
  async onInstall (nuxt) {
    // One-time setup: create database schema, generate config files, etc.
    await generateDatabaseConfig(nuxt.options.rootDir)
  },
  async onUpgrade (nuxt, options, previousVersion) {
    // Handle version-specific migrations
    if (isLess(previousVersion, '1.0.0')) {
      await migrateLegacyData()
    }
  },
  setup (options, nuxt) {
    // Regular setup logic that runs on every build
    addServerHandler({ /* ... */ })
  },
})
```

这一节给的理由是"**防止每次构建都做不必要的工作**，并带来更好的开发体验"。示例里三行的角色很清楚：`onInstall` 只跑一次、`onUpgrade` 按 `previousVersion` 分支处理迁移、**`setup` 是"每次构建都跑的那部分"**。

用这节时必须记得另一页给的两条硬约束：**`meta.name` 与 `meta.version` 都要给**（钩子靠它们在 `.nuxtrc` 里追踪状态），且**钩子抛错只记录、不中断构建**。

顺带一提，这个示例的导入面写的是 `nuxt/kit`，而 Kit 与配方那几页写的是 `@nuxt/kit`；**两节用了两种 specifier，文档没有说明差别**。

## 后面六条没有量化标准

| 条 | 页面的说法 | 有没有判据 |
| --- | --- | --- |
| Be TypeScript Friendly | Nuxt 对 TypeScript 是一等集成；暴露类型、用 TS 开发，**即使用户不直接写 TS 也受益** | 无 |
| Use ESM Syntax | Nuxt 依赖原生 ESM，请去读原生 ES 模块那一节 | 无 |
| Document Your Module | readme 里考虑写三问：为什么用这个模块、怎么用、这个模块做了什么；链接到集成站点的文档总是好主意 | 三问可核对 |
| Provide a Demo | 做一个最小复现并放到 StackBlitz（`nuxt.new/s/v4`），加进 readme | 可核对：有没有 demo 链接 |
| Stay Version Agnostic | 用"X for Nuxt"而不是"X for Nuxt 3"以免生态割裂；用 `meta.compatibility` 设版本约束 | 命名可核对 |
| Follow Starter Conventions | starter 自带一套工具与配置（例如 ESLint），开源模块沿用它就能与其他社区模块风格一致、**便于别人贡献** | 可 diff |

其中"版本无关"那条是唯一给了解释的生态理由：**Nuxt、Nuxt Kit 与新工具都是按向前与向后兼容来设计的**，所以名字里钉住某个大版本会割裂生态；版本约束该由 `meta.compatibility` 承担（它对应的是不匹配时那条 WARN 并禁用模块的机制，而不是改名字）。

## 交付前能核对的清单

按可验证程度排：

1. 起一次 dev，**看有没有那条 setup 超过 1 秒的警告**。
2. 全项目搜一遍你注入的组件名、composable 名与服务端路由，**确认都带模块前缀**，路由用 `/api/_模块名/` 形态。
3. 检查 `meta` 里是否同时有 `name` 和 `version`（用了生命周期钩子就是必须的），并确认一次性逻辑不在 `setup` 里。
4. readme 能不能回答那三问，以及有没有一个能点开的 StackBlitz 最小复现。
5. 描述与命名里**不要出现"Nuxt 3"字样**，版本要求写进 `meta.compatibility`。
