"在 Nuxt 做到某一步时插一段代码"——这件事在文档里由两节负责，而两节的分工本身就值得先讲清楚，因为**很多人只看了其中一页就去写模块**。

## 两节的分工

两节的描述句逐字相同：**Nuxt 提供一个强大的钩子系统，让你用钩子扩展几乎每一个方面**。

区别在内容：**用法那一节讲"哪一类钩子给谁用、怎么挂"**，四个小节；**参考那一节放三张表**，并在每一节开头给一句"完整清单看源码"。两节还互相 read-more 指向对方——**从任何一页进来都会被送回另一页**，所以先读哪页都行，但**只读一页一定缺一半**。

机制本身有一条 tip：**钩子系统由 unjs/hookable 驱动**。这与前面见过的 unimport（自动导入）、defu（合并）、c12（配置加载）同属一个家族。

## 三张表怎么切

参考页的三个 `##` 标题已经把分类说了：

| 表 | 条数 | 标题原文 | 谁能用 |
| --- | --- | --- | --- |
| App Hooks（Runtime） | 20 | App Hooks (Runtime) | 用法页原话：**主要由 Nuxt 插件用来钩进渲染生命周期，但也可以用在 Vue 组合式函数里** |
| Nuxt Hooks（Build Time） | 52 | Nuxt Hooks (Build Time) | 用法页原话：**这些钩子对 Nuxt 模块与构建上下文可用** |
| Nitro App Hooks（Runtime, Server-Side） | 9 | Nitro App Hooks (Runtime, Server-Side) | 用法页原话：**这些钩子供服务端插件使用，以钩进 Nitro 的运行时行为** |

**分界线是"活在哪一侧"，不是功能**：同一个"错误"概念在三侧都有钩子（`app:error`、`build:error`、`error`），所以选钩子的第一步是判断你写的代码在哪一侧跑。

三张表的列也不一样，这一点读表时必须知道：

- **App 表四列：Hook、Arguments、Environment、Description**。**Environment 的取值是 `Server & Client`、`Server`、`Client` 三种**——**只有这张表告诉你钩子在哪个端触发**。
- **构建期表三列：Hook、Arguments、Description**，**没有 Environment**（构建期本来只在 Node 侧跑）。
- **Nitro 表四列：Hook、Arguments、Description、Types**，第四列给的是指向类型源码的链接。

**"全部钩子"这句话在三节各出现一次**，形式是：App 那节让你查 app 源码（`packages/nuxt/src/app/nuxt.ts#L37`），构建期那节查 schema 源码（`packages/schema/src/types/hooks.ts#L83`），Nitro 那节直接说"完整钩子列表看 Nitro 文档"。**也就是说这三张表是节选，表里没有的钩子不等于不存在**。

## 三种挂法

**第一种：写在 `nuxt.config.ts` 里。**

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  hooks: {
    close: () => { },
  },
})
```

**第二种：写在模块里，用 `nuxt.hook`。**

```js
import { defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    nuxt.hook('close', async () => { })
  },
})
```

这两条挂法在文档里都用同一个钩子举例（`close`），对照关系是：**配置里的 `hooks` 是"钩子表的简写糖"，模块里则拿到实例可以显式调用**。模块定义对象上那个 `hooks` 键也是同一件事（Kit 的参数表里那句是"If provided, the module will install the hooks"）。

**第三种：运行时与服务端，挂在各自的实例上。**

```ts [app/plugins/test.ts]
export default defineNuxtPlugin((nuxtApp) => {
  nuxtApp.hook('page:start', () => {
    /* your code goes here */
  })
})
```

```ts [~~/server/plugins/test.ts]
export default defineNitroPlugin((nitroApp) => {
  nitroApp.hooks.hook('render:html', (html, { event }) => {
    console.log('render:html', html)
    html.bodyAppend.push('<hr>Appended by custom plugin')
  })

  nitroApp.hooks.hook('render:response', (response, { event }) => {
    console.log('render:response', response)
  })
})
```

**应用侧是 `nuxtApp.hook(...)` 一层，服务端是 `nitroApp.hooks.hook(...)` 两层**——这个差别很容易被漏，写成 `nitroApp.hook(...)` 会直接报没有这个方法。

服务端那段还顺带给出一条实际能力：**`html.bodyAppend.push(...)`**，即**在 `render:html` 这个时机往 body 末尾追加内容**。

## 命名的规律

三张表里的名字都遵循 **`范围:事件`**，可以更细：**`page:loading:start`、`nitro:build:before`、`schema:beforeWrite`** 是"范围:子范围:事件"或带 before/after 阶段的形态。

三条要从表里直接读出来的事实：

**`app:` 这个前缀横跨两张表**：`app:created`、`app:error`、`app:rendered`、`app:mounted` 在**运行时**表里，而 `app:resolve`、`app:templates`、`app:templatesGenerated` 在**构建期**表里。**前缀不等于侧**，必须回到表里查。

**`close` 也出现在两张表**：构建期表里有 `close`（`nuxt` 实例优雅关闭时调用），Nitro 表里也有 `close`（Nitro 被关闭时调用）。

**`dev:ssr-logs` 同样出现在两张表**：运行时表里它的 Environment 是 `Client`、描述是"带着一组已经传到客户端的服务端日志被调用（如果 `features.devLogs` 开着）"；**Nitro 表里它是第一条**，参数是 `{ path, logs }`，描述是"在请求周期结束时带一组服务端日志被调用"。**同一个名字在两侧各有含义，一个讲的是"收到"、一个讲的是"产生"**。

## 自定义钩子要动哪三个接口

用法页最后一节：**你可以通过扩展 Nuxt 的钩子接口来定义自己的自定义钩子**。三处声明分别是：

```ts
import type { HookResult } from '@nuxt/schema'

declare module '#app' {
  interface RuntimeNuxtHooks {
    'your-nuxt-runtime-hook': () => HookResult
  }
  interface NuxtHooks {
    'your-nuxt-hook': () => HookResult
  }
}

declare module 'nitropack/types' {
  interface NitroRuntimeHooks {
    'your-nitro-hook': () => void
  }
}
```

三点值得对照：

- **运行时与构建期两个接口都增广 `#app`**（`RuntimeNuxtHooks` 与 `NuxtHooks`）。
- **Nitro 那个接口增广的是 `nitropack/types`**，模块名与前两个不同。
- **前两个的返回类型写 `HookResult`（从 `@nuxt/schema` 导入），Nitro 那个示例写的是 `void`**——**这一处差异页面没有解释**，但它是三份声明里唯一一个不返回 `HookResult` 的，照抄时要注意自己走的是哪一族。

有了接口声明，还需要真的把钩子调用出去——那部分在模块高级配方那一节：**在 `modules:done` 里 `await nuxt.callHook('你的钩子', payload)`**，理由是"确保其他模块都有机会在自己的 setup 里注册监听"。

## 一处表格瑕疵

参考页 Nitro 表的第一行是错位的：表头是 **Hook｜Arguments｜Description｜Types** 四列，而 `dev:ssr-logs` 那一行填进去的是 `{ path, logs }`、**"Server"**、然后是描述文本——**那个 "Server" 是 App 表 Environment 列的值，落到了 Description 列上，描述又被推到了 Types 列**。所以读这一行时要按内容认列，**不能按列名读**。
