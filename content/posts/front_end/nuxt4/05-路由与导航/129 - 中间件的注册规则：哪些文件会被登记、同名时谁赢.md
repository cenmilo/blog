  摘要：这一篇只管两件事：**一个文件怎么才能被登记成中间件**，以及**同名时谁覆盖谁**。注册侧的规则官方写成三条 note：其一，"只有目录顶层的文件（或子目录里的 index 文件）会被注册。**一个 index 文件从包含它的那个文件夹取得名字：`middleware/auth/index.ts` 注册为 `auth`**"；其二，"**中间件名字会被规范化为 kebab-case：`myMiddleware` 变成 `my-middleware`**"；其三，位置是"存放在 `app/middleware/`（除非另行设置）"——两个 API 页都挂着同一个 `nuxt-config#middleware` 链接。命名与全局的差别只有一处但影响很大：**命名中间件"在被页面使用时通过异步导入自动加载"**，而**全局中间件"带 `.global` 后缀，会在每一次路由变化时运行"**；两者之间的执行顺序官方定为"1. 全局中间件 2. 页面定义的中间件顺序（如果用数组语法声明了多个）"，而**全局之间默认按文件名字母序执行**，需要控制时官方建议用字母序编号前缀（`01.setup.global.ts`、`02.analytics.global.ts`）并提醒"文件名是作为字符串排序而不是数值排序，`10.new.global.ts` 会排在 `2.new.global.ts` 之前"。**"同名谁赢"一共有四处，各写在不同页面上**：① 在插件里用 `addRouteMiddleware('named-middleware', ...)` 注册的命名中间件，官方明确写"**当在插件里定义时，它会覆盖 `app/middleware/` 目录里任何同名的既有中间件**"；② 构建期在 `nuxt.config` 的 `pages:extend` 钩子里设置 `page.meta.middleware`，官方注释写"**注意这会覆盖页面里 `definePageMeta` 设置的任何中间件**"；③ Kit 的 `addRouteMiddleware`（模块里用）带一个 `options.override`，定义是"**若为 `true`，替换同名的中间件**"，默认 `false`；④ 同一个 Kit 函数还有 `options.prepend`，"**若为 `true`，把中间件前置到既有中间件之前**"，默认 `false`——它不改名字，只改顺序。另外父子路由之间的 `middleware` 不是覆盖关系而是**合并**关系：官方的字段说明是"**它会与任何匹配的父/子路由里用到的所有其他中间件合并。**"

"我把中间件放进子目录了为什么不生效""我在插件里注册了同名中间件，会不会跟文件冲突"——这两类问题的答案都不在写法里，而在注册规则里。

## 一、文件怎么才能被登记

官方给的注册条件，逐条都是硬边界：

| 官方规则 | 后果 |
| --- | --- |
| "**只有目录顶层的文件（或子目录里的 index 文件）会被注册。**" | `middleware/checks/role.ts` **不会**被登记——它既不是顶层文件，也不是 index |
| "**一个 index 文件从包含它的那个文件夹取得名字：`middleware/auth/index.ts` 注册为 `auth`。**" | 想分组组织文件，就用 `auth/index.ts` 这种写法，名字仍是 `auth` |
| "**中间件名字会被规范化为 kebab-case：`myMiddleware` 变成 `my-middleware`。**" | 文件名用驼峰时，页面里要点名得写 `my-middleware` |
| "路由中间件存放在 `app/middleware/`（**除非另行设置**）。" | 目录可以被配置改走（官方在中间件页与两个 API 页都挂了同一个 `nuxt-config` 的 `middleware` 项） |

一句话记法：**能被登记的只有"顶层文件"和"子目录的 index 文件"，名字来自文件名（或文件夹名），并经 kebab-case 规范化。**

## 二、命名与全局：后缀决定它什么时候跑

| | 命名中间件 | 全局中间件 |
| --- | --- | --- |
| 识别方式 | `app/middleware/` 下的普通 `.ts` | 同目录，带 **`.global`** 后缀 |
| 何时运行 | "在被页面使用时**通过异步导入自动加载**"（所以要被 `definePageMeta` 点名） | "**会在每一次路由变化时运行**"（无需点名） |
| 加载形态 | 异步导入 | 进入全局链 |
| 顺序 | 按页面 `middleware` 数组里声明的顺序 | **先于所有页面定义的中间件**；全局之间默认**按文件名字母序** |

官方给的顺序规则只有两档：

1. 全局中间件
2. 页面定义的中间件顺序（如果用数组语法声明了多个）

而全局之间想控制顺序，官方建议编号前缀：

```bash [Directory structure]
-| middleware/
---| 01.setup.global.ts
---| 02.analytics.global.ts
---| auth.ts
```

配套的提醒很关键：**"文件名是作为字符串排序、而不是作为数值排序的。例如 `10.new.global.ts` 会排在 `2.new.global.ts` 之前。这就是示例里给个位数前缀补 `0` 的原因。"**

也就是说：**想排第十个，名字要写 `10.`；但那样它会排在 `2.` 前面**——超过 9 个全局中间件时得两位补零（`01`…`09` 之后写 `10`…）。

## 三、"同名谁赢"有四处，各在不同页面

这是最容易踩的一片，因为四条规则分散在四个地方。

### ① 插件里注册同名 → 覆盖目录里的文件

官方在 `addRouteMiddleware`（运行时那一个）里写得很明确：

> **当在插件里定义时，它会覆盖 `app/middleware/` 目录里任何同名的既有中间件。**

```ts [app/plugins/my-plugin.ts]
export default defineNuxtPlugin(() => {
  addRouteMiddleware('named-middleware', () => {
    console.log('named middleware added in Nuxt plugin')
  })
})
```

中间件页的插件示例里也用同一句话描述了这个效果：**"this named middleware was added in a plugin and would override any existing middleware of the same name"**。

**含义**：`app/middleware/named-middleware.ts` 与插件里的 `addRouteMiddleware('named-middleware', ...)` 同名时，**跑的是插件那一份**。这在"第三方模块想接管某个中间件"时是有用的，但在自己项目里就是隐患。

### ② 构建期 `pages:extend` → 覆盖 `definePageMeta`

官方在中间件页 "Setting Middleware at Build Time" 的示例里，把那行注释写得很直白：

```ts
page.meta ||= {}
// Note that this will override any middleware set in `definePageMeta` in the page
page.meta.middleware = ['named']
```

**含义**：`nuxt.config` 的 `pages:extend` 钩子里赋值 `page.meta.middleware`，会**整条替换**页面里 `definePageMeta({ middleware: ... })` 的结果——不是追加。

### ③ Kit 的 `override`：显式选择替换

模块侧的 `addRouteMiddleware`（来自 `@nuxt/kit`）带一个 options 表：

| 属性 | 类型 | 默认 | 官方说明 |
| --- | --- | --- | --- |
| `override` | `boolean` | `false` | **若为 `true`，替换同名的中间件。** |
| `prepend` | `boolean` | `false` | **若为 `true`，把中间件前置到既有中间件之前。** |

**含义**：默认不覆盖——同名时不是替换而是共存/追加；要接管同名就显式写 `{ override: true }`。

### ④ Kit 的 `prepend`：改顺序而不是改名字

`prepend` 解决的是"我要比别的中间件先跑"，与覆盖无关。配合第二节那条"全局之间按文件名字母序"，模块给的中间件要抢在前面时有两种手段：文件前缀编号（`01.`）或 `{ prepend: true }`。

## 四、父子之间不是覆盖，是合并

页面侧那个字段官方的定义里带一句合并口径：

> **它会与任何匹配的父/子路由里用到的所有其他中间件合并。**

所以这条链上的关系是：

```
全局中间件（字母序 / 编号前缀 / prepend）
    ↓
父路由 middleware  +  子路由 middleware   ← 合并
    ↓
本页 definePageMeta 声明的顺序（数组顺序即执行顺序）
    ↑
但整条可能被 pages:extend 覆盖（②）
```

`middleware` 字段的类型也支持这三种写法（官方参数表）：`MiddlewareKey | NavigationGuard | Array<MiddlewareKey | NavigationGuard>`——**字符串、函数（匿名/内联）、或字符串与函数的数组**。

## 五、同名注册的两副面孔：先分清是哪个函数

两处都叫 `addRouteMiddleware`，但用途与参数完全不同：

| | 运行时（插件里） | 构建期（模块里） |
| --- | --- | --- |
| 来源 | `api/utils/add-route-middleware` | `api/kit/pages` |
| 签名 | `addRouteMiddleware(name, middleware, options?)` 或 `addRouteMiddleware(middleware)` | `addRouteMiddleware(input: NuxtMiddleware \| NuxtMiddleware[], options?)` |
| 传的是 | **函数** | **文件路径**（`{ name, path, global }`） |
| `global` 怎么给 | 第三个参数 `{ global: true }`，或首参直接传函数（官方："**它会被自动视为全局中间件**"） | 对象里的 `global` 属性 |
| 覆盖控制 | 插件里的命名注册**天然覆盖**目录同名文件 | 需要显式 `{ override: true }` |

这两副面孔的完整拆解见 131。
