"我在中间件里判了登录，为什么接口还能被直接访问？"——因为那个中间件根本不在请求路径上。Nuxt 里有两条导航/请求链，各有一道门，只装一道等于没装。

## 先把边界念一遍

两条官方措辞，一条比一条硬：

| 出处 | 原文 |
| --- | --- |
| 路由页（important） | "路由中间件**不会**为服务端路由（例如 `/api/*`）或其他服务端请求运行。要对这些请求应用中间件，请使用服务端中间件。" |
| 中间件页（note） | "路由中间件运行在你 Nuxt 应用的 **Vue 部分**。尽管名字相似，它们与服务端 middleware **完全不同**，后者运行在你应用的 **Nitro 服务端部分**。" |

所以这不是"有时生效有时不生效"，而是两条互不相交的链：**你写在 `app/middleware/` 里的东西，永远看不到一次打到 `/api/login` 的 HTTP 请求。**

官方在认证配方里把后果说得很直白：

> **保护服务端路由是确保你数据安全的关键。客户端中间件对用户有帮助，但如果没有服务端保护，你的数据仍然可能被访问。**对任何含敏感数据的路由都必须保护，我们应当在那些路由上于用户未登录时返回一个 `401` 错误。

**这句里的"对用户有帮助"就是它的定位**：客户端中间件管的是界面（别让用户看到一个空壳页面），数据安全靠的是服务端那一句检查。

## 两道门各长什么样

### 门一：服务端（决定数据安不安全）

官方的例子是一个只有登录用户能访问的接口：

```ts [server/api/user/stats.get.ts]
export default defineEventHandler(async (event) => {
  // make sure the user is logged in
  // This will throw a 401 error if the request doesn't come from a valid user session
  const { user } = await requireUserSession(event)

  // TODO: Fetch some stats based on the user

  return {}
})
```

两条细节：

- **拦截方式是抛错**（那行注释：不是有效会话就抛 `401`），而不是"返回一个跳转"。
- 官方给这个函数来自 `nuxt-auth-utils` 模块（`requireUserSession`、`setUserSession`、`useUserSession` 都由它提供）；**换成任何后端校验也一样，位置必须在服务端。**

登录成功那一刻写会话，官方也是在服务端做的：

```ts [server/api/login.post.ts]
export default defineEventHandler(async (event) => {
  const { email, password } = await readValidatedBody(event, bodySchema.parse)

  if (email === 'admin@admin.com' && password === 'iamtheadmin') {
    // set the user session in the cookie
    // this server util is auto-imported by the auth-utils module
    await setUserSession(event, {
      user: {
        name: 'John Doe',
      },
    })
    return {}
  }
  throw createError({
    status: 401,
    message: 'Bad credentials',
  })
})
```

### 门二：客户端（决定界面好不好看）

官方的写法：

```typescript [app/middleware/authenticated.ts]
export default defineNuxtRouteMiddleware(() => {
  const { loggedIn } = useUserSession()

  // redirect the user to the login screen if they're not authenticated
  if (!loggedIn.value) {
    return navigateTo('/login')
  }
})
```

页面侧点名（官方用 `definePageMeta`）：

```vue [app/pages/index.vue]
<script setup lang="ts">
definePageMeta({
  middleware: ['authenticated'],
})
</script>
```

**而这里有一条与接口侧相反的规则**，官方特意写出来：**"与服务端不同，客户端中间件不会自动应用到所有端点，我们需要指定想把它应用在哪里。"**

也就是说：`server middleware` 是**每个请求都跑**，`app/middleware` 的命名中间件是**被点名才跑**（要每次跑得用 `.global`，见 128）。

## 服务端中间件本身：只能抛错，不能返回响应

门一的常见形态是"一个中间件挡在所有接口前面"。官方对 `~~/server/middleware` 的描述是两条：

> Nuxt 会自动读取 `~~/server/middleware` 里的任何文件来为你的项目创建服务端中间件。中间件处理器会**在任何其他服务端路由之前**，对**每个请求**运行，用来添加或检查请求头、记录请求，或扩展事件对象。

> （note）**中间件处理器不应返回任何东西（也不应关闭或响应请求），只应检查或扩展请求上下文，或者抛出一个错误。**

这两句合起来决定了它的写法：**把用户状态挂到 `event.context` 上，交给具体处理器去读；要拒绝就抛错**——不要指望在服务端中间件里 `return { code: 401 }`。

**对比一下客户端那侧**（128、132）：路由中间件恰恰是**靠返回值表达指令**（`navigateTo`、`abortNavigation`），两边规则相反。这是最容易写串的一处。

## 一条完整的请求，两条链

```
浏览器发起一次导航/请求
├── 直接打 /api/*（Postman、curl、别人写的页面都算）
│     → Nitro：server middleware（每个请求、抛错拦截）
│     → server/api/*、server/routes/* 处理器（自己再校验一次）
│     ⚠ 全程不会经过 app/middleware
│
└── 打开一个页面 URL
      → 服务端渲染那趟：Vue 代码在服务器上跑一次
      → 浏览器：水合 → app/middleware（导航时）→ 渲染页面
      → 页面里的数据请求，又走上面那条链
```

官方对"页面那条链会跑两趟"的说明（128）在这里也要一并记住：初始页的路由中间件在服务端渲染时跑一次、客户端再跑一次；**错误页那次是独立的页面加载，任何已注册的中间件都会再运行**。

## 对照表：两道门的分工

| | 路由中间件（`app/middleware/`） | 服务端中间件（`server/middleware/`） |
| --- | --- | --- |
| 跑在哪 | Nuxt 应用的 **Vue 部分** | **Nitro 服务端部分** |
| 触发时机 | 客户端**路由变化**时；初始页服务端+客户端各一次 | **每个进入服务端的请求**，先于其他服务端路由 |
| 覆盖范围 | 页面路由；**不为 `/api/*` 运行** | 所有服务端请求（含 `/api/*`） |
| 是否自动应用 | 命名中间件**要页面点名**；`.global` 才每次都跑 | 目录下文件即自动生效 |
| 怎么表达"拦住" | **返回值**：`return navigateTo(...)` / `return abortNavigation(...)` | **抛出一个错误**；不应返回任何东西 |
| 能保护数据吗 | **不能**（官方：没有服务端保护数据仍可被访问） | 能，这才是安全边界 |
| 典型用途 | 未登录跳登录页、界面级前置逻辑 | 校验会话/权限、加请求头、记日志、扩展 `event.context` |

模块作者侧还有一条登记入口：Kit 的 `addServerHandler`，官方说明"**添加一个 Nitro 服务端处理器。如果你想创建服务端中间件或自定义路由，就用它。**"

## 四种常见误解

| 误解 | 现实 |
| --- | --- |
| "写了 `authenticated` 中间件，接口就安全了" | 接口根本不经过它。安全靠服务端那道检查 |
| "服务端中间件可以像前端那样 `return navigateTo('/login')`" | 服务端中间件**不应返回任何东西**，只能扩展上下文或抛错；而且那里没有路由中间件的概念 |
| "客户端中间件会自动保护所有页面" | 官方明说客户端中间件**不会自动应用**，得用 `definePageMeta` 点名（或做成 `.global`） |
| "前端判断通过了，页面里取的数据就是可信的" | 页面里的数据是另一个请求，走上面那条链，接口自己还得再判一次 |

## 会话这一侧的两条前提

官方配方用的是**加密且密封的 cookie**（"这个模块使用安全且密封的 cookie 来存储会话数据，所以你不需要建一个数据库来存会话数据"），密钥来自 `NUXT_SESSION_PASSWORD`：

```ini [.env]
NUXT_SESSION_PASSWORD=a-random-password-with-at-least-32-characters
```

两条与 073 呼应的说明：**"如果未设置，在开发模式下运行 `nuxt` 时会自动把这个环境变量加进你的 `.env`。"** 以及一句必须执行的提醒：**"你需要在部署前把这个环境变量添加到你的生产环境里。"**（生产环境不读 `.env`，这正是 073 那条规则的现实后果。）
