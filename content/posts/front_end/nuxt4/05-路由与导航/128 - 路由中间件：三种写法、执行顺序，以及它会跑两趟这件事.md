summary: >-
  摘要：官方对路由中间件的定位是"Nuxt 提供了一个可定制的路由中间件框架……理想用于抽取你想在导航到某个特定路由之前运行的代码"，并直接列出三种：**匿名（或内联）路由中间件，直接定义在页面内部**；**命名路由中间件，放在 `app/middleware/` 里，在被页面使用时通过异步导入自动加载**；**全局路由中间件，放在 `app/middleware/` 里并带 `.global` 后缀，会在每一次路由变化时运行**。前两种可以由 `definePageMeta` 定义。注册规则有三条容易被忽略的 note：**中间件名字会被规范化为 kebab-case（`myMiddleware` 变成 `my-middleware`）**；**只有目录顶层的文件（或子目录里的 index 文件）会被注册，index 文件从包含它的文件夹取名——`middleware/auth/index.ts` 注册为 `auth`**；**路由中间件运行在你 Nuxt 应用的 Vue 部分，尽管名字相似，它们与服务端 middleware 完全不同，后者运行在应用的 Nitro 服务端部分**，而路由页那条 important 更硬：**路由中间件不会为服务端路由（例如 `/api/*`）或其他服务端请求运行**。写法上官方说"**路由中间件是接收当前路由与下一个路由作为参数的导航守卫**"，并提供两个全局可用的 helper：`navigateTo`（重定向到给定路由）与 `abortNavigation`（中止导航，可带一条可选错误信息）。**与 vue-router 的导航守卫不同：不传第三个 `next()` 参数，重定向或取消导航是由中间件的返回值来处理**，官方给出五种返回值：什么都不返回（不阻塞导航，会走向下一个中间件函数（如果有）或完成这次路由导航）、`return navigateTo('/')`（服务端发生重定向时把重定向码设为 `302 Found`）、`return navigateTo('/', { redirectCode: 301 })`（服务端设为 `301 Moved Permanently`）、`return abortNavigation()`（停止当前导航）、`return abortNavigation(error)`（用一个错误拒绝当前导航），并用 important 补了一句：**"我们建议使用上面的 helper 函数来执行重定向或停止导航。vue-router 文档里描述的其他可能返回值也许有效，但未来可能会有破坏性变更。"** 执行顺序官方给了两步：**先全局中间件，再页面定义的中间件顺序（如果用数组语法声明了多个）**。全局中间件之间默认**按文件名以字母序执行**，需要指定顺序时官方建议**用'字母序'编号做前缀**（`01.setup.global.ts`、`02.analytics.global.ts`），并提醒"**文件名是作为字符串排序而不是数值排序的，例如 `10.new.global.ts` 会排在 `2.new.global.ts` 之前，这就是示例里给个位数补 `0` 的原因**"。还有一个新手一定要知道的行为：如果站点是服务端渲染或生成的，**初始页面的中间件会在页面渲染时执行一次、然后在客户端再执行一次**；官方给了三种跳过写法（`import.meta.server` 直接 return、`import.meta.client` 直接 return、以及 `import.meta.client && nuxtApp.isHydrating && nuxtApp.payload.serverRendered`），并强调**即使你在服务端的中间件里抛出错误并渲染了错误页，中间件仍会在浏览器里再跑一次**，另有一条 note：**渲染错误页是一次完全独立的页面加载，这意味着任何已注册的中间件都会再运行一次，你可以在中间件里用 `useError` 来判断当前是否正在处理一个错误**。最后是关于取路由：官方要求"**始终在中间件里使用 `to` 与 `from` 参数来访问下一个与上一个路由，并完全避免在这个上下文里使用 `useRoute()`**"，理由是"**中间件里没有'当前路由'的概念，因为中间件可以中止一次导航或重定向到另一个路由；`useRoute()` 在这个上下文里将永远不准确**"，还有一条 warning：**有时你调用的某个组合式函数内部使用了 `useRoute()`，即使你的中间件里没有直接调用也会触发这个警告——这与上面是同一个问题，所以应当把函数组织成在使用于中间件时接受路由作为参数**。官方错误码 E2005 对应的就是这件事：`useRoute()` 在路由中间件里（直接或间接）被调用；此时目标路由尚未解析完成，`useRoute()` 可能返回意外值，中间件应当使用作为参数收到的 `to` 与 `from`。

"进这一页之前先判一下登录状态"——这件事在 Nuxt 里叫路由中间件。它看着简单，但有四个地方反复出错：注册范围、执行顺序、它会跑两趟、以及在里面取路由的方式。

## 三种写法

官方给的分类只有一句一层：

| 种类 | 官方定义 | 写在哪 |
| --- | --- | --- |
| **匿名（内联）** | 直接定义在页面内部 | `definePageMeta({ middleware: [function (to, from) { ... }] })` |
| **命名** | 放在 `app/middleware/`，被页面使用时**通过异步导入自动加载** | 文件 + `definePageMeta({ middleware: ['auth'] })` |
| **全局** | 放在 `app/middleware/` 并带 **`.global` 后缀**，**在每一次路由变化时运行** | 文件，无需页面点名 |

官方还补了一句：前两种可以在 `definePageMeta` 里定义。

页面侧引用命名中间件的官方示例：

```bash [Directory Structure]
-| middleware/
---| auth.ts
```

```vue
<script setup lang="ts">
definePageMeta({
  middleware: ['auth'],
  // or middleware: 'auth'
})
</script>
```

> 现在，在对该页面的导航完成之前，`auth` 路由中间件会先运行。

## 注册规则：三条 note 决定"文件为什么没生效"

| 官方 note | 后果 |
| --- | --- |
| "中间件名字会被规范化为 **kebab-case**：`myMiddleware` 变成 `my-middleware`。" | 文件名写驼峰，`middleware` 里要点名时得写连字符形式 |
| "**只有目录顶层的文件（或子目录里的 index 文件）会被注册。index 文件从包含它的那个文件夹取得名字：`middleware/auth/index.ts` 注册为 `auth`。**" | 往 `middleware/` 里放子目录的普通文件（比如 `middleware/checks/role.ts`）**不会**被注册 |
| "路由中间件运行在你 Nuxt 应用的 **Vue 部分**。尽管名字相似，它们与服务端 middleware **完全不同**，后者运行在你应用的 **Nitro 服务端部分**。" | 两条链，不要指望前端中间件管接口 |

最后这条还有一句更硬的补充，来自路由那一节的 important：**"路由中间件不会为服务端路由（例如 `/api/*`）或其他服务端请求运行。要对这些请求应用中间件，请使用服务端中间件。"**

目录位置也可以改——官方在中间件页与两个 API 页都写了"存放在 `app/middleware/`（除非[另行设置](nuxt-config#middleware)）"。

## 写法与两个 helper

官方的定义句："**路由中间件是接收当前路由与下一个路由作为参数的导航守卫。**"

```ts [middleware/my-middleware.ts]
export default defineNuxtRouteMiddleware((to, from) => {
  if (to.params.id === '1') {
    return abortNavigation()
  }
  // In a real app you would probably not redirect every route to `/`
  // however it is important to check `to.path` before redirecting or you
  // might get an infinite redirect loop
  if (to.path !== '/') {
    return navigateTo('/')
  }
})
```

这段里的第二条注释是官方的提醒，值得抄进习惯：**重定向前要检查 `to.path`，否则可能得到无限重定向循环**。

官方提供的两个全局 helper：

1. `navigateTo` —— 重定向到给定路由
2. `abortNavigation` —— 中止导航，可带一条可选的错误信息

## 与 vue-router 守卫的关键差别：没有 `next()`

官方写得很直接：

> 与 vue-router 的导航守卫不同，**不会传入第三个 `next()` 参数，重定向或取消导航是由中间件的返回值来处理的。**

五种返回值（官方逐项）：

| 返回 | 官方描述的效果 |
| --- | --- |
| 什么都不返回（简单 `return` 或干脆不返回） | **不阻塞导航**，会走向下一个中间件函数（如果有），或完成这次路由导航 |
| `return navigateTo('/')` | 重定向到给定路径；若重定向发生在服务端，会把重定向码设为 `302 Found` |
| `return navigateTo('/', { redirectCode: 301 })` | 重定向到给定路径；服务端时把码设为 `301 Moved Permanently` |
| `return abortNavigation()` | **停止当前导航** |
| `return abortNavigation(error)` | **用一个错误拒绝当前导航** |

配套的 important：**"我们建议使用上面的 helper 函数来执行重定向或停止导航。vue-router 文档里描述的其他可能返回值也许有效，但未来可能会有破坏性变更。"**

这张表下一篇（132）会逐格展开，这里只要记住一句：**在中间件里，`return` 本身就是指令。**

## 执行顺序：全局先跑，然后按页面声明的顺序

官方给的顺序只有两档：

1. 全局中间件
2. 页面定义的中间件顺序（如果用数组语法声明了多个）

官方的例子把两档拼在一起：

```bash [app/middleware/ directory]
-| middleware/
---| analytics.global.ts
---| setup.global.ts
---| auth.ts
```

```vue [pages/profile.vue]
<script setup lang="ts">
definePageMeta({
  middleware: [
    function (to, from) {
      // Custom inline middleware
    },
    'auth',
  ],
})
</script>
```

> 你可以预期中间件会按以下顺序运行：`analytics.global.ts` → `setup.global.ts` → 自定义内联中间件 → `auth.ts`

### 全局之间的顺序要自己编号

官方说明：**"默认情况下，全局中间件按文件名以字母序执行。"** 需要指定顺序时："**我们建议给全局中间件加上'字母序'编号作为前缀。**"

```bash [Directory structure]
-| middleware/
---| 01.setup.global.ts
---| 02.analytics.global.ts
---| auth.ts
```

紧跟的 note 是新手最常翻车的地方：**"如果你不熟悉'字母序'编号，请记住文件名是作为字符串排序、而不是作为数值排序的。例如 `10.new.global.ts` 会排在 `2.new.global.ts` 之前。这就是示例里给个位数前缀补 `0` 的原因。"**

## 它会跑两趟：服务端一次、客户端一次

官方 "When Middleware Runs" 一节的原文：

> 如果你的站点是服务端渲染或生成的，**初始页面的中间件会在页面被渲染时执行，然后在客户端再一次**。这可能是需要的，如果你的中间件需要一个浏览器环境——例如你有一个生成的站点、积极地缓存响应，或者想从 local storage 里读一个值。

想避免这一趟，官方给了三种写法：

```ts [middleware/example.ts]
export default defineNuxtRouteMiddleware((to) => {
  // skip middleware on server
  if (import.meta.server) {
    return
  }
  // skip middleware on client side entirely
  if (import.meta.client) {
    return
  }
  // or only skip middleware on initial client load
  const nuxtApp = useNuxtApp()
  if (import.meta.client && nuxtApp.isHydrating && nuxtApp.payload.serverRendered) {
    return
  }
})
```

然后是最容易被忽略的一句：

> **即使你在服务端的中间件里抛出错误并渲染了错误页，这也是真的。中间件仍会在浏览器里再运行一次。**

配套的 note：**"渲染错误页是一次完全独立的页面加载，这意味着任何已注册的中间件都会再运行一次。你可以在中间件里使用 `useError` 来检查是否正在处理一个错误。"**

这解释了现场问题：**未登录时服务端已经抛了 401 错误页，浏览器里中间件又跑了一遍**——所以权限判断要写成幂等的，或者用 `useError()` 先挡一下。

## 取路由：只能用 `to` / `from`

官方一节的标题就是 Accessing Route in Middleware，措辞是命令式：

> **始终在你的中间件里使用 `to` 与 `from` 参数来访问下一个与上一个路由。完全避免在这个上下文里使用 `useRoute()` 组合式函数。**
>
> **中间件里没有"当前路由"的概念**，因为中间件可以中止一次导航或重定向到另一个路由。`useRoute()` 组合式函数在这个上下文里**将永远不准确**。

warning 把范围放大：

> 有时候，你可能会调用一个内部使用 `useRoute()` 的组合式函数，即使你的中间件里没有直接调用也会触发这个警告。这与上面是**同一个问题**，所以应当把函数组织成在使用于中间件时**接受路由作为参数**。

官方给了三块对照代码：

```ts [middleware/access-route.ts]
// @errors: 2304
export default defineNuxtRouteMiddleware((to) => {
  // passing the route to the function to avoid calling `useRoute()` in middleware
  doSomethingWithRoute(to)

  // ❌ this will output a warning and is NOT recommended
  callsRouteInternally()
})
```

```ts [utils/handle-route.ts]
// providing the route as an argument so that it can be used in middleware correctly
export function doSomethingWithRoute (route = useRoute()) {
  // ...
}
```

```ts [utils/dont-do-this.ts]
// ❌ this function is not suitable for use in middleware
export function callsRouteInternally () {
  const route = useRoute()
  // ...
}
```

第二个例子是官方给的**修法**：把 route 做成默认参数（`route = useRoute()`），这样在组件里调用能自动取到，在中间件里显式传入即可。

官方错误码 E2005 就是这一条的运行时表现："`useRoute()` was called inside a route middleware (directly or via another composable). At that point the target route is not yet resolved, so `useRoute()` can return unexpected values; middleware receives the `to` and `from` routes as arguments instead."

## 动态注册与构建期注册

**运行时（插件里）**，官方说法："可以用 `addRouteMiddleware()` helper 函数手动添加全局或命名路由中间件，例如在一个插件内部"：

```ts
export default defineNuxtPlugin(() => {
  addRouteMiddleware('global-test', () => {
    console.log('this global middleware was added in a plugin and will be run on every route change')
  }, { global: true })

  addRouteMiddleware('named-test', () => {
    console.log('this named middleware was added in a plugin and would override any existing middleware of the same name')
  })
})
```

**构建期（给所有页面批量挂）**，官方在 "Setting Middleware at Build Time" 一节给的做法是在 `nuxt.config` 的 `pages:extend` 钩子里改 `page.meta.middleware`，并明确注了一句：**"注意这会覆盖页面里 `definePageMeta` 设置的任何 middleware。"**

```ts [nuxt.config.ts]
import type { NuxtPage } from 'nuxt/schema'

export default defineNuxtConfig({
  hooks: {
    'pages:extend' (pages) {
      function setMiddleware (pages: NuxtPage[]) {
        for (const page of pages) {
          if (/* some condition */ Math.random() > 0.5) {
            page.meta ||= {}
            // Note that this will override any middleware set in `definePageMeta` in the page
            page.meta.middleware = ['named']
          }
          if (page.children) {
            setMiddleware(page.children)
          }
        }
      }
      setMiddleware(pages)
    },
  },
})
```
