## 为什么"报告得好"比"会改代码"更有价值

页面开头的说法是：再怎么努力，我们也永远无法彻底消除 bug；**即使你修不了底层代码，把一个 bug 报告写得好，就能让另一个对代码库更熟悉的人看出规律、或者快速改一下**。

这一句定了整篇的立场：报告者的产出物不是"抱怨"，而是**一条可被复现、可被验证的线索**。

## 第一步：先确认这是不是 bug

官方给的岔路口很清楚：考虑一下你是在**寻求某件事怎么做的帮助**，还是认为**Nuxt 本身有缺陷**。前者应当走"求助"那条路而不是提 bug——原话是"我们很乐意帮你，但最好的方式是通过 asking for help 而不是 report bugs"。

## 第二步：搜已有条目

要搜两个地方：`nuxt/nuxt` 的 open issues 与 discussions。**如果找到像是同一个 bug 的，去已有那条线程里评论，比新建一个重复的好得多。**

求助那一节还补了一条相关规则，别漏：**如果你找到的那条是已关闭的 issue，请新建一个。**（关闭的线程通常不再被跟进，评论进去没人看得见。）

## 第三步：做最小复现

这一节是整篇的重心。为什么要它，页面给了两个理由：**能把可能造成问题的范围缩小**，而且**让别人不仅能找到原因，还能验证一个潜在的修复方案**。

做法上有一句关键限定：**从 Nuxt sandbox 开始，只加复现你所遇到的 bug 所必需的"最少"代码。**

官方给的入口是两组卡片。Nuxt 侧两个：

| 平台 | 地址 |
| --- | --- |
| Nuxt on StackBlitz | `https://nuxt.new/s/v4` |
| Nuxt on CodeSandbox | `https://nuxt.new/c/v4` |

两个地址只差一个字母（`s` 与 `c`），路径尾都带 `/v4`，也就是**这四个沙盒是按版本给出的**。

**如果你的问题涉及 Vue 或 Vite，请先用 Vue SSR starter 试着复现一次。**这条 note 的用意是分离责任：如果裸 Vue SSR 就能复现，那就不是 Nuxt 这一层的问题。为此页面给了三个入口：

| 平台 | 地址 |
| --- | --- |
| Vue SSR on StackBlitz | `https://stackblitz.com/github/nuxt-contrib/vue3-ssr-starter/tree/main?terminal=dev` |
| Vue SSR on CodeSandbox | `https://codesandbox.io/p/sandbox/github/nuxt-contrib/vue3-ssr-starter/main` |
| Vue SSR Template on GitHub | `https://github.com/nuxt-contrib/vue3-ssr-starter/generate` |

第三条是 GitHub 的 generate 入口，也就是**直接从这个模板生成你自己的仓库**——需要把复现交到别人手上长期维护时用它。

复现出来之后还有一步，页面把它单独写在末尾：

> 一旦你复现了这个问题，就从你的复现里**删掉尽可能多的代码**（同时 bug 仍然能被重现）。花在把复现做得尽量小上的时间，会给那个着手修复问题的人带来巨大的差别。

这一步很少有人做。它的实际收益是：删掉的每一行都在替修复者排除一个可能性。

## 第四步：想清楚该报给谁

最后一节讲的是"报到哪里"，页面说得很直白：**Nuxt 项目里有很多活动部件**，从 Nuxt modules 到其他 JavaScript 库；**试着把 bug 报在最相关、最具体的地方**，而那**很可能是造成问题的 Nuxt 模块，或者 Nuxt 所依赖的那个上游库**。

这条能省掉最多的往返。判断路径可以这样走：

1. 裸 Vue SSR starter 能复现吗？能 → 报给 Vue 或那个上游库。
2. 只有装了某个模块才复现吗？是 → 报给那个模块的仓库。
3. 只有配合 Nuxt 的配置或目录约定才出现？→ 才是 `nuxt/nuxt`。

## 提交前把六项填齐

- 目标写清楚：你要达成什么，而不只是"它坏了"。
- 版本与环境：你用的 Nuxt 版本、构建器、是否 SSR；这一节没有给模板要求，但**版本对齐是官方文档检索那条路强调过的**（不同版本的文档不一样）。
- 已搜过哪里：open issues 与 discussions，各自的关键词。
- 复现链接：Nuxt 沙盒或 CodeSandbox，**并且已经删到不能再删**。
- 期望与实际：按文档应该发生什么，实际发生了什么——这个对照正是判定"是 bug"的依据。
- 归属判断：是否已经确认它属于 Nuxt 而不是某个模块或上游库。

## 一处文档未说明的地方

**这一节没有给出 issue 模板的必填字段、也没有说复现链接是不是硬性要求**，只描述了做法与理由。所以真被要求补充信息时，不要当成刁难——按上面的六项补齐即可，这也是它自己那套说法的自然结果。

贡献这一侧还有两条路：给文档与网站本身提内容，以及给框架提 PR。下一篇先讲前者，因为它对新手更容易开始。
