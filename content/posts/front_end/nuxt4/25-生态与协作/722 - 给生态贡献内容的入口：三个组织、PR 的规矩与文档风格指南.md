## 生态是三个组织，不是一个仓库

页面把可贡献的范围列成三项：

- **`nuxt/`**：Nuxt 框架本身的核心仓库；其中 **`nuxt/nuxt`** 装着框架（这一句在页面上写的是"包括 2 与 3 两个版本"）。
- **`nuxt-modules/`**：社区贡献并维护的模块与库。有一个把模块迁移过去的流程；**这些模块各有维护者，但不依赖单个人**。
- **`unjs/`**：其中许多库被整个 Nuxt 生态使用，设计目标是通用、与框架和环境无关；**官方欢迎其他框架与项目使用和贡献**。

这三项决定了"该把改动提到哪"：模块问题去 `nuxt-modules`，底层工具问题去 `unjs`，框架行为去 `nuxt/nuxt`。

## 六类可以做的事

**一、处理 issue 与参与讨论。**去看你想帮的那个项目的 issue 与 discussions（页面对 Nuxt 给了两个入口）。原话是：**帮助其他用户、分享绕过办法、创建复现，甚至只是往一个 bug 里挖一点并把发现分享出来，都能带来很大差别**。

**二、创建 issue。**这一节按类型分了三条：报 bug 先去读报告 bug 那一节；**功能请求要先确认没有现成的 issue 或讨论覆盖它**，如果这个功能属于生态的其他部分（例如某个模块），**先在那边提**；如果想法很通用或 API 还不清晰，**先在 Discussions 的 Ideas 分区开一帖**与社区讨论。

**三、提 PR**（下一节展开）。

**四、创建模块**：用 Nuxt 做了很酷的东西，为什么不把它抽成模块分享出去——官方说现有模块已经很多，**但总有空间**。做的时候需要帮助就去"求助"那一节。

**五、写 RFC**（再下一节）。

**六、跨生态的约定**（最后一节）。

## 提 PR：开工前的三种情况

**修 bug**：建议先确认**是否已有一个描述它的 issue**，因为这可能是文档问题，或者有一些你需要知道的上下文。

**做功能**：**要求先开一个功能请求 issue** 与维护者讨论这个功能是否被需要、以及它的设计。理由写得很直白：**这样为维护者和贡献者都省时间，功能也能更快上线**。而且有一句是硬条件：**这个 issue 需要被框架团队成员确认过，然后才在大 PR 里把它做出来**。

**改错别字**：建议**把多个错别字修进同一个 PR**，以保持提交历史干净。

**对 Nuxt 本身的大改动**：建议**先创建一个 Nuxt 模块把特性实现在那里**，这样能快速做出可行性验证；然后再以讨论的形式写 RFC。**随着用户采用它、你收集到反馈，它可以被打磨，最后要么进 Nuxt 核心，要么继续作为独立模块存在。**

## Commit 约定：`fix:` 与 `feat:` 的边界

用 [Conventional Commits](https://www.conventionalcommits.org) 写提交信息，因为**这样可以基于提交自动生成交替日志**；不熟的话让你把那份指南读完。

这一节给了一个容易搞错的界线：**`fix:` 与 `feat:` 只用于真实的代码改动（可能影响逻辑的那种）**；错别字或文档改动要用 `docs:` 或 `chore:`。页面上的对照写法是：`fix: typo` 应当改成 `docs: fix typo`。

monorepo 项目（比如 `nuxt/nuxt`）里还要求**在方括号里写上主要作用域**，示例是：`feat(kit): add 'addMagicStuff' utility`。

## 提 PR 时的四条流程说明

- PR 标题同样要遵循上面那套约定。
- **如果 PR 修复或解决了已有 issue，务必在 PR 描述里提到它们**。
- **一个 PR 里有多个 commit 是可以的；不需要为此 rebase 或强推，因为合并时会用 `Squash and Merge` 把提交压成一个**。
- 仓库**没有加 commit 钩子**，为的是快速提交；但在提 PR 之前**你要自己确认 lint 与测试脚本通过**。

还有一条通用要求，是评审质量的关键：**PR 里不要有"无关改动"**。举的例子是编辑器顺手改了别的空白或格式——**要还原回去，好让别人看得清你到底改了什么**；也把多个不相关的功能或修复合并到一个 PR 里，**能拆就拆开分别评审与合并**。原话总结是：**一个 PR 只做一件事**。

## 提了 PR 之后，那些标记是什么意思

这一节是替贡献者解读界面，避免误读：

- **被指派给某个维护者**，意味着那个人会专门评审它，并实现其中需要的改动。
- **被请求修改（request changes）**：**请忽略那行红字！这不代表我们认为这是个坏 PR**，它只是一个让人一眼看清一批 PR 状态的手段。
- **被标为 'pending'**：意思是评审者手上还有另一件事要做——**这是写给自己的内部备注，并不一定代表这个 PR 的主意好不好**；我们会尽量用评论解释 pending 的原因。

页面在这里还挂了一张 PR 决策流程图（mermaid 链接）与一张 issue 决策流程图，说明"我们会尽量照它来"。

## AI 辅助贡献：两条原则

这一节明确欢迎"有思考地使用 AI 工具"，但要求遵守两条核心原则（页面指向一篇解释它们的博客）：

**绝不让 LLM 替你说话**：所有评论、issue 与 PR 描述都应当用你自己的语气写；**他们看重清楚的人类沟通，胜过完美的语法或拼写**；避免粘贴那些并不反映你自己理解的 AI 生成总结。

**绝不让 LLM 替你思考**：可以用 AI 工具生成代码或探索想法；**但只提交你完全理解、并且能够解释的贡献**；贡献应当反映你自己的推理与解决问题过程。

收尾那句说明了动机：**目标是保证质量，并维持"与真实的人协作和交流"这件事的乐趣**。

## 先做模块，再写 RFC

RFC 那一节的第一句还是同一个建议：**优先创建一个模块**去验证大的新特性并获得社区采用。

如果已经做过、或者不适合新建模块，那就**先开一个新讨论**，内容要求三条：**尽可能清楚地解释你的想法**、**为新 API 提供代码示例或函数签名**、**引用现有的 issue 或痛点并带上例子**。如果他们觉得这应当是 RFC，会**把分类改成 RFC 并更广泛地广播以收集反馈**。

RFC 会经过五个阶段，逐条照抄：

| 阶段 | 含义 |
| --- | --- |
| `rfc: active` | 当前开放评论 |
| `rfc: approved` | 已被 Nuxt 团队批准 |
| `rfc: ready to implement` | 已创建并指派了一个实现用的 issue |
| `rfc: shipped` | 已实现 |
| `rfc: archived` | 未被批准，但归档留作参考 |

## 跨生态的约定：七项

页面说这批约定**在 `nuxt/` 组织内是必需的，并推荐给生态里的其他维护者**：

1. **模块约定**：模块应遵循 Nuxt module template（`nuxt/starter` 的 module 分支）。
2. **用 `unjs/` 的核心库**：点名三个——`pathe`（通用的路径工具，替代 node 的 `path`）、`ufo`（URL 解析与拼接）、`obuild`（由 rolldown 驱动的构建系统），其余去翻那个组织。
3. **用 ESM 并默认 `type: module`**：生态多数能直接消费 ESM；**避免 CJS 专用写法，例如 `__dirname` 和 `require`**。
4. **Corepack**：它保证运行对应命令时用的是正确版本的包管理器；项目可能在 `package.json` 里有 `packageManager` 字段——示例是 `"packageManager": "pnpm@7.5.0"`，此时 **Corepack 会（在你还没有的情况下）安装 pnpm 7.5.0 并用它跑你的命令**。
5. **用 ESLint**：既做 lint 也做格式化，用的是 `@nuxt/eslint`。推荐 VS Code 加 ESLint 扩展，还可以保存时自动修复，配置片段是 `editor.codeActionsOnSave` 里把 `source.fixAll` 设 `"never"`、`source.fixAll.eslint` 设 `"explicit"`。
6. **不用 Prettier**：既然 ESLint 已经配置了格式化，就没有必要用 Prettier 重复这个功能；格式化跑 `yarn lint --fix`、`pnpm lint --fix`、`bun run lint --fix` 或 `deno run lint --fix`；**如果你编辑器里装了 Prettier，参与这个项目时建议关掉以免冲突**。
7. **包管理器**：模块、库与应用推荐 `pnpm`；**要启用 Corepack 才能与项目用同一个版本**，启用命令是 `corepack enable`，**一台机器上装好 Node.js 之后只需做一次**。

## 文档风格指南：九组规则

文档被列为"生态的重要组成部分"，随后给了可执行的九条。

- **语言**：用**美式英语**拼写（*behavior* 而不是 *behaviour*，*customize* 而不是 *customise*）。工具与项目名用它们的官方大小写，**即使 npm 包名是小写**——例子里给了三对：*PostCSS* 而非 `postcss`、*Vite* 而非 `vite`、*ESLint* 而非 `eslint`；**只有在指代包本身时（例如安装说明）才用小写 npm 包名并加反引号**。这一条由 case police 在 `pnpm lint:docs` 时自动检查。
- **标题**：按 Chicago title case——首词、尾词与所有实词大写，**冠词、并列连词与介词无论长短都小写**（a、and、or、with、from、to）；例子是 `How to Contribute to the Docs`。**标题里的代码保持原样大小写，且不参与大写判断**，例如 *Using `useFetch` in Components*。
- **行内代码**：五类要包反引号——**文件名与路径**（`nuxt.config.ts`、`server/api/`）、**npm 包名**（`@nuxt/kit`、`postcss`）、**配置键、选项与值**（`ssr: false`、the `css` option）、**代码标识符**（函数、组合式函数、组件、变量、类型，例如 `useFetch`、`<NuxtLink>`、`defineNuxtConfig`）、**终端命令**（`npx nuxt init`）。而**工具、项目或通用概念的名字不要加反引号**——指代工具时写 *Vite* 而不是 `vite`。
- **代码示例**：**给代码块加文件名**，让读者知道这段属于哪；不属于具体文件时用描述性标签如 `[Terminal]`。**示例必须可复制粘贴**：带上必要的 import，**避免在代码中间放 `...` 这类占位符**，读者应当能把它贴进项目并在最少改动下工作。
- **链接**：链到文档其他页时**用不带域名、也不带版本段的相对路径**——写 `/docs/getting-started/installation`，而不是带 `4.x` 或完整 URL。理由那句很关键：**nuxt.com 会插入"那一节从哪个分支构建"的版本段，所以同一个链接在每个版本上都解析正确，文档改动也能在不同分支间原样 cherry-pick**。**只有当你故意指向另一个版本的文档时（例如路线图里那张发布表）才写版本段，并且用完整 URL**，好在评审时看出意图。指向外部资源时**要链到最终 URL 而不是会重定向的那个**，页面还给了检查命令：

  ```bash [Terminal]
  curl -sILo /dev/null -w '%{http_code} %{url_effective}\n' https://example.com/some-page
  ```

  它会跟着整条重定向链打印最终状态与 URL；**状态 200 且 URL 就是你请求的那个，说明链接没问题**；不同就改指向最终那个。
- **语气**：友好而专业，**直接对读者说话（用 you）**，简洁，**并假定善意**——读者背景与经验层次不同，避免任何让人被轻视的表达；可以有个性，**但清晰永远优先**。
- **写作风格**：**尽量避开主观词**，例如 *simply*、*just*、*obviously*——对背景不同的人这些词不传达意思，而且可能伤人。对照例子是"Simply make sure the function returns a promise" 改成 "Make sure the function returns a promise" 并把 promise 做成链接。**优先用主动语态**：把 "An error will be thrown by Nuxt" 写成 "Nuxt will throw an error"。
- **API 页的节名与顺序**：五节固定——**Usage、Type、Parameters、Return Values、Example**，只写适用的那些，**并且要用这些确切的名字**：用 `Parameters` 而不是 `Params`，用 `Example` 而不是 `Examples`。
- **最低版本标注**：介绍某个特性或工具时补上**所需的最低 Nuxt 版本**，分两级——**整页级**在 frontmatter 写 `minimalVersion: "3.9"`（**不带 v 前缀**，布局会自动渲染成 `v3.9` 这样的徽章）；**局部（某个选项或特性）**在旁边加小徽章 `:badge[v3.8]{color="info" size="xs" class="align-middle"}`，例子是 `useFetch` 里的 `getCachedData`、`callOnce` 里的 `navigation` 模式。**去哪找这个版本号**也给了三个：源码 JSDoc 里的 `@since`、GitHub 的 release notes、Nuxt 博客。

## 从哪一条开始最省力

按投入排序：**处理 issue 与讨论**（不需要改代码）→ **Quick Edit 修文档错别字**（下一讲展开入口）→ **做模块并分享** → **报 bug 带最小复现** → **提框架 PR**（需要本地环境与测试）。这条顺序也是这一节自己的语气：它对每一项都写了"我们欢迎"。
