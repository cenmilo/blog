## 一个命名与内容的错位

页面标题是 **Releases**，描述写的是"发现 Nuxt 与 Nuxt 官方模块的最新发布"，**而它的 URL 路径是 `community/changelog`**。这三者放在一起读，得到的结论很实际：**文档站不提供 changelog 内容本身，只告诉你去哪看。**

所以别在文档站里找"某个版本改了什么"——这个问题在这里没有答案，**它只给你十个正确的门牌号**。

## 十个入口，逐个列出

| 仓库 | 这一节给它的说明 |
| --- | --- |
| `nuxt/nuxt` | Nuxt 框架的发布 |
| `nuxt/cli` | Nuxt CLI（`@nuxt/cli`）的发布 |
| `nuxt/a11y` | Nuxt A11y 的发布 |
| `nuxt/content` | Nuxt Content 的发布 |
| `nuxt/devtools` | Nuxt DevTools 的发布 |
| `nuxt/fonts` | Nuxt Fonts 的发布 |
| `nuxt/hints` | Nuxt Hints 的发布 |
| `nuxt/image` | Nuxt Image 的发布 |
| `nuxt/scripts` | Nuxt Scripts 的发布 |
| `nuxt/ui` | Nuxt UI 的发布 |

每个入口的链接形状都一样：`https://github.com/<org>/<repo>/releases`。**注意 `nuxt/cli` 单独占一行**——CLI 不在 `nuxt/nuxt` 里发版，所以如果你在项目里遇到的是命令行为问题（例如 `nuxt dev` 的选项、`nuxt docs`、`nuxt devtools`），要追的日志在 `nuxt/cli`，不是框架仓库。

页面最后还有一条 read-more，指向 **`https://github.com/nuxt`**，让你去发现这个组织里的其他仓库。

## 这十项为什么被挑出来

对照另一页就能看出选谁是有标准的：核心模块路线图那张表里，a11y 的状态是 Public Alpha、支持 4.x 与 5.x。**这一节给的四项官方产品（A11y、Content、DevTools、Image）加上 UI、Fonts、Hints、Scripts、CLI 与框架本身，就是"跟 Nuxt 一起发版的东西"的清单。**

而社区贡献的模块在另一个组织 `nuxt-modules/`，**这一节一个都没列**——那些模块的发布要跟各自仓库，与官方节奏无关。判断自己该盯哪个，可以先回答一个问题：**这个包是不是 `nuxt/` 组织下的。**

## 升级时这套入口怎么用

一个具体的排查顺序，比"看日志"更有用：

1. **确认你升级的是哪一层**。`nuxt` 是框架；`@nuxt/cli` 是命令与开发服务器；`@nuxt/kit` 与 `@nuxt/schema` 是模块作者用的两件套——**而 kit 与 schema 就在 `nuxt/nuxt` 这个 monorepo 里**，所以它们的发布记录跟框架是同一条。
2. **框架版本与 kit/schema 版本要对齐**。Kit 那一节的要求是：单独安装时，**`@nuxt/kit` 与 `@nuxt/schema` 的版本必须大于等于你的 `nuxt` 版本**，以避免意外行为。升级 `nuxt` 之后没有同步这两项，是很多"升级后模块报错"的直接来源。
3. **模块问题去模块仓库**。这一点在报告 bug 那一节也被强调过：**要报在最相关、最具体的地方**，通常是造成问题的 Nuxt 模块或 Nuxt 依赖的上游库。
4. **只改了开发工具行为？看 `nuxt/devtools`**。而这一项还有个特别的版本风险：**DevTools 的破坏性变更可能不会反映在 Nuxt 的版本号上**（配置参考里那一节明写了这句），所以它要单独跟。

## 想用一个新特性时，先确认版本号

这一节解决"什么时候改了什么"，而文档里还有一条配套规则告诉你怎么在文档里认出它：**给 API 页加最低 Nuxt 版本**，做法分两级——**整页级在 frontmatter 写 `minimalVersion`（不带 v 前缀，布局会渲染成 `vX.Y` 徽章）**；**局部（某个选项或特性）在旁边加小徽章**，形状是 `:badge[v3.8]{color="info" size="xs"}`。

而找"这个特性是哪个版本进来的"，官方给的三个查证入口正好是：**源码 JSDoc 里的 `@since`、GitHub 的 release notes（就是这一节链接的那十个地址）、Nuxt 博客**。也就是说，这一节是那三个入口里第二个的门牌。

## 还有一个不用点链接的办法

前面讲 MCP 那一节给过：那个服务提供了一个工具 `get-changelog`，作用是**取 Nuxt 核心与官方模块的最新发布**。如果你的编辑器或助手接了 MCP，这就是同一份信息的程序化入口——**不需要人工在十个 releases 页面之间跳**。

## 把整套内容收个尾

到这里，全系列结束。留三条判断方式，它们比任何单条 API 都更耐用：

- **看目录而不是看记忆**：Nuxt 的能力大量由目录约定驱动（组件、页面、组合式函数、服务端路由只扫那四个子目录、类型只扫一层）。改动没生效，先确认文件在不在被扫描的位置。
- **分侧再动手**：构建期（配置、模块、钩子）与运行时（插件、`nuxtApp`、水合）不共享状态与代码，只有运行时配置例外。想传值就走 `runtimeConfig`，想读配置别 import Kit。
- **版本与产物是两件事**：`.output` 一旦产出就独立于 `nuxt.config` 与模块；而版本节奏里唯一被允许含破坏性变更的地方，是明确标记为 `experimental` 的那些选项。
