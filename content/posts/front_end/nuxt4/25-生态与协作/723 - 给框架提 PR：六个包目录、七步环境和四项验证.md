## 先读通用那一页

页面第一句是前提：**读完通用贡献指南之后**，下面这些是针对 `nuxt/nuxt` 仓库的专门说明。所以 commit 约定、PR 流程、AI 使用原则那几件事在通用页，不在这里重复。

## 六个包目录，对应六个发布名

| 目录 | 它是什么 | 发布为 |
| --- | --- | --- |
| `packages/kit` | 编写 Nuxt 模块的工具集 | `@nuxt/kit` |
| `packages/nuxt` | Nuxt 的核心 | `nuxt` |
| `packages/schema` | 跨版本的 Nuxt 类型定义与默认值 | `@nuxt/schema` |
| `packages/rspack` | Nuxt 的 Rspack 打包器 | `@nuxt/rspack-builder` |
| `packages/vite` | Nuxt 的 Vite 打包器 | `@nuxt/vite-builder` |
| `packages/webpack` | Nuxt 的 webpack 打包器 | `@nuxt/webpack-builder` |

这张表有两个用处。**一是决定提交的作用域**：通用页要求 monorepo 的提交在方括号里写主要作用域（例如 `feat(kit): ...`），这个作用域就是目录名。**二是解释了两处口径冲突的来源**：`packages/rspack` 在这里是一个正式的核心包，而"构建器"那一章只说"三个官方 builder"、`buildNuxt` 那节写的是"目前 vite 或 webpack"——**这份包清单是三个构建器都存在的最直接证据**。

## 环境搭建：七步

**1. fork 再 clone**：把 `nuxt/nuxt` fork 到你自己的 GitHub 账号，然后 clone 到本地设备。

**2. 确保使用最新的 Node.js**。这一句没有给版本号，所以**具体需要哪个 Node 版本，这一页没有说**。

**3. 启用 Corepack**，这样才有 `pnpm` 与 `yarn`：

```bash [Terminal]
corepack enable
```

**4. 用 pnpm 安装依赖**：

```bash [Terminal]
pnpm install --frozen-lockfile
```

紧跟一条 note，是依赖管理的关键规则：

> 如果你要添加一个依赖，请使用 `pnpm add`。
>
> **`pnpm-lock.yaml` 是所有 Nuxt 依赖的唯一来源（source of truth）。**

也就是说不要手工编辑锁文件、也不要用别的包管理器安装——**它指定了唯一的版本来源，这一步出错会让 PR 的 diff 里出现一堆无关的锁文件改动**（通用页对"无关改动"的提醒正对应这里）。

**5. 激活那套被动开发机制**：

```bash [Terminal]
pnpm dev:prepare
```

页面对它的说法就是这一行命令，**没有解释它准备了什么**；它的作用是把各包的本地开发产物准备好，好让 playground 与测试能引用到工作区里的包。

**6. 检出一个你工作和提交的分支**：

```bash [Terminal]
git checkout -b my-new-branch
```

**7. 提交 PR 之前，先对照 playground 试、并测试你的改动**——页面把这两项写在下一步的小节里。

## 四项验证，各自的命令与边界

**playground（`pnpm dev`）**：改 PR 的时候要检查改动是否正确，做法就是**修改 `playground/` 里那个示例应用**然后跑 `pnpm dev`。这里有一条重要提示，是新手最常犯的错：

> 请确保**不要把它提交到你的分支里**，但把一些示例代码加进你的 PR 描述会很有帮助。这能让评审者和其他 Nuxt 用户深入理解你做出来的特性。

也就是说 playground 的改动是**给你自己看的临时状态**，要展示就贴进 PR 描述，不要提交。

**测试（`pnpm test`）**：规则是**每个新功能都应该有一个对应的单元测试（在可行的情况下）**。同时它也承认现状：**这个仓库里的 `test/` 目录目前仍是一个进行中的工作**，但请参照已有例子的方式尽量新建一个测试。检查点写在命令前：**在创建 PR 或把它标记为 ready-to-review 之前，跑 `pnpm test` 确保所有测试通过。**

**Lint（`pnpm lint`）**：用 ESLint 强制代码标准，**提交改动之前跑它验证代码风格**。可以用 `pnpm lint --fix` 修掉大部分风格问题；**如果还有剩余错误，必须手工改**。

**文档**：如果你在加新功能、做重构，或者以任何其他方式改变 Nuxt 的行为，**你多半需要把这些改动写进文档**，并且**把文档的改动包含在同一个 PR 里**。时间上留了余地：**第一个 commit 不必写好文档，但要尽快——在 PR 足够成熟的时候**。约束只有一句重要提示：**改动要依照文档风格指南来做**（在通用那一页）。

**最终检查表**：提交 PR 时有一份要你填写的模板，**请在检查表里把所有合适的项勾上**。页面没有列出模板的具体条目。

## 文档贡献这一侧：五个入口

这一节是单独给"只改文档"的人准备的，门槛比上面低。

**发现就提**：如果你看到文档或**错误信息**有可以改进的地方，就直接开 PR——**哪怕只是修一个错别字**。

**快速修改**：看到一个错别字或想重写某句话，可以点页面右侧 Community 分区里的 **Edit this page** 链接，**直接在 GitHub 界面里改，然后开一个 Pull Request**。这条路不需要本地环境。

**较长的修改**：文档内容在 `nuxt/nuxt` 仓库的 `docs/` 目录里，**用 markdown 写**。两条配套 note：**要在本地预览文档，请按 `nuxt/nuxt.com` 那个仓库里的步骤来**（也就是说预览器在另一个仓库）；**推荐为 VS Code 安装 MDC 扩展**。

**文档 lint**：文档用 MarkdownLint 与 case police 检查以保持统一，命令是 `pnpm lint:docs`，**另有 `pnpm lint:docs:fix` 可以标出并解决 lint 问题**。

**开 PR 时**：标题要符合 Conventional Commits，页面给的示例是：

```bash [Example of PR title]
docs: update the section about the nuxt.config.ts file
```

这一条与通用页那条界线正好对上：**文档改动用 `docs:`，不是 `fix:`**。
