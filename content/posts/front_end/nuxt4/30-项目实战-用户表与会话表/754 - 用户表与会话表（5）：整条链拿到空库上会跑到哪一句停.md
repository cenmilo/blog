## 十段句子，一张依赖表

`db/migrations/` 里四份 `.sql`，按 `--> statement-breakpoint` 切开来数，各份段数是 1、5、2、2，一共十段。这张表是本站的全部材料：每一段需要什么对象、那个对象在哪一段被造出来。左边那列是段号，写法直接照文件抄。

| 哪一段 | 首句 | 它需要谁已经存在 | 那一位由哪一段提供 |
| --- | --- | --- | --- |
| `0000` 段 0 | `create extension if not exists citext;`（同段还有 pgcrypto 与 `CREATE TABLE "ping"`） | 无 | —— |
| `0001` 段 0 | 两行 `create extension` ＋ `CREATE TYPE "public"."user_role" AS ENUM(...)` | 无 | —— |
| `0001` 段 1 | `CREATE TABLE "users" (` | 类型 `citext`、函数 `gen_random_uuid`、类型 `user_role` | 前两位在 `0000` 段 0 或本份段 0；`user_role` 就在本份段 0 |
| `0001` 段 2 | `CREATE TABLE "sessions" (` | 无（uuid、text、时间戳都是内置） | —— |
| `0001` 段 3 | `CREATE TABLE "login_tokens" (` | 类型 `citext`、函数 `gen_random_uuid` | 同上 |
| `0001` 段 4 | `ALTER TABLE "sessions" ADD CONSTRAINT ...` | 表 `users`、表 `sessions` | 段 1、段 2 |
| `0002` 段 0 | `CREATE TABLE "audit_logs" (` | 无（`jsonb`、`bigserial`、`bigint` 都是内置） | —— |
| `0002` 段 1 | `ALTER TABLE "audit_logs" ADD CONSTRAINT ...` | 表 `users`、表 `audit_logs` | `users` 在 `0001` 段 1 |
| `0003` 段 0 | `CREATE TABLE "meter_events" (` | 无 | —— |
| `0003` 段 1 | `ALTER TABLE "meter_events" ADD CONSTRAINT ...` | 表 `users`、表 `meter_events` | `users` 在 `0001` 段 1 |

顺序合法不等于依赖成立：**`0002` 和 `0003` 各有一条句子引用了 `users`**，而 `users` 是 `0001` 的段 1 建的。链条靠的不是文件序号，是这张"谁需要谁"的关系。

## 单拿一份文件到空库上，会停在哪

按上面那张表逐份推：

- 只拿 `0000`：段 0 自带那两行扩展，`ping` 用的都是内置类型 ⇒ 跑得完。
- 只拿 `0001`：看着依赖 `citext` 和 `gen_random_uuid`，但它自己第 0 段就写了那两行扩展，`user_role` 也在同段 ⇒ 也跑得完。这一条容易推错，值得停一下：判据不是"这份文件序号靠后"，而是"这一份里有没有那两行"。
- 只拿 `0002`：段 0 建表成功，段 1 那句 `REFERENCES "public"."users"("id")` 找不到表 ⇒ **停在段 1**。注意此刻库里**已经留下 `audit_logs` 这张表**了，只是没挂上约束——半套结构。
- 只拿 `0003`：形状完全相同，停在段 1。

前一站量过一件事：新生成的那份文件里 `create extension` 命中 0 次。所以真正会停在更早位置的，是那种"用到了 `citext` 却没带那两行"的新文件——它一开头就撞"类型不存在"。这也是为什么每次生成之后要手工把那两行钉在新文件最前面（第 4 步那条规矩，在链条上的作用到这里才显出来）。

手工逐句跑为什么会留半套，而 `npm run db:migrate` 不会？因为上一站从包里读到的是**整批语句放在同一个事务里**执行：任何一句失败，这一批里已经执行的部分连同记账插入一起回滚。所以"停在段 1、但 `audit_logs` 留下了"这个形状，只出现在你自己拿 `psql` 一段一段喂进去的时候（这个差别本轮没连库，没造现场，属下面"你自己跑一遍"那节）。

## 同一份跑第二遍，会停在哪

换个问题：库里已经有这套结构了，再把某一份文件从头执行一遍，停在哪一句？答案只看句子写法：

- `0000` 段 0：两行 `create extension if not exists` 过得去，**停在 `CREATE TABLE "ping"`**——同一段里就它有幂等写法之外的形状。
- `0001` 段 0：扩展两句过得去，**停在 `CREATE TYPE`**：Postgres 的 `CREATE TYPE` 没有 `IF NOT EXISTS` 这种写法（这条是 Postgres 的语法，不在 Nuxt 文档范围里，本文只按写法判、不断言具体错误码）。
- `0001` 段 1、`0002` 段 0、`0003` 段 0：**停在 `CREATE TABLE`**。这里要说准一点：Postgres 本身支持 `CREATE TABLE IF NOT EXISTS`，**是生成器没这么写**，所以"第二遍必撞"是文件写法决定的，不是数据库能力决定的。
- 那几条 `ADD CONSTRAINT` 也一样：这句没有幂等写法，第二遍必撞。

数这些句子的时候踩过一次前一站记过的坑，顺手再钉一遍：按"出现次数"数 `if not exists`，`0000` 是 3 次、`0001` 是 2 次，但真正带这个从句的语句两边都是 2 句——`0000` 多出来的那一次在第 2 行的注释里（那行注释正好引用了这个短语）。**数语句要看句子，别数关键字。**

## 顺序这件事由谁保证

`_journal.json` 的 `entries` 是个数组，包里读目录时**按数组顺序**遍历，而"这份跑过没有"用每条的 `when` 与库里最大那个 `created_at` 比大小（上一站从包里读到的判据）。所以链的顺序有两道不同的东西在管：

- 执行顺序＝数组顺序；
- 是否执行＝`when` 的大小比较。

这两道是分开失效的。第三站那批结构自检（`node scripts/check-migrations.mjs`）管的是账本层面：本轮在副本上试了两种破坏，结果正好一红一绿。

第一种，把 `journal` 的第 2、3 条记录顺序互换：

```text
FAIL 0002_previous_maddog：journal 里 idx=2，但它排在第 1 条（读入按数组顺序，不认 idx）
FAIL 0001_core_tables：journal 里 idx=1，但它排在第 2 条（读入按数组顺序，不认 idx）
FAIL 0001_core_tables：when=1791965717036 不比上一条（1792065286115）大，migrate 的「跑过没有」判据会失准
FAIL 0003_snapshot.json：prevId=912c1f7d-...，应等于上一份的 id=89ec6ee0-...（链断了）
问题 6
```

这六条各管一件事：两条是 `idx` 与数组位置不符（读入按数组走，`idx` 只是账面上的号），一条是 `when` 不再递增，剩下三条被连累的是 `meta/` 记录之间的 `prevId` 链——**一次乱序，六条问题**。

第二种，把 `0001` 与 `0002` 两份文件的**内容整份互换**（文件名、journal、`meta/` 都不动）：

```text
  0001_core_tables       when=1791965717036  stmts=2  tables=4
  0002_previous_maddog   when=1792065286115  stmts=5  tables=5

问题 0
```

**绿了。** 段数与表数那两行已经明显错位（本该 5 段的那份变成 2 段），但没有一项检查看 SQL 内容——它管账本，不管账本里写的句子。**依赖顺序这张表只能人读**，脚本给不了你兜底。

## 出问题对照

| 症状 | 原因 | 怎么办 |
| --- | --- | --- |
| 新库上跑一份"靠后"的迁移，报"表 users 不存在" | 单拿一份文件跳过了前面的段 | 整条链按序跑，或者干脆用 `db:migrate` |
| 跑到一半失败，再跑时报"表已经存在" | 你自己逐句执行过一部分，记账却没写全 | 把库清回初始状态重来，别手工补 DDL |
| 同一份文件跑第二遍报"类型已存在" | `CREATE TYPE` 没有幂等写法，重放必撞 | 只追加新迁移；旧文件不动（第 5 步那条判据） |
| 结构自检全绿，但库里结构明显不对 | 它只查成对、顺序、链，不查 SQL 内容 | 用上面那张依赖表人工读一遍；必要时逐段对着库看 |
| 新生成的迁移在空库上第一句就失败 | 生成器不带 `create extension`，而新文件用了 `citext` 或 `gen_random_uuid()` | 手工把那两行钉在新文件最前面（第 4 步的规矩） |

## 你自己跑一遍

1. 把四份文件按 `--> statement-breakpoint` 切开，数段数（预期 1、5、2、2，合计十段），再照本站那张表把"需要谁"逐段填一遍——这一步不需要任何工具。
2. 数 `if not exists`：按出现次数与按语句各数一遍，看看 `0000` 为什么差一次。
3. 跑 `node scripts/check-migrations.mjs`，再在自己的副本上做两次破坏（换 journal 顺序、换文件内容），把"问题 6"和"问题 0"这两种结果亲手做出来。
4. 需要库的三条留给可丢弃的实例：拿 `0002` 单独跑，看它停在段 1 且 `audit_logs` 已经留在库里；再从头整链跑一遍；最后用 `npm run db:migrate` 跑同一个动作，看失败时是不是整套都不留（这条正是"整批一个事务"的现场，本文没有读数）。

## 这一站的边界

没有连库，所以第 4 节里"停在段 1、表留下"和最后一节那三条都是从句子写法和包里读到的执行方式推出来的，不是量出来的；具体错误码本文一个都不写。十段的划分、每段的首句、依赖关系、两种破坏实验的读数（问题 6 与问题 0）都是本地跑出来的，可以逐条复算。
