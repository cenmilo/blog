写到这里，测试相关的方法你已经见过十几个，散在四个小节里。最容易搞混的一组是"我怎么在浏览器里操作页面"——官方给的路不止一条。

先把 e2e 那侧的方法面收齐，再并表。

## e2e 的七个方法

| 方法 | 官方定位 | 拿到什么 | 有浏览器吗 |
| --- | --- | --- | --- |
| `setup(options)` | 在每个用到 e2e 方法的 `describe` 里准备测试上下文 | 无返回（在四个钩子里搭环境） | 取决于 `browser` 选项，默认 `false` |
| `$fetch(url)` | Get the HTML of a server-rendered page | HTML 字符串 | 没有 |
| `fetch(url)` | Get the response of a server-rendered page | 响应对象（示例解构 `body`、`headers`） | 没有 |
| `url(path)` | Get the full URL for a given page | 含测试服务端口的完整地址（示例形如 `http://localhost:6840/page`） | 没有 |
| `getServerLogs()` | 自上次 `startServer()`（或 `clearServerLogs()`）以来捕获的服务端子进程 stdout/stderr 行 | 日志行数组 | 没有 |
| `clearServerLogs()` | 清掉已捕获的服务端日志行 | 无 | 没有 |
| `createPage(url)` | 创建一个配置好的 Playwright 浏览器实例，可选指向运行中服务器的某个路径 | Playwright 的 `page` | **有** |

七个里六个不带浏览器。这一条就把"端到端测试"拆成了两件事：**问服务器要结果**（`$fetch`/`fetch`/`url`）和**在浏览器里操作**（`createPage`）。`getServerLogs`/`clearServerLogs` 是第三类：从子进程输出反推服务端做了什么。

`url(path)` 这个方法的用途文档写得很短，但有个隐含场景：它给出的地址带端口，而这个端口在测试里通常不是你指定的（`port` 选项默认 `undefined`，不给就随机）。所以要把地址交给 `page` 之外的东西用——比如非浏览器的 HTTP 客户端——就得靠它拼。

## 三种浏览器入口并表

| 维度 | `createPage` | Playwright 测试运行器 | Vitest Browser Mode |
| --- | --- | --- | --- |
| 导入位置 | `@nuxt/test-utils/e2e` | `@nuxt/test-utils/playwright`（`expect`、`test`）+ 类型 `ConfigOptions` | `vitest/browser` 的 `page.render`，或 `@nuxt/test-utils/browser` 的 `render` |
| 运行器 | Vitest／Jest／Cucumber（官方原句列这三种） | Playwright 自己的 runner | Vitest |
| 谁开浏览器 | test-utils（底层用 Playwright） | Playwright runner | Vitest Browser Mode，provider 是 `@vitest/browser-playwright` |
| 配置在哪 | 测试里的 `setup({...})` | `playwright.config.ts` 的 `use.nuxt`，或测试文件里 `test.use({ nuxt })` | `vitest.config.ts` 里一个 `defineVitestProject` project |
| 跑的是整个应用吗 | 是（构建或 `host` 指向的部署版本） | 是 | 组件级：示例渲染的是 `MyCounter` 单个组件 |
| 导航与等待 | `page` 上的 Playwright API | `goto(path, { waitUntil: 'hydration' })` | 没有页面导航概念（示例只做 `click`） |
| 断言 API | 你自己写的（示例用 `isVisible()` 配 `expect(...).toBe(true)`） | Playwright 的 `expect(page.getByRole('heading')).toHaveText(...)` | Vitest 浏览器断言 `await expect.element(...).toBeVisible()` |
| 官方示例的适用场景 | 登录页两个字段可见（配合 `host`） | 首页标题文本 | 计数器按钮点一下数字变 1 |

三行值得单独记住的差别：

**第一，前两种跑的是整个应用，第三种跑的是组件。** 前两种的配置单位是"一个 Nuxt 应用"（`rootDir`、`host`、`build`、`server`），断言对象是某个 URL 渲染出来的页面。Browser Mode 挂在 Vitest project 上，官方示例里出现的是 `render(MyCounter)`——它更接近"在真浏览器里渲染一个组件"，而不是"访问一个路由"。

**第二，配置项同源但位置不同。** 官方那句 "with the same configuration details as the `setup()` function" 说的就是 Playwright 运行器模式下 `ConfigOptions` 能写的东西，与测试里 `setup()` 的选项是同一份。所以选哪一种，改变的只是这份配置写在哪个文件，不是它能配什么。

**第三，只有 Playwright 运行器那条路给了 `waitUntil: 'hydration'`。** 想在测试里明确等水合完成，文档里唯一的记载就是这个 `goto` 的取值；它在 `createPage` 那一节没出现，Browser Mode 那节也没有。**文档没说明另外两种入口如何等待水合。**

## 选哪一条

按文档能给出的判断只有三条：

- 要断言的是「服务端渲染出来的这段 HTML/这个响应」，不需要浏览器 → `$fetch` 或 `fetch`，不用开浏览器，最快。
- 要操作真实浏览器、而且测试单位是「一个 URL」 → `createPage`（继续用 Vitest 或你已有的 Jest/Cucumber）或 Playwright 运行器（要 Playwright 的自动等待断言与 `goto`）。
- 要在真浏览器里验证单个组件的交互，测试单位是「一个组件」 → Vitest Browser Mode。

`browser` 那个 `setup` 选项（默认 `false`，置真会启动浏览器供后续套件控制）与 `createPage` 的关系，文档没有明说区别，只在选项里描述了行为、在 `createPage` 一节给了用法。

## 自查

- e2e 七个方法里只有 `createPage` 给浏览器；`$fetch` 给 HTML、`fetch` 给响应、`url` 给带端口的完整地址、`getServerLogs`/`clearServerLogs` 管服务端输出。
- 三种浏览器入口的单位不同：前两种是「一个应用／一个 URL」，Browser Mode 是「一个组件」。
- Playwright 运行器的 `ConfigOptions` 与 `setup()` 选项同源，只是位置从测试文件挪到 `use.nuxt` 或 `test.use`。
- `waitUntil: 'hydration'` 只在 Playwright 运行器的 `goto` 示例里出现；另两种入口怎么等水合，文档未说明。
- `browser` 选项与 `createPage` 的关系官方没写清楚，别当成同义词用。
