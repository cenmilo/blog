本地 `npx vitest` 全绿，流水线里第一步就红。日志是空的，或者干脆是 "Test timed out"。

先去翻官方测试那一节找 CI 章节，会找不到——**`getting-started/testing` 那一节整段没有 CI 相关内容**。这一节讲安装、Unit Testing、端到端测试、内置 mock、helpers、浏览器模式，到 Playwright 运行器结束。

那能确证的是什么？散在其他页上的那些"框架自己 detect 到 CI"的行为，加上四条与测试直接相关的记载。

## 一、Nuxt 知道自己在 CI 里：六条

| 行为 | 在 CI 里的差别 | 出处 |
| --- | --- | --- |
| `logLevel` | "Defaults to 'silent' when running in CI or when a TTY is not available. This option is then used as 'silent' in Vite and 'none' in webpack" | `api/nuxt-config` |
| `nuxt analyze` | 构建完的结果本会起一个本地服务，**`--no-serve` 或环境里设了 `CI` 时不起** | `api/commands/analyze` |
| `nuxt dev` 的交互面板 | 非终端、CI、attach 了调试器、终端太小时，**退回纯日志流** | `api/commands/dev` |
| CLI 每日更新检查 | 检查在 CI、StackBlitz、非终端时**跳过** | `api/commands/overview` |
| Nuxt Kit 的依赖安装 | **CI 或无交互终端时什么都不装**，缺失包作为带安装命令的诊断报出来，函数把它们报为缺失以便模块优雅降级 | `api/kit/dependencies` |
| `nuxt prepare` | 创建 `.nuxt` 目录并生成类型，**"This can be useful in a CI environment or as a `postinstall` command"** | `api/commands/prepare` |

第一行解释了一个最常见的困惑：流水线里没日志不是坏了。日志级别默认降到 `silent`，Vite 侧是 `silent`、webpack 侧是 `none`。想看日志就得自己把级别提上来（`--log-level` 在命令的全局选项里，或者显式配 `logLevel`）。

倒数第二行对模块作者有用：模块里如果用了 Kit 的依赖安装能力，CI 里它不会装东西，只会报诊断——所以流水线里那个"缺依赖"的提示是预期行为，不是你配错了。

## 二、跟测试直接挂钩的四条

**类型先准备好。** `prepare` 那一节把 CI 环境明确列为它的适用场景之一，理由是生成 `.nuxt` 与类型。测试里要用自动导入的类型（`#components`、`#imports`），这些类型文件不存在时，TS 检查会先于测试失败。把这一步固定成 `postinstall` 或流水线里的第一个脚本，是这一节支持的唯一做法。

**Windows runner 的超时更长。** `setupTimeout` 的默认值官方写的是 `120000` **or `240000` on windows**。也就是说同一份测试在 Linux runner 上刚好过、在 Windows runner 上也该更宽裕，但反过来不行：如果你的矩阵里有 Windows，别把 `setupTimeout` 手工压小；`setup` 那项说明里提到这段时间可能包含构建或生成文件，视传进来的选项而定。拆掉环境的时间是另一个值：`teardownTimeout` 默认 `30000`，示例场景里包括关浏览器。

**流水线里可以用 `host` 换掉构建。** `host` 选项那句写的是"用这个 URL 作为测试目标，而不是构建并新起服务器"，适合对着已部署版本或已在本地跑着的服务器测，并明说能显著减少执行时间。Target `host` 小节里还有一句直接对准流水线：

> For local development or automated deploy pipelines, testing against a separate local server can be more efficient and is typically faster than allowing the test framework to rebuild between tests.

这是文档在 CI 这个话题上给得最明确的一条建议：**把构建与测试解耦，让流水线跑一个已经起好的服务器**。

**`nuxt test` 的 `NODE_ENV` 是条件式的。** 原句 "sets `process.env.NODE_ENV` to `test` **if not already set**"。流水线里 `NODE_ENV` 经常已经被设成 `production`（很多构建镜像会预设），这时候用 `nuxt test` 并不会把它改回 `test`，你的代码里按环境变量分支的部分就跑在 `production` 分支上。要确定性，自己显式传：要么显式设 `NODE_ENV=test`，要么明确按 `production` 测。

## 三、跑挂了怎么看到东西

三条组合起来用：

- `captureServerLogs` 默认 `true`，服务端的 stdout/stderr 被从控制台压掉、只能靠 `getServerLogs()` 读。文档明说置 `false` 恢复旧的继承 stdio 行为，"useful when debugging a test locally"——流水线里临时把日志找出来同理。
- `logLevel` 是服务端子进程的 consola 级别（默认 `1`），那行括号里写着可用 **`NUXT_TEST_LOG_LEVEL` 环境变量覆盖**。流水线里不方便改代码时，用这个变量。
- 服务端断言本身要靠轮询：`getServerLogs()` 的示例用 `vi.waitFor` 包住断言。CI 上机器更慢，`waitFor` 的默认超时不够用时会表现成"本地过、CI 红"，这种失败要看的是超时不是断言逻辑。

## 四、文档没写的那些

为了不猜，把缺口列清楚：

- **缓存策略**：测试跑完之后 `.nuxt`、构建缓存该不该缓存、缓存哪些目录，文档没有给出与测试命令相关的缓存指引。（构建缓存本身在 experimental 开关那一节有记载，但它与测试的关系没有写。）
- **并行与分片**：Vitest 的 shard、并发数，官方测试文档里没有；给出的四条运行命令只有全量、`--project unit`、`--project nuxt`、`--watch`。
- **浏览器安装**：Playwright 那节只让装 `@playwright/test` 与 `@nuxt/test-utils` 两个包，**没提浏览器二进制怎么在 CI 里装**。这一步得看你选的平台自己的文档。
- **失败重跑**：文档没有任何重试机制的记载。

能确证的流水线顺序只有一条来自文档字面（`prepare` 适合 CI），其余要你自己按项目补：

```bash
npx nuxt prepare
npx vitest --project unit
npx vitest --project nuxt
npx playwright test
```

前三条是文档里出现过的命令；最后一条是 Playwright 运行器的常规入口，官方那一节只给了配置文件与测试文件的写法，**没有给出运行它的命令**。

## 自查

- 官方测试页没有 CI 章节；CI 相关的事实分散在配置页与命令页上。
- `logLevel` 在 CI 或无 TTY 时默认 `silent`，这是"流水线里没日志"的第一嫌疑。
- `nuxt prepare` 被文档点名适合 CI，用它先备好 `.nuxt` 与类型。
- `setupTimeout` 在 Windows 上是 `240000`，`teardownTimeout` 是 `30000`；别为 CI 手工压小前者。
- 想省时间就按文档那条走：`host` 指向已起好的服务器，构建与测试解耦。
- `NODE_ENV` 只在未设置时才被 `nuxt test` 设为 `test`，流水线里预设成 `production` 时行为跟着变。
- 临时找日志：`captureServerLogs: false` 或 `NUXT_TEST_LOG_LEVEL`。
