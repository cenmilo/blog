你写了一个 Nuxt 模块。它在你自己的示例项目里跑得好，但你真正担心的是：别人装了它之后，`nuxt.config.ts` 里那行 `modules: ['my-module']` 会不会把事情搞坏。

模块作者的测试要解决的就是这个。官方那一节（`guide/modules/testing`）给的思路很具体：**建一个装了你的模块的小应用，然后去请求它**。

## 先说这一节缺的那一半

这一节的说明文字是 "Learn how to test your Nuxt module with unit, integration and E2E tests."，正文也确实有两节。但 Write Unit Tests 那一节的**全部内容**只有一条提示：

> We're still discussing and exploring how to ease unit and integration testing on Nuxt modules.

后面跟一句 "Check out this RFC to join the conversation"，指向 `nuxt/nuxt` 仓库的 discussions/18399。

也就是说：**模块的单元测试与集成测试，4.x 文档目前没有给出方法**。这一节有实质内容的只有端到端和手工验证两节。按标题去凑"三种测试各写一段"是凑不出来的——凑出来的一定是猜的。

## 端到端的五步

开头一句定位：**"Nuxt Test Utils is the go-to library to help you test your module in an end-to-end way."**，接着给出要采纳的工作流：

1. 在 `test/fixtures/*` 里创建一个作为 "fixture" 用的 Nuxt 应用
2. 在测试文件里用这个 fixture 配好 Nuxt
3. 用 `@nuxt/test-utils` 提供的方法与这个 fixture 交互（例如请求一个页面）
4. 对这个 fixture 做检查（例如 "HTML contains ..."）
5. 重复

fixture 侧的官方示例是一个配置文件：

```ts [test/fixtures/ssr/nuxt.config.ts]
// 1. Create a Nuxt application to be used as a "fixture"
import MyModule from '../../../src/module'

export default defineNuxtConfig({
  ssr: true,
  modules: [
    MyModule,
  ],
})
```

三处细节都在传递同一件事：`ssr: true` 是显式写出来的（这个 fixture 要验证的就是服务端渲染）、模块**从 `../../../src/module` 直接引源码**而不是引包名、目录层级是 `test/fixtures/<名字>/`。

测试侧的官方示例：

```ts [test/rendering.ts]
import { describe, expect, it } from 'vitest'
import { fileURLToPath } from 'node:url'
import { $fetch, setup } from '@nuxt/test-utils/e2e'

describe('ssr', async () => {
  // 2. Setup Nuxt with this fixture inside your test file
  await setup({
    rootDir: fileURLToPath(new URL('./fixtures/ssr', import.meta.url)),
  })

  it('renders the index page', async () => {
    // 3. Interact with the fixture using utilities from `@nuxt/test-utils`
    const html = await $fetch('/')

    // 4. Perform checks related to this fixture
    expect(html).toContain('<div>ssr</div>')
  })
})

// 5. Repeat
describe('csr', async () => { /* ... */ })
```

把五步编号对回代码：第 3 步是 `await $fetch('/')`，第 4 步是 `expect(html).toContain('<div>ssr</div>')`，第 5 步是最后那句注释下的 `describe('csr', ...)`。

**这份示例里没有 `import { setup } from '@nuxt/test-utils/e2e'` 之外的环境配置**，也没提 vitest 配置怎么写、`rootDir` 要不要出现在别处。也就是说模块作者的这套 fixture 写法走的是 e2e 那条入口，`rootDir` 指到 fixture 目录即可，不需要把整个模块仓库配成应用。

三个容易被忽略的点：

- `rootDir` 用 `fileURLToPath(new URL('./fixtures/ssr', import.meta.url))` 拼，而不是相对 `process.cwd()`。这是 ESM 下唯一稳定的写法，示例给的就是它。
- 断言是 `toContain('<div>ssr</div>')`——**字符串包含**，不是选择器查询。模块的输出形态变了，这条断言会先响。
- 每个 `describe` 对应一个 fixture（`ssr` 与 `csr` 是两个场景），文档的注释就写着 "Repeat"。

文档还留了一句 "An example of such a workflow is available on the module starter"，指向 `nuxt/starter` 仓库 module 分支的 `test/basic.test.ts`。

## 手工验证：playground 与 npm pack

最后一节叫 Test Manually，两段。

第一段只有一句：开发模块时**有一个 playground Nuxt 应用来测它是非常有用的**，并指出模块 starter 已经为此内置了一个（链接指向 `guide/modules/getting-started` 的 Develop Your Module 小节）。

第二段是可以直接照做的跨项目验证流程：把自己的模块拿到**不属于这个仓库的 Nuxt 应用**里测。做法是用 `npm pack`（或你包管理器的等价命令）从模块打出一个 tarball，然后在测试项目里把它作为 `"my-module": "file:/path/to/tarball.tgz"` 加进 `package.json` 的依赖，装完之后就能像任何普通项目那样引用 `my-module`。

这条流程的价值在于它绕开了软链：`file:` 协议装进去的是一份真实副本，接近别人 `npm install` 之后拿到的东西。文档只写了这一步怎么做，没写装完之后要不要在 `nuxt.config.ts` 里做什么额外处理——按那句 "reference `my-module` like in any regular project"，就是照常写进 `modules` 数组。

## 自查

- 这一节只给了端到端与手工验证两种做法；**单元与集成测试官方仍在 RFC 讨论中，没有方法可抄**。
- fixture 的三要素：放在 `test/fixtures/<场景名>/`、`nuxt.config.ts` 里从 `../../../src/module` 引源码、显式写出 `ssr: true` 这类要验证的开关。
- 测试文件里 `setup({ rootDir })` 用 `fileURLToPath(new URL(...))` 拼路径；每个 `describe` 对一个 fixture。
- 官方断言方式是 `$fetch('/')` 拿 HTML 再 `toContain(...)`，不是 DOM 查询。
- 跨项目手工验证走 `npm pack` + `file:/path/to/tarball.tgz`，装完按普通项目引用。
