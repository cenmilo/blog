你在 `server/api/hello.ts` 里写了个处理函数，想给它写测试。第一个卡住你的问题很基础：**请求路径该写什么**。

## 路径由目录决定

`directory-structure/server` 那一节给的是两条前缀规则：

> Files inside the `~~/server/api` are automatically prefixed with `/api` in their route.
> To add server routes without `/api` prefix, put them into `~~/server/routes` directory.

官方示例是一个文件加一句结果：

```ts [server/routes/hello.ts]
export default defineEventHandler(() => 'Hello World!')
```

> Given the example above, the `/hello` route will be accessible at http://localhost:3000/hello.

写成表就是：

| 文件位置 | 请求路径 |
| --- | --- |
| `server/routes/hello.ts` | `/hello` |
| `server/api/hello.ts` | `/api/hello` |

这一条在测试里特别容易搞错，因为测试服务器的端口不是 3000——端到端那侧的端口由 `setup` 的 `port` 决定，或者干脆由它随机分配（`url('/page')` 的示例结果里是 6840）。所以测试里**只写路径，不要写死端口**。

还有一句要留在心里：那一节的 `::note` 说服务端路由目前不支持 pages 那样的完整动态路由功能。你要测动态段的路由行为，别按 pages 的经验假设。

## 通道一：真的起一个服务器

端到端这一侧走的是真请求。前提在 `setup` 的选项里：

- `server`：是否启动一个响应请求的服务器，默认 `true`（给了 `host` 就是 `false`）。
- `build`：是否单独跑一步构建，默认 `true`（`browser` 或 `server` 关掉、或给了 `host` 时为 `false`）。
- `host`：给了就直接对那个 URL 测，不构建也不新起服务器。

三个方法对应三种断言粒度：

| 方法 | 官方定义 | 拿到什么 |
| --- | --- | --- |
| `$fetch(url)` | Get the HTML of a server-rendered page | HTML 字符串 |
| `fetch(url)` | Get the response of a server-rendered page | 响应对象，示例里取 `res.body` 与 `res.headers` |
| `url(path)` | Get the full URL for a given page | 含测试服务端口的完整地址 |

```ts
import { describe, expect, it } from 'vitest'
import { $fetch, setup } from '@nuxt/test-utils/e2e'

describe('my test', async () => {
  await setup({
    // test context options
  })

  it('my test', async () => {
    const html = await $fetch('/')
  })
})
```

测服务端路由时最容易顺手写的是"断言返回的 JSON 字段"。**文档里没有这种示例**——`$fetch` 那节的定义只说取页面 HTML。`fetch` 返回的 `body` 与 `headers` 里，示例只演示了解构，没演示断言。要断言状态码、断言 JSON 形状，官方未给出写法，只能你自己按 `fetch` 返回对象的实际能力试，并在试出来之前不要把它写进团队的测试规范里。

服务端行为怎么断言？只有一条通道，而且文档里唯一的例子恰好就是服务端路由：

```ts
import { expect, it, vi } from 'vitest'
import { $fetch, clearServerLogs, getServerLogs } from '@nuxt/test-utils/e2e'

it('captures console.log output from a server route', async () => {
  clearServerLogs()
  await $fetch('/api/log-test')
  await vi.waitFor(() => {
    expect(getServerLogs().some(line => line.includes('[test] server-log-marker'))).toBe(true)
  })
})
```

三行连起来看：先清空、再请求、然后用 `vi.waitFor` **轮询**日志里有没有标记串。为什么不能直接断言——`getServerLogs()` 返回的是"自上次 `startServer()`（或 `clearServerLogs()`）以来从服务端子进程 stdout/stderr 捕获的行"，日志到达与请求完成之间没有同步点，所以需要 `waitFor`。另外它有个前提：`captureServerLogs` 为 `true`（默认值），置 `false` 就退回继承 stdio，那时控制台能看到但 `getServerLogs()` 读不到内容。

这条通道只到"服务端打印了什么"，不是"服务端返回了什么"。

## 通道二：在单元环境里造一个假接口

如果你要测的是**组件**——它挂载时会请求某个接口，而你并不想测那个接口本身，那用 `registerEndpoint`：

> `registerEndpoint` allows you create Nitro endpoint that returns mocked data. It can come in handy if you want to test a component that makes requests to API to display some data.

```ts
import { registerEndpoint } from '@nuxt/test-utils/runtime'

registerEndpoint('/test/', () => ({
  test: 'test-field',
}))
```

第一个参数是接口名（例如 `/test/`），第二个是返回假数据的工厂函数。默认方法那句要记住：**"By default, your request will be made using the `GET` method."** 换成别的方法要把第二个参数改成对象：

```ts
registerEndpoint('/test/', {
  method: 'POST',
  handler: () => ({ test: 'test-field' }),
})
```

对象三个属性：`handler`（事件处理函数）、`method`（可选，要匹配的 HTTP 方法）、`once`（可选，为 `true` 时该处理器只服务第一个匹配请求，之后自动移除）。

`once` 这一条在连续请求的测试里会咬你一口：设了它，第二次请求就没有处理器了。文档没写那时请求会怎样，别猜，自己跑一次看返回。

组件请求的是外部 API 时，官方给的是另一句：用 `baseURL`，然后通过环境覆盖配置（写作 `$test`）把它置空，于是所有请求都落到 Nitro 服务器上，也就是落到你刚注册的假接口。

## 该走哪条

按文档能确证的区分是这样的：**要验证真实的服务端路由实现，只能走通道一**，因为只有它跑着真的应用；通道二造出来的是假接口，它验证的是"组件在拿到这份数据时的表现"。

`server/` 目录本身在两种模式下的差别也写在选项里：单元环境（`@nuxt/test-utils/runtime`）没有加载你的服务端路由，接口是你 `registerEndpoint` 显式注册的；端到端环境里跑的是构建出来的应用，路由按目录规则自动生成。

## 自查

- 路径按目录定：`server/api/**` 带 `/api` 前缀，`server/routes/**` 不带；测试里只写路径，端口由 `setup` 决定。
- 通道一的三个方法各有粒度：`$fetch` 拿 HTML、`fetch` 拿响应、`url` 拿完整地址；断言 JSON 字段与状态码的写法官方未给示例。
- 服务端行为只能断言日志：`clearServerLogs()` → 请求 → `vi.waitFor` 轮询 `getServerLogs()`，前提是 `captureServerLogs` 为 `true`。
- 通道二的 `registerEndpoint` 默认 GET，改方法要传对象（`handler`/`method`/`once`），`once` 只服务第一个匹配请求。
- 外部 API 靠环境覆盖 `$test` 把 `baseURL` 置空引到 Nitro；单元环境不会加载你的 `server/` 路由。
