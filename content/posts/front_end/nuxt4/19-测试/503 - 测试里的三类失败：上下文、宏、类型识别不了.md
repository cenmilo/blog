给组件写完第一个测试，一跑就红。红法有几种，每种指向的修法完全不同，认出现场比改断言重要。

## 一、组合式函数找不到实例

错误码 `NUXT_E1001`，官方描述：

> A composable that needs the Nuxt instance (`useNuxtApp()`, `useRoute()`, `useFetch()`, …) ran outside a plugin, Nuxt hook, route middleware, or Vue `setup()`. The most common trigger is calling it inside an async callback (`setTimeout`, `.then()`, after an `await`) where the context has been lost.

修法原句：

> Call the composable synchronously at the top of `setup()` / a plugin / middleware and reuse the captured result later. For server-side async work, wrap the call with `nuxtApp.runWithContext()`.

四个合法位置是：**插件、Nuxt 钩子、路由中间件、Vue `setup()`**。

测试里为什么特别容易撞上？因为测试代码经常长得像"异步回调"：你在 `it()` 里 `await` 之后再调组合式函数，`await` 之后上下文就已经丢了——这正是描述里点名的第三种触发。官方给的两条路在测试里同样适用：要么在测试开头同步取好值，要么用 `nuxtApp.runWithContext()` 包住。

另一条更常见的成因是**测试根本没跑在 Nuxt 环境里**。官方在 Organizing Your Tests 的 `::important` 里把这条讲成正面规则：

> Unit tests should not depend on Nuxt runtime features like auto-imports or composables. Only add TypeScript path alias support if your tests import from your source files (e.g., `~/utils/helpers`), not for Nuxt-specific features.

也就是说：用了 `useState`、`useFetch` 的测试，不该待在 `test/unit/`。要么挪进 Nuxt 环境的 project，要么用文档给的单文件开关——在文件顶部写 `// @vitest-environment nuxt`，或者把文件命名成 `.nuxt.spec.ts`。这两种办法出现在"Conflict with End-To-End Testing"那一节，原文是 "you can split your tests into separate files. You then either specify a test environment per-file with the special `// @vitest-environment nuxt` comment, or name your runtime unit test files with the `.nuxt.spec.ts` extension."

## 二、编译期宏在运行时被执行

`NUXT_E1007`，官方描述：

> A compile-time macro such as `definePageMeta()` executed at runtime. These helpers are transformed away by the Nuxt build and must never run dynamically. Usually this means the macro was called inside a composable or a non-page component instead of directly in a page.

修法：**只在页面组件 `<script setup>` 的顶层调用**；composables、条件分支、非页面组件三处是禁区。

这条在测试里的现场通常是：你把 `definePageMeta()` 塞进了准备单测的那个组合式函数，或者测的是个复用了页面写法、但并不是页面的组件。错误页讲的是通用规则，**没有专门说测试环境下的行为差异**——不要以为跑在测试里就有例外。

顺带一条相关的：官方在 E1001 那页的 read-more 指向的是错误处理页，不是测试页。也就是说这两条错误的正解都在"怎么写组件"这一侧，不在测试配置里。

## 三、类型识别不了：不是报错，是上下文没带上

症状长这样：`useRouter()` 报"找不到名称"、`~/app.vue` 这条 import 在编辑器里是红的、`#components` 解析不出来。但测试跑起来可能反而正常——或者反过来。

文档给的机制只有一句：

> By default, test files in `test/nuxt/` and `tests/nuxt/` directories are included in the Nuxt app TypeScript context.

在这个上下文里才认 `~/`、`@/`、`#imports` 这些别名，也让 TypeScript 知道自动导入。所以**目录位置决定类型识别**，不是文件名。

配套那条 `::tip` 补了一句：这与推荐结构一致，只有需要 Nuxt 运行环境的测试才放这些目录；`test/unit/` 之类目录里的单元测试如果需要，得手工加进去。手工加的方法在配置里：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  typescript: {
    tsConfig: {
      include: [
        // this path is relative to the generated .nuxt/tsconfig.json
        '../test/other-nuxt-context/**/*',
      ],
    },
  },
})
```

注释那行是硬要求：**路径是相对生成的 `.nuxt/tsconfig.json` 写的**，不是相对项目根。这条写错了表现就是"配置加了、类型还是认不出来"。

但 `::important` 那段又立刻划了线：只有当测试真的从你的源码文件导入（`~/utils/helpers` 这种）才去加别名支持，**不要为了让单元测试能用 Nuxt 特性而加**。想清楚了顺序是：先问这个测试该不该在 Nuxt 环境里，再谈类型配置。

## 四、看着像 bug 的两件事

**单元测试里没有水合。** 环境事实写在 Running Tests 的 `::warning`：跑在 happy-dom 或 jsdom 里，测试执行前会初始化一个全局 Nuxt 应用（包括插件和 `app.vue` 里的代码）。所以你在断言里等"水合完成"是等不到的——那段过程在这个环境里不存在。要覆盖水合得走端到端，Playwright 那侧的 `goto('/', { waitUntil: 'hydration' })` 是文档里唯一出现 `hydration` 字样的测试用法。

**全局状态会串。** 同一条 `::warning` 的后半句是"要特别小心别改动全局状态，需要改的话就在之后把它重置"。加上 `mockNuxtImport` 那句 "can only be used once per mocked import per test file" 和"记得恢复 mock"的提醒，能解释一类很难查的现象：**单独跑一个测试文件是绿的，全量跑就红**——顺序变了，前一个测试留下的状态被后一个看见。这类失败别去改断言，改的是重置。

## 自查

- `NUXT_E1001` 认四个合法位置（插件／Nuxt 钩子／路由中间件／`setup()`），`await` 之后与异步回调是丢上下文的典型触发；修法是同步取值或 `nuxtApp.runWithContext()`。
- `NUXT_E1007` 认顶层：宏只能在页面组件 `<script setup>` 顶层，composables／条件／非页面组件都是禁区。
- 类型认不出来先看目录：只有 `test/nuxt/` 与 `tests/nuxt/` 默认在 Nuxt TypeScript 上下文里；其它目录用 `typescript.tsConfig.include`，**路径相对 `.nuxt/tsconfig.json`**。
- 想让单个文件进 Nuxt 环境：`// @vitest-environment nuxt` 或 `.nuxt.spec.ts` 后缀，两处写法都在 e2e 冲突那一节。
- 单元测试不发生水合；单跑绿全量红先查全局状态与 mock 未重置，别改断言。
