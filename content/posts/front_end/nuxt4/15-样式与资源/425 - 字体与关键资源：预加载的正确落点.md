首屏字体晚到导致文字跳一下（CLS），或者最大的那张图开始下载得太晚（LCP），常见解法是加 `<link rel="preload">`。在 Nuxt 里这件事写在哪、和另外两种预取怎么区分，是这一篇的内容。

## 落点是 useHead 的 link 数组

`useHead` 的定义："The `useHead` composable allows you to manage your head tags in a programmatic and reactive way, powered by Unhead."，参数表里对 `link` 那行写得很具体：

> `link` | `Link[]` | Array of link objects. Each element is mapped to a `<link>` tag, where object properties correspond to HTML attributes.

也就是说：**数组里每个对象变成一个 `<link>` 标签，对象的键就是 HTML 属性**。所以预加载直接写：

```ts
useHead({
  link: [
    { rel: 'preload', href: '/fonts/FarAwayGalaxy.woff', as: 'font', type: 'font/woff' },
  ],
})
```

（`rel`/`href`/`as`/`type` 这些是属性映射的通用形态，官方给 `link` 数组的示例值是 `rel: 'stylesheet'` + `href`；`useHead` 支持响应式输入。）

同一套机制也用于挂外部样式表——styling 那一节给了两种写法，静态用 `app.head`：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  app: {
    head: {
      link: [{ rel: 'stylesheet', href: 'https://cdnjs.cloudflare.com/ajax/libs/animate.css/4.1.1/animate.min.css' }],
    },
  },
})
```

动态用 `useHead({ link: [...] })`。官方注明底层是 `unhead`，更多控制看它自己的文档。

## 静态还是动态：按是否需要响应式选

427 之前讲过 head 的两种入口，这里按预加载的性质分：

- **每页都要、地址固定** → `app.head.link`（静态；`::important` 明说它不支持响应式数据）。
- **按页/按状态决定** → `useHead()`（支持响应式）。

还要注意 422 那条不对称：只有**构建器看得见的字面量路径**会被自动补 `app.baseURL`；运行时拼出来的 href 不补。预加载字体这类路径若是拼的，前缀要自己处理。

## 字体优先走两条更省事的官方路

预加载是补救手段，官方在字体上其实先给了两条常规路：

1. **本地字体**：文件放 `public/`（例如 `public/fonts`），样式表里用 `url()` 引（`@font-face` + `font-display: swap` 那份示例就是 `src: url('/fonts/FarAwayGalaxy.woff') format('woff')`）。
2. **网络字体**：用 Nuxt Google Fonts 模块加载；用 UnoCSS 的话它自带 **web fonts presets**，能从包括 Google Fonts 在内的常见供应商取字体——这种场景就别再叠一个字体模块。

再往上一层是模块化的方案：Nuxt Fonts 会处理 CSS 里的 `font-family` 声明，自动**解析字体、生成 `@font-face`、代理并缓存到 `/_fonts` 本地自托管、创建 fallback metrics 以减小 CLS、把字体打进构建并设长缓存头**。performance 那页的原话是它"will automatically optimize your fonts (including custom fonts) and remove external network requests for improved privacy and performance"。

也就是说：手写 preload 之前，先看是不是该由字体模块统一做——它会消掉外链请求，也就消掉了大部分手工预加载的必要。

## 首屏大图用 preload 属性

图片侧官方给的示例是 NuxtImg 上的 `preload`：

```html
<!-- 🚨 Needs to be loaded ASAP -->
<NuxtImg
  src="/hero-banner.jpg"
  format="webp"
  :preload="{ fetchPriority: 'high' }"
  loading="eager"
  width="200"
  height="100"
/>

<!-- 🐌 Can be loaded later -->
<NuxtImg
  src="/facebook-logo.jpg"
  format="webp"
  loading="lazy"
  fetchpriority="low"
  width="200"
  height="100"
/>
```

官方给这组的分类依据是**图片是否属于 LCP**："the ones that are needed to be delivered first at initial load (i.e. `Largest Contentful Paint`), and the ones that can be loaded later or when specifically needed."

## 别和"跨路由转发预加载"混

三个东西名字都带 preload，作用域完全不同：

| 手段 | 目的 | 位置 |
| --- | --- | --- |
| `<link rel="preload">` | 本页马上要用的关键资源 | `useHead`/`app.head` 的 `link` |
| `<NuxtImg preload>` | 本页首屏关键图（LCP） | 组件属性 |
| `experimental.prefetchPreloadTags` | 把**目标页**的 preload 提示转发进当前文档 | 实验开关，**默认关闭**（424 讲了理由与代价） |

424 那条的要点在这儿复述一句：转发出去的图片请求不带 `Purpose: prefetch` 头，会按普通流量计入图片 CDN 的配额与统计，所以它是"确认值得再开"的选项，不是性能默认项。

## LCP 侧的四条通用手段

如果目标是全局 CSS 下载更快，performance 那一节给的不是 preload 而是四条：用 CDN 让文件离用户更近、压缩资源（理想用 Brotli）、用 HTTP2/HTTP3 传输、资源同域托管（不要换子域）。官方补了一句：用 Cloudflare、Netlify、Vercel 这类现代平台时，多数已自动做好。

字体那边对应的推荐是 **Fontaine 降 CLS**（metric fallback），不是 preload。

## 自查

- 手写预加载的落点是 `useHead` 的 `link` 数组（每个对象映射成一个 `<link>`、键即属性），或静态的 `app.head.link`（不支持响应式）。
- 字体优先两条常规路：`public/fonts` + `url()` 本地自托管，或 Google Fonts 模块 / UnoCSS web fonts presets；要自动化就用 Nuxt Fonts（含 fallback metrics 降 CLS、自托管去掉外链）。
- 首屏关键图用 `<NuxtImg preload>`，分类依据是它是否属于 LCP；次要图 `loading="lazy"` + `fetchpriority="low"`。
- 别把"本页 preload"、"组件 preload"和"跨路由转发 preload（默认关）"混为一谈。
- 运行时拼出来的 href 不会被补 `app.baseURL`，只有构建器可见的字面量才自动补。
- 全局 CSS 提速官方给的是 CDN/Brotli/HTTP2-3/同域四条，不是 preload。
