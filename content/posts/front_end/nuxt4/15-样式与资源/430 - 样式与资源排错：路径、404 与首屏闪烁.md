样式问题难查是因为症状都长成"没生效"。但把它分三族，每族都能落到前面某一条已确认的文档事实上，不用靠猜。

## 族一：路径对、请求 404

按这条顺序查：

**① 文件是不是放错了目录。** `app/assets/` 是交给构建工具处理的，官方 `::note` 写死：

> Nuxt won't serve files in the `app/assets/` directory at a static URL like `/assets/my-file.png`. If you need a static URL, use the `public/` directory.

浏览器里敲 `/assets/img/logo.png` 打不开是设计如此（421）——那类文件被打包成了带 hash 的产物。需要固定 URL 的（`robots.txt`、`favicon.ico`、分享图、字体）必须在 `public/`（422）。

**② 路径是不是运行时拼出来的。** 静态字面量才会被重写，`:src` 绑拼出来的值"opaque to the build tool, so none of that rewriting happens"。两类后果：

- `` :src="`~/assets/img/${name}.png`" `` → 构建器从没见过它当 import，**完全不解析**，直接坏。
- 运行时拼的 public 路径 `` `/img/${name}.png` `` → **不会补 `app.baseURL` 前缀**；站点跑在子路径下时它就指到了站点根，于是 404。官方给的处置是自己用 `useRuntimeConfig().app.baseURL` 拼（例如 `joinURL`）。

**③ 子路径部署本身配了没。** 整站挂 `/app/` 下要有 `app.baseURL: '/app/'` 或 `NUXT_APP_BASE_URL=/app/`（361）；资源最终地址是 `baseURL` 拼 `buildAssetsDir`（默认 `/_nuxt/`）。这一条不配对，样式与 JS 会**一起** 404，症状比单张图更明显。

**④ 设了 cdnURL 却指望 head 里的字面量跟着走。** `app.cdnURL` 会让 `public/` 资源从 CDN 出，但 `app.head` 里写死的 `href: '/favicon.ico'` 是字面量、**不参与解析**（422）——要用 `useHead()` 从 runtime config 拼。

## 族二：配置写了、样式不生效

**① 预处理器包没装。** `css` 数组"automatically guess the file type by its extension and use the appropriate pre-processor"，紧跟那句 **"You will still need to install the required loader if you need to use them."**（416）。写了 `.scss` 就得 `npm install -D sass`，否则报错指向预处理器而不是你的配置。

**② 配置写在了不被读的文件里。** `vite.config.ts`、`postcss.config.js` 这些独立文件 Nuxt 不读，必须写进 `nuxt.config` 的 `vite` / `postcss` 键（347、429）。

**③ 换了构建器还留着 Vite 专属配置。** 两条官方限定：预处理器"Nuxt uses Vite by default. If you wish to use webpack instead, refer to each preprocessor loader documentation."；`features.inlineStyles` "currently available **only when using Vite**."。用 `builder` 切过 webpack/rspack 的项目，`vite.css.*` 与 `inlineStyles` 都要重新按 loader 文档处理。

**④ PostCSS 插件只写了配置没装依赖。** `postcss.plugins` 以**包名**为键（419），像 `postcss-nested` 这种默认四插件之外的都得自己装；且它在配置参考里没有具名条目，属正常（不是"不支持"）。

**⑤ 想看谁覆盖了谁。** `css` 数组项之间的层叠先后**文档没写规则**（416），要判定只能看产物：构建出的 CSS 与内联次序，或浏览器 Styles 面板看那条规则最终被谁赢。顺带一个快速判读：`inlineStyles` 开着时 head 里是 `<style>`，关掉/走全局文件时是 `<link>`（427）——先确认你看的是哪种形态。

## 族三：首屏闪一下、字体跳

**① 字体晚到。** 这是 CLS 问题，官方两条对症：给关键资源加 `<link rel="preload">`（落在 `useHead` 的 `link` 数组，425），或用 **Fontaine** 造 fallback metrics 对齐字体度量来降 CLS（它同时把字体自托管到 `/_fonts`、去掉外链请求，425）。

**② 主题两端不一致造成水合不匹配。** 373 说过症状之一就是"content flashing or unexpected layout shifts"，374 的第一/第五类成因正好覆盖样式场景：`localStorage` 读主题、`new Date()`/环境判断写进首屏。这也是 `@nuxtjs/color-mode` 被官方点名的理由——它和 `nuxt-time` 一起被列在"manipulate the DOM to avoid hydration mismatches"（428）。所以主题切换不要在服务端渲出与客户端不同的首屏，用 `<ClientOnly>`（376）或客户端钩子（Kit 那个示例是挂 `app:mounted` 改 `preference`）。

**③ 外部样式表拖慢渲染。** 官方定性："External stylesheets are render-blocking resources: they must be loaded and processed before the browser renders the page. Web pages that contain unnecessarily large styles take longer to render."（415）外链越多越大，首屏越晚。

**④ 图太小/太大都影响 LCP。** 关键图（属于 LCP 的那张）用 `<NuxtImg :preload="{ fetchPriority: 'high' }" loading="eager">`，可以晚点的用 `loading="lazy" fetchpriority="low"`（425）；别把 `noScripts` 当成会去掉 CSS——它只去脚本，"CSS is unaffected"（353）。

## 通用工具

debugging 那页三件照用（338/389）：sourcemaps（`sourcemap: { server: true, client: true }`）、`nuxt dev --inspect`（官方限制：**Node 与 Chrome 要同平台、Docker 里不行**）、IDE 断点配置（VS Code 的 `webRoot` 指向 `srcDir`，默认 `app`）。

## 三族速查

| 症状 | 先查（对应篇） |
| --- | --- |
| 资源 404 | 目录对不对（421/422）→ 是否运行时拼路径（421）→ `app.baseURL`（361）→ cdnURL 字面量（422） |
| 样式不生效 | 预处理器包（416/418）→ 配置文件位置（347/429）→ 构建器是否还是 Vite（429/427）→ PostCSS 插件依赖（419） |
| 首屏闪 / 字体跳 | preload 或 Fontaine（425）→ 两端一致性、color-mode（374/428）→ 外链 render-blocking（415） |

## 自查

- 404 族：`assets/` 不提供静态 URL、运行时拼的 `:src` 完全不重写、运行时拼的 public 路径不补 baseURL、`app.head` 里的字面量不走 cdnURL。
- 不生效族：loader 要自装、独立配置文件不被读、Vite 专属配置在 webpack 下无效、PostCSS 插件按包名传且需自装。
- 闪烁族：字体用 preload/Fontaine 治 CLS、主题两端不一致会水合不匹配（官方因此点名 color-mode）、外链是 render-blocking。
- 层叠顺序文档无规则，看产物或 Styles 面板；head 里是 `<style>` 还是 `<link>` 能立刻告诉你 `inlineStyles` 的形态。
- 工具三件不变：dev 控制台、sourcemaps、`--inspect`（Docker 不能用）。
