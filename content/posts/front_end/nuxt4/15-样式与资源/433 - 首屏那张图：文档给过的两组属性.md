Lighthouse 跑出来 LCP 超标，报告里点名的那块内容就是首页顶部那张大图。你按网上教程把 `<img>` 换成 `<NuxtImg>`，重新跑一遍——分数没动。

原因不意外：`<NuxtImg>` 换的是"这张图怎么被处理和输出"，不是"这张图什么时候被下载"。后者由属性决定，而官方在性能那一节正好给了两组属性写法。

先补一句术语。**LCP**（Largest Contentful Paint）指页面里最大那块内容被画出来的时间，首屏横幅图通常就是那块内容。

## 官方的定性只有一句

原话是这样：

> Unoptimized images can have a significant negative impact on your website performance, specifically the Largest Contentful Paint (LCP) score.

关键词是 **unoptimized**（未优化）。这一节接着介绍了 Nuxt Image 模块，说它是"plug-and-play image optimization"，能用内置优化器或你自己的图片 CDN 来缩放和转换图片。也就是说，光换标签不做配置，"未优化"这个前提没被消掉。

## 图要按重要性分两堆

分组判据官方也写了一句：

> Images in your website can usually be separated by importance; the ones that are needed to be delivered first at initial load (i.e. `Largest Contentful Paint`), and the ones that can be loaded later or when specifically needed.

翻译过来：一次首屏加载就需要送达的，归第一堆；可以晚点、或者用户具体用到才需要的，归第二堆。然后它给的两段示例，属性正好是一正一反。

第一堆，文档注释写的是"需要尽快加载"：

```html
<template>
  <!-- 需要尽快加载 -->
  <NuxtImg
    src="/hero-banner.jpg"
    format="webp"
    :preload="{ fetchPriority: 'high' }"
    loading="eager"
    width="200"
    height="100"
  />
</template>
```

第二堆，注释是"可以晚点加载"：

```html
<template>
  <!-- 可以晚点加载 -->
  <NuxtImg
    src="/facebook-logo.jpg"
    format="webp"
    loading="lazy"
    fetchpriority="low"
    width="200"
    height="100"
  />
</template>
```

## 六个属性逐个对回原文

把两段示例里出现的属性拆成一张表，"有没有解释"指的是：除了示例本身，官方文档里有没有一句说明这个属性干什么。

| 属性 | 出现在哪组 | 官方有没有解释 |
| --- | --- | --- |
| `src` | 两组 | 组件参考页：`src` 会被转成 provider 优化后的 URL |
| `format="webp"` | 两组 | 核心参考未解释，细节在 Image 模块文档 |
| `:preload="{ fetchPriority: 'high' }"` | 第一组 | 核心参考未解释；它产生的是提示标签 |
| `loading="eager"` | 第一组 | 组件参考页只说"支持原生懒加载以及其它 `<img>` 属性" |
| `loading="lazy"` | 第二组 | 同上，这句就是懒加载的出处 |
| `fetchpriority="low"` | 第二组 | 核心参考未解释，是原生 `<img>` 属性 |
| `width` `height` | 两组 | 组件参考页：按 `width` 和 `height` 自动缩放 |

三个要留意的点：

**`loading` 和 `fetchpriority` 一个是驼峰命名差异的写法要照抄**。示例里 `loading` 两处都写成小写属性，而 `fetchpriority` 在第二组是小写全连写、`fetchPriority` 在第一组是驼峰且作为 `preload` 对象的键。这不是笔误：前者是直接落到 `<img>` 上的原生属性名，后者是对象里的键名。

**第一组那个 `preload` 不只是"加个提示"**。424 那篇说过，`<NuxtImg preload>` 这类提示标签的转发受一个实验开关控制，`experimental.prefetchPreloadTags` **默认是关闭的**。所以照抄第一段之后，先在输出 HTML 里确认那条 `link` 关系头有没有真的出来。

**第二组用了 `lazy` 又用了 `fetchpriority="low"`**，两件事方向一致：既让浏览器别急着下载，也让它在浏览器自己的调度里排到最后。

## 这一节没写的部分

`<NuxtImg>` 在核心参考里**没有属性表**，423 那篇已经把这一点讲明了（那一节只有五条能力清单）。上面这六个属性是官方示例里真实出现过的用法，不是一份完整参数列表。`format`、`preload`、以及 `sizes` 的具体取值规则，都得回到 Image 模块自己的文档去查。

有个自查动作可以直接验证分组有没有生效，不用等上线跑 Lighthouse：本地跑 `nuxt dev`，打开浏览器网络面板按发起顺序排，看首屏那张图的请求是排在关键脚本前面还是后面。如果它还排在一大堆脚本之后，说明第一组属性没配全或者提示没落地。

## 自查

- 换标签不解决 LCP，官方说的是 **未优化** 的图片拖 LCP，优化本身要靠 Image 模块的 provider 或你自己的图片 CDN。
- 分组判据：首屏就要送达的，和可以晚点或按需的。
- 第一组三件套：`format="webp"`、`:preload="{ fetchPriority: 'high' }"`、`loading="eager"`，再带 `width`/`height`。
- 第二组三件套：`format="webp"`、`loading="lazy"`、`fetchpriority="low"`，同样带 `width`/`height`。
- `preload` 产生的提示标签默认被 `experimental.prefetchPreloadTags` 关着。
- 示例里的六个属性不等于属性表，完整参数在模块文档。
