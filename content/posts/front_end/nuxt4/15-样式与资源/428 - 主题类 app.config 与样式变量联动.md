把主色、圆角、深浅色开关这些"主题值"从散在 CSS 里挪到一处可配置的对方，官方给的容器就是 `app.config`——它的示例文档里写的正好就是 `theme`。这一篇讲这条链的哪几段是文档记载的、哪一段得自己接。

## 官方示例就是主题

`directory-structure/app/app-config` 的第一个例子：

```ts [app/app.config.ts]
export default defineAppConfig({
  theme: {
    primaryColor: '#ababab',
  },
})
```

configuration 那页给的另一个例子也是同一形状（`title` 加 `theme: { dark: true, colors: { primary: '#ff0000' } }`）。也就是说"主题类配置放 app.config"是官方示例本身的选择，不是社区约定。

读取是通用的一行：

```vue
<script setup lang="ts">
const appConfig = useAppConfig()

console.log(appConfig.theme)
</script>
```

官方注明这**在服务端渲染页面时和浏览器里都能通用访问**。

## 主题配置需要的三个性质，它都有

| 性质 | 官方依据 |
| --- | --- |
| 构建期确定的公开值 | "used to expose public variables that can be determined at build time"；与 `runtimeConfig` 相反，**不能用环境变量覆盖** |
| 响应式、支持热更 | "with the ability to update it at runtime within lifecycle or using a nuxt plugin and editing it with HMR (hot-module-replacement)"；348 那张表里 app.config 的 Reactive 与 HMR 都是 ✅ |
| 运行期可改 | `updateAppConfig(newAppConfig)` 直接生效 |

主题改动要立刻看到效果（改主色不必重启），这三条正好对应；而"能不能被环境变量覆盖"对主题是**不需要**的——它本来就该在构建期定死。

**一条不可越的边界**，官方用 `::caution` 写着：

> Do not put any secret values inside `app.config` file. It is exposed to the user client bundle.

主题值公开无妨，但这意味着 `app.config` 永远不是放密钥的地方（要密钥走 `runtimeConfig` 私有层，见 341/345）。

## 接到 CSS 上：靠 `v-bind`，且这一步是文档给的

要说清一条：**4.x 文档没有"app.config 自动映射成 CSS 变量"这种通道**。把值用到样式上，官方记载的能力是 SFC 样式块里的 `v-bind`：

> You can reference JavaScript variables and expressions within your style blocks with the v-bind function. The binding will be dynamic, meaning that if the variable value changes, the style will be updated.

于是这条路就顺了——`useAppConfig()` 拿到的响应式值，直接用 `v-bind` 进 style 块：

```vue
<script setup lang="ts">
const appConfig = useAppConfig()
</script>

<template>
  <button class="cta">主按钮</button>
</template>

<style>
.cta {
  background-color: v-bind('appConfig.theme.primaryColor');
}
</style>
```

组件级够用；要全站共享一组变量，就需要自己把值写到根元素的 CSS 自定义属性上（例如在布局根节点绑 `:style`）。**这一段是常规 CSS 手法，文档没有专门记载，别当成 Nuxt 特性去找开关。**

## 深浅色开关：官方走的是 color-mode 模块

`dark` 这类偏好，文档里出现的是 `@nuxtjs/color-mode`，而且有两处真实身份：

**① Kit 插件示例**——一个 `mode: 'client'` 的插件里改偏好：

```ts [runtime/plugin.ts]
export default defineNuxtPlugin((nuxtApp) => {
  const colorMode = useColorMode()

  nuxtApp.hook('app:mounted', () => {
    if (colorMode.preference !== 'dark') {
      colorMode.preference = 'dark'
    }
  })
})
```

注意时机：官方这个例子把动作挂在 **`app:mounted`**（371：客户端挂载后才触发）而不是 setup 顶层——这跟 369/370 那条"浏览器专属操作放挂载之后"是同一条规矩。

**② onPrehydrate 页把它当范例点名**：

> For example, `nuxt-time` and `@nuxtjs/color-mode` manipulate the DOM to avoid hydration mismatches.

也就是主题切换这类"必须改 DOM 上的标记"的活，官方明确归到**要避免水合不匹配**的那一类（374 的头号成因正是两端算得不一样）。这也是为什么它偏好在服务端不可靠、要放到客户端去做。

## 值与样式变量的分工建议

把两件事分开会更清楚：

- **主题值**（主色、开关）→ `app.config`，响应式、支持 HMR、进客户端包所以别放密钥。
- **实际渲染出来的样式**→ CSS（`v-bind`、类名、媒体查询），组件内隔离用 `scoped`/CSS Modules（417）。
- **图层复用**：多项目共用一套主题默认值，走图层里各自的 `app.config`，用官方的合并策略——**数组值的键可以用 Function Merger 覆盖默认**（但官方 `::note` 限定：function merger 只能用在被扩展的图层里，不能用在项目主 `app.config`）。

## 一条要提前知道的限制

`app.config.ts` **与 Nitro 共享**，因此有两项后果（官方 Known Limitations）：不能在里面直接 import Vue 组件；部分自动导入在 Nitro 上下文不可用。官方还给了方向：Nitro v3 会通过**移除对 app config 的支持**来解决这些限制——所以重度依赖 `app.config` 承载复杂逻辑的，要留意这条路线变化。

类型侧别忘了：`app.config` 文件里的键，在服务端路由、`shared/` 与 `nuxt.config` 里被推成 `unknown`，要三处都可见就把增强 `.d.ts` 放 `shared/`（409/396）。

## 自查

- 官方示例本身就是 `theme`；`useAppConfig()` 服务端与浏览器都能读。
- 三条性质：构建期确定的公开值（**不能用环境变量覆盖**）、响应式＋支持 HMR、`updateAppConfig` 运行期可改。
- `::caution`：`app.config` 进客户端包，**不放任何密钥**。
- 文档**没有** app.config→CSS 变量的自动通道；官方记载的接法是 style 块里的**动态 `v-bind`**，全站变量要自己绑到根元素（这一步是常规手法）。
- 深浅色官方走 `@nuxtjs/color-mode`：Kit 示例在 `mode:'client'` 插件里挂 `app:mounted` 改 `preference`；onPrehydrate 页点名它"操作 DOM 以避免水合不匹配"。
- 图层共用主题用各自的 `app.config`＋数组键的 Function Merger（仅扩展图层可用）。
- 限制：与 Nitro 共享（不能 import Vue 组件、部分自动导入不可用），且 Nitro v3 计划移除 app config 支持。
