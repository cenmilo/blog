423 说清了 NuxtImg 能做什么。这一篇说它**不能**做什么、以及哪些和图片有关的行为是**默认关着**的——后者在图片上特别容易踩，因为图片优化本身就是为了省流量，一个默认关闭的开关若不小心打开，反而会把流量放大。

## 边界一：组件依赖模块，也能被关掉

正面：`npx nuxt module add image` 装了并启用，`<NuxtImg>`/`<NuxtPicture>` 才存在（423）。

反面：模块可以在图层里按**配置键**关掉。layers 那一节给的写法里就有这一行：

```ts
image: false, // Disables @nuxt/image
```

并且官方直接点名了键名规律：

> The config key is defined by each module. Common examples include `image` for `@nuxt/image`, `pinia` for `@pinia/nuxt`, and `content` for `@nuxt/content`. Check the module's documentation for its specific config key.

也就是说：**`@nuxt/image` 的开关键是 `image`**，设为 `false` 就禁用；modules 那一节也另有一处 "Disable `@nuxt/image` module" 的示例。反过来——想知道某个模块能不能这么关，看它自己的配置键，不是猜包名。

后果值得提醒：图层里关了 `image`，用到 `<NuxtImg>` 的页面就没有这个组件了（回到 423 那句"没装/没启用就没有"）。

## 边界二：逐属性细节不在核心文档

4.x 的 `api/components/nuxt-img` 与 `nuxt-picture` 两节**没有任何属性表**，只有五条能力清单一句 drop-in 定义，末尾 `::read-more` 指向 `image.nuxt.com/usage/nuxt-img`。

所以在 Nuxt 核心文档里查"某个属性支持不支持"是查不到的——按 423 的口径，这部分归 Image 模块文档。核心文档里能看到的具体用法只有 performance 那一节给的两个例子（`format="webp"`、`:preload="{ fetchPriority: 'high' }"`、`loading="eager"` 与 `loading="lazy" fetchpriority="low"`，配合 `width`/`height`）。

## 边界三：`prefetchPreloadTags` 默认关闭

这是和图片直接相关、且官方**写明默认关**的那个实验项。它做的事：

> When a `<NuxtLink>` is prefetched and the destination route has payload extraction enabled (the default for prerendered and cached routes), forward any `<link rel="preload">` hints that the destination set via `useHead` (or via modules like `@nuxt/image`'s `<NuxtImg preload>`) into the current document.

拆开条件：目标路由得**开着 payload extraction**（预渲染与缓存路由的默认），且这条链是由 `<NuxtLink>` 预取触发的。被转发的提示里就包含 `<NuxtImg preload>` 产生的那些。

转发规则官方写了三条：

- 转发来的 link 从 `rel="preload"` **降级为 `rel="prefetch"`**；**例外**是 `as="image"` 的提示——它们保留 `rel="preload"`，但会**剥掉 `fetchpriority`**。
- **只转发用户自定义的 head 标签**；构建期的 JS/CSS chunk 预加载由预取流水线另外处理，不在这里。

## 为什么默认关：官方给了完整理由

> This flag is off by default because, combined with `prefetchOn: 'visibility'` (the `<NuxtLink>` default), it could trigger a lot of cross-route prefetches at once. Enable it once you are confident the destination preloads are worth forwarding for the links your users typically encounter.

三个要点：

1. 原因是**叠加效应**：`prefetchOn: 'visibility'` 是 `<NuxtLink>` 的默认（链接一进视口就预取），再叠上"转发目标页的 preload"，一次能触发大量跨路由预取。
2. 开启时机官方给了判据：**确认**你的用户真的常点的那些链接、其目标页预加载值得转发，再开。
3. 还有两条代价官方点名了：

> Chromium and Safari log a `was preloaded using link preload but not used within a few seconds` warning for each forwarded image hint on a route the user never visits. Forwarded image requests also carry no `Purpose: prefetch` header, so they count as ordinary traffic against image CDN quotas, rate limits and analytics.

也就是：用户没去的路由，每个被转发的图片提示都会在 Chromium/Safari 留一条"preload 未被使用"的警告；而且转发出的图片请求**不带 `Purpose: prefetch` 头**，因此在图片 CDN 那边按**普通流量**计入配额、限流与统计。

开法（想清楚之后再写）：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    prefetchPreloadTags: true,
  },
})
```

官方还挂了 issue #34953 作为动机说明的去处。

## 边界速查

| 事项 | 文档口径 |
| --- | --- |
| 组件是否可用 | 需装启用 `image` 模块；图层里 `image: false` 可关 |
| 逐属性细节 | 核心文档无属性表，归 Image 模块文档 |
| 跨路由预加载转发 | `experimental.prefetchPreloadTags`，**默认关**，理由与代价官方写明 |
| 转发例外 | `as="image"` 保留 `rel="preload"` 但剥掉 `fetchpriority` |
| 转发范围 | 只转发用户自定义 head 标签，chunk 预加载另有通道 |

## 自查

- 模块能力边界三层：装才有组件、`image: false` 能在图层关掉它、逐属性细节在 Image 模块文档而非核心参考。
- 模块配置键由各模块自己定义，`@nuxt/image` 的是 `image`。
- `prefetchPreloadTags` 默认关闭，因为它与 `<NuxtLink>` 默认的 `prefetchOn: 'visibility'` 叠加会一次触发大量跨路由预取。
- 开它的代价：未访问路由会刷"preload 未被使用"警告；转发图片请求无 `Purpose: prefetch` 头，按普通流量算进 CDN 配额。
- `as="image"` 的提示转发时保留 `rel="preload"` 但被剥掉 `fetchpriority`；只转发用户自定义 head 标签。
