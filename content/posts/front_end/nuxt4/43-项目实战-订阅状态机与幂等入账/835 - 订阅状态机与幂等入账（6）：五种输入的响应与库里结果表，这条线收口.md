## 屏幕上已经有十九行读数了

带库带密钥那一趟这样收尾：

```text
Running 21 tests using 4 workers
[验签HTTP·缺头] …
[样本·正序] …
[入账·乱序] …
20 passed (1.0m)
1 skipped
```

五站的判据都按文件排着，每档 `console.info` 一行 JSON，而不是按输入排：同一条"重放"，一条在 `webhook-idempotency.spec.ts`，一条在 `billing-fixtures-ordering.spec.ts`。这一站把它们按输入重排成一张表，再对着当初那句验收条件判一次。

## 那句验收条件先数一遍

这条线开工时对照的是计划里那一行，原话：

> webhook 三类事件（created/updated/deleted）+ 重放 + 乱序 + 签名错 五种输入的响应与 DB 结果表

它自己数不上：三类事件算三种，加"重放""乱序""签名错"是六个标签，句子却写五种。取能对上代码的那种数法。本站 `shared/types/billing.ts` 里的 `HANDLED_EVENT_TYPES` 有五个名字：`checkout.session.completed`、`customer.subscription.updated`、`customer.subscription.deleted`、`invoice.payment_failed`、`invoice.paid`。那句话里的 created 就是结账会话完成；发票那两条是写状态机时补的（扣款失败与补款都要动状态）。于是表按"三种事件各一行，重放与乱序各两种打法，签名错三种输入各一行"排，一共十一行。

这句话还漏了一档：密钥留空回 503。它不是渠道送来的输入，是本站没准备好，运维要看见的不该是同一个码，所以表里给它单独一行。

## 这张表

响应那一列是判据打印的 `状态` 与 `码`，库里那一列读 `stripe_events` 与 `subscriptions`。数值全是本轮那一趟的原文。

| 输入 | 响应 | 库里那一行 | 判据在哪一档 |
| --- | --- | --- | --- |
| 结账会话完成首发 | 200，体里只有 `received` | 事件行落下且 `processed_at` 非空；订阅 1 行、`active`、毫秒 1700000000000 | 834① 第 1 发 |
| 订阅被改 | 200 | 事件行在；订阅 `cancellation_scheduled`、1700000060000 | 834① 第 2 发 |
| 订阅被删 | 200 | 事件行在；订阅 `inactive`、1700000120000 | 834① 第 3 发 |
| 同一条字节重放 | 200 | 事件行仍 1 行；订阅行的毫秒前后都是 1792443800000 | 833② |
| 同一条样本换新时间戳与新签名 | 200 | 行版本一位没动：事件 4060→4060、订阅 4059→4059 | 834② |
| 时间新的先到、旧的补在后 | 200 两发 | 停在 `cancellation_scheduled`、1792443803000；两条事件行都在；行版本 4066→4066 | 833③ |
| 终态后再补一条更旧的 | 200 | 停在 `inactive`、1700000120000；迟到的那条留痕且 `processed_at` 非空；行版本 4085→4085 | 834③ |
| 不带签名头 | 400，`WEBHOOK_SIGNATURE_INVALID` | 0 行 | 832① 加 ⑥ |
| 头里有摘要但验不过 | 400，同一个码 | 0 行 | 832② 加 ⑥ |
| 签名对、时间戳超出容差 | 400，同一个码 | 0 行 | 832③ 加 ⑥ |
| 密钥留空 | 503，`WEBHOOK_NOT_CONFIGURED` | 走不到入库 | 832⑤ |

最后一列那个"加 ⑥"就是这一站唯一的新判据，下一节说它为什么必须存在。

## 表里原本空着的那一格

前四站把签名错钉成了一句"回 400 且三种输入同码"，但**没人读过库里**。这一格空着时，有一类写反测不出来：把入账挪到验签之前——先写一行痕迹、再抛 400。响应码一位不变，表里前七行照样绿——坏的只有那三个 0。坏的地方在第二次：同一条坏载荷再投一次，主键撞上那行痕迹，被当成"处理过了"直接回 200，这道门从此对它永久失效。

所以补了这一档，三条被拒的输入各读一次行数：

```text
[验签HTTP·被拒不留痕] {"时间戳秒":1792443797,
 "响应码":{"evt_reject_nohdr_1792443797":400,"evt_reject_badsig_1792443797":400,"evt_reject_stale_1792443797":400},
 "留痕":{"evt_reject_nohdr_1792443797":0,"evt_reject_badsig_1792443797":0,"evt_reject_stale_1792443797":0}}
```

写反一次的读数（把 `throw` 之前先调一次入账）：

```text
留痕：{"evt_reject_nohdr_1792443557":1,"evt_reject_badsig_1792443557":1,"evt_reject_stale_1792443557":1}
1 failed / 4 passed
```

红的是这一档，另三档（缺头、错签、超容差的响应码）照旧绿——**响应码看不出顺序，只有行数看得出**。

第三个 id 是真签过的（时间戳旧、摘要正确），不然这一档会退化成"又一个错签"，容差那条路径就没被走到。事件 id 带上本次秒数，末尾再把三行删掉：固定 id 的话，那次变异留下的行会让这一档一直红，看着像代码坏了。

## 同一批判据，在两趟里读到的是两件事

不带 `NUXT_E2E_DB` 与密钥那一趟，同样四个文件：

```text
19 skipped
2 passed (32.1s)
```

那两档不带库也能跑：832⑤（密钥留空回 503，正好只有不配密钥时读得到）和 830①（方法门：`GET`／`PUT` 回 404 而 `POST` 不是）。带库那一趟反过来 skip 掉的正是 832⑤——它要求密钥为空，两趟的条件不可能同时成立。**skip 不等于测过**：表里每一个"库里那一行"都只在那一趟存在，默认趟里它们一条都没跑。

## 五步各留一句

- 表先落地，主键用渠道给的那串 id：`subscriptions.id` 存 `sub_…`、`stripe_events.id` 存 `evt_…`，幂等的落点不用再查一遍。
- 状态机写成不碰库的纯函数，比的是事件里那个 `updated`；时间相等也算旧的，不覆盖。
- 门按"格式、摘要、容差"三步走，缺头／错签／超容差回同一个 400，不给对方试探差异的口子。
- 幂等是一句带唯一约束的插入：`on conflict do nothing` 加 `returning`，抢不到那一行就当已经处理过。
- 三份自录样本加两种打法，判据一律写成"响应码＋库里那一行"两条并列，只断 200 等于没判。

## 渠道文档没规定、本站定了四件事

这四条都是选择，不是文档抄来的事实，收口时得逐条认账：

1. **读不懂也回 200**：收下、留痕、盖标记位、不动订阅行。非 2xx 会让渠道重试并重新生成签名与时间戳，一条读不懂的事件就永远卡在队列里。
2. **没有可信 id 时用 `unparsed-<requestId>` 兜**，绝不用空串——空串是一条真主键，第二条读不懂的载荷会撞上它，被当成重复事件。
3. **缺归属三列（用户、客户、价格）任一则一行都不写**，不写半空的订阅行。
4. **同一秒的两条事件，后落库的那条算旧的**：渠道文档没承诺过这件事；真出现同秒双事件，行为以先落库者为准。

还有一条约定要点名：`metadata.userId` 是本站创建订阅时写进渠道对象的。**渠道本身不知道你是谁**，事件回来认出用户全靠这一格；做结账那一步时会再碰到它。

## 这张表判不了的

逐条列。计数以本轮读到的为准：前几站的记录里"某站剩 4 条"与"剩 3 条"两种说法互相不一致，所以把五份记录摊开重数，去重后 12 条。

1. `data.object.updated` 在真投递里放在哪一层，仍然没有凭据：载荷都是自录的，读得到不等于渠道真给。
2. 没有任何判据能证明这三份文件与某次真投递逐字相同——本站没接渠道，这一条永远不会闭合。
3. `paused` 翻成 `inactive`，而"终态不再变"会把恢复挡在外面：真渠道的 `paused → active` 会被判成终态。要么给终态开例外，要么让它单独占一格。
4. "站内状态与渠道报的那格不一致"只进日志，库里没地方存，判据读不到。
5. `reason`（`stale` 还是 `terminal`）只有纯函数那一档看得见，端到端与库里都没有这一位，与第 4 条同一族缺面。
6. `processed_at` 为空的那一行没有重放机制：进程若在占位与处理完之间被杀，就留下一行永不再处理的痕迹。
7. 成功响应体里没有 `requestId`（本轮又读到一次 `有请求号:false`），只有失败那支能拿请求号对上日志。
8. `v0` 这种摘要段只在测试模式出现，本机没有渠道账号，那条输入是自造的。
9. 库侧那两格的破坏性反证没做：把 `processed_at` 改成非空、给事件表挂外键，都要在真库上做 DDL。
10. 规则表只登记了当时试过的 13 种组合，`past_due` 之后收到重复结账这类没逐条钉。
11. `current_period_end` 为空时"过期"那一步直接跳过：没带周期末的更新事件永远不触发过期，真渠道是否每条都带没取证。
12. 行版本只回答"这一行被动过没有"，回答不了"被改成了什么值"，后者还得读数据本身。

真凭据那一档从头到尾没接：这一段全程用自签的本地样本，换一个真账号时只动环境变量。构建流水线也不跑带库那一趟，所以这张表在项目层面仍记作"本机可算合上，带两个条件"。

## 三个当场撞上的现象

| 症状 | 为什么 | 怎么办 |
| --- | --- | --- |
| 一批 16 条同时红，日志里是 `getaddrinfo ENOTFOUND <数据库主机>` | 数据库主机名那一刻没解析出来 | 与代码无关：解析一次确认可达，再原样重跑同一批（本轮重跑即 20 passed） |
| `listen EADDRINUSE :::3590`，但端口表里没有 LISTENING | Windows 出站连接用掉的号还挂在 `TIME_WAIT` | 换 `E2E_PORT`，别改判据 |
| 这一档一直红，库里真躺着 `evt_reject_…` 几行 | 上一趟做过"先入账再拒"的变异，行留下来了 | 现在的 id 带本次秒数并自删；旧版固定 id 要手工删那几行 |

## 本轮跑法记录

本线判据现跑：单测 39 条／7 个文件；端到端 21 条／4 个文件，带库带密钥那趟 **20 passed／1 skipped**（3589），不带那两个变量那趟 **2 passed／19 skipped**（3591，3590 撞在端口占用上）。`npm run check` 八项全 ok（单测 **320 条／50 个文件**，与上一站同数；组件层 67 条／16 个文件）。全量端到端 **255 passed／91 skipped**（3592），跳过分档 要库 43／外部服务变量 24／内容目录 14／另一趟构建 10，没有一条归不进类——多出的那条正是 832⑥。变异一趟：入账挪到拒绝之前，1 failed／4 passed，已还原。应用代码零改动。

往前是结账那一步——`metadata.userId` 得真被写进渠道对象，事件回来才认得出人；再往后是发票页与到期降级。计划里还留着一句"换国内支付渠道要动哪几层接口"，只讲边界，不假装接了。
