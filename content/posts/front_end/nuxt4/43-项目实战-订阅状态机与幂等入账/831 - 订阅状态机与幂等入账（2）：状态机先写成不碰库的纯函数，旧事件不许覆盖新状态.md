## 一条迟到的事件就能把用户状态打回去

`subscriptions` 表里躺着一行：`status` 是 `active`，`updated_at` 是上一笔生效事件的时间。这时候渠道送来一条 `customer.subscription.updated`，而它对象上的 `updated` 比库里那份更早—— webhook 要过网络、会重试、可能排队，到达顺序不是保证得出的；本项目的 §5 那张状态机表就是按"顺序不保证"来定的（Stripe 那一页只给了 `id`／`type`／`created` 三个字段定义，**没有承诺顺序，也没有承诺不会重发**，所以这条规矩得自己立）。接口里如果写的是"收到就更新"，这位用户就会从 `active` 掉回旧状态，而且没有任何报错。

这一站先把这件事处理干净：规则写成一个**不吃数据库、不发请求、不读环境变量**的函数，期望值手写。下一站才建接口，再下一站才谈幂等入账。

## 为什么不顺手写在接口里

同一个理由讲了两次了（聚合函数那一站是第一次）：如果期望值也是调用一遍实现算出来的，改错规则时判据会跟着一起改，绿灯换成另一个意思。状态机比聚合更容易这样——它有"改没改""为什么不改"这种第二位的输出，只测最终状态看不出区别。

所以这个函数的返回是三样东西：

```ts
export interface SubscriptionTransition {
  state: SubscriptionState
  changed: boolean
  reason: 'stale' | 'terminal' | 'expired' | 'transition' | 'no-rule'
}
```

`reason` 是给日志和判据读的那一位。**只有五种**，不许调用方猜"没改"是因为迟到、因为已终结、还是因为根本没这条规则。

## 形状放在 `shared/types/`，时间用毫秒数

两条理由都踩过：

- `#server` 别名只能在服务端用，客户端 import 它会直接报错。而发票页要把"这个订阅现在是什么状态"标出来，所以形状放 `shared/types/billing.ts`，两端共用一份。
- **时间一律 epoch 毫秒，不比 ISO 字符串**。`2026-11-04T10:00:00+08:00` 与 `2026-11-04T02:00:00Z` 是同一时刻，但字典序不认——比出来的结果取决于谁写了哪种格式。判据里干脆用 10、20、30 这种小数字：能被心算的判据，读的人才看得出实现是不是在比大小。

还有一处必须说清：这一层的五个状态名（`none`／`active`／`past_due`／`cancellation_scheduled`／`inactive`）是**本站自己的**，不是渠道那八个（上一站把 Stripe 那份取值清单原文抄下来了，两边只重合 `active` 与 `past_due`）。**渠道名到站内名的映射不在这个文件里**，也不在状态机里，它属于入账那一站——因为只有那里才看得见完整的 payload。

## 判定的顺序比规则本身更容易错

```ts
export function applySubscriptionEvent (当前: SubscriptionState, 事件: SubscriptionEvent): SubscriptionTransition {
  if (事件.occurredAt <= 当前.updatedAt) {
    return { state: 当前, changed: false, reason: 'stale' }
  }
  if (当前.status === SUBSCRIPTION_INACTIVE) {
    return { state: 当前, changed: false, reason: 'terminal' }
  }
  const 周期末 = 事件.currentPeriodEnd ?? 当前.currentPeriodEnd
  if (周期末 !== null && 周期末 <= 事件.occurredAt) {
    return { state: { status: SUBSCRIPTION_INACTIVE, updatedAt: 事件.occurredAt, currentPeriodEnd: 周期末 }, changed: true, reason: 'expired' }
  }
  // 之后才是那四条迁移：删除、结账完成、扣款失败、补款成功、订阅被改
}
```

三步前置各挡一类误判：

| 顺序 | 挡的是什么 | 放后面会怎样 |
| --- | --- | --- |
| 迟到先挡 | 旧事件把新状态改回去 | 任何规则都可能被一条过期事实触发 |
| 终态不再变 | 已停的订阅被乱序事件复活 | 用户"取消后又变成生效"，还得靠人工修 |
| 到期先看 | 周期末已过的订阅还挂着生效 | 会先按"到期取消开了"写成 `cancellation_scheduled`，而它其实已经到期 |

第三条有个配套读法：**事件带新周期末时以事件为准**（`??` 那一句）。逾期之后补款成功，那条事件里的周期末已经被推到未来，于是不算过期、正常回到生效——这条规则如果写成"先看当前那份周期末"就会把补好的用户判成到期。

## 十三条规则，期望值全部手敲

判据是一张表，每行都写着"名字、现状、事件、期望状态、期望改没改、期望原因"：

```json
[状态机·迁移表] [
 {"名":"结账完成把订阅从无带到有","状态":"active","改没改":true,"原因":"transition","新时间":10},
 {"名":"生效中扣款失败掉进逾期","状态":"past_due","改没改":true,"原因":"transition","新时间":20},
 {"名":"逾期后补款成功拉回生效","状态":"active","改没改":true,"原因":"transition","新时间":30},
 {"名":"开了到期取消","状态":"cancellation_scheduled","改没改":true,"原因":"transition","新时间":20},
 {"名":"逾期状态也能挂上到期取消","状态":"cancellation_scheduled","改没改":true,"原因":"transition","新时间":20},
 {"名":"撤回到期取消","状态":"active","改没改":true,"原因":"transition","新时间":30},
 {"名":"渠道说订阅没了","状态":"inactive","改没改":true,"原因":"transition","新时间":20},
 {"名":"周期末已过：到期取消那条先被过期盖住","状态":"inactive","改没改":true,"原因":"expired","新时间":200},
 {"名":"补款带来新周期末，就不算过期","状态":"active","改没改":true,"原因":"transition","新时间":150},
 {"名":"没订阅时收到补款成功：没有规则，不许凭空造一个生效","状态":"none","改没改":false,"原因":"no-rule","新时间":0},
 {"名":"生效中收到补款成功：不动（只有逾期能被它拉回）","状态":"active","改没改":false,"原因":"no-rule","新时间":10},
 {"名":"没订阅时收到扣款失败：同样没有规则","状态":"none","改没改":false,"原因":"no-rule","新时间":0},
 {"名":"已终结之后什么事件都不复活","状态":"inactive","改没改":false,"原因":"terminal","新时间":10}]
```

每行还多钉一句：**改没改决定时间戳走不走**。改了才推到事件时间，没改必须原样退回旧值——否则下一条事件会被前面的这条误判成"迟到"。

## 相等算旧：这条是本站定的，所以钉死

渠道文档没规定同一秒内两条事件谁赢。本站取"相等视为旧"：**同一秒以先落库的那份为准**。判据把这一位单独钉住，同时给它一条正对照（晚一毫秒必须能改）：

```json
[状态机·同一秒] {"相等":{"改没改":false,"原因":"stale"},"晚一毫秒":{"改没改":true,"原因":"transition"},
  "口径":"相等视为旧：同一秒内以先落库的那份为准"}
```

这个选择直接决定下一站的写库量。把 `<=` 改成 `<`（相等算新）之后，红的不是这一档，还有幂等那一档：

```json
[状态机·喂两次] {"第一次":{"状态":"active","改没改":true,"时间":10},
  "第二次":{"状态":"active","改没改":true,"原因":"transition","就是第一次那份":false}}
```

**同一个事件喂两次，第二次也说"改了"** ⇒ 库级幂等再稳（主键冲突挡住重复插入），状态机这一层仍然会白跑一遍、白写一次更新时间。函数级幂等就是这么一条判据：`第二次.state` 必须与第一次的输出是同一个对象引用。

## 正对照不是可选项

"迟到事件被挡"这一档如果只断"没改"，那一个把所有事件都判成旧的实现也能过。所以同一档里必须并排放一条只差时间的正对照：

```json
[状态机·旧事件] {"旧":{"状态":"active","改没改":false,"原因":"stale","就是原来那份":true},
  "新":{"状态":"cancellation_scheduled","改没改":true,"原因":"transition"}}
```

`就是原来那份:true` 是第三件事：没改的时候返回的是**同一个对象**，不是复制品。写库那一步就是靠这一位决定"这条要不要写"。

## 改错一格，红的就是那一格的名字

第二次变异把"逾期后补款成功"这条的目标状态写成 `past_due`（等于什么都没改但说改了）。红的只有迁移表那一档，消息里直接带着行名：

```text
AssertionError: 逾期后补款成功拉回生效：状态不对: expected 'past_due' to be 'active'
```

表驱动的判据要能报到行，不然一次改错要人肉比对十二条输出。做法是把名字放进断言消息，而不是放进日志。

另有一档静态判据钉"这一层没有 IO"：读 `server/services/billing/state.ts` 的源码（**先剥注释**，否则注释里提到的词会变成假阳性），扫 `useDb(`、`await `、`process.env`、`useRuntimeConfig`、`from 'drizzle-orm`、`$fetch` 六个串。本轮命中是空清单。

还有一档专门钉起点：`none` 那一份的 `updatedAt` 必须是 `0`。写成"当前时间"的话，第一条事件永远比它早，会被迟到那条规则挡掉——症状是"用户付了钱但状态一直没动"，很难往这里想。

## 读数对不上时先看哪一处

| 症状 | 先看哪里 | 为什么 |
| --- | --- | --- |
| 付费后状态没动 | 起点那份的 `updatedAt` 是不是 0 | 第一条会被"迟到"规则挡掉 |
| 状态被改回旧值 | 前置三步的顺序 | 迟到判断必须在任何迁移之前 |
| 同一事件写库两次 | 相等算旧还是算新 | 算新就白跑一遍、白更新一次时间 |
| 已取消用户又生效了 | 终态那条是否先于其它规则 | 乱序的更新事件会把它拉回去 |
| 补款后仍显示到期 | 过期那步用的是哪份周期末 | 要用事件带来的新值，没带才沿用量上那份 |
| 状态名对不上渠道 | 站内五个名与渠道八个取值是两套 | 映射在入账那一站，不在这里 |
