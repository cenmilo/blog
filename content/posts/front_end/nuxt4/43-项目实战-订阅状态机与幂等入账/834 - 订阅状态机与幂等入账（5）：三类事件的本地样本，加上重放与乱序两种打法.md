## 机制对上之后，该问真形状了

上一站的载荷是判据里现拼的字符串：一条 `checkout.session.completed` 重发一次，看库里那一行不动。机制已经证了。这一站要问的是另一件事——**三种真形状的事件各自走一遍这两条路，还走得通吗**？

`data.object` 在三种事件里是三种东西：订阅对象、发票对象、结账会话对象。它们都有 `id`、都有一套自己的状态字段，取时间的位置也不同。

于是先把样本落成文件，放在 `test/fixtures/billing/`：

```text
checkout.session.completed.json
customer.subscription.updated.json
customer.subscription.deleted.json
customer.subscription.updated.stale.json
```

前三份就是口径点名的三类事件。第四份是同一类型、时间更早的一份，专门喂"乱序"那一档。为什么要落成文件而不是在判据里现拼：一份真形状的 JSON 摊在目录里，改了哪一格一眼能看到；藏在判据里的字符串只有写它的人看过。

第四份不能复用第三份的 `evt_…`：**同一个事件 id 会被主键当成重放挡掉**，那样测的就不是乱序，而是上一站已经测过的重复投递。这条区别是整个打法的关键。

样本里的时间是固定的秒数（渠道给的单位是秒），三份正序的 `occurredAt` 是 1700000000000、1700000060000、1700000120000，乱序那份是 1700000030000——夹在中间，比最后一份早。数值写死，判据才能手敲期望。

## 输入也得有判据

fixture 是判据的一部分，不是脚手架。它坏的方式都很安静：改了文件名没改内容里的 `type`；两份文件的订阅 id 对不上；有人把自己账号的真实 id 与邮箱贴进来。所以先给文件本身写七条判据（`test/unit/billing-fixtures.test.ts`，不连库，CI 直接跑）：

```json
[样本·形状] [{"文件":"checkout.session.completed.json","类型":"checkout.session.completed","对象种类":"checkout.session","订阅id":"sub_834_unit","时间毫秒":1700000000000,"时间取自":"事件根的 created"},{"文件":"customer.subscription.updated.json","类型":"customer.subscription.updated","对象种类":"subscription","订阅id":"sub_834_unit","时间毫秒":1700000060000,"时间取自":"对象的 updated","渠道状态":"past_due"},{"文件":"customer.subscription.deleted.json","类型":"customer.subscription.deleted","对象种类":"subscription","订阅id":"sub_834_unit","时间毫秒":1700000120000,"时间取自":"对象的 updated","渠道状态":"canceled"},{"文件":"customer.subscription.updated.stale.json","类型":"customer.subscription.updated","对象种类":"subscription","订阅id":"sub_834_unit","时间毫秒":1700000030000,"时间取自":"对象的 updated","渠道状态":"active"}]
```

这一张表把三类对象的差别一次摊开：会话对象没有 `updated` 那一格，只能退回事件根的 `created`；订阅对象两处都有，取对象自己的。同一件事在判据里写成一位 `时间取自`，改了取法会立刻红。

```json
[样本·顺序] {"正序":[1700000000000,1700000060000,1700000120000],"乱序样本":1700000030000,"递增":true,"比终态那条早":true}
[样本·链] {"轨迹":["active:改","cancellation_scheduled:改","inactive:改"],"末步":{"状态":"inactive","改没改":false,"原因":"stale"}}
```

`[样本·链]` 是端到端那条链的纯函数版本：三份样本依次作用在同一个现状上，一步一格；再把乱序那份喂进去，它被"迟到"这条规则挡在门外（不是被"终态"挡的——两条规则谁先跑，这里读得出来）。

还有一档钉词表边界：会话对象自己有个 `payment_status`（值是 `paid`），它既不是订阅状态也不是发票状态，不能顺手当状态机的输入：

```json
[样本·词表边界] {"会话有状态格":false,"会话原文里的状态格":["payment_status"]}
```

这些样本是本站自录的：字段名与单位照渠道那几节写，值全是编的。渠道不提供整条事件的样本文件，所以"照真形状录"不等于"从渠道下载下来的"——这句话必须写在文件头上，否则下一个人会以为这里是真凭据。

## 正序：三份各发一次

```json
[样本·正序] [{"文件":"checkout.session.completed.json","响应":{"状态":200,"码":"(体里没有这一位)"},"事件行":{"在":true,"类型":"checkout.session.completed","处理过":true},"订阅行":{"行数":1,"状态":"active","时间毫秒":1700000000000}},{"文件":"customer.subscription.updated.json","响应":{"状态":200,"码":"(体里没有这一位)"},"事件行":{"在":true,"类型":"customer.subscription.updated","处理过":true},"订阅行":{"行数":1,"状态":"cancellation_scheduled","时间毫秒":1700000060000}},{"文件":"customer.subscription.deleted.json","响应":{"状态":200,"码":"(体里没有这一位)"},"事件行":{"在":true,"类型":"customer.subscription.deleted","处理过":true},"订阅行":{"行数":1,"状态":"inactive","时间毫秒":1700000120000}}]
```

判据是**两条并列**：每一发都读响应码，也读库里那一行——状态走到哪一格、时间毫秒是多少、事件行有没有落下。只断 200 等于什么都没判；只断库里那行，就等于把"渠道收到什么回应"这件事放掉了。三发之后 `subscriptions` 仍是 1 行：迁移走的是更新，不是每来一条插一行。

## 重放那一次，签名是全新的

上一站的重发用的是同一条头（同一个 `t`）。这一站故意换个打法：同一串字节、同一个 `evt_…`，但时间戳现取，于是**签名是全新的**。为什么这值得一判？渠道那一节写着：

> If Stripe retries an event (for example, your endpoint previously replied with a non-`2xx` status code), then we generate a new signature and timestamp for the new delivery attempt.

真重投每一次的签名都不一样。如果幂等键错挂在"这条头是不是见过"上，第二次投递就会把同一事件再处理一遍。读数：

```json
[样本·重放] {"第一发":{"状态":200,"码":"(体里没有这一位)"},"第二发":{"状态":200,"码":"(体里没有这一位)"},"那一行的事件表":{"在":true,"类型":"customer.subscription.updated","处理过":true},"之前":{"订阅":"3935","事件":"3936","行":{"行数":1,"状态":"cancellation_scheduled","时间毫秒":1700000060000}},"之后":{"订阅":"3935","事件":"3936","行":{"行数":1,"状态":"cancellation_scheduled","时间毫秒":1700000060000}}}
```

`订阅` 与 `事件` 那两格是行版本（下一节解释）。重放之后两个都没动，说明这一趟连 `processed_at` 都没再盖一次。

## 别拿表级计数当"这一行被改写"的证据

这一站撞到的坑，正好推翻上一站的一条判据。表级累计计数是这么读的：

```ts
await client.query('select pg_stat_force_next_flush()')
const 结果 = await client.query(
  "select n_tup_upd from pg_stat_user_tables where relname = 'subscriptions'",
)
```

同一趟运行里，重放那一档的表级差读到 `{stripe_events:3, subscriptions:0}`，而那一行的版本没动。**差 3 是隔壁用例正在写别的行**——Playwright 会用多个 worker 并行跑同一文件里的用例。上一站那条"更新次数必须为 0"碰上别的调度顺序就会莫名红一次；下次有人为了消红把断言删掉，判据就没了。

改法是问一行，不是问一张表：Postgres 每重写一次一行，就给它一个新的 `xmin`（写它的那个事务号）。

```ts
const 结果 = await client.query('select xmin::text as 版本 from subscriptions where id = $1', [订阅id])
```

行版本前后相等，就等于这一行一个字节都没被重写，与别的用例在写谁无关。上一站的 `833③` 一起换成行版本，本轮它的读数是 `{"前":"3942","后":"3942","没动":true}`——同一趟里表级计数报 1、行级报没动，两个数并排印在日志里，谁在说谎一眼可辨。

## 乱序：比终态还早的那一条

```json
[样本·乱序] {"终态":{"行数":1,"状态":"inactive","时间毫秒":1700000120000},"迟到":{"状态":200,"码":"(体里没有这一位)"},"迟到之后":{"行数":1,"状态":"inactive","时间毫秒":1700000120000},"迟到那条的事件行":{"在":true,"类型":"customer.subscription.updated","处理过":true},"行版本":{"前":"3960","后":"3960","没动":true},"四张事件行都在":4}
```

四件事同时成立才算这档过了：留痕（事件表多一行、标记位盖上）、回 200（回非 2xx 会被重试并重新签名）、状态不动、这一行没被重写。最后那条尤其别漏：状态没变不代表没写库，写回同一个值也是一次更新，数据面看不出来，只有行版本会涨。

## 占位符把下划线吃掉了

四份文件里有两格是洞：探针用户 id 与一次性后缀。第一版写成 `sub_834__RUN__`，替换的令牌是 `__RUN__`——开头那两条下划线就是分隔符本身，替换之后成了 `sub_834d179…`，中间那个下划线没了。

症状很怪：端到端报"库里没这行"，而同一个用例里按用户查 `subscriptions` 数出一行来。把那一行的 id 印出来才看清少了一横。修法两半：洞改成不吃下划线的写法 `{{RUN}}` 与 `{{USER_ID}}`；再加一条判据，不问文本、问填完之后真的等于什么：

```json
[样本·填洞] {"期望订阅id":"sub_834_zz1700000000000","填完":[{"名":"checkout.session.completed.json","订阅id":"sub_834_zz1700000000000","事件id":"evt_834_checkout_zz1700000000000"},{"名":"customer.subscription.updated.json","订阅id":"sub_834_zz1700000000000","事件id":"evt_834_updated_zz1700000000000"},{"名":"customer.subscription.deleted.json","订阅id":"sub_834_zz1700000000000","事件id":"evt_834_deleted_zz1700000000000"},{"名":"customer.subscription.updated.stale.json","订阅id":"sub_834_zz1700000000000","事件id":"evt_834_stale_zz1700000000000"}]}
```

订阅 id 四份都相同、事件 id 四份都不同——这两条正是这套打法的前提，所以值得单独一档。

还有一条规矩落到探针上：这些文件是带缩进的多行 JSON，一律用 `content-type: text/plain` 发。上一站读到过带 `application/json` 时客户端会重编内容（26 字节变 32 字节），签名就对不上了；多行 JSON 被压平是同一类事故。测试要验的是服务端，不是客户端的编码习惯。

## 两次改错

把订阅 id 的取法加回兜底（`对象.id` 优先）：红两档——`第 1 步之后订阅状态不对`、`第一发就该建出一行`，另两档照绿。因为只会有会话对象那份受影响：它的 `id` 是 `cs_…`，于是建行的订阅 id 与后两发要迁的那条对不上。红两档而不是四档，恰好说明这条判据定位得准。

短路掉"抢不到那一行就返回"：只有重放那档红，消息是 `重放又处理了一遍这条事件（processed_at 被盖了第二次）`——事件行的版本从 3936 变成 3937，而订阅行的版本没动。两层守卫（库级幂等、状态机的 `changed`）本来就是两件事，各红各的才对。

两处都还原并回到原样位置。

## 读数对不上时先看哪一处

| 症状 | 先看哪里 | 为什么 |
| --- | --- | --- |
| 库里明明有行，按 id 查不到 | 洞的写法有没有吃掉分隔符 | `sub_834__RUN__` 替换后少一个下划线 |
| 三条事件打在两个订阅上 | 三份文件的订阅 id 是不是同一格 | 形状判据里 `订阅ids.size === 1` 会先红 |
| 乱序那档测成了重放 | 迟到样本的事件 id 换没换 | 同 id 会被主键挡，测不到顺序 |
| 白写判据偶尔红一次 | 用的是表级还是行级 | 表级计数并行下会把别的用例数进来 |
| 发出去的字节和签的不一样 | 有没有带 `application/json` | 客户端可能重编内容；多行 JSON 会被压平 |
| 会话事件把 `payment_status` 当状态用了 | `渠道状态` 只在订阅对象上带 | 两套词表混起来，翻译表就挡不住了 |
