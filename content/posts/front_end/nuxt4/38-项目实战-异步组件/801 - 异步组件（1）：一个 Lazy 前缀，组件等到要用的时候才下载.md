## 屏幕上那一行，写法已经改过一次

浏览器打开 `http://localhost:3100`，滚到页面下方"接线自检（给部署的人看，不是介绍）"那一节，中间有一行：

```text
契约演示：CmdRagon@example.com
```

它不是直接写在页面里的，是一行组件引用：

```vue
<LazyWiringEmailContract hydrate-on-visible />
```

`Lazy` 是组件名的前缀，不是标签；`hydrate-on-visible` 是一个属性。这两个写法在 788 那一步为了首屏减重加进来的（那一行走的 `parseLoginLink` 站在 zod 上）。这一站不做新机制，只回答一个一直没说清的问题：**加上前缀之后，到底哪件事变了？**

先把三个词说死。**chunk**＝打包后拆出来的小文件；**水合**＝浏览器接手服务端给的那段 HTML、把事件挂上去；**modulepreload**＝HTML 头部先声明一批"这个页面待会儿要用的模块"，浏览器解析到就去取。

## 官方那两段，一句给机制、一句泼冷水

讲组件目录那一节的 `Dynamic Imports` 段：「To dynamically import a component (also known as lazy-loading a component) all you need to do is add the `Lazy` prefix to the component's name. This is particularly useful if the component is not always needed.」

紧接着的 `Delayed (or Lazy) Hydration` 段自己就把话说回来了：「Lazy components are great for controlling the **chunk sizes** in your app, but they don't always enhance runtime performance, as **they still load eagerly unless conditionally rendered**.」

这句是这条线的靶心。"控制 chunk 大小"与"晚点下载"是两件事，官方只承诺了前者。要量的是后者到底有没有发生。

## 六条读数

## 分出去的是 950 字节，不是那 78,654

`契约演示：` 这段文本只会出现在承载这个组件的文件里，所以拿它当标记去扫 64 个客户端文件，命中一个、**950 字节** —— `Lazy` 前缀确实把它从页面那个文件里拆出去了，这一位符合官方承诺。

但同一趟读数里还有两位：`组件在预载里: false`、`组件第几个被请求: 27`、`zod第几个被请求: 28`。翻译过来是：它不在预载名单里（所以不是"入口一解析完就被抢着取"那种），可浏览器在第一趟还是把它取了下来，而紧随其后的那一条就是它 import 的那块校验库，78,654 字节，正是首屏最大三条里的第二条。

顺序本身就是证据：27 与 28 连着，说明 zod 不是被谁静态引进去的，而是**跟着那位组件一起被动态导入拉进来的**。这一层差别在下一站很重要——条件渲染把 27 那一条挪走，28 那一条才会跟着一起不出现。

也就是说：

- 前缀改变的是"代码在哪个文件"和"什么时候开始解析"；
- 没有改变"要不要下载"——因为这一位是无条件渲染的，官方那句 `they still load eagerly unless conditionally rendered` 说的就是这种形状；
- 依赖跟着组件走：组件被 eager 地动态导入，它带的 zod 也一起进来。788 那一刀把 950 字节分出去了，那 78,654 字节仍在首屏最大三条里。

**要让它真的晚下载，得配条件渲染**——这是下一站 802 的全部内容。

## 被推迟的那件事，长得什么样

`hydrate-on-visible` 改变的是**什么时候接手**。这句以前在页面上是看不见证据的：内容一直在那儿（服务端渲的），点了又没反应也说不清是"没水合"还是"事件写错了"。这一站的改动就一处：给这一位挂上 `@hydrated` 计数。

```vue
<LazyWiringEmailContract
  hydrate-on-visible
  @hydrated="水合次数 += 1"
/>
<p data-testid="hydrate-count">这块接手次数：{{ 水合次数 }}</p>
```

依据是同一节 `Listening to Hydration Events` 那句：「All delayed hydration components emit a `@hydrated` event when they are hydrated.」

于是判据能这样钉：开局这一位在视口外（读回来距视口顶 911 像素、视口高 720），计数是 0；`window.scrollTo` 滚到底，计数在 8 毫秒内变成 1。那个"8 毫秒"不是"立刻"的意思——观察者在下一帧才触发，这个数只是"从开始等到看见变化"的间隔，它要证明的是接手没有卡在别的地方（比如等一个永远不来的滚动事件）。

还有一条容易混的：`[异步组件·关脚本] {"有这一行":true}`。这一位被 SSR 照样渲进 HTML，所以关掉脚本、或者爬虫不执行 JS，那行字仍在。延迟水合延迟的不是内容，是这块能不能响应用户。

## 五条注意里，本轮占到两条

同一节末尾列了五条最佳实践，这一站碰到的是这两条：

- **首屏内容别用延迟水合**（「Prioritize In-Viewport Content」）：这一位在页面下方，所以合理；把它挪到第一屏就会伤体验。
- **如果本来就 `v-if="false"`，用普通 lazy 组件就够**（「When using `v-if="false"` on a lazy component, you might not need delayed hydration」）：这一句直接说明"晚下载"归条件渲染管，不归延迟水合管。

另外三条限制（只在单文件组件里生效、props 必须写在模板里不能用 `v-bind` 摊开、从 `#components` 直连不生效）留到 805 各撞一次，本轮不引用来当结论。

## 排错表

| 想核对的东西 | 现成的读数 | 它为什么在那儿 |
| --- | --- | --- |
| 组件代码是否单独成文件 | 扫独有文本，看命中几个文件 | 文件名会随构建变，文本不会 |
| 它是不是"晚点才下载" | 首趟请求序列里的位次 ＋ 预载名单 | 只数总字节看不出"什么时候来" |
| 依赖有没有跟着一起进来 | 同一趟里再扫一份依赖标记 | 拆组件不等于拆依赖 |
| 什么时候开始接手 | `@hydrated` 计数 | 事件不发就没有可读的时机 |
| 内容有没有被延迟掉 | 不带脚本读一次 HTML | SSR 仍然渲，别把延迟水合当 `server: false` |

npm run build
