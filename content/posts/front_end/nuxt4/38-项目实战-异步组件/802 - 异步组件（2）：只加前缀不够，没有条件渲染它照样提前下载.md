## 上一站留的那句话，这一站没兑现

上一篇的结尾写着"要让它真的晚下载，得配条件渲染"。这一站就照着做：在文档页开一个实验档，放一个按钮，把面板组件挂成 `<LazyLabAsyncPanel v-if="显示面板" />`，`显示面板` 起始是 `false`。

浏览器打开 `http://localhost:3100/docs/getting-started?islandLab=async`，屏幕上只有两样东西：一行"按需面板还没进来"，一个"翻开按需面板"的按钮。面板那一行字不在页面上，服务端也没把它写进 HTML——这些都是对的。不对的是 Network 面板：那个装面板组件的文件 `B8rDRKbT.js`，在页面刚打开的第一趟请求里就下来了，排在第 29 个，672 字节。

条件渲染挡住的是渲染，没挡住下载。这一站就把这件事查到能解释为止。

## 官方那两句，一句给写法、一句给承诺

讲组件目录的那一节里，`Dynamic Imports` 那段给的示例正是这个形状：

```vue
<button @click="show = true">Load List</button>
<LazyMountainsList v-if="show" />
```

它说的是「This is particularly useful if the component is not always needed」。同节往下几段的 `Delayed (or Lazy) Hydration` 又补了一句冷水：「they still load eagerly unless conditionally rendered」。两句合起来的承诺是：**只要 `v-if` 起始为假，这份代码就不会提前来**。这一站测的就是这句承诺。

## 先摆上页面的东西

新增组件 `app/components/LabAsyncPanel.vue`。它故意 import 了站在 zod 上的 `parseLoginLink`，因为"这一块到底多重"要看它带什么依赖，光看自己的 672 字节会低估：

```vue
<script setup lang="ts">
import { parseLoginLink } from '#shared/schemas/auth'
const 契约 = parseLoginLink({ email: 'Lab.Async@Example.COM' })
</script>

<template>
  <p data-testid="async-panel">
    按需面板 LAB_ASYNC_802：{{ 契约.ok ? 契约.email : 契约.issue }}
  </p>
</template>
```

`app/pages/docs/[slug].vue` 里的闸门与挂载位，形状和官方示例一致：

```vue
<script setup lang="ts">
const 显示面板 = ref(false)
</script>

<template v-if="实验档 === 'async'">
  <p data-testid="async-note">按需面板还没进来</p>
  <button data-testid="async-open" type="button" @click="显示面板 = true">翻开按需面板</button>
  <LazyLabAsyncPanel v-if="显示面板" />
</template>
```

`app/pages/docs/index.vue` 加了一条入口链接（`data-testid="lab-async"`），方便手点。判据是新文件 `test/e2e/async-component-conditional.spec.ts`，六条。

## 三种写法付的是同一份下载

要问的是"晚一点下载"，那就得看位次，不是看总字节。三档摆在一起：

| 模板里的写法 | 它在不在 DOM 里 | 第一趟位次 | 第一趟总条数 |
| --- | --- | --- | --- |
| 无条件渲染（首页那一位，上一站读的） | 在 | 27 | 36 |
| `v-if` 起始为假（实验档） | 不在 | 29 | 36 |
| 常规访问（实验档不成立，整块不挂） | 不在 | 29 | 36 |

第一列说明渲染这件事管住了：起始为假时 `在页面上:0`，HTML 里也没有 `LAB_ASYNC_802` 那一段。第三列说明下载这件事一点没变：位次都是 29，条数都是 36。上一站读到的首页那一位（`B3i2o3du.js`）也一样在第一趟，位次 27，它带的 zod 在 28、29 位。

也就是说，把 `v-if` 从模板里删掉、让它为假、让整块根本不挂，三种写法的**下载位次一个都没挪走**。

## 取它的不是那句 `import()`，是 HTML 头部的一行链接

这里要先排除一个看起来最像答案的解释。编译后的页面文件 `DhgPiXGD.js` 里，这一位长这样：

```text
z=b(()=>D(()=>import(`./B8rDRKbT.js`).then(e=>e.default||e),__vite__mapDeps([0,1,2,3]),import.meta.url))
```

`import(...)` 包在一个箭头函数里，只有真的要把组件实例化时才会执行。起始为假时它一次都没跑（跑了才会渲染出内容，而 `在页面上:0`）。所以那句 `import()` 不是第一趟下载的来源。

来源在 HTML 头部。`[条件渲染·谁取的]` 那一行给的是同一个页面收到的两种链接：

- `modulepreload` 28 条，这是"这个页面真要用的模块"，浏览器解析到就取，取完立刻可用。zod 那两个文件就在这一份名单里（`zod在modulepreload里: true`）。
- `prefetch` 3 条：`JwTKxSLW.js`、`B8rDRKbT.js`、`PS3oT_5X.js`。**面板那个文件在这里**，`面板在modulepreload里: false`。

再问一句"那这次请求是谁发起的"，用浏览器自己的网络记账读回来的答案是 `起因:["parser"]`——发起方是 HTML 解析器，不是任何一段脚本。三条 prefetch 就是三行 `<link rel="prefetch" as="script" crossorigin href="/_nuxt/…">`，写在服务端返回的那份 HTML 里。

结论要说得比官方那句更准：**在这套版本（Nuxt 4.5.2 加它自带的打包器）上，一个 `Lazy` 组件只要静态写在模板里，它的文件就进了这一页的 prefetch 名单，跟 `v-if` 的真假无关，也跟它渲不渲出来无关。** 上一站读到的 `组件在预载里: false` 没读错，只是那份名单只看了 `modulepreload` 一种；这一站分开读两种名单，首页那一位同样在 prefetch 里，`组件在prefetch里: true`。两页走的是同一条路。

## 点开之后：同地址的第二次请求，传 0 字节

`v-if` 为假的时候确实什么都没执行。那按下去呢？判据把按之前和按之后各读一次：

- 位次不变：`点前位次:29`、`点后位次:29`。
- 这一位的请求次数从 1 变成 2 —— 注意，这不代表下了两遍。
- 浏览器记账给出两次各传了多少：`[{"字节":672,"发起方":"link"},{"字节":0,"发起方":"script"}]`。

第一次是 HTML 那行 prefetch 链接叫走的，实打实传了 672 字节；第二次是组件真被实例化时 `import()` 自己执行的，浏览器直接用了同一份缓存，传 0 字节。所以**点这一下没让它重传，只是"用上了早就躺在缓存里的东西"**。

这里有个判据设计的教训值得抄下来：一开始这条钉的是"总请求条数不增加"，结果红了——按下去之后页面还在预取别的文件，总条数从 31 涨到 38。要问"这一位取了几次"，就得只数这一位自己的次数，别拿整页的条数当证据。字节数（`transferSize`）比条数更可靠，因为它能区分"又下了一遍"和"命中缓存"。

## 关掉那一档配置，形状一模一样

这条线上一步（799）为了 `nuxt-client` 把 `experimental.componentIslands` 配成了 `{ selectiveClient: true }`。这份提前下载会不会是它逼出来的？把这一档换成布尔 `true`（岛屿照常启用、`nuxt-client` 不认）再跑同一套判据：

```text
[条件渲染·起始] {"档位":"off","面板文件":["C9bsxRcq.js"],"面板位次":13,"第一趟请求条数":20,"在页面上":0,"闸门在":1}
[条件渲染·谁取的] {"档位":"off","面板文件":["C9bsxRcq.js"],"modulepreload条数":12,"prefetch条数":3,"面板在modulepreload里":false,"面板在prefetch里":true,"zod在modulepreload里":true,"起因":["parser"]}
```

位次从 29 变成 13，是因为整页第一趟的条数从 36 降到 20（岛屿那套客户端代码不来了），**不是因为它不再提前下**：`在页面上:0` 照旧，prefetch 名单照旧 3 条照旧含它，发起方照旧是 `parser`。所以这份提前下载与 `selectiveClient` 无关。

## 那 `v-if` 到底挡住了什么

挡住的是两件事，都在"用"这一侧：

1. **渲不渲**。起始为假时它不进 DOM，服务端 HTML 里也没有那一段（`HTML里有那一段: false`）。
2. **跑不跑**。组件还没实例化，它 `<script setup>` 里那次 `parseLoginLink(...)` 自然也没跑到（页面上读不到那一行文本）；按下去之后页面上才出现 `按需面板 LAB_ASYNC_802：Lab.Async@example.com`，域名部分被归一成小写，本地部分保持原样。

没挡住的是**取不取**。代码字节已经在磁盘上躺着了。

这条区分对性能的实际意义：如果你的组件很贵是因为"执行它要花时间"（同步做一大堆计算），`v-if` 完全够用；如果是为了"少下几个字节"，`v-if` 在你把它写进模板那一刻就已经失去这个作用了。至于 prefetch 这一趟排在队列哪里、会不会挤掉要紧的资源，本轮只读到它确实下载了 672 字节，没读它的优先级，这条**未验证**。

## 排错表

| 想确认的东西 | 这一站用的读法 | 为什么这样读 |
| --- | --- | --- |
| 组件是不是单独成文件 | 拿模板里独有的一段文本去扫产物目录 | 文件名随构建变，文本不会 |
| 它算不算"提前下载" | 第一趟 `/_nuxt/` 请求序列里的位次 | 位次说明"什么时候来"，总量不说明 |
| 是谁叫走的 | HTML 里按 `rel` 分开数 `modulepreload` 与 `prefetch`，再读网络记账的发起方 | 只数一种名单会得出"没人叫它"的假结论 |
| 按下去有没有重传 | 同一地址的 `transferSize` 各是多少 | 请求条数会把缓存命中也算成一次下载 |
| 是不是某个配置造成的 | 换一个配置档再跑同一套判据 | 对照组只能是同一套判据，不是另一套猜测 |

## 自己动手跑一遍

```bash
npm run build
npx playwright test test/e2e/async-component-conditional.spec.ts
```

预期 `6 passed`。想看对照档，把这一位换成布尔再跑一次：`$env:NUXT_SELECTIVE_CLIENT="off"`（PowerShell）或者 `NUXT_SELECTIVE_CLIENT=off`（Git Bash），然后同样一条命令，位次会到 13 附近但 `面板在prefetch里` 仍是 `true`。

手点版：开 DevTools 的 Network，勾上 Preserve log，访问 `http://localhost:3100/docs/getting-started?islandLab=async`。在 HTML 里能直接搜到 `<link rel="prefetch" as="script"` 这几行；对应的那个 `.js` 在页面上还没有它的文本时就已经下完了。再点"翻开按需面板"，同地址会再出现一行，Size 那一列是 0 —— 这一行是缓存命中，DevTools 给它的具体字样（`memory cache` 之类）由浏览器决定，本站只认记账里的 `transferSize` 为 0。
