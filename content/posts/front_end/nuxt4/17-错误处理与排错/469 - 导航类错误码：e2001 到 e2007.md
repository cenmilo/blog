用户点了个"跳转到合作伙伴站点"的按钮，浏览器里跳出 `NUXT_E2001`；换个入口拼出来的地址又报 `NUXT_E2002`。

导航这一段的六个错误码各管一件事，其中两条实际上是**安全机制**而不是用法错误。先记一件事：错误码页的编号**不连续，没有 `e2006`**——按号去猜 URL 会打不开。

## 六条对照

| 码 | 官方标题句 | 触发（描述原文要点） | 官方 Resolution |
| --- | --- | --- | --- |
| e2001 | External navigation without `external: true` | `navigateTo()` 收到外部 URL 但没有 `{ external: true }` 选项；Nuxt 要求显式确认，以避免意外把用户带离应用 | `navigateTo('https://example.com', { external: true })` |
| e2002 | Navigation with dangerous protocol | `navigateTo()` 拿到危险协议（`javascript:`、`data:`、`vbscript:`）的 URL，Nuxt 拦下以防 XSS；**"这几乎总意味着未过滤的用户输入到达了 `navigateTo()`"** | 导航前先校验并清洗用户提供的 URL，只允许 `http:`、`https:` 或相对路径 |
| e2003 | `abortNavigation()` called outside middleware | 只能从中间件处理器内部取消导航；从组件、插件、组合式函数，或已丢失中间件上下文的回调里调用会失败 | 把这个调用移进 `defineNuxtRouteMiddleware()` 处理器函数体 |
| e2004 | Unknown route middleware | 引用了某个中间件（通常经 `definePageMeta({ middleware: [...] })`），但不存在这个名字的中间件。常见原因是名字拼错，或中间件文件被改名/删除后引用没更新 | 确保名字能对上 `middleware/` 里的文件；名字由文件名派生——`middleware/auth.ts` 以 `auth` 引用 |
| e2005 | `useRoute` called within middleware | 在路由中间件里（直接或经另一个组合式函数）调了 `useRoute()`；此时目标路由尚未解析完成，`useRoute()` **可能返回不符合预期的值**；中间件是通过参数拿到 `to` 与 `from` 的 | 用 `to` / `from` 代替 `useRoute()` |
| e2007 | `setPageLayout` called on server within component | 在服务端渲染期间从组件的 `setup()` 调了 `setPageLayout()`；服务端必须在组件渲染前决定布局，在这里改会产生**错误的 SSR 输出** | 从路由中间件设置布局，或用 `definePageMeta({ layout: '...' })` 静态声明 |

## 两条是安全防线

e2001 与 e2002 的成因不是"写法不对"，官方给的是**保护机制**。

e2001 那句解释了为什么要显式确认：

> Nuxt requires explicit opt-in for external navigation to avoid accidentally redirecting users away from your app.

**跳出去必须显式加 `external: true`**，这样"把用户带离应用"这个动作不会被一次普通的 `navigateTo` 参数变化误触发。

e2002 更直接：

> `navigateTo()` was given a URL using a dangerous protocol (`javascript:`, `data:`, `vbscript:`). Nuxt blocks these to prevent XSS. This almost always means unsanitized user input reached `navigateTo()`.

三个协议名是官方列出的（`javascript:`、`data:`、`vbscript:`）。第二句是定位用的：**框架拦下它，说明有一条用户输入未经清洗就流到了导航参数里**。所以这一条报错要当成一次安全告警读——修的地方不是这一行调用，而是那个输入。官方的修法也是这么写的：先校验清洗，**只允许 `http:`、`https:` 或相对路径**。

## 三条是位置与时机

e2003、e2005、e2007 和 468 那三条同一类型：报的是"在不能用的地方用了"。

e2003 的边界写在描述里：**只能从中间件处理器内部取消导航**。它的常见触发方式和 E1001 是同一个机制——"a callback that lost the middleware context"（丢了中间件上下文的回调）。

e2005 给了理由，而不只是禁令：

> At that point the target route is not yet resolved, so `useRoute()` can return unexpected values; middleware receives the `to` and `from` routes as arguments instead.

关键词是 **unexpected values**——不是报错，是**拿到不该拿的值**。这也是它比一般用法错误更难发现的原因。官方的修法示例：

```ts
export default defineNuxtRouteMiddleware((to, from) => {
  // use `to` / `from` instead of useRoute()
})
```

e2007 的理由句同样落在 SSR 上：

> On the server the layout must be decided before the component renders, so changing it here produces incorrect SSR output.

两条出路都在文档里：从**路由中间件**设布局，或者用 `definePageMeta({ layout: '...' })` **静态声明**。这一条接得上 378/094 那批布局规则，也接得上 466 讲的"宏的属性要能被静态提取"。

## 一条是名字对不上

e2004 是唯一"配置引用悬空"的那条。官方给的定位顺序很实在：先查拼写，再查**文件是不是被改名或删除而引用没跟着改**。

它还写明了命名规则：**中间件名从文件名派生**，`middleware/auth.ts` 的引用名就是 `auth`。这条对得上 060 那篇的扫描规则（`.global` 后缀与顺序也在那篇）。

## 一处阅读错误码页时的坑

e2004 与 e2005 两节末尾的 read-more 链接写的是 `docs/4.x/guide/directory-structure/middleware`，而 4.x 的中间件参考页在 `directory-structure/app/middleware` 下（本系列 060 那篇依据的就是这一节）。**同一批错误码页里还残留着旧的目录写法**，照着链接找会绕路——按页名搜比按 URL 拼更可靠。

## 自查

- 六条里没有 `e2006`；错误码编号在这段就是不连续的，别按号推 URL。
- e2001 要显式 `external: true`（防意外跳出应用）；e2002 拦三种危险协议，出现它就要往"未过滤的用户输入"上游查。
- e2003 只能在 `defineNuxtRouteMiddleware` 处理器里调 `abortNavigation()`；丢失上下文的回调里调会失败。
- e2005 的本质是"值不符合预期"而不是抛错——中间件里一律用 `to`/`from`。
- e2007 在服务端渲组件前布局就得定下来，所以改布局要放到中间件或 `definePageMeta`。
- e2004 查引用名与文件名是否对得上（名字来自文件名）。
