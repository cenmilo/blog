接口出错了，用户看到什么，这件事有一串决定要做：错误对象怎么造、信息放哪个字段、页面就地提示还是整页错误、错误页能读什么、怎么回到正常状态。

前面十几篇把这些规则一条一条记过了。这一篇把它们串成一条链——**注意：官方没有写过端到端演练，这条链是我按各页原文规则拼起来的**，每一环标出依据，你可以逐环回查。

## 第 1 环：接口里造错误

服务端路由按官方给的形状写：

```ts [server/api/order.post.ts]
export default eventHandler(() => {
  throw createError({
    status: 500,
    statusText: 'Order Failed',
    data: { fields: ['coupon'], hint: '该券已过期' },
  })
})
```

依据与取舍：

- 形状来自 `api/utils/create-error`（官方示例是 `server/api/error.ts` 里 `throw createError({ status: 404, statusText: 'Page Not Found' })`），`status`、`statusText`、`data` 三个键都在它列出的参数集合里。
- **`status: 500` 与 `data` 的组合是我的用法**，官方示例只分别演示过 `status: 500`（配 `message` 与 `cause`）和 `status: 404`（配 `data`）。
- 为什么不写 `message`：官方明写"API 路由里传给 `createError` 的 `message` 不会传播到客户端"，可达的是短 `statusText`，要带东西就用 `data`。
- 还有一条安全句要照做：**别把动态用户输入放进 message**。所以那句中文提示放在 `data.hint`，不放在任何对外字段里拼。

## 第 2 环：页面读到它

`useFetch` 处理这个错误时，自定义数据的位置官方给得很具体——**`error.value.data.data`**：

```vue [app/pages/checkout.vue]
<script setup lang="ts">
const { error, refresh } = useFetch('/api/order.post', { method: 'POST' })

const hint = computed(() => error.value?.data?.data?.hint)
</script>

<template>
  <p v-if="hint" role="alert">{{ hint }}</p>
  <button @click="refresh">重试</button>
</template>
```

两处依据：外层 `error.value.data` 是 h3 错误对象的包装、内层才是你放进 `createError({ data })` 的值（462 记的那条双 `.data`）；`refresh` 是取数返回值里的方法（243 那篇）。

**这一段是组合写法**：官方没给过"从 POST 错误里取 hint"的示例，但每个零件都有出处。`role="alert"` 是我按可访问性常识加的，4.x 文档没在错误处理语境里写过它。

## 第 3 环：就地提示，还是整页错误

这两个效果由**抛法**决定，官方那句不对称的规则是判据（462）：

| 你要的效果 | 官方给的做法 |
| --- | --- |
| 只在这一块内容里提示，页面其余照常 | `<NuxtErrorBoundary>` 的 `#error` 插槽（095）；插槽收到 `error`，把 `error` 设为 `null` 会重渲染默认插槽，官方提醒要先确认错误真的解决了；换个路由会自动清掉 |
| 客户端抛出但不想全屏 | 直接 `throw createError({...})`——**客户端默认是非致命的**，等你处理 |
| 客户端也要全屏错误页 | 显式 `fatal: true`（官方原话） |
| 服务端渲染时进错误页 | 服务端任何未处理错误就是 fatal（460 那句定义）；请求头是 `Accept: application/json` 时改成返回 JSON |

`statusText` 只放 HTTP 合规的短文本（官方那句：只该含水平制表符、空格与可见 ASCII），中文说明放 `data`——这也是第 1 环那个安排的依据。

## 第 4 环：错误页只读那一个 prop

要自定义那一页，就得建 `error.vue`，位置在应用源码目录、与 `app.vue` 同级（464）。它的硬约束三条：不是路由所以不进 `pages/`、不用 `definePageMeta`；只有 `error` 这一个 prop；自定义字段必须走 `data`（否则丢失）。

```vue [error.vue]
<script setup lang="ts">
import type { NuxtError } from '#app'

const props = defineProps({
  error: Object as () => NuxtError,
})

const handleError = () => clearError({ redirect: '/' })
</script>

<template>
  <div>
    <h2>{{ props.error?.status }}</h2>
    <button @click="handleError">
      Clear errors
    </button>
  </div>
</template>
```

这段是官方示例原样（props 断言写法、`error?.status`、`clearError({ redirect: '/' })`）。两处要留意：

**读状态用 `status`**，`statusCode` 是官方标注的 legacy 等价物（464）。

**这里显示的是 `status`，不是那句中文提示**——467 记过：服务端渲染错误页时 `error.data` 会不会被解析，由默认开启的 `experimental.parseErrorData` 管，而官方只给了一句定性，关掉后的形态没写。想让错误页稳定显示业务提示，别把宝押在这一项上；最稳的是让提示在第 2 环那一层（页面内）就出。

## 第 5 环：清掉与上报

`clearError()` 三件事（463）：重置 `useError()` 那份状态、带着 options 调 `app:error:cleared`、让抛过错的插件得以重跑。

上报要接成对的两个钩子：`showError` 调的是 `app:error`，`clearError` 调的是 `app:error:cleared`；Vue 侧还有 `vue:error`（冒泡到顶层才叫）和 `vueApp.config.errorHandler`（**连已被处理的错误也会进来**）——想全量上报就用后者（460）。

两个坑再提醒一次（461、463）：错误页是**一次独立加载，所有中间件会再跑一遍**，所以中间件里先用 `useError()` 判断；插件如果正是抛错源头，**在你清掉错误之前它不会重跑**，`$router`/`$route` 之类的东西用之前要确认。

## 走完这条链的验收清单

1. 接口返回体里能不能看到那个 `data`？看得到才谈得上客户端读它。
2. 页面里 `error.value.data.data` 取到的是不是你放的那个对象（别漏一层）。
3. 客户端抛出的错误有没有默认变成全屏页？按官方规则不该有——要全屏必须 `fatal: true`。
4. `error.vue` 里的字段读法对不对（`status` 而不是 `statusCode`）；自定义字段有没有塞进 `data`。
5. 点"清除错误"后有没有真的回到正常页（`redirect` 生效）、中间件有没有被这一趟二次加载带偏。
6. 上报有没有同时覆盖 `app:error`、`app:error:cleared` 与 Vue 侧那一个。

## 自查

- 五个环的顺序是：造错误（短 `statusText`＋`data`）→ 客户端读（`error.value.data.data`）→ 选呈现（就地／`fatal: true`）→ 错误页只读 `error` → `clearError` 收尾并接两个钩子。
- 全链里只有第 4 环那段代码是官方示例原样，其余是零件组合，已在正文逐处标明。
- 业务提示放 `data`、别放 `message`；错误页显示 `status`；这两条最容易被写反。
- 官方没写过这条链，所以任何一环出问题时，回到对应那一页原文核对，而不是照本文推。
