错误处理这一分区读下来，最难的是记住二十几条规则各自在哪一层生效。本篇把它们排成一张可以在上线前逐条打勾的表。

用法上先说清：**每条"判据"都能在对应编号那篇里找到官方原句**，本篇不新增任何规则；凡是自行排列的次序都标了出来。

## 一、呈现层

| 检查项 | 判据 | 依据 |
| --- | --- | --- |
| 有没有自己的错误页 | `error.vue` 建在应用源码目录、与 `app.vue` 同级，用来覆盖默认错误页 | 464 |
| 它没被当路由用 | 不进 `pages/`、里面不写 `definePageMeta`；要带布局就 `<NuxtLayout name>` | 464、465 |
| 静态站的 404 页不是空壳 | 两种 fallback **默认是空壳**；要把 `error.vue` 服务端渲成 `404.html` 得设 `experimental.prerenderErrorPages` | 465 |
| 知道什么情况出全屏页 | 服务端任何未处理错误，或客户端 `fatal: true`；请求带 `Accept: application/json` 时改出 JSON | 460、462 |
| `statusText` 没塞长文本 | 官方限定它只含水平制表符、空格与可见 ASCII；详细说明用 `message` | 462 |
| cv5 的差异知道 | 设了 `compatibilityVersion: 5`：页面错误必出错误页，服务端路由/中间件错误返回 JSON | 460、466 |

## 二、数据层

| 检查项 | 判据 | 依据 |
| --- | --- | --- |
| 接口错误带结构化信息 | 只能放 `data`；**API 路由里的 `message` 不传播到客户端** | 462、467 |
| 客户端取对了层级 | `useFetch` 处理错误时自定义数据在 **`error.value.data.data`** | 462 |
| 错误页的 `data` 能解析 | `experimental.parseErrorData` **默认开**；官方对关闭后的形态没有任何记载，别把它当可靠依赖 | 467 |
| 没把用户输入放进错误文案 | 官方原话是避免潜在安全问题 | 462 |
| 复杂类型没进 `data` | devalue 那条只写在载荷侧，错误数据序列化文档未记载；保守做法是只用可 JSON 化的形状 | 467 |

## 三、接手点

| 检查项 | 判据 | 依据 |
| --- | --- | --- |
| Vue 侧错误有一层收口 | `onErrorCaptured`（组件）、`vue:error`（冒泡到顶层才叫）、`vueApp.config.errorHandler`（**连已处理的也收**） | 460、468 |
| 启动阶段有兜 | `app:error` 覆盖插件、`app:created`/`app:beforeMount`、SSR 渲 HTML、挂载、`app:mounted` 五项，**挂载那项官方建议改走 Vue 侧** | 460 |
| 局部失败不整页崩 | `<NuxtErrorBoundary>` 的 `#error` 插槽；把 `error` 设 `null` 会重渲染默认插槽，要先确认问题真解决 | 460、477 |
| Nitro 服务端生命周期错误 | **官方明写目前不能定义服务端处理器**，只能落到错误页——别去找这个钩子 | 460 |

## 四、恢复路径

| 检查项 | 判据 | 依据 |
| --- | --- | --- |
| 用户能自己走出来 | `clearError()` 清状态；`{ redirect: '/safe' }` 跳安全页；返回 `Promise<void>` | 463 |
| 中间件不会被错误页带偏 | 错误页是独立一次加载，**所有中间件再跑一遍**；中间件里先用 `useError()` 判断 | 461、463、465 |
| 插件产物用前确认 | 插件若是抛错源头，在你清掉错误之前不会重跑，`$router`/`$route` 可能不可用 | 463、465 |
| 上报接成对 | `showError`→`app:error`，`clearError`→`app:error:cleared`（**钩子表里这条的说明句抄了上一行，与函数页矛盾**） | 462、463 |

## 五、chunk 与部署

| 检查项 | 判据 | 依据 |
| --- | --- | --- |
| chunk 失败有处理 | 默认内置硬重载；`experimental.emitRouteChunkError` 可 `false`/`manual` | 460、439 |
| 想过新版本部署 | 官方点名的成因之一就是**新部署使旧 hash chunk 地址失效** | 460、436 |
| 切得细等于取的机会多 | 岛屿、全局组件、`Lazy` 前缀都增加 chunk 数量；`Lazy` 不配条件渲染仍急加载 | 439、444 |
| 流式下的错误两种路径 | 壳前出错走缓冲错误渲染并带正确状态码；壳后出错靠 `payload.error` 由客户端渲错误页 | 450 |

## 六、与性能的交叉

这一组是我按"上线后最容易静默坏"排的次序（**官方没有这种排序**）：

| 检查项 | 判据 | 依据 |
| --- | --- | --- |
| 插件数量与初始化开销 | 插件在水合阶段运行，低效写法阻塞渲染 | 435、456 |
| `noScripts` 用在对的路由上 | 页面外观不变但**没有任何东西可交互**；`nuxt-client` 与岛屿在其中不会激活 | 456、472 |
| dev 与生产是否一致 | `features.noScripts` 默认 `'production'`，依赖客户端 JS 的行为在 dev 正常、部署后静默坏（e8007 是这条的开发期警告） | 472 |
| 客户端只在浏览器渲染的那块 | `ClientOnly` 默认插槽 tree-shake 出服务端构建，里面 CSS 可能不内联；防位移用 `#fallback` | 455 |

## 七、配置类错误码先自清

| 检查项 | 判据 | 依据 |
| --- | --- | --- |
| `compatibilityDate` 有没有 | 不写会"悄悄采纳新默认"；Resolution 用当天日期＝接受当前默认 | 471 |
| `runtimeConfig.app` 干净 | 自定义键改到 `public`（客户端）或顶层（仅服务端） | 471 |
| 根目录没有独立配置文件 | `vite.config`/`webpack.config`/`nitro.config`/`postcss.config` 会被**忽略**，先搬进对应键再删 | 471 |
| 需要转译的依赖已登记 | ESM 语法错、E1006 都指回 `build.transpile`；别忘了间接依赖 | 438、468 |
| 宏没写错位置 | `definePageMeta` 不能在组合式函数、条件分支、非页面组件里 | 468 |

## 八、观测与报障

| 检查项 | 判据 | 依据 |
| --- | --- | --- |
| 日志级别不是白设的 | `logLevel` 在 CI 或无 TTY 时默认按 silent；Vite 侧译成 `silent`、webpack 侧 `none` | 478 |
| 看错误有快捷路径 | dev 面板 `e` 跳最后一条错误、`l` 翻历史；attach 调试器会退化成纯日志流 | 478、475 |
| 模块日志走 Kit | `useLogger(tag, { level })`（底层 consola），需要提问用 `useTerminal()`；`interactive` 为 `false` 时退化成日志 | 478 |
| 报障材料齐了 | 先分清求助还是 bug → 搜 open issues/discussions 并回原帖 → 最小复现（sandbox 起步，涉及 Vue/Vite 先用 Vue SSR starter）→ 判责任层 | 476 |
| 版本信息一条命令 | `nuxt info` 给解析到的 Nuxt/Nitro/Vite、包管理器、加载的模块与 build modules；脚本读用 `--json` | 476 |

## 自查

- 顺序建议照这张表走，但**判断标准只有一条**：每条检查项都要能背出它的判据出自哪一篇。
- 最容易静默坏的四项：`noScripts` 与交互、`features.noScripts` 的 dev/生产分岔、错误页上中间件二次执行、chunk 地址在部署后失效。
- 三处"官方没写所以不能当依据"的地方：错误页可用 API 清单、`parseErrorData` 关闭后的形态、`app:error:cleared` 在钩子表里的说明。
