错误页要显示"回到搜索"的按钮，你想拿当前路由的 query 拼一个返回链接，于是在 `error.vue` 里写 `useRoute()`——它到底能不能用？

先把结论摆明：**官方没有这份清单**。这一篇按"证据强度"分三层，把能确定、要小心、以及只能自己试的分开列。

## 第一层：官方示例里出现过，因此可用

这些不是推测，是官方自己写的代码里出现过的东西。

| 可用的 | 官方出处 |
| --- | --- |
| `defineProps` 接 `error`，类型从 `#app` 导入 `NuxtError` | `error.vue` 页与错误处理页的两段示例 |
| `<NuxtLink to="/">` | 两节示例都用它做"回首页" |
| `clearError({ redirect: '/' })` | 错误处理页示例里 `handleError` 就是它 |
| `<NuxtLayout name="...">` | `NuxtLayout` 那一节专门给了一段 `[error.vue]` 示例 |

`NuxtLayout` 那条还带两个配套细节。官方定性句写的是"show layouts on **pages and error pages**"，并说"你可以用 `<NuxtLayout />` 在 `app.vue` **或 `error.vue`** 上启用 `default` 布局"。它给错误页的示例是：

```vue [error.vue]
<template>
  <NuxtLayout name="error-layout">
    <NuxtPage />
  </NuxtLayout>
</template>
```

两个要注意的地方：

**布局名会被归一成 kebab-case**。官方 `::note` 举例：文件叫 `errorLayout.vue`，传给 `name` 时就要写 `error-layout`。

**这段示例里出现了 `<NuxtPage />`**，而 464 记过"`error.vue` 不是路由、不该用 `definePageMeta`"。**这两处放一起看是别扭的，但官方页面没做任何解释**（文档未说明）。要照抄之前，先确认你的错误页是否真的需要页面出口——多数情况只需要 `error` prop 和静态内容。

## 第二层：明文写着要小心的三件

**一、依赖插件的东西不能假定可用。** 那条 `::important`：

> Make sure to check before using anything dependent on Nuxt plugins, such as `$route` or `useRouter`, as if a plugin threw an error, then it won't be re-run until you clear the error.

注意它给的因果：**插件如果正是那个抛错的源头，它在错误被清掉之前不会重跑**，于是它 `provide` 的一切（包括 `$router`/`$route` 这类）都可能是空的。463 记的 `clearError` 就是解开这件事的钥匙。

**二、中间件一定会再跑一遍。** 这一条两节都有话，错误处理那一节是：

> Rendering an error page is an entirely separate page load, meaning any registered middleware will run again. You can use `useError` in middleware to check if an error is being handled.

中间件那一节说得更狠：

> This is true even if you throw an error in your middleware on the server, and an error page is rendered. The middleware will still run again in the browser.

也就是说，**服务端中间件抛错 → 渲染错误页 → 浏览器端同一个中间件还会再执行一次**。如果那个中间件里写着"未登录就跳走"，用户会先从错误页被带走。判据就是官方点名那句：在中间件里调 `useError()`，有值说明正在处理错误。

**三、在错误页里写 cookie 有平台特例。** 一条 `::note`：

> If you are running on Node 16 and you set any cookies when rendering your error page, they will overwrite cookies previously set. We recommend using a newer version of Node as Node 16 reached end-of-life in September 2023.

**Node 16 且设了 cookie 时，先前设置的会被覆盖**；官方同时建议升级，因为 Node 16 已在 2023 年 9 月终止支持。

## 第三层：官方没写、只能自己试的

`error.vue` 里能不能用 `useRoute()`、`useHead()`/`useSeoMeta()`、`useState()`、`useFetch()`、以及你自己写的组合式函数——**这五项在 4.x 文档中没有任何一处给出可用或不可用的判断**（文档未记载）。

能给的不是答案，是**三分钟自测法**：

1. 在 `error.vue` 里加一行调用，比如 `const r = useRoute()`，并在模板里渲染 `r.path`。
2. 触发一次真实错误：最省事的是临时加一条路由中间件，按官方示例抛出去——

```ts [app/middleware/error.ts]
export default defineNuxtRouteMiddleware((to) => {
  if (to.params.id === '1') {
    throw createError({ status: 404, statusText: 'Page Not Found' })
  }
})
```

官方对这段的效果说明是："The above route middleware will **redirect a user to the custom error page defined in the `~/error.vue` file**, and expose the error message and code passed from the middleware."——**中间件抛错、错误页收到 message 与 code**，这是文档里记载得最完整的一条通路。

3. 分别看**开发模式与构建产物**两种情况：错误页有服务端渲染的一面也有客户端再加载的一面（上面第二条警告就是因为它），只验一种会得出片面结论。

顺带记一条与这一层相关的部署事实：官方在部署那一节写着，两种 fallback 默认是**空壳**，把 `experimental.prerenderErrorPages` 设上才会把 `error.vue` 服务端渲染成 `404.html`。也就是说**构建期产出的那份错误页里没有运行时数据**——这条正好影响你在错误页里塞动态内容的可行性。

## 自查

- 官方没有"错误页可用 API"清单；能确定的只有示例里出现过的四样（props、`<NuxtLink>`、`clearError`、`<NuxtLayout name>`）。
- 布局名要写 kebab-case 形式；官方那段错误页示例里的 `<NuxtPage />` 与"不是路由"两处并存且无解释。
- 三条警告：插件产物可能没就绪（清掉错误才重跑）、中间件必再跑一遍（用 `useError` 判断）、Node 16 下错误页设 cookie 会覆盖。
- 其余组合式函数只能自测，且要开发模式与构建产物各验一次。
- 记载最完整的进入路径是中间件 `throw createError({ status, statusText })`。

## 下一篇

下一篇 466 讲两条产生 404 的路，它们不是同一件事：`definePageMeta` 里的 `validate` 返回 `false` 会让这条路由变成 404，还能直接返回带 `status`/`statusText` 的对象来自定义错误；而 `experimental.early404` 处理的是**路径压根匹配不到任何页面路由**的请求，它在建好静态路由匹配器后提前返回 404，不加载 Vue 应用、插件与中间件。
