线上一个报错，堆栈里全是 `index.js:1:238417`。你想 debugger 单步，容器里连不上。这两件事在官方调试那一节里各有一节，但**那一节没告诉你先做哪一步**。

这一篇把这一节能给的东西全部拿走，再说明它为什么给不出一套流程。

## 这一节只有四节

| 节 | 内容 | 能拿走什么 |
| --- | --- | --- |
| Sourcemaps | 默认状态与更细的配置写法 | 服务端默认开、客户端仅 dev 默认开 |
| Debugging with Node Inspector | `nuxt dev --inspect` 与一条平台限制 | Docker 里这条路不通 |
| Debugging in Your IDE | VS Code 与 JetBrains 两份完整配置 | 三个调试目标的名字与结构 |
| Other IDEs | 一句"欢迎开 PR 贡献示例配置" | 官方只覆盖上面两种 |

## 第一件：source map 的默认值不对称

官方原话：

> Sourcemaps are enabled for your server build by default, and for the client build in dev mode, but you can enable them more specifically in your configuration.

这句话解释了两个常见现象：**服务端报错一般能映射回源码**，而**客户端构建产物（生产）默认没有 map**——需要时才显式开：

```ts
export default defineNuxtConfig({
  // or sourcemap: true
  sourcemap: {
    server: true,
    client: true,
  },
})
```

两个键分开设，是因为**给不给浏览器读源码是一个发布决定**，而不是调试决定。`sourcemap: true` 是那个"或"的写法，官方注释就一行。

083 那篇把 `debug`、`logLevel`、`sourcemap`、`inspector` 四个开关列成配置清单，本篇不重复那份表；这里只取这一节实际写明的部分。

## 第二件：Node inspector 与那条容器限制

官方给的命令只有一行：

```bash
nuxt dev --inspect
```

行为描述两句：

> This will start Nuxt in `dev` mode with debugger active. If everything is working correctly a Node.js icon will appear on your Chrome DevTools and you can attach to the debugger.

判据写得很具体：**正常时 Chrome DevTools 里会出现 Node.js 图标**，从那儿 attach。图标没出现，就别往下走——先确认端口和 Chrome 是否看得见那个进程。

然后是这一节唯一一条 `::important`：

> Note that the Node.js and Chrome processes need to be run on the same platform. This doesn't work inside of Docker.

**两个进程必须同平台，Docker 里不成立。** 这一条能解释一种很费时间的现象：本地按文档操作能连上，同事在容器化开发环境里做同样的事就连不上——**不是配置错了，是这条路本身不通**。

`api/commands/dev` 那一节把这条链的细节写得更全（默认地址端口、attach 目标、CLI 进程与 Nuxt 进程分在两个端口），475 那篇专门讲这部分。

## 第三件：IDE 配置的两份样例

官方态度一句：

> It is possible to debug your Nuxt app in your IDE while you are developing it.

### VS Code

开头有个提醒要照做：**"你可能需要用自己浏览器的路径更新下面这份配置"**。

```json5
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "chrome",
      "request": "launch",
      "name": "client: chrome",
      "url": "http://localhost:3000",
      // this should point to your Nuxt `srcDir`, which is `app` by default
      "webRoot": "${workspaceFolder}/app"
    },
    {
      "type": "node",
      "request": "launch",
      "name": "server: nuxt",
      "outputCapture": "std",
      "program": "${workspaceFolder}/node_modules/nuxt/bin/nuxt.mjs",
      "args": [
        "dev"
      ],
    }
  ],
  "compounds": [
    {
      "name": "fullstack: nuxt",
      "configurations": ["server: nuxt", "client: chrome"]
    }
  ]
}
```

这份配置的形状值得单独看：**三个调试目标**——`client: chrome`（浏览器那一侧）、`server: nuxt`（用 Node 启动 `nuxt dev`）、`fullstack: nuxt`（compound，把前两个一起起）。第三项是关键：**一次启动就同时能断服务端与客户端**，这正对应 Nuxt 是两端框架这个事实。

两处细节：`webRoot` 那条注释写明**它应当指向你的 `srcDir`，默认是 `app`**（079 那篇的基准关系在这里落地——改过 `srcDir` 就要跟着改）；`program` 指的是包里的 `nuxt/bin/nuxt.mjs`、`args` 传 `dev`。

想用你日常那个浏览器的扩展，官方给的加行是：

```json5
"userDataDir": false,
```

### JetBrains

官方给的是两步操作：**在项目根新建文件 `nuxt.run.xml`**，然后把这份配置粘进去：

```html
<component name="ProjectRunConfigurationManager">
  <configuration default="false" name="client: chrome" type="JavascriptDebugType" uri="http://localhost:3000" useFirstLineBreakpoints="true">
    <method v="2" />
  </configuration>

  <configuration default="false" name="server: nuxt" type="NodeJSConfigurationType" application-parameters="dev" path-to-js-file="$PROJECT_DIR$/node_modules/nuxt/bin/nuxt.mjs" working-dir="$PROJECT_DIR$">
    <method v="2" />
  </configuration>

  <configuration default="false" name="fullstack: nuxt" type="CompoundRunConfigurationType">
    <toRun name="client: chrome" type="JavascriptDebugType" />
    <toRun name="server: nuxt" type="NodeJSConfigurationType" />
    <method v="2" />
  </configuration>
</component>
```

覆盖的 IDE 官方点了三个名字：**IntelliJ IDEA、WebStorm、PhpStorm**。结构与 VS Code 那份一致（同样是三个目标，`type` 分别是 `JavascriptDebugType`、`NodeJSConfigurationType`、`CompoundRunConfigurationType`，服务端那条的 `application-parameters` 是 `dev`）。

## 文档没给的那部分：顺序

这一节没有任何"先查什么"的流程。所以下面这份起手式**是把这一节与相邻几节写明的能力拼出来的**，官方没这样写过：

1. **先分清是哪一侧**：报错来自服务端渲染/接口，还是浏览器里的交互。这一分决定后面用哪个目标（`server: nuxt` 或 `client: chrome`）。
2. **确认能不能映射回源码**：客户端生产包的堆栈没 map 就是默认状态（第一节那句），需要就先开 `sourcemap.client`。
3. **在能用的地方用 compound 起**：IDE 里选 `fullstack: nuxt`，两端一起。
4. **容器环境**：`--inspect` 这条路直接不通（那条 `::important`），改走日志与 `nuxt info`（476 那篇）。
5. **怀疑是框架行为而不是自己代码**：先按错误码查（468-473 那四篇），查不到再去报障（476）。

## 自查

- 这一节给的是三件配置类事实加一份平台限制，**没有排错流程**。
- source map 默认状态两端不对称：服务端开，客户端只在 dev 开；生产要显式开，这是个发布决定。
- `nuxt dev --inspect` 的可用判据是 Chrome DevTools 上出现 Node.js 图标；Node 与 Chrome 须同平台，Docker 不行。
- 官方 IDE 样例只有 VS Code 与 JetBrains 两份，都是三个目标、含一个 compound；VS Code 的 `webRoot` 要跟着 `srcDir` 改。
- 起手式那五步是我的组合，不是官方配方。

## 下一篇

下一篇 475 把双端调试的机制说清：`--inspect` 开的是**服务端代码的 inspector**（服务端路由、中间件、SSR 都跑在 Nitro 的 worker 线程里，默认 `127.0.0.1:9229`，重载后调试器会自动重连）；而 `nuxt.config`、模块与构建钩子跑在 **CLI 进程**里，它有自己的 inspector、默认在下一个端口 9230，要手动加为 attach 目标。
