升级完 Nuxt，某个默认行为变了；或者你在项目根放了 `vite.config.ts`，里面写的插件一条都没生效。

这两个现象各有对应的错误码，都在 `b5xxx` 这一组。它们的共同点是：**修的地方是配置文件，不是代码**。

## 三条一览

| 码 | 官方标题句 | 触发 | 官方 Resolution |
| --- | --- | --- | --- |
| b5001 | Missing compatibilityDate | `nuxt.config` 里没有 `compatibilityDate` | 加上它，用**当天的日期**，表示选择当前默认 |
| b5003 | Reserved runtimeConfig.app namespace | 在 `runtimeConfig.app` 下放了自己的键 | 移到 `runtimeConfig.public`（客户端可见）或顶层自定义命名空间（仅服务端） |
| b5004 | External config file not supported | `nuxt.config` 旁边有独立的 `vite.config` 或 `webpack.config` | 把配置搬进 `nuxt.config` 的对应键，然后删掉外部文件 |

## b5001：这个日期决定的是"默认值集合"

官方描述句里有两个关键信息：

> No `compatibilityDate` is set in your Nuxt configuration. Nuxt uses this date to decide which behaviour defaults to apply, so your project stays stable across Nuxt and Nitro updates instead of silently picking up new defaults.

**它决定的是应用哪一组行为默认值**，作用范围同时覆盖 **Nuxt 与 Nitro 的更新**；不写的后果官方用词是 "silently picking up new defaults"——**悄悄换成新默认**。

Resolution 那段给了写法和一个明确要求：

```ts
export default defineNuxtConfig({
  // use the current date, e.g. the day you add this line
  compatibilityDate: 'YYYY-MM-DD',
})
```

注释那句"用当天的日期，也就是你加这一行的那天"，官方解释的意图是"这样你就选入了当前的默认"。这层意思要读对：**填今天不是在向后兼容，而是承认并接受现在这套默认行为**；填一个过去的日期，才是要求框架保持旧行为。018 那篇（第一份 nuxt.config）与升级页都按这个口径讲。

## b5003：app 是保留命名空间

描述句把"为什么不能放"讲清了：

> You have custom keys under `runtimeConfig.app`, a namespace Nuxt reserves for internal values (such as `baseURL` and `cdnURL`). Custom keys here can collide with Nuxt's own config.

`app` 下面实际住着什么，配置页那份默认值就是证据——`runtimeConfig` 的默认结构里 `app` 有四个内部值：`buildId`、`baseURL`、`buildAssetsDir`、`cdnURL`（`public` 默认是空对象）。**这四个都是框架自己在用的**。

两条去处官方写得很具体，且各自带一个可见性说明：

> Move custom keys to `runtimeConfig.public` (exposed to the client) or to a top-level custom namespace (server-only):

```ts
export default defineNuxtConfig({
  runtimeConfig: {
    // instead of runtimeConfig.app.myKey
    public: {
      myKey: 'value',
    },
  },
})
```

也就是：**要客户端能读，放 `public`；只想留在服务端，放顶层自定义键**。这两档的区别和 `.env` 的覆盖规则（341 那篇那条 `NUXT_` 前缀链）是连在一起的。

## b5004：这些文件会被忽略，不是被合并

描述句有两个判断：

> Nuxt found a standalone `vite.config` or `webpack.config` file next to your `nuxt.config`. Nuxt manages the bundler internally and ignores these files, so they are usually leftovers from a migration or a copied non-Nuxt project.

**Nuxt 内部管理打包器、并且忽略这些文件**——"配置写了不生效"就是因为它们根本没被读。官方的归因也很实在：这类文件通常是**迁移残留**或**从非 Nuxt 项目复制过来**的。

Resolution 给了一个顺序和四张映射：

> Move the configuration into `nuxt.config` under the matching key, then delete the external file:

- `vite.config`：用 `vite` 键
- `webpack.config`：用 `webpack` 键
- `nitro.config`：用 `nitro` 键
- `postcss.config`：用 `postcss` 键

搬进来之后的形状官方也给了示例：

```ts
export default defineNuxtConfig({
  vite: {
    // your Vite config here
  },
})
```

这个清单正是本系列反复用的那条红线的官方出处：**`nitro.config`、`vite.config`、`postcss.config`、`webpack.config` 这四类独立文件在 4.x 不再被读取**，配置必须写进 `nuxt.config` 的同名节。

两点落地提醒：

第一，**顺序不能倒**——官方写的是"先搬进对应键，再删外部文件"。直接删会丢掉里面还没迁的配置。

第二，`vite` 节搬进来不等于原样支持：429 那篇记过官方那句限定"not all vite options are supported in Nuxt"，跨构建器的插件要用 Kit 的 `addBuildPlugin`。

## 修完之后：配置需要重启

这三条的修复都动的是 `nuxt.config`。072 那篇记过：主配置文件、`.env`、`.nuxtrc`、`.nuxtignore` 这四个文件变化会触发**完全重启**，而 dev 的重启会列出实际不同的键。**改完看不到效果，先确认进程真的重启过**，再去怀疑配置本身。

## 自查

- b5001：`compatibilityDate` 决定默认行为集合（覆盖 Nuxt 与 Nitro 更新），填当天日期表示接受当前默认；不写会悄悄跟上新默认。
- b5003：`runtimeConfig.app` 是保留命名空间，里面住着 `buildId`、`baseURL`、`buildAssetsDir`、`cdnURL`；自定义键去 `public`（客户端可见）或顶层（仅服务端）。
- b5004：独立配置文件是被**忽略**而非合并；四类文件各有对应键（vite/webpack/nitro/postcss），先搬再删。
- 搬进 `vite` 节要记得并非所有 Vite 选项都被支持。
- 三条都改 `nuxt.config`，验证前先确认框架真的重启了。
