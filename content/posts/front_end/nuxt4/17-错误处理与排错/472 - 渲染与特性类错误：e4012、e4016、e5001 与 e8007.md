有一条错误只在生产出现、有一条只在子路由上出现、还有一条只在开了 noScripts 之后出现。

这四条（`e4012`、`e4016`、`e5001`、`e8007`）都不是配置写错，而是**某个能力要用的前提没到位**。逐条看。

## 四条一览

| 码 | 官方标题句 | 前提缺在哪 | 官方 Resolution |
| --- | --- | --- | --- |
| e4012 | Failed to parse island response | 服务端组件端点返回的不是预期的 island payload（例如错误页或畸形 HTML） | 检查服务端组件里有没有阻止它渲染的错误，并**查看那条 island 请求的实际响应** |
| e4016 | 父页面没渲染 `<NuxtPage />`，嵌套页面显示不出来 | 父页面组件里没有页面出口 | 给父页面加 `<NuxtPage />`；如果你并不想要嵌套路由，就改 `pages/` 结构让它没有子路由 |
| e5001 | App manifest is not enabled | 代码依赖 app manifest，但 `experimental.appManifest` 关着 | 在 `nuxt.config` 里把 `appManifest` 设为 `true` |
| e8007 | 路由依赖客户端 JS，但 noScripts 会在生产把脚本剥掉 | `features.noScripts` 默认 `'production'`，dev 与生产行为不同 | 去掉该路由上的客户端依赖，或把剥脚本限定在真正静态的路由（用 `noScripts` 路由规则），或设 `features.noScripts: 'all'` 让 dev 复现生产 |

## e4012：岛屿拿回来的不是岛屿

描述句给了两种实际返回：

> Nuxt could not parse the response returned when rendering a server component (island). This usually means the server component endpoint returned something other than the expected island payload, such as an error page or malformed HTML.

**"错误页"或"畸形 HTML"**——注意第一个：如果那个服务端组件的请求被某个中间层改写成错误页（鉴权失败、路由规则改动），你看到的就是解析失败而不是 500。

官方的排查动作也写得很具体，两句：

> Check the server component for errors that would prevent it from rendering, and confirm the island endpoint returns a valid response. Inspect the network response for the island request to see what the server actually returned.

最后一句是可直接执行的一步：**在网络面板里找到那条 island 请求，看服务端到底返回了什么**。这一条错误码页把排查起点定在这里，而不是让你去改配置。

## e4016：出口没打开，子页面无处渲染

描述句解释了机制：

> The current route matches a nested page, but the parent page component does not render `<NuxtPage />`. Vue Router can only display a child page inside its parent's `<NuxtPage />` outlet, so the child page is never shown.

**Vue Router 只能把子页面显示在父页面那个 `<NuxtPage />` 出口里**，没有出口就永远不显示。

官方还给了触发它的具体目录形状：

```bash [Directory Structure]
-| pages/
---| parent/
------| child.vue
---| parent.vue
```

并写明条件："when `parent.vue` does not contain `<NuxtPage />`"。

Resolution 有两条方向相反的路：

> Add `<NuxtPage />` to the parent page component so the child route can render inside it. If you did not intend to create a nested route, restructure your `pages/` directory so the page no longer has child routes.

**要么承认嵌套、补出口；要么承认不想要嵌套、把目录改成不产生子路由的形状**。第二条很容易被忽略——很多人是**不小心**造出了 `parent/` 加 `parent.vue` 这种组合（057 那篇的命名约定里这正是嵌套路由的来源）。

## e5001：manifest 是两项能力的前提

描述句把"为什么必须开"写成了能力清单：

> Code that relies on the app manifest ran while `experimental.appManifest` is disabled. The manifest powers features such as route rules matching and prerendered-payload detection on the client, so it must be enabled for them to work.

**manifest 支撑的两项：路由规则匹配、客户端的预渲染载荷探测**。修法只有一句配置：

```ts
export default defineNuxtConfig({
  experimental: {
    appManifest: true,
  },
})
```

这一项还牵着别处的一条规则：440 记过 `checkOutdatedBuildInterval`（检查新构建的时间间隔）在 `experimental.appManifest` 为 `false` 时是**禁用**的。也就是说，"客户端不知道自己落后于新版本"这一类线上表现，可能和这一项关着是同一个根因——两个错误码/开关指向同一个前提。

## e8007：dev 与生产分岔的那条警告

这一条的性质不同，官方明确它是**开发期发出的警告**：

> This warning is emitted during development when a rendered route uses one of these features.

成因段写明了默认值与分岔：

> With `features.noScripts: 'production'` (the default when `noScripts` is enabled), scripts are only stripped from rendered HTML in production builds. In development the page still ships JavaScript, so behaviour that depends on it (lazy hydration strategies, `nuxt-client` components inside server components) appears to work in dev and then silently breaks after deployment.

三点：`features.noScripts` 在启用 noScripts 时**默认是 `'production'`**、脚本只从**生产构建**的渲染 HTML 里剥掉、开发模式仍然发 JS。后果官方用了 **silently breaks**（静默坏掉）。

被点名会坏的两类能力：**延迟水合策略**，以及**服务端组件里的 `nuxt-client` 组件**——450 也解释过原因：这两类都靠一段内联脚本来搬移或激活，脚本没了它们就不生效。

Resolution 给了三条路，重点在"让问题在 dev 就可见"：

> Either remove the client-side dependency from the affected route, or scope script stripping to the routes that are genuinely static using the `noScripts` route rule (which applies in development too, so any breakage is visible immediately):

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  routeRules: {
    '/static/**': { noScripts: true },
  },
})
```

最后一条替代方案："Alternatively, set `features.noScripts: 'all'` to strip scripts in development as well, making the production behaviour observable in dev."

三条的取舍很清楚：**去掉依赖**（最稳）、**改用路由规则按路径限定**（官方点明它在 dev 也生效，所以坏会当场暴露）、**或全局设 `'all'`**（把 dev 拉成和生产一样，用于验证）。

## 四条合起来读

这四页放在一起能看出一条共同结构（**这是我把四条并排读出的规律，官方没这样归纳**）：报错的位置不是问题所在，**缺前提的那个能力才是**。e4012 要查请求、e4016 要查目录形状、e5001 要查开关、e8007 要查环境与生产的差异。

## 自查

- e4012 先看那条 island 请求实际返回了什么（错误页或畸形 HTML 都会导致解析失败）。
- e4016 的出路有两条且相反：补 `<NuxtPage />`，或改掉 `pages/` 结构使父页面没有子路由。
- e5001 说明 manifest 是"路由规则匹配"与"客户端预渲染载荷探测"的前提；`checkOutdatedBuildInterval` 在它关着时也是禁用的。
- e8007 是开发期警告，根因是 `features.noScripts` 默认 `'production'` 造成的 dev/生产分岔；依赖客户端 JS 的两类是延迟水合与服务端组件里的 `nuxt-client`。
- 想让这类问题当场暴露，用 `noScripts` 路由规则（dev 也生效）或 `features.noScripts: 'all'`。
