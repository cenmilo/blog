同一行 `useRoute()`，写在页面里没事，挪进组合式函数就炸；`onPrehydrate()` 在自己的组件里能用，装进某个第三方包就不认了；`definePageMeta()` 放进条件分支里，构建阶段直接报错。

这三件事的错误码分别是 `NUXT_E1001`、`NUXT_E1006`、`NUXT_E1007`。三个错误码页各只有两段：一段讲触发条件，一段给修法。

## 三条一览

| 码 | 官方标题句 | 触发（官方描述） | 修法（官方 Resolution） |
| --- | --- | --- | --- |
| E1001 | Composable called outside Nuxt context | 需要 Nuxt 实例的组合式函数（`useNuxtApp()`、`useRoute()`、`useFetch()` 等）在插件、Nuxt 钩子、路由中间件或 Vue `setup()` **之外**运行 | 顶部同步调用并复用结果；服务端异步工作用 `nuxtApp.runWithContext()` |
| E1006 | onPrehydrate not processed by build pipeline | `onPrehydrate()` 运行时没有被 Nuxt 构建流水线转换——它需要编译期处理且只在服务端工作 | 把那个库加进 `nuxt.config.ts` 的 `build.transpile` |
| E1007 | Compiler-hint helper called at runtime | `definePageMeta()` 这类编译期宏在运行时被执行——这些 helper 会被构建 transform 掉 | 只在页面组件 `<script setup>` 的顶层调用宏 |

## E1001：上下文丢在异步里

官方原文把合法位置列了四个：

> A composable that needs the Nuxt instance (`useNuxtApp()`, `useRoute()`, `useFetch()`, …) ran outside a plugin, Nuxt hook, route middleware, or Vue `setup()`. The most common trigger is calling it inside an async callback (`setTimeout`, `.then()`, after an `await`) where the context has been lost.

四个合法位置值得背下来：**插件、Nuxt 钩子、路由中间件、Vue `setup()`**。第二句给出的是最常见的那种踩法：在 `setTimeout`、`.then()` 或一个 `await` 之后调用——**这时候上下文已经没了**。

修法两条，官方各管一种场景：

> Call the composable synchronously at the top of `setup()` / a plugin / middleware and reuse the captured result later. For server-side async work, wrap the call with `nuxtApp.runWithContext()`.

**第一条是"提前取、之后用"**：在 `setup()`、插件或中间件的顶部同步调用，把结果存下来，异步回调里用那个变量而不是重新调用组合式函数。

**第二条是给服务端异步工作的**：用 `nuxtApp.runWithContext()` 把调用包起来。这条对应的是"必须在异步里取"的情况，比如服务端插件里 await 完外部请求还要写状态。

有意思的是这一页的 read-more 指向的是入门的错误处理那一页，而不是 Nuxt 上下文那一页——**说明官方把 E1001 当作错误处理问题，而不是概念问题**。

## E1006：不是运行时报错，是构建没登记

官方描述里两个限定词是重点：

> `onPrehydrate()` ran without being transformed by the Nuxt build pipeline. It needs compile-time processing and only works on the server, so this happens when it is called from a dependency that Nuxt does not transpile.

**需要编译期处理**、**只在服务端工作**。所以触发条件是"它出现在一个 Nuxt 不转译的依赖里"——不是你自己写错了，是那个库没进转译名单。

修法一句：

> Add the offending library to `build.transpile` in `nuxt.config.ts` so the build pipeline can process its `onPrehydrate()` call.

这条和 438 那篇是同一个入口：`build.transpile` 接受包名、函数、字符串与匹配文件名的正则四种写法。**登记之后别忘了官方在 ESM 排错那页补的提醒：被那个库导入的包可能也要一起登记。**

## E1007：宏被 transform 掉了，不能动态跑

官方描述句里那句"is transformed away"是整个 Nuxt 编译机制的关键表述：

> A compile-time macro such as `definePageMeta()` executed at runtime. These helpers are transformed away by the Nuxt build and must never run dynamically. Usually this means the macro was called inside a composable or a non-page component instead of directly in a page.

**这些 helper 在构建时被替换掉**，所以运行时它们根本不该存在。最常见的现场是两个位置：**组合式函数里**，或者**非页面组件里**。

修法划了三条禁区：

> Call the macro only at the top level of a page component's `<script setup>`. It cannot be used inside composables, conditionals, or non-page components.

**只有页面组件的 `<script setup>` 顶层可以**。三处不行：组合式函数、条件分支、非页面组件。

第二条"条件分支"最容易误伤——`if (...) { definePageMeta({...}) }` 这种写法看着合理，但 441 记过 `definePageMeta` 的属性是被构建期静态提取的（默认提取 `middleware` 与 `validate`），466 也提过这点：**编译期要读到的东西不能依赖运行时分支**。

`defineNuxtPlugin` 与 `defineNuxtRouteMiddleware` 同理，它们也在静态处理名单里（441 的 `asyncFunctions` 默认值正是这两个）。

## 一条共同的判断方式

这三页合起来看，可以得出一条排查用的规律（**这是我把三条放在一起归纳的读法，官方没这么写过**）：它们报的都不是"值不对"，而是"位置不对"。所以修的方向只有三个——**挪到合法位置**（E1001、E1007）、**包一层上下文**（E1001 的 `runWithContext`）、**加进构建登记**（E1006 的 `build.transpile`）。给它们加 `try/catch` 不会有任何效果。

## 自查

- E1001 的四类合法位置是插件、Nuxt 钩子、路由中间件、`setup()`；异步回调（`setTimeout`/`.then()`/`await` 之后）是最常见触发；两条修法是顶部同步取值复用、服务端异步用 `runWithContext` 包。
- E1006 说明 `onPrehydrate()` 需要编译期处理且只在服务端生效；来自未转译的依赖就把它加进 `build.transpile`，别忘了间接依赖。
- E1007 的宏会被构建 transform 掉，只能写在页面组件 `<script setup>` 顶层，不能进组合式函数、条件分支或非页面组件。
- 三条的修法都在"位置/构建登记"这一层，不在异常处理这一层。
