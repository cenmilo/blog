## 这一站的屏幕上多了三行链接和一颗会炸的按钮

打开 `http://localhost:3100/docs`，页面最下方那一排"实验位"链接又多三条：`实验位：点一下抛个错`、`实验位：渲染期就抛错`、`实验位：服务端渲染时抛错`。点第一条进去，正文下方是这样：

```text
这一段专门用来抛错 LAB_ERR_807
同页另一块 LAB_ERR_KEEP_807，看抛错之后它还在不在
处理器被跑到几次：0
[事件里普通抛错] [点一下抛一个致命错] [现在挂上那一位会炸的组件]
探针面板 LAB_BOOM_807：这一位正常工作
```

为什么要先花一整站量"没有边界"的状态：这条线的目标（会员区那块数字别因为一次抛错就整片不见）很容易被想歪成"加了边界就不会白屏"。可实际上**不白屏是默认行为**，真正会发生的是那块内容**悄悄消失**，谁都不知道。所以这一站不加任何边界，只把炸在不同环里的后果各读一遍。

## 官方给这一条线的依据只有两句

讲 `<NuxtErrorBoundary>` 那一节的头一句限定了它的管辖范围：「The `<NuxtErrorBoundary>` component handles **client-side** errors happening in its default slot.」

讲错误处理那一节给了什么时候会换整页：「If you throw an error created with `createError`: … on client-side, it will throw a non-fatal error for you to handle. If you need to trigger a full-screen error page, then you can do this by setting `fatal: true`.」

两句合起来要现场验的是三件事：管不到哪一路、`fatal` 那一支的形状、以及"非致命"那一支在页面上到底留不留痕迹。

## 探针与三档挂法

新组件 `app/components/LabBoomPanel.vue` 只干一件事：`where` 这个 prop 是 `render` 时，它在自己的 setup 里直接抛；其它值时正常工作。

```vue
<script setup lang="ts">
const props = defineProps<{ where?: string }>()

if (props.where === 'render') {
  throw new Error('LAB_BOOM_807：渲染期抛错（没有边界包住它）')
}
</script>

<template>
  <p data-testid="boom-panel">探针面板 LAB_BOOM_807：这一位正常工作</p>
</template>
```

页面 `app/pages/docs/[slug].vue` 里三种挂法：`?islandLab=err-ssr` 在页面 setup 里 `throw createError({ status: 500, fatal: true })`（服务端那一次渲染就炸）；`?islandLab=err-render` 直接挂 `where="render"`（服务端渲染时也要渲它）；`?islandLab=err` 这一档页面是健康的，两颗按钮分别抛普通错与致命错，第三颗按钮 `err-mount` 才把 `where="render"` 那一位挂上——**"只在浏览器里挂"这一路才是边界管的那一种**。

判据在 `test/e2e/error-baseline.spec.ts`，六条，全部不需要库。

`6 passed`。最后那条是正对照：一颗按钮都不按时，这几位全在、也没有错误——上面那些"没了"才只来自抛错本身。

## 服务端那两路：掀掉的是整条响应

`err-ssr` 那一趟的响应码是 500，回来的 HTML 里 `data-testid="error-status"` 在、`data-testid="doc-title"` 不在，字节数从 7,184 掉到 3,305。`err-render` 是同一件事的另一种触发方式（探针在**服务端那一次渲染**里就被挂上，所以浏览器拿到的仍是那份 500 的错误页）。

**破坏范围：整条响应。** 这一路与边界无关——官方那句写得很死，它只管客户端。这是 811 那一步要单独量、单独讲清的一条：给那一块套再多边界，服务端渲染时抛的错还是整页。

## 客户端渲染期：不白屏，但也没人知道

`err` 档里点第三颗按钮（`现在挂上那一位会炸的组件`），读回来的形状和"整页完蛋"完全相反：正文、抛错提示、旁边那块，点前点后一位没少；错误页那位是 0；`pageerror` 一条都没有；页面上渲出来的探针数量还是 1——新挂的那位**根本没渲出来**，它抛的那个错只在控制台留下一行 `Error: LAB_BOOM_807：渲染期抛错（没有边界包住它）`。

这就是这条线真正的靶子。用户看到的是"那块数字不见了，其它都还好好的"，而开发者要打开控制台才知道红过一次。**"不许整片白屏"这句验收，在本站读到的不是"会白屏"，而是"会静默"**。下一站（808）把边界套上去，要改变的正是这两点：那块的位置要留下可见的回退，红过一次要留下可读的数。

事件处理器里抛普通错（`err-plain`）的形状几乎一样：`点后` 与 `点前` 逐位相等、没有错误页、`pageerror` 0 条、控制台 1 条。这一档配了一位哨兵：`处理器被跑到几次：0 → 1`。没有它，"页面没变"有可能是"处理器根本没执行"，两种解释分不开。

## `fatal: true`：一次点击换掉整页

同一页上，另一颗按钮（`err-fatal`）抛的是 `createError({ status: 500, fatal: true })`。点下去之后：`正文` 从 1 变 0、`错误页` 从 0 变 1、错误页上那一位数字是 `500`，而且按钮给的是 `error-reload`（重新加载）而不是返回首页——`app/error.vue` 里 `fatal` 那一支就是这么分支的。

同一次点击、同一个组件，只多了一个 `fatal: true`，破坏范围从"零"变成"整页"。这句在官方那里是那句"If you need to trigger a full-screen error page"，在本页它是可点出来的对照。

## 顺手把一条老基线的扫描改准了

`app/` 里 `NuxtErrorBoundary` 用了几处，这条基线一直由 `test/e2e/console-baseline.spec.ts` 数文件内容。这一站刚开工就把它弄红了：`Received: 2`。原因不是有人用了边界，而是**新组件与页面的注释里写着这个名字**。

原来的判据把"提到"和"用起来"算成了同一件事，所以补了一层剥注释再数：

```ts
const 剥注释 = (文本: string) => 文本
  .replace(/<!--[\s\S]*?-->/g, '')
  .split('\n')
  .filter(行 => !/^\s*(?:\/\/|\*|\/\*)/.test(行))
  .join('\n')
```

同一位的原文命中数也一起打印，差异看得见。改完读回来：

```text
[baseline error boundary] {"vueFiles":22,"boundaryHits":0,"原文命中边界":2,"mainHits":2,"hasErrorPage":true}
```

顺带说明另一位数变小的原因：`mainHits` 从上一轮的 4 变成 2——那 4 位里有两位本来就是注释里写的 `<main`。对照组的意义在于"扫描真的读了这些文件"，2 仍然满足；**基线的值是"用起来 0 处"**，这条现在才是干净的。

## 排错表

| 想知道的 | 读哪一位 | 别把它和什么混起来 |
| --- | --- | --- |
| 服务端渲染抛错的代价 | 那一趟的响应码与 HTML 字节 | 客户端抛错（回 200，页面上换错误页） |
| 客户端某块炸了会不会白屏 | 同页其它 `data-testid` 的存活数 | 会不会"有痕迹"——它没白屏也没痕迹 |
| 这次抛错到底有没有被报出来 | `pageerror` 与控制台各记几条 | 只看 `pageerror`（这一路它是 0） |
| 处理器到底跑没跑到 | 自己加的一位计数（0→1） | "DOM 没变"不等于"没执行" |
| `fatal` 与普通错的差别 | 同一页两颗按钮，各点一次 | 两种不同的错误来源（渲染期与事件里） |

## 自己动手跑一遍

```bash
npm run build
npx playwright test test/e2e/error-baseline.spec.ts
```

预期 `6 passed`。手点版：进 `?islandLab=err`，先把 DevTools 开在 Console；点`事件里普通抛错`，页面上什么都不变，控制台多一行；点`现在挂上那一位会炸的组件`，还是什么都不变（新那一位根本没出现），控制台再多一行；最后点`点一下抛一个致命错`——整页换成错误页。这三下就是"没有边界"的全部内容。
