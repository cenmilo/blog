## 库里多了一行，页面上的数字没动，接口已经变了

会员区那一栏写着 `1`。这时候从另一条连接往计量表里再插一行——库里两行、接口回 `2`、页面上还是 `1`。三个数都在说话，说的是三件事。上一篇把"页面显示的与接口回的是不是同一份"读完之后，这一篇问的是**时间轴**：数字什么时候跟着库走、谁先不动、以及怎么让它动。

判据是一条新的规格文件，跑法与前两站一样分两趟：

```bash
# 默认那趟（不连库）：四条全部 skip
npm run test:e2e -- test/e2e/reconcile-write-then-read.spec.ts
# 带库那趟
NUXT_E2E_DB=1 npm run test:e2e -- test/e2e/reconcile-write-then-read.spec.ts
```

## 三个位置，一次写入，各自变成多少

先立住"三处一起变"这件事。写两行读一次，再写一行读一次，本轮打印：

```json
[写入·三位置] {"第一回":{"库":2,"接口":2,"页面":"2"},
  "第二回":{"库":3,"接口":3,"页面":"3"},
  "各自变化":{"库":"2→3","接口":"2→3","页面":"2→3"}}
```

这里的"页面"读的是 `GET /console` 的响应体里那一位文字，也就是**服务端当场算的那一份**——服务端每次请求都会重新取一次数，所以它跟着库走。这三处一起变不代表页面上开着的页面也会变，这正是下一节要撞的。

## 开着的页面为什么不动

浏览器接手这一段 HTML、把事件挂上去叫水合；接手时它读的是服务端一起发下来的那段 JSON（负载）。取数结果就记在负载的 `data` 那一位上，按取数键存放。官方给的默认缓存函数就一句：

```ts
const getDefaultCachedData = (key, nuxtApp, ctx) => nuxtApp.isHydrating
  ? nuxtApp.payload.data[key]
  : nuxtApp.static.data[key]
```

于是"页面开着的时候库里多了一行"这件事，读出来是这样一个对照：

```json
[写入·谁没变] {"进场顶栏":"1","进场面板":"1","库里":2,
  "没动的顶栏":"1","没动的面板":"1","接口现在":2,"页面状态":"success"}
```

没变的那一位现在有名字：**页面手上那份取数结果**（键是 `console:metrics`）。它不是接口的缓存——同一时刻单独打接口就拿到 `2`；它也不是浏览器的 HTTP 缓存——下一节的 `refresh()` 一发请求就拿到新值。库里没有新行时两者恰好一样，所以这个数字对不上之前，从来没人注意到它们是两个东西。

## 两种让它变的法子

页面上加了一位按钮（这是本轮唯一的应用代码改动）：

```vue
<button
  type="button"
  data-testid="metrics-refresh"
  @click="void 重新取数()"
>
  重新取一次
</button>
```

`重新取数` 就是取数返回值里那个 `refresh`：

```ts
const { data: consoleMetrics, status: metricsStatus, refresh: 重新取数 } = await useConsoleMetrics('/api/console/metrics')
```

官方那份类型里它是**一个普通函数**（`refresh: (opts?) => Promise<void>`，与 `data`、`status` 那些 ref 并列；同一段还给了 `status` 的四个取值 `idle`／`pending`／`success`／`error`）。为什么要有这一位：仪表盘上"重新取一次"本来就是正常动作，而两种刷新法的差别正是这一篇要问的——不加它就只能整页重刷，问题问不出来。

本轮两条路一起读：

```json
[写入·两法] {"进场":"1","点完顶栏":"2","点完面板":"2","点完状态":"success",
  "刷完顶栏":"3","刷完面板":"3","库里":3,"重刷后HTML那一位":"3"}
```

点一下：只重取这一份，不重跑整页；整页重刷：服务端重新算一次，负载重新带一份。两条都把新数带回来了，`点完状态` 仍是 `success`——重取不会把状态打回 `pending`（`pending` 只在还没落定的那一瞬读得到）。

## 一起变才叫同一份

上面那条读数里最有用的是 `点完面板` 这一位：**只点了顶栏那一路的 `refresh()`，面板也跟着变成 2**。两处调用共用的就是同一个键、同一份数据。

把出口里的键摘掉再跑一次，这一位立刻分家：

```json
{"点完顶栏":"2","点完面板":"1"}
```

判据在这一档红：`顶栏刷新了而面板没跟：两处读的不是同一份`，而另外三条（三位置、谁没变、隔离）全绿。上一篇留过一句"数字相等证明不了同一份"，这一篇给它补上了时间轴上的另一半：**一起变才是同一份**。屏幕上看是看不出区别的——两处显示同一个数的时刻，可能是一份数据，也可能是两份恰好一样的数据。

## 两位用户各有行：把"看到别人的数字"量出来

上一站留了一条没合上的口径：库里只有一位用户有行时，去掉 `where user_id` 这件事测不出来——反正只有一个人的数。这一站建两位探针用户，各写各的行：

```json
[写入·隔离] {"甲":{"读数":{"库":1,"接口":1,"页面":"1"},"分组":[{"kind":"w827_jia","count":1}]},
  "乙":{"读数":{"库":3,"接口":3,"页面":"3"},"分组":[{"kind":"w827_er","count":1},{"kind":"w827_yi","count":2}]},
  "全表":5}
```

甲一位三处对平 `1`，乙一位三处对平 `3`，两边的分组里都不出现对方的 `kind`，而全表是 5 行——数字确实混在一起躺着。把服务层那个条件换成恒真再跑，四条一起红，其中这一条的读数最刺眼：

```json
{"甲":{"接口":5,"分组":[{"kind":"login","count":1},{"kind":"w827_er","count":1},{"kind":"w827_jia","count":1},{"kind":"w827_yi","count":2}]},
 "乙":{"接口":5}}
```

两个人读到同一个 5，甲的分组里出现了乙的三种动作。这就是"先确认是谁在问，再算数字"那句规矩要挡的事——它不是风格问题，是一个功能级的口子。改回原样后四条全绿。

## 第一跑四条一起红，红在请求头里

这批判据第一次跑，四条全红在同一个地方：

```text
TypeError: apiRequestContext.get: Invalid character in header content ["cookie"]
```

原因不在代码逻辑，在探针的命名：会话 id 是从用例标签拼出来的，我把标签写成了中文（`sess_w827_三位置_…`），而这一位要原样进 `Cookie` 请求头——头的值只许 ASCII。换成 ASCII 标签后一次跑通。这与讲错误契约那一站"状态短语只放 ASCII"是同一族规矩，只是撞在了另一头上。

## 这一档没验的那一路

上面的行是用 SQL 直接写进表里的**探针行**，每个用例自己建用户、跑完自己删（`meter_events` 与 `sessions` 的外键是 `onDelete: 'cascade'`，删用户就把行一起带走）。问的是缓存归属，不是在证明应用侧写入通了：`recordMeterEvent` 只有真登录那一路会被调到，而真登录要一封真邮件，那是"要外部服务变量"那一档仍缺的东西。这一条要写清楚，别让读者以为应用的写入路径也测过了。

## 读数对不上时先看哪一处

| 症状 | 先看哪里 | 为什么 |
| --- | --- | --- |
| 库和接口都变了，页面没变 | 正常，那是进场时带下来的那一份 | 没有机制通知这一页 |
| 点了重新取一次，只有一栏变 | 两处调用是不是同一个键 | 键不同就是两份数据，一起变才是同一份 |
| 整页重刷后两栏不等 | 负载与水合那一段（上一篇） | 服务端那份与接手后那份对不上 |
| 页面数字与库里不等 | 用的是哪一位用户的会话 | 边界在 `where user_id` 上 |
| 四条一起红在 cookie 头 | 会话 id 里有没有非 ASCII 字符 | 请求头值只许 ASCII |
| 四条全部 skip | 有没有带 `NUXT_E2E_DB=1`，`.env` 在不在当前目录 | skip 是没测，不是测过 |
