## 同一条请求，两个状态码

先摆本轮真跑出来的两趟。跑的是同一条判据、同一个形状合法的令牌参数：

```bash
E2E_PORT=3487 npm run test:e2e -- test/e2e/verify.spec.ts
# 4 passed (30.9s)

NUXT_E2E_DB=1 E2E_PORT=3489 npm run test:e2e -- test/e2e/verify.spec.ts
# 1 failed / 3 passed (32.5s)
# Error: expect(received).toBe(expected)  Expected: 503  Received: 401
```

第一趟读到 `503 DB_NOT_CONFIGURED`，第二趟读到 `401`。服务端代码一个字没改，改的只是"这个进程有没有连到库"。

**`503` 说的是"这道闸门根本没法判"**——没配库时身份查不出来，任何令牌都到不了能发会话的那一步；**`401` 说的是"判过了，不通过"**——库连着，身份查得到，只是这次没有会话。两个码差一个字，运维上是完全不同的两件事。

## 为什么带库跑要一个开关，而不是无条件读配置

这一节最容易做错的"顺手简化"是：把那个开关去掉，让测试配置永远读 `.env`。真去掉之后上面那趟 `503` 会变成 `401`——判据仍然绿，但它读的是另一件事。这一站在仓库里对应的那条判据（"形状合法但没配库 ⇒ `503`"）就是这么被顶掉的。

为什么产物服务读不到 `.env`，官方那节写得很明确：

> In addition to any process environment variables, if you have a `.env` file in your project root directory, it will be automatically loaded at dev, build and generate time.

紧接着讲生产的另一段是：

> Your `.env` files will not be read at this point. How you do this is different for every environment.

也就是说，`.env` 只在 dev、`nuxt build`、`nuxt generate` 这几个时刻生效；端到端测的是 `nuxt build` 之后再 `node .output/server/index.mjs` 起的那个进程——那时框架不替你读文件。所以本项目把"要不要读"显式化成 `NUXT_E2E_DB=1`，读法只有这一处：

```ts [playwright.config.ts]
if (process.env.NUXT_E2E_DB === '1') {
  try {
    process.loadEnvFile('.env')
  } catch {
    console.warn('[e2e] NUXT_E2E_DB=1 但 .env 读不到：带库的用例会自己 skip')
  }
}
```

还有一句常被混掉的：换别的 env 文件，Nuxt CLI 的旗标是 `--dotenv`（`npx nuxt dev --dotenv .env.local`），不是 Node 的 `--env-file`。前者让框架读，后者让 Node 进程读——端到端那趟用的是后者做不到的事。

## 探针说库是好的，接口还是 500：两个名字不是一回事

`runtimeConfig` 那一节给了一条硬规则：**只有以 `NUXT_` 开头的环境变量会被捡进 `runtimeConfig`**。所以 `DATABASE_URL` 那个名字，框架不看。

```ts [server/utils/db.ts]
export function useDb () {
  const connectionString = useRuntimeConfig().databaseUrl
  if (!connectionString) {
    throw new Error('useDb(): runtimeConfig.databaseUrl 是空串，请设环境变量 NUXT_DATABASE_URL（CLI 侧那个 DATABASE_URL 不会被读）')
  }
```

而取数用的小工具两个名字都认：

```js [scripts/db-probe.mjs]
if (!process.env.NUXT_DATABASE_URL && !process.env.DATABASE_URL) {
  process.loadEnvFile('.env')
}
const source = process.env.NUXT_DATABASE_URL ? 'NUXT_DATABASE_URL' : (process.env.DATABASE_URL ? 'DATABASE_URL（注意：应用侧不读这个名字）' : '两个都没有')
const url = process.env.NUXT_DATABASE_URL ?? process.env.DATABASE_URL ?? ''
```

两边认的不止是取值顺序，而是**整条路径**：应用只有一条（`runtimeConfig.databaseUrl`，由 `NUXT_DATABASE_URL` 覆盖），工具多一条兜底。于是就有了那个最费时间的画面——探针连着库把行数读给你看，应用侧同一个进程却抛"databaseUrl 是空串"。

这个不对称本轮被钉成三条判据（`test/unit/db.test.ts` 从 3 条扩到 6 条）：工具两个名字都认、应用一行 `process.env` 都不读、应用读的是 `useRuntimeConfig().databaseUrl`。判据钉的是源码形状，任何环境都跑得动。

它还被一次变异验证过——把加载那行从 `loadEnvFile('.env')` 改成 `loadEnvFile('./.env')`（语义完全没变），那条判据就红：

```
AssertionError: 探针不再自己找 .env ⇒ 用法要改成必须带 --env-file，本档同步改:
- process.loadEnvFile('.env')
+     process.loadEnvFile('./.env')
```

改回之后 `Tests 6 passed (6)`。

## 在哪个目录跑，决定你读到的是行数还是空 message

这是本轮最值钱的一条更正。以前记的说法是"探针不带 `--env-file` 就会连本机 5432"，这一轮两种写法都跑通了——因为这个工具自己会 `process.loadEnvFile('.env')`。真正的前提是**当前目录有没有 `.env`**：

```bash
# 在 Substrate/ 目录里（.env 就在脚下），带不带 --env-file 都一样
node scripts/db-probe.mjs "select count(*)::int as n from meter_events"
# 连接串来自 NUXT_DATABASE_URL
# [{"command":"SELECT","rowCount":1,"rows":[{"n":1}]}]

# 换到上一级目录跑同一条
node Substrate/scripts/db-probe.mjs "select count(*)::int as n from meter_events"
# （当前目录没有 .env，只按进程环境变量判）
# 连接串来自 两个都没有
# {"error":{"message":"","code":"ECONNREFUSED"}}
```

最后那行值得盯两秒：**`message` 是空的**，只有 `code` 是 `ECONNREFUSED`。它看起来像"数据库挂了"，实际是"我连的是本机默认端口，那台机器上根本没人监听"。上一轮就照着这个空消息判断过一次"托管库不通"，白折腾半天。

顺手把对账要用的分母取到了（只读，没写任何一行）：计量表此刻有 **1** 行，按 `kind` 分组是 `login: 1`。

```bash
node --env-file=.env scripts/db-probe.mjs "select kind, count(*)::int as n from meter_events group by kind order by kind"
# [{"command":"SELECT","rowCount":1,"rows":[{"kind":"login","n":1}]}]
```

## 把这道门槛写成能跑的判据

读库这件事本身没法进判据（跑测的机器不一定有库），但**造成读不到库的那些形状**每一条都能钉住。这一站钉了三个：环境变量名的不对称、工具按当前目录找 `.env`、以及输出前先把口令遮掉。前两条正是上面两段读数的来源，第三条是"我可以放心把这条命令的输出抄进文章"的前提。

```ts [test/unit/db.test.ts]
describe('scripts/db-probe.mjs 与 useDb() 的取数口径', () => {
  const 剥注释 = (源: string) => 源.split('\n').filter(行 => !行.trim().startsWith('//')).join('\n')

  it('探针认两个名字，运行时只认 NUXT_ 那一个', () => {
    expect(剥注释(探针源), '探针不再两个名字都认 ⇒ 这条不对称消失，本档的成因说明要改')
      .toContain('process.env.NUXT_DATABASE_URL ?? process.env.DATABASE_URL')
    expect(剥注释(运行源).includes('process.env'), '运行时也开始读进程环境变量 ⇒ 那句不对称要重写').toBe(false)
  })
})
```

三条都在，跑一次是 `Tests 6 passed (6)`（这一档原来只有 3 条）。它们不看任何环境变量、不碰网络，所以在没配库的机器上也是绿的——这一点很重要：**门槛类判据不许依赖它要钉的那个环境**，否则它就变成了那条被跳过 25 次的使用例。

## 有一条判据被读数纠正

上面那三条形状判据里，头一版本红了一次：

```
AssertionError: 运行时也开始直接认 DATABASE_URL ⇒ 上面那句要重写: expected true to be false
```

原因是我搜的字符串 `process.env.DATABASE_URL` 出现在 `server/utils/db.ts` 的**注释**里（那句"不回落到 process.env.DATABASE_URL——那个名字归 CLI"）。搜索器不认识注释和代码的区别，判据就把一条正确的实现读成了坏的。修法不是放宽断言，是先把行注释剥掉再比形状——仓库里端到端那一档早就这么干了（扫 `.vue` 源码时也剥注释），这次轮到单测用。

## 你会撞上的几种形状

| 症状 | 实际发生了什么 | 该怎么办 |
| --- | --- | --- |
| 判据从 503 变成 401，以为代码坏了 | 那个进程连上了库，闸门从"没法判"变成"判过不通过" | 带库跑要显式开关，并且只点名要跑的那条 spec |
| 整趟端到端都带库跑 | 钉"没配库"的那几条会一起红 | 只在需要的那一条上加开关，默认那趟保持干净 |
| 探针读到行数，接口说没配库 | 你只设了 `DATABASE_URL`，应用侧只认 `NUXT_DATABASE_URL` | 设带前缀那一个；两个都要设时以 `NUXT_` 为准 |
| 一条 `ECONNREFUSED`，message 是空的 | 当前目录没有 `.env`，连的是本机默认端口 | 回到项目根跑，或把连接串放进进程环境 |
| 想用另一个 env 文件 | `--env-file` 是 Node 的旗标，Nuxt 不认 | Nuxt CLI 用 `--dotenv .env.local` |
| 源码形状判据红得莫名其妙 | 命中的是注释里的字符串 | 先剥注释再比，注释不是契约 |

## 这一站的三条结论

门槛是一个显式开关，不是"顺手多读一个文件"——读与不读改变的是状态码的含义。
连库这件事有两条独立的路：框架的 `runtimeConfig` 只认 `NUXT_` 前缀，取数工具两个都认，两者的差就是"工具说没事、应用还在抛"。
`.env` 只在 dev、build、generate 三个时刻被读，所以测产物那趟必须自己安排；而它读的是**当前目录**那一个文件，跑命令的位置会改变结果。

下一站做第一次真正的对账：库里的行数、按 `kind` 分组的和、聚合接口回的总数，三个数摆在一起看是否相等。这一站只读了数，没写——会员区写入那一步需要一次明确授权，仍没拿到。
