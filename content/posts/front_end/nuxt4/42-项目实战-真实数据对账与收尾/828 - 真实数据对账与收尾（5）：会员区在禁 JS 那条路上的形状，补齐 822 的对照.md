## 门后那一格还空着

`noScripts` 这一位是路由规则：命中时服务端不把 Nuxt 的脚本与 JS 资源提示写进 HTML。讲渲染那一节给的原话是 Disables rendering of Nuxt scripts and JS resource hints for sections of your site.

上一线已经在两条公开实验位上量过这件事：规则盖住的那一页，入口 `<script>`、import map、内联负载段、JS 资源提示四类一位都不剩，正文与样式一位不差。但那两条路由**没有门**。会员区这一页要多了两样东西：一道会话、一份从库里算出来的数字。这两样都不在渲染层里，所以"禁 JS 时门后页还出不出内容"这句话，不能拿公开实验位的读数直接替它答。

四种组合摆开是这样的：

| 会话 | 脚本 | 该看见什么 |
| --- | --- | --- |
| 没有 | 发 | 302 到登录入口，正文一个字都没有 |
| 没有 | 不发 | 同上——门管不着脚本发不发 |
| 有 | 发 | 全文＋数字＋负载＋水合 |
| 有 | 不发 | 全文＋数字，四类脚本面一位都没有，永不水合 |

## 为什么这一档不能直接开在 `/console` 上

最省事的做法是给 `/console` 加那一位规则。但本站刚立的三条判据都要碰它：826④ 要等水合标记出现才读数，827③ 要点那一页上的"重新取一次"按钮，`identity-payload` 要读那一页的负载段。规则一盖，这三条读到的都是"读不到"——判据不会告诉你原因，只会红。

所以照 820 的办法新开**一对内容同形的门后页**，只在路由规则那一位上不同：

```ts
// nuxt.config.ts:81-82
'/console/nojs-lab': { ssr: true, prerender: false, noScripts: true },
'/console/js-lab': { ssr: true, prerender: false },
```

两个页面文件里，门、收录表态、标题、取数、岛屿都写得一样：

```ts
definePageMeta({ middleware: ['console-auth'] })
useSeoMeta({ title: '会员区无脚本实验位' })
if (import.meta.server) { useSeoMeta({ robots: 'noindex' }) }
const { data: 会员数, status: 取数状态 } = await useConsoleMetrics('/api/console/metrics')
const 总数 = computed(() => 会员数?.value?.metrics.total ?? '(没值)')
```

数还是从那个出口来（键锁在出口里，见 783），这一位没有新写一份取数。

## 没有会话那一半：门在脚本规则之前

```json
[门后·无会话] {"/console/js-lab":{"状态":302,"落点":"/me","正文字节":89,"有标记句":false,"请求号在":true},
  "/console/nojs-lab":{"状态":302,"落点":"/me","正文字节":89,"有标记句":false,"请求号在":true}}
```

两位逐位相同，都是 302、落点都是 `/me`、正文都是那 89 字节、门后那一句都不在。这一格里最有用的读数是**状态码不是 404**：404 意味着新页压根没进产物，后面三档全在空转；302 才说明页面存在、被门挡在门外。

顺序也是可读的：`x-request-id` 在，说明服务端中间件已经跑过一遍，而路由规则动的是渲染那一步。**先确认是谁在问，再决定发什么**——脚本发不发改变不了这一位。

## 有会话 × 发脚本：对照页的形状

```json
[门后·发脚本] {"状态":200,"脚本面":{"入口模块脚本":1,"全部脚本标签":4,"modulepreload":31,
  "prefetch":1,"负载段在":true,"importmap在":true,"整页字节":8192},
  "接口总":2,"页面那一位":"2","状态栏":"success","岛屿里读回的props":"页面递进来的总数=2",
  "岛屿静态位":"1","me状态":200,"me负载段在":true,"me脚本面":{"modulepreload":28,"整页字节":4810}}
```

对照组要成立，四类就得一位不少（判据里就钉着这一位）。顺带并排读了 `/me`：同一枚会话下 4810 字节、28 条 modulepreload——实验位多出来的那几条资源提示是多挂的那两块岛屿带来的，不是别的东西。

## 有会话 × 不发脚本：四类没了，数还在

```json
[门后·不发脚本] {"状态":200,"脚本面":{"入口模块脚本":0,"全部脚本标签":0,"modulepreload":0,
  "prefetch":0,"负载段在":false,"importmap在":false,"整页字节":3591},
  "接口总":2,"页面那一位":"2","状态栏":"success","岛屿里读回的props":"页面递进来的总数=2",
  "岛屿静态位":"1","岛屿根在":true,"页面slot按钮在":true}
```

这一格就是 M4 验收第二句欠着的门后那一半：**不发脚本时那一栏照样有真数**（`2`，与接口体同一个数），状态栏照样是 `success`。原因不神秘：取数在服务端那一趟就跑完了，浏览器还没参与进来，脚本发不发都碰不到它。整页从 8192 字节掉到 3591，掉的正是脚本面那四类。

## 岛屿那块显示的数从哪来

口径的后半句问的是这个。官方讲服务端组件那一节把隔离写成一条硬话：

> you cannot share state (provide/inject, Pinia, `useState`) between the page and the island; pass data via props instead

所以页面算出来的那个数要进岛屿，只有一条路——props：

```vue
<IslandFacts slug="console-lab" :page-path="`页面递进来的总数=${总数}`" />
```

同一枚会话下把两页的 HTML 并排逐位比：

```json
[门后·逐位] {"开规则":{"页面":"3","props":"页面递进来的总数=3","静态位":"1","岛屿根":true,"客户端位":"3"},
  "没开":{"页面":"3","props":"页面递进来的总数=3","静态位":"1","岛屿根":true,"客户端位":"3"},
  "接口":{"total":3,"kinds":[{"kind":"w828_both","count":3}]}}
```

两侧逐位相同，props 那一位带着的就是接口算出来的那个 3。于是这句话可以落地成读数：**岛屿那块显示的数来自 props，而 props 来自服务端算好的那一份库里的数**——不发脚本这一路上它照样成立，因为这一段本来就是服务端渲完再拼进 HTML 的。

顺带一条官方自己提醒过的：Props are serialized and sent as GET query parameters。也就是说递进岛屿的东西会出现在查询串里，而查询串会进访问日志、CDN 缓存和 `Referer`。这条路上别把敏感值当 props 递进去。

## 两次变异：一次红两档，一次红一档

- **摘掉 `/console/nojs-lab` 的 `noScripts`**：828③ 红 `还发着入口模块脚本：规则没盖住这一页 Expected: 0 Received: 1`，同时 `no-scripts.spec.ts` 基线④ 也红（键清单只剩一位）。828④ **照旧绿**——它比的是内容位，不比脚本面。
- **把 nojs 页里那句 props 改成写死的数**：只有 828④ 红 `Expected: "页面递进来的总数=3" Received: "页面递进来的总数=写死的数"`，另三档全绿。

第二条里还有一件要诚实记下的事：改完之后 ③ 的打印里那一格明明写着 `页面递进来的总数=写死的数`，**却一点不红**——因为 ③ 只把 props 打印出来，没有断言它。而 ④ 那句失败消息原本写的是"props 这一段被脚本规则碰过"，可这次红的原因根本不是脚本规则，是我手改了表达式。断言能证伪什么，消息就只能说什么，所以把它改宽成"要么规则碰了 props 这一段，要么两页的表达式已经不是同一份"。

## 加一条路由会撞到别人钉的清单

这一轮真正花时间的不是新判据，而是**四条早就存在的清单型判据**红了或需要跟着变：

| 被撞的地方 | 原来钉的 | 现在 |
| --- | --- | --- |
| `indexing-surface.test.ts` 门后名单 | 两位 | 四位（新增两位门后页） |
| 同文件门后计数断言 | `toBe(2)` | `toBe(4)` |
| `no-scripts.spec.ts` 基线④ | 开了规则的路由只有 `/no-js-lab` | 清单加一位 |
| `console-fetch-surface`／`data-fetch-surface` 的出口调用清单 | 两个调用点 | 四个调用点 |

这些红不是页面写坏了，是世界多了一条路由而清单还是旧的。判断标准只有一条：**新事实就登记进清单，别改判据的形状**。门后那两位必须进名单，否则它们会被当成公开页，撞上"其余页面都要 index"那一句；出口调用清单加了两位，恰好说明新页没有另起一份取数写法。

## 本机读不到的一条版本差

错误码那一节有一条 E8007，讲的正是在开发环境里客户端依赖看起来好好的、部署后被 `noScripts` 静默打断那种情况，它还写明路由级那一位在开发阶段同样生效。本站装在 4.5.2 上，包内搜不到这条码（821 那一站已把这一位钉成版本差），所以这里只登记文档的说法，不当成本机结论。本机的形状全部在上面那几段读数里。

## 读数对不上时先看哪一处

| 症状 | 先看哪里 | 为什么 |
| --- | --- | --- |
| 实验位读到 404 | 页面文件在不在 `app/pages` 下、路由名对不对 | 404 是压根没有这一页，不是被门挡 |
| 无会话时读到 200 | `definePageMeta` 里那道具名中间件写了吗 | 具名中间件不会自动生效 |
| 不发脚本那页四类还在 | `routeRules` 那一位有没有生效、路径写得对不对 | 路径没命中就整条规则都不动 |
| 不发脚本那页正文空了 | 那一页的取数与门是不是同一趟 | 门后内容靠服务端取数，不靠脚本 |
| 两页内容不一致 | 两边模板是不是同一份表达式 | 同形一对只在规则那一位上不同 |
| 清单型判据红 | 是不是新加了一条路由或一个调用点 | 新事实登记进清单，别改判据形状 |
