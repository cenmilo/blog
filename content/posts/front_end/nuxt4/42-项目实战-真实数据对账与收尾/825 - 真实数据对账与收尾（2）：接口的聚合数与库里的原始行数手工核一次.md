## 一个数字，三段链

页面上那一栏写着 `1`。要回答"这个 1 是不是库里那个 1"，就得把同一条链读三遍，而不是读一遍然后宣布一致：

| 读的是哪一段 | 怎么读 | 本轮读到的 |
| --- | --- | --- |
| 库 | `select kind, count(*)::int from meter_events where user_id = $1 group by kind` | `[{"kind":"login","n":1}]`，相加得 1 |
| 聚合接口 | `GET /api/console/metrics`，带上这位用户的会话 | 状态 200，`{"total":1,"kinds":[{"kind":"login","count":1}]}` |
| 页面 | `GET /console` 带同一枚会话，从 HTML 里数那一位 | `metrics-total` 是 `1`，状态栏是 `success` |

三段都等 ⇒ 这一句验收才算合上。任何一段自己看自己都"对"，串起来仍然可能是错的：库里数的是所有人、接口数的是别人、页面显示的是缓存里那位。

跑法用上一站量清楚的门槛：带库那一趟只点名跑这一条判据。

```bash
NUXT_E2E_DB=1 npm run test:e2e -- test/e2e/dashboard-reconciliation.spec.ts
# 4 passed (45.6s)
```

不带这个开关跑同一条文件是 **4 skipped**——库里读不到行就没东西可对，skip 是"没测"，不是"测过了"。

## 为什么要真连库，而不是拿假数据比

上一站留了一句关键的：没配库时这道闸门回 `503 DB_NOT_CONFIGURED`，配上库回 `401`。这两个码都不是"数字对上了"。所以判据必须落在**能连库的那一趟**里，才有可对的东西。

这一趟的读数也顺手结掉了另一条旧账：接口先确认是谁在问、再算数字（`requireUser` 拿的是这次请求自己的会话），所以 `where user_id = ?` 那个值不可能由查询串决定。这一点过去只有单测里的手写数据在钉，本轮第一次在真库上读到"全表有 1 行、而我这一侧读到 0"。

## 三个数不许互相作弊

服务层那条口径是：`total` 由**各行相加**得到，不是再发一次 `count(*)`。为什么这样写，在真表上读一次就明白：

```js
// 库里两种问法，同一时刻各读一次
`select coalesce(sum(n),0)::int as 和 from (select count(*)::int as n from meter_events where user_id = $1 group by kind) t`
`select count(*)::int as n from meter_events where user_id = $1`
```

本轮读到 `{"分组后相加":1,"直接count":1}`——相等。但这条判据的措辞要留一句实话：**在只有一行、又没有并发写入的表上，相等是运气好**。两次查询之间插入的行会让两者不等，而那时"总数与分项对不上"这件事在页面上是看不出来的，只会看到 `total` 比 `kinds` 的和多一位。所以这一档钉的不是"永远相等"，而是"本站此刻这两种问法给出同一个数，一旦哪天不等了要在这里红"。

顺序也顺手复核了一次：接口发出的 `kinds` 是按 `kind` 字典序排的，页面照这个顺序渲。数字会变，排序规则不该跟着变。

## 一个人都没有的时候，读到什么

新建一位从来没有计量记录的探针用户，带上他的会话读接口：

```
[对账·空表] {"状态":200,"总":0,"分组长度":0,"页面那一位":"0","页面状态":200}
```

`200` 加一个 `0`，不是 `404`，也不是 `500`，页面那一位也不是 `-`。这一条是"会员第一次进来看见什么"的真实形状：空是一个合法答案，而把空当成错误（`group by` 一行都没返回时去读 `rows[0]`）是最容易写错的地方。

紧跟着的是边界那一半：

```
[对账·边界] {"全表行数":1,"我这侧状态":200,"我这侧总数":0}
```

同一时刻全表有 1 行，我这侧读到 0。要是把 `where user_id` 那一位去掉，这一条立刻变成"我的数 = 别人的数"。

## 让这条边界红一次

把服务层那句过滤换成恒真条件（只改那一行，跑完改回），同一趟判据里两条一起红：

```
Error: expect(received).toBe(expected)
Expected: 0
Received: 1
Error: `where user_id` 那一位漏了：别人的行会算到我头上
```

红的是"空表那一位"与"边界那一档"——正好是这一站唯一无法用别的手段证明的两件事。改回之后 4 passed。

而三段链那一档（第一个表格）在这种变异下**没红**：全表只有一位用户有行，把过滤去掉，那位用户读到的数还是 1。这条很值得记住：**数据只有一个人的时候，"隔离"这件事是量不出来的**。要让隔离成为证据，表里得有两个人的行（这就是下一站要处理的写入授权问题）。

## 两处被读数纠正的断言

第一条：页面状态栏那一位，我按记忆写成 `ok`，实际读到 `success`：

```
Error: 页面状态栏不是服务端渲出来的成功形状
Expected: "ok"   Received: "success"
```

取数的状态栏有四个取值，接口回的是 HTTP 状态码——两套词，不能互相代。改成钉 `success`，并且这一位读的是响应体里的 HTML（不是水合后的 DOM）：官方讲数据获取那一节写明负载是给客户端**避免重复取数**用的，也就是说水合之后页面上那个数可能来自负载而不是这一趟接口；要读"服务端渲出来的那一份"，就得读 HTML 文本。

第二条：最后一个用户是自己建、自己删的，会话也是。第一版让后一档沿用了前一档的会话号，结果读到 `401`——前一档的收尾已经把它删了。改成**每条自己建一条自己的会话、`finally` 里删掉**，四档才互不依赖。

## 一条不属于本站的红

这一站第一次跑全量时红了一条，而且是很眼熟的那条：

```
1) test/e2e/landing.spec.ts:179 › 链接一进视口就预取：品牌链指向预渲染的首页，载荷文件在点击之前就被取走
Error: expect(received).toBeGreaterThan(expected)  Expected: > 0  Received: 0
```

紧接着重跑一次全量是 **252 passed／61 skipped／0 failed (56.1s)**，同一条判据的读数里载荷文件又被取回来了。它属于"预取什么时候发"这一类时间敏感的判据，与本线的路由规则无关（本线那两页与 `/` 的预取路径不同）。这一回终于拿到了它的名字——之前有过一次同样的间歇红，当时没留下用例名。现在记进未闭合，处理方式不是把等待调长到它不响，而是把"预取该由什么触发"这件事单独量一次。

## 容易读错的几处

| 症状 | 实际是什么 | 该怎么办 |
| --- | --- | --- |
| 接口和页面都显示 1，就宣布对账通过 | 库里可能压根不是 1，两边读的是同一份缓存 | 三段各读一次，并排放 |
| 空表时接口 500 | 聚合那层直接取了不存在的第一行 | 空是合法值：`total: 0`、`kinds: []` |
| 只有一个用户时"隔离"测不出来 | 去掉过滤也读得到同一个数 | 想让边界成为证据，表里要有两个人的行 |
| 后一档沿用前一档的会话号 | 前一档收尾时删了它 | 探针行每条自建自删 |
| 页面数字与水合后不一致就被改 | 负载会替客户端省一次请求 | 要比服务端那一份就读响应体，别读 DOM |

## 这一站的三条结论

三段链在同一时刻对上：库里 `1` ＝ 接口 `total: 1` ＝ 页面 `1`，会员区那句"数字与库里一致"到这一站有了真连库的读数。
空表与边界是两条独立判据：前者防"没有数据时把空写成错误"，后者防"把别人的行算成我的"；后者要靠一次恒真变异才证明自己拦得住。
数据只有一位用户时隔离测不出来——这一句直接决定下一站要不要谈写入授权。

下一站不新增数字来源，而是反过来查"页面上那些位是不是同一个来源"：面板那一块与顶部那一栏读的是同一次取数还是两笔。
