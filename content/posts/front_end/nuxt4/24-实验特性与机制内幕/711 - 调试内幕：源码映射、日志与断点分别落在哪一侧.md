## 第一步是把问题归侧

三侧的表现长得很不一样，归错了会白找很久：

| 症状 | 落在哪一侧 | 该用的手段 |
| --- | --- | --- |
| 界面不对、事件没响应、水合告警 | 浏览器 | Chrome 调试（VS Code 的 `client: chrome` 或浏览器 DevTools） |
| 接口返回不对、SSR 报错、服务端日志缺失 | 服务端运行时 | `nuxt dev --inspect`，或 `server: nuxt` 那项 IDE 配置 |
| 配置没生效、注册的东西不见了、类型没生成 | 构建期进程 | 模块与钩子那一侧的观察手段（本系列已在模块排错那篇逐项给过） |

值得强调的是第三行与第二行的区别：**同一段 Node 代码，模块的 `setup` 与你的接口 handler 不是一回事**——前者只在构建时跑一次，后者每个请求都跑。

## sourcemaps：默认值按两侧分开算

官方那句原文：sourcemaps **对服务端构建默认启用，对客户端构建则在开发模式启用**；你可以在配置里更精确地开启。

配置有两种写法：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  // or sourcemap: true
  sourcemap: true,
})
```

或者按侧分开：

```ts
export default defineNuxtConfig({
  sourcemap: {
    server: true,
    client: true,
  },
})
```

实际含义：**在生产构建里看客户端的报错栈，默认是没有映射的**，要自己开 `client`。这一条与错误处理那一侧直接相关——线上错误上报里如果全是压缩后的位置，先检查这里，而不是先怀疑上报工具。

## `--inspect`：只管那个 Node 进程

命令是一行：

```bash
nuxt dev --inspect
```

文档说明：这会让 Nuxt 以开发模式启动并且调试器处于激活状态；一切正常时，**Chrome DevTools 上会出现一个 Node.js 图标，你可以附加过去**。

那条重要提示划定了它的物理边界：

> Node.js 与 Chrome 这两个进程必须运行在同一平台。**在 Docker 里这不工作。**

这一页没有给容器场景的替代做法，也没提 `nuxt build` 侧有没有对应的 inspect 参数。所以容器化开发时，现实的选择是把 dev 跑在宿主机上，或者退回用日志与 IDE 配置。

## 两份 IDE 配置，都把两侧拆成两项

VS Code 那份配置的结构值得记住，因为它体现了"分侧"这件事：**两个 `configurations` 加一个 `compounds`**。

- `client: chrome`：`type` 是 `chrome`、`request` 是 `launch`、`url` 是 `http://localhost:3000`，而 `webRoot` 指向 `${workspaceFolder}/app`，文档在旁边写了注释：**这一项应当指向你的 `srcDir`，而 `srcDir` 默认是 `app`**。也就是说改过 `srcDir` 却没改这里，客户端断点就会对不上源文件。页面另外提醒：你可能需要用自己浏览器的路径更新这份配置。
- `server: nuxt`：`type` 是 `node`，`outputCapture` 是 `"std"`，`program` 指向 `${workspaceFolder}/node_modules/nuxt/bin/nuxt.mjs`，`args` 是 `["dev"]`。**这一项启动的就是那个既跑模块 setup、又跑服务端渲染的 Node 进程**，所以构建期与服务端两侧的问题都可以从这里下断点。
- `fullstack: nuxt`：一个 compound，把上面两项一起起。

还有一个常被需要的选项：如果你想用自己平时装的浏览器扩展，就在这份配置的 chrome 那项里加上 `"userDataDir": false`。

JetBrains 那份（IntelliJ IDEA、WebStorm、PhpStorm 通用）是两步：在项目根目录新建 `nuxt.run.xml`，然后把给定内容粘进去。文件里同样是三段——`client: chrome` 用 `JavascriptDebugType`、`uri` 是 `http://localhost:3000` 并带 `useFirstLineBreakpoints="true"`；`server: nuxt` 用 `NodeJSConfigurationType`、`application-parameters="dev"`、`path-to-js-file` 指到 `$PROJECT_DIR$/node_modules/nuxt/bin/nuxt.mjs`、`working-dir` 是 `$PROJECT_DIR$`；`fullstack: nuxt` 用 `CompoundRunConfigurationType` 把前两项列进 `toRun`。

页面最后一节是 Other IDEs：**如果你用别的 IDE 并愿意贡献示例配置，可以开一个 PR**——换句话说这一页只维护这两份。

## 三条容易踩的错位

1. **把客户端问题拿到服务端去断**。表现是断点永远不命中。`client: chrome` 与 `server: nuxt` 是两个不同的调试目标，需要两边同时看就用那个 compound。
2. **改了 `srcDir` 却没改 `webRoot`**。这时映射路径不对，断点会打在一个"看起来对但永不命中"的位置上。
3. **在生产环境里找源码位置**。客户端 sourcemap 默认只在 dev 开，生产要么改 `sourcemap.client`，要么接受压缩栈。

## 与错误处理的接合点

排"报了什么错"这一类问题，先看错误落在哪：服务端接口抛错走的是 h3 的错误通路（`createError` 带状态码），SSR 渲染错误会走 `app:error`，chunk 加载失败则是一个独立的通路（`emitRouteChunkError`，它有 `automatic`、`automatic-immediate`、`manual`、`false` 四种处置）。这三类各自的位置不同，用上面的归侧表先定位，再决定要不要动那几个实验开关。

## 一次排查的最短路径

- 判断侧：浏览器／服务端运行时／构建期。
- 服务端一侧优先 `--inspect`（同平台前提下），或 `server: nuxt` 配置。
- 浏览器一侧用 `client: chrome`，需要扩展就加 `userDataDir: false`。
- 要看生产栈就先打开对应侧的 sourcemap，再重新构建。
