## 官方自己写在页面上的三处免责

这三句决定了"能不能把它当稳定能力用"：

- 节首 note：这些特性是实验性的，**未来可能被移除或修改**。
- `externalVue` 一节的单独警告：这一特性**很可能在不久的将来被移除**——57 个里只有它被这样单独点名。
- `defaults` 一节的迁移预告：这些选项将来很可能被挪到 `app.config` 或 `app/` 目录。

还有一句是寿命声明：`routeTypedFetch` 那节的 note 写着**这个选项只在两套类型并存的期间存在，从 Nuxt 5 起生成的路由集是唯一来源、选项就没了**。

配合发布节奏那一页的承诺看：**主版本与次版本不应包含破坏性变更，除非改动落在明确标记为 experimental 的选项里**。这一节正是那个豁免区。

## 三档风险，按"要改多少已有代码"分

**高档：开了就要动别的地方**

| 开关 | 你必须要处理的事 |
| --- | --- |
| `ssrStreaming` | 渲染期间设置的 `setResponseStatus()`、`useResponseHeader()`、`useCookie()` 与 h3 的 `setHeader()` **会被丢弃**；`await` 之后注册的 head 标签变成客户端补丁，**没列进 `botRegex` 的爬虫与 `curl` 完全看不到**；`routeRules` 里的 `noScripts`/`cache`/`isr`/`swr`/`redirect`、`ssr: false`、预渲染路由、服务端 `navigateTo()` 都会让它自动退回；样式侧有 dev 与生产两类 FOUC |
| `viteEnvironmentApi` | **改变 Vite 插件被注册与配置的方式**，须按迁移章节改插件 |
| `routeTypedFetch` 配 `strictRouteTypes` | 手工增强 `ServerRoutes` 声明的路由**需要重写**；`params` 不再接受；开了 `strictRouteTypes` 后**请求 `public/` 里的文件会报错**；有 catch-all 页面时这个约束等于不存在 |
| `enforceModuleCompatibility` | 一个不兼容模块会让项目**加载失败**，CI 里表现为整条构建挂掉 |
| `typescriptPlugin` | 引入 `@dxup/nuxt` 这个外部模块，且要 `typescript` 依赖＋VS Code 用工作区版本 |
| `decorators` | 支持的是 TC39 提案而**不是** `experimentalDecorators`；要装 `@babel/plugin-proposal-decorators` 与 `@babel/plugin-syntax-jsx`；标准未定，之前仍可能改 |
| `buildCache` | 九个配置与锁文件一动就全量重建；**Nitro 永远重建**；只留 10 份 tarball |

**中档：不改代码，但会改变可观察行为**

- `payloadExtraction`：三态取值，且 **`ssr: false` 时被强制为 `false`**——这条常被当成"我的 `_payload.json` 怎么没了"的原因。
- `clientNodePlaceholder`：传给 `.client.vue` 的 `class`、`style` **不再出现在 SSR HTML 里**，要防布局位移得改用带 `#fallback` 槽的 `<ClientOnly>`。
- `prefetchPreloadTags`：默认关的理由就是代价——与 `prefetchOn: 'visibility'` 叠加会一次触发大量跨路由预取，转发出去的**图片请求不带 `Purpose: prefetch`，会算进图片 CDN 的配额、限流与统计**。
- `navigateToEarlyReturn`：成功导航之后 `defineExpose` 与后面注册的生命周期钩子**都不执行**。
- `sharedPrerenderData`：要求每个唯一 key 始终解析到同一份数据；不给 key 的动态页面写法不安全。
- `restoreState`：从 `sessionStorage` 恢复，**只在 Vue 挂载后应用，首屏可能闪**；自动生成的 `useState` key 可能跨构建不一致。
- `early404`：会破坏插件里 `router.addRoute()` 的用法（开启后 `useRouter` 的类型上**直接移除了 `addRoute`**）与把未知路径重定向到已有页面的中间件。
- `normalizePageNames`、`normalizeComponentNames`：组件名与路由名对齐之后，**按名字的 `<KeepAlive>` 与 DevTools 里的定位都会变**。
- `componentIslands`、`asyncContext`、`typedPages`、`scanPageMeta`：属于"能力开关"，但 `scanPageMeta` 一旦关掉，`extraPageMetaExtractionKeys` 与 `extractSerializablePageMeta` 同时失效。

**低档：局部、可逆、影响面小**

`navigationRepaint`、`headNext`、`cookieStore`、`localLayerAliases`、`templateRouteInjection`、`templateImportResolution`、`writeEarlyHints`、`serverPathFallback`、`lazyHydration`、`granularCachedData`、`purgeCachedData`、`renderJsonPayloads`、`parseErrorData`、`pendingWhenIdle`、`alwaysRunFetchOnKeyChange`。这一档的共同点是：出问题一般只需把值改回去，不需要动代码。

## 开一个之前：四步

1. **读完整节**，确认它的默认值属于哪一种句式。规整句式（`This flag is enabled by default`）只有 16 个，明确写"默认关"的 5 个，**剩下多数整节不声明**，所以"没写就是关"这个推断不成立。
2. **查联动**。会改写别的开关默认值的四处是：`future.compatibilityVersion`（一批开关跟着变）、`debug`（`debugModuleMutation`）、开发模式（`browserDevtoolsTiming`）、`appManifest`（`checkOutdatedBuildInterval`）、`ssr: false`（`payloadExtraction`）、`hashMode`（`serverPathFallback` 无效、`early404` 自动停用）、`scanPageMeta`（关掉使两项失效）。
3. **确定验证方式**。对流式与样式相关的项，文档明确要求**对着 `nuxt build && nuxt preview` 验证**，因为 dev 下的样式注入方式不同会误导你；对 bot 相关的项，要分别看匹配 `botRegex` 与不匹配的两类响应。
4. **写下回滚路径**：这一项是不是和别的项一起开的？能不能单独关掉？

## 想试下一个大版本，用总闸而不是逐个开

`future.compatibilityVersion: 5` 那句原话是：把 `compatibilityVersion` 设为 5 会**改变你整个 Nuxt 配置里的默认值**以选择加入 v5 行为。它一次带上的包括 `viteEnvironmentApi`、`extractSerializablePageMeta`、`clientNodePlaceholder`、`normalizePageNames`、`navigateToEarlyReturn`、`routeTypedFetch`、`watcher` 变 `'builder'`、`payloadExtraction` 变 `'client'`、`useState.resetOnClear` 变 `true`。

两种用法要分清：

- **整体试 v5**：只设 `compatibilityVersion`，让默认值一起变，这样测到的就是将来的形状。
- **只想提前用其中一项**：显式设那一个 `experimental` 键。文档对 `viteEnvironmentApi` 与 `routeTypedFetch` 都写明，**显式设置可以"无论兼容版本如何都选定这一边"**，也允许"先升到 5、之后再单独接"。

反过来做（一边 `compatibilityVersion: 5` 一边逐项手动关）会让配置读不出真实状态，属于最难排查的一种。

## 回滚的三步

关掉一个实验开关时，光改配置常常不够，因为构建类的项目会在生成目录里留下上一次的产物：

1. 把那个键改回去（或直接删掉这一行，让它回到默认）。
2. 涉及构建产物、模板或类型生成的项，**清掉构建目录**：`npx nuxt cleanup` 会删 `.nuxt`（或 `buildDir` 指定的位置）、`.output`、`dist`、`node_modules/.vite`、`node_modules/.cache` 这五处。**它不删 `node_modules`，也不删锁文件。**
3. 如果这一项需要额外依赖（`decorators` 的两个 Babel 包、`typescriptPlugin` 的 `@dxup/nuxt`、dev handler 场景里的 `h3@^1`、`@nuxt/kit` 版本下限），关掉之后**这些依赖可以留着不影响运行，但要从 `dependencies` 分清楚是谁引入的**——`@nuxt/kit` 那类版本要求属于例外：它是对象形态 `handler` 的前提，不随开关关闭而消失。

## 上线前的八项检查

- 这次上线一共开了几项，能不能一句话说清每项换来什么。
- 高档项是否都有单独可关的路径（不要两个高档项绑在同一次发布里）。
- 有没有依赖"文档没写默认值"就假设了行为的项。
- `botRegex` 是自己写的还是沿用默认？**设了就是替换默认，不是追加。**
- SEO 关键标签（canonical、社交 meta）是否仍在同步注册路径上。
- 响应头与状态码的设置是否都挪到了插件里，或者那条路由是否已关流式。
- 类型相关项（`routeTypedFetch`、`strictRouteTypes`）改过之后，`public/` 里文件的请求有没有改成带显式响应类型。
- 构建缓存与清理步骤在 CI 里是否可复现——`.nuxtrc`、`package.json` 与四种锁文件任何一处变化都会让缓存整体失效。
