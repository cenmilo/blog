## 这一节长什么样

写法只有一个：在 `nuxt.config.ts` 的 `experimental` 对象里给键赋值。文档给的形状是：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    appManifest: false,
  },
})
```

这一节和 `future` 节是分开的两处。`future.compatibilityVersion` 设成 `5` 或更高时，**有几个实验开关会自动打开**，页面里明确这么写的两处是 `extractSerializablePageMeta` 和 `viteEnvironmentApi`（后者那句原文是：当你把 `future.compatibilityVersion` 设为 `5`，这个特性默认启用；也可以显式开启来做测试）。

## 默认值有四种句式，别按一种读

57 个开关里，页面声明默认值的方式并不统一。四种句式各自的例子：

- **"This flag is enabled by default, but you can disable this feature"**——最规整的一种。`appManifest`、`externalVue`、`renderJsonPayloads`、`parseErrorData`、`localLayerAliases`、`cookieStore`、`navigationRepaint`、`lazyHydration`、`templateImportResolution`、`templateRouteInjection`、`purgeCachedData`、`granularCachedData`、`headNext`、`serverPathFallback`、`navigateToEarlyReturn` 都是这句式。
- **"This flag is disabled by default, but you can enable it"**——`alwaysRunFetchOnKeyChange`、`enforceModuleCompatibility`、`buildCache`、`typescriptPlugin` 四个。
- **把默认值挂在别的设置上**：`debugModuleMutation` 是"在 `debug` 模式开启时默认启用"；`checkOutdatedBuildInterval` 是"当 `experimental.appManifest` 为 `false` 时禁用"；`extractSerializablePageMeta` 与 `viteEnvironmentApi` 挂在 `compatibilityVersion` 上。
- **用别的句子描述默认行为**：`emitRouteChunkError` 写的是"默认行为是在导航到新路由、chunk 加载失败时重新加载新路由"；`pendingWhenIdle` 写的是"当它是 `false`（**默认值**）时……"；`watcher` 写的是"Nuxt 默认使用 `chokidar-granular`"；`entryImportMap` 写的是"默认情况下 Nuxt 用 import map 来提升 chunk 稳定性"。

**还有相当一部分开关整节没有声明默认值**，比如 `asyncContext`、`typedPages`、`componentIslands`、`viewTransition`、`ssrStreaming`、`clientFallback`、`crossOriginPrefetch`、`writeEarlyHints`、`scanPageMeta`、`decorators`、`defaults`、`routeTypedFetch`、`strictRouteTypes` 等，只给了开启的示例代码。**这一类不能靠"文档没写就是关着"来判断**，要确认只能自己打印出解析后的配置去看。页面没有给出查询当前生效值的办法。

## 那句风险声明配的是版本承诺

note 那句很短："这些特性是实验性的，未来可能被移除或修改。"

它的分量要放到发布节奏那一节才能读出来。那一节承诺：从 2023 年 1 月起按 semver 走、目标一年一个大版本、patch 大约每周、minor 大约每月，而**这些版本不应该包含破坏性变更，除非是在明确标记为 `experimental` 的选项范围内**。

合起来读就是一句话：**你放在 `experimental` 里的东西，官方保留了随时改它的权利**。这不是修辞——它直接决定了实验特性能不能进生产。页面没有给出"哪些实验特性已经准备好上生产"的判断标准。

## 开关之间是有依赖的

两处依赖关系写在页面上，动之前必须知道：

- `strictRouteTypes` 那一节开头就写着"需要 `routeTypedFetch`"，因为它要的是后者给出的类型来源。
- `checkOutdatedBuildInterval` 在 `experimental.appManifest` 为 `false` 时**整个失效**——前者管的是检查新构建的时间间隔，而这件事只在有 app manifest 时存在。

还有一处是行为联动而不是依赖：`stripNeverHydratedData` 描述的是"对组件里用 `hydrate-never` 懒水合的 `useAsyncData`/`useFetch` 调用默认施加 `serialize: false`"，它同时牵动水合策略与 payload 两个区域。

## 三个"默认关但一改就动到全局"的

- `enforceModuleCompatibility`：原文问句是"Nuxt 是否应该在某个 Nuxt 模块不兼容时抛错并**加载失败**"。默认关闭，开了以后一个不兼容模块就会把整条启动流程拦下来。
- `buildCache`：按配置与源文件的哈希缓存构建产物，而且**只对 `srcDir` 与 `serverDir` 里 Vue/Nitro 那部分源码生效**；这一项还牵动"九个文件一动就全量重建"那组行为。
- `typescriptPlugin`：开启的方式是引入 `@dxup/nuxt` 这个模块，页面称它提供"增强的 TypeScript 开发体验与更好的 DX"。它不是纯粹的内部开关，而是把一个外部模块带进项目。

`defaults` 那一节也值得单独看：它用来给核心组件与组合式函数指定默认选项，同时挂着**一句明确的迁移预告**——"这些选项未来很可能被挪到别处，例如 `app.config` 或 `app/` 目录"。这是这一节上少数直接写了"位置会变"的开关。

## 动开关之前的三步

1. 读完那一整节，判断它属于哪一种默认值句式；句式是"由别的设置决定"时，先把那个设置确定下来。
2. 查它是否被联动：`appManifest`、`compatibilityVersion`、`debug` 这三处都会改写别的开关状态。
3. 想好回滚：实验特性可以随时被改动或移除，所以任何一个开关都要能单独关掉而不留残留。那七个主题分组接下来的几篇会逐个给具体开关的边界与代价，最后有一篇把这一节整理成可执行的操作手册。
