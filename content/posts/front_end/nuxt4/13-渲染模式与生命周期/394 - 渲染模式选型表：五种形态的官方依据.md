前面 30 篇把渲染模式一块块拆开了。这一篇把它拼回一张可查的表——每种形态怎么开、官方说适合什么、有什么官方明确写的限制。做技术选型时直接对着这张表核。

## 五种形态一览

| 形态 | 怎么开 | 官方点名的适用场景 | 关键限制 |
| --- | --- | --- | --- |
| Universal（SSR+水合） | 默认；`app.ssr` / `ssr` 相关配置 | 内容型站：博客、营销站、作品集、电商、市场 | 两端 API 差异带来的开发约束；要一台一直在跑的服务器 |
| Client-Side（SPA） | `ssr: false` | SaaS、后台、在线游戏（不需索引或高频回访） | 首屏等 JS；SEO 慢；`#__nuxt` 空；`payloadExtraction` 被强制 `false` |
| Hybrid | `routeRules` 按路由配 | 一个站里既有静态内容页又有动态区（内容站 + 后台） | **`nuxt generate` 下不可用** |
| Prerender（SSG） | `nuxt generate` ≈ `nitro.static: true` ≈ `nuxt build --prerender` | 纯静态托管、可提前生成的内容页 | 输出**不含服务器**，server 端点不可用；数据陈旧到下次重建 |
| Edge（ESR） | Nitro preset（Cloudflare Pages / `NITRO_PRESET=vercel-edge` / `netlify-edge`） | 要低延迟、离用户近 | 官方定性"更像部署目标不是独立渲染模式"；可叠加 hybrid |

## 逐条的依据句

**Universal 默认与一行切换**：

> By default, Nuxt uses **universal rendering** to provide better user experience, performance and to optimize search engine indexing, but you can switch rendering modes in one line of configuration.

**Universal 适合内容站**：

> Universal rendering is very versatile and can fit almost any use case, and is especially appropriate for any content-oriented websites: **blogs, marketing websites, portfolios, e-commerce sites, and marketplaces.**

**CSR 适合重交互应用**：

> Client-side rendering is a good choice for heavily interactive **web applications** that don't need indexing or whose users visit frequently ... such as **SaaS, back-office applications, or online games.**

**ESR 是部署目标**：

> Note that ESR is more a deployment target than an actual rendering mode.

## Hybrid 的九个开关

Hybrid 的实现载体是 `routeRules`，官方列了九项属性（367 逐条讲过）：`redirect`、`ssr`、`cors`、`headers`、`swr`、`isr`、`prerender`、`noScripts`、`appMiddleware`。选形态时常用的是 `ssr: false`（这块纯客户端）、`prerender: true`（构建期生成）、`swr`/`isr`（按需生成 + 缓存 TTL，isr 还能进 CDN）。

注意官方清单里**没有 `proxy`**，别按旧教程把它当这一页记载的属性。

## 三条必须记住的官方硬限制

选型时最容易上线才发现的三条：

**① hybrid 不能配 `nuxt generate`：**

> Note that Hybrid Rendering is not available when using [`nuxt generate`].

`nuxt generate` 是纯静态、没有运行时服务器，而 hybrid 靠服务端注册中间件与缓存层。

**② 预渲染输出里没有服务器，server 端点用不了：**

> If you prerender your app with the `nuxt generate` or `nuxt build --prerender` commands, then you will not be able to use any server endpoints as no server will be included in your output folder. If you need server functionality, use `nuxt build` instead.

要 `server/api` 那类能力，就走 `nuxt build`（产物带 Nitro 服务器）。这条和 ① 同因。

**③ `ssr: false` 会连带关掉 payload 抽取：**

`experimental.payloadExtraction` 的默认是 `true`（`compatibilityVersion: 5` 下 `'client'`），但 **`ssr: false` 时强制 `false`**。没有服务端渲染就没有可转发的服务端数据，抽取自然没意义。

## 再叠加的两条体验开关

选完形态，还有几个正交的开关会影响体验与体积，都在 365-394 讲过：

- **`noScripts`（路由级或 `features.noScripts`）**：让命中的页发纯 HTML+CSS、**完全不水合**（无 `@click`、`<NuxtLink>` 不预取、无客户端导航）。适合内容路由，代价是那页没有任何交互。
- **延迟水合（`defineLazyHydrationComponent`）**：保留脚本、把水合推到 visible/idle/interaction/mediaQuery/if/time/never 之一，削首屏 JS 成本。
- **`ssrStreaming`**：改的是 TTFB（先发壳再流 body）；`navigationRepaint` 改的是 INP。两者和形态选择正交。

官方那份"以静态为主"的配方就是把这几件叠起来：`prerender` + `noScripts` + `.server.vue` 岛屿 + 延迟水合（381）。

## 自查

- 五形态：universal(默认)/client-side(`ssr:false`)/hybrid(routeRules)/prerender(generate)/edge(Nitro preset，官方称部署目标)。
- 官方点名场景：内容站→universal；重交互、不需索引→CSR。
- 三条硬限制：hybrid 不支持 `nuxt generate`；预渲染输出无服务器→server 端点不可用（要后端就 `nuxt build`）；`ssr:false` 强制 `payloadExtraction:false`。
- routeRules 九项属性里没有 `proxy`。
- 形态之外还有正交开关：`noScripts`（完全不水合）、延迟水合、`ssrStreaming`(TTFB)、`navigationRepaint`(INP)。
