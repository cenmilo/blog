组件里放个每秒跳一次的倒计时，很多人顺手这么写：

```vue
<script setup>
const now = ref(Date.now())
setInterval(() => { now.value = Date.now() }, 1000)   // 建在 setup 顶层
</script>
```

本地跑得好好的。但 Nuxt 默认 universal，这个 `setInterval` 在**服务端那一趟也被建了**，却没有任何东西把它拆掉——于是服务器上的定时器一个个留着不走。这就是官方在生命周期那一节专门用 `::important` 拦住的一类写法。

## 官方原话

同一步（服务端七步的 Page and components）后的 `::important`：

> You should avoid code that produces side effects that need cleanup in root scope of `<script setup>`. An example of such side effects is setting up timers with `setInterval`. In client-side only code we may setup a timer and then tear it down in `onBeforeUnmount` or `onUnmounted`. However, because the unmount hooks will never be called during SSR, the timers will stay around forever. To avoid this, move your side-effect code into `onMounted` instead.

拆成三步：

1. **要避免的模式**：在 `<script setup>` 根作用域写"需要清理的副作用"。文档举的例子就是 `setInterval`。
2. **纯客户端的习惯**：setup 时建定时器，`onBeforeUnmount` 或 `onUnmounted` 里拆掉。
3. **在 SSR 下为什么不成立**：**卸载钩子在服务端永远不会被调用**（承接 369——那些钩子 SSR 期间根本不跑），所以定时器"会一直留着"。
4. **解法**：把副作用代码挪进 `onMounted`。

## 为什么偏偏是 `onMounted`

这不是随便挑一个钩子。369 讲的是 "`onMounted` 在服务端不执行"——这里正是用它这面：`onMounted` **只在浏览器跑**，而浏览器的卸载是会正常触发的。副作用建在 `onMounted` 里、拆在 `onBeforeUnmount`/`onUnmounted` 里，两者都只发生在客户端这一半，配对完整，就不存在"服务端建了没人拆"。

## 改成不泄漏的写法

```vue
<script setup>
import { onMounted, onBeforeUnmount, ref } from 'vue'

const now = ref(Date.now())
let timer

onMounted(() => {
  timer = setInterval(() => { now.value = Date.now() }, 1000)
})

onBeforeUnmount(() => {
  clearInterval(timer)   // 客户端才有这一步，能真正拆掉
})
</script>
```

关键差别：`setInterval` 从 setup 顶层挪进了 `onMounted`。服务端那一趟 `onMounted` 不触发，就不会在服务端留下定时器。

## 其它同类副作用

文档只点名了 `setInterval`。按同一条"需要清理的副作用别放根作用域"的道理，其它要成对清理的东西同理——`addEventListener`、订阅、WebSocket 连接这类。**注意这是我把 `::important` 的规则外推到同类情形，官方原句只以 `setInterval` 举例、并未逐一列举哪些 API 算副作用**；判断标准就用那句"produces side effects that need cleanup"：凡是要在卸载时清理的，都别放 `<script setup>` 根作用域，放 `onMounted` 建、放卸载钩子拆。

官方在这条 `::important` 下面还挂了一个视频 callout：Daniel Roe 讲的 "Server Rendering and Global State"——根作用域副作用之外，服务端"全局态"（每个请求共用一份模块状态）也是同一类隐患，那是另一条线。

## 自查

- 别在 `<script setup>` 根作用域写"要清理的副作用"（官方以 `setInterval` 举例）。
- 根因：SSR 期间卸载钩子永不执行，服务端建的定时器/监听器没人拆。
- 解法：副作用建在 `onMounted`（只客户端跑）、拆在 `onBeforeUnmount`/`onUnmounted`，配对都发生在客户端。
- 其它要成对清理的副作用按同一标准归类；文档未逐一列举，判据是"需要 cleanup"。
