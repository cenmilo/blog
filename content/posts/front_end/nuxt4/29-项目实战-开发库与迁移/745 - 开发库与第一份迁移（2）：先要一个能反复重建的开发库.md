## 一条真查询才作数

上一站留了一句：`useDb()` 返回客户端不等于连上了库。这一站就从这条开始，把"库到底行不行"做成能重复跑的判断。

```text
node scripts/db-probe.mjs "select count(*)::int as n from users"
连接串来自 NUXT_DATABASE_URL
[{"command":"SELECT","rowCount":1,"rows":[{"n":33}]}]
```

三行都有用：第一行是命令，第二行说这份连接串是从哪个名字来的，第三行才是"连上了、库里有这张表、能读"。少了第二行那种信息，就会出现工具说库是好的、接口那边还是 500 的怪事——这站的最后一节就是补这个。

## 三个词

**实例／库／schema**：一台 Postgres 上是实例，实例里分库，库里再分 schema。这张站的表都在 `public` 下，而 drizzle-kit 的记账在另一个 schema `drizzle` 里——分层是刻意的，别把记账行当成业务数据去清。

**连接超时**：`connectionTimeoutMillis`。它决定"连不上"这件事是几毫秒回你，还是让你干等到超时——两者是完全不同的故障。

**记账表**：`drizzle.__drizzle_migrations`。每一行是一份迁移的哈希与时间戳，`npm run db:migrate` 靠它决定"这份跑过了，别再跑"。

## 六种连法，六份读数

改连接串里的某一位，别的都保持原样（口令、库名、主机、端口各改一次，值不进任何文件）：

| 怎么连 | 回什么 | 用时 |
| --- | --- | --- |
| 原样 | 查询成功 rows=1 | 1526ms |
| 口令换成假的 | `DatabaseError` code=`28P01`，消息是 password authentication failed | 1461ms |
| 库名换成不存在的 | `DatabaseError` code=`3D000`，database does not exist | 1312ms |
| 主机换成解析不到的名 | code=`ENOTFOUND`，syscall=`getaddrinfo` | 11ms |
| 主机指回 `127.0.0.1:5432`（这台机器没起服务） | code=`ECONNREFUSED`，syscall=`connect` | 1ms |
| 端口换成一个没人听的号 | **没有 code**，`Connection terminated due to connection timeout` | 8008ms |

三条判读经验：

- **时间手感能分诊**。名字解析失败与"拒绝连接"是毫秒级——本地就答完了；认证失败与"库不存在"要等一个来回（一千多毫秒），因为包真的到了服务器；而**端口被防火墙丢包的那一种只会超时**，一点错误码都不给。看到"卡了八秒"就该怀疑最后一类，别按"没人听"去查。
- `28P01` 与 `3D000` 是两个不同的锅：口令错要改凭据，库名错要改串里那一段路径，别互相试。
- `ENOTFOUND` 通常是自己把主机名写错（少了一段、多了一段），和库本身无关。

顺手再钉一次"建池不等于连上"：

```text
只建池不查询 → 不抛错，totalCount=0、waiting=0
```

池子一个连接都没开，也不报错。所以任何"库健康检查"都必须带一次真查询。

## 连上了，怎么判断"就是仓库这套结构"

对着库做四条只读查询，再和仓库里的文件比：

```text
public 下的表 6 张：audit_logs, login_tokens, meter_events, ping, sessions, users
已装的扩展：citext, pg_stat_statements, pgcrypto, plpgsql, supabase_vault, uuid-ossp
枚举类型 13 个（跨所有能看见的 schema）
drizzle.__drizzle_migrations 记账 4 行
```

表这一项逐一对得上：`db/tables/` 下五个文件声明 `audit_logs`、`login_tokens`、`meter_events`、`sessions`、`users`，`db/schema.ts` 还带一张 `ping`，一共 6 张。扩展里 `citext` 与 `pgcrypto` 在位——这两行是**手工补**在 `0000_baseline.sql` 开头的，因为生成器只管表、列、索引：

```sql [db/migrations/0000_baseline.sql 的开头]
create extension if not exists citext;
create extension if not exists pgcrypto;

CREATE TABLE "ping" (
	"id" serial PRIMARY KEY NOT NULL,
	"note" text NOT NULL,
	"created_at" timestamp with time zone DEFAULT now() NOT NULL
);
```

枚举那 13 个要打折看：仓库只造了 `user_role` 一个（取值 `free`、`member`、`admin`），剩下十二个属于托管实例自己的 schema。`pg_type` 不按 namespace 过滤就会把别人的东西数进自己账上——这条判据必须写清范围。

## 对账的硬证据：时间戳与哈希都能逐行咬合

`db/migrations/meta/_journal.json` 记着 4 条，`when` 是毫秒时间戳：

```text
idx=0 tag=0000_baseline        when=1791912513899
idx=1 tag=0001_core_tables     when=1791965717036
idx=2 tag=0002_previous_maddog when=1792065286115
idx=3 tag=0003_legal_rattler   when=1792204845185
```

库里的记账表同一顺序的 `created_at` 是 `1791912513899`、`1791965717036`、`1792065286115`、`1792204845185`——四个数字一模一样。再对第二层：把每份 `.sql` 的原样字节做 sha256，取前 12 位。

```text
0000_baseline.sql        文件 sha256 前 12 位=6153a23bc13b  记账=6153a23bc13b  对上
0001_core_tables.sql     …=769be43ce241  记账=769be43ce241  对上
0002_previous_maddog.sql …=30ceae56796b  记账=30ceae56796b  对上
0003_legal_rattler.sql   …=cf7ba90d4e2b  记账=cf7ba90d4e2b  对上
```

四份全对上，而且 `0000` 那一份**把首尾空白去掉就对不上**——记账的哈希钉的是文件的字节。所以"迁移文件一旦提交就不要再改"不是洁癖：动一个空格、加一行注释、少一个行尾换行，`hash` 就变。至于变了之后 `migrate` 会怎么处理，第 5 步从包里的判据给了答案（提示：它不比这个哈希）。

## 反复重建的三条路，各自代价

1. **在一个空实例上跑 `npm run db:migrate`**。判据是两条：记账表出现 4 行，`public` 出现 6 张表。这条路是唯一"从零到能用"的正路。
2. **拿单份 `.sql` 去空库重放**。仓库里那五条硬约定写清楚了幂等边界：`0000` 那 3 句里只有两句 `create extension if not exists` 可重放，`CREATE TABLE "ping"` 第二遍就撞 `already exists`；`0001` 更早撞——第 3 句是 `CREATE TYPE`，而 PostgreSQL 的 `CREATE TYPE` 与 `ADD CONSTRAINT` 语法里根本没有 `IF NOT EXISTS`。**真正让跑过的不再跑的是记账表，不是 SQL 自己幂等**。
3. **只跑 `npm run db:generate` 就当结构没问题**。 schema 没改时它回 `No schema changes, nothing to migrate`；改了 schema 但没跑 `migrate`，库和文件就已经分叉了——对账要看上一节那两个数字，不是看命令有没有报错。

## 没有库的时候，用例怎么办

这个仓库的端到端用例里，需要库的那条是这么写的：

```ts [test/e2e/async-data-count.spec.ts]
test.skip(DATABASE_URL === '', '需要配了 NUXT_DATABASE_URL 的产物实例（见文件头那行命令）')
```

不带库跑一趟的读数：

```text
npm run test:e2e -- async-data-count
  -  1 test\e2e\async-data-count.spec.ts:20:1 › 三种进入方式各跑一次，数浏览器真的发了几趟 /api/console/metrics
  1 skipped        退出码 0
```

**跳过不是通过**。退出码 0 只说明这条没参加判决——所以带库那一趟要另外跑（`NUXT_E2E_DB=1`），两条读数分开记。为什么要把开关做成显式的：构建后的服务不读 `.env`（上一站那条），如果在配置里无条件把连接串塞进测试进程，那条"形状对但没配库 ⇒ 回 503"的断言就会悄悄变成另一回事——绿灯换成另一个意思，比红灯更难查。

讲测试那一节给的分层要求也是同一立场：把需要 Nuxt 运行时的用例与端到端用例分开跑，测试才稳定。

还有一条同名不同事的坑：这台机器上 `.env` 的四个键都非空（只说长度：两条连接串各 113、会话密钥 48、站点地址 21），所以 `db-probe` 那行来源打的是 `NUXT_DATABASE_URL`；而**构建后的服务在同一份 `.env` 面前看到的还是空串**（上一站 A 趟的读数）。工具与应用读的是两套东西，这正是这一站开头那条"来源行"存在的理由。

## 本轮在仓库里补的一处

`scripts/db-probe.mjs` 原来只从进程环境里取串，取不到就去连一个默认地址，报的错误和库本身无关；而且它两个名字都认（`NUXT_DATABASE_URL` 优先，兜到 `DATABASE_URL`），应用侧却只认后者的覆盖名。补两件事：没有 env 变量时自己读一次项目根的 `.env`（和 drizzle-kit 命令行同一条路径），并打印用的是哪一个名字。

三条读数：有库时 → 来源行＋`rowCount:1`；不给 SQL → 用法行、退出码 2；表名不存在 → `{"error":{"message":"relation \"no_such_table_probe\" does not exist","code":"42P01","position":"15"}}`、退出码 1。`npm run lint` 退出码 0（仍只有那条 `vue/no-v-html` 的 warning）。

## 出问题对照

| 症状 | 读数里的线索 | 怎么办 |
| --- | --- | --- |
| 命令行能连，接口报 500 | 工具打的是 `DATABASE_URL`，应用要 `NUXT_DATABASE_URL` | 两位都填；看工具打的那行来源 |
| 一上去就 ENOTFOUND，11ms 回 | syscall 是 `getaddrinfo` | 主机名写错了，和库无关 |
| 立刻 ECONNREFUSED | syscall 是 `connect`，指向本机端口 | 服务没起，或端口映射不对 |
| 干等到超时、没有错误码 | 用时接近 `connectionTimeoutMillis` | 查防火墙／安全组，别查口令 |
| 认证失败但凭据看着没错 | code=`28P01` | 用户名与口令的组合，或该用户没这个库的权限 |
| 库连上了却查不到表 | code=`3D000` 或 `42P01` | 前者是库名错，后者是迁移还没跑 |
| 改了旧迁移文件却没任何反应 | 记账 hash 与文件 sha256 不再相等，但 migrate 不看 hash | 只追加新迁移；改过的要按 hash 重新对账（判据见第 5 步） |

## 自己跑一遍

1. `node scripts/db-probe.mjs "select 1 as one"`——这条通了才谈得上别的。
2. 把串里的端口换成一个不存在的号，感受一次"没有 code 的超时"；再换成 `127.0.0.1:5432`（本机没起服务时）感受一次 1ms 的 `ECONNREFUSED`。
3. 跑一次只读对账：数 `public` 的表、数 `drizzle.__drizzle_migrations` 的行，和 `db/migrations/meta/_journal.json` 的条目数比。
4. 对每份 `.sql` 算一次 sha256，前 12 位与记账 hash 比——四份全等，才叫"文件与库一致"。
5. 不带库跑一趟需要库的那条用例，确认它是 `skipped` 而不是通过；再带库跑一趟，把两条读数分开记。
