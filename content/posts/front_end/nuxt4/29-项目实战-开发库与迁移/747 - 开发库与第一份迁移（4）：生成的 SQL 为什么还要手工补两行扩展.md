## 生成物里夹着人写的行

`drizzle-kit` 只认表、列、索引、外键这四类东西，Postgres 扩展不在它的词汇里。所以那两行必须人来补，而且顺序不能动：

```sql [0000 与 0001 的开头，一字未改]
create extension if not exists citext;
create extension if not exists pgcrypto;
```

问题是：补在哪儿才算补对？这一站先把它数清楚，再做一个能说明"这份依赖没人记账"的实验。

## 三个词

**扩展**：Postgres 的插件。装了 `citext` 才有"大小写不敏感的文本"这个列类型，装了 `pgcrypto` 才有 `gen_random_uuid()` 这个函数。

**`--> statement-breakpoint`**：生成器插在语句之间的分句标记。它只出现在自己写的那些语句之间——手工补的行不参与。

**隐式依赖**：新迁移里用了 `"citext"` 这个类型名，但它并不创建这个类型，靠的是更早某份文件里那两行。这层依赖在迁移文件里没有任何地方写着。

## 先把四份文件数一遍

本轮对着 `db/migrations/` 逐行数出来的：

| 文件 | 手工扩展语句 | `--> statement-breakpoint` | 生成语句数 |
| --- | --- | --- | --- |
| `0000_baseline.sql` | 2 | 0 | 1 |
| `0001_core_tables.sql` | 2 | 4 | 5 |
| `0002_previous_maddog.sql` | 0 | 1 | 2 |
| `0003_legal_rattler.sql` | 0 | 1 | 2 |

一条规律自己浮出来：**分句标记数 = 生成语句数 − 1**，而手工补的那两行不进这个计数（它们自带分号、写在最前面，生成器根本不认识它们）。`0001` 的五行生成语句是：`CREATE TYPE "user_role"`、三张 `CREATE TABLE`、一句 `ALTER TABLE ... ADD CONSTRAINT`。`0002`、`0003` 各两句：建表加外键。

`0001` 里 `grep` 还会多算一行——第 2 行是一条注释，内容正好提到 `create extension`。数语句要数行首，别数关键字命中次数。

## 那两行到底给了什么

一句只读查询就能看见扩展提供的行为差别：

```text
node scripts/db-probe.mjs "select ('abc'::citext = 'ABC'::citext) as citext_eq,
  ('abc'::text = 'ABC'::text) as text_eq, ... "

[{"command":"SELECT","rowCount":1,"rows":[{"citext_eq":true,"text_eq":false,"two_ext":2,"uuid_ok":true}]}]
```

`citext` 那一对相等、`text` 那一对不相等——这就是为什么 `users.email` 与 `login_tokens.email` 用 citext：唯一约束要按不区分大小写算，否则 `Abc@x.com` 与 `abc@x.com` 能注册两次。`two_ext: 2` 是 `citext` 与 `pgcrypto` 都在；`uuid_ok: true` 是 `gen_random_uuid()` 能调用，而 `uuid('id').defaultRandom()` 在包里就是 `default(sql\`gen_random_uuid()\`)`。

两行都有 `if not exists`，所以它们可重放；它们下面的每一条 DDL 都没有这个待遇。这就是为什么整条链能重放、单份文件不一定能。

## 生成器不会替你补：一次可撤销的实验

往 `login_tokens` 加一个可空的 citext 列：

```ts [db/tables/login-tokens.ts 临时加的一行]
probeEmail: citext('probe_email'),
```

跑 `npm run db:generate`，新文件全文只有一句：

```sql [db/migrations/0004_silly_moira_mactaggert.sql 全文]
ALTER TABLE "login_tokens" ADD COLUMN "probe_email" "citext";
```

**这份文件里 `create extension` 命中 0 次。**类型名被照写，但没有任何一行保证那个类型存在。也就是说：拿这份新迁移到一个空库上单独跑，会直接失败——缺的不是这一句，是前面那两行人补的。而这层依赖不出现在 `.sql` 里、不出现在 `meta/*_snapshot.json` 里，也不出现在 `_journal.json` 的那条 `{idx, when, tag, breakpoints}` 里。

失败长什么样，用一个只读查询取个同类形状：

```text
node scripts/db-probe.mjs "select 'x'::no_such_type_probe"
{"error":{"message":"type \"no_such_type_probe\" does not exist","code":"42704","position":"13"}}
```

`42704` 就是"这个类型不存在"的错误码，缺扩展时撞的是同一类（**真实缺扩展那一趟本轮没造**，要它得在一个没装 citext 的库上重放迁移，那属下一站）。

实验做完全部撤销：删掉那一行、删掉新生成的 `.sql` 与 `meta/0004_snapshot.json`、把 journal 里追加的那条改回去，然后核对还原：

```text
cmp journal 与开工前备份 → 逐字节相同
四份 .sql 的 sha256 前 12 位 → 6153a23bc13b / 769be43ce241 / 30ceae56796b / cf7ba90d4e2b
再跑一次 generate → No schema changes, nothing to migrate 😴
```

## 重跑生成会不会吃掉手写行

不会，这一条本轮又验了一次：连跑两次 `db:generate`（一次无改动、一次实验还原后），四份文件哈希与 journal 全部不变。生成器的动作只有两种——**没差异就什么都不写，有差异就新写一个文件**。它既不回头改旧文件，也不把别处的手写行复制进新文件。

由此得到三条能直接照做的规矩：

1. **判断一份迁移能不能单独跑，看它用到哪些类型和函数**：出现 `"citext"` 或 `gen_random_uuid()`，就必须在同一条链上更早的某份文件里有过那两行 `create extension`；否则这份文件只能跟在别人后面跑。
2. **别去改已经提交过的旧迁移**——包括"顺手删掉那两行注释"。前一站数过：库里的记账 hash 钉的是文件的原样字节，动一个空格就对不上。
3. **不需要扩展的时候别补**：`0002`、`0003` 里没有那两行是对的，`bigserial`、`jsonb`、`bigint` 都是内置类型，加外键也不需要任何扩展。往每份新文件开头机械地抄两行，是把幂等行当装饰。

## 顺手一条对照

同样在 `0002`、`0003` 这两份里，外键的删除策略是相反的：

```sql [两份文件里各一句]
ALTER TABLE "audit_logs" ADD CONSTRAINT "audit_logs_actor_users_id_fk" ... ON DELETE set null ...;
ALTER TABLE "meter_events" ADD CONSTRAINT "meter_events_user_id_users_id_fk" ... ON DELETE cascade ...;
```

审计行选 `set null`（`actor` 可空），删用户时留下"有人干过这件事"的痕迹；计量行选 `cascade`，账号没了他的计数跟着没，不留一个谁都对不上的匿名数字。这个选择不是随手写的，`db/tables/meter-events.ts` 的头几行注释把两边为什么相反讲得很清楚，读那两行比读 SQL 更省事。

## 出问题对照

| 症状 | 原因 | 怎么办 |
| --- | --- | --- |
| 新迁移在旧库上跑得好、在空库上报"类型 citext 不存在" | 生成器不管扩展，新文件里没有那两行 | 判据是整条链按序重放，不是单拿一份 |
| `grep -c create extension` 数出来比预期多一行 | 注释里也提到了这个关键字 | 只数行首的语句行 |
| 手工补的两行位置被挪到建表之后 | 顺序是硬要求 | 扩展行钉在最前面，类型与函数都在它之后才被用到 |
| 重跑 generate 后发现旧文件被改过 | 不可能（本轮两次核对哈希不变） | 若真变了，多半是你自己动了文件，按记账 hash 重新对账 |
| 每份新迁移开头都被抄上两行扩展 | 把幂等行当装饰 | 用到才需要，`0002`、`0003` 就没抄 |
| 改了旧迁移，migrate 却不报错也不重跑 | 判据只看库里最大 `created_at` 与 journal 的 `when`，hash 只是写进去的指纹 | 已提交的迁移只追加、不修改；对账要自己比 hash（下一站讲这套判据） |

## 自己跑一遍

1. 把 `db/migrations/*.sql` 四份各数一次：行首的 `create extension` 行数、`--> statement-breakpoint` 出现次数、以及语句总数，看是不是"标记数 = 生成语句数 − 1"。
2. 跑一次只读查询验扩展给的行为：`citext` 相等而 `text` 不等、`gen_random_uuid()` 可用、`pg_extension` 里那两条都在。
3. 往任一表加一个 `citext` 可空列，跑 `npm run db:generate`，在新 `.sql` 里搜 `create extension`——命中 0，这一站的核心就这一句。
4. 撤销第 3 步（删字段、删新 `.sql` 与它的 `meta` 记录、把 `_journal.json` 那条改回去），然后核对：`cmp` 判 journal 与备份一致、四份哈希不变、再跑一次 generate 回到 `No schema changes`。
5. 用 `select 'x'::no_such_type_probe` 取一次"类型不存在"的错误形状（code `42704`），把它当缺扩展时的同类参照。

本轮的实验改动已全部还原并逐字节核对，仓库没有留下永久改动；还原之后复跑：`npx nuxt typecheck` **rc=0、输出 0 字节**，`npm run lint` **rc=0**（还是那条 `vue/no-v-html` 的 warning），`npm run test:unit` **25 文件 184 用例全过**。
