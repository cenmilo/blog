## 九个文件摊在那里，谁保证它们成对

`db/migrations/` 现在摊着九个文件：四份 `.sql`，`meta/` 里四份 `0000_snapshot.json` 这样的记录文件，加一份 `_journal.json`。它们对不上时的症状很安静——`npm run db:migrate` 在一个新库上少建一张表，或者整批回滚，屏幕上不会写出"少了哪一份"。

上一站已经把判据钉死：跑不跑只由库里最大的 `created_at` 和 journal 里的 `when` 比大小决定。既然跑不跑是数字说了算，文件成不成对就得有人查。这一站分三层：**本地文件成对**（写成一条能反复跑的脚本）、库侧哈希（脚本不连库，人来比）、类型检查看不看得到 `db/`（跑四趟问出来）。

## 三方对得上，才算一条链

`_journal.json` 每条记录五个字段，本轮读到的第一条：

```text
idx=0  version="7"  when=1791912513899  tag=0000_baseline  breakpoints=true
```

由这三个数就能定位另外两个文件：`.sql` 必须叫 `<tag>.sql`，`meta/` 里对应的那份必须叫 `<tag 前四位>_snapshot.json`。journal 那四条记录与磁盘上九个文件的对应关系，本轮全对得上。

`meta/` 那四份之间还有一条更硬的链。每份里面有 `id` 和 `prevId`，下一份的 `prevId` 应当等于上一份的 `id`，第一份的 `prevId` 固定是一串全 0：

```text
0000_snapshot  id=000d991c-3ad9-4d5c-8c70-19aa71eb3f32  prevId=00000000-0000-0000-0000-000000000000
0001_snapshot  id=89ec6ee0-31a7-45b4-9593-f584445550a7  prevId=000d991c-3ad9-4d5c-8c70-19aa71eb3f32
0002_snapshot  id=912c1f7d-df05-460b-9ea9-500ecc5302fb  prevId=89ec6ee0-31a7-45b4-9593-f584445550a7
0003_snapshot  id=53a407a6-50ef-4054-b1b3-3c36d161fe15  prevId=912c1f7d-df05-460b-9ea9-500ecc5302fb
```

这条链值得单独查一遍：`db:generate` 生成下一份迁移时，拿的是**最后一份 `meta/*_snapshot.json`** 和当前 schema 做比较（前一站量过，生成不碰库）。起点错了，下一份 `.sql` 就是按错的结构差集写出来的。那几份里面还各带一个 `tables` 计数，本轮四份累计是 `1 / 4 / 5 / 6`——最后那份对应 `public` 里的六张表。

## 把对账写成一条命令

`scripts/check-migrations.mjs` 只做本地文件的事，**一条 SQL 都不发**，所以没有库也能跑、CI 上不用给它配连接串。它按 journal 的顺序走一遍，每一项只看一件事：

```js [scripts/check-migrations.mjs 的中间几行]
const sqlFile = path.join(folder, `${tag}.sql`)
if (!fs.existsSync(sqlFile)) {
  fail(`journal 记了 ${tag}，但 ${sqlFile} 不在（包里的读入阶段同一句抛 No file ... found）`)
  continue
}
const body = fs.readFileSync(sqlFile, 'utf8')
const stmts = body.split(BREAKPOINT).length
if (stmts > 1 && !entry.breakpoints) {
  fail(`${tag}：文件里有 ${stmts - 1} 个分句标记，journal 却写着 breakpoints=false`)
}
const snapshot = /** @type {Record<string, unknown>} */ (readJson(snapshotFile))
if (snapshot.prevId !== prevSnapshotId) {
  fail(`${snapshotName}：prevId=${String(snapshot.prevId)}，应等于上一份的 id=${prevSnapshotId}（链断了）`)
}
```

切句用的是同一个标记串 `--> statement-breakpoint`，跟包里的读入逻辑一字不差，所以它报的"段数"是 migrate 眼里的段数。跑完把四个数打出来，末尾一句 `问题 N`，有非 0 就 `exitCode = 1`。本轮在自己仓库上的输出：

```text

dialect=postgresql  version=7  journal 条数=4

  0000_baseline          when=1791912513899  stmts=1  tables=1
                         sha256=6153a23bc13b53ebfbbeb7f4660506ae047cce0c73882886add6ed6276723032
  0001_core_tables       when=1791965717036  stmts=5  tables=4
                         sha256=769be43ce241772699db623c8ee0c85567154e2fb2a9c82dcf8521fde12a9505
  0002_previous_maddog   when=1792065286115  stmts=2  tables=5

  0003_legal_rattler     when=1792204845185  stmts=2  tables=6
```

它已经挂进聚合入口。`package.json` 多一条 `"check:migrations": "node scripts/check-migrations.mjs"`，`scripts/check.mjs` 那份名单的第一位变成它——便宜的先跑：

## 三种手抖，只有两种拦得住

脚本得证伪过才算护栏。三趟都在 `db/migrations/` 的副本上做（`node scripts/check-migrations.mjs <副本目录>`，目录是第一个参数）：

| 手工破坏 | 本轮读数 |
| --- | --- |
| 删掉 `0002_previous_maddog.sql` | **问题 3**：`journal 记了 0002_previous_maddog，但 ...sql 不在`、`0003_snapshot.json：prevId ... 应等于上一份的 id ...（链断了）`、`0002_snapshot.json 在 meta/ 里，但没有任何 journal 记录用得到它` |
| 多一份 journal 里没有的 `0004_stray.sql` | **问题 1**：`... 在目录里，但 journal 没有它这条记录（migrate 不会执行它）` |
| 给 `0000_baseline.sql` 末尾加一行注释 | **问题 0、rc=0**，可打印的 sha256 从 `6153a23bc13b…` 变成了 `db9b0fe90542…`（文件 562 字节 → 593 字节） |

第一行三个问题不是重复报警：每项检查只看一件事，一份文件缺失会同时把"文件不在""链断了""记录文件没人认领"三处点着。

第三行才是这条脚本的天花板。**本地它拦不住改旧迁移的字节**，因为本地没有基准可比——基准在库里那一行 `hash`，或者在版本控制的历史里。这个仓库里没有 `.git` 目录（本轮 `ls -d .git` 报 `No such file or directory`），所以"入库"这一环只能落成一条命令加一份清单，落成不了提交前的钩子。

## 库里那一半：脚本不连库，人来比

那半段判据要读者在自己的开发库上跑一条只读查询：

```sql
select hash, created_at from drizzle.__drizzle_migrations order by created_at;
```

四行，逐行对两个数：`hash` 与上面每一行的 sha256 相等、`created_at` 与那一行的 `when` 相等。再加上 `public` 里的表数对最后一份 `meta/0003_snapshot.json` 的 `tables`（本轮 6）。四个数一起对上，才叫"文件与库是同一条链"。

脚本自己不去连这个库，是刻意的：`npm run check` 必须在一台没有库的机器上也能跑完——新同事的电脑、CI 的 runner，都没有那个连接串。

## `db/` 归谁看守，跑四趟才问清

先说配置的位置。`tsconfig.json` 是告诉 TypeScript「哪些文件算数、按什么规则算数」的那份配置，Nuxt 会生成四份（`app`、`server`、`shared`、`node` 各一），官方文档明确**不要直接改生成的文件**，要在 `nuxt.config.ts` 的 `typescript` 节里扩展。那一节一共 11 个子项：

| 子项 | 类型 | 默认 | 只管哪一份 |
| --- | --- | --- | --- |
| `tsConfig` | 文档未给 | 文档未给 | 四份共用的 `compilerOptions`；但 `include`、`exclude`、`vueCompilerOptions` **只进 app 那份** |
| `appTsConfig` | 文档未给 | 文档未给 | `tsconfig.app.json`（含旧的 `.nuxt/tsconfig.json`），优先于 `tsConfig` |
| `sharedTsConfig` | 文档未给 | 文档未给 | `tsconfig.shared.json` |
| `nodeTsConfig` | 文档未给 | 文档未给 | `tsconfig.node.json`——本仓库的 `db/**` 就写在这里 |
| `serverTsConfig` | 文档未给 | 文档未给 | `tsconfig.server.json`，优先于 `tsConfig` |
| `typeCheck` | `boolean` | `false` | 构建期类型检查；置 `true` 连开发期一起查；要先装 `typescript` 与 `vue-tsc` |
| `strict` | `boolean` | `true` | 严格检查的总开关 |
| `shim` | `boolean` | `false` | 要不要生成 `*.vue` 的声明文件 |
| `builder` | 文档未给 | `null` | 装哪套 builder 环境类型；`false` 是自己管，`shared` 给模块作者 |
| `hoist` | `array` | 17 个包名 | 给 `compilerOptions.paths` 生成深别名，pnpm monorepo 关掉 hoist 时才需要 |
| `includeWorkspace` | `boolean` | `false` | 把上层 workspace 也算进项目 |

`nuxt dev` 与 `nuxt build` 默认**不做**类型检查（文档给的理由是性能），所以护栏要靠 `nuxt typecheck`：typecheck 就是只把类型对一遍、不打任何包。本仓库的四趟：

| 现场 | 命令 | 读数 |
| --- | --- | --- |
| `db/schema.ts` 末尾一句 `export const probeBadType: number = '这不是数字'`，include 里有 `../db/**/*` | `npx nuxt typecheck` | rc=2，报 `db/schema.ts(22,14): error TS2322`（同一行打印 3 次） |
| 同一句错还在，把 `../db/**/*` 从 `nodeTsConfig.include` 撤掉 | `npm run typecheck` | **还是 rc=2，还是那一行** |
| 错句挪到谁都没 import 的 `db/probe-orphan.ts`，include 恢复 | `npm run typecheck` | rc=2，只报 `db/probe-orphan.ts(3,14)` |
| 这个孤立文件留着，`../db/**/*` 再撤掉 | `npm run typecheck` | **rc=0，报错 0 行**（生成的 include 从 14 项变 13 项） |
| 再加一份 `scripts/probe-bad.mjs`，同样一句错、用 JSDoc 标成 `number` | 上面几趟 | 它一次都没出现在报错里 |

三个结论：

- `include` 管的是**没人引用的文件**。`db/schema.ts` 撤出名单后照样报错，是因为它被六个文件 import（`server/services/` 下四个、`server/services/metrics/index.ts`、`server/utils/db.ts`），TypeScript 顺着引用就把进来的文件一起查了。
- 孤立文件只有被 include 覆盖到才有人看。第四趟那句错一直躺在磁盘上，rc=0 一声不响。
- `.mjs` 完全在类型检查之外。`scripts/` 下七个脚本全是 `.mjs`，名单里写的是 `../scripts/**/*.ts`，所以新加的 `check-migrations.mjs` 只剩 eslint 一层（`npx eslint scripts/check-migrations.mjs` rc=0）。想给它上类型护栏，路子是改写成 `.ts`：本机 `node --version` 是 v24.11.1，`node scripts/probe-ts-run.ts` 直接跑出 `hello probe`、rc=0，而 `../scripts/**/*.ts` 已经在名单里。

四趟跑完，探针文件全删，`db/schema.ts` 与 `nuxt.config.ts` 各自还原并逐字节比对通过，复跑上面那张七项表全绿。

## 出问题对照

| 症状 | 原因 | 怎么办 |
| --- | --- | --- |
| 新库上 migrate 完少一张表，命令没报错 | journal 记了、`.sql` 不在，读入阶段之前没人查 | `node scripts/check-migrations.mjs`，第一位已在 `npm run check` 里 |
| 生成出来的下一份迁移结构差集不对 | `meta/` 里那条 `prevId` 链断了 | 同一脚本报链断；缺哪份 `*_snapshot.json` 就从哪个提交找回 |
| 改了旧迁移，本地检查却全绿 | 本地没有基准可比 | 拿库里 `hash` 与文件 sha256 逐行比；有版本控制就在提交前拦 |
| `db/` 里一个文件的类型错没人报 | 它没被任何文件 import，又不在 include 名单里 | 写进 `typescript.nodeTsConfig.include`，别改生成的 tsconfig |
| 脚本里的类型标注没人查 | `.mjs` 不在任何一份 tsconfig 的名单内 | 要么改写成 `.ts`，要么给它一条能跑、能看输出的自证脚本 |

| 745 | 六种连错法各回什么错误码，以及"连上了"的三行判据；库与文件的对账第一次做出来 |

两趟留给读者在自己的可丢弃库里补：在一个空实例上跑 `npm run db:migrate`，判据是记账表出现 4 行、`public` 出现 6 张表；再把 journal 里某个 `when` 手工改大，看那份重跑撞 `already exists`。
