## 屏幕上先看见这三行

在仓库根跑 `npm run check:env`，打出来的是键名和结论，永远不打值（这份输出要能贴进工单）：

```text
已设  DATABASE_URL
已设  NUXT_PUBLIC_SITE_URL
已设  NUXT_SESSION_SECRET
环境变量合法
```

同一台机器上，把这条命令换到一个没有 `.env` 的目录里跑，把进程里的三个变量剔掉：

```text
（当前目录没有 .env，只按进程环境变量判）
未设  DATABASE_URL
未设  NUXT_PUBLIC_SITE_URL
未设  NUXT_SESSION_SECRET
环境变量不合法 → DATABASE_URL: Invalid input: expected string, received undefined; NUXT_PUBLIC_SITE_URL: …; NUXT_SESSION_SECRET: …
退出码 1
```

三行"已设"看着像万事俱备。但**这份清单里没有 `NUXT_DATABASE_URL`**——而站里每个要查库的接口读的都是那一个名字。这一站就讲这个分工。

## 两个名字各自被谁读

```ts [drizzle.config.ts：CLI 侧那一处]
export default defineConfig({
  schema: './db/schema.ts',
  out: './db/migrations',
  dialect: 'postgresql',
  dbCredentials: { url: process.env.DATABASE_URL! },
})
```

```ts [server/utils/db.ts：运行期那一处]
export function useDb () {
  const connectionString = useRuntimeConfig().databaseUrl
  if (!connectionString) {
    throw new Error('useDb(): runtimeConfig.databaseUrl 是空串，请设环境变量 NUXT_DATABASE_URL（CLI 侧那个 DATABASE_URL 不会被读）')
  }
  // ...协议名再校一次，然后建连接池
}
```

读的东西不一样：命令行读的是**进程环境变量**（Node 自己给的 `process.env`），运行期读的是 **runtimeConfig 里那位叫 `databaseUrl` 的键**。名字前面带不带 `NUXT_`，决定了它能顶谁——这不是习惯，是规则。

## 文档把这条规则写成了两句话

讲 runtimeConfig 那一节给的两条要求：自定义键**必须先在 `nuxt.config` 里声明**（否则任意环境变量不会暴露给应用），以及**只有以 `NUXT_` 开头、全大写、用下划线切分大小写变化的那个名字**能顶替它。

紧接着那条 warning 是本站的反面教材：把 `runtimeConfig` 的默认值写成另一个名字的环境变量（例如给 `myVar` 填 `process.env.OTHER_VARIABLE`）**只在构建期有效，跑产物时会坏**；官方建议直接用与 `runtimeConfig` 结构对得上的名字。

所以 `nuxt.config.ts` 里那位是空串起步的，没有任何 `process.env` 掺进来：

```ts [nuxt.config.ts 的 runtimeConfig 片段]
runtimeConfig: {
  sessionSecret: '',
  databaseUrl: '',        // 由 NUXT_DATABASE_URL 覆盖
  // public 里的键客户端也能读，值由 NUXT_PUBLIC_SITE_URL 覆盖
  public: { siteUrl: 'http://localhost:3000' },
}
```

"先声明"这件事有静态证据。`nuxt prepare` 之后打开 `.nuxt/types/runtime-config.d.ts`，`SharedRuntimeConfig` 里一位一位列着 `sessionSecret`、`databaseUrl`、`smtpUrl`、`mailFrom`、`contentDir`、`githubClientId`……没声明的键在这张类型里根本不存在。

`.env` 那一节补了另一半：Nuxt 命令行在 dev／build／generate 三个时刻自动读项目根的 `.env`；**服务构建完之后，`.env` 不再被读**，那一份得由部署环境自己给。同一节末尾还有一句重要的：生产环境里 **`NUXT_` 开头以外的环境变量，runtimeConfig 收不到**。

## 三趟真请求，证明互相顶替不了

做法：临时加一个接口，里面调一次 `useDb()`，只回布尔与信息形状，**连接串绝不回**（这份输出会被贴进文章）。然后拿 `npm run build` 的产物跑三趟，区别只在启动时给了哪个名字。

```text
A 什么都不设
200 | {"stage":"useDb 抛出","mentionsNuxtName":true,"mentionsCliName":true,"protocolChecked":false,"configuredLength":"没看到协议名"}

B 只设 NUXT_DATABASE_URL（值是一条明显假的串：假用户、假口令、端口 59999）
200 | {"stage":"useDb 返回了客户端","hasDb":true}

C 只设 DATABASE_URL（和 B 一模一样的串，只换名字）
200 | {"stage":"useDb 抛出","mentionsNuxtName":true,"mentionsCliName":true,"protocolChecked":false,"configuredLength":"没看到协议名"}
```

**C 与 A 逐字节相同**。那条串喂给 `DATABASE_URL` 时，运行期那位仍然是空串——`DATABASE_URL` 顶不了 `databaseUrl`，正如文档那句"不以 `NUXT_` 开头的收不到"。

B 那行还带出一条容易被误读的读数：拿到客户端**不等于连上了库**。`useDb()` 只做三件事——看空串、校协议名、建连接池；池子要到第一次查询才真去连。所以"接口回 200 说拿到客户端"和"库能不能通"是两件事，后者归这一条线的第 2 步。

顺带一条：A 那趟的启动目录里就放着 `.env`（里面有真的连接串），产物仍然报空——这正是"构建完之后 `.env` 不被读"的直接读数，不是推测。

## 校验入口为什么不覆盖另一位

`.env.example` 里这段是刻意的安排：schema 认识的前三位是 `DATABASE_URL`、`NUXT_PUBLIC_SITE_URL`、`NUXT_SESSION_SECRET`；`NUXT_DATABASE_URL` **故意不在校验名单里**，因为开发库没起时它留空，而 zod 的 `url()` 会把空串判死。取舍写明白了：那一位走 runtimeConfig 那条路，缺了由 `useDb()` 在第一次用时抛出并点名。

于是这一位的失败形状有两种，都在单测里钉着（`test/unit/db.test.ts`）：空串 → 抛出并点名 `NUXT_DATABASE_URL`；漏协议名（`localhost:5432/库名` 这种 zod 能放行、驱动不认的写法）→ 驱动层的形状检查拦下。第三条用例名字是"合法串 → 返回带 select 的客户端，且此刻不连库"，与上面 B 那趟对上。

命令行那一侧也有个不对称要知道：`nuxt build --help` 里有 `--dotenv=<dotenv>`（指定别的 env 文件）和 `--envName=<env_name>`，而 **`drizzle-kit generate --help` 的 10 个旗标里没有这类入口**（`--config`、`--dialect`、`--driver`、`--casing`、`--schema`、`--out`、`--name`、`--breakpoints`、`--custom`、`--prefix`）。drizzle-kit 0.31.11 自己会读项目根的 `.env`，所以在这台机器上跑 `npm run db:generate` 不必额外传值——换 CI 或换机器时，这一点仍然依赖 `.env` 在位。

## 出问题对照

| 症状 | 原因 | 怎么办 |
| --- | --- | --- |
| 迁移命令跑得好，站点里所有查库接口报 500 | 只设了 `DATABASE_URL` | 运行期要的是 `NUXT_DATABASE_URL`，两轨都要写 |
| `useDb()` 抛出"是空串" | 那一位没被覆盖，默认值就是空串 | 启动服务前显式设 `NUXT_DATABASE_URL` |
| 本地能跑、线上读不到值 | 产物不读 `.env` | 用部署面板或启动命令显式给环境变量 |
| 明明设了 `NUXT_` 变量却收不到 | 键没在 `nuxt.config` 的 `runtimeConfig` 里声明 | 先声明，默认值给空串，再由环境变量覆盖 |
| 一串数字形状的密钥读出来不是字符串 | 值被 `destr` 按 JS 类型解析了 | 值本身带引号：`.env` 里写成 `NUXT_X='"4848e0"'` 这种形式 |
| 从 `.env` 删掉一行后它还在生效 | 已经在进程里的值不会被"删掉" | 重启拿进程；`--dotenv` 指另一份文件也行 |

## 自己跑一遍

1. 在仓库根跑 `npm run check:env`，记下三行"已设"和最后一句结论。
2. 换到一个没有 `.env` 的目录跑同一份脚本，看它先打"（当前目录没有 .env…）"再打三个"未设"，退出码 1。
3. 跑 `npx nuxt prepare`，打开 `.nuxt/types/runtime-config.d.ts`，找 `databaseUrl` 在不在 `SharedRuntimeConfig` 里——它就是"必须先声明"的证据。
4. 起产物服务两次：一次只设 `DATABASE_URL`，一次只设 `NUXT_DATABASE_URL`（用一条假串就行），比较一个会读到数据库的接口回什么。想省事的等价做法：读 `test/unit/db.test.ts` 三条用例的名字，它测的就是这三段分支。
5. 跑 `npx drizzle-kit generate --help` 与 `npx nuxt build --help`，各数一遍与"环境文件"有关的旗标——一个都没有，一个有两个。

本轮为了拿这三趟读数临时加的接口与那条 e2e spec 都已删除；删后 `nuxt prepare` 重跑，路由表回到 22 条、生成物里搜 `probe` 命中 0，`npx nuxt typecheck` **rc=0、输出 0 字节**，`npm run lint` **rc=0**（那条 `vue/no-v-html` 的 warning 依旧）。用到的版本：nuxt 4.5.2、nitropack 2.13.4、drizzle-kit 0.31.11、drizzle-orm 0.45.4、zod 4.6.7、pg 8.23.1。

## 本文依据

- runtimeConfig 的两条要求（先声明、`NUXT_` 全大写下划线命名）、默认值写成另一个环境变量的名字会在运行期坏的 warning、destr 的类型转换与加引号做法、客户端只见 `public` 与 `app`、服务端全量只读、建议把 `event` 传给 `useRuntimeConfig`：`https://nuxt.com/docs/4.x/guide/going-further/runtime-config`
- `.env` 只在 dev／build／generate 三个时刻被读、构建后的服务不读 `.env`、`--dotenv` 指定别的文件、删掉一行不会撤销已生效的值、生产环境里 `NUXT_` 之外的变量 runtimeConfig 收不到：`https://nuxt.com/docs/4.x/directory-structure/env`
- `runtimeConfig` 与 `app.config` 的分工表（能不能被环境变量覆盖、客户端可见性）：`https://nuxt.com/docs/4.x/getting-started/configuration`
- `runtimeConfig` 选项本身：`https://nuxt.com/docs/4.x/api/nuxt-config`
- 工具侧的旗标与版本读自本机安装内容：`npx drizzle-kit generate --help`（0.31.11，10 个旗标）、`npx nuxt build --help`（`--dotenv`、`--envName`）
