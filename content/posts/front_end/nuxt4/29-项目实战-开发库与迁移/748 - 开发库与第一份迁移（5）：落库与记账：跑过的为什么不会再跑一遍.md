## 判据不长在迁移文件里

前面几站对账对到两处：`_journal.json` 里的四个 `when` 与库里记账表的 `created_at` 逐行相等；每份 `.sql` 的原样字节做 sha256，前 12 位与库里的 `hash` 一致。这一站回答那个更扎心的问题：**这两样东西，migrate 到底看哪个？**

答案在包里，不用猜。`drizzle-orm/migrator.js` 读目录：

```js [node_modules/drizzle-orm/migrator.js 的关键四行]
const result = query.split('--> statement-breakpoint').map((it) => it)
migrationQueries.push({
  sql: result,
  folderMillis: journalEntry.when,          // 比大小用的是这个
  hash: crypto.createHash('sha256').update(query).digest('hex'),
})
```

`drizzle-orm/pg-core/dialect.js` 决定跑不跑：

```js [同一包里决定执行的那几行]
const dbMigrations = await session.all(
  `select id, hash, created_at from drizzle.__drizzle_migrations order by created_at desc limit 1`
)
const lastDbMigration = dbMigrations[0]
await session.transaction(async (tx) => {
  for await (const migration of migrations) {
    if (!lastDbMigration || Number(lastDbMigration.created_at) < migration.folderMillis) {
      for (const stmt of migration.sql) { await tx.execute(sql.raw(stmt)) }
      await tx.execute(`insert into drizzle.__drizzle_migrations ("hash", "created_at") values(${migration.hash}, ${migration.folderMillis})`)
    }
  }
})
```

三件事一次说清：

- **只取库里 `created_at` 最大的那一行**，拿它和这份的 `folderMillis`（也就是 journal 里的 `when`）比大小；
- `hash` 是被**写进去**的字段，那段判断里**没有它**——它是个指纹，不是判据；
- 整趟在一个事务里（`session.transaction` 在循环外面），所以任何一句失败，这一批里已执行的部分和记账插入一起回滚。

## 本地预演一遍

不连库也能算出它会做什么决定。`_journal.json` 四个 `when`（本轮读出来的）：

```text
1791912513899 < 1791965717036 < 1792065286115 < 1792204845185      严格递增 = true
```

它们严格递增，比大小才成立（生成时 `when` 取的是那一刻的毫秒，天然递增）。再看两个场景：

| 库里的状态 | 判据代入 | 结果 |
| --- | --- | --- |
| 空的（没有 `drizzle` 这个 schema） | `!lastDbMigration` 直接为真 | 四份按序全跑，最后库里 4 行 |
| 已有 4 行、最大 `created_at` 是 `1792204845185`（上一站从库里读到的） | 每一份的 `when` 都不大于它 | 一份都不跑，插不进新行 |

第二行就是"跑过的为什么不会再跑一遍"的全部机制——不是它认得文件名，是它拿一个数字比大小。

## 顺带把切段这件事看清

`split('--> statement-breakpoint')` 说明一件事：**一个段就是一次 execute**。本地把四份文件按这个标记切一遍：

```text
0000_baseline        → 1 段
0001_core_tables     → 5 段
0002_previous_maddog → 2 段
0003_legal_rattler   → 2 段
```

`0001` 的第 0 段全文是这样的：

```sql [0001 的第 0 段（注释＋两行扩展＋建枚举，同一段）]
-- 下面两行不是 drizzle-kit 生成的，是手工补的：生成器只管表、列、索引、外键，扩展不在它的产物里
-- 顺序是硬要求：citext 提供 "email" "citext" 这个列类型，pgcrypto 提供 DEFAULT gen_random_uuid()，
create extension if not exists citext;
create extension if not exists pgcrypto;

CREATE TYPE "public"."user_role" AS ENUM('free', 'member', 'admin');
```

两条手写扩展行和 `CREATE TYPE` 在**同一次执行**里——因为它们之间没有分句标记。这既解释了上一站那条规律（标记数 = 生成语句数 − 1），也说明为什么扩展行钉在文件最前面就一定先于 `CREATE TYPE` 生效：同一个字符串里，Postgres 按顺序执行。

## 三种改动，三种下场

判据定了之后，几种"手抖"的结果就能推出来，其中第一条本轮已经在库上量过：

| 你改了什么 | 会发生什么 |
| --- | --- |
| 改旧 `.sql` 的字节（加一句注释、删掉行尾换行） | 文件的 sha256 变了（上一站量过：`0000` 去掉首尾空白就对不上），但 `when` 没变 ⇒ **migrate 既不会重跑也不会报错**，它压根不看 hash。库里结构和文件从此悄悄分叉 |
| 手工把 journal 里某条 `when` 改大 | 那份会**再执行一遍**，撞的就是"已存在"那一类错误：`table "ping" already exists`、`type "user_role" already exists`——Postgres 的 `CREATE TYPE`、`ADD CONSTRAINT` 没有 `IF NOT EXISTS` 写法 |
| 直接在库里改结构，不写迁移 | migrate 完全不知情：它比较的是时间戳，不检查结构。对账要靠人（本站那张表就是给对账用的） |

第一条最容易踩，因为它不报错。想确认自己没踩，两个数一对就行：把 `.sql` 的 sha256 与库里那行的 `hash` 比一次（本站没做这一步，因为要连库——见文末的待办）。

## 记账表本身长什么样

跑 migrate 之前，包会先执行这两条（都在 `dialect.js` 里）：

```sql [每次 migrate 都会先跑的幂等 DDL]
CREATE SCHEMA IF NOT EXISTS drizzle;
CREATE TABLE IF NOT EXISTS drizzle.__drizzle_migrations (
  id SERIAL PRIMARY KEY,
  hash text NOT NULL,
  created_at bigint
);
```

也就是说，"跑一次 migrate"至少要往库里落两条 DDL（都幂等）。三列各有分工：`id` 只是插入顺序，判据用的是 `created_at`；`hash` 是留给人的证据；`created_at` 是那份迁移在 journal 里的那个毫秒。清业务数据时**别顺手删这个 schema**——删了它，所有迁移都会被重跑。

还有两条包里的报错文案，正好解释上一站那条"同生同死"的规矩：

```text
Can't find meta/_journal.json file
No file <目录>/0002_previous_maddog.sql found in <目录> folder
```

前者是没带 `meta/`，后者是 journal 记了、文件没在。两者都在读目录阶段就抛，不会跑一半。（这两条是从包里读的原文，本站没有故意造现场去触发。）

## 出问题对照

| 症状 | 原因 | 怎么办 |
| --- | --- | --- |
| 改了旧迁移，跑 migrate 什么都没发生 | 判据只看 `created_at`，不看 hash | 只追加新迁移；要重来另建一个库 |
| 新库上跑到一半报 `already exists` | 之前手工执行过部分语句，记账却没写全 | 别手工执行 DDL；把库清成初始状态再 migrate |
| 一次迁移里前几句改了、最后一句失败，结果全没生效 | 整批在一个事务里 | 这是保护，不是 bug；修完那份迁移再跑 |
| 迁移文件在，journal 里没有它 | 只删了 `meta/` 或只拷了 `.sql` | 两者同生同死；对不上就按包里的第二句报错找缺失项 |
| 跑完 migrate 发现多了两条 DDL | 它会先建 `drizzle` schema 与记账表 | 正常，且幂等；别把这两条也算进"我的结构变更" |

## 自己跑一遍（都在本地，不碰库）

1. 打开 `node_modules/drizzle-orm/pg-core/dialect.js`，搜 `__drizzle_migrations`，看那三行：取最大 `created_at` 的 select、比较条件、插入语句。
2. 打开 `node_modules/drizzle-orm/migrator.js`，确认 `folderMillis` 取自 journal 的 `when`、`hash` 是整个文件字符串的 sha256。
3. 对每份 `.sql` 按 `--> statement-breakpoint` 切一次，数段数；再看 `0001` 第 0 段里有什么。
4. 把 `_journal.json` 的四个 `when` 抄下来，检查是否严格递增；再把上一站从库里读到的最大 `created_at` 代进比较式，看有几份会被执行。
5. 想真验"跑过的不再跑"，需要一个可丢弃的库（本站没做）：`npm run db:migrate` 会往目标库执行两条幂等 DDL，跑之前先记下四份文件的 sha256 与记账表内容，跑完比对——正常应当一字不变。

**这一站的边界**：没有对 `.env` 里那个共享库跑 `db:migrate`，也没有再连库取一次数（写库与连库都需要用户批准）。所以库里那四行的读数是上一站的，本轮只做本地推导与包内取证；"改 `when` 后重跑"和"空库整链重放"两条仍待补。本地读到的数字与包内代码行号都在上文，可以逐条复算。
