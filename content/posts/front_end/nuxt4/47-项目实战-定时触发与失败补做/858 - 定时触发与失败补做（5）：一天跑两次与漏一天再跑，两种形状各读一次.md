上一站的最后一段留了一句话：`补发通知` 是一条能被调用的路，但没有谁去调用它。今天你把它接进任务，然后按 853 那一次的记忆再跑第二次——屏幕上读回来的是这个：

```
[窗口·真库跑两次] {"第一次":{"候选人数":1,"处理行数":1,"发信失败":1,…},
"第二次":{"候选人数":0,"处理行数":0,"发信失败":0,"停在发送中":0,
"补做":{"名单人数":1,"抢到":1,"没抢到":0,"补发成功":0,"补发仍失败":1,"已不必发":0}}}
```

**"第二次跑全 0"这句话从今天起只对一半成立**。降级那四个数归 0，因为那个人已经是 `free` 了；补做那几个数不是 0，因为他那一封信还没送到。这两个"0"以前长得一样，现在不一样了——这一站要的就是这个差别。

## 接在哪一行，比接不接更要紧

`server/tasks/refresh-roles.ts` 里现在是这样排的：

```ts
const 停在发送中 = await 数停在发送中()
const 补做 = await 补发通知(开始)
const 结果 = await 刷新会员角色(开始)
```

补做在降级之前。反过来写（先降后补）看起来更顺——"这一轮刚记成 `failed` 的人，顺手给他补一次"——但那一趟里同一个人会被叫两次 transport：SMTP 坏的时候，每一天、每一个人都寄两遍，而 852 钉的那条闭环（`发信成功 ＋ 发信失败 === 真被改动的人数`）在同一趟里对不上。排在前面，这一轮新建的失败行要到下一轮才进名单。

顺序是能被读出来的，两条各管一段：

```
[窗口·形状] {"任务读钟处数":3,"交给服务层的时刻":2,"停在函数体长度":303,
"那一段有写":false,"那一段有钟":false}
[窗口·不补本轮] {"结果":{"处理行数":1,"发信失败":1,"补做":{"名单人数":0,…}}}
```

后一条是关键的那一眼：这一轮刚降下来、刚记成失败的那个人，**不在这一轮的补做名单里**。把补做挪到后面，这个 0 就变成 1。

## 报回的键从八个变成十位，表里的格从八格变成十五格

CLI 打印的那一份 `result` 是这条线的对外契约（853 逐字钉过键名与顺序）。这一站不动那八个键的名字和位置，多出来的两位排在最后：

```ts
停在发送中,
补做,   // { 名单人数, 抢到, 没抢到, 补发成功, 补发仍失败, 已不必发 }
```

嵌套是有意选的。把六个数摊平进去，读的人会以为它们和前面八个是一类：那些说的是"这一轮对用户做了什么"，这两位说的是**上一轮欠的账还了多少**。

`task_runs` 那边跟着加七列（`db/migrations/0007_superb_pyro.sql`，全是 `ALTER TABLE … ADD COLUMN`，都可空）：

```
[窗口·真库漏一天] {"这一趟":{"候选人数":1,"处理行数":1,"发信成功":1,"发信失败":0,
"补做":{"名单人数":1,"抢到":1,"补发成功":1,…}},
"最后一条痕迹":{"candidates":1,"processed":1,"mail_sent":1,"mail_failed":0,
"retry_list":1,"retry_claimed":1,"retry_sent":1,"retry_failed":0,"stale_sending":0}}
```

生成与应用两步都要跑。换一台机器只跑到 `0005` 的话那七列不存在，而 `写下轮痕迹` 是吞掉写失败的（856 就这么定的），于是症状不是报错、是"这一轮压根没有痕迹"：

```bash
npm run db:generate   # 长出 0007_superb_pyro.sql
npm run db:migrate
```

`null` 与 `0` 那条纪律跟着这七格一起走。抛错那一轮十五格全是 `null`；跑到了却没账要补，才是 `retry_list: 0`。两种形状在带库那一趟里都读到过——第一行痕迹是 `mail_failed: 1`／`retry_list: 0`，第二行是 `candidates: 0`／`retry_list: 1`／`retry_failed: 1`。

## 四种形状，四种读数

| 你跑的 | 报回里看得见的 |
| --- | --- |
| 同一天第二次（SMTP 还是坏的） | 降级四个 0；补做 `名单人数:1`、`补发仍失败:1`，痕迹第二行照留 |
| 下一轮换上能用的 SMTP | `补做.补发成功:1`、`候选人数:0`；表里那一行成 `sent`，收件端收到一封 |
| 漏一天再跑（两种欠账同时挂着） | 同一趟里 `处理行数:1` 且 `补做.补发成功:1`；两封信的先后是"欠的在前" |
| 半路抛错那一轮 | 十五格全 `null` ＋ 一句 `error`，错照样抛出去 |

第三行那句"欠的在前"是读出来的，不是推断的：

```
[窗口·真库漏一天] {"新到":2,"收件人":["s858.debt.1792581835915@example.com",
"s858.new.1792581838554@example.com"]}
```

`debt` 那位是上一轮欠的，`new` 那位是这一轮刚降的。顺序反了就说明补做没排在降级之前。

## 停在 `sending` 的那一位：只读出来，不猜时长

```
[窗口·真库sending] {"停在发送中":1,"补做":{"名单人数":0,…},
"那两行":["sending","sending"],"痕迹":{"stale_sending":1,…}}
```

同一个用户名下种两行 `sending`，读回来是 1——这一格答的是"几位卡住了"，不是"几行"（上一站量过：周期末读不出那一族，一个人能攒出多行）。

它不改那一行。要改就得先回答"多久没落定算死了"：给 `sending` 配一个过期时刻，就要再定谁写谁读；让补做去猜一个分钟数，就是**把猜测写进跟钱相关的路径**。今天没有这个依据，所以这一站只把缺口变成一个数——`stale_sending` 有值，说明有人卡着；怎么捞，留给有依据的那一站。

## 这一站踩到的四处，症状都不是"报错"

**其一，自己的守卫把自己的欠账当成别人的。** 补做的名单是 `where status='failed'` 全库筛，所以带库那份规格加了一条"别人在场就让路"。第一版没把自己这几位排除掉：① 跑完第一轮留下一行 `failed`，第二轮就被自己的守卫挡下——**症状是这一档静默跳过、一行读数都打不出来**，看起来像"补做不工作"。修法是 `user_id <> all($1::uuid[])`，把 `我的人是` 排除掉。

**其二，自证名单要一次报全。** ③ 那一档两只探针都在开跑前建好，第一趟却只把一位交给守卫，另一位就被认成"别人在场"。真正该改的是建探针的时机：那位新到期的必须在第一趟之后才建——一个挂着 `member` 而名下没有任何订阅行的人，会在第一趟就被"没有一行"那一支降掉，两种形状就分不开了。

**其三，别绕过统一入口。** ④ 那一档不数封数，就直接进了 `连库()`——而"没给库就 skip"这一条挂在统一入口上。离线全量那一趟于是真的去连 5432，`connect ECONNREFUSED ::1:5432` 红一条，连带同档后面两条 `did not run`。少写一行 `await 起手()` 的代价是整批证据脏一次。

**其四，占锁之后 30 秒预算不够。** 上一站那份规格原本不占锁；这一站让它占了（因为它跑 `补发通知`，读的是全库名单），于是排在后面的档要等：`[锁·等不到] {"已等毫秒":20292,"上限毫秒":20000}`。**红的是排队的人，不是写坏的人**——两条带库档各给了 90 秒预算，并在文件头写明为什么。

## 五处改动，各撞红哪一档

| 改坏什么 | 红在哪 |
| --- | --- |
| 补做挪到降级之后 | 单测 ①②④ ＋ `task-run-record` ②③⑤⑥，七条同趟红 |
| `数停在发送中` 顺手把卡住的行改成 `failed` | ③（行为）＋⑥（形状）两红 |
| 那一位按行数、不按人数算 | 只 ③ |
| 抛错那一轮把 `retry_list` 写成 0 | `retry-window` ⑤ ＋ `task-run-record` ④ |
| 让某一份跑全库名单的规格不占锁 | `task-run-closure` ⑤（认调用形状，名单变两份） |

第一行那七条里有一条是形状档自己：`先补后降: false`，红话是"SMTP 坏时每轮寄两封"。第五行是这一站新加的守卫：`task-run-closure` ⑤ 原本只问"谁建了 `member` 探针"，现在两个面都问——批量改一张表，和**读一份全库的名单**。

## 撞上这些现象，先查这一行

| 现象 | 大概率是哪里 |
| --- | --- |
| 带库那一档一行读数都没打，状态是 skipped | 被自己的守卫让路了：欠账/名单排除自己了吗 |
| 离线全量里冒出一条 `ECONNREFUSED :5432` | 那一档绕过了带 skip 的统一入口 |
| 跑第二轮，`补做.名单人数` 是 0 而表里明明有 `failed` | 那一行是 `sending` 或 `not_due`，不在 `failed` 名单里 |
| 同一轮里同一个人收到两封 | 补做排到了降级后面 |
| `npm run check` 报键数对不上 | 报回的十位与 `task_runs` 的十五格不是同一趟（两处清单各钉一份） |

本轮的数：单测 424 条／66 文件；不带库全量 260 passed／149 skipped／0 failed（归族：要库 77、外部服务 43、内容目录 14、另一趟开关 11、让路 4，没有未归类）；带库全量 **362 passed／47 skipped／0 failed**（17/14/11/5）。带库那一趟里有一条让路：`task-scope-baseline 848①` 等锁 20 秒没等到——这是这一站新加锁带来的排队，写在这里而不是当成"今天全绿"。

## 手边能验的三件事

1. 跑 `npm run test:unit -- retry-window`，看 `[窗口·不补本轮]` 那行的 `名单人数` 是不是 0；再把 `refresh-roles.ts` 里那两行调换顺序跑一次，看它变 1。
2. 带库那份单跑：`NUXT_E2E_DB=1 E2E_PORT=4153 npx playwright test test/e2e/retry-window-db.spec.ts`，把 ① 的两行痕迹抄下来，注意第二行的 `retry_list` 是 1 而不是 0。
3. 你自己的库上试一次"半路抛错"：把 `DATABASE_URL` 指到一个空库再跑任务，读 `task_runs` 里那句 `error`——它带着被包住的整条语句，能看出卡在哪一步。

## 还没闭合的那几格

- `sending` 的回收仍然没有人做，这一站只是把它变成一个能被读出来的数。
- **审计失败那一路没有补做**：补的是信。少的那一行审计痕迹仍然只有标准输出读得到（851 立的"任务这一路少一条日志行"同族）。
- 多实例部署时两个进程各自跑：抢这一条挡住重复寄信，但同一时刻两位都读到同一行 `failed` 的话，落定顺序决定哪一封算数。
- 补做读的是全库名单——它按设计就不分"这是谁欠的"，所以共享库上跑它必须占锁；这一条是这一站学到的第二个共享面。
- `nuxt task` 那条命令在本项目装的 nuxi 里仍然不存在；`isTest` 下 runner 不起跑，"到点自己跑"仍然只能靠人肉叫起来这一趟。
