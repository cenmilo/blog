上一站跑完一轮，`task_runs` 里多了一行，那八个数字告诉你：候选人 12、降了 3、发信失败 3。然后呢？

**这三个数字答不出"是谁"**。你想替那三个人做点什么——重发一次、或者手工告诉他——手上只有一个计数。`audit_logs` 也不行，它记的是"谁的 role 被改了"，不记"谁的信没送到"；把投递结果塞进它的 `meta` 里更糟，那是一张只能追加的历史表，而补做要的是当前状态：这一封现在到底寄到没寄到，会被反复改。

所以要第三张表。

## 按轮记数的那张，按人记状态的那张

`db/tables/task-runs.ts` 上一行是一轮的八个数；新加的 `db/tables/downgrade-notices.ts` 一行是一个人的一期：

```ts
export const downgradeNotices = pgTable('downgrade_notices', {
  id: bigserial('id', { mode: 'number' }).primaryKey(),
  userId: uuid('user_id').notNull().references(() => users.id, { onDelete: 'cascade' }),
  periodEnd: timestamp('current_period_end', { withTimezone: true }),
  status: text('status').notNull(),
  reason: text('reason'),
  messageId: text('message_id'),
  updatedAt: timestamp('updated_at', { withTimezone: true }).notNull().defaultNow(),
}, 表 => [unique('downgrade_notices_user_period_unique').on(表.userId, 表.periodEnd)])
```

`(user_id, current_period_end)` 那条唯一约束是这一行的去重键：一个人可以同时有多行订阅、也可以同一期被记两次，但"这一期通知到哪一步了"只许有一行。

建完表要跑两步，第二步别漏——漏了的症状是服务层第一次写就报 `relation "downgrade_notices" does not exist`：

```bash
npm run db:generate   # 长出 db/migrations/0006_fixed_black_panther.sql
npm run db:migrate    # 真的把那张表建到库上
```

## 发信与记账合成一步，写入者只留一家

`server/services/billing/refresh.ts` 里原来直接叫 `sendDowngradeNotice(...)`。这一站把它挪进新的 `server/services/billing/notify.ts`，落点那一份只调 `发通知并记账(...)`。这不是洁癖：发信和记结果是同一件事的两半，分在两份文件里，就会出现"表上写着 sent、计数里那次是失败"——两处各 catch、各累加，谁也不知道另一个数是怎么来的。

这一条是能被读出来的，形状那一趟打印：

```
[补做·形状] {"通知的写入者":["server/services/billing/notify.ts"],
"补做或取数里改users":false,"口径实现":["server/services/billing/rows.ts"],
"问规则在发信之前":true,"抢在发信之前":true}
```

`refresh.ts` 里的发信调用点从 1 处变成 0 处，`notify.ts` 里是 2 处（正常轮次一封、补做一封）。这两个数各自钉在 `downgrade-notice.test.ts` 的 ⑥ 档里。

## 补做的顺序：先抢，再问规则，最后才寄

```ts
export async function 补发通知 (现在毫秒: number): Promise<补做结果> {
  const 失败行 = await useDb().select({…}).from(downgradeNotices)
    .where(eq(downgradeNotices.status, NOTICE_FAILED))
    .orderBy(desc(downgradeNotices.updatedAt))
  // 按人去重（`current_period_end` 为空那一族不受唯一约束保护，见下面第三条）
  const 按人 = await 取按人订阅行(用户ids)   // 与 851 同一条口径，只有一处实现
  const 邮箱 = await 取邮箱(用户ids)
  for (const 这一行 of 名单) {
    const 抢到 = await useDb().update(downgradeNotices)
      .set({ status: NOTICE_SENDING, updatedAt: new Date() })
      .where(and(那一行(… ), eq(downgradeNotices.status, NOTICE_FAILED)))
      .returning({ id: downgradeNotices.id })
    if (抢到.length === 0) { 出.没抢到 += 1; continue }
    const 结论 = 判降级(按人.get(这一行.用户id) ?? [], 现在毫秒)  // 那一份规则，843 立的
    if (结论.判定 !== '该降') { /* 推进到 not_due */ continue }
    const 送出 = await sendDowngradeNotice({ to: 地址 })
    /* 按 送出.sent 落定成 sent 或 failed */
  }
}
```

三处顺序都不是随便排的。

**先抢再发**用的是 833 那条老法：带条件写＋`returning`，读回真改了几行。`and status = 'failed'` 这一位是"同一个人不被通知两次"的落点——两条补做同时跑，只有一位能把 `failed` 改成 `sending`，另一位读回空数组就走人。

**发出之前再问一次规则**：上一轮失败的人可能在这之后续上了。这时候还念"会员期已经结束"就是说假话，所以那一行推进到 `not_due`（终态），一封都不发。

**补做一行都不碰 `users`**：它补的是信，不是权限。补做成功不等于"再降一次"，补做失败也不等于"把他升回去"。这条写在 `notify.ts` 的头注释里，形状档盯着 `.update(users` 这个写法有没有出现在那两份文件里。

## 三件事只有真库答得出来

`notice-retry.test.ts` 那八档喂的是假连接：它按顺序吐行，不执行任何约束。所以下面三条必须由 `test/e2e/notice-retry-db.spec.ts` 跑在真库上，读法是把 `NUXT_E2E_DB=1` 打开：

```bash
set -a && . ./.env && set +a
NUXT_E2E_DB=1 E2E_PORT=4142 npx playwright test test/e2e/notice-retry-db.spec.ts --reporter=line
```

**其一，`on conflict do update` 真的覆盖。** 同一人同一期先记 `failed`、再记 `sent`，表里只剩一行，后写盖掉前写：

```
[补做·真库upsert] {"头一次":"failed","记一次之后":["failed/not_configured"],
"第二次":"sent","行数":1,"那一行":{"status":"sent","reason":null,
"message_id":"<ca11bdeb-0944-bc59-a45d-9899f05fd8b6@substrate.test>",
"current_period_end":"2026-10-21T08:46:50.607Z"},"新到":1}
```

去重键两次必须是**同一个数**。这一列是 `timestamptz`，毫秒位也参与比较，各调一次 `Date.now()` 就成了两个不同的期，走两条 INSERT，冲突那条一辈子不撞——症状是"测了个假冲突、还全绿"。

**其二，抢在真并发下只让一位过。** 两趟补做同时放进去（`Promise.all`），一位抢到、另一位没抢到，替身只收到一封：

```
[补做·真库并跑] {"两趟":[{"名单人数":1,"抢到":1,"没抢到":0,"补发成功":1,…},
{"名单人数":1,"抢到":0,"没抢到":1,"补发成功":0,…}],
"抢到总数":1,"成功总数":1,"新到":1,"那一行":{"status":"sent",…}}
```

这一条是"不许重复"这句验收唯一的硬证据。把那个 `and status = 'failed'` 删掉，`抢到总数` 立刻变 2。

**其三，唯一约束不挡 `null`。** 没有任何订阅行的人，`最新周期末` 给 `null`；同一人这样记两次，表里是**两行**：

```
[补做·真库空期] {"记两次行数":2,"补做":{"名单人数":1,"抢到":1,"补发成功":1,…},
"补过之后":["sent/null","sent/null"],"新到":1}
```

Postgres 把两个 `null` 当成互不相同的值，所以那条 `unique` 兜不住这一族。上面代码里那一次"按人去重"不是保险起见，是这一族唯一的去重处。同时也能看出 `那一行(…)` 里为什么必须用 `isNull(periodEnd)` 写成 `eq(…, null)` 在库侧永远不成立（839 量过同族）。

## 一只替身要贯穿整份规格

这一档第一版给每条用例各起一只本地 SMTP 替身，结果 ② 那一段读回来是：

```
[补做·真库空期] {"补做":{"名单人数":1,"抢到":1,"补发成功":0,"补发仍失败":1,…},
"补过之后":["failed/transport_failed","failed/transport_failed"],"新到":0}
```

信没寄出去，可配的是活的替身。原因在 `server/services/auth/mailer.ts:22-35`：

```ts
let transport: Transporter | null = null
export function getTransport (smtpUrl: string): Transporter {
  if (!transport) transport = createTransport({ url: smtpUrl, … })
  return transport
}
```

`if (!transport)` 之后那个 `smtpUrl` 就再也不被看一眼。服务端进程是**长驻**的——模块作用域那个 `let` 活得比任何一次请求、任何一轮任务都久，所以"第一次寄到哪个端口，以后全寄到那里"。浏览器侧每进一页都重新建，这类状态不容易暴露；放到 Nitro 的运行时里，它就是第一个要想到的东西。

这在生产里不是缺陷（一个进程不会中途改 `NUXT_SMTP_URL`，要改就得重启），在测试里是：**一份规格只能有一个 SMTP 端点**。改成全档共用一只替身之后 ② 绿了；而"寄不出去"那一族（⑤）排到最后一条，进来先把那只替身关掉，让缓存着的连接自己撞墙，读到的才是真的 `transport_failed`。

## 四条改动，各撞红哪一档

新长出来的每一档都手动改坏一次产品代码，确认它会红：

| 改坏什么 | 红在哪 |
| --- | --- |
| 抢那条去掉 `and status='failed'` | 单测 ④ 的"按状态筛"变空 |
| 把"问规则"整块搬到发信之后 | 单测 ⑥ 发出了一封假话、⑧ 的顺序变 false |
| `refresh.ts` 里再叫一次发信 | ⑥ 的发信文件名单从 1 份变 2 份 |
| 发成功却不记那一行 | ① 少一格 `记通知`、补做 ① 读不到名单 |

四条红里，第二条同时红了行为档与形状档——这正是形状档存在的理由：运行时要换个场景才能造出"续上的人"，而源码里的先后一眼可查。

## 四种状态，与那一格今天收不回来的

| 状态 | 含义 | 下一轮还会问他吗 |
| --- | --- | --- |
| `sent` | 寄出去了，`message_id` 留着对账 | 不会 |
| `failed` | 没寄成，`reason` 是 `not_configured`／`transport_failed`／`no_address` | 会，这就是补做的名单 |
| `sending` | 已经被人抢走，正在发或已经死了 | 不会——**这里有个洞** |
| `not_due` | 发信前先问了规则：他不该再收这封信 | 不会（终态） |

那个洞照实写：**抢到之后进程死在发信中途，那一行永远停在 `sending`**。今天没有超时回收，也没有第三个进程去捞它。为什么不顺手补上——补它要么给 `sending` 配一个过期时刻（多一个数要定谁写谁读），要么让补做去猜"多久没落定就算死了"（那是把猜测写进钱相关的路径）。这一格留给下一站和收口那一站，别在这一站假装解决了。

## 撞上这些现象，先查这一行

| 现象 | 大概率是哪里 |
| --- | --- |
| 跑完补做，替身一封都没收到，`名单人数` 是 0 | 那一行是 `sending` 或 `not_due`，不在 `failed` 名单里 |
| `抢到` 有数、`补发成功` 是 0，`reason` 是 `transport_failed` | 同一个进程里已经建过 transport，换个端口不生效 |
| 表里同一人攒出两行 | 那一族的 `current_period_end` 是 `null`，唯一约束挡不住 |
| 服务层一写就报 `relation … does not exist` | 只跑了 `db:generate`，没跑 `db:migrate` |
| 单测全绿但你仍然不信幂等 | 假库不执行约束与并发，去跑那份带库的规格 |

带库那一趟今天的结果是 `359 passed, 46 skipped, 0 failed`，比上一站多出来的正好是这 5 条。那 46 条跳过不是"没测"，按它们自己那行跳过条件归族是四类：要外部服务变量 17、要内容目录读得到 14、要另一趟构建的开关 11、要库 4，合计正好 46。同一套用例不带库跑是 `260 passed, 145 skipped`，归族变成要库 77、外部服务 43、内容目录 14、另一趟开关 11。两趟相差 99 条，其中 73 条是"要库"那一族、26 条是"要外部服务变量"——这一条比总数有用：总数只能证明"跑了几条"，归族才答得出"少跑的那些各自缺哪一种环境"。两趟都没有落进"没归类"的那一档。

## 手边能验的三件事

1. 跑 `npm run test:unit -- notice-retry`，把那行 `[补做·形状]` 抄下来，再在 `notify.ts` 里删掉抢的条件跑一次——看它红在哪一条，比读十遍注释有用。
2. 连着跑两趟带库那份规格，第二次 `名单人数` 应当是 0（第一次已经把那位推进到 `sent`）。
3. 自己把 `②` 那条替身换掉：给每条用例各起一只，看 `补发成功` 变 0 时你会先怀疑谁。

## 还没闭合的那几格

- `sending` 的超时回收——今天没有人写那一格。
- 补做**还没有被谁叫起来**：`补发通知` 是一条能被调用的路，任务那一趟里没接它（接它要动那八个报回键的约定，那是下一站"一天跑两次与漏一天再跑"的事）。
- 多实例部署时，两个进程各自的排期会同时跑：抢这一条挡住重复发信，但挡不住重复降级那一路的读放大。
- 邮箱位为空记成 `no_address` 的人，补做还是 `no_address`——补地址这件事不在这一站的能力里。

下一篇是 858《定时触发与失败补做（5）：一天跑两次与漏一天再跑，两种形状各读一次》。同一件事的两种形状必须给出**不同**的答案：同一天第二次跑应当全 0，漏一天之后那一趟要能把该降的都降完——而半路抛错那一轮留在表上的形状，也是这一站埋下的那格 `error`。
