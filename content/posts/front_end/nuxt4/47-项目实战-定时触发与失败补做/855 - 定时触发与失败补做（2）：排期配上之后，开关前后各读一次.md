上一站把落点写在了配置旁边：每天跑一次归 `nitro.scheduledTasks`，执行者仍然是那一个任务。这一站动手配上。第一趟构建之后终端上多出来的是这一行：

```
[nitro]  WARN  Scheduled task subscription:refresh-roles is not defined!
```

它后面照旧跟着 `Build complete`，退出码 0。**这一站要讲的就是这一行的形状**：排期的名字写错，构建不会失败，服务也不会起不来，它只是永远不跑。

## 先配上，再把那三行撤掉

要配的东西就一行键、一行值，键是表达式、值是这一条排期要跑的任务名数组：

```ts
nitro: {
  experimental: {
    tasks: true,
  },
  scheduledTasks: {
    // 分 时 日 月 周 ⇒ 每天 03:10（机器本地时区）
    '10 3 * * *': ['refresh-roles'],
  },
}
```

表达式是给 croner 看的五位（分、时、日、月、周）。上一站留了一个报警器在 `test/unit/schedule-baseline.test.ts` 的 ② 档，专门问"这两个键各有几处"——开关只等于"目录会被扫"，什么时候跑是另一件事。配上之后把它撤掉再跑一次，两个读数必须不同：

```
[排期·两个键] {"开关处数":1,"排期处数":0,"在nitro节里":true}   ← 撤掉那三行
[排期·两个键] {"开关处数":1,"排期处数":1,"在nitro节里":true}   ← 配上
```

撤掉那一趟同时把新加的 ⑦ 档撞红了，红的话是这一句：`排期表读空了 ⇒ 这一档没在问东西（配置形状变了，或键名又换了）`。它不是回归，是这一档在报告"此刻没有东西可问"。报警器红过一次，"配上了"这件事才算被读到，而不是只被写进了文件。

## 名字这一位：任务自己写的说明，不是排期能点的那个

第一版 ⑦ 档是这样写的：从配置文件读出排期点的名，再从任务文件读出 `meta.name`，两边比逐字。七条判据全绿，而构建当场打出上面那句警告。**它核错了对象。**

注册名不是 `meta.name`。Nitro 扫 `server/tasks` 的时候，名字是拿文件路径推出来的（`nitropack@2.13.4` 的 `core/index.mjs:944`）：

```js
const name = f.path.replace(/\/index$/, "").replace(/\.[A-Za-z]+$/, "").replace(/\//g, ":");
```

所以 `server/tasks/refresh-roles.ts` 的注册名就是 `refresh-roles`。`meta.name` 里那句 `subscription:refresh-roles` 只是这份任务自己写的说明——853 那一站读的就是它，读得没错，但排期点不到它。想要带冒号的名字，只有一条路：把文件放进子目录，`server/tasks/subscription/refresh-roles.ts` 才会得到 `subscription:refresh-roles`。现在这一版是"文件在平级、说明带命名空间"，两套名字并存，⑦ 档把两边都读出来并排打印：

```
"已注册":["refresh-roles"],"meta名":["subscription:refresh-roles"],
"不一致":["server/tasks/refresh-roles.ts：subscription:refresh-roles ≠ refresh-roles"]
```

## 四趟构建，把两种失败分开

本站这一层的产物能不能被读到，靠的是构建自己打印的文件清单。四趟构建，配置只差那一行：

| 那一行怎么写 | 构建退出码 | 产物清单里的 `chunks/tasks/refresh-roles.mjs` | 那句警告 |
| --- | --- | --- | --- |
| 没有这一行 | 0 | 没有 | 没有 |
| 有，名字写 `meta.name` | 0 | 没有 | 一次 |
| 有，名字对、表达式只写四位 | 0 | 有，8.64 kB | 没有 |
| 有，名字与表达式都对 | 0 | 有，8.64 kB | 没有 |

第二行那一趟值得多说一句：不只是"这条排期被丢掉了"。名字写错之后，连任务自己的代码都没进生产包——`refresh-roles`、`/_nitro/tasks`、`runTask`、`startScheduleRunner` 这四个串在那趟 `.output/server/` 里逐条 grep，计数全是 0，跟"根本没配排期"那一趟一模一样。原因还是包内那几行：条目里的名字全部筛不掉就整条丢掉，丢光之后 `scheduledTasks` 写成 `false`，于是打包时这条支路没有任何人引用，任务文件被摇掉了。**后果是这台服务器上既没有定时跑、也没有手工触发**，因为那个任务在产物里根本不存在。

配上之后同一处读到的是这两串，⑥ 档把它们打印出来（只打印、不当判据）：

```
[排期·包内事实] {"版本":"2.13.4","入口有那句":true,"运行时有isTest早退":true,"配置默认值":true,
"产物":{"那一句":"[{\"cron\":\"10 3 * * *\",\"tasks\":[\"refresh-roles\"]}]",
"有任务chunk":true,"函数名grep命中":true}}
```

`函数名grep命中` 这一位在上一站读到的是 `false`——那时没有排期引用它，runner 整段被摇掉；这一趟是 `true`。

## 表达式写少一位，会在哪一刻炸

位数这种事，自己数空格是猜，交给 croner 本体问一次才是读数。⑦ 档把配置文件里那条表达式原样递过去（`{ paused: true }`：只解析，不真挂定时器），三种答案本站这一趟都拿到了：

```
{"表达式":"10 3 * * *","抛错":false,"下一次UTC":"2026-10-21T19:10:00.000Z",
 "下一次本机":"Thu Oct 22 2026 03:10:00 GMT+0800 (中国标准时间)"}
{"表达式":"10 3 * *","抛错":true,
 "消息":"CronPattern: invalid configuration format ('10 3 * *'), exactly five, six, or seven space separated "}
```

五位那一条顺手把"03:10 到底是哪一刻"量出来了：croner 没收到 `timezone` 就按进程所在机器的时区解释表达式，所以这一行在本机（UTC+8）是本地三点十分，写成 UTC 是前一天 19:10Z。同一份产物搬到 UTC 机器上，跑的时刻跟着那边变——页面给人看的那一列是按 UTC 出字的（840 定的），两件事别混在脑子里。

四位那一条更值得留意的是它**什么时候**才炸。构建不拦：那少写一位的表达式原样写进了产物，`scheduledTasks = [{"cron":"10 3 * *","tasks":["refresh-roles"]}]`，`Build complete` 照打。抛错发生在服务启动、runner 第一次 `new Cron()` 的那一刻。所以这两种失败要分开钉：**名字写错＝静默不跑，位数写错＝起不来**。⑦ 档因此两条都问：先数位数，再把表达式交给 croner，两条各一句红的话。

## 还是量不到的那一段

配上了不等于测到了。两处今天测不到，写清楚而不是假装测过。

一处是 `startScheduleRunner()` 的第一句 `if (!scheduledTasks || scheduledTasks.length === 0 || isTest) return`：测试模式下它根本不跑，所以端到端那一层量不到"到点自己跑"。另一处更麻烦——**它跑成功了也不出声**。runner 只在任务抛错的那条支路里打一行 `Error while running scheduled task "…"`（`runtime/internal/task.mjs:51-58`），任务本体这一路也没有日志行（853 记的）。于是就算把表达式改成每分钟、真的等它跑一次，只要它跑得顺，日志里不会有任何东西。今天能拿到的证据只到"包里有那条排期、有那个任务文件"为止，再多就没有了。

命令行那一条入口也帮不上：`nuxt task` 在本项目装的 nuxi 3.37.0 里根本没有这个子命令（853 量的 `USAGE` 十八条里没有它）。所以此刻这台站上，排期是唯一挂上了的执行者，而它"跑过没有"事后问不出来。这正是下一站要改的事：让那两个失败数落到一个能被追问的地方。

## 你自己跑一遍

```bash
cd Substrate
npm run build
npm run test:unit -- schedule-baseline   # 7 档，全离线
npm run check                            # 八项
```

想复现那四种形状，改 `nuxt.config.ts` 里那一行再各跑一次上面两条就够，不用等时钟。

| 撞上的现象 | 原因与读法 |
| --- | --- |
| 构建打了一句 `Scheduled task … is not defined!`，但构建成功 | 排期点的是注册名，不是你 `meta.name` 里那个；这条排期已经被丢掉，任务代码也没进包 |
| 什么提示都没有，可它就是不跑 | 先跑 ⑦ 档看 `对不上` 与 `已注册` 这两格，别看日志——名字写错只有构建期那一句警告，没人会去翻它 |
| 服务启动即报 `CronPattern: invalid configuration format` | 表达式不是五位；构建不拦这一位，产物里就写着那串错的 |
| 页面看到的到期时间是 UTC，任务却在本地时刻跑 | 表达式按进程本机时区解释。要么统一按 UTC 配，要么给排期明确时区，别指望两边一致 |
| ⑦ 档红在"排期表读空了" | 那一行被撤掉了。这条红是它在报告"此刻没东西可问"，不是回归 |

这一站改完，仓库里跑出来的数：`npm run check` 退出码 0（八项全过，单测 63 个文件、组件层 16 个文件），不带库的全量端到端 260 passed／140 skipped，带库那一趟 351 passed／1 failed／46 skipped／2 did not run——红的那一条是下单按钮那一路的 846⑤，报的是 30 秒超时，单独把那份文件跑一次 5 条全过，与本站的改动无关（一趟全量的绿红不能当结论，这条规矩在 841 记过）。换到第二趟带库（换个端口再跑一次）红的是另外两个规格，报的还是 30 秒超时。三处红都落在要读库的档上，形状一样：**那一趟慢的是远端连接，不是判据**。

下一站（856）《定时触发与失败补做（3）：跑完的那组数要落到能被看见的地方》：把 `审计失败`、`发信失败` 从"终端上闪过的一行"变成事后能被问出来的东西，同时不开第二个写入者。
