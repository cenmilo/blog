上一站把排期配上了：`'10 3 * * *': ['refresh-roles']`。今天早上你想确认昨晚那一次到底跑没跑，能查的地方只有 `audit_logs`——它读到 **0 行**。这 0 行有三种可能：压根没跑、跑了但没人到期、跑了但审计写失败。三种在表里长得一模一样。

这就是本站要补的格子，而且它不是"再多加两行日志"那么轻：

- 排期的执行者成功时不出声。包内 `runtime/internal/task.mjs:51-58` 只在任务抛错那条支路里打一句 `Error while running scheduled task "…"`，跑顺了什么都不说。
- 任务这一层本来就没有日志行（851 记的那条取舍：留痕的入口吃一个请求事件，而任务里没有请求事件）。
- 库里八张表没有一张记着"上一轮"（854 量的：审计行只有 `ts`／`actor`／`action`／`target`／`meta`／`request_id`）。

## 三个位置，为什么选新表

| 位置 | 能不能事后追问 | 代价 |
| --- | --- | --- |
| 往 `audit_logs` 塞一行整轮汇总 | 能，一句 SQL | 那张表的定义是"一行＝一次改了谁的什么"，`target` 是 `notNull` 且一直存用户 id。整轮没有"被改的那个人"，只能塞假值——于是任何按 `target` 连用户的读法都会捞到一行不是人的记录，而 853 那条"第二次跑不重复留痕"恰恰是按 `target` 数的 |
| 只往标准输出打一行 | 只在进程活着的时候能 | `audit.ts` 自己的头注释写着日志行会被容器轮转掉。追责要的是进程没了还读得到 |
| 新开一张 `task_runs`，一轮一行 | 能，且列名各归各位 | 要生成迁移、要跑一次迁移；这张表自己也得有唯一写入者 |

选第三个。决定与两条反面理由写进表文件头，别只留在提交信息里：**两个含义不许挤在同一列**（`0` 与 `null` 那次是 840，两种 `null` 靠 `trigger` 分开那次是 851，这一次是 `target`），而**"能被追问"这件事的门槛是进程死了还在**。

表就十四个格子，八格计数与任务报回的那八个键一一对应：

```
db/migrations/0005_unusual_hemingway.sql
CREATE TABLE "task_runs" (
        "id" bigserial PRIMARY KEY NOT NULL,
        "task" text NOT NULL,
        "trigger" text NOT NULL,
        "started_at" timestamp with time zone NOT NULL,
        "finished_at" timestamp with time zone NOT NULL,
        "error" text,
        "candidates" integer,
        "processed" integer,
        ...
);
```

前四格不可空、八格计数可空——这个不对称就是这一站的设计。

## 空与 0 不是一回事

凌晨那趟如果连名单都没读到就抛错了，"候选人数"这一格该写什么？写 `0` 就是编一个读数：`0` 的真含义是"库里一个 `member` 都没有"，而当时的真相是"根本没问到"。所以抛错那一轮八格交 `null`、`error` 那一格写句子，**然后错照样往外抛**——这一层的职责是留证据，不是替上面决定这算不算失败。判据里读到的形状是：

```
[痕迹·抛错那轮] {"抛没抛":"抛了","那一行":{"task":"subscription:refresh-roles","trigger":"unknown",
"error":"Failed query: select \"id\", \"email\" from \"users\" where \"users\".\"role\" = $1\nparams: member",
"candidates":null,"processed":null,"not_downgraded":null,"read_unchanged":null,
"audit_rows":null,"audit_failures":null,"mail_sent":null,"mail_failed":null}}
```

`error` 里那句是打包器给的原样（`Failed query: <那一条 SQL> params: …`），它自己就说清了卡在哪一步——不用翻日志也知道是问名单那次炸的。

而正常一轮，八格与递出的八个数逐格对上（判据按那条 INSERT 的列名与它绑定的参数 zip，不硬编码列顺序）。这里踩到一个小坑：第一版按位置直接 zip，读出来整行错一格、`mail_failed` 直接消失——因为自增主键那一列在语句里写的是 `default`，**不占参数位**。

```
[痕迹·一轮] {"那一行":{"id":"(这一列没绑参数)","task":"subscription:refresh-roles","trigger":"manual",
"error":null,"candidates":3,"processed":1,"not_downgraded":1,"read_unchanged":1,
"audit_rows":1,"audit_failures":0,"mail_sent":0,"mail_failed":1},
"递出":{"候选人数":3,"处理行数":1,"没降":1,"读到没改动":1,"审计行数":1,"审计失败":0,"发信成功":0,"发信失败":1}}
```

## 谁叫起这一轮：三态，读不出就写 unknown

`defineTask` 那份 `run()` 其实收得到一个事件对象（包内类型是 `{ name, payload, context }`），而排期那条路会递来 `{ scheduledTime }`。所以"是被排期叫起的、还是被人叫起的"这一位有证据可用。

注意那一串 `scheduledTime` 的真实身份：包内它在循环外构造一次（`task.mjs:47-49`），是 **runner 起动的时刻**，每一次触发都拿到同一个数。所以本站只用它"在不在"，绝不写进 `started_at`——两个时刻都由任务层自己读钟。

```
[痕迹·触发来源] {"没有事件":"unknown","空对象":"unknown","负载是空的":"manual","带排期那一刻":"schedule"}
```

`manual` 这一格的真含义是"被叫起时负载里没有排期那一刻"，**别把它读成"有个敲命令的人"**：端到端那趟直接调 `run()`、连事件都没有，读到的是 `unknown`。三种取值各留各的位置，是 840 那条"两种'没有'不许混"在这一层的形状。

## 跑两轮留下几行

这是最容易被读歪的一格。**审计按人记，痕迹按轮记**，所以跑两次应该是：库里那个人的审计行还是一条（不重复降），而 `task_runs` 有两行（每轮都跑过）。真库上跑出来的两个读数放在一起才说得清这件事：

```
[收口·真库跑两次] {"第一次":{"候选人数":1,"处理行数":1,"审计行数":1,"发信失败":1},
"第二次":{"候选人数":0,"处理行数":0,"审计行数":0,"发信失败":0},
"库里":{"role":"free"},"审计行数":1,"痕迹行数":2,
"痕迹":[{"trigger":"unknown","candidates":1,"processed":1,"mail_failed":1,"error":null},
{"trigger":"unknown","candidates":0,"processed":0,"mail_failed":0,"error":null}]}
```

第二行那八个 0 不是重复劳动的证据，是"这一轮确实跑了、只是没人该降"的证据。有了它，`0 行`这个读数才只剩一种解释：**没跑**（或者痕迹没写进去，见下一节）。

那一条 INSERT 本身失败怎么办——库断了、表还没迁移。这时**业务那半边一个数都不许变**（人已经降了、信也没发出去这件事照样报出来），只多一行 `task_run_write_failed`：

```
[痕迹·写失败] {"报回":{"候选人数":3,"处理行数":1,"发信失败":1},"发过那条INSERT":1,
"日志":"{\"ts\":\"…\",\"level\":\"error\",\"msg\":\"task_run_write_failed\",\"task\":\"subscription:refresh-roles\",…}"}
```

于是"库里读不到行"仍然有两种解释（没跑、或这一行的写失败）。差别今天只能靠标准输出，这一格进未闭合——**别把这张表当成绝对可靠**。

## 这一站的判据动到的四处老账

落点一立，四条老判据随形状改，都是登记而不是抹红灯：

| 动了什么 | 现象 | 为什么这样改 |
| --- | --- | --- |
| 854 留的第二个报警器 | `有轮次位的文件` 由 `[]` 变成 `['db/tables/task-runs.ts']`，八张表名单变九张 | 它红过一次才算"落点被读到"；期望挪成"只有这一处"，以后再长一处照样红 |
| 任务层读钟的处数 | 两条老判据都钉"读一次钟"，现在总数是 3 | 判定用的还是那一次（`const 开始`），另两次只写进痕迹的结束时刻。所以**分成两类各数一遍**，并补一条"交给服务层的那个必须是 `开始`"——继续数总数就把设计意图数没了 |
| `meta.name` 提成常量 | 849 那档用正则读 `name: '…'` 的字面量，读成 `(没有)` | 同一串名字还要写进 `task_runs.task`，拼两遍就会长出第三种名字。判据改成"认字面量，认不到就顺着标识符读它的 `const`" |
| 830 那档"最新那份迁移里有这两条建表语句" | 856 一追加迁移，它立刻红 | "最新"是那一刻的属性，不是那两张表的属性。改成**按内容找**：哪一份里有那两条 `CREATE TABLE` 就读那一份 |

新档那边也配了变异：摘掉两处留痕 ⇒ 五档一起红；抛错那轮改成写 0 ⇒ 只有那一格红；把 `unknown` 兜成 `manual` ⇒ 只有三态那档红；把 `started_at` 写成 `scheduledTime` ⇒ 行为档与形状档同趟各红一次；新开一个写入者 ⇒ 只有写入者名单那档红；八格里挑一格改 `NOT NULL` ⇒ 同样只有形状档红（假库不 enforce，这正说明形状档在补行为档看不见的那一段）。

## 你自己跑一遍

```bash
cd Substrate
npm run db:generate      # 表定义变了就要生成迁移
npm run db:migrate       # 换机器或新库：这一跑之后才有 task_runs
npm run test:unit -- task-run-record   # 7 档，全离线
npm run test:unit -- schedule-baseline  # 7 档
npm run check
E2E_PORT=4133 NUXT_E2E_DB=1 NUXT_STRIPE_WEBHOOK_SECRET=whsec_本地专用 \
  npm run test:e2e -- role-refresh-db   # 6 档，要连库
```

连接串放你自己的开发库，别贴进仓库；`whsec_…` 那个值是本地专用的假密钥，只用来让带库那一趟不静默跳过。

| 撞上的现象 | 原因与读法 |
| --- | --- |
| 端到端那档报" relation task_runs does not exist" | 迁移没跑。`db:generate` 只写 SQL 文件，`db:migrate` 才建表 |
| 库里一行痕迹都没有，可任务确实跑了 | 看标准输出有没有 `task_run_write_failed`。没配库时 `databaseUrl` 是空的，那一档直接返回 false，本来就不写 |
| `trigger` 全是 `unknown` | 你是直接调 `run()` 的（单测与端到端都这样）。要读到 `schedule`，得让 Nitro 那条排期路真去叫它 |
| 抛错那轮的八格读出来是 `0` 而不是空 | 有人图省事写了默认值。这一格的后果是"今天没跑"与"跑挂了"再次阅读不出来 |
| 追加一份迁移后，某条老判据突然红 | 先别看产品：搜一下判据里有没有"最新那份"这种按位置写的问法，那类断言只是当时成立 |

这一站跑完，仓库里读到的数：`npm run check` 退出码 0（八项，单测 64 个文件／410 条，比上一站多 8 条，新增的那一档在 `task-run-record`），不带库全量 4134 **260 passed／140 skipped／0 failed**（归族 72/43/14/11），带库全量 4135 **354 passed／46 skipped／0 failed**（归族 17/14/11/4；这一趟是连续两站之后第一次拿到 0 失败，慢的时候同一条命令会红在别的规格上，所以每一趟都要带上端口记名）。

下一站（857）《定时触发与失败补做（4）：发信失败与审计失败要能补做，补做不许重复》：`task_runs` 里那两格失败的数第一次有了能被读回来的地方，这一站要让它变成动作——读回"上一轮失败的是谁"，只对那几位重做，而且同一个人不许被通知两次。
