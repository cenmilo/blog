## 你屏幕上现在有的东西

走到这里，项目里多了三样东西：`nuxt.config.ts` 那一行 `'10 3 * * *': ['refresh-roles']`、一张每轮留一行的 `task_runs` 表、一条先补信再降人的任务。测试一片绿。

现在把当初立项时写的那份设计文档翻开，里面有一句：

> 到期降级任务可手工触发并有日志

刚才那一片绿，证明这句了吗？只证明了一半，而且证的是便宜的那一半。这一站不加实现，只量"绿灯"与"验收句"之间的差额——收口最容易犯的错，就是把跑出来的绿灯当成那句话已经交付。

## 第一件事：把那句验收在文档里的**全部写法**找出来

不要只挑最像的那一行，关键词一次搜完：

```bash
grep -n '到期降级\|降级任务\|subscriptions.downgrade\|每日\|定时' \
  docs/superpowers/specs/2026-10-13-nuxt4-project-series-design.md
```

本轮命中 6 行：15、17、30、139、178、213。逐句判下来：

| 行 | 文档里的写法 | 判定 | 依据的读数 |
| --- | --- | --- | --- |
| 15 | 做到最后手上有一个「注册→付费→会员区→后台→定时任务→日志」通着的站 | 做到一半 | 排期配上、任务代码进了生产包；「到点自己跑」一次都没量到 |
| 17 | 到期降级任务**可手工触发并有日志** | 前半做到，后半没做 | 「手工触发」＝那段代码能被叫起来连跑两次，第一次 `处理行数:1`、第二次全 0；「有日志」＝没做 |
| 30 | 管理后台要有「每日到期降级任务」 | 做到一半 | 表达式在 `nuxt.config.ts:82`；可主语是后台，而后台今天没有任何地方读那张痕迹表 |
| 139 | 文件名 `subscriptions.downgrade.ts`、键 `nitro.tasks.cron`、降 role、写审计、发提醒、`nuxt task` 触发 | 四件事四种结果 | 见下面逐条 |
| 178 | 文章清单里那一行写着「到期降级」 | 不算验收 | 那一行说的是这串文章要讲什么，撞了四个字，不构成任何交付 |
| 213 | M8 的验收：「降级任务手工触发日志与 DB 变更」 | 只做到 DB 变更 | `member` 变 `free` 端到端读得到；日志与 CLI 入口读不到 |

第 139 行那一处最值得说，它是一句话里塞了四件事：

- 文件名。文档写 `subscriptions.downgrade.ts`，站上实际是 `refresh-roles.ts`；任务自己写的名字是 `subscription:refresh-roles`，排期里点的却是按路径派生的注册名 `refresh-roles`。这一条不许写成「等价已交付」。
- 键名。文档里的 `nitro.tasks.cron` 这个键不存在，真正生效的是 `nitro.scheduledTasks`——属文档写错，不是本站漏做。
- 三个动作：降 `role`、写 `audit_logs`、发提醒邮件——都做了；降级有 `returning`，发信失败不回滚降级。
- CLI 触发。本轮重新量了一次：

```bash
node -e 'console.log(require("@nuxt/cli/package.json").version)'   # 3.37.0
node -e 'const s=require("fs").readFileSync("node_modules/@nuxt/cli/dist/index.mjs","utf8");
  for(const n of ["dev","build","start","generate","add","prepare","info","task","_task"])
    console.log(n, s.includes(`"${n}"`))'
```

14 个已知命令名里 9 个在，`task` 与 `_task` 都是 `false`。所以「用 `nuxt task` 手工触发」这一头的入口**今天不存在**，能跑的只有把 `run()` 当函数调两次那条路。

「有日志」那半句，量法很直接：

```bash
grep -rn 'console\.' server/tasks          # 命中 0
grep -rn 'console\.' server/services/task-run.ts server/services/billing/notify.ts
```

后一条只有两处命中，而且都在**失败分支**上（`task_run_write_failed` 与发信失败各一行）。正常跑完一轮，进程不出声。所以这句剩下的不是尾巴，是整半句：痕迹在库里，日志这一路今天没有。

## 第二件事：把这条线的三十八档判据按「能证伪到什么程度」分档

六站攒下 37 档，本站加 1 档，共 38 档：

| 判据文件 | 档数 | 行为档 | 形状档 | 这一份能钉住什么 |
| --- | --- | --- | --- | --- |
| `test/unit/schedule-baseline.test.ts` | 7 | 0 | 7 | 全站扫「有没有东西会自己开始」、两个开关键、表列名单、注册名逐字相等 |
| `test/unit/task-run-record.test.ts` | 7 | 5 | 2 | 跑一轮看十五格怎么填、抛错那轮交 `null`、痕迹写失败不阻断业务 |
| `test/unit/notice-retry.test.ts` | 8 | 7 | 1 | 假库跑任务读语句与名单；补做不改 `users`；两种抢占走向 |
| `test/e2e/notice-retry-db.spec.ts` | 5 | 5 | 0 | 只能上真库的：唯一约束不挡空值、同时补做恰好一位抢到 |
| `test/unit/retry-window.test.ts` | 6 | 5 | 1 | 两种形状给出不同读数；先补后降的顺序 |
| `test/e2e/retry-window-db.spec.ts` | 4 | 4 | 0 | 两种形状落到真库，两封信的先后 |
| `test/unit/task-run-closure.test.ts` 的 ⑦ | 1 | 0 | 1 | 上面六份文件本身：名单逐字、档数只增不减、没有永久跳过 |
| 合计 | 38 | 26 | 12 | 其中 9 档必须带库才跑 |

这份表里最扎眼的是第一行：**排期那七档全是形状档，一条行为档都没有**。不是偷懒，是量不到——包内那个排期 runner 在测试环境直接不起跑，真跑成功时也不打日志。于是「每天三点十分自己跑了一次」没有任何一档能证伪，报告要照实写「未覆盖」，不许因为形状档绿了就归进行为。

形状档还有一层脆弱：它钉的是源码现在的写法。`retry-window` 那条形状档能钉住「先补后降」，靠的是比对两处调用的先后——把这两行调换顺序它会红，把函数改名它就不认识了。所以形状档旁边必须有行为档兜着。

## 第三件事：验一下这套账本本身不是空的

收口档最容易写成「读的是空气」。两条变异，各撞一次红，撞完撤掉。

第一条，把账本里某个期望档数改成不可能的数：

```
' test/unit/notice-retry.test.ts': 99,   // 本来是 8
```

```bash
npm run test:unit -- task-run-closure
```

本轮打出来的读数：

```
[收口·二线账本] {"实际":{"test/unit/schedule-baseline.test.ts":7,
"test/unit/task-run-record.test.ts":7,"test/unit/notice-retry.test.ts":8,
"test/e2e/notice-retry-db.spec.ts":5,"test/unit/retry-window.test.ts":6,
"test/e2e/retry-window-db.spec.ts":4},"期望合计":128,"总数":37,"对不上":
["test/unit/notice-retry.test.ts：8 < 99"],"缺文件":[],"永久跳过":[]}
```

第二条，往其中一份判据文件里塞一句永不执行的永久跳过（`if (false) { describe.skip('变异探针', () => {}) }`），这一档立刻报出是谁：

```
"永久跳过":["test/unit/retry-window.test.ts"]
```

两条都红过，说明这份账本既能发现少一档，也能发现有一档被永久摘掉。改回去之后：

```
[收口·二线账本] {"实际":{...同上六个数...},"期望合计":37,"总数":37,
"对不上":[],"缺文件":[],"永久跳过":[]}
```

这里要分清两种 skip。`test.skip(条件, '要库')` 是**报环境不具备**，合法，全量跑完按族数一遍即可；`it.skip('这一档', fn)` 与 `describe.skip` 是把用例**永久摘掉**，收口不许靠它变绿。

## 第四件事：把没闭合的池子逐条重新量一遍

池子里的条目都是上一站记下的说法。**传话会把已经修掉的和从来没这回事的一起跑进来**，所以每条都要重量一次现状：

| 池子里那条说法 | 本轮重量 | 结论 |
| --- | --- | --- |
| 停在 `sending` 的人没有超时回收 | `notify.ts` 里「超时」只出现在一行注释，写的就是「今天仍然没有超时回收」 | 仍在 |
| 审计失败那一路没补做 | 服务端 11 处命中，全在计数与报回，没有补做消费它 | 仍在 |
| 那张痕迹表没有读者 | `server/api/` 与 `app/` 里含这张表名的文件 0 个 | 仍在 |
| 多实例下没人协调 | `server`、`shared`、`app` 三处 `pg_advisory` 命中 0 | 仍在（那把锁只在测试里） |
| `infinity` 与空周期末同形 | 两处目录里 5 处命中，全是注释，代码没有分支 | 仍在 |
| 订阅只摊开一行 | `read.ts:50-51` 仍是 `orderBy` 加 `limit(1)` | 仍在 |
| 没有发票页 | `app/pages` 只有 console、docs、index、me、两个 lab | 仍在 |
| `/api/_health` 整站不存在 | 全仓 `_health` 命中 1 处，而且是一条注释 | 仍在 |
| 顶层开关够不够 | 开的是 `experimental.tasks`；只写 `$production.nitro` 够不够从没测过 | 仍在 |
| 「归族看不到主动让路」 | 归族脚本第 26 行就有这一族，本轮也打出了 4 | 早就看得到，这条是传话传错的 |

十条里只有一条是过时说法，而它必须靠重新量才能发现——这就是收口站不写新判据、仍然要把池子重数一遍的理由。

## 剩下的格（想改代码的冲动都写在这里）

按能被验收的顺序：

1. **给那张痕迹表一个读者**：一个后台页，或一个只回最近十行的接口。没有读者，那张表就只是只写不读，文档第 30 行那句「后台有每日任务」永远停在做到一半。
2. **补一条任务层的日志行**：成功一轮至少出声一次，报任务名、来源和那几个计数。这直接结掉第 17 行的后半句。
3. **`sending` 的超时回收**：抢到之后进程死在发信中途，那一行就永远停在那里。今天只能读出"有几个人卡着"，捞不出他们。
4. 审计失败也纳入补做名单：现在补的是信，审计少的那一行没人管。
5. 命名并轨：把任务文件挪进子目录，让注册名与 `meta.name` 一致。这要动文件，本站不动。
6. 带库全量要允许重跑：远端库慢时会整档 30 秒超时，某一趟的红往往是连接额度而不是判据属性，结论得逐趟具名。

## 三个容易写歪的地方

| 症状 | 为什么 | 怎么办 |
| --- | --- | --- |
| 报告写「验收已达成，因为有 `task_runs` 表」 | 把「有痕迹」当成「有日志」，两回事 | 那句验收拆成两个动作分别判，读数分开贴 |
| 任务文件改了名，报告仍写「按文档做了」 | 文件名与任务名本身就是那句话的一部分 | 名字不同就写没做，改不改是另一站的事 |
| 全量绿了就宣布收口 | 排期这一路一条行为档都没有 | 未覆盖那格单独成段，别放进「已通过」的表里 |

## 这一站跑完的几趟读数

`npm run check` 八项 rc=0；单测 425 档通过、66 个文件（多的那档是本站的账本档）；不带库全量第一趟红一档、2 档没跑，红的正是已知闪红的 `test/e2e/landing.spec.ts:179`，重跑一趟 260 通过、149 跳过、0 失败；带库那一趟 362 通过、47 跳过、0 失败，归族要外部服务变量 17、要内容目录 14、要另一趟构建的开关 11、要库 5。

带库那一趟还顺手量到本线一直挂着的一件事：痕迹表里 `trigger` 那一格，端到端读出六次全是 `unknown`——测试自己把 `run()` 当函数调，没有排期负载，这一格只能报"读不出来源"。想看到 `schedule`，得等一次真的定时触发，而那一头正是前面量不到的。

第二十三条线从 860 开始，选题就从上面那张「剩下的格」里挑：读者、日志、回收，任何一件都够走一站。
