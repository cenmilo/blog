设计文档里那句写得很干脆：任务每天把过期未续的人降回 `free`，写在 `nitro.tasks.cron` 里。可你今天把这条链跑完，**没有任何东西会自己开始**——上一站手工调了两次才降下来的人，如果没人再敲那两下，会一直挂着 `member` 到明天。这一站不写产品代码，只把这句话量成五个能复跑的读数，再定下落点。

## 五个问题，各一个读数

盘点档 `test/unit/schedule-baseline.test.ts` 六条判据，问的都是能撞红的形状，不是主题词。

```
[排期·自己会开始] {"名单":[],"处数":0,"前端":[]}
[排期·两个键] {"开关处数":1,"排期处数":0,"在nitro节里":true}
[排期·痕迹] {"全部表":["audit_logs","login_tokens","meter_events","ping","sessions","stripe_events","subscriptions","users"],
"审计列":["ts","actor","action","target","meta","requestId"],"有轮次位的文件":[]}
[排期·执行者] {"写users的文件":["server/services/billing/refresh.ts"],"任务文件":["server/tasks/refresh-roles.ts"],"排期里的任务名":[]}
[排期·谁在读失败数] {"服务端":["server/services/billing/refresh.ts","server/tasks/refresh-roles.ts"],
"前端":[],"除写它与递它之外的读者":[]}
```

| 问的 | 读到什么 | 这句话的意思 |
| --- | --- | --- |
| 有没有东西会自己开始跑 | 服务端 `setInterval(`／`setTimeout(`／`startScheduleRunner(`／`scheduledTasks`／`\bcron\b` 全 0 | 今天没有执行者，一行都没有 |
| 开关与排期 | `tasks: true` 一处；`scheduledTasks` 0 处 | 开关开了只等于"目录会被扫"，不等于"什么时候跑" |
| 跑过的痕迹 | 八张表，没有一张记着轮次；审计行只有 `ts`／`target`／`meta` | 只能反推"有人被降过"，推不出"这一轮跑成什么样" |
| 执行者几家 | 写 `users` 的只有 `refresh.ts` 一份 | 848 定的落点仍然成立 |
| 两个失败数有谁读 | 除了写它的与递它的，没有别人 | 数已经报出来了，但没人看 |

第四行那句要说明白：`发信成功`／`发信失败` 是任务的返回值，跑一次终端上就闪过一行。跑得没人敲的时候（也就是"每天一次"本该发生的那种情形），**这两个数连闪过的机会都没有**。

## 排期这条路，实现里写死了三件事

Nuxt 那一节只给命令行入口（`nuxt task list` / `nuxt task run <名字>`），并且明说它是"对着为你项目跑起来的 `nuxt dev` 服务器说话"；任务本体与排期都被指向 Nitro 那一节。`nuxt.config.ts` 里的 `nitro` 那一节原话就是"Configuration for Nitro"，再往下指。所以要想知道"配上去会由谁执行"，只能读装进来的那一份实现（`nitropack@2.13.4`）：

```
[排期·包内事实] {"版本":"2.13.4","入口有那句":true,"运行时有isTest早退":true,"配置默认值":true,"产物grep命中":false}
```

1. 节点运行入口里那句是 `if (import.meta._tasks) { startScheduleRunner() }`——**排期与任务是同一个开关管的**，而且是构建期决定的。
2. `startScheduleRunner()` 里第一句就退回：`if (!scheduledTasks || scheduledTasks.length === 0 || isTest) return`。前半个条件是"没配就等于不起"，最后那一位是**测试模式下它根本不跑**——这决定了下一站"配上去之后能不能被端到端量到"的答案。
3. 配置项的默认值是 `scheduledTasks: {}`，键名以 `nitro.` 开头传给 Nitro。设计文档里写的那个 `nitro.tasks.cron` **不是这个名字**，照它配会静默无效。

那个 `产物grep命中: false` 只打印、不当判据。产物是打包过的，查不到字符串不能证明没接线（这条纪律在 846 记过）；要证"生产里能不能触发"，靠的是上一站那条对着活服务器问一次的判据（`/_nitro/tasks` 读 404，而对照路由读 401）。

## 落点：排期归 Nitro，执行者仍只有一个

决定写在 `nuxt.config.ts` 的 `nitro` 那一节旁边，因为要配的就是那一节：

```ts
// 854 定下的落点：**"每天跑一次"归 `nitro.scheduledTasks`，
// 执行者仍只有 `subscription:refresh-roles` 这一个任务**。两条代价照实记：进程内的定时器
// 意味着多实例部署会各跑一遍（降人这一头由那条 `and role = 'member'`＋`returning` 兜住，
// 提醒信会重复发），重启期间没有窗口补偿。
```

三条路里为什么不选另两条：**再加一个任务**会让"谁改了 `users.role`"变成两家（判据里那条名单会红，症状却是"一半对一半永远不动"那种排查不出的东西）；**开一条本站自己的内部 HTTP 入口给外部调度器打**，等于新造一个必须鉴权的路由，而这条链今天还没有那个需求；**什么也不配、只靠人敲**就是现在的状态，量出来正是这一站要写的。**代价留在这里不藏着**：单实例下今天没问题，多实例要等"提醒信不重复发"那一格补上才敢横向扩。

## 这一站的判据自己也露过一次盲区

盘点档第一版扫目录时只认 `.ts`。于是问"界面有没有长驻定时器"、"有没有人在页面上读那两个失败数"这两条，**一辈子看不见 `.vue` 文件里的答案**——而本项目 `app/components/islands/IslandGate.vue` 里正好就有一个 `setTimeout`（那个是界面去抖，不该算执行者，但它证明了这个目录里有 `.vue` 代码）。补上 `.vue` 之后，把 `发信失败` 写进 `app/pages/console/index.vue` 立刻红：

```
× ⑤ 那两个失败数，今天没有任何人读
AssertionError: 界面开始读这两个数 ⇒ 856 那一站的落点已兑现，这一档要改期望:
expected [ 'app/pages/console/index.vue' ] to deeply equal []
```

同趟还验了另外四处：**服务端加一个 `setInterval`** ⇒ 只有 ① 红；**配置里加一行 `scheduledTasks: {}`** ⇒ 只有 ② 红（这一条是故意留给下一站的报警器：真配上排期，它必须红，红了才说明"配了"这件事被读到）；表里造一个带 `heartbeat` 的名字 ⇒ 只有 ③ 红；**在另一份服务文件里再写一次 `users`** ⇒ 新判据与 848 那份老判据**同趟都红**（两家执行者这件事不该只有一处看得见）。

## 顺手补的一处：等锁要有上限

带库那一趟今天红了五趟里的两到三条，红的规格每趟都不一样，错都是 `connect ETIMEDOUT …:5432` 与 `Test timeout of 30000ms exceeded`——远端库慢，不是代码坏。但顺着这条线查出另一件真风险：上一站那把锁用的是无限等的 `pg_advisory_lock`，而 Playwright 每条用例默认只给 30 秒；批量写那份规格有六档、每档都占着锁跑几秒，**排在后面的规格可能把整条预算等光**，症状就是一条与产品无关的超时红灯。改成 20 秒轮询、等不到就让路并说出等了多久（`[锁·等不到] {"已等毫秒":…}`），两份用锁的规格同跑一次仍是 9 条全过。

## 你自己跑一遍

```bash
cd Substrate
npm run test:unit -- schedule-baseline   # 6 档，全离线
npm run check                            # 八项
```

| 撞上的现象 | 原因与读法 |
| --- | --- |
| 你按设计文档写了 `nitro.tasks.cron`，什么都没发生 | 键名不对，实现里读的是 `nitro.scheduledTasks`；配错了不报错，所以要先读到"两处不同答案"再说它生效 |
| 配上排期后端到端还是量不到 | `startScheduleRunner()` 在 `isTest` 下直接退回——这一段本来就测不到，要写清楚而不是假装测过 |
| 全库扫描那两条判据红了，但你没动产品 | 先看红的是哪一处名单：多半是新增了一份会建 `member` 探针或会写 `users` 的规格，那是要登记的形状变化 |
| 带库那一趟红在互不相干的规格上 | 先复测连通再判回归；本机的库走 IPv6 时最容易撞这个（`dns.lookup` 给 IPv6、`resolve4` 报 `ENODATA`） |

下一站（855）兑现这个落点：把 `nitro.scheduledTasks` 配上，配前配后各读一次，并且老实写出"哪一段仍然量不到"。

## 本文依据

- `docs/4.x/api/commands/task`——命令表与"这条命令对着为你项目跑起来的 `nuxt dev` 服务器说话，`--url` 可指向另一台"；任务本体与配置在那一节里被转到 Nitro 的文档去。
- `docs/4.x/api/nuxt-config` 的 `nitro` 那一条——原文只有一句"Configuration for Nitro"再指向 Nitro 的配置文档，所以 `scheduledTasks` 这个键在 Nuxt 这边没有说明，读了实现才敢配。
- `docs/4.x/directory-structure/server`——`server/` 下各目录的分工；`services/` 不成为路由，所以执行者与写者各自只有一处，这两条才可能被判据钉住。
- `nitropack@2.13.4` 包内三处（`presets/node/runtime/node-listener.mjs`、`runtime/internal/task.mjs`、`core/index.mjs` 里 `scheduledTasks: {}` 那行默认值）——排期的执行方式与"测试模式下不起跑"来自这里，Nuxt 文档没写。
