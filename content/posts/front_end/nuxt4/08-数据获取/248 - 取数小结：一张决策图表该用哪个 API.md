## 一、先认人：这一族都有谁

| 成员 | 官方定位句 | 它是什么 |
| --- | --- | --- |
| `$fetch` | "Nuxt uses ofetch to expose globally the `$fetch` helper for making HTTP requests" | 纯请求，不带 payload 通道 |
| `useFetch` | "a convenient wrapper around `useAsyncData` and `$fetch`" | URL 进、数据出，自动 key |
| `useAsyncData` | "provides access to data that resolves asynchronously in an SSR-friendly composable" | 任意异步函数进，数据出 |
| `useLazyFetch` | "is equivalent to `useFetch` with `lazy: true` option set." | 只改导航是否阻塞 |
| `useLazyAsyncData` | "a wrapper around `useAsyncData` that triggers navigation before the handler is resolved by setting the `lazy` option to `true`" | 同上 |
| `createUseFetch` / `createUseAsyncData` | "A factory function to create a custom useFetch composable with pre-defined default options." | 造带默认值的组合式，宏 |
| `defineUseFetchAddon` / `defineUseAsyncDataAddon` | "defines a reusable extension for `useFetch` composables created with `createUseFetch`" | 给工厂造的组合式加行为 |
| `useNuxtData` | "gives you access to the current cached value of `useAsyncData`... with explicitly provided key" | 读那一格，可写 |
| `refreshNuxtData` | "Refresh all or specific asyncData instances in Nuxt" | 按 key 重取 |
| `clearNuxtData` | "Delete cached data, error status and pending promises of useAsyncData and useFetch" | 按 key 删除 |
| `callOnce` | "Run a given function or block of code once during SSR or CSR" | 一次性副作用，**不返回值** |
| `useRequestFetch` | "to forward the request context and headers when making server-side fetch requests" | 服务端那一趟带头 |
| `useRequestHeaders` | "to access the incoming request headers" | 手挑头（浏览器里是空对象） |
| `useRequestURL` | "returns an URL object working on both server-side and client-side" | 当前请求 URL |

## 二、需求 → 用哪个

| 我的需求 | 选它 | 依据篇目 |
| --- | --- | --- |
| 首屏就要有内容的数据 | `useFetch`（相对路径，自动代理请求头） | 210/222 |
| 数据源不是 URL（CMS/SDK） | `useAsyncData` + 自己的 handler | 210/219 |
| 导航别被拖住 | `lazy: true` 或 `useLazy*` | 210/224/225 |
| 服务端不想要这份数据 | `server: false`（并知道首屏没有它） | 217/241 |
| 提交/点击这类只发生的浏览器里的动作 | `$fetch` | 211 |
| 只跑一次的初始化、store action | `callOnce` | 230 |
| 两个接口一起等 | `useAsyncData` 里 `Promise.all`，各带 `signal` | 243 |
| 参数变了自动重取 | ref 放进 `query`（或 URL 用回调） | 239 |
| 用户输入驱动，别立刻打 | `immediate: false` + `execute` | 239 |
| 跨组件共享同一份 | 显式同一个 `key` | 215 |
| 只读缓存不再发请求 | `useNuxtData(key)` | 228 |
| 提交完更新界面 | 乐观更新（写那一格）+ `refreshNuxtData(key)` | 228/240 |
| 换 token / 全站作废 | `clearNuxtData()`（不给键＝全部） | 229 |
| 外部 API 要统一 baseURL 与鉴权头 | `createUseFetch` | 226/238 |
| 多个接口各自一套类型 | `createUseFetch({ routes })` | 226/244 |
| 想加"回前台就刷新"这种复用行为 | addon（`defineUseFetchAddon`） | 227 |
| 想让用户认得出还在加载 | `<NuxtLoadingIndicator>` + `status` | 210/214 |
| 页面绝对地址给 meta 用 | `useRequestURL`（注意缓存丢 host） | 204/237 |

## 三、四个问题分别由哪一层回答

我把常被混问的四件事拆开，因为它们不在同一层：

| 问题 | 答案所在 | 相关篇 |
| --- | --- | --- |
| 数据什么时候取、在哪一侧取 | `server`、`lazy`、`immediate`、`enabled` | 213/217 |
| 取到的东西活多久 | `payloadExtraction`、`purgeCachedData`、`getCachedData`、`granularCachedData`、`serialize` | 213/235/236 |
| 存在哪个格子、谁能共用 | `key`（自动或显式） | 215 |
| 类型对不对 | `useFetch` 的推断、`routes` 声明、`routeTypedFetch`/`strictRouteTypes` | 219/226/244 |

**第二层最容易被忽略**：很多人以为"数据是不是新"是取数函数决定的，其实一半由缓存与投递方式决定，而它们全在配置层。

## 四、五条最容易踩的（都在前面有专篇）

1. **位置与时机**：合法调用点是 `setup`、插件、路由中间件、钩子回调顶层；异步回调里就丢（E1001）。→ 233
2. **`watch` 不重算 URL**："the URL is constructed at the moment the function is invoked"。要变就用 `query` 挂 ref 或 URL 回调。→ 239
3. **四个 ref、三个函数**：`data`/`status`/`pending`/`error` 要用 `.value`，`refresh`/`execute`/`clear` 是函数。→ 214
4. **手动刷新可能仍吃缓存**：`granularCachedData` 默认开；解法是 `ctx.cause === 'refresh:manual'` 时返回 `undefined`。→ 236/240
5. **缓存路由命中时 setup 不跑**：`swr`/`isr` 缓存的是整个响应；命中即"不取数"，而请求头也会被丢。→ 237

再加一条与首屏有关：**内容进不进 HTML，取决于服务端有没有跑那次取数**，跟 `await` 无关。→ 241

## 自查

1. `useLazyFetch` 与 `useFetch({ lazy: true })` 是等价还是相似？（答：官方原话是 "is equivalent to `useFetch` with `lazy: true` option set."）
2. "数据是不是新鲜的"这个问题分别落在哪几层？（答：投递（`payloadExtraction`）、清理（`purgeCachedData`）、采用（`getCachedData`/`granularCachedData`）、是否进 payload（`serialize`），以及路由级缓存 `swr`/`isr`。）
3. 全站作废与丢弃某一格，分别用什么？（答：`clearNuxtData()` 不给键＝全部 state/缓存失效；组件内不知道 key 时用实例的 `clear()`。）
