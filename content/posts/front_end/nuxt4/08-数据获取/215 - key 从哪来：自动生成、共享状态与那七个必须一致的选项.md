我第一次把 key 当"可选参数"跳过，结果是两个组件各自请求了同一份数据；后来我把 key 写成同一个，又冒出"一个组件改了数据、另一个跟着变"的现象。**这两种表现其实是同一个开关的两面。**

## 自动 key 是按调用位置生成的

不给 key 时官方怎么生成，两节措辞略有差别，都抄下来：

- `useAsyncData`：「If you do not provide a key, then a key that is unique to the **file name and line number** of the instance of `useAsyncData` will be generated for you.」
- `useFetch`：「Unique key for de-duplication. If not provided, generated from the **URL, options and call site location** in the source code.」

`useFetch` 那一节还把后果写成三条，这是全篇最实用的部分：

> The auto-generated key is unique to each call site, so calling `useFetch` with the same URL and options in different components will **not** share state and each call performs its own request. Multiple instances of the same component do share state, since they use the same call site. To share the same `data`, `error` and `status` refs across different components, provide the same explicit `key` to each call.

翻成三种场景：

| 场景 | 是否共享 | 请求次数 |
| --- | --- | --- |
| 不同组件、相同 URL、都不给 key | **不共享** | 各发一次 |
| 同一组件被渲染多次（同一个调用位置） | 共享 | 一次 |
| 不同组件、都给 `key: 'random'` | 共享 | 一次 |

官方示例正好是第三行那个形状，两个组件里各写一行：

```vue [app/components/ComponentA.vue]
<script setup lang="ts">
// shares the data with ComponentB - only one request is made
const { data } = await useFetch('/api/random', { key: 'random' })
</script>
```

而 `useAsyncData` 那一节的推荐句是给"封装自己的 composable"这一类留的：

> Since the autogenerated key only takes into account the location where `useAsyncData` is invoked, it is recommended to always create your own key to avoid unwanted behavior, like when you are creating your own custom composable wrapping `useAsyncData`.

原因就在这张表里：**封装函数的调用位置只有一个（在封装文件里那行），但被多少页面用都不增加 key**。所以封装时把 key 当参数收进去，是官方这句建议的落地形式。

## 共享之后：七个必须一致，七个可以不同

同页 Shared State and Option Consistency 一节，先把后果说明白：

> When multiple `useAsyncData` calls use the same key, they share the same `data`, `error`, `status`, and `pending` refs. Keep the options listed below consistent across these calls.

然后是两张清单——**这是文档里唯一一处把选项按"能不能不同"分类**，我逐条抄：

| 必须一致（7 项） | 官方表里的位置 |
| --- | --- |
| `handler` 函数 | 第二个参数 |
| `deep` | 选项表 v3.8 |
| `transform` | 选项表 |
| `pick` | 选项表 |
| `getCachedData` | 选项表 v3.8 |
| `default` | 选项表 |
| `middleware` | 选项表 v4.6 |

| 可以不同（7 项，不触发警告） |
| --- |
| `server`、`lazy`、`immediate`、`dedupe`、`watch`、`enabled`、`serialize` |

规律其实很好读：**必须一致的那七个都是"决定数据长什么样"的**（怎么取、怎么变形、取哪几个键、默认值是什么、缓存怎么读、中间件链怎么走）；**可以不同的那七个都是"决定这次怎么跑"的**（在哪侧、阻不阻塞、什么时候触发、并发怎么合、要不要进 payload）。

官方还给了违反的后果：

```ts [app/pages/index.vue]
// ❌ This will trigger a development warning
const { data: users1 } = useAsyncData('users', (_nuxtApp, { signal }) => $fetch('/api/users', { signal }), { deep: false })
const { data: users2 } = useAsyncData('users', (_nuxtApp, { signal }) => $fetch('/api/users', { signal }), { deep: true })

// ✅ This is allowed
const { data: users1 } = useAsyncData('users', (_nuxtApp, { signal }) => $fetch('/api/users', { signal }), { immediate: true })
const { data: users2 } = useAsyncData('users', (_nuxtApp, { signal }) => $fetch('/api/users', { signal }), { immediate: false })
```

注意是 **development warning**，也就是开发环境告诉你、生产不一定看得见。所以看到这条警告别顺手压掉——它意味着两个调用对同一格数据期待的是不同形状。

## 只认 key 的两把外部钥匙

第一把是读：`useNuxtData`。

> `useNuxtData` gives you access to the current cached value of `useAsyncData`, `useLazyAsyncData`, `useFetch` and `useLazyFetch` with **explicitly provided key**.

签名只返回一个成员：

```ts
export function useNuxtData<DataT = any> (key: string): { data: Ref<DataT | undefined> }
```

官方对返回值的描述有两点值得留着：没有缓存时是 `undefined`；以及"**This `Ref` automatically updates if the cached data changes**"。它还给了适用场景："optimizing performance by reusing already-fetched data or implementing features like Optimistic Updates or cascading data updates"，并写死前提："To use `useNuxtData`, ensure that the data-fetching composable has been called with an explicitly provided key."

官方的例子正好把两把钥匙连起来用（父路由取列表存进 `posts` key，子路由读缓存当默认值）：

```vue [app/pages/posts.vue]
<script setup lang="ts">
// We can access same data later using 'posts' key
const { data } = await useFetch('/api/posts', { key: 'posts' })
</script>
```

```vue [app/pages/posts/[id].vue]
<script setup lang="ts">
// Access to the cached value of useFetch in posts.vue (parent route)
const { data: posts } = useNuxtData('posts')

const route = useRoute()

const { data } = useLazyFetch(`/api/posts/${route.params.id}`, {
  key: `post-${route.params.id}`,
  default () {
    // Find the individual post from the cache and set it as the default value.
    return posts.value.find(post => post.id === route.params.id)
  },
})
</script>
```

这个例子里 `default()` 读的是缓存，正好把 213 那句 "Factory for default value of `data` before async resolves." 落到实处：**详情页在拿到自己的数据之前，先用列表页缓存里的那条占位**，界面就不会闪。

第二把是重取：`refreshNuxtData`。

```ts
export function refreshNuxtData (keys?: string | string[])
```

- 参数可选：「A single string or an array of strings as `keys`... **All `useAsyncData` and `useFetch` keys are re-fetched when no `keys` are explicitly specified.**」
- 返回 Promise："resolving when all or specific `asyncData` instances have been refreshed."

所以 `refreshNuxtData()`（不给参数）是**全站重取**，我一般不会这么写；要精准重取就显式给 key 或数组（官方示例即 `await refreshNuxtData(['count', 'user'])`）。这也解释了 data-fetching 为什么把"设置 key 有两个好处"写成 share 与 refresh 两件事。

## 一个和 KeepAlive 有关的补充说明

`refreshNuxtData` 页有条 note 该单独拎出来，因为它和 137 讲的 `key`/keepalive 撞在一起：

> If your component is cached by `<KeepAlive>` and enters a deactivated state, the `asyncData` inside the component will still be refetched until the component is unmounted.

也就是说：**被保活的组件即使当前不显示，仍然会被重取**。如果你按"只有可见页面才该发请求"的直觉理解保活，这条会不符合预期——它的生效边界是卸载，不是激活。

## 自查

1. `useFetch` 不给 key 时用什么生成，`useAsyncData` 呢？（答：前者 URL + 选项 + 调用位置；后者文件名 + 行号。）
2. 同一 key 的多次调用，哪些选项必须一致？（答：handler、`deep`、`transform`、`pick`、`getCachedData`、`default`、`middleware` 七项。）
3. `refreshNuxtData()` 不给参数会怎样？（答：所有 `useAsyncData` 与 `useFetch` 的 key 全部重取。）
