  摘要：这一篇把取数放回整条时间线里，因为很多"为什么这里拿不到值"的问题只有放到顺序里才解释得通。官方对服务端那一趟的定义是一串步骤（"On the server, the following steps are executed for every initial request to your application"）：**Nitro 插件 → server middleware → App 插件 → 路由校验 → App 中间件 → 页面与组件（取数就在这一步）→ HTML 输出**。取数那一步原话最值钱：「Nuxt renders the page and its components and fetches any required data with `useFetch` and `useAsyncData` during this step. Since there are no dynamic updates and no DOM operations occur on the server, **Vue lifecycle hooks such as `onBeforeMount`, `onMounted`, and subsequent hooks are NOT executed during SSR.**」，并附两条配套结论：「By default, Vue pauses dependency tracking during SSR for better performance.」与 callout「There is no reactivity on the server side because Vue SSR renders the app top-down as static HTML, making it impossible to go back and modify content that has already been rendered.」还有一条 important 我认为是这一页最实用的警告：**在 `<script setup>` 根作用域放需要清理的副作用（示例是 `setInterval`）会永久留着**，因为卸载钩子在 SSR 期间根本不会被调用，"To avoid this, move your side-effect code into `onMounted` instead."。客户端那一趟步骤更少（App 插件 → 校验 → 中间件 → `app.mount('#__nuxt')` 与水合 → Vue 完整生命周期），水合那一步官方给的取数建议是："These methods ensure that the data fetched on the server side is reused during hydration, avoiding repeated requests. **Any new requests should only be triggered after hydration, preventing hydration errors.**"

先声明这一篇解决哪一类困惑：`onMounted` 里写的取数在首屏拿不到值、`setInterval` 清理不掉、"为什么服务端那次读不到 DOM"。这些都不是 API 用法问题，是**顺序问题**。

## 服务端那一趟：七个步骤

官方引导句："The goal of this chapter is to provide a high-level overview of the different parts of the framework, their execution order, and how they work together." 然后 "On the server, the following steps are executed for **every initial request** to your application"（注意是"每一次初始请求"，不是"每次导航"）。

| # | 步骤 | 官方要点（含原文片段） |
| --- | --- | --- |
| 1 | Nitro 插件 | "When Nitro starts, it initializes and executes the plugins under the `/server/plugins` directory"；callout：**"Nitro plugins are executed only once when the server starts... However, they are not awaited."**（serverless 下每个请求都会重新起） |
| 2 | server middleware | "middleware under `server/middleware/` is executed for every request"；warning：**"Returning a value from middleware will terminate the request and send the returned value as the response."** |
| 3 | App 插件 | "The Vue and Nuxt instances are created first. Afterward, Nuxt executes its app plugins."（含内置的 Vue Router 与 `unhead`）；此后调 `app:created` 钩子 |
| 4 | 路由校验 | "After initializing plugins and **before executing middleware**, Nuxt calls the `validate` method if it is defined in `definePageMeta`."，返回 false 或含 `status`/`statusText` 的对象即终止请求 |
| 5 | App 中间件 | 三种中间件；**"Nuxt executes all global middleware on the initial page load (both on server and client) and then again before any client-side navigation."**；服务端重定向会发 `Location:` 头，"All application state will be reset when this happens, unless persisted in a cookie." |
| 6 | 页面与组件 | 取数发生在这里（下面细说） |
| 7 | HTML 输出 | "Nuxt combines the rendered components with settings from `unhead` to generate a complete HTML document."；先后调 `app:rendered` 与 Nitro 的 `render:html` |

第 6 步就是本篇的主角，原文：

> Nuxt renders the page and its components and fetches any required data with `useFetch` and `useAsyncData` during this step. Since there are no dynamic updates and no DOM operations occur on the server, Vue lifecycle hooks such as `onBeforeMount`, `onMounted`, and subsequent hooks are **NOT** executed during SSR.

这一句回答了我最早的那个问题：**`onMounted` 里的取数在服务端根本没跑**，所以首屏 HTML 里没那块内容（198 讲 `<ClientOnly>` 时我说过"壳里的组件不在服务端跑"，这是它在生命周期上的解释）。

同一节还给了两条更基础的结论：

> By default, Vue pauses dependency tracking during SSR for better performance.

> There is no reactivity on the server side because Vue SSR renders the app top-down as static HTML, making it impossible to go back and modify content that has already been rendered.

**"自顶向下渲染成静态 HTML，改不回已经渲染过的部分"** —— 这句话把 210 的"数据必须在渲染前拿到"变成了原因而不是规矩。

## 一条 important：服务端不要放需要清理的副作用

这一条我在踩之前读到会省很多时间，原文完整：

> You should avoid code that produces side effects that need cleanup in root scope of `<script setup>`. An example of such side effects is setting up timers with `setInterval`. In client-side only code we may setup a timer and then tear it down in `onBeforeUnmount` or `onUnmounted`. **However, because the unmount hooks will never be called during SSR, the timers will stay around forever.** To avoid this, move your side-effect code into `onMounted` instead.

链条是这样的：服务端跑 `<script setup>` 根作用域 → 你起了定时器 → 卸载钩子不会执行 → **定时器留在服务器进程里**。解法官方只给一句："move your side-effect code into `onMounted`"——**而 `onMounted` 又不会在服务端跑**，两句话合起来才是完整方案。

这也和 199 那条"有副作用的第三方库要在hydration完成后初始化"、212 那条"handler 要无副作用"串成同一条纪律。

## 客户端那一趟：五步，最后才有 Vue 生命周期

> This part of the lifecycle is fully executed in the browser, no matter which Nuxt mode you've chosen.

顺序是 **App 插件 →（同样的）路由校验 → App 中间件 → 挂载与水合 → Vue 生命周期**。三条我要引：

- 插件那一步限定了后缀：**`.client` 结尾的插件在客户端执行**（与第 3 步服务端只跑 `.server` 形成对称）。
- 中间件那一步给的是分流写法："If you want certain code to run in specific environments, consider splitting it by using `import.meta.client` for the client and `import.meta.server` for the server."（185 里我在布局那节也引过同一招。）
- 挂载与水合那一步信息量最大：

> Calling `app.mount('#__nuxt')` mounts the Vue application to the DOM. If the application uses SSR or SSG mode, Vue performs a hydration step to make the client-side application interactive. During hydration, Vue recreates the application (excluding Server Components), matches each component to its corresponding DOM nodes, and attaches DOM event listeners.
>
> To ensure proper hydration, it's important to maintain consistency between the data on the server and the client. For API requests, it is recommended to use `useAsyncData`, `useFetch`, or other SSR-friendly composables. These methods ensure that the data fetched on the server side is reused during hydration, avoiding repeated requests. Any new requests should only be triggered after hydration, preventing hydration errors.

**"挂载目标是 `#__nuxt`"** 这句顺带解释了 052/090 里那个 id 从哪来；括号里的"Server Components 除外"则是 174 那条"代码不进客户端包"的另一处记载。

最后一句是这一篇最可执行的规则：**新请求要放在水合之后触发**，否则就是 199 那类错配。所以"点击后取数""`onMounted` 里取数"都是安全的，"在 `<script setup>` 顶层裸 `$fetch`"才危险（211）。

前后两个钩子官方也点了名：挂载前 `app:beforeMount`、挂载后 `app:mounted`。

## 第 7 步：为什么 head 和 HTML 是一起出来的

服务端最后那一步把两件事绑在一起：

> After all required data is fetched and the components are rendered, Nuxt combines the rendered components with settings from `unhead` to generate a complete HTML document. This HTML, along with the associated data, is then sent back to the client to complete the SSR process.

两个含义：**`unhead` 的设置要等到数据取完才合并进 HTML**（这就是 193/204 那句"取数之后再注册 head 标签可能追不上"的由来之一）；"along with the associated data" 就是 payload（210）。

紧随两条 callout：渲染完 HTML 调 `app:rendered`；发出前 Nitro 调 `render:html`，官方说这个钩子"allows you to manipulate the generated HTML, such as injecting additional scripts or modifying meta tags"。**想在框架外面统一塞 meta 或脚本，官方给的位置就是这个钩子**（196 提到流式时 `render:html` 只认 `htmlAttrs`/`head`/`bodyAttrs`/`bodyPrepend` 的改动，是同一处）。

## 把整条线连起来看取数

| 我要做的事 | 该放在哪一步 |
| --- | --- |
| 首屏必须有数据 | 页面/组件那一步，用 `useAsyncData` 或 `useFetch`（第 6 步） |
| 全站初始化一次（埋点、store action） | `callOnce`（230），它靠 payload 记录去重 |
| 只给服务端接口用的鉴权 | App 插件或 server middleware（注意第 2 步"返回值会终结请求"） |
| 参数合法性 | `validate`，它跑在中间件**之前** |
| 需要 DOM/浏览器 API | 水合之后：`onMounted`，或 231 那个水合前的注脚本 |
| 统一注入 meta/脚本 | `render:html` 钩子 |

## 自查

1. 服务端那一趟会不会执行 `onMounted`？依据句是什么？（答：不会，官方原话是这些钩子 "are **NOT** executed during SSR"。）
2. 为什么 `<script setup>` 根作用域里的 `setInterval` 危险？（答：卸载钩子在 SSR 永不调用，定时器会一直留在服务器进程；解法是挪进 `onMounted`。）
3. 路由校验与中间件谁先跑？（答：`validate` 先，官方写 "before executing middleware"。）
