这一篇不谈"怎么调接口更快"，只谈**官方文档里写明能省时间的四件事**，因为它们各有原话可查，也各有代价。

## 省第一次：别取两遍

性能页的 Fetching data 小节只有一段，但把 210 的结论压缩得很干净：

> To avoid fetching same data twice (once on the server and once on client) Nuxt provides [`useFetch`] and [`useAsyncData`]. They ensure that if an API call is made on the server, the data is forwarded to the client in the payload instead of being fetched again.

这条是**框架层面的**优化，不需要你做什么，只要别绕开它：用裸 `$fetch` 取首屏数据就是自愿多跑一遍（211 那条 note）。

## 省第二次：把不相关的请求并起来

官方 Recipe 的措辞是条件式的："**When requests don't rely on each other**, you can make them in parallel with `Promise.all()` to boost performance."

```ts
const { data } = await useAsyncData((_nuxtApp, { signal }) => {
  return Promise.all([
    $fetch('/api/comments/', { signal }),
    $fetch('/api/author/12', { signal }),
  ])
})

const comments = computed(() => data.value?.[0])
const author = computed(() => data.value?.[1])
```

三处细节都是原文带的：

1. **`Promise.all` 在 handler 里面**，不是包在 `useAsyncData` 外面——一整格数据装的是"这一组请求的结果"。
2. **每个 `$fetch` 都收 `{ signal }`**。只给第一个加、第二个不加，取消时第二个会继续跑完（247 细说 signal）。
3. 结果按下标取（`data.value?.[0]`），并且**用了可选链**——官方示例自己就防着 `data` 为空的时刻。

同页还有一块"购物车两个优惠接口"的同款例子（`coupons`/`offers` 合成一个对象返回），说明**返回结构可以自己组装**，不一定按下标。

至于有依赖关系的请求（先拿 ID 再拿详情），文档没给链条写法——**那就是两格 key 串起来的事**（215/228），不是并行能解决的。

## 省第三次：别一次全加载

Common Problems 里这一条的 Problem/Solution 我整段抄：

> **Problem**: When a page is loaded and it is not correctly instructed about the order of loading elements it will result in fetching everything at the same time - which can be slow and result in bad User Experience.
>
> **Solution**: Use concepts such as Progressive Enhancement where core webpage content is set first, then more nuanced and technically rigorous layers of presentation and features are added on top as the browser/internet connection allow.

这句 "not correctly instructed about the order of loading elements" 我认为正好对应取数上的一句话：**默认行为是"每个 `useFetch` 都阻塞导航"**（210/224）。一个页面挂六个 `useFetch`，落地时间就是最慢那一个决定的。

对应的三档降速办法，官方各有出处：

| 办法 | 官方依据 | 代价 |
| --- | --- | --- |
| `lazy: true` 或 `useLazyFetch` | "lazy is the explicit way to opt into non-blocking navigation" | 得自己管 `status` |
| 首屏不需要的数据 `server: false` | 用途句 "for example, **non-SEO sensitive data**" | 首屏 HTML 里没这块内容 |
| 组件级延后加载 | `<LazyMyComponent hydrate-on-visible />`（lazy hydration，v3.16 起） | 交互延后 |

**"delay the hydration of some components until they're visible, or until the browser is done with more important tasks"** 这句是官方给延迟水合的理由，而它改善的指标也写明了：time-to-interactive。

## 省第四次：让 payload 瘦下来

两条体积手段都已在前面讲过，这里只按性能页口径归位：

- `pick`：**"helps you to minimize the payload size stored in your HTML document"**（235）。列表接口最见效。
- `serialize: false`：把某格数据彻底移出 payload（217/235），官方还建议配 lazy hydration 用。

另外状态那一侧有一条同类的："If you don't need your state to be deeply reactive, you can combine `useState` with `shallowRef`. **This can improve performance when your state contains large objects and arrays.**"

```ts
const state = useState('my-shallow-state', () => shallowRef({ deep: 'not reactive' }))
// isShallow(state) === true
```

这两条针对的不是网络，而是**HTML 体积与水合成本**——大数组深响应式在水合时是很贵的一笔。

## 内容型站点的组合拳

性能页在 lazy hydration 末尾给了一句"极限配置"，我认为值得整句留着，因为它是**官方主动把几个特性连起来讲**的少数几处之一：

> For content and marketing sites that need little or no client-side interactivity, you can go further and combine prerendering, the `noScripts` route rule, [server components] and lazy hydration to ship near-zero JavaScript.

（175 已细引过这句与它的前后文。）

但要注意它对取数的连带影响：**`noScripts` 的路由会额外产出 `_payload.json`，客户端导航取那个文件而不是重跑取数**（141 记过），岛屿组件与 `noScripts` 同时用还会退回缓冲渲染（171）。所以"近零 JS"不是免费的。

## 一张自查清单

- [ ] 首屏数据是否都走 `useFetch`/`useAsyncData`，没有裸 `$fetch`？
- [ ] 同一页多个请求里，不相互依赖的是否已并到一个 handler 的 `Promise.all`？
- [ ] 每个 `$fetch` 是否都收到了 `{ signal }`？
- [ ] 是否有页面因为 `lazy: false` 被最慢的接口拖住？（判据：导航停在旧页 + `<NuxtLoadingIndicator>` 出现）
- [ ] 列表接口是否用了 `pick`？
- [ ] 大对象状态是否用 `shallowRef` 包过？
- [ ] 首屏不需要的块（评论、推荐位）是否延后水合或改 `server: false`？

## 自查

1. 官方的并行写法里，`Promise.all` 放在哪一层？（答：放在 `useAsyncData` 的 handler 内部，一整格数据承载这组结果。）
2. "别一次全加载"这条 Problem 的原文关键短语是什么？（答："it is not correctly instructed about the order of loading elements ... result in fetching everything at the same time"。）
3. 减少 payload 体积的两个选项分别是什么，各自作用粒度？（答：`pick`（选字段）与 `serialize: false`（整格移出 payload）。）
