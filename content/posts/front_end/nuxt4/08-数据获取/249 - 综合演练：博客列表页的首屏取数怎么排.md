  摘要：这一篇把 P08 排到最后一个具体页面上：`/blog` 列表页，需求是"首屏有内容、能翻页、点进详情页时列表数据不重复取、静态发布"。我按五个决定来写，每个决定都指回一条原文。**决定一，取数放页面 `setup` 顶层而不是 `onMounted`**——生命周期那一节写着 "Vue lifecycle hooks such as `onBeforeMount`, `onMounted`, and subsequent hooks are **NOT** executed during SSR"，而第 7 步是"取完数才与 `unhead` 合并出 HTML"。**决定二，翻页参数挂进 `query` 而不是拼进 URL**——官方那句反例 "watching a reactive value won't change the URL fetched ... because the URL is constructed at the moment the function is invoked" 说明拼字符串配 `watch` 是无效的，正解是 "attach each param as a reactive value. Nuxt will automatically use the reactive value and re-fetch each time it changes."。**决定三，给显式 `key`**，这样详情页能用 `useNuxtData('blog-list')` 读到同一格（官方那句前提："ensure that the data-fetching composable has been called with an explicitly provided key"）。**决定四，只要模板用到的字段**（`pick` 的定位就是 "minimize the payload size stored in your HTML document"）。**决定五，评论这种非首屏块用 `server: false` + `lazy`**，因为官方给的用途原话是 "non-SEO sensitive data"。另两处容易漏：列表要真的渲染 `<NuxtLink>`（预渲染抓取只认 anchor），以及静态站上"数据是构建期快照"这件事（"data can be stale until the next rebuild"）。

先把验收标准写清楚，不然后面的选择没有依据：首屏 HTML 里要有文章条目、翻页要能换数据、从详情页返回不重复请求、`nuxt generate` 之后各页仍是完整 HTML、评论不拖慢首屏。

## 骨架：页面这一侧

```vue [app/pages/blog/index.vue]
<script setup lang="ts">
const route = useRoute()
const page = computed(() => Number(route.query.page) || 1)

const { data: posts, status, error, refresh } = await useFetch('/api/posts', {
  key: 'blog-list',
  query: { page },
  pick: ['title', 'slug', 'excerpt', 'publishedAt'],
})

useSeoMeta({
  title: () => `博客列表 第 ${page.value} 页`,
  description: '按时间倒序的文章列表。',
})

const { status: commentsStatus, data: comments } = useFetch('/api/comments', {
  server: false,
  lazy: true,
})
</script>

<template>
  <div>
    <div v-if="status === 'pending'">
      加载中
    </div>
    <div v-else-if="error">
      列表读取失败
      <button @click="refresh()">
        重试
      </button>
    </div>
    <ul v-else>
      <li
        v-for="post in posts"
        :key="post.slug"
      >
        <NuxtLink :to="`/blog/${post.slug}`">
          {{ post.title }}
        </NuxtLink>
      </li>
    </ul>

    <ClientOnly>
      <Comments :items="comments" />
      <template #fallback>
        <p>评论加载中</p>
      </template>
    </ClientOnly>
  </div>
</template>
```

这段里每一处都能回指原文，我把对应关系列出来，**因为有两处是我按规则拼的、不是文档原样**：

| 写法 | 依据 |
| --- | --- |
| 取数写在 `setup` 顶层 | 第 6/7 步（232/241） |
| `page` 用 computed、放进 `query` | Computed URL 那句 "attach each param as a reactive value"（239）；**"把 ref 放进 query 就自动被监听"是官方选项 note**（216/221） |
| `pick: [...]` | "minimize the payload size stored in your HTML document"（235） |
| `status` 分三支 + 重试按钮 | Watch/Not immediate 与 `refresh` 的官方形状（214/239/240） |
| 评论用 `server: false` + `lazy: true` | 官方用途句 "non-SEO sensitive data"（217/241） |
| 评论外面套 `<ClientOnly>` | **这一处是我的组合**：文档没要求，`server: false` 已经让服务端不取；包壳是为了让那块内容整体不进服务端构建（165/198 讲的 tree-shake 语义） |

`key: 'blog-list'` 是给下一步用的（215 说过共享必须显式同 key）。**`query: { page }` 里放 computed 而不是 `.value`**，这一点是官方示例的形状（`query: { user_id: id }`）。

## 详情页：读那一格而不是再取一次

```vue [app/pages/blog/[slug].vue]
<script setup lang="ts">
const route = useRoute()
const { data: list } = useNuxtData('blog-list')

const { data: post, status } = useLazyFetch(`/api/posts/${route.params.slug}`, {
  key: `post-${route.params.slug}`,
  default () {
    return list.value?.find(p => p.slug === route.params.slug)
  },
})
</script>
```

这个形状是官方 posts / posts-[id] 例子的原样（228 引过），三个要点都在原文里：

1. `useNuxtData` 的前提是"那次取数用了显式 key"。
2. `default()` 是工厂，正好用来放"列表里那条占位"。
3. `useLazyFetch` + 不 await：官方那句 warning 说得很清楚，**await 它不等于等到数据**，所以模板要判 `status`。

**但要注意 235 的一个限制**：`default()` 里 `list.value?.find(...)` 拿到的对象要能被序列化进 payload（列表数据本身当然可以，`pick` 之后只剩四个字段）。官方对 `useState` 那句 "serialized to JSON" 的警告同样适用于所有进 payload 的东西——**别往 `default()` 里塞类实例或函数**。

## 静态发布这条线上，有两件事必须做

**一，列表要真的渲染 anchor。** 预渲染抓取机制第 3 步是 "Find all anchor tags (`<a href=\"...\">`) in the HTML to navigate to other routes."，结论句 "pages that are not linked to a discoverable page can't be pre-rendered automatically"。所以用 `@click="navigateTo(...)"` 的条目等于**详情页不会被发布出去**。`<NuxtLink :to>` 渲染出的就是 anchor（112 那个例子给过 `href="/posts/123"`）。

**二，接受"构建期快照"。** 官方那句 "On a fully static site, client-side navigation reuses the data captured at build time, so data can be stale until the next rebuild." 意味着：**新文章不会因为用户点了刷新就出现**，`refresh()` 能重取但取到的是发布产物里的时间线（237 那类缓存另说）。这一点在项目说明里写清楚，比事后排查便宜。

## 翻页时的请求堆积

连点两页会发生什么，取决于两条已写规则：`dedupe` 默认 `'cancel'`（官方 abort 时机第一条："A new request is made with `dedupe: 'cancel'`"），而 `refresh` 自己会等上一次跑完。所以我没有在代码里加防抖——**默认策略已经是"新的挤掉旧的"**。

`page` 变化触发的是"自动重取"（响应式选项那条），走的还是同一条 `dedupe` 通道。**但"重取时旧数据是否还在屏幕上"文档没写**，我按 `useNuxtData`/`default` 那套思路自己处理，而不是假设框架会保留（要确认就测：连点两页，看列表是闪空还是直接替换）。

## 上线前的五步验证

1. `curl` 列表页 HTML：条目在不在、`<a href>` 指向详情页、`<title>` 对不对（209 那套）。
2. 点进详情页再返回，看网络面板里 `/api/posts` 有没有第二次请求（没有才说明 key 生效）。
3. 连点三页，看请求是不是被合并/取消（247）。
4. `nuxt build` + `nuxt preview` 看评论块首屏是 fallback 还是内容（198/096 那条：dev 里看不出来）。
5. `nuxt generate` 后确认 `200.html`/`404.html` 与各页 HTML 是否齐全（038/207 讲过默认兜底页是空壳、`prerenderErrorPages` 才服务端渲染错误页）。

## 自查

1. 为什么翻页用 `query` 而不是把页码拼进 URL 再配 `watch`？（答：官方反例明写 `watch` 不重算 URL；`query` 里放响应式值才会自动重取。）
2. 详情页为什么用 `useNuxtData` + `default()`，前提是什么？（答：先显示列表里那一条占位，避免闪空；前提是列表那次取数用了显式 key。）
3. 静态站上"新文章看不到"的第一解释是什么？（答：数据是构建期快照，要重新构建才有新内容。）
