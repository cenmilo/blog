210 讲清了"为什么会跑两遍"，这一篇讲 `$fetch` 自己的边界：**它不是不能用，而是它只负责把请求发出去，其他什么都不管**。

## 先认清它是谁

`$fetch` 来自第三方库 ofetch，Nuxt 把它挂成全局自动导入：

> Nuxt uses [ofetch](https://github.com/unjs/ofetch) to expose globally the `$fetch` helper for making HTTP requests within your Vue app or API routes.

> Nuxt includes the ofetch library, and is auto-imported as the `$fetch` alias globally across your application.

所以你能在组件里不写 import 直接调用它。同一页还顺手替它站过一次队：**"`$fetch` is the preferred way to make HTTP calls in Nuxt instead of @nuxt/http and @nuxtjs/axios that are made for Nuxt 2."**

## 三条限制，逐条抄原文

第一条是那个"跑两遍"的机制说明（note 原文）：

> Using `$fetch` in components without wrapping it with `useAsyncData` causes fetching the data twice: initially on the server, then again on the client-side during hydration, because `$fetch` does not transfer state from the server to the client. Thus, the fetch will be executed on both sides because the client has to get the data again.

关键词是 **"does not transfer state from the server to the client"**——210 里 payload 干的就是这件事，`$fetch` 没有这一层。

第二条是能力清单上的两个"没有"（data-fetching 页的 warning）：

> Beware that using only `$fetch` will not provide [network calls de-duplication and navigation prevention].

这两个词我解释一下，因为它们是 `useAsyncData` 那两个功能的名字：

- **去重（de-duplication）**：同一个 key 在一处已经被请求过时，框架可以把重复的调用合并/复用，而不是真的再发一次。
- **阻止导航**：数据没回来之前先别切页面（210 讲的 `<Suspense>` 那层）。`$fetch` 在这条上完全不参与，所以点了链接就走，页面带着空数据渲染。

同一条 warning 的后半句给了官方推荐的用法：

> It is recommended to use `$fetch` for client-side interactions (event-based) or combined with `useAsyncData` when fetching the initial component data.

"event-based" 这个词很准——**点击、提交这类由用户触发、只发生在浏览器里的动作**才是它的主场。

## 官方那个三行对照示例

`$fetch` 页的 Usage 一节把三种写法的结果直接注释在代码里，这是最省口舌的一段：

```vue [app/app.vue]
<script setup lang="ts">
// During SSR data is fetched twice, once on the server and once on the client.
const dataTwice = await $fetch('/api/item')

// During SSR data is fetched only on the server side and transferred to the client.
const { data } = await useAsyncData('item', () => $fetch('/api/item'))

// You can also useFetch as shortcut of useAsyncData + $fetch
const { data } = await useFetch('/api/item')
</script>
```

第三行那句注释也是一条等价关系，值得记住：**`useFetch` 就是 `useAsyncData` + `$fetch` 的快捷写法**（212 会看到官方对这句话的精确版本与它的限定条件）。

事件型用法官方给的是这个形状：

```vue [app/pages/contact.vue]
<script setup lang="ts">
async function contactForm () {
  await $fetch('/api/contact', {
    method: 'POST',
    body: { hello: 'world' },
  })
}
</script>

<template>
  <button @click="contactForm">
    Contact
  </button>
</template>
```

配一句定位："You can use `$fetch` in any methods that are executed only on client-side." ——注意这里是 `await` 的，但等的是**接口响应**，不是导航。

## 便利那条：内部 API 不真的走网络

这一条我觉得是 `$fetch` 最被低估的优点，原文是 tip：

> During server-side rendering, calling `$fetch` to fetch your internal [API routes], will directly call the relevant function (emulating the request), **saving an additional API call**.

说的是打**自己项目里 `server/api/` 那些路由**时，服务端那一趟不会真去开一个 HTTP 连接，而是直接调用对应函数（模拟一次请求）。外部 URL 不在这条适用范围内——文档限定得很死："your internal API routes"。

## cookie 在两侧行为不一样，这是有意的

最容易写出隐性 bug 的就是这一段。原文（Passing Headers and Cookies）：

> When we call `$fetch` in the browser, user headers like `cookie` will be directly sent to the API.
>
> However, during Server-Side Rendering, due to security risks such as **Server-Side Request Forgery (SSRF)** or **Authentication Misuse**, the `$fetch` wouldn't include the user's browser cookies, nor pass on cookies from the fetch response.

也就是说：**同一个调用，浏览器里带 cookie，服务端那一趟不带**。文档给的官方示例把这条写在注释里：

```vue [app/pages/index.vue]
<script setup lang="ts">
// This will NOT forward headers or cookies during SSR
const { data } = await useAsyncData(() => $fetch('/api/cookies'))
</script>
```

表现症状通常是：本地登录状态正常，服务端渲染那一次却读不到用户（`getCookie(event, 'foo')` 拿到空）。文档给的两条出路：

```vue [app/pages/index.vue]
<script setup lang="ts">
// This will forward the user's headers and cookies to `/api/cookies`
const requestFetch = useRequestFetch()
const { data } = await useAsyncData(() => requestFetch('/api/cookies'))
</script>
```

或者手挑要带的头（data-fetching 页给的写法）：`const headers = useRequestHeaders(['cookie'])` 再 `$fetch('/api/me', { headers })`，那句解释是"Using an isomorphic `$fetch` call, we ensure that the API endpoint has access to the same `cookie` header originally sent by the user's browser. **This is only necessary if you aren't using `useFetch`.**"

而如果你用 `useFetch` 打相对路径，这件事是自动的：

> When calling `useFetch` on the server, Nuxt will use `useRequestFetch` to proxy client headers and cookies (with the exception of headers not meant to be forwarded, like `host`).

## 那些头不该转发

官方在这一节末尾放了一份 caution 清单，我原样留着，因为"只带你要的"这条原则很容易被忽略：

> Be very careful before proxying headers to an external API and just include headers that you need. Not all headers are safe to be bypassed and might introduce unwanted behavior. Here is a list of common headers that are NOT to be proxied:
>
> - `host`, `accept`
> - `content-length`, `content-md5`, `content-type`
> - `x-forwarded-host`, `x-forwarded-port`, `x-forwarded-proto`
> - `cf-connecting-ip`, `cf-ray`

`x-forwarded-*` 那一组暴露的是"你真实来源/协议"，`cf-*` 是 CDN 侧的客户端信息——把它们转给外部 API 等于把内部链路信息交出去。这份清单是官方给的，我不加也不减。

## 类型层面的一个小尾巴

要把 `$fetch` 本身当参数传（比如塞进插件或 `provide` 出去），官方给了专门的类型：

> To type a value that holds `$fetch` itself, such as a `$fetch` instance passed into a plugin or provided through `provide`/`inject`, use the `$Fetch` type (an alias of `TypedFetch`):

```ts
import type { $Fetch } from '#app'

function createClient (fetcher: $Fetch) {
  return {
    todos: () => fetcher('/api/todos'),
  }
}
```

注意这里是**类型**要显式从 `#app` 导入，函数本身仍然自动可用——154 讲过哪三种场合必须写显式 import，这一条属于"只导类型"的情况。

还有一条开发环境专用：`$fetch` 页的 note 写 "If you use `$fetch` to call an (external) HTTPS URL with a self-signed certificate in development, you will need to set `NODE_TLS_REJECT_UNAUTHORIZED=0` in your environment."

**这一条我要在引用之后加一句风险提示**：这个环境变量关掉的是整个进程对服务器证书的校验，中间人可以借此冒充任意 HTTPS 站点，被影响的不仅是那台自签证书的本地服务。所以我的做法是只在明确标注为测试的容器或本地终端会话里临时带上它、跑完即撤，并且绝不写进生产启动脚本或 CI 的通用环境变量里；更稳的替代方案是把那张自签证书对应的根 CA 交给 Node 信任（`NODE_EXTRA_CA_CERTS` 指一份 CA 文件），让它只认你自己那把钥匙，而不是对所有证书放行。文档那句话的适用范围本来就写了 "in development"，我认为这个范围还要再收窄一层。

## 自查

1. `$fetch` 缺的两个能力是什么，官方原话怎么说？（答：去重与导航阻止——"will not provide network calls de-duplication and navigation prevention"。）
2. 服务端渲染时用 `$fetch` 打内部 API 路由，会发生什么？（答：不真发一次请求，直接调用对应函数、省一次 API 调用。）
3. 服务端那一次为什么读不到用户 cookie，两条出路是什么？（答：官方出于 SSRF 与认证滥用风险不带 cookie；出路是 `useRequestFetch()` 或 `useRequestHeaders(['cookie'])` 手传，或者干脆改用 `useFetch` 打相对路径让它自动代理。）
