先接上错误码。你多半是因为屏幕上跳出一句 "Nuxt instance unavailable" 才翻到这里的——那是 `E1001`。它的定义：

> A composable that needs the Nuxt instance (`useNuxtApp()`, `useRoute()`, `useFetch()`, …) ran outside a plugin, Nuxt hook, route middleware, or Vue `setup()`. The most common trigger is calling it inside an async callback (`setTimeout`, `.then()`, after an `await`) where the context has been lost.

`runWithContext` 就是官方给的、针对这个的补救之一。但先说清：官方**不鼓励你到处用它**。use-nuxt-app 那节开头就一句 note：

> You are likely here because you got a "Nuxt instance unavailable" message. Please use this method sparingly, and report examples that are causing issues, so that it can ultimately be solved at the framework level.

也就是说它是"止血"，不是"日常写法"。下面先讲它怎么用，再讲为什么会有这个坑。

## 怎么用

最小形状（官方 Usage）：

```ts
const result = nuxtApp.runWithContext(() => functionWithContext())
```

- `functionWithContext`：任何需要当前 Nuxt 应用上下文的函数。"This context will be correctly applied automatically."
- 返回值：`runWithContext` will return whatever is returned by `functionWithContext`.

官方给的完整场景是一个路由中间件里 `try/catch` 包了 `await`，上下文被编译器丢掉：

```ts [app/middleware/auth.ts]
export default defineNuxtRouteMiddleware(async (to, from) => {
  const nuxtApp = useNuxtApp()
  let user
  try {
    user = await fetchUser()
    // the Vue/Nuxt compiler loses context here because of the try/catch block.
  } catch (e) {
    user = null
  }
  if (!user) {
    // apply the correct Nuxt context to our `navigateTo` call.
    return nuxtApp.runWithContext(() => navigateTo('/auth'))
  }
})
```

关键在最后那行：`navigateTo` 是个需要上下文的组合式，直接调用会 E1001；包进 `runWithContext(() => navigateTo('/auth'))` 就把上下文临时套回去。

## 为什么会丢：上下文是个"立刻被清掉的全局变量"

官方 "A Deeper Explanation of Context" 那节把这个机制写得很白，我翻成学生能懂的话：

> Vue.js Composition API (and Nuxt composables similarly) work by depending on an implicit context. During the lifecycle, Vue sets the temporary instance ... to a global variable and unsets it in same tick. When rendering on the server side, there are multiple requests from different users and nuxtApp running in a same global context. Because of this, Nuxt and Vue immediately unset this global instance to avoid leaking a shared reference between two users or components.

拆成因果：

1. 组合式不是自己找"我是哪个组件/哪个请求的"，而是读一个**隐式的全局变量**（当前实例）。
2. 服务端是**多用户共享同一个全局上下文**跑的——所以框架必须在这个 tick 一结束就把全局变量清掉，否则用户 A 的组件和用户 B 的会串（250 那条服务端串数据同源）。
3. 代价就是：这个隐式上下文**只在"当前这一 tick、任何 await 之前"有效**。官方给的概念例子：

```ts
async function setup () {
  getCurrentInstance() // Works
  await someAsyncOperation() // Vue unsets the context in same tick before async operation!
  getCurrentInstance() // null
}
```

`await` 之后 `getCurrentInstance()` 就变 `null` 了——这就是"组合式只能在 setup/插件/中间件的同步顶层调"（233 篇讲过那四处合法调用点）的底层原因。

## 平时为什么不丢：编译器帮你补回来了

你可能会问："`<script setup>` 里我 await 之后再读 ref，也没报错啊？"对，因为 Vue 编译时偷偷做了上下文恢复。官方给的"Compiled Output"：

```ts
const __instance = getCurrentInstance() // Generated by Vue compiler
getCurrentInstance() // Works!
await someAsyncOperation() // Vue unsets the context
__restoreInstance(__instance) // Generated by Vue compiler
getCurrentInstance() // Still works!
```

`runWithContext` 的定位就是这句——"where `runWithContext` can be used to restore context, similarly to how `<script setup>` works."（手动做编译器在 `<script setup>` 里自动做的那件事）。

Nuxt 对插件和中间件也提供了类似的自动 transform：官方说明用了 `defineNuxtPlugin()` 和 `defineNuxtRouteMiddleware()` 时，Nuxt 会自动给它们加上下文恢复。

## 残留问题：try/catch + await 还会漏

那为什么上面中间件例子还需要 `runWithContext`？官方 "Remaining Issues" 给了答案：

> The `unjs/unctx` transformation to automatically restore context seems buggy with `try/catch` statements containing `await` which ultimately needs to be solved in order to remove the requirement of the workaround suggested above.

也就是自动恢复在 **`try/catch` 里含 `await`** 这种情况下会出 bug（编译器丢了上下文，正如示例注释那句），于是这类场景仍需手动 `runWithContext` 兜一下。这也解释了 note 为什么让你"报告触发问题的例子"——这是框架层想根治的东西。

## 还有个更彻底的选项：asyncContext

官方在 "Native Async Context" 给了一条实验出路：

> Using a new experimental feature, it is possible to enable native async context support ... to make async context available natively to any nested async composable without needing a transform or manual passing/calling with context.
> Native async context support works currently in Bun and Node.

就是 `experimental.asyncContext`（在 experimental 页有）。它对嵌套异步组合式提供原生上下文，能少很多手动套上下文的场景；但它仍是实验特性、且官方 tip 写明目前只在 Bun 和 Node 生效。

## 用它的正确顺序

遇到 E1001，别第一反应就 `runWithContext`。官方 E1001 的 Resolution 给的优先顺序是：

> Call the composable synchronously at the top of `setup()` / a plugin / middleware and reuse the captured result later. For server-side async work, wrap the call with `nuxtApp.runWithContext()`.

1. **先**把需要上下文的调用挪到同步顶层：在 setup/插件/中间件开头就 `const route = useRoute()`，之后 await 完了用这个捕获下来的 `route`，不要在 await 之后才 `useRoute()`。
2. 只有"确实必须在异步/try-catch 里调组合式"时，才 `runWithContext` 兜。
3. 项目里这类场景很多、想根治，再评估开 `experimental.asyncContext`。

## 自查

- 先分辨：是不是只要在同步顶层捕获、后面复用就行？那是正解，`runWithContext` 是退路。
- `runWithContext` 用 `nuxtApp.runWithContext(() => ...)`，返回里层函数的返回值。
- 中间件/插件里 `try/catch` 含 `await` 之后上下文会丢，官方明说这是 transform 的已知 bug。
- 别滥用——官方 note 就是"用得越少越好，并把这些案例反馈出去"。
