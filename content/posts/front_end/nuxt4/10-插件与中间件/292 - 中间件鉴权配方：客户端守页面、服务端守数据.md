上一批 259 把会话存哪儿讲了（加密封装的 cookie）。这一篇聚焦那份官方 Sessions and Authentication 配方里**中间件**这一层：同一个登录态，要在客户端和服务端各守一道，缺一不可。

## 先记住那句定调的话

配方的 "Protect API Routes" 一节，开篇就是整件事的核心：

> Protecting server routes is key to making sure your data is safe. Client-side middleware is helpful for the user, but without server-side protection your data can still be accessed.

读法：客户端中间件是**体验层**——它让未登录用户看不到不该看的页面；但它**护不住数据**——数据在接口那边，你不锁接口，直接打接口照样拿得到。所以两道都要做。

## 第一道：服务端守数据（requireUserSession）

接口这侧，用 `nuxt-auth-utils` 的 `requireUserSession`：

```ts [server/api/user/stats.get.ts]
export default defineEventHandler(async (event) => {
  // 确保用户已登录：没有有效会话就抛 401
  const { user } = await requireUserSession(event)
  return {}
})
```

官方注释点明了它的行为："This will throw a 401 error if the request doesn't come from a valid user session."。这一层跟前端用不用中间件无关——就算有人绕过你的页面直接 `POST/GET` 这个接口，服务端这关也拦住。这是 291 讲的"服务端中间件/handler 才护得住数据"的具体落地。

## 第二道：客户端守页面（路由中间件）

页面这侧，配方的 "Protect App Routes" 一节解释了为什么还要再补一层。数据是安全的了，但"不这么做的话未登录用户访问 /users 页会看到一些奇怪的、空的/报错的数据"。于是用客户端路由中间件：

```typescript [app/middleware/authenticated.ts]
export default defineNuxtRouteMiddleware(() => {
  const { loggedIn } = useUserSession()

  // 未认证就把用户送去登录页
  if (!loggedIn.value) {
    return navigateTo('/login')
  }
})
```

这正好用上了 290 的三条规则：用 `defineNuxtRouteMiddleware`、用返回值 `navigateTo('/login')` 指令导航、没用它要读的"当前路由"（只用了 `useUserSession()` 的 `loggedIn`）。

## 点名：客户端中间件不自动全作用

这一节有一句限定特别关键，配方原文：

> Unlike on the server, client-side middleware is not automatically applied to all endpoints, and we'll need to specify where we want it applied.

对比 291：**服务端**中间件是"每个请求都跑"（自动全作用）；**客户端**路由中间件不是——你得指明哪些页面用它。做法就是页面里 `definePageMeta` 点名：

```vue [app/pages/index.vue]
<script setup lang="ts">
definePageMeta({
  middleware: ['authenticated'],
})

const { user, clear: clearSession } = useUserSession()

async function logout () {
  await clearSession()
  await navigateTo('/login')
}
</script>
```

没点名的页面，这个 `authenticated` 中间件就不跑。想要"全站都要登录"，那是另一条路——给它 `.global` 后缀做成全局中间件（290），但配方这里用的是"按页点名"。

## 退出与"读登录态"的统一入口

配方里读写会话都走同一个组合式 `useUserSession()`：

```vue
<script setup>
const { loggedIn, session, user, clear, fetch } = useUserSession()
</script>
```

- `loggedIn` → 中间件判要不要放行
- `user` → 页面显示当前用户
- `clear` → 登出（`clearSession()` 后 `navigateTo('/login')`）
- `fetch` → 登录接口成功后刷新客户端会话（259 讲过）

登录态本身是加密 cookie（259），`useUserSession` 只是读它的统一入口——这跟 290 强调的"中间件只处理导航、能力从别处拿"是一致的。

## 两道各管什么（收口）

| | 服务端 `requireUserSession` | 客户端 `authenticated` 中间件 |
| --- | --- | --- |
| 守的对象 | 接口/数据 | 页面访问体验 |
| 触发范围 | 每个打到该接口的请求 | 只有 `definePageMeta` 点名了它的页面 |
| 拦不住会怎样 | 数据被直接访问（严重） | 用户看到空/异常页面（体验差，但数据仍受服务端保护） |
| 失败动作 | throw 401 | navigateTo('/login') |

一句话记牢配方那句定调：**少了服务端那关，客户端中间件再怎么写都护不住数据。**

## 自查

- 只写了客户端中间件就以为"锁好了"？接口那边必须有 `requireUserSession(event)`，否则直接打接口绕过页面就能取数据。
- 客户端中间件默认不是全站生效——要保护的页面各自用 `definePageMeta({ middleware: ['authenticated'] })` 点名（或做成全局中间件）。
- 会话状态统一从 `useUserSession()` 读（loggedIn/user/clear/fetch），别自己造内存变量。
- 服务端那关抛的是 401（错误页/JSON 走 234、285 的错误处理）。
