`app/plugins/` 和 `app/middleware/` 挨在一起，都在 Vue 那一侧跑，新手常问"这段逻辑到底放哪个"。区别其实清楚：**一个管路由、一个管能力**。这一篇把边界画出来，再讲它们唯一的交点。

## 中间件：管"这次导航怎么走"

中间件的定义（app/middleware 页定位句）：

> Nuxt provides a customizable **route middleware** framework ... ideal for extracting code that you want to run before navigating to a particular route.

它的职权是"导航守卫"：接收当前路由 `to` 和上一个路由 `from`，靠**返回值**决定导航怎么走。官方列的可选返回：

- 什么都不返回 → 放行，进入下一个中间件或完成导航
- `return navigateTo('/')` → 改道（服务端重定向时是 302，可带 `redirectCode: 301`）
- `return abortNavigation()` → 停止当前导航
- `return abortNavigation(error)` → 带错误拒绝导航

也就是说：**"能不能进这个页面、要不要被送去别处"是中间件的活儿。** 它和 vue-router 的守卫还有个关键差异——官方明说没有第三个 `next()` 参数，"redirect or route cancellation is handled by returning a value from the middleware"。

中间件有两条硬边界，划清它"管不到"的地方：

1. **没有"当前路由"概念**（app/middleware 页）："There is no concept of a 'current route' in middleware, as middleware can abort a navigation or redirect to a different route. The `useRoute()` composable will always be inaccurate in this context."——只能用 `to`/`from`，别在里面用 `useRoute()`（间接用也算）。
2. **不作用在 /api**：routing 页那句 important "Route middleware does **not** run for server routes (e.g. `/api/*`) or other server requests. To apply middleware to these requests, use server middleware instead."——想挡 API 请求，得用服务端中间件（291）。

## 插件：管"给应用挂什么能力"

插件的定义（270 引过）："Nuxt has a plugins system to use Vue plugins and more at the creation of your Vue application." 它跑在应用创建那一刻，职权是**给应用装能力**：

- `nuxtApp.provide` / 返回 `{ provide }` → 挂全局 `$helper`（274）
- `nuxtApp.vueApp.use/directive` → 装 Vue 插件、注册全局指令（273、287）
- `nuxtApp.hook(...)` → 订运行时钩子（275）

插件**不靠返回值控制导航**——它没有 `to`/`from`，也不"放行/改道"。它的产出是"应用从此多了某个东西"。

一张分工表：

| | 路由中间件 | Nuxt 插件 |
| --- | --- | --- |
| 何时跑 | 导航到某个路由之前 | 应用创建时 |
| 核心职权 | 决定导航：放行 / navigateTo / abortNavigation | 给应用挂能力：provide / vueApp / hook |
| 拿路由的方式 | `to`/`from` 参数 | 用 `useRoute()` 等组合式（不在中间件那套限制里） |
| 作用在 /api？ | 否 | （插件本身与单条 /api 请求无关） |
| 两端都跑？ | 初始页服务端+客户端各一趟（见下） | 默认两端都跑，可用 `.server`/`.client` 限侧 |

## 交点：插件能反过来注册中间件

两个系统唯一的交点，是 app/middleware 页的 "Adding Middleware Dynamically"：

> It is possible to add global or named route middleware manually using the `addRouteMiddleware()` helper function, such as from within a plugin.

```ts
export default defineNuxtPlugin(() => {
  addRouteMiddleware('global-test', () => {
    console.log('this global middleware was added in a plugin and will be run on every route change')
  }, { global: true })

  addRouteMiddleware('named-test', () => {
    console.log('this named middleware was added in a plugin and would override any existing middleware of the same name')
  })
})
```

读这条要抓住三件事：

- 注册动作发生在**插件**里（应用创建时），但被注册的是一个**中间件**（导航前才跑）——正好把两个职权接起来：插件"提供"这条守卫，中间件"执行"守卫逻辑。
- 第三个参数 `{ global: true }` → 这是个全局中间件，每次路由变化都跑；不给就是命名中间件，得页面 `definePageMeta({ middleware: ['named-test'] })` 点名才用。
- 官方在示例里直接写死了同名覆盖语义——"would override any existing middleware of the same name"，所以在插件里用 `addRouteMiddleware` 注册一个和目录同名的中间件，插件这份**赢**。

## 顺带把"跑几趟"对齐（和水合有关）

中间件有个和插件不同的运行次数细节，app/middleware 页 "When Middleware Runs" 说清：SSR 或生成站里，初始页的中间件**渲染时跑一次、客户端再接手时再跑一次**。官方还给了跳过其中一趟的判据（用的正是 278/279 那两个成员）：

```ts
const nuxtApp = useNuxtApp()
if (import.meta.client && nuxtApp.isHydrating && nuxtApp.payload.serverRendered) {
  return
}
```

插件是"应用创建时跑"，中间件是"每次导航前跑"（初始页还会两端各一趟）。这也是为什么"只跑一次的全局初始化"更适合放插件，而"每次进某页都要检查"才是中间件。

## 自查

- 逻辑是"决定这次能不能进/要不要跳走"？→ 中间件（返回 navigateTo/abortNavigation）。是"给应用加个能用的东西"？→ 插件。
- 在中间件里想读当前路由？只能用 `to`/`from`，别 `useRoute()`（包括内部用了它的组合式）。
- 想守 `/api` 或每个服务端请求？路由中间件不作用在它们——用服务端中间件（291）。
- 要动态注册/覆盖中间件？在插件里 `addRouteMiddleware(name, fn, { global })`，同名会覆盖目录里的。
- "只跑一次"放插件、"每次导航"放中间件；初始页中间件会两端各一趟，需要时用 `isHydrating`/`payload.serverRendered` 跳过。
