先说清一件事，免得后面对 "插件" 这个词过敏。这里讲的**不是 Vue 生态里那些 `xxx.use()` 的"Vue 插件"本身**，而是 Nuxt 提供的、在你创建 Vue 应用那一刻跑一遍的**一层机制**——官方叫它 plugins 系统。它存在的理由很具体：有些"接入动作"必须发生在应用实例化的时机，而且只发生一次，比如把一个 Vue 插件注册进整个应用、注册一个全局指令。放组件里跑不合适（会跟着组件反复执行），放 `app.vue` 的 setup 也不合适（拿不到"应用级、只跑一次"的时机）。plugins 就是填这个位置的。

## 它的定位：Vue 应用创建时加载

官方 plugins 页的定位句：

> Nuxt has a plugins system to use Vue plugins and more at the creation of your Vue application.

一句关键机制：

> Nuxt automatically reads the files in the `app/plugins/` directory and loads them at the creation of the Vue application.

翻译给学生：你在项目里建 `app/plugins/` 目录，往里放 `.ts` 文件，Nuxt 会**自动**在应用创建时加载它们。你不用在 `nuxt.config` 里手写注册（除非你要放子目录，见下）。

## 自动注册的边界：只有顶层文件和子目录 index

不是往 `app/plugins/` 里塞任何 `.ts` 都会被注册。页上有一张带注释的目录图，逐行点明了哪些扫、哪些不扫：

```bash [Directory structure]
-| plugins/
---| foo.ts      // scanned
---| bar/
-----| baz.ts    // not scanned
-----| foz.vue   // not scanned
-----| index.ts  // currently scanned but deprecated
```

页上的原话：

> Only files at the top level of the directory (or index files within any subdirectories) will be auto-registered as plugins.

所以：

- `foo.ts`（顶层文件）→ 注册
- `bar/index.ts`（子目录的 index）→ 注册，但官方在注释里直接写了 **deprecated**——新代码里别再指望"子目录 index 自动注册"这条路
- `bar/baz.ts`、`bar/foz.vue` → **不注册**

要放子目录里的插件怎么办？用 `nuxt.config.ts` 的 `plugins` 数组显式登记：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  plugins: [
    '~/plugins/bar/baz',
    '~/plugins/bar/foz',
  ],
})
```

## 一个插件长什么样：入参只有 nuxtApp

最小形态是 `defineNuxtPlugin` 传一个函数，**这个函数唯一的入参就是 `nuxtApp`**：

```ts [plugins/hello.ts]
export default defineNuxtPlugin((nuxtApp) => {
  // 拿到 nuxtApp 做点事
})
```

`nuxtApp` 是什么，是这一章后面几篇的常客——它是 Nuxt 的应用实例，挂着你注册 Vue 插件（`nuxtApp.vueApp.use(...)`）、注册指令（`nuxtApp.vueApp.directive(...)`）、读写 payload（`nuxtApp.payload`）、订阅运行时钩子（`nuxtApp.hook(...)`）等的能力入口。第一篇先记住这个形状，细节留后面展开。

`defineNuxtPlugin` 除了函数形态还有对象形态（多个 `name`、`enforce`、`setup`、`hooks`、`env`、`parallel`、`dependsOn`、`order` 键）。对象形态第一篇不展开——下一篇（271）专门讲三种"返回值形状"（provide / hooks / env），再下一篇（272）专攻顺序相关的 `enforce`、`order`、`parallel`、`dependsOn`。

## .server 与 .client 后缀

页上有一句常被忽略但很实用的话：

> You can use `.server` or `.client` suffix in the file name to load a plugin only on the server or client side.

意思是插件文件名带 `后缀` 就能限定它在哪一侧跑：`app/plugins/vue-gtag.client.ts` 只在浏览器加载、`app/plugins/telemetry.server.ts` 只在服务端。官方那个 Google Analytics 的例子（`nuxtApp.vueApp.use(VueGtag, { property: { id: 'GA_MEASUREMENT_ID' } })` + `trackRouter(useRouter())`）文件名就是 `vue-gtag.client.ts`——因为 Google Analytics 只在浏览器有意义。

这条也解释了官方在 Vue Directives 一节那句 warning：

> If you register a Vue directive, you *must* register it on both client and server side unless you are only using it when rendering one side. If the directive only makes sense from a client side, you can always move it to `~/plugins/my-directive.client.ts` and provide a 'stub' directive for the server in `~/plugins/my-directive.server.ts`.

指令是应用级注册的能力。SSR 阶段服务端渲染 HTML 时也要能解析这些指令——所以要么同一个插件跑在两端（默认，不加后缀就是两端都跑），要么在客户端放真身、服务端放个"桩"（stub）。这背后是插件"两端都跑、但顺序与实例上下文有讲究"的共性——这一章后面几篇会展开。

## 什么时候不该写插件

官方 performance 页在 "Common Problems" 那一节第一条就是插件——原文：

> **Problem**: A large number of plugins can cause performance issues, especially if they require expensive computations or take too long to initialize. Since plugins run during the hydration phase, inefficient setups can block rendering and degrade the user experience.

给出的解法：

> **Solution**: Inspect your plugins and see if some of them could be implemented rather as a composable or utility function instead.

对新手最要记住的一句是 "plugins run during the hydration phase"——插件不是按需跑的。它跟一次页面加载一起跑，跑在应用被创建、被水合的那段时间里，多一个就多一份开销。plugins 页的 Providing Helpers 一节还有一句 important 呼应这个思路：

> Note that we highly recommend using `composables` instead of providing helpers to avoid polluting the global namespace and keep your main bundle entry small.

意思是：如果你只是想提供一个 `hello(msg)` 这类小 helper，`useNuxtApp().$hello(...)` 的插件写法能实现，但官方明确说更推荐直接封一个自动导入的组合式（`export function useHello() { ... }`）——插件那层的 provide 是往全局命名空间挂东西，代价是 bundle 变大和全局命名污染。

## 一句话总结这一章的入口

- **要接入 Vue 插件、注册全局指令、往 NuxtApp 上挂应用级东西** → 这是插件的正经用途。
- **要共享一段响应式状态、要跨组件复用一个 hook 式工具** → 优先组合式（`app/composables/`），别默认上插件。
- **要在"应用创建时"跑一次副作用** → 也放插件里。
- 加了后缀（`.server`/`.client`）就能限定在哪一侧跑；不写后缀就是两端都跑。

## 自查

- 打算写的那个"插件"，是不是其实用一个自动导入组合式就够了？官方明确推荐这条路。
- 是不是把插件写在 `plugins/foo/bar.ts` 却指望它自动注册？只有顶层文件和子目录 index 会自动扫（且后者已 deprecated）。
- 需要指令两端都可用：同一个插件不写后缀就是两端跑；只在客户端用，服务端要有 stub。
- 加了几个插件心里有个数——性能页 "Common Problems" 第一条就是"别滥用插件"。
