## 约定写在一行注释里，证据要另找

`server/utils/http/api-error.ts` 是对外报错的唯一出口，文件头把规矩写死了：

> 响应里能出现的，是「一个 HTTP 状态码 ＋ 一句给人看的话 ＋ 一个机器可读的码 ＋ 本请求的编号」，别的一律不带。理由很实在——`err.message` 常常是驱动层或依赖抛的原话，里面可能有表名、SQL 片段、本机文件路径甚至 `node_modules` 的目录结构。

规矩好不好读一遍就知道。要量的是另外两件事：**拦住泄露的那七条特征是不是真能命中**，以及**钉住这套约定的用例是不是真的会红**。两件都有读数，第二件的结果不太好看。

## 四样东西长这样

`apiError()` 造出来的错误对象，序列化之后就是这个串（本轮跑出来的完整输出）：

```json
{"message":"服务器暂时无法处理这个请求，请稍后重试","statusCode":500,"statusMessage":"Internal Server Error","data":{"code":"INTERNAL_ERROR","requestId":"req-probe"}}
```

四个顶层键、`data` 里两位，这就是全部。`statusMessage` 那句短语来自一张表（`400 Bad Request`、`401 Unauthorized`、`403 Forbidden`、`404 Not Found`、`409 Conflict`、`422 Unprocessable Entity`、`429 Too Many Requests`、`500 Internal Server Error`、`503 Service Unavailable`——最后一位是第四站查分叉时补进去的，写这一站时表里还是八行），表里没有的状态码兜成 `Error`；`code` 不传时兜成 `INTERNAL_ERROR`。

## 先证明那七条特征不是摆设

`test/unit/api-error.test.ts` 里放了一组"栈特征"，只要响应体命中任意一条，就说明内部结构漏到了客户端：

```ts [七条特征，一条都不会误报]
const STACK_MARKERS = [/\n\s+at\s+/, /\bat\s+\S+:\d+/, /\.mjs:/, /\.ts:\d+/, /node_modules/, /[A-Za-z]:[\\/]/, /select\s+.*\s+from\s+/i]
```

断言写的是"零命中"。而**零命中这件事必须先证明扫描在工作**，否则就是假绿——拿一个真实失败去撞它：

```text
[真实失败] {"len":1327,"命中数":5,"命中":["/\\n\\s+at\\s+/","/\\bat\\s+\\S+:\\d+/","/\\.ts:\\d+/","/node_modules/","/[A-Za-z]:[\\/]/"]}
[封装之后] {"body":"{...上面那个串...}","命中数":0}
```

一个模块找不到时，`message` 加 `stack` 一共 1327 个字符，**七条特征里五条命中**（帧行、`文件名:行号`、`.ts:行号`、`node_modules`、Windows 盘符路径）。同一个失败换成 `apiError()` 发出去，命中数 0。两侧都在，才说明"0 命中"是真的干净。

`/select\s+.*\s+from\s+/i` 这一条是给 SQL 用的，本轮这个失败命不中它——想让它现形得造一次真库查询失败，那是需要连库的动作，本文不做。

## 六条契约里有一条是空断言

契约文件里六条用例（本轮跑出来 `6 passed`、整文件 144 毫秒），其中最容易被写坏的是这条：

```ts
it('读不到 requestId 时 data 里就只有 code，不给一个空串占位', async () => {
  const err = await apiErrorWith({ statusCode: 403, message: '没有权限', code: 'FORBIDDEN' })
  expect(err.data).toEqual({ code: 'FORBIDDEN' })   // 原来的写法
})
```

**把实现摘坏试试**：`api-error.ts` 第 68 行原本是"读不到号就不放这一位"，改成无条件放：

```ts
// 摘坏前
...(requestId === undefined ? {} : { requestId }),
// 摘坏后
requestId,
```

改完跑这套用例：`6 passed`。**一条都没红**。

原因是 `toEqual` 会**忽略值等于 `undefined` 的键**。摘坏之后 `data` 变成 `{ code: 'FORBIDDEN', requestId: undefined }`，`toEqual` 照样判过。这条契约写的是"不给一个空串占位"，但它实际什么都没钉住。

换成 `toStrictEqual` 之后（本轮已改进仓库，附带一句解释注释）：

```text
❯ test/unit/api-error.test.ts (6 tests | 1 failed)
AssertionError: expected { code: 'FORBIDDEN', …(1) } to strictly equal { code: 'FORBIDDEN' }
```

再改回实现，`6 passed`。**同一次摘行，改之前测不出问题，改之后立刻红**——这就是"绿不等于对"的具体样子：断言强度不在用例名字里，在选的是哪个匹配器上。

顺带说清另一处为什么不用改：第 39 行那条 `toEqual` 比的是 `{ code, requestId }` 两位都有值的情况，键不会被忽略掉，所以它不是空断言。**只有"期望某个键不存在"的断言才必须用 `toStrictEqual`**。

六条契约各钉一件事，逐条列出来才知道它们合起来才是那四样东西：

| 用例钉的 | 对应实现里的哪一位 |
| --- | --- |
| 状态码原样透传、短语按表给 | `statusCode: input.statusCode ?? 500` 与 `STATUS_TEXT[statusCode]` |
| `code` 与 `requestId` 落在 `data` 的这两个位置 | `data: { code, ...(号存在才放) }` |
| 读不到号时 `data` 里就只有 `code` | 那条条件展开（本轮刚把它的断言换成 `toStrictEqual`） |
| `message` 是人话本身、响应体不含栈特征 | 约定本身＋`STACK_MARKERS` 七条 |
| 不传状态码按 500、不传码按 `INTERNAL_ERROR` | 两处兜底 |
| 表里没有的状态码也有短语 | `?? 'Error'`（用例用 418 试的） |

还有一点值得注意：这些用例跑在**普通 Node** 里，没有 Nuxt 运行时，所以被测模块依赖的 `createError`（服务端自动导入的那一个）必须先挂到 `globalThis` 上再动态 import 模块——挂的是 h3 的真货而不是假桩，因为"序列化之后到底带哪几个字段"正是这一层要测的东西，桩会把它测成假的。上一站量过的"单测层没有任何自动导入"，在这里是同一个道理。

## 这套约定现在被用了多少

| 维度 | 本轮数出来的 |
| --- | --- |
| 机器可读的码 | 23 种，形如 `DB_NOT_CONFIGURED`、`OAUTH_TOKEN_FAILED`、`CSRF_MISMATCH`、`RATE_LIMITED` |
| 状态码分布 | 503 十二处、400 十一处、403 三处、401 两处，502／500／429／404 各一处 |
| 出口调用点 | 分布在 18 个文件（接口、中间件、服务层都有） |
| 出现最多的码 | `OAUTH_NOT_CONFIGURED` 三处，其余两位数的都是配置类与解析类失败 |

**为什么必须有一个 `code`**：客户端要分的是"没配库"还是"没登录"还是"限流了"，这几种情况给的人话可能随时改字，`code` 是可枚举的常量。所以规矩是**按 `code` 分支，不去匹配 `message` 的措辞**——后者是给人读的，改文案是日常。

## 出问题对照

| 症状 | 原因 | 怎么办 |
| --- | --- | --- |
| 客户端把"暂时不可用"当成了"没权限" | 只看状态码，而 503 在这套约定里被复用了十二次 | 分支按 `data.code` 写，状态码只当粗分 |
| 响应体里出现了 `at Object.<anonymous>` 这种行 | 直接把 `err.message` 或整个错误对象发出去了 | 一律走 `apiError()`；`message` 只放人话 |
| 用例明明摘坏了还在绿 | 用了 `toEqual`，`undefined` 的键被忽略 | 期望键不存在就用 `toStrictEqual` |
| "零命中"其实是扫描没跑到 | 断言只有一个方向，没有正对照 | 像本文那样先用真实失败撞一次，数命中几条 |
| 前端想拿编号查日志，body 里却没有 | 那个请求没经过发号的中间件 | 号是搬来的不是造出来的，下一站讲这条链 |

## 你自己跑一遍

1. `npx vitest run test/unit/api-error.test.ts`，看 `6 passed`；再把 `server/utils/http/api-error.ts` 第 68 行改成无条件放 `requestId`，重跑——它现在会红一条（`toStrictEqual` 已经换上了）。
2. 临时写一个用例：`await import('一个不存在的包名')`，在 `catch` 里拿到那个错误，把 `message` 加 `stack` 拼成串，用上面那七条正则各测一遍，数命中几条。这一步是"证明扫描在工作"，别跳。
3. `grep -rhoE "code: '[A-Z_]+'" --include=*.ts server \| sort -u` 看你这份仓库里有几种码，和上面的 23 对一下。
4. 需要跑真服务的一条（本文没做）：起产物服务后 `curl -i` 一个不存在的接口路径，看框架自己的错误通道发不回同样的四键形状——那正好是下一站的题目。

## 这一站的边界

没有起服务、没有连库，所以本文所有读数都来自单测层与代码本身：四键响应体、七条特征的五条命中、`6 passed` 与摘坏后的 `1 failed`、23 种码与 18 个调用点。**真实 HTTP 响应头上那个编号与 body 里的是不是同一个值，这一站没有读数**，下一站专门量它。

仓库这一轮的永久改动只有一处：`test/unit/api-error.test.ts` 里那条断言从 `toEqual` 换成 `toStrictEqual`（附带两行说明为什么）。这不是润色——原写法钉不住任何东西。
