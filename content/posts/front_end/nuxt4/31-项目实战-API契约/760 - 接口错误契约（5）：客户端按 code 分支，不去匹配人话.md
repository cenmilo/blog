## 分好二十四类，页面一次都没用

前面四站把对外报错那层立起来了：状态码、人话、机器可读的码、本请求的编号，两位在 `data` 里。站里现在一共有 24 种 `code`，接口在 33 处调用点上都照着发。

然后来看客户端这一侧读了什么。`app/pages/docs/[slug].vue` 里取数失败那一段，改之前的原文是：

```ts
const upstream = error.value.status ?? 500
const unavailable = upstream !== 404
```

**接口分好的二十四类，到这儿只剩一句"是不是 404"。** 这一位还不是最难看的——最难看的一条量出来之后是一个真事故形状。本轮给它补了四条端到端用例，把这条链路量到底，读数在下面。

## 先认全 `data` 这一位：它有两种来源

官方讲 `useError` 那一节把错误对象的形状写得很清楚：

```ts
interface NuxtError<DataT = unknown> {
  status: number
  statusText?: string
  message: string
  data?: DataT
  cause?: unknown
  fatal: boolean
}
```

`data` 是"你要的自定义字段放这里"那一个位。问题在于，同一个 `data` 有两种来源，**层数不一样**：

| 这一位怎么来的 | `error.value.data` 装的是什么 | 码在哪 |
| --- | --- | --- |
| 页面自己 `createError({ data: { code, requestId } })` | 就是那两位 | `error.value.data.code` |
| `$fetch` 撞上一次非 2xx（经 `useAsyncData` 转手） | 整个响应体 | `error.value.data.data.code` |

第二种不是设计，是链路上顺出来的：`ofetch` 1.5.1 的 `FetchError` 把响应体挂在 `.data` 上（`dist/shared/ofetch.CWycOUEr.mjs:32` 那行 `["data", "_data"]` 就是它的取值路径，响应体在检查状态码之前已经被解析，同一文件 `:296-310`），而 h3 的 `createError` 只搬 `input.data` 这一位（`dist/index.mjs:88-90`）——搬的是整个 body，不是 body 里的 `data`。

读错一层，代码不会报错，只会安静地读到 `undefined`，然后走进"那就按状态码猜"那条兜底。本轮第一版就栽在这儿，读数见后面那条红趟。

## 归一之后怎么写

`app/pages/docs/[slug].vue` 现在那一段（注释是原文）：

```ts
if (error.value) {
  const upstreamBody = error.value.data as
    | { code?: string, requestId?: string, data?: { code?: string, requestId?: string } }
    | undefined
  const upstream = upstreamBody?.data ?? upstreamBody

  const notFound = upstream?.code !== undefined
    ? upstream.code === 'DOC_NOT_FOUND'
    : error.value.status === 404

  throw createError({
    status: notFound ? 404 : 503,
    statusText: notFound ? 'Not Found' : 'Service Unavailable',
    message: notFound ? '没有这篇文档。' : '文档暂时不可用。',
    data: {
      code: upstream?.code ?? (notFound ? 'DOC_NOT_FOUND' : 'CONTENT_UNAVAILABLE'),
      ...(import.meta.server || !upstream?.requestId ? {} : { requestId: upstream.requestId }),
    },
    fatal: true,
  })
}
```

三位分别说清：

- **先读 `code`，读不到才退回状态码**。因为 `code` 是穷举集合，而状态码在这一条线上是复用的——站内 503 有十二处，光看那三位数字分不出"这篇没有"和"目录读不到"。
- **`message` 由页面自己写**，上游那句人话一个字都不搬。这句是"不匹配人话"最直接的落点：上游改文案是日常，页面不该跟着变。
- **编号分两种进法**。服务端那一趟取数是**回环请求**——页面在服务端自己 HTTP 调自己一次，那次请求有它自己的号，但用户的浏览器里看不见它，看得见的是这次页面响应的 `x-request-id`。客户端导航时那次取数是浏览器自己发的，看得见的那个号就是它。所以服务端不搬、客户端搬，两种进法都取"用户能核对上的那一个"。

顺带一句为什么不能靠 `cause` 拿到上游那个错误：官方讲 `createError` 那段明写「in production, causes are never included in error responses or the error page payload」。

## 四条读数

用例在 `test/e2e/error-code.spec.ts`（四条，跑法 `E2E_PORT=<空闲位> npm run test:e2e -- test/e2e/error-code.spec.ts`）。**改之前**，客户端导航那一条是这个形状：

```text
[漂移形状·改前] {"屏上码":"错误码：DOC_NOT_FOUND","有编号行":false,"屏上人话":"没有这篇文档。",
  "整页":"404 页面不存在 没有这篇文档。 错误码：DOC_NOT_FOUND 地址可能拼错了，或者这一页已经下线。 重新加载"}
```

**改之后**同一条用例：

```text
[漂移形状·改后] {"屏上码":"错误码：CONTENT_UNAVAILABLE","有编号行":true,"屏上人话":"文档暂时不可用。",
  "整页":"503 出了点问题 文档暂时不可用。 错误码：CONTENT_UNAVAILABLE 编号：0f0f0f0f-1111-4111-8111-abcdefabcdef 请稍后重试，或返回首页。 重新加载"}
```

这一条用的是"漂移形状"：`page.route()` 造一次响应，**状态说 404、`code` 说 `CONTENT_UNAVAILABLE`**。真实接口目前不会这么自相矛盾（它的两种搭配是 404 配 `DOC_NOT_FOUND`、503 配 `CONTENT_UNAVAILABLE`，下面第三条就是真的那一次），造这一位是为了让"页面读的是哪一位"看得出来——如果页面按状态码猜，它会把一次暂时的故障报成"这篇不存在"，而这正是上面那行改前的结果。

另外三条都在真实响应上跑：

| 用例 | 环境 | 读数 |
| --- | --- | --- |
| 服务端直达一个不存在的 slug | 常规一趟 | 接口 404 `DOC_NOT_FOUND`；接口那趟的号 `c059864b-…`，页面响应的号 `b307d046-…`，**屏上显示的是 `b307d046-…`**（回环那个号浏览器里查不到，所以不搬） |
| 大写 slug（形状就不对） | 常规一趟 | 页面与接口两道闸门都不发那次取数；屏上 404、`DOC_NOT_FOUND`、编号是这次页面响应自己的号 |
| 内容目录指错（真 503） | `NUXT_CONTENT_DIR=__missing__` 单跑一趟 | 接口 503 `CONTENT_UNAVAILABLE` ⇒ 页面状态 503、屏上状态码 `503`、屏上码 `CONTENT_UNAVAILABLE`、人话 `文档暂时不可用。` |

两条趟的打印：常规那趟 `3 passed`（第 4 条 skip），指错目录那趟 `1 passed`、`3 skipped (25.4s)`。相邻的三个用例文件一起回归：`12 passed`、`8 skipped`（那八条要库与 SMTP）。`npm run check` 七项全 ok。

## 这二十四个码长什么样

```bash
grep -rhoE "code: '[A-Z_]+'" --include=*.ts server/ | sed "s/code: '//;s/'//" | sort -u | wc -l
```

本轮数出来的三件事：

| 数的是 | 结果 |
| --- | --- |
| 去重后的码 | 24 种，`BAD_REQUEST`、`CSRF_MISMATCH`、`DB_NOT_CONFIGURED`、`LINK_INVALID`、`MAIL_NOT_CONFIGURED`、`OAUTH_STATE_INVALID`、`RATE_LIMITED`、`SECRET_NOT_A_STRING`… |
| 不符合"大写下划线"写法的 | 0 条 |
| 页面侧自己造出来的码 | 2 种（`DOC_NOT_FOUND`、`CONTENT_UNAVAILABLE`），都已经在上面那 24 种里 |

第三行是这条链路的纪律：**页面不能新造码**。上一站说过状态短语不能自创，这一位同理——新造一个只有页面认识的码，接口那侧的日志与文档就不认识它了。

另外交代一句数差：第三站报过 23 种，本轮 24 种。差的那一种是探针接口里新写的一条 `code: 'LINK_INVALID'`——那串字面值本身早就存在（在登录服务里是个导出的常量，不被这条正则数到），所以**码的真实种类没有增加**，是这条正则第一次看见了它。这类"统计口径变化"要写清楚，否则下一轮会以为有人新增了错误类型。

## 出问题对照

| 症状 | 原因 | 怎么办 |
| --- | --- | --- |
| 一次暂时的故障被报成"内容不存在" | 页面按状态码分类，而状态码是复用的 | 先读 `code`，读不到才退回状态码 |
| `error.value.data.code` 一直是 `undefined` | `$fetch` 失败时那一位装的是整个响应体，码在再下一层 | 两种来源先归一再读（`?.data ?? 本体`） |
| 错误页上没有可抄的编号 | 页面重新造错误时没把上游 `data` 里的号带上 | 客户端导航那一趟搬号；服务端那一趟交给 `error.vue` 从请求事件里取 |
| 页面上出现"永远对不上"的用户报号 | 搬了服务端回环请求的号，那个号浏览器里查不到 | 只搬用户能核对上的那一个 |
| 上游改了一句文案，页面某块判断失灵 | 判断读的是 `message` | 判断只读 `code`；`message` 只给人看 |
| 页面上冒出一个接口从没发过的码 | 页面自己造了个新码 | 页面只搬运、不改写；新码先进服务层那份清单 |

## 你自己跑一遍

1. `E2E_PORT=3130 npm run test:e2e -- test/e2e/error-code.spec.ts` → `3 passed`、1 skipped；把 `NUXT_CONTENT_DIR=__missing__` 加上再跑一次，看第 4 条那行 `[真 503]`。
2. 亲手复现那个事故形状：把 `app/pages/docs/[slug].vue` 里 `const notFound = ...` 那三行换成 `const notFound = error.value.status === 404`（也就是不看 `code`），重跑第 1 步——客户端导航那条会红，屏上码回到 `DOC_NOT_FOUND`，编号那一行消失。改回来。
3. 数一自己的仓库：`grep -rhoE "code: '[A-Z_]+'" --include=*.ts --include=*.vue server/ app/ \| sed "s/code: '//;s/'//" \| sort -u`，再拿 `grep -vE "^[A-Z_]+$"` 接在后面看有没有不规范写法。
4. 打开 DevTools 走到 `/docs/nope-not-here`，把 Network 面板里那两个请求（页面与 `/api/docs/…`）的 `x-request-id` 记下来，对照页面上那行编号是哪个——这一步是把"回环请求有它自己的号"这件事亲眼看见。

## 这一站的边界

四条用例都在产物服务上跑（端口 3130 与 3132，指错目录那趟要单独一趟环境变量），没有连库、没有 SMTP，`.env` 里的值没进任何输出。`page.route()` 造的那个漂移响应只用于让"页面读哪一位"可观察，其余三条都在真实响应上。

三处**没做**：会员区那两块面板（`app/components/ConsoleMetricsPanel.vue` 与 `app/pages/console/index.vue`）也用 `useFetch`，同样会撞上那个层数问题，本轮没动它们（它们目前不读 `data`）；`app/error.vue` 的文案表还是按状态码分的，没按 `code` 分（改了要连带量一遍无障碍播报，归后面）；带登录态那条错误路径需要库，仍留给读者。

仓库这一轮的永久改动：`app/pages/docs/[slug].vue` 那一段（归一、按 `code` 分类、号分两种进法）与它注释里两处过期引用；新增 `test/e2e/error-code.spec.ts`（四条）。第三站那条 `[reflect]` 读数与第四站那句"八行表"在前两轮已同步过，本轮没有再改前面的文章。
