## 先想清楚这个号要拿来干什么

用户说"我点了一下就报错"。你打开服务端日志，每个请求一行 JSON，几百行铺在那里。要指到他那一次，你需要一个双方都持有的字符串：他报得出，你也查得到。

上一站定了响应体里能出现哪四样东西，"本请求的编号"是其中一位。这一站只谈这个号：从哪来、经过哪几处、写错了什么样。

发号的地方是 `server/middleware/request-id.ts`。这个目录里的文件，每个请求进来都会先过一遍，官方给的说法是：

> Middleware handlers will run on every request before any other server route to add or check headers, log requests, or extend the event's request object.

同目录那条提示块还补了一句边界，这句不是风格建议：

> Middleware handlers should not return anything (nor close or respond to the request) and only inspect or extend the request context or throw an error.

中间件一旦返回值（或者直接结束响应），那个值就成了响应，排在后面的接口根本不会被调用。所以这里只写上下文、只设头，不 `return`。

## 号只发一次

整个文件的有效逻辑是四行：

```ts [server/middleware/request-id.ts]
import { randomUUID } from 'node:crypto'

export default defineEventHandler((event) => {
  const requestId = randomUUID()
  event.context.requestId = requestId
  setHeader(event, 'x-request-id', requestId)
  logRequest(event, { msg: 'request', route: getRequestURL(event).pathname })
})
```

三个位置解释一遍，不然后面读不通。

- `event.context`：同一个请求内部共享的一块地方。中间件往里写，后面任何一个接口、任何一条日志读到的都是这一个值。
- `randomUUID()`：Node 自带的 `node:crypto` 里的函数，发一个 UUID 版本 4 的字符串，36 个字符含连字符，形如 `b230d610-b482-…`。不装任何包。
- `logRequest`：写在 `server/utils/http/` 下面，`server/utils/` 是自动导入目录，所以这里没有 `import` 也能用（上一站讲服务端自动导入时提过同一件事）。

## 到了报错那一层，是"搬"不是"再发一个"

`server/utils/http/api-error.ts` 里跟号有关的只有三行：

```ts
const requestId = event.context.requestId as string | undefined
// ...
...(requestId === undefined ? {} : { requestId }),
```

`data` 里这一位是从上下文搬过来的，函数自己不生成号。**最容易顺手写出来的错法是 `requestId ?? randomUUID()`**：类型合法、跑得起来、格式也漂亮，但它是新发的那一个，和响应头里的那个必然不同。用户报体里的号，你按号去搜日志，搜到的是另一条请求——对上的概率不是低，是零。

读不到号就连键都不放（上一站那条用 `toStrictEqual` 钉住的契约说的正是这一位）。什么时候会读不到？只有请求没经过发号中间件的时候，比如直接在 Nitro 插件里报错。

## 三处读数：同一个值

起开发服务，打一次探针接口，看三个地方：

```bash
npm run dev -- --port 3115
curl -i -s 'http://localhost:3115/api/error-case?kind=bad-request' | head -6
```

响应头里：

```text
HTTP/1.1 400 Bad Request
x-request-id: b230d610-b482-4997-a738-3f85745a1866
```

响应体里（本轮这一条返回的 `data`）：

```json
"data": { "code": "BAD_REQUEST", "requestId": "b230d610-b482-4997-a738-3f85745a1866" }
```

终端同一时刻打出来的日志行：

```json
{"ts":"2026-10-17T17:03:48.572Z","level":"info","msg":"request","requestId":"b230d610-b482-4997-a738-3f85745a1866","userId":null,"route":"/api/error-case"}
```

三处字符串逐字符相同，不需要任何"两边都调一次生成函数再碰运气"。日志行的六个键顺序也是固定的：`ts`、`level`、`msg`、`requestId`、`userId`、`route`，`test/unit/audit-log.test.ts` 里有 4 条用例钉着这一行，本轮跑出来 `4 passed`。

注意 `route` 只有路径 `/api/error-case`，查询串没有进来。日志会留存、会被采集器搬到别处，而查询串里可能有 token——这一位在写的时候就只取了 `getRequestURL(event).pathname`。

## 上了产物服务，号还在不在

上面那趟是开发服务。真正的验收得跑发布物：新增一个端到端契约文件 `test/e2e/api-contract.spec.ts`，它打的是 `nuxt build` 之后起起来的服务，五条用例本轮跑出来 `5 passed (25.8s)`，每条自己把读数打在控制台：

```text
[bad-request] {"status":400,"keys":["data","error","message","statusCode","statusMessage","url"],"statusMessage":"Bad Request","code":"BAD_REQUEST","headerId":"5eb3189d-abd2-4e3a-9627-cbc571726196","bodyId":"5eb3189d-abd2-4e3a-9627-cbc571726196","same":true}
[server-fail] {"status":500,"keys":[...同上...],"message":"服务器暂时无法处理这个请求，请稍后重试","code":"INTERNAL_ERROR","url":"http://localhost:3114/api/error-case?kind=server-fail","命中":[]}
[raw] {"status":500,"keys":["error","message","statusCode","statusMessage","url"],"message":"Server Error","statusMessage":"Server Error","dataKeys":[],"headerId":"4b4ae798-6236-463f-995c-aa1b52204dbb","hasStackField":false}
[reflect] {"status":400,"code":"UNKNOWN_KIND","message":"kind 参数只支持 bad-request、server-fail、raw 与 self-send","message含探针值":false,"url":"http://localhost:3114/api/error-case?kind=%3Cscript%3Ezzz%3C%2Fscript%3E","url含探针值":true}
[two requests] {"headA":"515ae66c-1356-49a7-a8f5-7ab15ae28af9","headB":"82052657-fd4e-48ad-a899-bc09627e4cfe","不同":true}
```

四件事在第一行到第三行里，一张表说清：

| 请求 | 状态码 | 响应头 | 响应体 `data` |
| --- | --- | --- | --- |
| `kind=bad-request` | 400 | 有号 | 有号，与头里逐字符相同 |
| `kind=server-fail`（走封装的 500） | 500 | 有号 | 有号，`code` 是 `INTERNAL_ERROR` |
| `kind=raw`（裸抛） | 500 | 有号 | `data` 这个键整个不存在 |
| `kind` 填一个不认识的串 | 400 | 有号 | 有号，`code` 是 `UNKNOWN_KIND` |

第三行是这一站最想让你记住的形状：**号会不会出现在响应体里，取决于这个错误是不是从 `apiError()` 出去的，跟状态码没关系。** 裸抛那一条，中间件照样发了号，头里有、日志里也有（开发服务上读到的这一对是 `636262de-b1e5-45a9-b5f0-a96573536314`，两处相同），唯独响应体里没有——用户只能复述"页面写了 Server Error"，你没法让他报一个号出来。

`[two requests]` 那行钉的是另一半：同一个接口连打两次，两个号不同。号是"请求级"的，不是"接口级"的，否则日志里同一接口的几百行会共用一个串，等于没有。

## 开发服务里的错误体和产物里的不是一回事

这条是本轮顺手读出来的，值得单独一节，因为它会让人把"干净"判断错。

| 分支 | 开发服务的顶层键 | 产物的顶层键 |
| --- | --- | --- |
| 走封装的 400 | 7 个，多一个 `stack` | 6 个 |
| 走封装的 500 | 7 个，多一个 `stack` | 6 个 |
| 裸抛的 500 | 6 个，无 `data`、有 `stack` | 5 个，无 `data` |

开发服务多出来的 `stack` 是一个数组，本轮那条 400 里是 10 行，内容是这台机器上的绝对路径和依赖包里的行号（路径各人不同，这里只留形状）：

```text
at createError (…/node_modules/h3/dist/index.mjs:71:15)
at apiError (…/server/utils/http/api-error.ts:62:9)
at Object.handler (…/server/api/error-case.get.ts:12:10)
```

更要紧的是 `message`。开发服务上裸抛的那一条，`message` 直接就是内部错误的原话：

```text
select id from users where email = $1 失败: connect ECONNREFUSED
```

表名、SQL 片段、驱动报错一个不少。同一个请求在产物里发回的是 `"message": "Server Error"`，框架把原话换成了兜底串，留在服务端 stderr 里，那一行前面还带完整请求地址：

```text
[request error] [unhandled] [GET] http://localhost:3114/api/error-case?kind=raw
```

所以"响应体漏没漏"这件事只能在产物上判，开发服务上量出来的是开发服务的形状。上一站那七条栈特征，这一站原样搬到真 HTTP 响应上重扫了一遍：走封装的 500 命中数 0，而且整份响应体里 `ECONNREFUSED` 和 `index.mjs` 这两个词都搜不到——内部错误那句原话确实一个字节都没出去。

## 摘掉那一行，看用例会不会红

"头里和体里同一个值"这条断言很容易是假的：两边各自读一个号，只要都非空就绿。验证办法是故意把它写坏——把中间件那一行改成另发一个号：

```ts
// 摘坏前
setHeader(event, 'x-request-id', requestId)
// 摘坏后
setHeader(event, 'x-request-id', randomUUID())
```

跑 `E2E_PORT=3115 npm run test:e2e -- test/e2e/api-contract.spec.ts`：

```text
2 failed
  > 47 |  expect(body.data?.requestId).toBe(headerId)
  > 119 | expect(bodyA.data?.requestId).toBe(a.headers()['x-request-id'])
3 passed (25.2s)
```

红的正是那两条"同一个值"，另外三条（栈特征零命中、裸抛形状、不回填输入）照旧绿——它们本来就不该依赖这一位。改回去重跑：`5 passed (25.8s)`，`npx eslint server/middleware/request-id.ts` 无输出。

## 顺序是隐性的，改名会换掉它

`server/middleware/` 里现在只有两个文件：`auth.ts` 与 `request-id.ts`。构建产物里的路由表按文件名字典序注册中间件，`auth` 排在 `request-id` 前面。

为什么值得写：日志行里那个 `userId` 读的是 `event.context.user`，而它是 `auth.ts` 挂上去的。哪天新增一个 `00-trace.ts`，或者把 `request-id.ts` 改成 `a-request-id.ts`，先后就换了，症状是 `userId` 恒为 `null`，而号一切正常——一半正常一半永远不动，最容易误判成"产物过期"。

反过来，"发号一定在报错之前"目前成立：这两个中间件里没有任何一处 `throw`（整个 `server/middleware/` 目录里 `throw` 只出现在注释文本中），拒绝请求的动作都发生在接口文件里，那时号已经发过了。

## 出问题对照

| 症状 | 原因 | 怎么办 |
| --- | --- | --- |
| 用户报的号在日志里搜不到 | `api-error.ts` 里顺手写了 `randomUUID()` 兜底 | 号只从 `event.context` 读，不在这层生成 |
| 头里一个号、体里另一个号，两条用例同时红 | 中间件把 `setHeader` 换成了新生成的值 | 两处引用同一个局部变量 |
| 500 响应体里没有 `data` | 那个错误是裸抛的，没经过 `apiError()` | 所有对外错误都走封装出口 |
| 日志行里 `userId` 永远是 `null` | 中间件先后被文件名改了 | 检查 `server/middleware/` 的文件名排序 |
| 日志行里出现了 token | `route` 用了完整地址而不是路径 | 只取 `getRequestURL(event).pathname` |
| 开发服务上看着漏了，线上一切正常 | 开发模式多塞 `stack`、`message` 用原话 | 泄露判断只在 `nuxt build` 的产物上做 |

## 你自己跑一遍

1. `npm run dev -- --port 3115`，另开一个终端跑 `curl -i -s 'http://localhost:3115/api/error-case?kind=bad-request' | head -6`，再对照终端里那一行日志，看三处字符串是不是同一个。
2. `E2E_PORT=3114 npm run test:e2e -- test/e2e/api-contract.spec.ts`，看 `5 passed` 和五条自打印的读数。端口被占用就换一位，别去动别人的进程。
3. 摘行验证：把 `setHeader(event, 'x-request-id', requestId)` 改成 `randomUUID()`，重跑第 2 步，确认红的是那两条而不是全部五条；改回去。
4. `npx vitest run test/unit/audit-log.test.ts`，`4 passed`——这一行日志的六个键顺序也是有用例钉着的。
5. 想看开发服务与产物的差别：第 1 步的 `curl` 结果里数一下顶层键有几个，再跑第 2 步，对比 `[raw]` 那行的 `keys`。

## 这一站的边界

日志三处同源那一组读数来自开发服务；响应头与响应体同源、裸抛形状、栈特征零命中、两个请求两个号，来自 `nuxt build` 的产物（端口 3114，整趟 25.8 秒）。没有连数据库，探针接口本身不碰库；`.env` 里的任何值都没进过上面任何一段输出。

两件**没有读数**的事：网关或 CDN 会不会覆盖 `x-request-id`（不少反向代理用同名头，部署环境上要自己确认一遍再依赖它）；带登录 cookie 的请求里日志行 `userId` 是否真填得上（那是登录链路那一篇的读数，本线没做）。

仓库这一轮的永久改动：新增 `test/e2e/api-contract.spec.ts`（五条契约）；`server/middleware/` 两个文件的注释里删掉了外部读者看不到的路径引用。实现代码一行没动。
