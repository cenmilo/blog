## 先看清一件事：这条命令以前不存在

前五站立了规矩：发哪四位、号从哪来、什么时候不许 `throw`、状态短语只能用什么、客户端读哪一位。但这套规矩有个共同的软肋——**违反它们的时候，什么都不会变红**：

- 那张状态码表少一行，请求照样发得出去，只是状态行安静兜成 `Error`（第四站就是这么撞上的：503 用了两处、表里没这行）。
- 自回那一路的短语是手抄的字面值，抄歪一个词，只有读状态行的东西看得见。
- `code` 写成小写或带空格，类型检查不会管（它是 `string`），客户端那条分支永远走不到。

所以这一站的产出只有一个：`npm run check` 多了一项，专查这三件事。跑一次长这样（本轮打印）：

```text
错误契约：调用点 35 处（throw 16、自回 19），分布在 17 个文件
状态码 8 种：503×12、400×11、401×4、403×3、404×2、502×1、500×1、429×1
表里 9 行；用到的码 21 种，另有 1 处是模板串拼出来的（不算进种数）
表里暂时没人用的码：409、422
只有自回那一路在用、表里还没有的码：502（现在不影响状态行；若改成 throw 会发 'Error'）
问题 0
```

## 为什么不能用一条 grep 数了就算

第三站那份统计是 `grep -rhoE "code: '[A-Z_]+'" server/` 数出来的，本轮把整层重数一遍才发现这条管道**数不准**，三种形状它看不见：

| 那一位怎么写 | grep 看得见吗 | 站里的例子 |
| --- | --- | --- |
| 字面量写在调用点里 | 能 | `code: 'CSRF_MISMATCH'` |
| 写成常量再传进去 | 不能（那是 `const X = '…'`） | `server/services/auth/oauth.ts:57` 的 `UNREACHABLE` |
| 传的是变量 | 不能 | `callback.get.ts` 里那句 `code: identity.code` |
| 模板串拼出来的 | 不能（引号不对） | `login-link.post.ts` 那句按 issue 拼大写 |

于是真实数字是这样的：出口调用点上的字面码 21 种，服务层结果对象里另外有 3 种（`OAUTH_TOKEN_FAILED`、`OAUTH_PROFILE_FAILED`、`OAUTH_NO_VERIFIED_EMAIL`），常量里藏着 1 种（`OAUTH_PROVIDER_UNREACHABLE`）——**能到达 `data.code` 的一共 25 种**，而那条管道报 24。差的那一种不是数字游戏，它恰好是"看不见的那一类"。

守卫脚本走的是另一条路：它找的是调用点，然后把读不出字面值的三种情况**明说**（打印里那句"另有 1 处是模板串"就是这一位）。

## 守卫查的三条

`scripts/check-error-codes.mjs`（只读文件、只打印，退出码非 0 就有问题）。它先把 `STATUS_TEXT` 那张表读成一张映射，再扫 `server/` 下每个 `.ts`，取出两类调用点的 `statusCode`、`statusMessage`、`code`，然后判三件事：

1. **走 `throw` 的调用点用到的每个码都必须在表里**。只有那一路会查表；缺行不会崩，只会安静发 `Error`。
2. 自回那一路手写的短语必须等于表里同一个码的那句。两条出口发同一个状态码时，状态行必须一模一样。
3. `code` 必须是大写字母开头、只含大写字母数字下划线；模板串单列出来，不硬判。

这两条"看起来都一样"的规矩，用两次改名验出来它们各自会红：

```text
把表里 503 那句改成 'Unavailable'
  问题：…503 的短语自回写的是 'Service Unavailable'，表里是 'Unavailable' ⇒ 同一个码两种状态行
  问题 10   （10 个自回的 503 调用点，每个一条）

把表里 503 那一行整个删掉
  问题：server/services/auth/login-link.ts：走 throw 的调用点用了 503，但表里没有这一行 ⇒ 状态行会发 'Error'
  问题 2    （正是第四站修掉的那处）
  另外那行提示也跟着变：只有自回那一路在用、表里还没有的码：502、503
```

一次改名红 10 条、一次删行红 2 条。删行那次只红 2 条是有原因的：那一行不在了，第二条规矩就没得比了——**能看出"查不了"和"查过了但没问题"是两回事的，只有第一条**。两处改完都已还原（`api-error.ts:53` 现在是 `503: 'Service Unavailable'`）。

## 每个接口该给哪个码

这张表就是脚本 `--by-file` 那一档打印的原文（格式是 `状态码/码/出口`）：

| 文件 | 会发出去的（状态码／码／出口） |
| --- | --- |
| `api/admin/users/[userId]/sessions.delete.ts` | 400／`USER_ID_INVALID`／throw |
| `api/auth/github/callback.get.ts` | 400／`CODE_MISSING`／自回；403／`OAUTH_STATE_INVALID`／自回；502／变量传入／自回；503／`DB_NOT_CONFIGURED`、`OAUTH_NOT_CONFIGURED`、`SESSION_CREATE_FAILED`／自回 |
| `api/auth/github/start.get.ts` | 503／`OAUTH_NOT_CONFIGURED`／自回 |
| `api/auth/login-link.post.ts` | 400／模板串（按邮箱那几道检查的结果拼出来）／throw |
| `api/auth/verify.get.ts` | 400／`TOKEN_MISSING`／自回；401／`LINK_INVALID`／自回（常量传入）；503／`DB_NOT_CONFIGURED`、`SESSION_CREATE_FAILED`／自回 |
| `api/docs.get.ts` | 503／`CONTENT_UNAVAILABLE`／自回 |
| `api/docs/[slug].get.ts` | 404／`DOC_NOT_FOUND`／自回（常量）；503／`CONTENT_UNAVAILABLE`／自回 |
| `api/email-check.get.ts` | 400／模板串／throw |
| `api/error-case.get.ts`（契约探针） | 400／`BAD_REQUEST`、`UNKNOWN_KIND`／throw；401／`LINK_INVALID`／自回；500／`INTERNAL_ERROR`／throw |
| `api/session-demo.post.ts` | 400／`BAD_REQUEST`／throw |
| `api/token-demo.post.ts` | 400／模板串、`IP_UNKNOWN`／throw |
| `services/auth/login-link.ts` | 400／`IP_UNKNOWN`／throw；503／`MAIL_NOT_CONFIGURED`、`MAIL_SEND_FAILED`／throw |
| `utils/auth/require-user.ts` | 401／`UNAUTHENTICATED`／throw |
| `utils/auth/require-admin.ts` | 403／`FORBIDDEN`／throw |
| `utils/http/csrf.ts` | 403／`CSRF_MISMATCH`／throw |
| `utils/http/rate-limit.ts` | 429／`RATE_LIMITED`／throw |
| `utils/runtime-secret.ts` | 503／`SECRET_NOT_A_STRING`／自回 |

读这张表的三条经验，都是前几站量过的：

- **同一个状态码在不同文件里代表不同的事**。503 十二处，分着"没配库""没配 SMTP""没配 OAuth""写会话失败""内容目录读不到""配置项类型不对"——这正是为什么客户端要按 `code` 分支。
- **授权那几条路由一律是自回**：`verify` 与 GitHub 那两条的查询串里带凭据（第三站那条）。
- **`utils/` 里的守卫发的是 throw**：它们被接口调用，失败属于"这个请求不该继续"，地址里没有凭据，白拿三个安全头反而更好。

## 那位变量传的码，用类型锁住

表里唯一"看不见值"的一位是 OAuth 回调那句 `code: identity.code`——码是服务层那段状态机给的。翻开 `server/services/auth/oauth.ts`，那一位以前标的是 `code: string`：

```ts
export type OAuthFailureCode =
  | 'OAUTH_PROVIDER_UNREACHABLE'
  | 'OAUTH_TOKEN_FAILED'
  | 'OAUTH_PROFILE_FAILED'
  | 'OAUTH_NO_VERIFIED_EMAIL'

/** 机器可读码，交给 `apiFailureResponse` 的 data.code；值域见上面那个联合 */
code: OAuthFailureCode
```

改成联合之后，编译器替这条规矩站岗。本轮把它当探针试了一次：把其中一处 return 改成 `code: 'OAUTH_TOKEN_FAILD'`（少一个字母），`npm run typecheck` 立刻红（`rc=2`）：

```text
server/services/auth/oauth.ts(98,51): error TS2820: Type '"OAUTH_TOKEN_FAILD"' is not assignable to type 'OAuthFailureCode'. Did you mean '"OAUTH_TOKEN_FAILED"'?
```

那句 "Did you mean" 是 TypeScript 给的，不用自己写提示。改回来之后 typecheck `rc=0`。**这一位的价值不在"发现现在的错"（现在没有），在于以后加一步新故障时，必须先在那个联合里登记，编译器才会去查每一个 return。**

## 两种"看得见但不动手"

打印里那两行提示是故意只提示不算问题的：

- **表里没人用的码：409、422**。留着。它们对应的状态码在这条线上是标准动作（冲突、内容形状不对），只是还没有接口用到；删掉以后真要用的时候又会忘记补，那正是第四站那个缺口的成因。
- **只有自回在用的码：502**。表里也没有它，但这一位不该补：表是给 `throw` 那一路查的，502 目前只出现在自回出口，短语由调用点自己写，补一行就是没人读的死数据。脚本仍把它列出来，是因为这处一旦改成 `throw`，状态行会当场退化成 `Error`——那是一次真实的改动，值得留一行提示。

## 六步各留一句

| 站 | 一句话 |
| --- | --- |
| 756 | 响应里只有四样东西：状态码、一句人话、一个机器可读的码、本请求的编号；说"零命中"之前先证明扫描在工作 |
| 757 | 号在中间件里发一次，之后处处都是搬；裸抛的那一支体里连 `data` 都没有，客户端无从引用 |
| 758 | 查询串里带凭据就不许 `throw`——框架的错误通道会把完整地址写进响应体，未处理那一路还把它打进日志；代价是自回要自己把关响应头 |
| 759 | 状态短语只能是可见 ASCII，越界的字符 h3 是删掉不是报错；表里缺行不崩，只是安静兜成 `Error` |
| 760 | 客户端按 `code` 分支、不搬上游的人话；`$fetch` 失败时 `data` 是整个响应体，比页面自己造的错误多一层 |
| 761 | 这三类错都不会让用例变红，所以把它们收进一条命令：`npm run check` 现在八项 |

## 出问题对照

| 症状 | 原因 | 怎么办 |
| --- | --- | --- |
| `npm run check` 第 2 项红，说某个码不在表里 | 新增了状态码但没登记 | 往 `STATUS_TEXT` 补一行 ASCII 短句，别在调用点自己兜 |
| 表里加了行、用例却全绿 | 用例只测了走 `throw` 的分支，没测短语一致性 | 跑 `node scripts/check-error-codes.mjs`，它按调用点比 |
| 同一个状态码在不同接口状态行不一样 | 自回那一路手抄的短语与表里的分叉 | 以表为准改调用点；表里没有就补表 |
| 客户端分支不生效 | `code` 写成小写或带空格 | 守脚本第三条会点名；写之前照已有码的写法抄 |
| 统计数字每轮都不一样 | 用一条 grep 数常量与模板串都数不到 | 用脚本按调用点走查，读不出的明说"读不出" |
| 页面把一次故障报成"内容不存在" | 页面按状态码猜分类 | 先读 `code`（第五站那条），并让服务层用联合类型锁死值域 |

## 你自己跑一遍

1. `node scripts/check-error-codes.mjs` 看那六行打印；再加 `--by-file` 看那张逐文件表。
2. 改名验证：把 `api-error.ts` 里 503 那句改成 `'Unavailable'`，跑第 1 步——`问题 10`；再把那整行删掉——`问题 2`，且提示行里多出 503。两次都改回来。
3. 类型守卫验证：把 `oauth.ts` 某处 return 的 `code` 少打一个字母，跑 `npm run typecheck`——`TS2820` 且带 "Did you mean"；改回来。
4. `npm run check` 现在应当打印八项全 ok（新加的 `check:errors` 只用两百多毫秒）。
5. 拿自己项目对一遍：把 `apiError`／`apiFailureResponse` 换成你自己的出口名，这个脚本的三条规矩照样能用。

## 这一站的边界

这一站的读数全部来自静态走查与本地命令（`node scripts/check-error-codes.mjs`、两次改名验证、一次 `typecheck` 红趟、`npm run check` 八项 rc=0：check:errors 262、check:migrations 249、lint 2748、typecheck 6490、unit 1581、build 24224、test:nuxt 3738 毫秒）。没有起服务、没有连库，`.env` 里的值没进任何输出；**连库/写库的授权问到第十轮仍无答复**，所以库里那些计数（审计行、计量事件）依旧一处都没数。

三处点名没做，属于后面几条线：`app/components/ConsoleMetricsPanel.vue` 与 `app/pages/console/index.vue` 用 `useFetch` 取数，同样会撞上第五站那层嵌套，只是这两处目前不读 `data`，所以不算故障；`app/error.vue` 的文案表还是按状态码分的，改成按 `code` 分要连带重量一遍路由播报；`server/api/*` 里那几个演示接口（`token-demo`、`session-demo`、`email-check`）以后要撤，撤的时候这张表跟着改。

仓库这一轮的永久改动：新增 `scripts/check-error-codes.mjs`；`scripts/check.mjs` 的清单从六项 `npm run` 变成七项（整个入口从七项变八项）；`package.json` 加一条 `check:errors`；`server/services/auth/oauth.ts` 里 `OAuthFailure.code` 从 `string` 收成四个字面量的联合。**下一站起是新的功能线，动笔前要先把那条线登记进三处**（排期表、功能线明细、逐篇清单），本线的六位读者指针到这一篇闭合。
