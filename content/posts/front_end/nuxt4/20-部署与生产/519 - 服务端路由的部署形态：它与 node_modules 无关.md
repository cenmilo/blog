`server/api/*.ts` 这些文件，部署时要不要单独带上去？要不要在服务器上装它们 import 的那些包？

按官方的产物形状，答案都在"这些代码已经被打进那份可独立运行的 dist 里"这句话上。

## 它变成什么

`.output` 的定性在 Server Engine 那一节的 Standalone Server 小节：**"Nitro produces a standalone server dist that is independent of `node_modules`."**，以及 **"Nuxt generates this dist when running `nuxt build` into a `.output` directory."**

同页还有一句关于内容：这份输出包含**在任何环境跑 Nuxt 服务端的运行时代码**（官方甚至括注了实验性的浏览器 service worker），并提供静态文件；此外 Nuxt 实现了一个原生存储层，支持多来源驱动与本地资源。

服务端这一层的执行者是 Nitro。API Layer 那节的定性：**"Server API endpoints and Middleware are added by Nitro that internally uses h3."**——注意是 `server/` 目录同时提供**路由**与**中间件**两类东西，两者都由 Nitro 注册。

官方列的三条关键能力，直接决定你写处理函数的自由度：

| 能力 | 官方原文 |
| --- | --- |
| 直接返回对象/数组 | Handlers can directly return objects/arrays for an automatically-handled JSON response |
| 返回 Promise | Handlers can return promises, which will be awaited (`res.end()` and `next()` are also supported) |
| 辅助函数 | Helper functions for body parsing, cookie handling, redirects, headers and more |

## 两处限制会体现在部署结果上

**第一处：动态路由能力不完整。** `directory-structure/server` 的 Server Routes 一节末尾那条 `::note`：**"Note that currently server routes do not support the full functionality of dynamic routes as pages do."**

这句话的分量在于它没给范围——**"缺哪部分能力"文档没写**。所以别把 `pages/` 里那套动态段经验直接搬到 `server/`；用到的时候先跑一次实际请求验证匹配行为。同一节还给了 URL 规则：`~~/server/api` 下的文件自动带 `/api` 前缀，不要前缀就放 `~~/server/routes`（示例是 `server/routes/hello.ts` 对应 `http://localhost:3000/hello`）。**前缀规则在生产同样成立**——`app.baseURL` 变了它挂在 baseURL 下面，不是消失。

**第二处：类型生成的条件。** Typed API Routes 那节：**"When using API routes (or middleware), Nitro will generate typings for these routes as long as you are returning a value instead of using `res.end()` to send a response."**

这一条与上面的能力表是同一件事的两面：`res.end()` 是支持的，但**用了它就没有类型**。类型缺失不影响运行，影响的是你在客户端用 `$fetch()`／`useFetch()` 时能不能拿到自动补全和检查——也就是**上线后才发现路径写错**这类问题的拦截能力。

## 内部调用不发 HTTP，这是产物形状带来的

Direct API Calls 那节给的是运行时行为，也是部署时要理解的：

> Nitro allows 'direct' calling of routes via the globally-available `$fetch` helper. This will make an API call to the server if run on the browser, but will directly call the relevant function if run on the server, **saving an additional API call**.

也就是说同一句 `$fetch('/api/x')`：**浏览器里是真 HTTP 请求，服务端里是直接调用那个函数**。对部署的含义是两件事——服务端渲染阶段不会因为内部接口而多打一次网络；但如果你在服务器上抓访问日志看"接口被调了几次"，**这个数字不等于你代码里 `$fetch` 的调用次数**。

## 想再挂一层存储：只有两个官方入口

Server Storage 那节先给定性：**"Nitro provides a cross-platform storage layer."**，然后：**"In order to configure additional storage mount points, you can use `nitro.storage`, or server plugins."**

第一种写法（官方以 Redis 为例，配置项直接铺在 `nitro.storage` 下）：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitro: {
    storage: {
      redis: {
        driver: 'redis',
        /* redis connector options */
        port: 6379, // Redis port
        host: '127.0.0.1', // Redis host
        username: '', // needs Redis >= 6
        password: '',
        db: 0, // Defaults to 0
        tls: {}, // tls/ssl
      },
    },
  },
})
```

然后在处理函数里用挂载名取：`useStorage('redis').getKeys()`、`.setItem('foo', 'bar')`、`.removeItem('foo')`。

这里必须停下来看一处冲突：这一节把连接参数（端口、主机、账号密码）**写在 `nuxt.config.ts` 里**。而按环境变量那一节的规则，这类值在生产不该硬编码进配置——官方自己的 Redis 示例里 `username`/`password` 是空串占位，但**"这些参数怎么从环境变量取"这一节没有给写法**，只提到另一种做法是用 server plugin 加 runtime config。把凭据放进仓库是安全问题，别照示例直接填真值。

第二条入口是 server plugins，那节说明是"Nuxt 会自动读 `~~/server/plugins` 里的文件、在 Nitro 启动时执行"（详见中间件与插件那两节）。

## `nitro` 节被官方标为高级选项

上面两种写法都要往 `nitro` 里写东西，而这条警告正好冲着这个用途（`directory-structure/server` 的 Nitro Config 小节）：

> This is an advanced option. Custom config can affect production deployments, as the configuration interface might change over time when Nitro is upgraded in semver-minor versions of Nuxt.

读法：**你在 `nuxt.config` 里写的 Nitro 配置不属于 Nuxt 的公共接口保证范围**，Nuxt 的 semver-minor 升级就可能带来配置接口变化，而受影响的是生产部署。所以只写必需项，升级时把这一节单独过一遍。

最后一条属于写法自由度，也和产物有关：嵌套路由可以用 h3 自己建，官方示例是 `server/api/hello/[...slug\\].ts` 里 `createRouter()` + `router.get('/test', ...)` + `export default useBase('/api/hello', router.handler)`。这仍然是被 Nitro 注册的处理函数，不需要额外的服务器。

## 自查

- `server/` 的代码跟应用一起进 `.output`，那份 dist **独立于 `node_modules`**；这一层由 Nitro 执行、内部是 h3。
- 三条能力决定写法：可返回对象/数组、可返回 Promise（`res.end()`/`next()` 也支持）、有请求体/cookie/重定向/请求头的辅助函数。
- 两个限制会体现在部署结果上：服务端路由**不支持 pages 那样完整的动态路由**（缺什么文档没写），以及**用 `res.end()` 就不生成路由类型**。
- `$fetch` 打内部路由时：浏览器发 HTTP、服务端直接调用函数——服务端访问日志里的接口调用次数会偏少。
- 加存储挂载只有 `nitro.storage` 与 server plugins 两条；`nitro` 节被官方标为高级选项，配置接口可能随 Nuxt 的 semver-minor 变化并影响生产部署。
- 连接凭据别照 Redis 示例硬写进配置；官方在该节没给从环境变量取值的写法，另一条路是 server plugin 加 runtime config。
