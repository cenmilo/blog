`nuxt build` 跑完，你打开项目根，看到一个新目录 `.output`。想搞清里面每个文件是干什么的，于是去翻官方那一节。

那一节很短。短到它其实没有回答你的问题。

## 整页的全部记载

一句定性：**"Nuxt creates the .output/ directory when building your application for production."**

三句使用说明，原样列出来：

| 位置 | 原文 | 性质 |
| --- | --- | --- |
| `::important` | This directory should be added to your `.gitignore` file to avoid pushing the build output to your repository. | 硬性要求 |
| 正文 | Use this directory to deploy your Nuxt application to production. | 用途，并链到部署页 |
| `::warning` | You should not touch any files inside since the whole directory will be re-created when running `nuxt build`. | 禁止事项 |

一个 read-more 指向 `getting-started/deployment`，然后这一节就结束了——**没有目录树，没有文件清单，没有内部结构说明**。

`::warning` 那句的逻辑值得再读一遍：不能动里面文件的原因不是"改了就丢"，而是**整个目录会被重建**。所以任何在 `.output` 里手工改的东西，下一次构建都不存在。要改产物，改的是 `nuxt.config.ts` 和源码。

## 那两条硬提示意味着什么

`::important` 是版本控制层面的：`.output` 不进仓库。同页之外还有一处呼应——`nuxt cleanup` 那条命令的清除列表里明确列了五项：你的构建目录（默认 `.nuxt`，除非 `buildDir` 改了它）、`.output`、`dist`、`node_modules/.vite`、`node_modules/.cache`。**`.output` 在这份列表里被当成"可再生的生成物"**，这也正是它该进 `.gitignore` 的原因。

顺带一个容易混的点：`.nuxt` 与 `.output` 都是生成目录，但用途不同——前者是开发期与类型生成的工作目录，后者是**生产产物**。`nuxt cleanup` 一次清两个，说明官方把它们归在同一类。

## 目录内部：只能从别的页拼

这一节没给结构，但其他页在示例里写出过完整的 `.output` 路径。把它们列出来，就是文档目前能支撑的全部形状：

| 出现过的完整路径 | 出处与语境 |
| --- | --- |
| `.output/server/index.mjs` | 部署页的生产启动命令 `NODE_ENV=production node .output/server/index.mjs`；PM2 配置里 `script` 指向 `./.output/server/index.mjs`；preview 那一节的 `--env-file` 示例同一个文件 |
| `.output/server/index.mjs` 是 ES 模块 | ESM 概念页："we output a `.output/server/index.mjs` file. That tells Node.js to treat this file as a native ES module." |
| `.output/public/` | 预渲染页：可以把这个目录部署到任何静态托管服务，本地用 `npx serve .output/public` 预览 |
| `.output/public/index.html` | `defineRouteRules` 那一节：`nuxt build` 时首页会被预渲染进这个文件并静态服务；部署页 `ssr: false` 那段说 `nuxt generate` 会输出这个入口加 JS bundle |
| `.output/public/` 里的兜底页 | 渲染概念页：`nuxt generate` 与 `nuxt build --prerender` 把兜底页写进 `.output/public/`，**而不带 prerender 的普通 `nuxt build` 不会** |
| `_payload.json` | 预渲染页：预渲染的路由会同时产出 `_payload.json`，存进 `.output/public/`，客户端导航时被复用 |
| `.output/public` 里的静态资源 | runtime config 那一节：`NUXT_APP_CDN_URL` 用来让 `.output/public` 内的静态资源走自定义 CDN |

从这张表能安全得出的结论只有三条：**产物分 `server` 与 `public` 两块**（多处路径都落在这两个前缀下）、服务端入口是那一个 `.mjs` 文件、静态与预渲染输出全在 `public` 下。**除此之外文档没有列过其他文件或子目录**，`.output/server/` 里还有什么、chunk 怎么命名，官方在这一节和那些引用处都没写。

有一处引用不一致，值得留意：预渲染页在描述写入位置时出现过 `~/.output/public/` 这种写法（带 `~`），而其他页一律写 `.output/public/`。**这一处文档未作解释**，按别处的多数写法读更安全。

## 三种"看它到底有什么"的办法

文档没给目录清单，所以只能自己取。三个可行的取证动作：

- 跑 `npx nuxt build` 之后直接列目录（`ls -R .output | head`），把看到的与上表对照。
- 跑 `npx nuxt build --prerender`，对比同一份文件列表的变化——按渲染概念页那句，兜底页只在这种构建里出现。
- 跑 `npx nuxt preview` 看它报什么：那一节写明在某些预设下命令会**告诉你它正在跑什么**，这也是唯一一处官方让你从命令行读出"这份产物要怎么起"的地方。

上表之外的一切内部结构，都属于"文档未记载"，别在部署脚本里依赖它。

## 自查

- 这一节只有四句：构建生产版本时创建、要进 `.gitignore`、用它部署到生产、里面任何文件都别动（整个目录会被重建）。
- **它不描述目录内部**；`.output` 的两块划分是从其他页出现过的完整路径拼出来的。
- `nuxt cleanup` 把 `.output` 与 `.nuxt`、`dist`、两个 `node_modules` 缓存并列清除，官方把它当可再生成物。
- 服务端入口 `.output/server/index.mjs` 被 ESM 那一节明说是原生 ES 模块；静态与预渲染产物都在 `.output/public/`，其中兜底页只在带 prerender 的构建里出现。
- 预渲染页出现的 `~/.output/public/` 与其他页写法不一致，文档未解释。
