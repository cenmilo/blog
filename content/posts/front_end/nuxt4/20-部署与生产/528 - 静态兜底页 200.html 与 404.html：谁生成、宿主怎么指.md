静态部署后直接输入一个深层路径，浏览器给你的是"404 Not Found"——来自主机，不是你的页面。你的应用里明明写了错误页。

差的就是那两个兜底文件。

## 为什么需要两个

渲染概念页那节第一句就把动机说清：**"Static hosts need an HTML shell for client-side routes and missing paths. Nuxt emits two SPA fallbacks for that"**，然后各给一句：

| 文件 | 官方定义 | 用在什么情况 |
| --- | --- | --- |
| `200.html` | Serve this for unmatched paths when you want the client router to handle the URL. | 未匹配路径要让**你的客户端路由**去处理（比如深层路由硬刷新） |
| `404.html` | Serve this when the host should keep a 404 status and still load your app. | 要**保持 404 状态码**、同时仍然加载应用显示错误页 |

两个文件的差别不是内容，**是状态码语义**：一个承认"这是应用能处理的路径"，一个坚持"这是没找到的路径"。部署页那句补了同样的分工，措辞是"which can render dynamic routes or 404 errors on the client"，并当场提醒 **"though you may need to configure this on your static host"**。

## 谁生成、什么时候不生成

这条最容易踩，官方在渲染页写得非常具体：

> `nuxt generate` and `nuxt build --prerender` write these into `.output/public/`. A plain `nuxt build` without prerender does not. With hybrid route rules, add the fallbacks with route rules or run a prerender build if you need them. Point your host at the file your provider expects.

三档结论：

- `nuxt generate`、`nuxt build --prerender` → **两个都产出**。
- 不带 prerender 的 `nuxt build` → **不产出**。这就是"我用 build 部署到静态主机、深层路径 404"的直接原因。
- 用路由规则做混合渲染、只预渲染部分页面 → 要么给兜底页加规则，要么跑一次预渲染构建。

加规则就是部署页给的那份配置：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  routeRules: {
    '/200.html': { prerender: true },
  },
})
```

注意官方只演示了 `200.html` 这一条。**`404.html` 要不要同样补一条规则，文档没写**；从上一段那句 "add the fallbacks"（复数）看意图是两者都要有，但要确证就得看产物里有没有那个文件。

另外，客户端渲染的应用（`ssr: false`）预渲染时默认产出的是**三个**文件——`index.html`、`200.html`、`404.html`。要阻止其中任意一个生成，官方给的是 Nitro 的 `prerender:generate` 钩子：

```ts twoslash [nuxt.config.ts]
// @errors: 2353 7006
export default defineNuxtConfig({
  ssr: false,
  nitro: {
    hooks: {
      'prerender:generate' (route) {
        const routesToSkip = ['/index.html', '/200.html', '/404.html']
        if (routesToSkip.includes(route.route)) {
          route.skip = true
        }
      },
    },
  },
})
```

## 默认是空壳，这一点两处文档都写了

部署页那句：**"By default both fallbacks are empty shells."**（两个兜底默认都是空壳。）渲染页那句更具体：**"By default `404.html` is an empty shell, so your `error.vue` (and its layout and data) only appear once the client app has booted."**

也就是说：**不设东西时，兜底页里只有一个空的应用外壳**，你的错误内容要等客户端 JS 起来之后才出现——搜索引擎抓到 `404.html` 时看到的是空壳，用户也会先看到白屏再跳到错误页。

要让它带内容，官方给的开关是 `experimental.prerenderErrorPages`：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    prerenderErrorPages: true,
  },
})
```

设了之后：**Nuxt 在构建期用一个合成的 404 错误渲染 `error.vue`，把结果写进 `404.html`，并让它"在实际服务它的那个 URL 上原地水合"**。还能传 400 到 599 之间的状态码数组（示例 `[404, 500]`）多渲几页，前提是宿主能服务它们。

随之而来的限制要一起接受：**同一个文件服务所有缺失路径，所以错误页不能依赖请求。** 官方点名的三项在预渲的 HTML 里都是构建期的值——`useRoute()`、`useRequestURL()`、按当前路径取的数据，**要等水合才被纠正**。两条应对写在同一段：请求相关的标记包进 `<ClientOnly>`，请求相关的数据用 `import.meta.prerender` 跳过（官方示例是 `{ server: !import.meta.prerender }`，注释说"构建期路径是 `/404.html`，所以放到客户端去取"）。

最后一句解释了为什么这样不亏：**`import.meta.prerender` 只在页面被生成时为 `true`，所以同一份 `error.vue` 在带服务器的部署里仍然会服务端渲它的数据。**

## 宿主侧：三个平台三种认法

部署页那段末尾是操作提醒：**"Some providers use `200.html`, some use `404.html`, and some let you configure both. Check your hosting provider's static fallback or rewrite settings after deployment."**

**具体哪家认哪个，文档没有清单**——官方给的动作是"部署之后去查你平台的静态兜底或重写设置"。渲染页那句 "Point your host at the file your provider expects" 是同一个意思：**文件产出了不等于宿主在用**，两边要对上。

## 自查

- 两个兜底页的差别是状态码语义：`200.html` 让客户端路由接管，`404.html` 保持 404 同时加载应用。
- 生成条件按构建方式分：`generate` 与 `build --prerender` 会产出，**普通 `nuxt build` 不产出**；混合渲染要自己补规则（官方只演示 `/200.html`，`404.html` 是否也补文档未写）。
- 客户端渲染应用预渲染默认产出 `index.html`+两个兜底，可用 `prerender:generate` 钩子逐个跳过。
- 默认是空壳；`experimental.prerenderErrorPages` 才把 `error.vue` 渲进 `404.html`，代价是错误页不能依赖请求（靠 `<ClientOnly>` 与 `import.meta.prerender`）。
- 平台认哪个文件没有统一答案，部署后必须核对静态兜底/重写设置。
