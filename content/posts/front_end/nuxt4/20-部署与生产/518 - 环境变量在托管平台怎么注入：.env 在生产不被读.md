本地跑得好，`.env` 里那条数据库地址也确实在用。部署到云上以后接口连不上——十有八九是**生产环境根本没读那个文件**。

## 读与不读的分界线

`.env` 那页给的是时机清单：**"Nuxt CLI has built-in `.env` support via c12 in development mode and when running `nuxt build` and `nuxt generate`."**，接着 "In addition to any process environment variables, if you have a `.env` file in your project root directory, it will be automatically loaded **at dev, build and generate time**."

Runtime Config 那页把边界说成一句警告：

> The Nuxt CLI has built-in support for reading your `.env` file in development, build and generate. But when you run your built server, **your .env file will not be read**.

`.env` 那页的 Production 一节说得更直白：**"After your server is built, you are responsible for setting environment variables when you run the server."**、**"Your `.env` files will not be read at this point. How you do this is different for every environment."**

理由官方写在下一段，属于设计决定而不是 bug：**"This design decision was made to ensure compatibility across various deployment environments, some of which may not have a traditional file system available, such as serverless platforms or edge networks like Cloudflare Workers."**

同页还有一句容易忽略的："Note that removing a variable from `.env` or removing the `.env` file entirely will not unset values that have already been set."——**删掉变量不会把已经设进 `process.env` 的值撤掉**。本地调试时这会造成"我明明删了它还在"的假象。

## 生产侧被点名的三条注入做法

官方列的三种常见做法，原文照搬：

```bash
$ NODE_ENV=production DATABASE_HOST=mydatabaseconnectionstring node .output/server/index.mjs
```

- **命令行前缀**：如上，直接把变量当作启动命令的参数传。
- **shell 配置文件**：官方提到 `.bashrc` 或 `.profile`。
- **平台自己的接口**：官方举例 Vercel、Netlify、AWS 这类云服务商提供 dashboard、CLI 工具或配置文件来设环境变量。

那页末尾还有一行 `::important`：**"`runtimeConfig` won't pick up environment variables that don't start with `NUXT_` in production]"**——注意这条的方括号在文档里是配错的（写成 `]` 结尾），但意思明确：**不带 `NUXT_` 前缀的变量在生产环境不会进 `runtimeConfig`**。上面那个 `DATABASE_HOST` 只是"进程环境变量怎么传"的示例，它不等于能被 `useRuntimeConfig()` 读到。

`nuxt preview` 那页补了第四种写法，也是本地最贴近生产的一种（Node.js 20+）：

```bash
NODE_ENV=production node --env-file .env .output/server/index.mjs
```

这是用 Node 自己的 `--env-file` 把文件读进进程，不是 Nuxt 在读。

## 要让应用读得到，两个硬要求

Runtime Config 那页写的是"值会被匹配的环境变量在运行时自动替换"（**"Runtime config values are automatically replaced by matching environment variables at runtime."**），然后列出两条要求：

1. **自定义的 runtime config 变量必须先在 `nuxt.config` 里定义**。官方给的理由值得照抄："This ensures that arbitrary environment variables are not exposed to your application code."
2. **只有特定命名的变量能覆盖 runtime config 属性**：大写的、以 `NUXT_` 开头、用 `_` 分隔键与大小写变化。

配套的官方示例把映射关系摊开了：

```ini [.env]
NUXT_API_SECRET=api_secret_token
NUXT_PUBLIC_API_BASE=https://nuxtjs.org
```

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  runtimeConfig: {
    apiSecret: '', // can be overridden by NUXT_API_SECRET environment variable
    public: {
      apiBase: '', // can be overridden by NUXT_PUBLIC_API_BASE environment variable
    },
  },
})
```

对应关系是 `apiSecret` ⇔ `NUXT_API_SECRET`、`public.apiBase` ⇔ `NUXT_PUBLIC_API_BASE`——**嵌套靠 `NUXT_PUBLIC_` 这一段表达**。

一条同页警告能解释一整类"本地正常、线上读到空值"：**把默认值写成不同名的环境变量只在构建期有效，运行时会坏**（原文："Setting the default of `runtimeConfig` values to *differently named environment variables* (for example setting `myVar` to `process.env.OTHER_VARIABLE`) will only work during build-time and will break on runtime."），官方建议直接用与 `runtimeConfig` 结构相匹配的变量名。

## 值会被自动转型，这一条要记

那页的 `::warning` 给了一个具体到数字的例子：

> Environment variable values are automatically cast to their JavaScript type using destr. For example, `NUXT_MY_VAR=4848e0` becomes the number `4848`. To keep a value a string, the environment variable value itself must contain literal double quotes: in a `.env` file, write `NUXT_MY_VAR='"4848e0"'`; when setting the variable directly (in a shell, Dockerfile, or hosting dashboard), make sure the quotes are part of the value and not stripped by the shell (for example `NUXT_MY_VAR='"4848e0"' node .output/server/index.mjs`).

三件事：**转型由 destr 做**、`4848e0` 这种值会被吃成数字 `4848`（这在密钥、ID、版本号上是静默错值）、保字符串的办法是让**引号成为值本身的一部分** `'"..."'`，而且官方特别提醒在 shell、Dockerfile、平台面板里设的时候要确认引号没被剥掉——**这三处的剥引号规则不一样，所以平台面板里设的值要和 `.env` 里的写法分别验**。

## 一处可选替代：appConfig

`.env` 页末尾那条提示给的是另一种需求的答案：如果你要的是"构建期设进去、之后不需要再改（或只需要在应用内部响应式地改）"，`appConfig` 可能是更好的选择——它既能在 `nuxt.config` 里定义（用环境变量取值），也能写在项目的 `~/app.config.ts` 里。

这条正好对应官方那句"某些环境没有传统文件系统"：构建期固化进产物的东西，不依赖运行时读文件。顺带记一处文档瑕疵：这条提示块里那个 `read-more` 被写成了 `:read-more{...}`（少一个冒号），所以在渲染出来的页面上它可能不成链接——这是文档自身的排版问题，不是你的配置错了。

## 自查

- `.env` 只在 dev／build／generate 三个时机被 CLI 读；**跑构建好的服务器时不读**，设计理由是要兼容没有传统文件系统的平台。
- 删掉 `.env` 里的变量不会撤掉已设进 `process.env` 的值。
- 生产注入的三条官方做法：命令行前缀、`.bashrc`/`.profile`、平台 dashboard/CLI/配置文件；本地预览推荐 `nuxt preview`，或用 Node 的 `--env-file`。
- 想让 `useRuntimeConfig()` 读到，必须先在配置里定义、且变量名大写以 `NUXT_` 开头（嵌套用 `NUXT_PUBLIC_`），不带 `NUXT_` 前缀的在生产进不了 `runtimeConfig`。
- 值会被 destr 自动转型（`4848e0` → 数字 `4848`），要保持字符串得把双引号写进值里，并注意 shell/Dockerfile/面板会不会剥掉引号。
- 构建后不需要再变的值可以考虑 `appConfig`，而不是环境变量。
