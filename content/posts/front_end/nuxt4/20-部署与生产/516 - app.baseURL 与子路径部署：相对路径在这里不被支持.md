站点要放到 `https://example.com/docs/` 下面。改完代码里的路径、又试着把 `baseURL` 写成 `'./'`，构建直接不对——这一篇讲这个值能怎么写、不能怎么写。

## 默认值与它的写法

`api/nuxt-config` 对 `app.baseURL` 的记载：**"The base path of your Nuxt application."**

- **类型**：`string`
- **默认**：`"/"`

官方示例：

```ts
export default defineNuxtConfig({
  app: {
    baseURL: '/prefix/',
  },
})
```

注意示例里两侧都有斜杠：`/prefix/`。文档没有解释少写一侧斜杠会怎样，**"必须带尾斜杠"这类规则官方没有写出来**，要确认就照抄示例形状，然后看产物里资源引用是否变成 `/prefix/_nuxt/...`。

同节还给了第二个写入时机：**"This can also be set at runtime by setting the NUXT_APP_BASE_URL environment variable."**，示例：

```bash
NUXT_APP_BASE_URL=/prefix/ node .output/server/index.mjs
```

这一点很实用：同一份构建可以用不同的 `baseURL` 启动，不用重新构建。但要看清适用面——**这是"运行时启动时注入"**，只对跑得起来的服务端有意义；纯静态站点没有启动这一步，而且 `.env` 那一节明确写了「纯静态站点在预渲染之后无法再设运行时配置」。

## 相对路径被挡住，官方给了两种替代

那条 `::note` 是这个键最容易撞的限制，原文：

> Relative paths (like `./`) are not supported directly in `nuxt.config.ts` due to Nitro limitations. For static hosting with relative asset paths, use one of these approaches:

然后是两个方案，官方原样给代码：

```bash
# Option 1: Environment variable at build time
NUXT_APP_BASE_URL=./ npm run generate
```

```ts
// Option 2: Runtime config
export default defineNuxtConfig({
  runtimeConfig: {
    app: {
      baseURL: './',
    },
  },
})
```

差别不是"两种等价写法"，而是**位置**：第一种在构建时用环境变量注入（所以它发生在配置被解析之前），第二种把值放进 `runtimeConfig.app` 而不是 `app` 节。方案二的适用面文档限定得很清楚——它出现在"要给静态托管用相对资源路径"这句话之下。

顺带一个细节：方案一写的是 `npm run generate`，也就是通过你 `package.json` 里的脚本跑，不是 `npx nuxt generate`。这条差异官方没有解释，能确证的只有那句 `NUXT_APP_BASE_URL=./` 是**在构建时**生效。

## 资源目录挂在它下面

`app.baseURL` 不只影响路由，还决定另一项的位置。`app.buildAssetsDir` 的定义是：**"The folder name for the built site assets, relative to `baseURL` (or `cdnURL` if set). This is set at build time and should not be customized at runtime."**

这句话里有三个约束：**它是相对 `baseURL` 算的**（`baseURL` 一变，资源前缀跟着变）、**如果设了 `cdnURL` 就改成相对 `cdnURL`**、**它在构建期固定，不该在运行时定制**。默认值是 `"/_nuxt/"`。

也就是说，子路径部署下你通常只需要动 `baseURL` 一个值——资源路径会自动跟上。想同时把资源挪到 CDN 上，才需要 `cdnURL` 参与，那是另一篇的内容。

## 与"多个公开路径共用一份构建"不是一回事

部署页的 Serving the Same Build at Multiple Paths 小节开头一句正好把两者分开：**"For a normal subpath deployment, set `app.baseURL` or the `NUXT_APP_BASE_URL` environment variable."**

也就是说：`baseURL` 管**正常的一条子路径**。紧接着它讲的是另一种情况——反向代理**故意**把同一个渲染结果暴露在多个公开路径下，这时"Nuxt 可能在水合时用服务端渲染所依据的那个路径替换掉浏览器地址"，官方给的保留办法是在服务端插件里把渲染路径从 payload 中删掉。那条属于"多路径"这个专题，我在讲这个场景的那篇逐行拆开，包括官方对它的警告：**只有在代理已经为每个公开路径处理好资源与路由时才这么用**，删掉之后 Nuxt 就没法纠正请求地址与渲出路由之间真实的错配。

## 自查

- `app.baseURL` 是 `string`、默认 `"/"`，官方示例形状是带前后斜杠的 `'/prefix/'`。
- 可以延后到启动时注入：`NUXT_APP_BASE_URL=/prefix/ node .output/server/index.mjs`；纯静态站点没有这一步，预渲染后无法再设。
- **相对路径 `./` 不能直接写进 `nuxt.config.ts`**（Nitro 的限制），替代是构建期环境变量 `NUXT_APP_BASE_URL=./` 或写在 `runtimeConfig.app.baseURL`。
- `buildAssetsDir` 默认 `/_nuxt/`，相对 `baseURL`（设了 `cdnURL` 就相对它），并且官方说它构建期设定、不该运行时定制。
- 「子路径部署」与「同一份构建暴露在多个公开路径」是两件事，后者的做法与警告归多路径那篇。
