会员区那一页上有两栏字，一栏写着订阅的状态"生效中"，另一栏写着角色 `free`。这不是坏了：从这条链上线那天起，这个角色栏对每一个付费的人都在念 `free`。

这一站要接的就是那句"到期降级"。上一站已经判清楚它一个字都没做，所以这一站先不动手——把两件事量成读数："任务"这一层在这个仓库里能站在哪儿，以及"降级"要改的那一列现在谁在读、谁在写。

## 先量那一列：有读者，没有写者

```
[任务层·角色] {"读role的文件":["app/pages/console/index.vue","app/pages/me.vue",
              "server/services/auth/session.ts","server/utils/auth/require-admin.ts"],
              "按admin判":1,"按member判":0,"写users表的语句":0,
              "创建用户的文件":["server/services/auth/verify.ts"],"那一条的values里带role":false}
```

四份文件读它，但读法分两类：`require-admin.ts` 里那一句是 `user.role !== 'admin'`，管的是后台那道门；两个页面上只是把那一位打在屏幕上。**按 `member` 判权限的地方是 0 处**——会员能不能用，今天完全由订阅那一行决定（845 那条占位门就是它）。

写它的那一侧更干净：全站唯一创建用户的那条语句是 `verify.ts` 里的 `.insert(users).values({ email })`，`role` 不在括号里，于是每个人出生就拿列上的默认值 `free`；再把整条服务层扫一遍，`UPDATE users` 出现 0 次。

⚠ 这两句合起来是这一站最该记住的读数：**应用里没有任何路径能把一个人变成 `member`**。所以"到期把他降回 `free`"这个动作，今天要降的是一个谁都没有的标签。缺的从来不只是那个定时器。

## 任务这一层：五个目录、零处注册、零个自己醒来的东西

```
[任务层·目录] {"顶层目录":["api","middleware","routes","services","utils"],"defineTask处数":0,"task函数处数":0}
[任务层·配置] {"nitro那几行":["nitro: { prerender: { crawlLinks: true, routes: ['/'] } },"],"带tasks开关":false,"有experimental节":false}
[任务层·自发] {"setInterval的文件":[],"cron的文件":[],"scheduler的文件":[]}
```

`server/` 下面只有那五个目录，**没有 `tasks/`**；`defineTask` 全仓 0 处；配置文件里 `nitro` 只出现一行，那一行里没有任务开关。官方那一节写得直白：只有把 `nitro.experimental.tasks` 打开，Nitro 才去扫你的 `tasks` 目录——本站连"扫不扫"这一层都没开始谈。

还要补一句容易被跳过的：本站也没有任何会自己醒来的东西。`setInterval`、`cron`、`scheduler` 在应用层与服务层正文里都是 0 处。上一站量过的那件事在这里再确认一次——"到期"只在有人来问的时候被算一次，来问的只有两条路：一条事件进来、一次页面被打开。

`nuxt task list` 这件事本身要有个跑起来的服务器才能问。这一档本轮没跑到：起开发服务被本机权限策略判为"要用户确认的常驻服务"，没有起。要自己看的话是这两条：

```bash
cd Substrate && npx nuxt dev --port 3753        # 另开一个终端
npx nuxt task list --url http://localhost:3753  # 现在应当报"没有可用任务"
```

## 那"该被降的人"到底长什么样

只读问一遍问不出来，因为库里今天没有一个真人是 `member`。所以这一档自己造一个：`role='member'`，只有一行订阅、状态 `active`、周期末在一小时前。三个读数同框：

```
[任务范围·已过的人] {"库里的角色":"member",
  "那一栏":{"status":"active","currentPeriodEnd":1792539565741,"periodState":"已过"},
  "结账":{"状态":503,"码":"CHECKOUT_NOT_CONFIGURED"},"在候选名单里":true}
[任务范围·还在期内的人] {"库里的角色":"member",
  "那一栏":{"status":"active","periodState":"未到"},
  "结账":{"状态":409,"码":"CHECKOUT_ALREADY_ACTIVE"},"在候选名单里":false}
```

**这个人就是任务该处理的对象**：标签还说他是会员，库里已经没有任何一行占位，而没有任何东西会去动他。第二行是对照——同一种人、一样的标签，一个占位一个不占位，读出来的结账码正好相反（409 与 503）。

候选名单这一档顺手补了上一站入池的那条账（"残留没有按编号前缀数过"）。它不问全表有多少人，只问**这一次自建的那位在不在名单里**：

```
[任务范围·名单自证] {"之前有他":false,"之中有他":true,"之后有他":false,"之前长度":0,"之中长度":1,"之后长度":0}
```

`之前长度: 0` 那一位就是上面那句话的实证：本机库里今天没有第二个这样的人。

## 落点：先决定谁把他升上去，再谈把他降下来

"降级"改 `role`，前提是这一列表达"这个人是会员"。摆在三条路里：

| 写法 | 谁写这一列 | 代价 |
| --- | --- | --- |
| 入账时升、任务降 | 两个写入者 | 订阅那一行与 `role` 各被一方写，谁落后都不知道——两句话互相吞的老症状 |
| 这一列不再表达会员 | 没人写 | 与需求文档那句"降回 `free`"对不上，屏幕上那一栏永远念 `free` |
| **这一列由那一行投影，升与降都归任务** | 一个写入者 | `role` 会有延迟（两次运行之间不一致），但延迟是看得见的，权限不受影响 |

这一线走第三条。理由就是上面那两条读数：**今天没有任何一处按 `member` 判权限**，所以让 `role` 做一个落后的投影不会改变任何人能做的事；而它一旦被两个写入者分别改，就成了"一半对一半永远不动"那种排查不出的东西。投影也解释了屏幕上那两栏为什么会不一致——844 那一站已经立过同一条规矩：**两句话各处说一句，不许折中成一句**。

于是 851 要写的不是"降"，而是**同一个执行者负责升与降**；而它取"此刻"这件事，会变成这个仓库里第一次有人替到期判断主动读时钟。这条线接下来每一站的判据都要围绕这个新增读者写。

## 判据先把自己的两处毛病照出来了

新写的静态档五档，第一次跑就撞出两处判据的错，不是代码的错：

- **只认一种写法就会假红。** 把 `read.ts` 里的 `Date.now()` 换成 `new Date().getTime()`（取值一个字都没变），名单少了一个名字。这不是发现，是判据漏读——842 那一档用的是三种写法并起来的式子，所以它一点没红。同一件事在两档里的覆盖面不同，这一站把"取此刻"的式子也写成两种。
- **名单铺到全仓就变成噪声。** 用宽式子扫整个 `server/`，捞回来 15 份文件——审计、日志、发信都要给自己盖时间戳，那不是"有人在替到期判断取一次现在"。于是这一档改成只问 billing 那一路：

```
[任务层·取此刻] {"billing文件总数":10,"取此刻的名单":["server/api/billing/checkout.post.ts",
  "server/api/billing/webhook.post.ts","server/services/billing/ingest.ts",
  "server/services/billing/read.ts","server/services/billing/signature.ts"],"其中在tasks目录的":[]}
```

改完再拿真变异验一次：在 `entitlement.ts`（那个不许碰库的纯函数）里加一句取此刻，名单立刻多出一个名字，`①` 那边塞一个 `tasks:` 字面量也跟着红。两处都还原后五档全绿。

## 你自己跑一遍

```bash
cd Substrate
npm run test:unit -- task-layer-baseline        # 五档，离线可跑
NUXT_E2E_DB=1 E2E_PORT=3750 npx playwright test test/e2e/task-scope-baseline.spec.ts
```

| 撞上的现象 | 原因与读法 |
| --- | --- |
| 三条端到端全 skip | 没给 `NUXT_E2E_DB=1`，库串是空串；这一档第一条 skip 条件就是它 |
| `①②` 读到 409 而不是预期那个码 | 本站配了渠道密钥，或者占位那一门的口径变了——先读 `[任务层·取此刻]` 的名单有没有多出一个名字 |
| `④` 的"写 users 表的语句"不再是 0 | 有人开始写这一列了。**这一站的前提作废**，落点那张表要重判：现在有两个写入者 |
| `⑤` 少了一个名字但你没改任何逻辑 | 大概率是判据只认一种写法。先看式子，再怀疑代码 |
| 库里找不到一个 `member` | 正常。今天没有任何路径写这一列，`③` 那句 `之前长度: 0` 就是这件事的读数 |

## 收了哪一格，还欠哪一格

这一站没有新增实现，收口的是一句更硬的话：**"到期降级"缺的不是一个定时器，是一整层还没有归属的状态**。角色这一列有读者没有写者，任务这一层连目录都没建，而这两件事合起来决定了后面五站要怎么写——先有唯一的执行者，再谈它什么时候醒。

下一站（849）开始动手：建 `server/tasks/`、写第一个 `defineTask`，并且把开关打开前后各读一次——那两个读数必须不一样，否则这一层是假的。

## 本文依据

- `docs/4.x/api/commands/task`——`nuxt task list` 与 `nuxt task run <名字> --payload` 都是对着一个跑起来的服务器说话；那一节的提示块原话写着：任务开关没打开时，Nitro 不会扫你的 `tasks` 目录。
- `docs/4.x/directory-structure/server`——`server/` 下被自动扫描的目录有哪几类，`utils` 与 `services` 属本地约定。这一站读到的顶层就是那五个名字，`tasks` 不在其中，框架也不会因为少这一个目录报任何东西。
- `docs/4.x/guide/concepts/error-handling`——这一站的对照读数仍然复用那一份错误形状：结账被占位门挡下回的是 `data.code` 为 `CHECKOUT_ALREADY_ACTIVE` 的 409，放行才轮到"没配置"那个 503。
