上一站那句回话是"选取规则在这份文件里，取数与落点写入还没开"。这一站开完了，屏幕上第一次看得见区别：会员区顶上那一栏原来写着 `member`，跑完之后它念 `free`。全站第一条改 `users` 这张表的语句也在这里——在此之前，那一列有四个读者、零个写者。

## 落点分三层，每层只回答一个问题

| 文件 | 只回答 | 这一层不许 |
| --- | --- | --- |
| `server/tasks/refresh-roles.ts` | 什么时候跑、跑完报什么数 | 出现任何 SQL；读第二次钟 |
| `server/services/billing/refresh.ts` | 名单从哪来、谁真的被改了、痕迹留下没有 | 自己读钟（时刻由调用方给） |
| `server/services/billing/downgrade.ts` | 这个人该不该降（上一站的那份选取） | 碰库 |

分这么细的理由很实在：**SQL 写进任务文件，红的时候分不清是"任务这一层没接上"还是"选错了人"**。判据也按这三层各钉各的——离线那一档喂一个假连接，只读它发出了哪些语句、按什么顺序发。

名单这一头只问一种人：

```ts
const 候选 = await db.select({ id: users.id }).from(users)
  .where(eq(users.role, 'member'))
```

上一站把"`admin` 不进名单"写在文件头里。写在头里不算成立——**只有 SQL 才让它成立**，所以这条现在是判据里逐字钉着的一句（`select "id" from "users" where "users"."role" = $1`，参数 `['member']`）。

## 带条件写，再读回真改了几行

```
update "users" set "role" = $1 where ("users"."id" in ($2, $3) and "users"."role" = $4) returning "id"
参数：["free","u1","u2","member"]
```

两个条件各挡一种事故。`id in (…)` 是名单；后面那个 `role = 'member'` 挡的是**这趟读到他是 member、写的那一刻已经不是了**（同一时刻里有人被升上去、被改成别的）。少了它就等于把"读到时的样子"当成"现在还是那样"。

`returning` 那一半更值钱：**处理行数不许自称**。判据里有一档专门造这个形状——判成该降的两个人，库里只动了一个：

```
[落点·只动一个] {"该降":["u1","u2"],"降了":["u1"],"没改动":["u2"],"审计目标":["u1"],"审计行数":1}
```

`没改动` 那位不是漏掉了，是他不该被算成"降过"。这也顺手把幂等钉住了：同一个人第二次跑，`候选人数: 0`——他上一趟已经被自己改成 `free`，早不在名单里。

## 痕迹这一头有两个坑

**第一个：任务里没有 event。** 站里已有的 `writeAudit(event, 输入)` 从 event 上取两位：`requestId` 和 `databaseUrl`，还要靠它打那行日志。任务这一趟没有 event，于是新开一个入口 `writeSystemAudit(输入)`，走同一张表、同一个写入文件。它少了一行日志，只留表里那一行——这个取舍写在文件头，也记进了还欠的账。

更要紧的是 `actor` 那一格。表上它是个可空外键，而 `null` **已经有含义**："这个账号已经不在了"（站里就有一条端到端判据钉着这件事）。系统触发的降级也只能填 `null`，两种 `null` 在列上长得一模一样。所以新入口把"谁触发的"做成**必填**：

```ts
export interface SystemAuditInput {
  action: string
  target: string
  count: number
  /** 谁触发的这一趟。`actor` 那一格的 null 已被"账号不在了"占了，不填这一位就分不开 */
  trigger: string
  meta?: Record<string, string | number | boolean>
}
```

真库里读回来的那一行是这样：

```
审计行 {"actor":null,"action":"role_downgraded","target":"68055e50-…","count":"1",
"request_id":null,"meta":{"reason":"没有一行还占位","trigger":"task:subscription:refresh-roles"}}
```

`meta.reason` 那一位不是装饰：判据把它和选取的结论对上，事后才问得出"为什么降的他"。一人一条而不是整批一条，也是同一张表自己定的形状——它的注释写着"一行 = 一次改了谁的什么"，`target` 存被操作那个人的 id；顺带让判据能按 `target` 精确数到自己那一行，不必去数全表。

**第二个：降级与留痕不做成一个事务。** 表里那一行已经改完，审计写失败了，怎么办？沿用站里已有的方向：撤销权限这一族（登出、全端下线同类）不该因为审计写不进去而把人卡在原地。代价照实付——少一行痕迹，所以返回值里 `审计失败` 单独报数，而不是被一句 `catch` 吞掉。判据造的就是这个形状：假连接让那条 INSERT 抛错，读回来 `顺序: ['SELECT','SELECT','UPDATE','INSERT']`、`降了: ['u1']`、`审计失败: 1`。

## 测试自己喂错了行的形状

离线那一档要给假连接喂几行数据。第一版按直觉写对象：

```ts
return { rows: [{ id: 'u1' }] }
```

结果全档读不到人：`候选人数: 2` 却 `该降: []`，判据说"没人该降"。看起来像产品写错了，实际是 **drizzle 的 node-postgres 会话在每条查询上写死了 `rowMode: 'array'`**（`node_modules/drizzle-orm/node-postgres/session.js:61`），真库回来的行也是**按列顺序排的数组**，映射按位置做。给对象就得改成给数组：

```ts
// 列顺序 = select { id }；订阅行那一趟 = select { 用户id, id, status, currentPeriodEnd }
const 候选人 = (id: string): unknown[] => [id]
const 订阅行 = (用户id: string, id: string, status: string, 周期末: Date | null): unknown[] => [用户id, id, status, 周期末]
```

改完这一档七条一次过（`Tests 7 passed (7)`）。这件事值得单独一节：报错的方向是反的。假连接不会告诉你"形状不对"，只会让结论变成"没人该降"，而那句听起来像个合理的业务结论。

## 把服务端代码引进测试，类型检查会红一片

端到端那一档想跑**同一份服务代码**（而不是在测试里重抄一遍 SQL），于是照常见写法 import。`nuxt typecheck` 立刻掉出六行：

```
server/services/audit.ts(41,11): error TS2304: Cannot find name 'useDb'.
server/services/billing/refresh.ts(78,49): error TS7006: Parameter '这一位' implicitly has an 'any' type.
```

原因不在代码：端到端档属于 `node` 那份 tsconfig 项目，而 `useDb()`、`useRuntimeConfig()` 是 Nitro 的自动导入，声明只写在 `.nuxt/types/nitro-imports.d.ts` 里，那份项目看不见它。`TS7006` 那两条是同一条错误的下游——`useDb()` 认不出来，回调参数自然推不出类型。

先试的是改成动态 import（站里另一档读服务层就是这么写的），不解决问题：类型检查照样顺着模块图把服务端文件拉进来。真正补上的是配置那一处：

```ts
nodeTsConfig: {
  include: ['../*.ts', '../db/**/*', '../test/e2e/**/*.ts', '../scripts/**/*.ts', '../.nuxt/types/nitro-imports.d.ts'],
}
```

这一处按两个方向都验过：不加那一项就是上面那六行，加上就干净（`rc=0`）。给服务端代码补显式 import 也能过，但那是要让产品迁就测试的形状。

## 真库上的四档

跑法（要连库，没库那趟四档全 skip）：

```bash
NUXT_E2E_DB=1 E2E_PORT=4100 npm run test:e2e -- test/e2e/role-refresh-db.spec.ts
```

批量写跑在共享的开发库上，第一件事是**自证前提**：这条 SQL 问的是全库所有 `member`，所以跑之前先读一次名单。除了本次探针造的这几位还有别人的账号挂着 `member`，这一档就让路，并把多出来的 id 一起打出来——硬跑会降别人的测试账号，悄悄跳过又会让读数看着像测过了。整套件并行那一趟里，造 `member` 探针的那份文件正好在场，所以这四处记成 skip；**要读的数取单跑那一趟**：

```
[降级·真库] {"结果":{"候选人数":1,"该降":["68055e50-…"],"降了":["68055e50-…"],"没改动":[],"没降":[],
"审计行数":1,"审计失败":0},"库里":{"role":"free"},"页面":{"跑前":"member","跑后":"free"}}
[降级·不动] {"该降":["68286a34-…"],"两人":[{"role":"free"},{"role":"member"}],"乙的审计行数":0,"页面乙":"member"}
[降级·判不出] {"结果":{"候选人数":1,"该降":[],"降了":[],"没降":[{"判定":"判不出","依据":"周期末读不出"}],
"审计行数":0},"库里":{"role":"member"}}
[降级·跑两趟] {"第一次":{"降了":["4e97da5a-…"],"审计行数":1},"第二次":{"候选人数":0,"降了":[],"审计行数":0},"审计行数":1}
```

四条各自说清一件事：降了的人库与页面同时改口；还在期内的不动、也不留痕；读不出时刻的不动（上一站那条口径第一次落到真数据上）；跑第二次不多降人、不多留痕。

## 变异：每一档都要能被它守的那种坏形状打红

离线那一档先五处一起下手（去掉 `and role = 'member'`、把候选名单当"降了"而不读 `returning`、第二趟加 `.limit(1)`、空名单也去问第二趟、`判降级` 调两次），红的是 ①②③④⑦ 五档，⑤⑥ 没红——它们守的是别的东西。真库那一档另起一次，把降成的值写成 `admin`，端到端①当场报 `库里 role='admin'`、`页面 跑后 'admin'`，其余三档不红。

| 改坏的那一处 | 红的那一档 | 为什么只有它 |
| --- | --- | --- |
| 用候选名单当"降了"（不读 `returning`） | ③ 与 ④ | 只有这两条比"读回来的是谁"；其余档看的是 SQL 文本 |
| 去掉 `and users.role = 'member'` | 只有 ③ | 它逐字钉那条语句；库里此刻没别人，行为一样 |
| 第二趟加 `.limit(1)` | 只有 ② | ②钉"没有 limit 也没有排序"，而函数拿到的数组不受影响 |
| 空名单也去问第二趟 | 只有 ① | ①数语句条数；后面几档本来就有人 |
| 审计不带 `trigger` | 只有 ⑤ | 别的档不看 `meta` |
| `actor` 从 null 写成 `'system'` | ⑤ | 它数 params 里两个 null；库里那条外键要真写才报，测试进程看不出来 |
| 吞掉审计失败数（`catch` 里不计数） | 只有 ⑥ | ⑥是唯一让 INSERT 抛错的一档 |
| 在另一份文件里也写审计表 | 只有 ⑦ | ⑦扫的是"哪些文件出现这个写入"，不是数某一份文件里的次数 |

最后一行是这一站新加的尺。它第一版只数 `audit.ts` 自己那份内容——那样的话，别的文件里新开一个写入点，它一辈子看不见。改成扫整个 `server/` 目录、把命中的**文件名**列出来，这一改同一批变异才撞得红（读回到两份文件才算数）。

## 收了哪一格，还欠哪一格

还掉的是 spec 那句里的"改 `users` 那一列"与"有日志"两格：全站第一条 `UPDATE` 在那儿，审计行按人落下、带着能读的理由。

**仍欠两格，别混着说**。这一档的"真跑"是测试进程调服务层跑出来的——SQL、库里的值、页面上的字都是真的，但**执行它的不是任务调度器**：`nuxt task run subscription:refresh-roles` 那条入口一次都没真跑过，因为起服务要一次授权。所以"任务被扫到了没有"这一格从 849 一直空到现在，853 收口时要单独点名。另一格是提醒邮件与排期（cron 每日那一半），那是 852 和后面要说的事。

下一站（852）动的是那句"发提醒邮件"：降完的人要收到一封信，而信发不出去的时候，不许把已经降下来的 `role` 撤回。

## 你自己跑一遍

```bash
cd Substrate
npm run test:unit -- role-refresh              # 7 档，离线（假连接记语句）
npm run check                                  # 八项，含类型检查
```

| 撞上的现象 | 原因与读法 |
| --- | --- |
| 离线档读回来"没人该降"，可库里的样子明明对 | 假连接的行给了对象而不是数组：drizzle 让 pg 按 `rowMode:'array'` 回行，映射按位置做 |
| 一 import 服务端文件，类型检查就报 `Cannot find name 'useDb'` | 那份 tsconfig 项目里没有 Nitro 的自动导入声明。补 `nodeTsConfig.include` 那一项，别改服务端代码 |
| `候选人数` 一直是 0，而你确认库里有 member | 看第一趟那条 SQL 的参数——多半是名单条件被改宽或改窄了 |
| 第二次跑又落了一条审计行 | 留痕按人算，第二趟的 `降了` 应该空；如果它不空，那条 `and role = 'member'` 没生效 |
| 端到端四档全 skip | 没给 `NUXT_E2E_DB=1`，那条命令里的连接串没载入 |

## 本文依据

- `docs/4.x/api/commands/task`——`nuxt task run <名字> --payload` 的形状。这一站的名单与痕迹就是为那个入口准备的，而入口本身仍未真跑过（需要一次起服务的授权）。
- `docs/4.x/directory-structure/server`——`server/` 各目录的分工：`services/` 是内部函数、不会成为路由，SQL 因此放在这一层而不是任务文件里。
- `docs/4.x/api/nuxt-config`——`typescript.tsConfig`／`nodeTsConfig` 的 `include`：那一条说明 include 只作用于生成的那一份 tsconfig 项目，这正是补上自动导入声明能修好类型检查的原因。
