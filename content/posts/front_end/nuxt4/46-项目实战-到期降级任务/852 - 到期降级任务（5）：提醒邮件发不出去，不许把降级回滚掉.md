上一站跑完，屏幕上能看见两样东西：会员区顶上那一栏从 `member` 念成 `free`，审计表里多了一行 `role_downgraded`。第三样东西没有——**他本人不知道自己被降了**。第二天他打开会员区，看见一处原本能点现在点不动的地方，只会来问一句"我是不是坏了"。这一站补的就是那一封信，以及一句方向：信发不出去的时候，不许把已经降下来的那一列改回去。

## 信放在哪儿，为什么和登录那封共用一份

发信这一层站里已经有了：`server/services/auth/mailer.ts`，登录链接从它那里出去。新加的那封放在同一个文件里，共用同一个 transport。这不是省事——**transport 上挂着三个时间上限**（打招呼 3 秒、建连 5 秒、静默 15 秒），另建一份就等于把这套上限重写一遍，两处还会各自漂。

配置走 runtime config 的私有键，三个都得有：`NUXT_SMTP_URL`、`NUXT_MAIL_FROM`，以及正文里那条回会员区的地址用的 `NUXT_PUBLIC_SITE_URL`。少任何一个，这一趟不发信，但降级照做。

新的出口长这样，注意它对失败的处理**和登录那一封刻意相反**：

```ts
export async function sendDowngradeNotice (params: { to: string }): Promise<NoticeResult> {
  const config = useRuntimeConfig()
  const smtpUrl = config.smtpUrl as string | undefined
  const mailFrom = config.mailFrom as string | undefined
  const siteUrl = (config.public as { siteUrl?: string }).siteUrl ?? ''

  if (!smtpUrl || !mailFrom || siteUrl === '') return { sent: false, reason: 'not_configured' }

  try {
    const info = await getTransport(smtpUrl).sendMail({ from: mailFrom, to: params.to, ...downgradeEmail({ siteUrl }) })
    return { sent: true, messageId: info.messageId }
  } catch (error) {
    return { sent: false, reason: 'transport_failed', 原因: (error as Error).message.slice(0, 200) }
  }
}
```

登录那封连不上时是**照原样抛出去**的——发不出去就把刚生成的券撤掉，人在等，看得见比什么都重要。这一封由任务发，抛出去会让整趟降级崩在半路：已经改完的人留在库里，还没轮到的人一个没动。所以它自己 `catch`，把失败收成一个返回值。两处都写了判据：按函数体切成两段各问一次，全文找一个 `catch` 会一边假绿一边假红。

## 三种"没发出去"，各有各的数

`刷新结果` 里多了两个数：`发信成功` 与 `发信失败`。判据要求它们相加等于真被改动的人数——**"他被降了而没人告诉他"这件事必须落在一个数上**，否则跑完谁都不知道要去补配置。

三种失败形状，离线那一档各造了一条：

| 形状 | 怎么造 | 读数 |
| --- | --- | --- |
| 没配 SMTP | 三个键传空串 | `发信失败: 1`、`封数: 0`、`降了: ['u1']` |
| 配了但连不上 | `smtp://127.0.0.1:1` | 同上，而且这一趟没崩 |
| 名单里读不到邮箱 | 候选那一行的邮箱位给空串 | `发信成功: 0`、`发信失败: 1`、`封数: 0` |

第三种最容易写成"跳过他"。真写成跳过，那一趟的读数是 `发信失败: 0`——**一个都没失败，也一个都没发出去**。这一格是新加的：判据先只写了前两种，第三种补上之后，"读不到邮箱就当没事"这个变异才当场撞红。

## 信只跟着"真被改动的人"走

发信的循环遍历的是 `降了`（`returning` 读回来的那几位），不是 `该降`。差别在一种形状上：判成该降的两个人，库里只动了一个。给那个没被动过的人发一封"你的会员期已经结束"，信与库里的事实就开始各说各的。

这一条**第一版测不出来**。那条判据原本造的第二人是"还在期内"，于是他压根不在 `该降` 里，`降了` 和 `该降` 两个名单一模一样——把循环改成遍历 `该降`，一条判据都不红。补法是让第二人也判成该降（他那一行不占位），而 `returning` 只回一人，再加第三人还在期内：

```
[通知·只发真降的] {"该降":["u1","u2"],"降了":["u1"],"没降":[{"用户id":"u3","判定":"还在期内","依据":"还占着位"}],
"收件人":["one@example.com"],"成功":1,"失败":0}
```

同一趟里第二个 SELECT 只发一次、第二次跑 `封数: 0`，钉的是"每日跑一次不会给同一个人反复寄"。

## 一封信两段，两段都得带入口

正文有 `text` 与 `html` 两份。判据不查"有没有正文"，而是按段读：

```
[通知·发出] {"封数":1,"收件人":"reader@example.com","主题":"会员期已经结束","正文含地址":true,
"正文两段":["text/plain","text/html"],"每段编码":["base64","base64"],"html含链接":true}
```

`每段编码` 那一位是本轮踩出来的。站里那台本地替身（`scripts/smtp-sink.mjs`，766 那一站立的）第一版只解 quoted-printable，因为登录那封信就是那个编码；通知这封信寄到替身手里时两段都是 base64，于是"正文含地址"读回来是 `false`——**看着像信写坏了，其实是收件端没解开**。补上按 `Content-Transfer-Encoding` 分派之后，同一份替身两种编码都读得出。换个邮箱客户端只渲染其中一段，另一段漏了链接就是"他收到信却点不动"。

主题与正文里没有任何凭据，审计那一行也只有 id：

```
[通知·审计不含邮箱] {"参数":["null","role_downgraded","u1","1","{\"reason\":\"没有一行还占位\",…}","null"],"有邮箱":false}
```

`meta` 里不许出现 `@`——表上的原则是"存 id 不存邮箱，邮箱是可变的身份信息"。这一档顺手带一条反假绿的对照：同一趟 `发信成功: 1`，证明邮箱确实被用过了，不是"压根没发所以里没有"。

## 顺序：留痕在前，发信在后

一条 UPDATE、若干条审计 INSERT、然后才发信。这个先后不是审美：**SMTP 卡住的那几秒里，"谁被降了"得已经在表上**。反过来写，就成了信可能一封没发、痕迹也还没落。

判据怎么钉住一个运行时读不出来的先后？源码里的位置。这一档读的是两份文件里两个调用点的偏移：

```
[通知·形状] {"transport的文件":["server/services/auth/mailer.ts"],"服务里发信调用":1,"服务里读邮箱列":1,
"审计点":2314,"发信点":2717,"任务递出成功":true,"任务递出失败":true,"登录段发信":true,"登录段catch":false,
"通知段发信":true,"通知段catch":true}
```

把发信循环整段挪到留痕前面，只有这一档红——那条 `顺序: ['SELECT','SELECT','UPDATE','INSERT']` 的判据看不见信，信不是 SQL。

## 并跑的时候，这一趟把别人的账号一起降了

这一站最贵的不是信，是它。全量带库那一趟跑出 3 failed，其中一条不是自己的：造 `member` 探针的那份规格读回 `库里角色: 'free'`，而它自己那位还在期内。同一份降级规格单跑，五档全过。

原因是这条 SQL 问的是**全库所有 `member`**，而规格里那道"让路"只能证明它读名单那一刻干净：服务层随后还要再读一次名单。别人正好插在这两次读之间建出一个 `member` 探针，这一趟就把它一起降了。让路判据挡不住这种时序，它挡的是"已经在场的人"。

先试的是排期：把这份规格单独放进一个 project，用 `dependencies` 排到整套件最后。这条路退了——依赖里只要有一条红（首页预取那一档是已知会闪红的），Playwright 会把后面那个 project **整个丢掉**，本轮读到 `7 did not run`，带库那批证据一条没跑。为了躲互踩把证据整批抹掉，比并跑更难查。

真正补上的是库侧的一把门闩：`test/e2e/member-lock.ts`，一个会话级 advisory lock。

```ts
const 锁号 = 850_001

export async function 占会员名单 (client: Client): Promise<void> {
  await client.query('select pg_advisory_lock($1)', [锁号])
}
```

写人的那份规格在 `连库()` 里一连上就占住名单，会建 `member` 探针的那份用同一把锁。两边**互相等**，而不是互相跳过；锁挂在连接上，`client.end()`、进程被杀、连接断了都会自动释放，不留死锁。改完全量带库那一趟：`350 passed`、`46 skipped`、0 failed。

## 真库上那一封是成对读出来的

跑法（没给 `NUXT_E2E_DB` 那一趟五档全 skip）：

```bash
NUXT_E2E_DB=1 E2E_PORT=4107 NUXT_STRIPE_WEBHOOK_SECRET=whsec_本地专用 \
  npm run test:e2e -- test/e2e/role-refresh-db.spec.ts
```

```
[降级·真库] {"结果":{"候选人数":1,"该降":["d91a9d7b-…"],"降了":["d91a9d7b-…"],"审计行数":1,"审计失败":0,
"发信成功":0,"发信失败":1},"库里":{"role":"free"},"页面":{"跑前":"member","跑后":"free"}}
[通知·真库] {"信":{"封数":1,"收件人":["s851.notice.1792558824861@example.com"],"主题":"会员期已经结束"},
"那一列":{"role":"free"},"结果":{"降了":["d6ce6d05-…"],"审计行数":1,"发信成功":1,"发信失败":0}}
```

前一档故意不配 SMTP，读的是"信没发出去，而库里那一列已经改了、也没被改回去"；后一档把收件端指向本地替身，读的是同一趟里信与库同时成立。收件人那一格是这份规格自建的探针邮箱（域名是 `example.com`，跑完连用户一起删）。**只读到一半都不算过**：只有信是"改了不说"，只有库是"说了没改"。

## 收了哪一格，还欠哪一格

spec 那句"发提醒邮件"接上了：降下来的人各收到一封，三种失败都落在 `发信失败` 这个数上，任务把两个数原样递出去（判据读那两份文件里两个键在不在，删掉一行就红）。

仍欠的没变：**`nuxt task run subscription:refresh-roles` 那条入口还是一次都没真跑过**——起服务要一次授权，这一档的证据全是测试进程调服务层跑出来的。另外三个键没配齐时信一封不发，而任务不会为此报失败，只看数；审计失败也还是没有修复动作。这些都要在 853 收口时逐条点名。

下一站（853）是这条线最后一步：把"手动跑两次同一个任务"这件事量一次，再把六站的读数和未闭合的那几格一起交出去。

## 你自己跑一遍

```bash
cd Substrate
npm run test:unit -- downgrade-notice           # 7 档，含真发到本地替身
npm run test:unit -- role-refresh               # 上一站那 7 档，形状变了要跟着改
npm run check                                   # 八项，含类型检查与 build
```

| 撞上的现象 | 原因与读法 |
| --- | --- |
| `发信失败` 等于 `降了` 的人数，一封没收到 | 三个键少了一个。这一档是**设计成这样的**：没配 = 不发，而不是发一封假的 |
| `发信成功: 0` 且 `发信失败: 0` | 没人被真改动。同一个人第二趟跑就是这样，不是发信坏了 |
| 判据把"正文含地址"读成 `false`，而你确认信里有 | 收件端没按编码解：通知这封两段是 base64，登录那封是 quoted-printable |
| 离线档怎么改都红不了 | 造的那两个人可能同进同退。`该降` 与 `降了` 要能给出不同答案，这一档才测到东西 |
| 跑完整套件，别人的规格红了一条 `库里角色` | 并跑互踩。确认两份规格都还在 `连库()` 里占那把锁 |
| 环境变量明明设了，读出来却是空 | `NUXT_` 开头、大写、下划线分层才对得上键名；值还会被按类型转，看着像数字的那一位要用引号包住 |

## 本文依据

- `docs/4.x/guide/going-further/runtime-config`——私有键只在服务端可读，只有 `NUXT_` 开头的大写环境变量能在运行时覆盖它；环境变量的值会按类型转换，所以要引号才保住字符串。这三句正是"三个键少一个就不发"能成立的前提。
- `docs/4.x/api/commands/task`——`nuxt task run <名字> --payload` 的形状。这一站的两个数就是给那个入口递出去的，而入口本身仍未真跑过。
- `docs/4.x/directory-structure/server`——`server/` 下各目录的分工：`services/` 是内部函数、不会成为路由，所以发信与 SQL 都放在这一层，任务文件里一行 SQL 都不写。
