前面五站做完，你在文档里能查到一句"任务可用 `nuxt task run subscription:refresh-roles` 手工触发"。把这行敲进终端，屏幕上回来的不是任务报的数，而是一句外壳话：`'nuxt-task' 不是内部或外部命令`。这一站先量这个——不是量"我们做没做"，是量"这条入口今天在这套版本上到底存不存在"。

## 三个读数：入口这一头，今天是什么形状

这一站最别扭的地方在于：要问一条命令通不通，得有一个跑起来的服务器；而起一个常驻服务器不在被允许的自动化范围里。绕开它的办法不是等授权，是换问法——端到端那一趟自己就会起服务器，那条命令本来就在允许范围内。于是变成三个能复跑的问法：

```
[CLI·命令表] {"版本":"Nuxt CLI (nuxi v3.37.0)","有task命令":false,"命令数":18,
"用法行":"USAGE nuxi [OPTIONS] [COMMAND] add|add-template|analyze|build|cleanup|_dev|dev|devtools|generate|info|init|module|prepare|preview|start|test|typecheck|upgrade"}
[CLI·task list] {"码":0,"输出含任务名":false,"外壳找不到":true}
[CLI·内部入口] {"列表":{"状态":404},"触发":{"状态":404},"对照活路由":401}
```

三条各说一句：装在这个项目里的命令行工具（`nuxi`，就是 `nuxt` 那个命令本体）**的命令表里 18 条，没有 `task`**；真去跑 `nuxt task list --url …`，它把认不出的子命令交给系统外壳去找一个叫 `nuxt-task` 的外部包，于是回你开头那句；产物服务的内部任务入口 `/_nitro/tasks` 读 404——而同一个服务器上产品自己的路由是活的（`/api/whoami` 读 401，那是"没带 cookie"的正确答案），所以这个 404 不是"服务没起来"。

**这条入口不是"我们没接"，是这一步的版本组合里没有它。** 官方那一节写得没错，它写的是"这条命令对着为你项目跑起来的 `nuxt dev` 服务器说话，用 `--url` 可以指向另一台"——它没写的是：`nuxt dev` 与生产产物在这一条上不是同一个东西，而这条命令本身要新版 CLI 才有。要真触发，剩下的路是 dev 服务器上那个内部入口（`POST /_nitro/tasks/<名字>`），那一次要起 dev，本轮没量到，照实挂着。

## "跑两次"量到了：把任务那一段直接调起来

`defineTask` 在这个版本里就是原样返回你传给它的那个对象（只多校验一句"有没有 `run`"），所以测试里把全局那位换成恒等函数，任务文件导出的就是 `{ meta, run }`——可以像调任何函数一样调它两次，报回来的是那条命令本来要打印的同一份东西。

```
[收口·第一次] {"结果":{"候选人数":2,"处理行数":1,"没降":0,"读到没改动":1,"审计行数":1,"审计失败":0,"发信成功":0,"发信失败":1},"语句数":4}
[收口·第二次] {"结果":{"候选人数":0,"处理行数":0,"没降":0,"读到没改动":0,"审计行数":0,"审计失败":0,"发信成功":0,"发信失败":0},"语句数":1}
[收口·真库跑两次] {"meta名字":"subscription:refresh-roles",
"第一次":{"候选人数":1,"处理行数":1,"审计行数":1,"发信成功":0,"发信失败":1},
"第二次":{"候选人数":0,"处理行数":0,"审计行数":0,"发信成功":0,"发信失败":0},"库里":{"role":"free"},"审计行数":1}
```

第一段是离线档（假连接记语句）：两个人被判该降、库里只动了一个 ⇒ `处理行数: 1` 而不是 2；第二趟`语句数: 1`——只问了名单那一条，没有第二个动作。第三段是真库上把同一段代码连调两次：第一次降一人、留一条痕迹、信没发出（那台机器上没配 SMTP），第二次四个数全归零，而按 `target` 数出来**痕迹仍然只有一条**。这就是"每日跑一次不会把同一批人反复按下去、也不会把审计表刷满"的那句承诺，第一次被从任务这一层的输出读出来。

报回的键也钉了一份，顺序都钉：`候选人数／处理行数／没降／读到没改动／审计行数／审计失败／发信成功／发信失败`。这八个就是给人看的那一行，**漂一个键名，跑的人读到的就是空位**（把 `处理行数` 改名试过一次：三条判据同趟红）。

## 一把锁要有看守，而看守自己先得不被骗

上一站的事故是：这条 SQL 问的是全库所有 `member`，另一个规格正好在两次读名单之间建出一个探针，就被一起降了。补法是库侧的一把门闩（会话级 advisory lock：一条 SQL 占住一个号，别的连接想占就得等，连接断了自动还）。这一站补的是**它的看守**：凡是端到端里会把用户建成 `member` 的规格，都必须占这把锁。

```
[收口·锁的看守] {"建会员的":["role-refresh-db.spec.ts","task-scope-baseline.spec.ts"],"没占锁的":[]}
```

这条判据**第一版是假的**。它当时问的是"文件里有没有 `占会员名单` 这个名字"——于是把调用删掉、只留那一行 `import`，它照样一路绿灯。改问**调用**之后（`占会员名单(client)` 那个形状），同一个变异当场报出`没占锁的: ["task-scope-baseline.spec.ts"]`。这是同一条老规矩第四次撞上：判据能不能证伪，只能由一次真变异量出来，不能由它写了什么决定。

## 那句验收，一格一格对上

规格里这件事有三处写法，逐句判下来是这样的：

| 那一格 | 现在的证据 | 结论 |
| --- | --- | --- |
| 有个任务、开关打开 | `server/tasks/refresh-roles.ts`；开关全站一处 | 接上 |
| 谁该被降 | 选取纯函数 21 行边界表 | 接上 |
| 把过期未续的人降回去 | 真库上 `member`→`free`，页面跟着改口 | 接上 |
| 写审计 | 一人一条，`meta.trigger` 必填 | 接上 |
| 发一封到期提醒 | 三种失败各有数，信与库同一趟成对 | 接上 |
| 跑两次不重复 | 任务层输出第二次全 0，痕迹仍一条 | 接上 |
| 用 `nuxt task …` 手工触发 | 命令表里没有 `task`；产物服务 404 | **没接**（版本与授权） |
| 每日定点自己跑（cron） | 执行者找到了：运行时里 `startScheduleRunner()`＋croner，配置位是 `nitro.scheduledTasks`；测试模式下它不起 | **没接**（本站没配排期） |
| "并有日志" | 表行有；**日志流里那一行没有**（任务这一路没有 event） | 半格 |

还有一处偏离要写明白：规格里那个任务叫 `subscriptions.downgrade`，本站落地成 `refresh-roles`、任务名 `subscription:refresh-roles`。名字是给人敲的契约，不是内部编号——改名的成本要同时落在文件、`meta.name`、六站判据和已发布文章的标题上，所以**这一站不动它**，但也不写成"等价所以已交付"。另外那一行硬指标里还提到 `/api/_health` 读数据库连通——整站没有这个路由，也不在本线范围，登记给下一线。

## 你自己跑一遍

```bash
cd Substrate
npm run test:unit -- task-run-closure        # 6 档，离线：真调 run() 两次＋两条体检
E2E_PORT=4118 npm run test:e2e -- test/e2e/task-cli.spec.ts   # 3 档：别带库，见下
NUXT_E2E_DB=1 E2E_PORT=4116 NUXT_STRIPE_WEBHOOK_SECRET=whsec_本地专用 \
  npm run test:e2e -- test/e2e/role-refresh-db.spec.ts        # 6 档，含真库跑两次
```

| 撞上的现象 | 原因与读法 |
| --- | --- |
| `nuxt task` 报"不是内部或外部命令" | 这一版命令行工具没有 `task` 这一条（读它的 `USAGE` 便知）；不是路径错，也不是任务没建 |
| `/_nitro/tasks` 读 404，你以为任务没注册 | 先读一个产品自己的路由做对照；对照活了，这个 404 说的是**生产产物不暴露内部入口** |
| 跑 `task-cli` 那一份时顺手加了带库开关 | 别加：任务真被触发就会批量写，而那道"名单自证与让路"在测试进程里，不在产品里 |
| 第二次跑 `run()` 还有数 | 那条带条件的 `and role = 'member'` 没生效，或者名单读歪了——先比 `候选人数` 与 `处理行数` |
| 锁的看守一路绿 | 问的是名字还是调用？只 `import` 不占锁的那种写法能骗过第一版 |

这条线到这里收官：一个"顶着 `member` 却没有任何一行还占位"的人，从今天起会被真的降下来、留下能读的理由、收到一封信，而跑第二次不会多降人、不会多留痕、不会多发信。**还欠的那几格都写在上面的表里**，最贵的两条是：真正定点自己跑（排期与执行者）、以及那条命令行入口本身。

## 本文依据

- `docs/4.x/api/commands/task`——原话是这条命令"对着为你这个项目跑起来的 `nuxt dev` 服务器说话，传 `--url` 可以指向另一台"，并给出 `nuxt task list` 与 `nuxt task run <NAME> [--payload=<json>]` 两种形状。本文那三个读数就是在这句的范围内问出来的：命令表里有没有它、跑下去回什么、生产产物答不答。
- `docs/4.x/directory-structure/server`——`server/` 各目录的分工：`services/` 是内部函数、不会成为路由；SQL 因此在服务层，任务文件只报数。
- `docs/4.x/guide/going-further/runtime-config`——私有键只在服务端可读、由 `NUXT_` 开头的大写环境变量在运行时覆盖；这一站读到的"没配 SMTP 就记一次发信失败"靠的就是这一条。
