## 先看目录里有什么

如果你手上有一个刚 `npm create nuxt` 出来的目录：一个 `app.vue`、几条自动导入的规则、`npm run dev` 一开就能看页面。这时候你想加登录，会立刻撞上一串没有答案的问题——会话存哪儿、cookie 上哪几位属性、刷新页面之后前端怎么知道我是谁、不开 JS 的访问者看到的是哪一段 HTML、部署时环境变量怎么进去。

散着的教程给的是单点答案。这套文章给的是**同一个站从空目录走到能上线**：每一篇只让你动一小块，动完就能跑一条命令核对。站的名字叫 **Substrate**。

## 这个站做什么

产品形态是一个开发者工具站：来看介绍、注册账号、付费订阅、进会员区用它的一个工具（邮件地址归一化与校验，正好能演示"表单校验的规则服务端和客户端只有一份"）。技术上要覆盖的能力清单如下，每一条在后面都有对应的功能线：

| 能力 | 落到哪里 | 在哪一段 |
| --- | --- | --- |
| 服务端渲染与混合渲染 | 落地页预渲染、内容区服务端渲、会员区不缓存 | 第三段、第四段 |
| 数据层 | Postgres ＋ Drizzle，四份迁移 | 第二段 |
| 登录 | 邮件魔法链接 ＋ GitHub OAuth，会话落库 | 第二段 |
| 权限与防护 | 会话轮换、CSRF 双提交、开放重定向、限流、审计 | 第二段 |
| 被搜到 | 内容区、`sitemap.xml`、`robots.txt`、`llms.txt`、head 元数据 | 第三段 |
| 会员区 | 读自己库的真实计数、islands、异步组件、错误边界 | 第四段 |
| 付费 | Checkout、webhook 幂等与状态机、到期降级 | 第五段 |
| 业务纵深 | 多资源增删改、批量导入、导出、搜索筛选、配额 | 第六段 |
| 规模与并发 | 队列与重试、缓存分层与失效、慢查询 | 第七段 |
| 后台与运维 | 管理后台、日志与请求号、备份演练、灰度回滚 | 第八、九段 |
| 上线 | 构建产物独立运行、发布检查表、复盘 | 第十段 |

## 明确不做的东西

这些不是"来不及做"，是为了让每一篇都能真跑通而砍掉的：

- **不做多租户与团队协作**。一张 `users` 表加一个 `role` 枚举（`free` / `member` / `admin`）足够讲清权限，多了只会让每一步都要解释归属关系。
- **不做国际化**。语言这一位只在 `<html lang>` 上出现一次，做完无障碍那一步就到位了。
- **不接真支付渠道**。第五段用测试模式与本地替身把状态机跑全：webhook 的三类事件、重放、乱序、签名错。真凭据留给你补环境变量，那一步只需要你换几个值。
- **不自己写组件库**。样式保持最小可读，注意力全部放在 Nuxt 这一层的机制上。
- **不做微服务**。单体一个 Nitro 服务，扩到第七段讲队列与缓存层次为止。

## 每一段以什么读数算完成

"学完了"不算完成，能贴出读数才算。十段各自的验收口径：

| 段 | 完成的样子 |
| --- | --- |
| 一 工程基线 | `npm run lint` 0 错、`npm run typecheck` 0 错、构建成功；一张基线数字表（首屏 JS、产物体积、四项分数、两页 TTFB） |
| 二 数据与权限 | 迁移能在空库上重放；登录全流程端到端绿；限流真的回 401；重放过的链接第二次失败 |
| 三 公开面 | 三份公开文件与内容区逐条一致；缓存位有响应头证据；分数有报告 |
| 四 会员区 | 页面数字与库里的行数对得上；禁 JS 时岛屿区块仍出内容；一块取数失败不白屏 |
| 五 订阅付费 | 三类事件＋重放＋乱序＋签名错五种输入的响应与库结果一张表 |
| 六 业务纵深 | 一批导入的预览→落库→整批回滚三段都有行数核对；导出与查询逐行一致 |
| 七 规模与并发 | 压测报告来自真实运行；队列积压/重试/死信三条路都有库里的证据；慢查询有 `EXPLAIN` 原文 |
| 八 后台 | 封禁之后目标用户下一次请求即被拒；降级任务的日志与库变更对得上 |
| 九 可观测与运维 | 停掉数据库时健康检查回 503 且日志带请求号；备份演练有行数与时间戳 |
| 十 发布 | 流水线全绿；产物在不装开发依赖的环境里独立跑通；上线检查表逐条打勾 |

**每一篇的读数都来自实跑**，包括跑错的时候。凡是本仓库某一步量下来与官方描述不一样的地方，文章里会明确写成"本机这一版是这样"，不替框架圆场。

## 这套文章怎么读：一条功能线连着几篇

编号就是顺序，不跳号、不用挑着读。划分单位是**功能的实现步骤**，不是机制名：同一个功能的教程连成一条线，线里每一步一篇，标题写成 `编号 - 功能名（n）：本步做什么`。

举第一条线（六篇）的例子，你会看到它是如何一步步推进的：

| 编号 | 这一步做的唯一一件事 |
| --- | --- |
| 726 | 立项：做什么、不做什么、怎么验收（就是这一篇） |
| 727 | 手写 `package.json`，让第一条页面能打开 |
| 728 | 第一次构建，看清 dev 与 build 的产物差在哪 |
| 729 | 钉住 Node 与包管理器版本，做一次真实重装 |
| 730 | 配置分层：默认值与环境覆盖块 |
| 731 | 环境变量进 `runtimeConfig`，用 zod 把 `.env` 变成有类型的东西 |

一条线 5-8 篇，**同一天发完**，读者一天可以跟完一个功能；不想连着读的，也能从任一步进去，因为每篇开头都会说明上一步留下的状态是什么。前面讲单个机制的那 726 篇文档精读（编号 000-725）是这套的后援：每一步遇到想深挖的机制，篇末会指到对应编号。

## 开工前先核对的四件事

这一篇不建仓库，先把环境对齐，省得下一步卡在无关的地方：

```bash
node -v
npm -v
git --version   # 只是确认机器上有；这套教程不用它，全部改动靠文件与命令
docker --version  # 可选：第二段起要起一个本地 Postgres；有托管库可以不用
```

三条要求：

1. **Node 版本以 `nuxt` 自己声明的下界为准**，别拿记忆里的数字判断能不能装；这条在下一篇会真跑一次。
2. **一个本地或托管的 Postgres**。第二段起要用，其他段不需要它。
3. **一个能改能看的编辑器**和一条习惯的终端。Windows 上的路径与大小写坑，遇到时会当场说。

| 现象 | 先查哪里 |
| --- | --- |
| `npm create nuxt` 卡住不动 | Node 版本是否过旧；终端是否在代理网络里 |
| 装完依赖 `node_modules` 大到离谱 | 是否把开发依赖装进了生产环境；下一段有专门量字节的那一篇 |
| 不知道从哪一篇开始动手 | 就按编号来；已在读文档精读系列的，遇到机制回指即可 |
| 想只挑感兴趣的功能看 | 可以，但请先读该功能线的第一篇，它给的是这一步之前的状态 |

下一站是这条线的第二步：不借助脚手架，手写 `package.json` 把第一个页面打开，顺便看清脚手架到底替你写了什么。
