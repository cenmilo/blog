先说清这个页面的形状，因为每一项配置都是被它逼出来的：文章存在 CMS 里，URL 是 `/articles/某个-slug`，正文有作者签名（用户自己填的），图片放在 `public/` 下，列表页会链接到它，转走链接时旧地址要还能用。

## 十项配置，按"落在哪"排

| # | 要做的事 | 写在哪 | 依据篇目 |
| --- | --- | --- | --- |
| 1 | slug 非法就给 404，不要渲染空壳页 | 页面里 `definePageMeta({ validate })` | 111 / 135 |
| 2 | 挂上带导航与页脚的外壳 | `definePageMeta({ layout: 'article' })`，名字用 kebab-case | 180 / 181 |
| 3 | 标题与描述（静态部分） | `useSeoMeta` 包在 `if (import.meta.server)` 里 | 190 |
| 4 | 标题随正文数据变 | `useSeoMeta({ title: () => ... })` getter 形态 | 190 |
| 5 | 作者签名这种不可信文本 | `useHeadSafe({ meta: [{ name: 'description', content: ... }] })` | 189 |
| 6 | 卡片图 | `ogImage`，值形态自己验一次 | 192 / 201 |
| 7 | 正式地址 | `useHead({ link: [{ rel: 'canonical', href: ... }] })`（**套用**）+ `useRequestURL` | 204 |
| 8 | 结构化数据 | `useHead({ script: [{ type: 'application/ld+json', innerHTML: ... }] })`（**套用**） | 193 |
| 9 | 站点级字段（品牌名、语言、兜底标题） | `app.head` + 布局里读 `route.meta` 拼 `og:title` | 185 / 186 / 194 |
| 10 | 转走旧地址 | `routeRules` 的 `redirect` + `statusCode` | 206 |

第 9 项放最后是因为它**不在这个页面里**：默认标题、`htmlAttrs.lang`、favicon 这些属于"不会变的那类"，官方建议就写在配置层（"It's good practice to set tags here that won't change such as your site title default, language and favicon."），而 `og:title` 那种要拼站点名的部分放布局。这样页面里只剩真正随文章变的字段。

## 骨架：页面这一侧写什么

下面这块把第 1 到第 8 项放在一起。**取数那一行是占位**——`useAsyncData`/`useFetch` 的行为要从 210 开始讲，这里只借它表示"文章数据来自服务端"。

```vue [app/pages/articles/[slug].vue]
<script setup lang="ts">
definePageMeta({
  layout: 'article',
  validate: route => /^[-\w]+$/.test(String(route.params.slug)),
})

const route = useRoute()
const article = /* 取数结果，见 210-249 那几篇 */

// 静态部分：搜索引擎读的是首屏那一次
if (import.meta.server) {
  useSeoMeta({
    twitterCard: 'summary_large_image',
    ogImage: '/og-image.png',
  })
}

// 随文章变的字段
useSeoMeta({
  title: () => article.value?.title ?? 'Untitled',
  description: () => article.value?.excerpt ?? '',
  ogTitle: () => article.value?.title ?? 'Untitled',
})

// 作者签名是用户填的，走安全版
const intro = () => article.value?.authorBio ?? ''
useHeadSafe({
  meta: [{ name: 'keywords', content: intro }],
})

// 正式地址与结构化数据
const url = useRequestURL()
useHead({
  link: [{ rel: 'canonical', href: url.href }],
  script: [{
    type: 'application/ld+json',
    innerHTML: JSON.stringify({
      '@type': 'Article',
      headline: article.value?.title,
    }),
  }],
})
</script>

<template>
  <article>
    <h1>{{ article?.title }}</h1>
    <p>{{ article?.authorBio }}</p>
  </article>
</template>
```

代码里每一个键都能回指到出处，但**四处需要特别标注**：

- `rel: 'canonical'`：文档没给 canonical 示例，我是按 `link` 的映射规则套的（204）。
- `type: 'application/ld+json'` + `innerHTML`：前者是"属性对应 HTML 属性"的直接用法，后者来自 `useHead` Usage 示例里那个 `console.log` 的写法；**这两者合起来构成 JSON-LD 不是文档教我的**（193）。
- `validate` 里那个正则是我随手写的示例形态，官方给的判据只是"返回 false 就 404"，也可以返回 `{ status, statusText }`（111）。
- `ogImage: '/og-image.png'` 这个值形态**恰好是两处示例里唯一不一致的那个字段**（201），我在这里保留了文件名的来源写法，但它必须由你按实测结论替换。

## 顺序敏感：这个页面里三处时机要求

拼装时有个"本地都对、上线少标签"的坑，原因全在时机上：

1. **同步注册**。文档点名的三类位置是"`useHead`/`useSeoMeta` called synchronously in `<script setup>` (before any `await`), in plugins, or in middleware"，并且对 SEO 标签特别写了 "Keep other SEO-critical tags (canonical links, social meta) synchronous"。上面那块代码里我把 `canonical` 放在最后，但**它在同一个同步 `setup` 里**，所以仍算同步注册；一旦你把它挪到 `await` 之后就不是了。
2. **别把 head 注册塞进只在客户端渲染的地方**。198 讲过 `<ClientOnly>` 里的组件不在服务端跑，那些标签不可能出现在服务端 HTML。
3. **水合两侧要一致**。199 那条 SEO 后果（"Search engines may index different content than what users actually see"）在这个页面上的具体来源就是 `Math.random()`、`new Date()`、`localStorage` 这类只在浏览器有值的读取——要读就走 `useCookie`/`useState`/`NuxtTime`。

## 这个页面能不能被爬到，取决于列表页

预渲染那一节的机制（200）在这里很实用：文章页是动态路由，`prerender.routes` 不会自动包含它们，能进静态产物的唯一途径是**被某个已预渲染页面的 `<a href>` 指向**。而 `<NuxtLink>` 渲染出来就是 anchor（112 那个例子把 `params` 渲染成 `href="/posts/123"`）。所以：

- 列表页要真的渲染出链接，而不是只在点击时 `navigateTo`。
- 只在 JS 里拼出来的路径（200 的推论一）抓取期看不见。
- 数据是构建期快照："On a fully static site, client-side navigation reuses the data captured at build time, so data can be stale until the next rebuild."——文章改了要重新构建才有新版本。

在线渲染（非静态）时，这条换成另一个问题：**开了 `ssrStreaming` 后，未命中 `botRegex` 的抓取者拿的是流式响应**，晚注册的 head 标签它读不到（JSON-LD、noscript、body 位置的除外）。真要保守，文档给的是 `routeRules: { '/articles/**': { streaming: false } }` 这条退出路径。

## 上线前我用这几步过一遍

1. `curl` 文章页，逐项确认：`<title>`、`description`、`og:title`、`og:image` 的值、`link[rel=canonical]` 有没有出现、JSON-LD 出现在 `<head>` 还是 `</body>` 之前。
2. 浏览器打开同一路由，等水合结束后再读一次，跟第 1 步比对（不一致就去找 199 那张成因表）。
3. `curl -I` 旧地址，确认状态码真是你写的 `301`/`302`（206）。
4. 拿一个不存在的路径过去，看返回的是不是带外壳的错误页（207），静态托管还要看那份 `404.html` 是不是空壳。
5. 读屏或无障碍检查工具跑一次导航，确认每篇文章标题不同、播报器读得出变化（101 那条"标题相同则什么都听不到"）。

## 自查

1. 这一页里哪两处是套用而不是文档原话？（答：canonical 的 `rel` 用法、JSON-LD 的 `script` + `innerHTML` 组合。）
2. 为什么 `ogImage` 这一项要留到实测？（答：文档四处示例三种绝对 URL、一种根路径，且没有"必须绝对"的规则，也没写它渲染成哪个属性。）
3. 静态站上文章改了但抓取者还看到旧内容，第一个要看的不是 head，而是？（答：是不是没有重新构建——数据快照时间在构建期。）
