  摘要：这一篇回答两个我一直没确认的问题：**布局里能用哪些自动导入**、**它在哪一步跑**。前者由官方示例直接证明——SEO 那一节给布局的例子同时用了路由与 head："> And then in your layout file, you might use the route's metadata you have previously set:" + `const route = useRoute()` 与 `useHead({ meta: [{ property: 'og:title', content: \`App Name - ${route.meta.title}\` }] })`（`layouts/default.vue`）。也就是说布局是 **Vue 应用上下文里的普通组件**，走的是 app 侧那份名单："**In the docs, every function that is not explicitly imported is auto-imported by Nuxt**"，范围包括 `app/components/`、`app/composables/`、`app/utils/` 与 Vue 的响应式 API/生命周期钩子；而 `nuxt/server` 那一族在 app 侧导入会构建失败（"**Importing `nuxt/server` from a Vue component, a plugin or the `shared/` directory fails the build**"，154）。**后者落在生命周期里**：布局属于 "Page and components" 那一步，而它在中间件之后——官方顺序句是"**After initializing plugins and before executing middleware, Nuxt calls the `validate` method**"，中间件步之后才是"Nuxt renders the page and its components and fetches any required data with `useFetch` and `useAsyncData` during this step"。**与中间件有关的那条双跑规则必须记住**："> If your site is server-rendered or generated, **middleware for the initial page will be executed both when the page is rendered and then again on the client**. This might be needed if your middleware needs a browser environment, such as if you have a generated site, aggressively cache responses, or want to read a value from local storage."，官方给的回避写法是中间件里 `if (import.meta.server) return` / `if (import.meta.client) return`。而布局里可以读路由、中间件里不行（060 那条禁令），这是两者最实用的分工差别。

我有一次想把"读 localStorage 判断主题"的逻辑写进布局，又担心它跟中间件抢顺序。查完官方给的两个事实我才理清：**布局能读路由，中间件不能**；而**首屏的中间件会跑两遍，布局不会**。这一篇说清这两条差别带来的分工。

## 布局是应用上下文里的普通组件

这不是我推的，是官方示例直接演示的形状。SEO 那一页给布局的例子同时用了路由元数据与 head：

> And then in your layout file, you might use the route's metadata you have previously set:

```vue [layouts/default.vue]
<script setup lang="ts">
const route = useRoute()

useHead({
  meta: [{ property: 'og:title', content: `App Name - ${route.meta.title}` }],
})
</script>
```

一句里出现三件事，都能在别的篇章对上：

| 出现的东西 | 说明 |
| --- | --- |
| `useRoute()` | 布局是 Vue 组件，路由上下文可用（对照 060：**中间件里禁止 `useRoute()`**，只能用参数 `to`/`from`） |
| `useHead()` | 布局也是 head 的合法宿主（187 起展开） |
| `route.meta.title` | 值来自页面 `definePageMeta({ title })`——官方那句补充说它是**构建期通过宏提取**的："this is extracted at build time via a macro, so it can't be set dynamically" |

所以布局的自动导入范围与页面、组件完全一致，判据还是那句：

> In the docs, every function that is not explicitly imported is auto-imported by Nuxt and can be used as-is in your code.

## 布局里可用与不可用

| 类别 | 具体 | 依据 |
| --- | --- | --- |
| 可用 | Vue 响应式 API 与生命周期钩子（`ref`、`computed`、`watch`、`onMounted`） | "Vue exposes Reactivity APIs like `ref` or `computed`, as well as lifecycle hooks and helpers that are auto-imported by Nuxt." |
| 可用 | 数据与上下文类（`useFetch`、`useAsyncData`、`useState`、`useRuntimeConfig`、`useNuxtApp`） | "Nuxt auto-imports functions and composables to perform data fetching, get access to the app context and runtime config, manage state..." |
| 可用 | 路由与导航（`useRoute`、`useRouter`、`navigateTo`）、head 一族、`useAppConfig`、`useLayout` | 各篇章（120-124、187、108、183） |
| 可用 | 你自己在 `app/composables/`、`app/utils/`、`shared/utils/`、`shared/types/` 里的导出 | 150、151 |
| 不可用 | `nuxt/server` 那一族（`defineEventHandler`、`getCookie`、`useSession`…） | "Importing `nuxt/server` from a Vue component, a plugin or the `shared/` directory **fails the build**" |
| 不可用 | `server/utils/` 的自动导入 | "In the `server` directory, Nuxt auto-imports exported functions and variables from `server/utils/`."——范围限定在服务端 |

**还有一类要按位置判**：布局在 SSR 阶段同样是"渲染一次"，所以 149 那条限制对它成立——`onBeforeMount`/`onMounted` 在服务端**不执行**，且 `<script setup>` 顶层写需要清理的副作用（例如 `setInterval`）会因为卸载钩子不被调用而留下来。

## 它排在中间件之后

把 149 的顺序按"布局落点"再走一遍：

| 顺序 | 步骤（官方原话节选） | 布局在哪 |
| --- | --- | --- |
| ① | 插件初始化 | 还没渲染布局 |
| ② | "After initializing plugins **and before executing middleware**, Nuxt calls the `validate` method" | — |
| ③ | App middleware（全局 + 命名/匿名） | 布局仍未渲染 |
| ④ | "Nuxt **renders the page and its components** and fetches any required data with `useFetch` and `useAsyncData` during this step." | **布局在这里**（它包住页面） |

这解释了一个具体的现象：**中间件里改布局（`setPageLayout` 或返回重定向）会先于布局渲染生效**（139 那条"要在 Vue 渲染前调用"的告诫，原因就在这张表里）。

## 但首屏的中间件会跑两遍，布局不会

这条对布局里的读值逻辑最相关，官方原话：

> If your site is server-rendered or generated, **middleware for the initial page will be executed both when the page is rendered and then again on the client**. This might be needed if your middleware needs a browser environment, such as if you have a generated site, aggressively cache responses, or want to read a value from local storage.

官方同时给了回避写法（`middleware/example.ts`）：

```ts [middleware/example.ts]
export default defineNuxtRouteMiddleware((to) => {
  // skip middleware on server
  if (import.meta.server) {
    return
  }
  // skip middleware on client side entirely
  if (import.meta.client) {
    return
  }
})
```

两侧的影响摆在一起看：

| | 布局 | 中间件 |
| --- | --- | --- |
| 首屏执行次数 | 服务端渲染一次、客户端水合一次（同一份模板） | 服务端 + 客户端**各跑一次逻辑** |
| 能读浏览器环境吗 | 水合后能（`onMounted` 里） | 能，但那是它跑第二遍的事 |
| 能读 `useRoute()` | ✅ | ❌（只有参数 `to`/`from`，E2005） |
| 能改导航 | ❌（渲染期，导航已完成） | ✅（返回值就是指令，132） |

**我因此定下的分工**：需要"读浏览器里的东西来决定去哪" → 中间件（并显式决定要不要在某一侧跳过）；需要"读路由结果决定长什么样" → 布局。写反的典型症状分别是：布局里做重定向造成一次多余渲染；中间件里 `useRoute()` 直接报错。

至于"布局被 SSR 渲染、再被客户端水合"这件事，它和中间件的双跑不是同一码事：水合**不重新执行 setup 里的服务端专属分支**、也不重新发 SSR 已取过的数据（149 那句"useAsyncData/useFetch 让服务端取过的数据在水合时被复用"）。

## 布局文件的加载时机另算

180 引的那条 tip 说的是加载，不是执行：

> For best performance, components placed in this directory will be **automatically loaded via asynchronous import when used**.

也就是"用到哪个布局才异步取哪个文件"。这与上面那张顺序表是两件事：**中间件决定这一页用哪个名字（181 那条链），布局文件随后被异步加载**。官方没有把两者的先后写成一句规则，我不补这个结论。
