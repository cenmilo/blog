## 为什么不能忽略

页首只有一句劝告和一个判断：

> When developing, you may face hydration issues. Don't ignore those warnings.

> Hydration mismatches are not just warnings - they are indicators of serious problems that can break your application:

后果分两组，逐条照抄：

| 分组 | 条目 | 原文 |
| --- | --- | --- |
| Performance Impact | 交互变慢 | "**Increased time to interactive**: Hydration errors force Vue to re-render the entire component tree, which will increase the time for your Nuxt app to become interactive" |
| Performance Impact | 体验差 | "**Poor user experience**: Users may see content flashing or unexpected layout shifts" |
| Functionality Issues | 交互坏掉 | "**Broken interactivity**: Event listeners may not attach properly, leaving buttons and forms non-functional" |
| Functionality Issues | 状态不一致 | "**State inconsistencies**: Application state can become out of sync between what the user sees and what the application thinks is rendered" |
| Functionality Issues | **SEO** | "**SEO problems**: Search engines may index different content than what users actually see" |

我看到那张表时的反应是：原来我把 SEO 问题归错了类。我一直以为"排名不好"是 meta 没写全，但文档把"索引到的内容与用户看到的不一致"放在**水合错配**的后果里——它是运行时问题的后果，不是标签缺失的后果。这和 198 的推论二是同一件事的两端。

检测方式文档只给了一条：开发环境浏览器控制台里的 Vue 水合不匹配警告（配了一张截图）。也就是说它没有提供命令行或构建期检查办法。

## 五个成因与官方给的解法

| 成因 | Problem 原话 | Solution |
| --- | --- | --- |
| 服务端用了浏览器 API | "Using browser-specific APIs during server-side rendering."，示例是 `const userTheme = localStorage.getItem('theme') \|\| 'light'`，注释写 "localStorage doesn't exist on the server!" | 用 `useCookie`：`useCookie('theme', { default: () => 'light' })`，注释 "This works on both server and client" |
| 两侧数据不一致 | "Different data between server and client."，示例模板里直接 `{{ Math.random() }}` | 用 SSR 友好状态：`useState('random', () => Math.random())` |
| 按客户端状态做条件渲染 | "Using client-only conditions during SSR."，示例 `v-if="window?.innerWidth > 768"` | 用媒体查询（`class="hidden md:block"` / `class="md:hidden"`）或放到客户端处理 |
| 有副作用的第三方库 | "Libraries that modify the DOM or have browser dependencies (this happens a LOT with tag managers)."，反例是 `if (import.meta.client) { ... SomeBrowserLibrary.init() }` | "**Initialise libraries after hydration has completed**"：挪进 `onMounted(async () => {...})` |
| 随时间变化的内容 | "Content that changes based on current time."，示例按小时给问候语 | 用 `NuxtTime`（`<NuxtTime :datetime="new Date()" format="HH:mm" />`）或客户端处理：`ClientOnly` + `#fallback` 里给 "Hello!"，`onMounted` 里再改 `greeting.value` |

有两条我觉得是这一页最容易被跳过的：

1. **`import.meta.client` 里初始化库也算反例**。我原来以为判了客户端就安全，文档把它放在 Problem 一侧，理由是时机不对——水合期间 DOM 被动过就会错配；正确写法是 `onMounted` 之后。那句括号 "this happens a LOT with tag managers" 也顺带解释了为什么这类问题常和 head 脚本一起出现（标签管理器就是往 head/body 里塞 script 的那类东西，见 193）。
2. **第五个成因给了两种解法而且并列**：`NuxtTime` 或者 `ClientOnly` + `onMounted`。这两种的差别不是"能不能修好警告"，而是首屏拿到什么——`ClientOnly` 那条走的是 198 讲的"服务端只有 fallback"。

In Summary 四条守则原文：

> 1. **Use SSR-friendly composables**: `useFetch`, `useAsyncData`, `useState`
> 2. **Wrap client-only code**: Use `ClientOnly` component for browser-specific content
> 3. **Consistent data sources**: Ensure server and client uses the same data
> 4. **Avoid side effects in setup**: Move browser-dependent code to `onMounted`

第 3 条是我最不想接受但最本质的一条：它不讲技巧，讲的是"两侧输入必须同源"。上面五个成因里，`localStorage`、`Math.random()`、`window.innerWidth`、`new Date().getHours()` 全都能归到这一条。

## useHydration：这页把它放在哪儿

上面第二条守则用 `useState` 而不是 `useHydration`，这不是随意。`use-hydration` 页自己有两段 note：

> This is an advanced composable, primarily designed for use within plugins, mostly used by Nuxt modules.

> `useHydration` is designed to **ensure state synchronization and restoration during SSR**. If you need to create a globally reactive state that is SSR-friendly in Nuxt, `useState` is the recommended choice.

签名和时机也写清了：

```ts
export function useHydration<T> (key: string, get: () => T, set: (value: T) => void): void
```

| 参数 | 文档说明 |
| --- | --- |
| `key` | "A unique key that identifies the data in your Nuxt application." |
| `get` | "A function executed **only on the server** (called when SSR rendering is done) to set the initial value." |
| `set` | "A function executed **only on the client** (called when initial Vue instance is created) to receive the data." |

数据落点是 `nuxtApp.payload`："The data returned from the `get` function on the server is stored in `nuxtApp.payload` under the unique key provided as the first parameter to `useHydration`. During hydration, this data is then retrieved on the client, preventing redundant computations or API calls."

顺手记一处示例笔误：这一页"Without useHydration"那段里，插件回调参数写的是 `(nuxtApp)`，而下面两处钩子调用写的是 `nuxt.hooks.hook('app:rendered', ...)` / `nuxt.hooks.hook('app:created', ...)`，`nuxt` 在那个作用域里并不存在。我照原样抄下来，是为了提醒：**别把这段当可运行代码**，要照它的手写等价形式，得自己确认钩子挂在哪个对象上。

## 自查

1. 文档把 SEO 问题列为水合错配的哪一组后果？具体句子是什么？（答：Functionality Issues 组第三条约 "Search engines may index different content than what users actually see"。）
2. 为什么在 `import.meta.client` 里初始化浏览器库仍然算 Problem？（答：官方给的解法是"在水合完成之后初始化"，即放进 `onMounted`；判了客户端不等于时机对。）
3. 需要全局响应式状态时，官方推荐哪个，理由句是什么？（答：`useState`；`useHydration` 是"advanced composable, primarily designed for use within plugins, mostly used by Nuxt modules"。）
