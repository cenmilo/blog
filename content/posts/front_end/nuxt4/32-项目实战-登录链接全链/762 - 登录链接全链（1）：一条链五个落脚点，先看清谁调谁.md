## 你只按了两个按钮，中间有五个落脚点

用户在页面上填邮箱、按"发登录链接"，然后打开邮件里那条地址，页面一跳转就是登录状态了。屏幕上看得见的就这两下。中间这一段在仓库里是五个文件、两行职责完全不同的表：

```text
POST /api/auth/login-link        ← 邮箱进来
  └─ server/api/auth/login-link.post.ts（27 行）
       ├─ shared/schemas/auth.ts  parseLoginLink()  格式与归一
       ├─ server/utils/http/rate-limit.ts  令牌桶
       └─ server/services/auth/login-link.ts（66 行）requestLoginLink()
            ├─ server/services/auth/token.ts（86 行）   生成券、写一行 login_tokens
            └─ server/services/auth/mailer.ts（54 行）  nodemailer 发信

GET /api/auth/verify?token=…     ← 用户点邮件里那条
  └─ server/api/auth/verify.get.ts（104 行）
       ├─ server/services/auth/verify.ts（97 行）  占券、认人、换会话
       └─ server/utils/http/safe-redirect.ts（41 行）  只准回本站相对路径
```

上面这棵树不是画给人看的示意图，**每一个 `└─` 都是从源码里的 `import` 抄下来的**（例如 `login-link.post.ts:6-7`、`login-link.ts:11-12`、`verify.get.ts:13-15`）。为什么要较真到行号：这条链以后每一步都要能回答"这次失败是哪一层给的"，而那一层只能靠调用方向回溯。

## 五个落脚点各管一件事

| 文件 | 行数 | 这一层负责什么 | 它会发出去的码 |
| --- | --- | --- | --- |
| `api/auth/login-link.post.ts` | 26 | 收请求、按顺序过三道闸 | `EMAIL_*`（按 issue 拼出来）、透传下游 |
| `services/auth/login-link.ts` | 66 | 决定"要不要发、发不出去怎么办" | `MAIL_NOT_CONFIGURED`、`MAIL_SEND_FAILED`、`IP_UNKNOWN` |
| `services/auth/token.ts` | 86 | 券的生成、摘要、过期时刻 | 不发消息，只给数据 |
| `services/auth/mailer.ts` | 54 | 把信交给 SMTP | 不发消息，失败靠上层翻 |
| `api/auth/verify.get.ts` | 104 | 点链接那一步的判定顺序 | `TOKEN_MISSING`、`LINK_INVALID`、`DB_NOT_CONFIGURED`、`SESSION_CREATE_FAILED` |
| `services/auth/verify.ts` | 97 | 占券、认人、建会话那三条 SQL | 不发消息，返回结果给路由 |

`api/auth/login-link.post.ts` 那一句"按顺序过三道闸"，顺序是写死的：**先格式，再令牌桶，最后才发信**。反过来的话，一个正在被人反复尝试的邮箱会既留下券、又消耗一次数据库连接——格式错的请求根本不该碰到库，这一点在文件头注释里写着理由。

## 这条链上的六个词，先各给一句人话

后面七站全都用这几个说法，这里一次说清，省得每站重讲一遍。

- 魔法链接：邮件里那条一次性地址，点开就等于登录。它的凭据是那条地址本身，不是账号口令。
- 券（代码里叫 `token`）：链接尾部那串随机字符。本站生成的是 32 字节随机数转成十六进制，所以是 64 个字符（`token.ts` 里 `TOKEN_BYTES = 32`）。
- 明文：那 64 个字符本身。它只活两个瞬间——拼进邮件链接的那一下，和用户点开来那一下。
- 摘要：把明文过一遍 sha256 得到的定长字符串（`hashToken()`）。**库里存的是摘要，不是明文**，所以库里查不到邮件里那串原文。
- 令牌桶：按"邮箱"和"来源地址"各记一份额度，超了就 429。它挡的是"拿这个接口挨个试邮箱"。
- 侧信道：不改响应内容、只靠快慢或次数差别泄露信息的那类通道。这条链上一处都没给它留口子，理由见下一节。

## 一条链上的两条"不看账号"

这一层最难写对的不是逻辑，是**不肯透露任何账号信息**。仓库里 `login-link.ts` 的文件头写三条：

```text
① 不看 users 表。这一步只做"发一张券并把链接交出去"，注册与登录的分叉留给校验那一步，
   所以攻击者既拿不到差别响应，也拿不到差别耗时——少一次查询就少一条侧信道；
② 发不出去就撤券。先生成再发送的话，SMTP 挂了会留下一堆没人能用的空券；
   现在发送失败 → 删掉那行 → 回 503，库里不留半成品；
③ 没配发信服务是服务器的问题，不是账号的问题，所以它回 503 而不是"看起来成功"。
   这条不泄露任何账号信息：它对任何邮箱都一模一样。
```

第 ① 条能不能信，**不能靠读注释**。这一趟产物服务上没有配 SMTP、也没有配库，正好用两个邮箱各打一次（一个是库里真有的地址，一个是编的）：

```text
[同一条路] {"状态":503,"两边同号":false,
 "挖掉号之后的形状":"{\"error\":true,\"url\":\"http://localhost:3137/api/auth/login-link\",
 \"statusCode\":503,\"statusMessage\":\"Service Unavailable\",\"message\":\"登录邮件暂时不可用，请稍后再试。\",
 \"data\":{\"code\":\"MAIL_NOT_CONFIGURED\",\"requestId\":\"<id>\"}}"}
```

**两个邮箱的响应体，除了各自的编号以外逐字节相同。** 这条断言由 `test/e2e/login-link.spec.ts` 钉着（本轮跑出来 `3 passed (26.0s)`），它比之前先把 `url` 与 `data.requestId` 这两位挖掉——那两位天然不同，不挖掉比的就是"你两次请求不是同一秒"。

第 ② 条在第 5 站细看；本轮能读到的证据是单元测试那一层：`npx vitest run test/unit/login-link.test.ts test/unit/auth-token.test.ts test/unit/auth-verify.test.ts test/unit/auth-mailer.test.ts` 一共 **33 条用例全过**，其中"发送抛错：先撤券再回 503"和"没配 SMTP：503，而且一张券都不落"这两条就是第 ② 与第 ③ 条的正面证据（发送层被 `vi.mock` 换掉，测的是撤不撤券，不是 nodemailer 的行为）。

## 这一条为什么可以走 `throw`

上一线第三站立过分界的规矩：**查询串里带凭据的路由不许 `throw`**，因为框架的错误通道会把完整地址回显进响应体。看这条链上的两个入口：

| 入口 | 凭据在哪 | 用哪条出口 | 回显出去的是什么 |
| --- | --- | --- | --- |
| `POST /api/auth/login-link` | 请求体里的邮箱 | `throw apiError(...)` | 地址上没有凭据，回显无害 |
| `GET /api/auth/verify?token=…` | **查询串里的那枚券** | `apiFailureResponse(...)`，`url` 只留路径 | 不回显，日志里也不带 |

上面那条读数里 `"url":"http://localhost:3137/api/auth/login-link"` 正好是这个规则的现成注脚：**同一个 `url` 位，一条链上两处都能出现，但只有一处需要防**。另一半证据也在同一行里——`"statusMessage":"Service Unavailable"`，这是上一线最后一站把 503 补进状态短语表之后才有的样子。

## 一次点击前后，库里动了哪几张表

这条链只碰三张表，但顺序不能乱。下表最后一列说明哪一步需要活库——那几步本轮没有读数，归这条线后面的站。

| 步 | 代码里是谁 | 动了什么 | 要库吗 |
| --- | --- | --- | --- |
| 1 过格式闸 | `parseLoginLink()` | 不碰库，只归一化（转小写、去首尾空格） | 不要 |
| 2 过令牌桶 | `assertRateLimit()` | 记邮箱维与 IP 维各一笔 | 不要 |
| 3 生成券 | `issueLoginToken()` | `login_tokens` 插一行：存摘要、`expires_at` 是当下 ＋ 900 秒、`created_ip` 记来源 | 要 |
| 4 发信 | `sendLoginEmail()` | 不碰库；失败则回头删第 3 步那一行 | 不要 |
| 5 用户点开 | `verify.get.ts` 前半 | 先只判形状（64 位十六进制），形状不对一次库都不问 | 不要 |
| 6 占券 | `claimLoginToken()` | `login_tokens` 上一条带三个条件的更新，改到行才算占到 | 要 |
| 7 认人 | `upsertUserByEmail()` | `users` 有则取、无则建（注册与登录共用这一句） | 要 |
| 8 同址撤券 | `revokeOtherTokens()` | 删掉这个邮箱名下其余的券 | 要 |
| 9 换会话 | `rotateSessionRow()` | `sessions` 删旧插新，登录前后不是同一个会话号 | 要 |
| 10 落地 | `safeRedirectTarget()` ＋ `sendRedirect` | 不碰库，302 到本站的相对路径 | 不要 |

三点先看一眼：第 3 步写完就要能删（第 4 步失败时），这是"不留半成品"的意思；**第 5 步排在第 6 步前面**，垃圾输入不占用数据库连接；第 9 步排在这次登录成功的那一刻，防的是"登录前后共用一个会话号"那种会话固定。

## 出问题对照

| 症状 | 原因 | 怎么办 |
| --- | --- | --- |
| 换个邮箱地址，报错文案不一样 | 有一层偷偷看了 `users` 表 | 这一步只发券；分叉留给兑换那一步 |
| 库里出现大量没人点过的券 | 先落券再发信，发送失败没撤 | 发送失败必须 `revoke`，看 `login-link.ts` 的 catch |
| SMTP 没配，接口回 200"已发送" | 想对用户隐身 | 回 503 ＋ 一个自己的 `code`，别把环境问题藏起来 |
| 一个脚本能把邮箱枚举一遍 | 没上令牌桶，或者桶在发信之后 | 桶在格式之后、发信之前；429 带 `retry-after` |
| 排查时说不上"这次失败在哪一层" | 只有 `message`，没有分类 | 每层发自己的 `code`（见上面那张表） |

## 你自己跑一遍

1. 自己把这棵树抄一遍再核对：`grep -n "^import" server/api/auth/login-link.post.ts server/services/auth/login-link.ts server/api/auth/verify.get.ts server/services/auth/verify.ts`，比对每层各引了谁。
2. `E2E_PORT=3137 npm run test:e2e -- test/e2e/login-link.spec.ts` → `3 passed`，读那行 `[同一条路]` 与 `[429 headers]`（本轮读到 `retry-after: 360`、`code: RATE_LIMITED`）。
3. `npx vitest run test/unit/login-link.test.ts` → 6 条，重点看"没配 SMTP 也不落券"和"发送抛错先撤券"。
4. 想看第 ① 条能不能被绕过：把 `login-link.ts` 里那段 `if (!smtpUrl || !mailFrom)` 临时改成回 `LOGIN_LINK_RESPONSE`（也就是"看起来成功"），跑第 2 步——第二条用例立刻红，因为状态码不再是 503。改回来。

## 这一站的边界

这一站没有新增业务代码，只把已有的一层量清楚，所以读数只有三类：源码里的 `import` 行号与文件行数、产物服务上那条 `[同一条路]`（端口 3137，`3 passed`、26.0 秒）、四个单测文件的 `33 passed`。**库里那一行券到底长什么样、占券的 SQL 真的怎么挡重放、发信成功的完整路径**这三件都需要活库或活 SMTP，本轮一处都没做，分别归这条线的第 4、6、5 站，且都以"读者的动手步骤"呈现。

**连库与写库的授权从第二条线起就在问，到这一站是第十一次，仍没有答复。** 没有它，这条链的库侧读数一律只能写成预测。

仓库这一轮的永久改动：`server/services/auth/login-link.ts` 文件头一处指向别处的引用改成自解释说法；`test/e2e/login-link.spec.ts` 里加一行自打印读数。
