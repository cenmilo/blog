## 三段代码的顺序，就是三种失败的顺序

`server/api/auth/login-link.post.ts` 去掉注释只剩四个语句：

```ts [server/api/auth/login-link.post.ts]
const parsed = parseLoginLink(await readBody(event))

if (!parsed.ok) {
  throw apiError(event, {
    statusCode: 400,
    message: EMAIL_COPY[parsed.issue ?? 'invalid'],
    code: `EMAIL_${(parsed.issue ?? 'invalid').toUpperCase()}`,
  })
}

// 邮箱维与 IP 维各一只桶，都在 assertRateLimit 里；429 会带上 retry-after
assertRateLimit(event, parsed.email)

await requestLoginLink(event, parsed.email)

return LOGIN_LINK_RESPONSE
```

三件事从上到下排：先判格式，再查额度，最后才轮到发信。文件头那句"顺序是有讲究的"不是修辞——上一站（763）留了个尾巴：`rate-check` 探针只有三条端到端，桶跨规格共享这件事它量不到。这一站就是去量它。

## 先把三个词说成人话

- 令牌桶：一只最多装 10 张牌的杯子，每 6 分钟补一张。每次请求取走一张，取不到就拒，并告诉客户端还要等多少秒才能补出一张。本站给登录链接定的额度就是这一套，容量 10、补牌间隔 6 分钟。
- 维度：同一次请求要同时从两只杯子里各取一张，邮箱一只、来源地址一只。任何一只空了都算超额度。
- 端到端用例：不是把某个函数单独拎出来跑，而是把 `nuxt build` 的产物真开起来，用 HTTP 请求去打它，读回来的状态码、响应头和响应体。

## 这三步各自挡什么

| 顺序 | 代码在哪 | 通过条件 | 失败时回什么 | 失败后留下什么 |
| --- | --- | --- | --- | --- |
| 判格式 | `parseLoginLink` | 归一之后像个邮箱，且不超过 254 字符 | 400，码是 `EMAIL_MISSING`／`EMAIL_INVALID`／`EMAIL_TOO_LONG` | 什么都不留，一张牌也不扣 |
| 查额度 | `assertRateLimit` | 两只桶都还有牌 | 429，码 `RATE_LIMITED`，另带一位 `retry-after` | 扣掉的牌要等补，不发券 |
| 才发信 | `requestLoginLink` | 发信配置齐、号码能生成、邮件能交出去 | 503，码 `MAIL_NOT_CONFIGURED` 或 `MAIL_SEND_FAILED` | 发送失败要把刚生成的券撤掉 |

第三步那一行还藏着一个次序：进 `requestLoginLink` 之后先看的是发信配置，配置不齐就直接 503，压根不碰数据库。所以本机这种"没 SMTP 也没库"的环境里，所有走满前两步的请求都停在 `MAIL_NOT_CONFIGURED`——上一站那行 `[同一条路]` 读数里的 503 就是这么来的。

## 把前两步换个头尾，先失败的是别人

顺序倒过来是这样：先扣牌，再判格式。看着没什么差别，两种写法都能回 400、都能回 429。真正的差别要在额度打空之后才看得见。

本站把入口真改成倒序跑了一趟端到端，再改回来。倒序那一趟读到的是：

```
[掏空之后] {"合法形状的码":429,"非法邮箱的码":429,"code":"RATE_LIMITED","人话":"请求太密集了，先等一会儿再发。"}
Expected: 400
Received: 429
```

顺过来之后同一份用例的读数是：

```
[掏空之后] {"合法形状的码":429,"非法邮箱的码":400,"code":"EMAIL_INVALID","人话":"邮箱地址格式不对，检查有没有 @ 和域名结尾。"}
```

这就是那两条代价的第二条：**格式错的请求不能扣牌**。只要它扣得到，一个脚本拿同一个非法邮箱连打十几次，就能把这台机器上真正想登录的人的额度掏空——受害者一行代码都不用改，只是忽然收不到登录链接了。代价的第一条在库里：顺序反了的时候，一个正在被枚举的邮箱会既留下券、又消耗数据库连接，这一条要连库才数得出行数，本站没拿到连库授权，留给读者自己跑。

## 端到端钉的是码序，不是"第 11 次"

用例在 `test/e2e/rate-order.spec.ts`，两条，串行：

```ts [test/e2e/rate-order.spec.ts]
test.describe.configure({ mode: 'serial' })

test('连着打同一个来源，越界之后是 429 带 retry-after', async ({ request }) => {
  for (let i = 0; i < 14; i++) {
    const res = await post(request, `sweep-${i}@example.com`)
    codes.push(res.status())
    if (res.status() === 429) { lastBlocked = res; break }
    shapes.push(shapeOf(await res.json()))
  }
  expect(shapes.length).toBeGreaterThanOrEqual(1)
  expect(new Set(shapes).size).toBe(1)
  expect(codes.filter(c => c === 429).length).toBe(1)
})
```

每个请求换一个合法形状的邮箱，所以每打一次扣的都是 IP 维那一张。单跑这一条（新的产物进程，桶是满的）打印出来的码序：

```
[码序] {"放行次数":10,"码":[503,503,503,503,503,503,503,503,503,503,429],"retry-after":"360"}
[429 headers] {"x-request-id":"496f11f7-2538-48f2-96e9-9d4b851725ce","retry-after":"360","code":"RATE_LIMITED"}
```

十条 503 是同一条失败路径，形状逐字节相同；第十一次换成 429，`retry-after` 是 360。这里有两个容易误判的地方。一是被限流那条也要有编号：限流发生在业务之前，日志里如果没这一条，"有人把自己打到 429"这件事就只剩客户端一句话，所以头里的 `x-request-id` 与体里的 `requestId` 必须是同一个。二是 `retry-after` 不必然是 360：它报的是"再过多少秒补出一张牌"，距离上一次取牌过了几秒，这里就少几秒——并进全套跑的那一趟读到的是 354。

## 桶是全进程共享的，用例之间会互相掏空

上面那句"单跑"不是随口一说。这一轮第一次把新用例并进全套，整套跑出来是这样：

```
Running 189 tests using 10 workers
2 failed
54 skipped
133 passed (33.1s)
```

红的那两条都不在新用例里，报的是：

```
TypeError: Cannot read properties of undefined (reading 'email')
```

出处是 `test/e2e/rate-check.spec.ts` 读探针响应里的 `keys.email`。令牌桶活在产物服务那一个 node 进程的模块作用域里，`buckets` 是一张进程内的 Map。同一台机器发出的请求全落进同一个 `ip:` 键——新用例把 IP 维打空之后，同一趟运行里后面所有需要 200 或 503 的读数都会变成 429，而 429 的响应体里没有 `keys` 这一位。看起来像代码坏了，其实是上一个用例把额度用完了。

三条路里选了最短的那条：把"允许打空额度"的规格单独关进一个 project，让它排在全套最后。

```ts [playwright.config.ts]
projects: [
  { name: 'site', testIgnore: /rate-order\.spec\.ts/ },
  { name: 'drain', testMatch: /rate-order\.spec\.ts/, dependencies: ['site'] },
],
```

`site` 那一组里，端到端一共只有 6 次请求会碰额度（入口的两条、探针的三次、契约用例的一次），容量 10，谁也掏不空。`drain` 排在它后面，打空也无所谓——全套最后一条了。改完之后同一套命令的读数是 135 条通过、54 条跳过、0 失败（33 秒内）。

同一趟里 `drain` 打印的码序也跟着变了：

```
[码序] {"放行次数":4,"码":[503,503,503,503,429],"retry-after":"354"}
```

10 张牌减掉前面那 6 次，正好剩 4 张。要是断言写的是"第 11 次才 429"，这一趟就红了，而产品代码一行都没错——这就是这一层只钉码序、把绝对次数留给单位层的理由。

最短的那条也带一个坑：位置参数只过滤目标 project，**不过滤它依赖的 project**。`npx playwright test test/e2e/rate-order.spec.ts` 看着是跑一个文件，实际把 187 条一起跑了，打印还是 `Total: 189 tests in 43 files`。要单跑得点名 project 并关掉依赖：

```json [package.json]
"test:e2e:drain": "playwright test --project=drain --no-deps"
```

至于"容量 10、每 6 分钟补一张、第 11 次要等 360 秒"这些数字，钉在 `test/unit/rate-limit.test.ts`。那一层的 `takeToken` 收一个 `now` 参数，能把时钟拨来拨去，不需要真等六分钟，也没有别的规格跟它抢杯子。端到端这一层只钉码序——同一件事钉两遍，第二遍一定会变成负担。

## 撞上这些症状的时候

| 症状 | 不是这个原因 | 是这个原因 |
| --- | --- | --- |
| 探针回显的 `keys` 是 undefined | 探针接口坏了 | 同一趟运行里额度已被打空，这一位回的是 429 |
| 只想跑一个文件却跑出全套 | 命令写错 | 那个文件属于带 `dependencies` 的 project，依赖组不受位置参数过滤 |
| `retry-after` 不是 360 | 补牌间隔配错了 | 它是"距离补出一张牌还剩几秒"，桶刚被碰过就小于 360 |
| 格式错的请求回了 429 | 邮箱校验松了 | 入口把判格式和查额度这两步换过头尾了 |
| 429 的响应体里找不到编号 | 限流没写日志 | 那一条没走 `apiError()` 封装——裸抛的错误体连 `data` 这个键都没有 |

## 交付前自查

- 入口四句话的次序能在 30 秒内复述出来：判格式、查额度、才发信，前两步谁先谁后有端到端用例钉着
- 格式错的请求一张牌也不扣——这条不只是断言状态码，还看了 `data.code` 是不是 `EMAIL_INVALID` 而不是 `RATE_LIMITED`
- 打空额度的规格被单独关起来，全套跑完 0 失败，而不是靠跳过凑绿
- 绝对次数留在单位层，端到端只钉码序与形状

三件没做：券在超额度那次到底有没有落库，要连库数 `login_tokens` 的行数，本站没授权，标成读者待跑；`requestLoginLink` 里"拿不到来源地址就回 400 `IP_UNKNOWN`"那一条在本机量不到，本机每个请求都有地址；`drain` 这个 project 现在只有两条用例，桶跨进程不共享（多实例各数各的）依然量不到，那是讲规模的那一段的事。

仓库这一轮的永久改动：`test/e2e/rate-order.spec.ts` 重写为两条串行用例（打空额度、看掏空之后的码序）；`test/e2e/login-link.spec.ts` 里那条连着打到 429 的用例搬过去，本文件只留不碰额度的两条；`playwright.config.ts` 新增 `site` 与 `drain` 两个 project；`package.json` 新增 `test:e2e:drain`；`server/utils/http/rate-limit.ts` 新增 `ipBucketKey()`，IP 维的键收到一处（上一站收的是邮箱维）；`server/api/rate-check.get.ts` 改用它；`test/unit/auth-schema.test.ts` 从 14 条到 15 条，补上"失败时 `email` 是空串这个键的存在"。
