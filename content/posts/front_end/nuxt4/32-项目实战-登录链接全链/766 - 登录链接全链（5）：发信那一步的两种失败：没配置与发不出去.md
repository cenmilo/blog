## 屏幕上先出现的是 503

一台没配发信服务的机器上点"发送登录链接"，回的是 503、`data.code` 是 `MAIL_NOT_CONFIGURED`。前两站量过这一位（762 那条 `[同一条路]` 就是它）。这一站把发信那一步单独拆开：它三种结局各回什么、券留不留、以及第三种没人管过的失败。

发信层总共六十来行，三个出口都在里面：`sendLoginEmail` 在配置不齐时**返回**一个 `sent:false`，配置齐了就 `sendMail`，送不出去就**抛**。两种"没送成"的写法不一样，不是随手，下面会说。

## 三种失败分别落在哪

| 哪一种 | 谁先发现 | 接口回什么 | 那张券 | 人看到的 |
| --- | --- | --- | --- | --- |
| 没配 SMTP 或没配发信地址 | `requestLoginLink` 进来第一句就看配置 | 503 `MAIL_NOT_CONFIGURED` | 根本没生成 | "登录邮件暂时不可用，请稍后再试。" |
| 配了但送不出去（连不上、被拒、超时） | `sendLoginEmail` 抛回来 | 503 `MAIL_SEND_FAILED` | 生成了，又被撤掉 | "登录邮件暂时发不出去，请稍后再试。" |
| 连上了却一个字都不回 | 以前没人管，靠对端或浏览器 | 挂到 nodemailer 的默认超时才走到第二行 | 挂着的时候券在库里 | 按钮转圈，转两分钟 |

配置检查排在最前面是有意的：**没配置就不该去碰数据库**。这一层和 `useDb()` 那条口径一致——没配等于不发，而不是发一封假的。

## 为什么"没配置"绝不能回成功

发不出去的时候回一句"成功了"很诱人，因为它不报错、不让页面变红。但用户在屏幕上看到的是"链接已发出，请查收邮件"，然后一直等一封永远不会来的信。**接口说自己成功了，就是它替对方作了保**：收件箱里有没有信、点不点得开，都不归它管，它唯一知道的事实是"我没交出去"。

两种 503 都不泄露账号信息——它对任何邮箱都一样，这一条与上一站那条"存在与不存在走同一条路"是同一个纪律。失败原因只进日志，不进响应：SMTP 的报错文本里常带着主机名、端口，有时还带账号名。

## 第三种失败是配置里没人管的那一段

`getTransport()` 原来是这么写的：

```ts [server/services/auth/mailer.ts]
if (!transport) transport = createTransport({ url: smtpUrl })
```

一个时间上限都没设。装上的 nodemailer 是 10.1.1，它的连接层把三个默认值写在注释里（`node_modules/nodemailer/dist/cjs/smtp-connection/index.js:129-131`）：打招呼等 30 秒、建立连接等 2 分钟、连接静默等 10 分钟。那是给批量邮件队列准备的数字——队列没人盯着屏幕。而这里是**一个人正按着登录按钮**：防火墙放行、服务挂了的时候（不是拒绝连接，是连上之后不回话），他会看着转圈的按钮等满两分钟。这两分钟里，令牌桶已经扣过一张牌，券也已经落进库里。

本站把三个数写上去：

```ts [server/services/auth/mailer.ts]
export const SMTP_TIMEOUTS = { connectionTimeout: 5000, greetingTimeout: 3000, socketTimeout: 15000 }
```

超时之后 `sendMail` 抛出，走的正是第二行那条路：撤券、回 503 `MAIL_SEND_FAILED`。

## 量出来的两行

配置这一层用一条对照证明它不是空话：

```
[超时对照] {"本站":{"connectionTimeout":5000,"greetingTimeout":3000,"socketTimeout":15000},"写在实例上":{"connectionTimeout":5000,"greetingTimeout":3000,"socketTimeout":15000,"secure":false,"port":2525,"host":"127.0.0.1"},"没给时":{"secure":false,"port":2525,"host":"127.0.0.1"}}
```

"没给时"那一份里三个键压根不存在（默认值不在 `options` 上，是连接层内部兜的），所以这条断言读的是真东西。行为那一层需要一个不写字节的对端——TCP 握手成功、什么回应都没有：

```ts [test/unit/auth-mailer.test.ts]
const stall = createServer(socket => { sockets.push(socket) })
await new Promise<void>(resolve => stall.listen(0, '127.0.0.1', resolve))
```

跑出来的：

```
[黑洞对端] {"结果":"rejected","用时毫秒":3012,"报错":"Greeting never received"}
```

3012 毫秒，正好卡在 `greetingTimeout` 上。这条用例把 vitest 的默认 5 秒上限抬到了 30 秒（第三个参数），因为挂住的那种写法根本不会自己结束。

## 两次变异：三个旋钮不是同一个旋钮

改完就要问"这条用例真在看守吗"。第一次变异只把打招呼调到 12 秒：

```
[黑洞对端] {"结果":"rejected","用时毫秒":5010,"报错":"Greeting never received"}
AssertionError: expected { connectionTimeout: 5000, …(5) } to match object { connectionTimeout: 5000, …(2) }
      Tests  1 failed ／6 passed (7)
```

**用时不是 12 秒，是 5 秒**——连接的总预算先到。包内那句 `Math.min(this.options.greetingTimeout || GREETING_TIMEOUT, 剩下的 connectionTimeout)` 就是原因。所以红的只有配置那条，行为那条照样绿。

第二次变异把两个都调到 20 秒：

```
[黑洞对端] {"结果":"rejected","用时毫秒":15012,"报错":"Timeout"}
AssertionError: expected 15012 to be less than 9000
      Tests  1 failed ／6 skipped (7)
```

15 秒，是那个**静默**上限（`socketTimeout`）在起作用。三次读数放在一起才是结论：三个旋钮各管一段（建连、打招呼、连接上没动静），只调一个看不出另外两个在兜底，而默认值是 30 秒／2 分钟／10 分钟。

## 券不留下来这一条，是怎么测的

`login-link.test.ts` 里六条用例名就是这个矩阵：`配置齐、发送成功：落一张券、发一封信、不撤券、也不查 users`、`没配 SMTP：503，而且一张券都不落（不发就不留空券）`、`发送抛错：先撤券再回 503，库里不留半成品`、`发送层说"没发"（配置不一致的兜底）：同样撤券`、`拿不到来源地址：400，也不落券`、`响应常量里没有任何账号信息`。

第四条那一手值得停一下：`sendLoginEmail` 唯一的 `sent:false` 是"配置不齐"，而配置在上一层已经查过了，所以这里收到 `sent:false` 只可能是两层看到的东西不一致。代码没有把它当成功咽下去，而是抛一句 `sendLoginEmail() 在未配置检查之后回了 not_configured`。**"这个分支理论上到不了"不等于"到了以后随便处理"**。

## 撞上这些症状的时候

| 症状 | 先看哪一位 | 为什么 |
| --- | --- | --- |
| 点了没反应，转圈很久 | `createTransport` 有没有带超时 | 默认值是 2 分钟与 10 分钟那种量级 |
| 每次都 503 但日志里没有 SMTP 报错 | 配置检查那句 | 压根没走到发信，`MAIL_NOT_CONFIGURED` |
| 报"暂时发不出去"但稍后再点就好了 | SMTP 端点抖动 | 超时是被拒的一种，撤券让下一次重新生成 |
| 收到邮件但链接点不开 | 库里那张券还在不在 | 发送失败会撤券，旧邮件里那条也随之作废 |
| 日志里出现 `login_mail_failed` | 那行的 `reason` | 原因只进日志，响应里被换成人话 |

## 交付前自查

- 三种失败各回什么码、撤不撤券，能用一条 503 的 `data.code` 分开说清
- 没配置时不碰数据库，也不发一封假的
- 发信有时间上限，超时的处理路径与"被拒"是同一条
- 三条用例都能被变异打红，包括那条测时间的

三件没做：**真发出去的那条路要一个真能收信的地址**，本站用本地替身测到"会话走完、`messageId` 有值、正文里那串明文哈希后等于库里的摘要"，真实邮箱的送达（进不进垃圾箱、SPF/DKIM 对不对）只能拿真域名测，留给上线那一段；`MAIL_SEND_FAILED` 之后要不要给用户一个"重试"按钮、重试是否重新占一张牌，是产品决定，本站只保证旧链接作废；发信失败的次数有没有进计量表，本轮没量。

仓库这一轮的永久改动：`server/services/auth/mailer.ts` 新增导出的 `SMTP_TIMEOUTS` 三个数并传给 `createTransport`；`test/unit/auth-mailer.test.ts` 从 5 条到 7 条（配置对照一条、黑洞对端一条），文件头那句指向内部文档的说法改成自解释。单位层 `27 passed (27)`／`199 passed (199)`，其中这一份文件 `7 tests`、3238 毫秒（那 3 秒是黑洞对端等着超时等出来的）。
