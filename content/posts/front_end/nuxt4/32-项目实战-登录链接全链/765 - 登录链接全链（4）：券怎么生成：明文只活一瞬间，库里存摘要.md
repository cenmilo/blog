## "看代码像是没进库"不是证据

`server/services/auth/token.ts` 里发券那一段只往库里交四位：

```ts [server/services/auth/token.ts]
const [row] = await useDb()
  .insert(loginTokens)
  .values({ email: params.email, tokenHash, expiresAt, createdIp: params.ip })
  .returning({ id: loginTokens.id })
```

`values()` 里没有 `token`，明文只出现在函数最后 `return` 的那个对象里。读到这儿你可以放心，但这一页代码没有告诉你两件事：**发给数据库的那句话长什么样**，以及**有没有别的地方也在发券**。这一站把这两个问题都变成能跑出来的东西。

## 三个数字先说清

- 32：`randomBytes(32)` 取 32 个随机字节，也就是 256 位熵。这个强度下没有"猜一猜"的空间，所以摘要用 sha256 就够了——慢哈希（bcrypt 那一类）防的是低熵口令被批量试，防随机数没有意义。
- 64：字节转十六进制，一个字节写成两个字符，所以明文和摘要都是 64 个字符。它们长度一样，形状也一样（都是 `[0-9a-f]`），肉眼分不出来。
- 900：有效期秒数，`TOKEN_TTL_SEC = 15 * 60`。过期时刻是发券那一刻算好绑进语句的参数，不是数据库自己算的。

## 手搓的假库不会把 SQL 渲染出来

`test/unit/` 里原来那两个文件用的假 `useDb()` 是一串手搓的链：记下 `values()` 收到过什么对象、`set()` 收到过什么键。它够用来证明"明文没被传进去"，但它**不会把 `where` 里的条件拼成一句话**——因为拼句子的活儿在 drizzle 里面，而手搓的链没有那一层。

要看见句子，就把假的东西换到更下面一层：`useDb()` 返回真的 drizzle 实例，底下挂一个只抄录不执行的 client。

```ts [test/unit/token-sql.test.ts]
function useRecordingDb (rows: unknown[]): Recorded[] {
  const log: Recorded[] = []
  const client = {
    query: async (query: unknown, params: unknown[] = []) => {
      log.push({ text: typeof query === 'string' ? query : (query as { text: string }).text, params })
      return { rows }
    },
  }
  ;(globalThis as Record<string, unknown>).useDb = () => drizzle(client as unknown as Client, { schema })
  return log
}
```

能这么做是因为 drizzle 的执行路径就一行：`node_modules/drizzle-orm/node-postgres/session.js:113` 是 `client.query(rawQuery, params)`——语句与参数在这一位已经渲染完了。所以我们读到的是数据库将要执行的那一句话本身，而一次库连接都没有建立。

## 读出来的第一句：发券

```
[发券 SQL] {"text":"insert into \"login_tokens\" (\"id\", \"email\", \"token_hash\", \"expires_at\", \"used_at\", \"created_ip\") values (default, $1, $2, $3, default, $4) returning \"id\"","params":["demo@example.com","8873a2de87dd6c81d052df5b9101744102f73a353a30e67d917fa23aa6209a6e","2026-10-17T20:12:41.218Z","::1"]}
```

这一句里有四个信息：

1. 参数第二位是那 64 位摘要。整条语句连参数一起序列化之后搜不到明文——而明文确实存在：`buildLoginLink('https://example.com', issued.token)` 里就有它，这是那条"搜不到"的正对照，否则一次都没生成的话，零命中什么都证明不了。
2. `id` 与 `used_at` 写的是 `default` 关键字，不是 `null`。前者走库里的 `gen_random_uuid()`，后者是列默认值，含义是"还没被用过"。
3. 过期时刻以 `2026-10-17T20:12:41.218Z` 这种带 `Z` 的形式绑上来。列本身在迁移里是 `timestamp with time zone`（`db/migrations/0001_core_tables.sql:33`），存的是绝对时刻，不是一段本地挂钟。
4. 这张表没有 `created_at` 列：发券时间没记，只记"什么时候过期"和"什么时候被用过"。

顺带一个容易忽略的对照：库里另外几张表的 `created_at` 是 `DEFAULT now()`，那个时刻来自数据库的时钟；而 `expires_at` 和 `used_at` 两位是应用算好绑上去的。**同一行里两种时钟并存**，判断券有没有过期用的两个值（写进去的那个和比对它的那个）都出自应用这一侧，所以不会因为我们没测数据库时钟而漂掉。

## 读出来的第二句：占券

```
[占券 SQL] {"text":"update \"login_tokens\" set \"used_at\" = $1 where (\"login_tokens\".\"token_hash\" = $2 and \"login_tokens\".\"used_at\" is null and \"login_tokens\".\"expires_at\" > $3) returning \"email\"","params":["2026-10-15T00:00:00.000Z","ffe054fe7ae0cb6dc65c3af9b61d5209f439851db43d0ba5997337df154668eb","2026-10-15T00:00:00.000Z"]}
```

三位条件都在同一条 `UPDATE` 里：摘要相等、没用过、没过期。改到行才算占到，所以"同一枚链接点两次"这件事不需要任何竞争窗口。参数第二位是摘要而不是明文——链接里那串明文从来不会作为查询条件发给库。

值得盯的是 `>` 这个符号。写成 `>=` 的话，正好卡在过期那一瞬间的点击还能兑换成功，而这条规则以前**没有人在看**：`token.ts` 里另有一个 `isTokenExpired(expiresAt, now)`，用的正是"等于也算过期"的判断，它有 3 条用例，然后**生产代码里一处都没调用它**（把两个文件名一起 grep，命中只有它自己的定义和那 3 条用例）。

本站把比较符改成 `gte` 跑了两趟。补断言之前：

```
Test Files  25 passed (25)
      Tests  191 passed (191)
```

规则改了，全套绿。补上那条读 SQL 的用例之后，同一处改动：

```
FAIL  test/unit/token-sql.test.ts > 占券那条 UPDATE > 三个条件都在，过期用的是严格大于
AssertionError: expected 'update "login_tokens" set "used_at" =…' to match /"expires_at" > \$\d/
      Tests  1 failed | 194 passed (195)
```

于是这一步的清理是：删掉那个没人用的 JavaScript 判定函数，把断言挪到真正发出去的那句话上。**一条规则有两个地方能改，就等于没有规则**——这句在 763 讲的是限流键，这里讲的是过期。

## 还有一道门也能发券

`.nuxt/types/nitro-routes.d.ts:51` 注册着这么一条地址：`'/api/token-demo': { 'post': … }`。它是早期留下的本地探针，直接 `import` 签发机器，自己落一行券、自己把邮件交出去。问题是它前面没有上一站那条闸门——把两个文件放在一起数：

```
server/api/auth/login-link.post.ts:3
server/api/token-demo.post.ts:0
```

（数的是 `assertRateLimit` 出现的次数，注释也算，所以那条入口是 3。）也就是说：**同一种副作用，一条路上有令牌桶，另一条路上没有。** 而 764 那两条端到端用例只跑在有桶的那条路上，所以整套测试对这道门一无所知。

这一站的处置分两步。能给的答案先给：给它装上同一道闸门（判格式之后、发券之前），并新增一份 `test/unit/token-surface.test.ts`——它扫 `server/api/` 与 `server/routes/` 下每个文件，凡是直接引到签发机器的，就必须带 `assertRateLimit(`，而且位置在 `parseLoginLink(` 之后。第一次跑它点名：

```
[能直接签发券的对外地址缺闸门的] ["server/api/token-demo.post.ts"]
      Tests  1 failed | 2 passed (3)
```

装上闸门之后同一份检查打印空名单，`27 passed (27)`、`197 passed (197)`。

至于这条探针地址本身要不要留着，那是另一个决定：它比正式入口多回三样东西（行号、摘要、精确过期时刻），而这些都是匿名调用者拿得到的。本站想把它删掉，`rm` 被工具的安全层按"破坏性命令"拦下，没有绕道——文件全文留在这轮的工程记录里，删与不删由人拍板。**守卫先立住了**：以后谁再开一条能发券的地址，忘装闸门就会红。

## 第三个发现：64 是抄来的，不是推来的

`server/services/auth/verify.ts` 里那道形状闸门写着 `/^[0-9a-f]{64}$/`，而它上面那行注释说"长度由 `TOKEN_BYTES` 决定"。这句话当时是假的：那个 64 是手抄的字面量。

把 `TOKEN_BYTES` 改成 16 跑一趟，就能看出抄来的代价：

```
FAIL  test/unit/auth-mailer.test.ts > …邮件里的明文，sha256 之后正好等于写进库里的那位摘要
FAIL  test/unit/auth-token.test.ts > generateToken() > 32 字节随机数转十六进制 ⇒ 长度是位数×2
FAIL  test/unit/auth-token.test.ts > issueLoginToken() > 返回的明文与摘要是两个不同的串
      Tests  3 failed | 194 passed (197)
```

三条红都在"长度"那一侧，**唯独 `isTokenShape()` 的用例是绿的**——因为它比的是自己写的 64 位字面量。也就是说这个改动在测试里呈现为"生成器变短了"，而闸门还在要求 64 位；真跑起来的症状是每一封邮件里的链接都换回 401。

改法是不再抄：

```ts [server/services/auth/verify.ts]
const TOKEN_SHAPE = new RegExp(`^[0-9a-f]{${TOKEN_BYTES * 2}}$`)
```

改完先用原样重跑一遍：`197 passed (197)`，那 7 条形状断言一条没动就过了，说明行为没变。再把 `TOKEN_BYTES` 改成 16 跑第二趟，名单多出一条：

```
FAIL  test/unit/auth-verify.test.ts > isTokenShape() > 只收 64 位小写十六进制
      Tests  4 failed | 193 passed (197)
```

现在两处会一起动。**能推出来的数字就别抄第二遍**，抄了就要靠一条"两个数字必须相等"的用例来圆，而那条用例本身也还是抄的。

## 撞上这些症状的时候

| 症状 | 先怀疑 | 先看的一处代码 |
| --- | --- | --- |
| 邮件里的链接点了就 401 | 明文形状与生成器长度对不上 | `isTokenShape` 里的长度是不是写死的 |
| 改了过期规则，测试全绿 | 断言读的是不是那句 SQL | `token-sql.test.ts` 有没有覆盖这条路径 |
| 额度明明没到却收不到 429 | 有别的地址也在发券但不计数 | `token-surface.test.ts` 的名单 |
| 备份里翻出 64 位十六进制串 | 那是摘要还是明文 | 摘要与明文同形同长，只能回到生成处对 |
| 过期时刻看着差了几小时 | 是不是把 `timestamp` 当成 `timestamptz` 读了 | `db/migrations/0001_core_tables.sql:33` |

## 交付前自查

- 发券那条语句里出现的凭据只有摘要，明文既不在句子也不在参数里，并且带一条正对照证明明文确实存在
- 过期判定只剩一处能改，另一处（那个 JavaScript 函数）已经删净，`grep` 命中 0
- 每一个能碰到签发机器的对外地址都被同一份检查要求带闸门
- 长度这一位从常量推出来，不再抄第二遍

三件没做：库里那一行真正长什么样（`used_at` 是不是 `default` 落成了 NULL、摘要撞唯一约束时的报错形状）要连库才数得到，本站连库授权问到第十四次仍无答复，全部留成读者的动手步骤；`token-demo` 这条地址删不删等人拍板；探针地址回不回那三样内部信息，本站只装了闸门、没改响应形状。

仓库这一轮的永久改动：新增 `test/unit/token-sql.test.ts`（4 条）与 `test/unit/token-surface.test.ts`（3 条）；`server/services/auth/token.ts` 删掉没人用的 `isTokenExpired`、文件头第三条边界改写成"判定只在占券那句 where 里做一次"；`server/services/auth/verify.ts` 的形状闸门改成从 `TOKEN_BYTES` 推、文件头那句"比较用的是应用给的时刻"补上；`server/api/token-demo.post.ts` 装上令牌桶；`test/unit/auth-token.test.ts` 从 12 条到 11 条（删掉那条测了个没人用的函数的用例）。单位层从上一站的 `25 passed (25)`／`191 passed (191)` 走到 `27 passed (27)`／`197 passed (197)`，运行时层仍是 5 个文件／14 条（这一轮没动它），`npm run check` 八项全通过。
