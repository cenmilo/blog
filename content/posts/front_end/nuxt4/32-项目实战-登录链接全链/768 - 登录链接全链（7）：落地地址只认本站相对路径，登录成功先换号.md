## 那个参数是外面带来的

`/api/auth/verify` 成功之后要落地，落到哪儿由查询串里的 `redirect` 决定。这个参数的可怕不在"跳走了"，而在**它是请求里带的**：攻击者把 `redirect` 换成他的站点，用户点完邮件链接直接被送过去，而跳转前一刻地址栏还是本站——伪装成本极低。这类漏洞有个名字：开放重定向。

`server/utils/http/safe-redirect.ts` 只有 41 行，判据是两条加一个等式：

```ts [server/utils/http/safe-redirect.ts]
const trimmed = raw.trim()
if (trimmed === '' || trimmed[0] !== '/') return fallback
// 第二个字符是 `/` 或 `\` 就是"协议相对"或"反斜杠归一"两种 off-site 写法
if (trimmed[1] === '/' || trimmed[1] === '\\') return fallback

try {
  const target = new URL(trimmed, siteUrl)
  // 复算 origin：兜住上面两条规则之外的任何新写法，规则清单不是安全边界，等式才是
  if (target.origin !== new URL(siteUrl).origin) return fallback
  return `${target.pathname}${target.search}${target.hash}`
} catch {
  return fallback
}
```

## 黑名单会漏，等式不会

`//evil.com` 与 `/\evil.com` 这两种写法第一眼像本站的相对路径，实际都不是：拿本机 Node 的 `new URL()` 一算，两者的 host 都是 `evil.com`。前一条是**协议相对**（`//` 开头就继承当前页的协议），后一条是浏览器把反斜杠归一成斜杠。所以第二道判据要单独看第二个字符，而最后那道 `origin` 复算是兜底——它不关心你想到没想到某种写法。

`test/unit/safe-redirect.test.ts` 里 13 条用例钉住的就是这些形状，几条值得单独看的：

- `/a?next=//evil.com` **照原样放行**（本站路径带着一个查询参数，参数里那个 `//` 不参与解析）——把黑名单当判据的实现会误杀这一条。
- `/%2F%2Fevil.com` 放行，且**不做二次 percent 解码**：解析后的 pathname 还是 `/%2F%2Fevil.com`，留在本站；解码反而把无害输入判成有害、把合法路径改坏。
- `/a\r\nX-evil: 1` 变成 `/aX-evil:%201`——换行进不了响应头，因为返回的不是原样字符串，是解析后的 `pathname + search + hash`。
- `['//evil.com']`（同一参数出现两次时 `getQuery` 给的是**数组**）退回首页；"取第一个"是常见的错写法。
- 空串与 `/` 同一条路，都回 `/`；非字符串一律走兜底。

先 `trim()` 也是同一个思路：URL 标准自己会剥首尾空白与控制字符，你不剥，就等于你和浏览器各算各的。

## 它接在哪几根线上，本轮才第一次有人管

这道闸门有 13 条用例，但"谁用了它"没人管。调用点是两处：登录链接那条 `verify.get.ts`，和 GitHub 回调 `callback.get.ts`。**"两处共用一个函数"是当下的事实，不是约束**——第三条路上有人写 `String(query.redirect)`，那 13 条一条都不会红：它们测的是函数，不是接线。

本轮补一份 `test/unit/redirect-surface.test.ts`（三条），扫 `server/` 下所有 `.ts`：凡是读到 `redirect` 这个查询参数的文件，必须同时调用 `safeRedirectTarget(`；第二个参数必须是本站地址（`public.siteUrl`），不许是请求带来的 `host`。跑出来：

## 登录成功先换号：cookie 四个属性一个都不能省

会话号在 `server/utils/http/session-cookie.ts` 里发出。`useCookie` 那一节的参数表给的默认值是：`httpOnly` 为 `false`、`secure` 为 `false`、`sameSite` 不写、`path` 为 `/`。**"什么都不写"得到的是一条页面 JS 读得到、http 明文照发、跨站也带着走的 cookie**，而 sid 恰恰三条都不能要。所以四个属性全写：

```ts [server/utils/http/session-cookie.ts]
const shared = { sameSite: 'lax' as const, path: '/', secure, maxAge: SESSION_MAX_AGE_SEC }
setCookie(event, SID_COOKIE, sid, { ...shared, httpOnly: true })
setCookie(event, CSRF_COOKIE, csrf, { ...shared, httpOnly: false })
```

两道差别只在最后一位：`csrf` 必须让页面 JS 读得到，双提交要拿它和请求头比；`sid` 关门。

`secure` 这一位是按本次请求的协议算的（`getRequestProtocol(event, { xForwardedProto: true }) === 'https'`），不是写死 `true`：写死之后本地 `http://localhost` 上的浏览器会直接把它丢掉，症状是"服务端明明回了 Set-Cookie，下一个请求却没有"。而 curl 不受这条限制——**本地用 curl 测得通、浏览器测不通**，两态各有一条端到端钉着。

换号换的是什么：

```ts [server/api/auth/verify.get.ts]
const staleSid = readSessionId(event)
const { sid } = issueSessionCookies(event)
try {
  await rotateSessionRow({ staleSid, newSid: sid, userId })
} catch (error) {
  clearSessionCookies(event)
  // 一句 503：SESSION_CREATE_FAILED
}
```

`staleSid` 是登录前浏览器里那个号（本站的演示接口发过、或者任何人能预测到的值），`sid` 是刚生成的 `randomUUID()`。作废旧号与写新行**在同一个事务里**：分成两条语句时，中间失败的样子是"旧号已删、新行没写"，浏览器里的 cookie 指向一条不存在的会话，而那枚券已经被写上 `used_at`——用户手里那条链接就此报废，只能重新申请。事务把两件事绑成一件：要么都成立，要么旧号还在（这个人至少还是登录状态）。

写库失败时上面那个 `catch` 还会把刚挂上的 cookie 撤回：库里没有对应行的会话号，绝不能留在任何人的浏览器里。会话行的 `expires_at` 与 cookie 的 `Max-Age` 同源于 `SESSION_MAX_AGE_SEC`（30 天），这一条有用例钉着——两边各写一遍天数，迟早一边改了一边没改。

## 为什么是 302 而不是 301

成功那一路最后一步是 `sendRedirect(event, target, 302)`。用 301 的话浏览器会**缓存这次跳转**：用户下次再点同一条链接（重放、或者从邮件客户端里再点一次），根本不会问到服务器，直接被带到那个被记住的落地地址。而这条地址里带着一次性凭据，重放本来就该得到 401——缓存会让"该被拒绝的点击"看起来仍然可用。

同一条响应在函数第一行就写了两位头：`cache-control: no-store` 与 `referrer-policy: no-referrer`。前者管这条带凭据的响应不进缓存，后者管浏览器不把完整地址（连 token）当来源带给下一站——落地路径是外面带来的，去向可能是别人家的站点。

## 撞上这些症状的时候

| 症状 | 先看哪一位 | 为什么 |
| --- | --- | --- |
| 登录后落到别人的站点 | 那一路有没有过 `safeRedirectTarget` | 单测只测函数，接线没人管 |
| 本地登录成功、刷新就掉线 | cookie 的 `secure` 是不是写死 true | http://localhost 上浏览器会直接丢弃 |
| 点了没反应，服务端却回了 Set-Cookie | `path` 写与删是否一致 | 删除靠同名同 path 同域、Max-Age=0 那条 Set-Cookie |
| 同一条链接第二次点也成功 | `Location` 有没有被缓存 | 301 会被记住，跳转不再经过服务器 |
| 合法的 `/me?tab=x` 被换成首页 | 判据是不是黑名单 | 参数里的 `//` 不参与 origin 解析 |

## 交付前自查

- 落地判据是"等式"而不是清单，且清单两条各自有用例、等式那条也有一组写法兜着
- 每一个读到 `redirect` 的文件都被静态检查要求过闸门，且这条检查自己做过变异验证
- cookie 四个属性显式写出，`secure` 按协议而不是常量；`sid` 与 `csrf` 的差别只有一位
- 登录一定换号，换号的两条语句在一个事务里，失败时撤回刚发的 cookie
- 成功用 302，带 `no-store` 与 `no-referrer`

三件没做：**真库上"登录前后不是同一个 sid、旧号从这一刻查不到"是带库那一档的读数**，本站没拿到连库授权，只跑到"形状对但没配库 ⇒ 503"那一位；`Location` 头的最终形态（nitro 会把相对路径原样发出还是补成绝对地址）需要真成功一趟才知道，本轮没测；`/console` 那条路以后要不要允许带 `redirect`（现在它只从登录链接进来），是产品决定，没做。
