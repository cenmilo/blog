## 从首页点进文档区，那一趟还在

`test/e2e/payload.spec.ts` 里有一条监听请求的判据：打开首页、点导航里的"文档"，把期间发出去的地址收下来。四档配置各跑一趟，`seen` 那一位读回来的是同一件事：

```
[payload nav] {"mode":"default","seen":["/_payload.json?_b=48af9dd0-6394-4251-89f2-d7d0df346e78","/api/docs"],"warnings":[]}
[payload nav] {"mode":"false","seen":["/api/docs"],"warnings":[]}
```

`/api/docs` 在**每一档都出现**。而那句常被引用的话是"数据会加进负载，好让页面在水合时不重新取一遍"——两句话摆在一起，就是这一站要量清的东西：**"不再发一趟"是有条件的，而条件不在取数写法上。**

## 官方给的是两处，不是一处

第一处在那个实验开关本身。讲 experimental features 的那一节把 `payloadExtraction` 的三种取值写成：

- `'client'`：服务端渲的那一份把负载内联进 HTML，客户端导航用的才抽成 `_payload.json` 文件
- `true`：两种场合都抽成独立文件
- `false`：完全不抽，负载一直在 HTML 里，也不生成 `_payload.json`

同节还有一句：默认是 `true`，设了 `compatibilityVersion: 5` 时默认是 `'client'`；`ssr: false` 时被强制成 `false`。

第二处是那一位默认实现。讲 `useAsyncData` 与 `useFetch` 的那两节给的同一段代码是：

```ts
const getDefaultCachedData = (key, nuxtApp, ctx) => nuxtApp.isHydrating
  ? nuxtApp.payload.data[key]
  : nuxtApp.static.data[key]
```

正在接手服务端那份 HTML 时读负载，过了那一段时间之后读内存里那份。紧接着的限定就是本文标题里那个条件句：**只有开着 `experimental.payloadExtraction` 时这份缓存才生效**。

## 四档各跑一趟，量到五件事

本站的实验台是几站前接好的：`nuxt.config.ts` 里读 `NUXT_PAYLOAD_MODE`，**没设这个环境变量时整一位不写**（写 `undefined` 与"不写"在这条路上不等价，直接给默认值就把 Nuxt 自己的默认藏掉了）。四趟的读数：

```
[payload home] {"mode":"default","bytes":5044,"inlinedData":true,"referencesFile":true,"fileOnDisk":true}
[payload home] {"mode":"client","bytes":4920,"inlinedData":true,"referencesFile":false,"fileOnDisk":true}
[payload home] {"mode":"true","bytes":5044,"inlinedData":true,"referencesFile":true,"fileOnDisk":true}
[payload home] {"mode":"false","bytes":4920,"inlinedData":true,"referencesFile":false,"fileOnDisk":false}
[payload 对照] {"mode":"false","ghostStatus":404,"ghostType":"text/html;charset=utf-8","realStatus":404,"realType":"application/json"}
```

一、**"不写这一位"与写 `true` 逐字节相同**（都是 5044、都引用文件、产物里都有那份文件）。这一位默认值就是 `true`，本机没设 `compatibilityVersion: 5`，所以不是 `'client'`。这条读数是本站唯一能给"默认值是多少"这个答案的方式——问的是产物，不是猜文档措辞。

二、`'client'` 与 `false` 的**首屏 HTML 一模一样长**（4920，都不引用文件），差别在产物里有没有那些文件：`client` 有（`fileOnDisk:true`）、`false` 没有。这正是那句定义的样子：初始那一份都内联，`'client'` 只是把**导航用的**那份另存成文件。

三、`false` 档里 `_payload.json` 这个地址本身回 404（`realStatus:404`，媒体类型仍是 json）。同一条判据在另三档读到的是 200。所以"有没有载荷文件"是能直接问出来的，不用靠配置文件。

四、**四档共同的底线守住了**：SSR 那份 `/docs` HTML 里就有 `<h1>文档</h1>` 与两条链接（`bytes:3043` 一档不变）。开关只该影响"客户端要不要再取一次数"，不该让服务端渲空——那条判据就是钉这件事的。

五、回到开头那个问题：为什么四档都还发 `/api/docs`？判据的注释里已经写过原因，本站复跑仍然成立——**`/docs` 既没被预渲染、也没进缓存**，所以产物里根本没有 `docs/_payload.json` 这份东西（运行时那个地址回的是页面兜底）。没有可用载荷，客户端导航就只能自己取一遍。断言钉的是这个现状：哪天有人把 `/docs` 改成预渲染或加上缓存路由，这条会红，那时"少跑一次取数"才轮到它出场。

顺带一条与首页有关的事：`default`／`client`／`true` 三档的 `seen` 里都有一条 `/_payload.json?_b=<编号>`，`false` 档没有。那一位是预取——讲 `NuxtLink` 的那一节写着一进视口就会预取"组件与载荷文件"，首页是预渲染页、有载荷文件可取，于是点击之前就先来了一趟。它不属于这次导航，预取本身另有判据钉着；而 `false` 档没有文件可预取，那条自然消失。

## 运行层：两支插槽与两条"不发一趟"

端到端量的是交付形状，**"读哪一支插槽"得换一层**。上一站立好的那双会记数的脚继续用，但这一份判据要的正好是"命中"，所以缓存位不钉死，用默认那一位。

先量前提：这一层 `nuxtApp.isHydrating` 读到的是假，读数原样是 `[载荷·水合那一位] {"趟数":1,"读到":"{\"metrics\":{\"total\":8888,\"kinds\":[{\"kind\":\"login\",\"count\":1}]}}","负载里有那一位":false,"正在水合":false,"静态位有那一位":false}`。三元式于是走后半支——读 `static.data`。把同一份数据分别种进两支插槽，差别当场出来：

```
[载荷·两支插槽] {"种负载":{"正在水合":false,"趟数":1,"读到":"{\"metrics\":{\"total\":8888,\"kinds\":[{\"kind\":\"login\",\"count\":1}]}}"},"种静态位":{"趟数":0,"读到":"{\"metrics\":{\"total\":5,\"kinds\":[{\"kind\":\"from-payload\",\"count\":1}]}}"}}
```

种进负载那一支照样发一趟，种进静态位才一趟不发、而且读到的是插槽里的 `total:5`（假脚回的是 8888，读到 5 就不可能是自己取的）。这正是三元式的可读形式：场合决定读哪一支。

自定义那一份还能看到来什么实参：

```
[载荷·实参] {"收到":[{"第几位":"ctrl:ph-args","静态位有值":true,"起因":"initial"}],"趟数":0}
```

第一位是**解析后的键**（不是写进去的选项），第三位带着 `cause`。要读哪一支插槽、什么时候拒绝缓存，都由这一位自己定——上一站那句"把缓存钉成永远未命中"就是通过它做到的，本站也复跑了一次：`[载荷·被覆盖] {"静态位有那一位":true,"趟数":1,"读到":"{\"metrics\":{\"total\":8888,\"kinds\":[{\"kind\":\"login\",\"count\":1}]}}"}`，插槽里明明有那份数据，覆盖了就照样重取。

**最后一条是给上一站纠错的。** 上一站把"同一个键第二次挂载一趟都不发"记成"键缓存跨挂载还在"，读起来像是命中了 `static.data`。这一站把它量窄了：

```
[载荷·第二次挂载] {"第一次":1,"第二次":0,"静态位有那一位":false,"第二次读到":"{\"metrics\":{\"total\":8888,\"kinds\":[{\"kind\":\"login\",\"count\":1}]}}"}
```

第二次确实一趟都不发，但 `static` 插槽是空的。所以它不是 `getCachedData` 命中的，而是同一个键上那份已经跑完的条目被直接复用——连查询这一步都没走。两条路都能让趟数变 0，区别是可验的：**只有插槽那条能被 `getCachedData: () => undefined` 覆盖掉**，条目复用那条覆盖不掉。

结论写成一句给读者的话：`data` 明明已经在负载或插槽里，页面上却重取一遍——先分清是哪一条路，再决定改哪一位。

## 撞上了去哪里看

| 撞上的现象 | 大概率是哪一位 | 先看哪里 |
| --- | --- | --- |
| 站内点进某一页还是打了接口 | 那一页没有可用载荷（没预渲染、没缓存） | 问 `那个地址/_payload.json` 是不是 404 |
| 首屏 HTML 里找不到数据 | `ssr: false`（开关被强制成 `false`） | `[payload home]` 那一行读数 |
| 换了 `payloadExtraction` 值、HTML 字节没变 | 默认与 `true` 本来就同档 | 四趟读数对表（5044／4920） |
| 插槽里有数据却还重取 | 写了自定义 `getCachedData` | `[载荷·被覆盖]` 那条的形状 |
| 第二次挂载不发但插槽是空的 | 复用的是同键的条目 | `[载荷·第二次挂载]` |

## 交付前自查

- "不再发一趟"被拆成两个条件：交付形状在端到端层量（四档各一趟），读哪一支插槽在运行层量（种两支插槽对照）
- **默认值这一位是问出来的不是猜的**：不写与写 `true` 逐字节相同，且本机没设 `compatibilityVersion: 5`
- 上一站那条归因被本站收窄，并且给了可验的区别（覆盖得掉与覆盖不掉）
- `/docs` 每次都取这件事写清了原因与"哪天会红"，没写成 Nuxt 的行为缺陷
- `warnings` 那一位四档都是空数组：开关没有制造水合不匹配
