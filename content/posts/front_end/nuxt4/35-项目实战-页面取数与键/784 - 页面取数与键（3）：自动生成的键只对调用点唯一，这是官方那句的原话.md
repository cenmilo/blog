## 那句被引用一半的话

上一站把键锁进了出口：页面和面板两块都调 `useConsoleMetrics`，锁死的键让它们合起来只发一趟。于是很自然地要问下一句——**不写键的时候呢？**

流传最广的版本是"自动生成的键只对调用点唯一，同一个 URL 在不同组件里各取各的"。讲 `useFetch` 的那一节原文有两半，第二半经常被省掉：

> The auto-generated key is unique to each call site, so calling `useFetch` with the same URL and options in different components will **not** share state and each call performs its own request.

> Multiple instances of the same component do share state, since they use the same call site. To share the same `data`, `error` and `status` refs across different components, provide the same explicit `key` to each call

三个断言，一个比一个反直觉：不同组件 ⇒ 各发一趟；**同一个组件的多个实例 ⇒ 共享**；要跨组件共享那几个 ref ⇒ 每次调用给同一个显式 `key`。

## 键这串字符怎么读出来

`useFetch` 不写键时，那串键是内部算出来的，调用点什么都看不见。上一站已经量过形状：`"$f" + hashKey(...)`，而记数的假脚收到的选项里**没有这一位**（读数是 `键:"(没给键)"`）。

要看到键本身，得换一位入口：`getCachedData(键, nuxtApp, 上下文)` 的第一个实参就是**解析后的键**，无论它来自显式 `key` 还是自动生成。于是判据里同时干两件事——把这一位钉成"永远未命中"（上一站记过：默认那份会让一次调用发两趟），顺手把键记下来。

```ts [test/nuxt/auto-key-scope.test.ts]
const impl = async () => {
  seen.趟数 += 1
  return { metrics: { total: seen.趟数, kinds: [{ kind: 'login', count: seen.趟数 }] } }
}
const pin = (extra: Record<string, unknown> = {}) => ({
  $fetch: impl as never,
  getCachedData: (key: string) => {
    seen.键.push(key)
    return undefined
  },
  ...extra,
} as never)
```

三条官方断言各一条判据，读数原样：

```
[自动键·两个调用点] {"趟数":2,"键":["$fnsmk7hs765az","$f3n6qj8xq8l71l"]}
[自动键·同一调用点两遍] {"趟数":1,"记到的键":["$f1lvb0ceievaop"],"两遍读到的值":["1","1"]}
[自动键·同组件两实例] {"趟数":1,"记到的键":["$f24zdgt0p2sljy"],"两实例读到的值":["1","1"]}
[自动键·显式同键对照] {"趟数":1,"记到的键":["ctrl:ab-shared"]}
```

第一行是"不同调用点 ⇒ 两趟"，两串哈希各不相同。第二、三行是那句被省掉的后半：同一个调用点跑两遍、同一个组件挂两次，都只有一趟，两遍读到的还是同一个值。**第四行是上一站那个"坑"的正解**：同一个键第二次挂载一趟都不发，不是缓存串了读数，而是它们本来就共用同一个键位。

## 什么算"调用点"：写错一行，量的就不是你想量的东西

"换 query 会不会变成两趟"这个实验，第一版我是这么写的：

```ts
await useFetch(ENDPOINT, pin({ query: { page: 1 } }))
await useFetch(ENDPOINT, pin({ query: { page: 2 } }))
```

两趟——看着像"query 进了键"。但这是**两行代码，本来就是两个调用点**，键必然不同，跟 query 一点关系都没有。这条判据当时什么都没证明。

改成同一个调用点跑两遍（`useFetch` 只出现在一行里，两次执行共用它），差别才只剩"这一项算不算进键"：

```ts
// 唯一的那一行调用点
const oneCall = async (extra: Record<string, unknown>) => {
  const { data } = await useFetch(path, pin(extra))
  seen.读到的值.push(String(data.value?.metrics?.total ?? '(空)'))
}
```

**调用点是代码里的位置，不是运行时执行了几次。** 这条分不清，后面所有关于"少发一趟"的推理都会歪。

## 自动键里到底算了什么

包内源码把那串哈希的原料写得很短（`node_modules/nuxt/dist/app/composables/fetch.js:65-69` 与第 20-48 行那段）：`"$f" + hashKey([调用点标记, 地址, method, baseURL, query 或 params, body])`。逐项量：

```
[自动键·换 query] {"趟数":2,"键":["$f3emrd7keklipg","$f3emrednqb3or1"],"读到的值":["1","2"]}
[自动键·换 method] {"趟数":2,"键":["$f2rhjmx9o8x262","$f3l1uv1owzhmu4"],"读到的值":["1","2"]}
[自动键·换 baseURL] {"趟数":2,"键":["$f2qhp241fai35k","$f3e1atpnnky5r2"],"读到的值":["1","2"]}
[自动键·换 headers] {"趟数":1,"键":["$f3fuvqm71v56qu"],"读到的值":["1","1"]}
[自动键·query 与 params] {"两项都给":{"趟数":1,"键数":1},"只给params":{"趟数":2,"键数":2}}
```

三行值得停下来看。

**换 query 那两串键的前缀是一样的**（`$f3emr…`）：调用点标记相同，只有后面那一段变了。自动键 = 调用点 ＋ 地址 ＋ 那几项选项，一眼就看得分开。

**headers 不进键**：两处调用只差一个授权头，键相同、只发一趟，第二处读到的是第一处那份返回值，而不是"用它自己的头取回来的东西"。同一页上这是省了一次请求；可一旦"两处带的头代表不同的取数条件"，那一份数就不是它自己那一份了。本站的身份来自会话 cookie、由服务端 `requireUser` 认人，两处读到同一个人的数，所以这里没有洞——但这个形状要记住：**不报错、不红判据，只是少发一趟、多共享一份。**

**`query` 与 `params` 同时给时，`params` 不算进键**：源码那行是 `[opts.query || opts.params]`（第 22 行），取的是"前一个真值"。所以只差 `params` 的两处调用，如果同时也给了 `query`，就是同一个键、同一份数据；只给 `params` 时才被算进去。官方那一节的参数表把 `query` 与 `params` 并列写着，没说它们怎么进键——这一条是包内源码的形状，行号在上面，可以自己打开核对。

顺带一句：那一节还提到用显式 `key` 建起来的这份状态，全应用可以用 `useNuxtData` 按键取回去。

## 两个"名字撞了"的警告

那一节的 `::warning` 有两条是给名字准备的：

- `useFetch` 是**编译器保留名**，会被编译期转换，别给自己的函数取同名；要做带默认选项的变体，用 `createUseFetch`（上一站那个出口就是这么写的）。
- 如果你从 `useFetch` 解构出来的 `data` 是一个**字符串**而不是解析好的对象，检查组件里有没有 `import { useFetch } from '@vueuse/core'` 这类导入——它把编译器要转换的那个名字换成了别人的实现。

两条都不是"报错信息"型的问题：名字撞了照样能跑，只是行为换了实现。这也是为什么这类话只值得抄原话，不值得现场推理。

## 撞上了去哪里看

| 撞上的现象 | 大概率是哪一位 | 先看哪里 |
| --- | --- | --- |
| 两个组件同 URL 同选项，接口被打两趟 | 自动键只对调用点唯一（设计如此） | 每次调用给同一个显式 `key` |
| 同一组件挂多份，只发一趟、数还都对 | 同一个调用点 ⇒ 同一个键 | 这正是官方后半句，不是 bug |
| 加了个不同的授权头，数却没变 | headers 不进自动键 | 把区分项放进 `query`，或给不同 `key` |
| 只差 `params` 却共用一份数据 | 同时给了 `query`，`params` 被跳过 | 只用 `query`（本站相对路径都这么写） |
| `data` 是字符串不是对象 | 从别处 import 了同名的 `useFetch` | 删掉那行导入，用自动导入的那个 |

## 交付前自查

- 官方那句话的两半都各自有一条判据，不是只引用一半
- 记键的入口换成 `getCachedData` 的第一个实参，因为假脚根本收不到自动键（旧读数 `键:"(没给键)"` 就是这件事的证据）
- 第一版那条判据错在哪、怎么发现的说全了：两行代码是两个调用点，量不出"选项算不算进键"
- 四条形状差异（query／method／baseURL 进键、headers 不进、`query || params`）都带原样读数，源码行号写在旁边
- 本站为什么没有"共享别人那份数"的洞讲清了（身份在服务端认），没有把源码形状写成官方保证
