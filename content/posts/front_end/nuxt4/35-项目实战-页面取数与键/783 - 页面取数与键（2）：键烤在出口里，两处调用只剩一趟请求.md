## 先换一个数得出趟数的量法

上一站留了个没解决的动作：会员区这一页上，页面自己渲一块"总共几次"，`<ConsoleMetricsPanel />` 渲第二块，两处都调同一个接口，可"进这一页真发几趟"在测试里数不到——那个环境没有可连的站点，读回来是空的。

这一站换个量法。**出口**（把某个接口唯一一份配置包成的那个函数）发请求的那双脚是可以换的：`useFetch` 从选项里收 `$fetch`，源码就一行（`node_modules/nuxt/dist/app/composables/fetch.js:106`）：

```ts
let _$fetch = fetchOptions.$fetch || $fetch$1
```

给它一双会记数的假脚，趟数就直接数得出来了。记的还不止趟数——每一趟实际用的**键**也记下来，因为没被摘掉的 `key` 会跟着选项一起交到那双脚上（同一个文件第 71 行把它并进 `_fetchOptions`，第 115 行随 `resolvedOptions` 传出去）。不记这一位，"只跑了一趟"有两种完全不同的解释：两处的键真的共用，或者别的原因让它没跑。

```ts [test/nuxt/console-fetch-outlet.test.ts]
function pin (impl: Foot, key?: string) {
  return { $fetch: impl as never, ...(key ? { key } : {}), getCachedData: () => undefined } as never
}

const seen = await probe(async impl => {
  await useFetch(ENDPOINT, pin(impl))
  return useFetch(ENDPOINT, pin(impl))
})
```

先跑一条正控制确认这双脚真在用，再跑三种键的写法。四段读数原样抄在这里：

```
[数脚·一次调用] {"趟数":1,"每趟":[{"地址":"/api/console/metrics","键":"(没给键)","第几趟":1}],"status":"success","读到的值":"{\"metrics\":{\"total\":1,\"kinds\":[{\"kind\":\"login\",\"count\":1}]}}"}
[数脚·都不写键] {"趟数":2,"每趟":[{"地址":"/api/console/metrics","键":"(没给键)","第几趟":1},{"地址":"/api/console/metrics","键":"(没给键)","第几趟":2}]}
[数脚·共键] {"趟数":1,"每趟":[{"地址":"/api/console/metrics","键":"ctrl:shared","第几趟":1}],"读到的值":"{\"metrics\":{\"total\":1,\"kinds\":[{\"kind\":\"login\",\"count\":1}]}}"}
[数脚·烤键的出口] {"趟数":1,"每趟":[{"地址":"/api/console/metrics","键":"ctrl:default-mode","第几趟":1}]}
```

同一个地址、同一个组件里连着调两次：不写键两趟，写同一个键一趟，都走那个把键烤好的出口一趟。第二处读到的值是 `"total":1`——假脚是按"第几趟"回不同数字的，读到 1 说明第二处根本没再取。

## 这一行是编译期宏，位置错了就抛错

把键烤进出口，写的是 `app/composables/use-console-metrics.ts` 那一行。讲 `createUseFetch` 的那一节开头有一句限定：它是一个**编译期宏**（构建时被改写成别的东西的写法），必须写成 `composables/` 目录里——或者任何编译器会扫到的目录里——一个**被导出**的声明，而 Nuxt 在构建期自动注入去重用的键。

改写只发生在导出声明里那一处。源码里那个判断很硬（`node_modules/nuxt/dist/index.mjs:5525` 只走 `ExportNamedDeclaration` 和 `ExportDefaultDeclaration` 两种节点）。所以同一个宏写在函数体里，编译期没人动它，运行时留下的就是一个会抛错的占位（`node_modules/nuxt/dist/compiler/runtime/index.js:9`）。跑一条给它看：

```ts
function makeOutlet () {
  return createUseFetch({ key: 'ctrl:not-exported' })
}

expect(makeOutlet).toThrowError(/e1007/)
```

抛出来的错误码是 `NUXT_E1007`，消息体只有那条错误码的文档地址。这条判据留在文件末尾，为的是让下一个把宏搬到函数里的人立刻看见，而不是等到构建产物里找不到自己那个 composable。

## 对象写法与函数写法：谁能盖住谁

那一节把两种写法分成两档，用词是 **Default Mode** 与 **Override Mode**。对象写法＝默认档，工厂给的算默认值，调用方可以给任何一项；函数写法＝覆盖档，工厂给的**反过来盖住调用方给的**，函数还能收到调用方那份选项用来算覆盖。原话给出的理由是"适合强制那些不该被调用方改动的设置"。

键正是最容易被"顺手改一下"的那一项。两种写法各量一遍，第二处都故意带一个自己的键：

```
[数脚·默认模式被改键] {"趟数":2,"每趟":["ctrl:default-split","ctrl:caller"]}
[数脚·覆盖模式锁键] {"趟数":1,"每趟":["ctrl:lock-mode"]}
```

对象那一档，趟数从 1 变 2，第二趟用的就是调用方塞进来的键；函数那一档，调用方的键顶不动，还是一趟。

本仓库的出口原来是对象写法，同一形状三处调用（第三处故意带键）读回来是两趟：

```
[数脚·真出口] {"趟数":2,"每趟":["console:metrics","ctrl:try-split"],"读到的值":"{\"metrics\":{\"total\":2,\"kinds\":[{\"kind\":\"login\",\"count\":2}]}}"}
```

改一行，外层从对象换成函数：

```ts [app/composables/use-console-metrics.ts]
// 改之前
export const useConsoleMetrics = createUseFetch({
  key: 'console:metrics',
})

// 改之后：键锁死，调用方其余选项照旧生效
export const useConsoleMetrics = createUseFetch(() => ({
  key: 'console:metrics',
}))
```

同一条判据再跑，变成一趟，且实际用的键只有那一个：

```
[数脚·真出口] {"趟数":1,"每趟":["console:metrics"],"读到的值":"{\"metrics\":{\"total\":1,\"kinds\":[{\"kind\":\"login\",\"count\":1}]}}"}
```

## 出口能烤的不止键

那一节的参数表列了三种签名，返回值也都是"跟 `useFetch` 同签名同返回类型"：

| 写法 | 参数 | 返回 |
| --- | --- | --- |
| 默认档 | `options?: Partial<UseFetchOptions> & { addons?: UseFetchAddon[] }` | `typeof useFetch` |
| 覆盖档 | `options: (callerOptions: UseFetchOptions) => Partial<UseFetchOptions>` | `typeof useFetch` |
| 带路由声明 | `createUseFetch<Routes>(options: Partial<UseFetchOptions> & { routes: Routes, addons?: UseFetchAddon[] })` | `DeclaredUseFetch<Routes>` |

能烤的选项是那节列的那些：`baseURL`、`headers`、`query`、`onRequest`、`onResponse`、`server`、`lazy`、`transform`、`getCachedData`，凡是 `useFetch` 有的都能放进去。三件值得单独记的：

- 想从 `useNuxtApp()` 拿一个自定义的 `$fetch`，**必须用函数写法**。那节有个 `::important` 说得很直白：函数签名是必需的，这样 `useNuxtApp()` 才落在 composable 的调用点（setup 上下文）里执行，而不是落在模块作用域——那里根本没有 Nuxt 实例。
- `routes` 那一档给第三方接口做类型，写的是 `routes: {} as PetStoreRoutes`，只读类型、发请求前把值丢掉；声明的路径**按写的那样匹配**，不要带 `baseURL` 前缀，运行时拼出来的路径落到 `unknown`。表里没有的路径和方法默认放行（结果是 `unknown`），要报错就同时开 `routeTypedFetch` 与 `strictRouteTypes`。这档写明是 4.6 起，本仓库装的是 4.5.2，所以本节不用它。
- 还有一个 `addons` 数组，用 `defineUseFetchAddon` 定义可复用的行为片段：能声明调用点专属的选项、在取数前后插代码、往返回对象上加字段。

顺带一句同族限定：`useFetch` 是编译器保留的名字，别给自己函数取同名；要做变体就用 `createUseFetch`。

## 键只有一个，写法也要钉住

运行层量到的东西，静态判据要接住，否则下一次改动就漂回去了。`test/unit/console-fetch-surface.test.ts` 扫 `app/` 下所有 `.ts` 与 `.vue`（连注释和模板注释一起剥掉）：

```
[键字符串的位置] {"扫到的文件数":15,"出现处":["app/composables/use-console-metrics.ts"]}
[宏的位置与写法] {"出现处":["app/composables/use-console-metrics.ts"],"锁键":true}
[出口调用点] [{"文件":"app/components/ConsoleMetricsPanel.vue","await了吗":true,"实参数":1},{"文件":"app/pages/console/index.vue","await了吗":true,"实参数":1}]
```

新增的那条判据查两件事：宏只许出现在出口那一处，且出口必须是"函数包对象"的锁键形状。为什么光有"键字面量只有一处"不够——把出口写成 `keyy:` 试一次（模拟那个键其实没烤上）：

```
[数脚·真出口] {"趟数":3,"每趟":["(没给键)","(没给键)","ctrl:try-split"],"读到的值":"{\"metrics\":{\"total\":3,\"kinds\":[{\"kind\":\"login\",\"count\":3}]}}"}
```

三处调用发了三趟，因为编译器给每个调用点注入了各自的去重键，而那串字面量仍然只在出口出现一次——老判据照绿，新判据红（`锁键:false`）。反过来把出口退回对象写法，运行层与静态那条一起红（2 趟 / `锁键:false`）。两条坏改动各有判据接住，这轮才算量完。

最后坦白一件量法上的事，它值得单独记：同一形状的探针，在默认缓存位下发过两趟（`{"第一次":2}`），带上一条 `getCachedData: () => undefined` 后是一趟（同一段探针的读数 `{"每趟":[1],"causes":["ctrl:reuse←initial"]}`）。这一层的挂载没有服务端、也没有新负载可水合，缓存位读回来的东西不参与决定发不发，但它会让一次调用发两趟。所以本节所有趟数都出自"把缓存钉成未命中"的探针——读数里只剩一个变量：两处的键是不是同一个。同理，同一份测试文件里多次挂载共用键缓存，同一个键第二次挂载一趟都不发，因此每段要看"第一次取数"的探针都配一个独有键。

## 撞上了去哪里看

| 撞上的现象 | 大概率是哪一位 | 先看哪里 |
| --- | --- | --- |
| 两处都调出口，接口还是被打两趟 | 某一处带了第二个实参，键被顶掉 | `[出口调用点]` 的 `实参数`；改函数写法可锁死 |
| 出口明明写了键，趟数等于调用点数 | 键名写错（比如 `keyy:`），根本没烤上 | `[宏的位置与写法]` 的 `锁键`，再看运行层每趟记的键 |
| 自己造的 composable 在测试里不好使 | 宏写在非导出的位置，运行时抛 `NUXT_E1007` | 那条抛错判据；把声明改成 `export const` |
| 一次调用读出两趟 | 默认缓存位在这一层的行为 | 探针带 `getCachedData: () => undefined` 再读 |
| 同一个键第二次挂载一个请求都不发 | 键缓存跨挂载还在 | 每段探针配独有键，别复用 `ctrl:` 名字 |

## 交付前自查

- 出口那一行是真改的（对象 → 函数），且改前改后各有一条运行层读数对照
- 宏的位置约束、默认档与覆盖档的归属都跑了自己的判据，不是引原话代替量
- 两个变异各红在哪、什么没红写全了：`keyy:` 那种形状只有新判据看得见
- 量法自身的两件事（缓存位、跨挂载共用键）没有当成结论写，只作为口径交代
- 这一层数的是"键相不相等"，不是"用户进这一页真发几趟"——后者仍要一条真会话
