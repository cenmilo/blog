用键盘试一次：tab 到导航里的"关于"，回车。页面换了，但光标还在导航里——你得把整个页头再 tab 一遍才能碰到新内容。

这不是你的组件写错了。官方在这一点上的说法很干脆：**框架不管这件事**。

## 官方给的成因

整段原文：

> After a client-side navigation, focus stays where it was, which is usually the link the user just activated. Vue Router does not move it and neither does Nuxt, so a keyboard user can end up tabbing through the whole header again to reach the content that just changed.

三处要点：**焦点留在刚激活的链接上**、**Vue Router 与 Nuxt 都不移动它**（这是责任划分，不是 bug 报告）、后果是**键盘用户要重新 tab 过整个页头**。

这一句和 480 那篇的第二句是同一件事的两面：文档不重载，浏览器替你做的那些默认动作就没了——播报是一件事，**焦点落点是另一件**。

## 第一配方：skip link

官方给的话：

> A skip link as the first tab stop of your app is the conventional fix, and it helps on the initial page load too:

```vue [app.vue]
<template>
  <a
    class="skip-link"
    href="#main"
  >Skip to main content</a>
  <AppHeader />
  <main
    id="main"
    tabindex="-1"
  >
    <NuxtPage />
  </main>
</template>

<style>
.skip-link {
  position: absolute;
  left: -9999px;
}
.skip-link:focus {
  position: static;
}
</style>
```

四个细节都在这段里，别改：

| 细节 | 内容 | 依据 |
| --- | --- | --- |
| 位置 | 它是应用的**第一个 tab 停靠点**（写在页头组件之前） | 官方原话"as the first tab stop of your app" |
| 指向 | `href="#main"`，主区给 `id="main"` | 示例 |
| 主区可聚焦 | `<main>` 加了 `tabindex="-1"` | 下一节解释 |
| 隐藏方式 | 平时用 `position: absolute` 加 `left: -9999px` 移出屏幕，`:focus` 时改成 `position: static` | 示例 CSS |

最后那条的**动机官方没写**（文档未说明），但从那段 CSS 的行为能读出设计意图：它平时不在屏幕上，**一旦被聚焦就回到正常流里**——所以它必须是能被键盘到达、且到达后可见的元素。

## 为什么是 `-1` 而不是正值

官方紧接着给了原因，这一句要照抄：

> `<main>` is not focusable on its own, so it needs `tabindex="-1"` to accept focus from the skip link or from a script. Use `-1` rather than a positive value, which would move the element in the tab order and surprise everyone else.

拆两层：

**加 `tabindex="-1"` 是因为 `<main>` 本身不可聚焦**，不加就接不住 skip link 或脚本交给它的焦点。

**不能用正值**，理由官方说得很形象：正值会**把这个元素挪进 tab 顺序里**，"让所有人都被吓一跳"。`-1` 的含义就是"可被程序或锚点聚焦，但不进 tab 流"。

## 第二配方：每次导航后把焦点交给主区

官方给的进阶做法，条件是"If it suits your app"：

```ts [app/plugins/focus-main.client.ts]
export default defineNuxtPlugin(() => {
  useRouter().afterEach((to, from) => {
    if (to.path === from.path) {
      return
    }
    nextTick(() => document.getElementById('main')?.focus())
  })
})
```

三处写法上的决定值得注意：

**文件名带 `.client` 后缀**——这个插件只在浏览器跑（061 那篇讲过后缀决定运行侧）。

**先比对 `to.path === from.path` 就返回**：同一路径的变化（比如只有 query 变）不该抢焦点。

**`nextTick` 包一层再 `focus()`**：等新 DOM 落位。这一句和 456 那条"插件在水合阶段跑、数量多了会阻塞"并不矛盾——它里面只有一层钩子和一次 `nextTick`，成本可以忽略。

顺带一条与 462 相邻的规则：`afterEach` 这类导航钩子在**错误页那一次独立加载**里也会再跑一遍（461 记过中间件会重跑，这是同一机制的另一个后果），所以错误页会不会被这个插件抢焦点，值得单独验一次。

## 键盘可达还依赖链接写法

Focus 之外，官方那一节的 Links 部分管的是"能不能被 tab 到"：

> Use `<NuxtLink>` for in-app navigation. It renders a real `<a href="...">`, which means it is focusable, appears in the tab order, and works with middle-click and "open in new tab", all of which you would have to reimplement on a `<div>` with a `@click` handler calling `navigateTo`.

**可聚焦、进 tab 顺序、中键与新标签页打开**——这三项是 `<a>` 白送的，换成 `<div @click>` 就得自己实现。456 那篇讲性能冲突时用的就是这条。

同一节还有两项与状态有关的写法：当前路由对应的那个链接**已经自带 `aria-current="page"`**；需要换个描述关系时（官方举的例子是多页表单里的步骤），设 `ariaCurrentValue`，示例是 `aria-current-value="step"`。链到 `public/` 里的文件或同域另一个应用要标 `external`（147、456）。

## 官方给的验证方法只有一句

整节末尾那条 `::tip` 是唯一写在文档里的验收动作：

> Navigate around your app with the keyboard alone. Tabbing from the skip link into `<main>` after a couple of navigations will surface most focus problems quickly.

**只用键盘在应用里走一圈**——从 skip link tab 进 `<main>`，几次导航之后，多数焦点问题会自己冒出来。这一句的成本是几分钟，比任何清单都有效。

## 自查

- 焦点落点是框架不管的：客户端导航后留在原处，Vue Router 与 Nuxt 都不移动。
- skip link 要是第一个 tab 停靠点，主区必须 `tabindex="-1"`；正值会把元素插进 tab 顺序，官方明确反对。
- 想每次导航后自动聚焦主区，用 `.client` 插件里的 `afterEach` + 同路径直接 return + `nextTick`。
- 能被 tab 到取决于有没有真 `<a href>`；当前项的 `aria-current="page"` 是自带的，需要时改 `ariaCurrentValue`。
- 验收只有一条：只用键盘走一圈。
