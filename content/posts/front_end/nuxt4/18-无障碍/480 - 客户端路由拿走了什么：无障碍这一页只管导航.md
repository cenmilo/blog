很多人以为用了服务端渲染，无障碍就"自动好了"。官方这一节第一句就把这个误解挡掉了：它管的事情和 SSR 无关，而且**大半内容不属于 Nuxt**。

这一篇讲清这一节到底划了什么范围——搞清楚边界，才知道哪些事得自己去查。

## 第一句就是划界

原文：

> Most of what makes an app accessible is not specific to Nuxt: color contrast, form semantics, and ARIA work the same here as in any Vue or plain HTML application, and the resources at the end of this guide cover them well.

三件事被点名"与 Nuxt 无关"：**色彩对比度**、**表单语义**、**ARIA**。官方给它们的去处是"这一节末尾那些资源"——也就是说，这一节**不打算教你这三样**。

这决定了读法：想找 `<button>` 与 `<div @click>` 的差别、想找 `aria-*` 用法表，在这一节翻不到。456 那篇讲冲突时用的都是这一节实际写了的东西（链接、焦点、滚动）。

## Nuxt 改变的是导航

第二句才是这一节的正题，值得整段读：

> What Nuxt does change is navigation. Once your app has hydrated, it routes on the client, so the document is never reloaded and the browser no longer announces a new page or resets focus for you. Nuxt ships with features that fill some of that gap, and a few conventions cover the rest.

拆开看，**水合之后**发生了三件事：

| 被拿走的默认行为 | 原因（官方措辞） |
| --- | --- |
| 文档不再重载 | 应用水合后在客户端路由（"it routes on the client"） |
| 浏览器不再播报新页面 | 没有新的文档加载，屏幕阅读器无从得知（下一节明说） |
| 焦点不再被重置 | 同上，浏览器只在整页加载时替你做这件事 |

最后一句给出补齐的两条路径：**框架自带能力填一部分空**，**剩下的靠约定**。这也就是这一节五节的由来。

这里有个容易搞反的点：**服务端渲染解决的是首屏那份 HTML**（460、413 讲过），它对"整页加载那一次的播报"有帮助，但帮不了之后的每一次客户端跳转。**无障碍缺口出现在水合之后，不在水合之前**。

## 自带能力补的是哪一格

五节各自对着上面哪一条被拿走的默认行为，这张对应关系是从原文里读出来的：

| 这一节 | 补的是哪格 | 官方给的东西 |
| --- | --- | --- |
| Route Announcements | 播报新页面 | `<NuxtRouteAnnouncer>` 渲染一个隐藏的 live region，每次导航后把新页面标题写进去 |
| Page Titles | 让上一条有用 | 每条路由要有可区分的标题；在 `app.vue` 设全局模板、页面填自己那部分 |
| Links | 键盘与常规导航能力 | `<NuxtLink>` 渲出真 `<a href>`，因此可聚焦、进 tab 顺序、支持中键与新标签页打开 |
| Focus Management | 焦点重置 | 官方明说"Vue Router does not move it and neither does Nuxt"，给 skip link 与一个客户端插件配方 |
| Scroll Behavior | 滚动位置 | Nuxt 默认会滚到顶部、返回时恢复位置、命中锚点时滚动；改法指向 `scrollBehaviorType` 与 `router.options.ts` |

第一节的开头那句把缺口说得很直白：

> Screen readers announce a full page load by themselves, but they have no way of knowing that a client-side navigation happened.

**屏幕阅读器自己会播报整页加载，但没有办法知道发生了一次客户端导航**——这就是 `<NuxtRouteAnnouncer>` 存在的唯一理由（483 那篇讲它的实现细节）。

## 还有一条工具提示，带版本警告

这一节唯一的 `::tip` 给了一个第三方模块：

> `@nuxt/a11y` surfaces accessibility problems in your components while you develop, alongside the practices below. It is in alpha, so expect its API to change.

两句都重要：它的作用是在**开发期把组件里的可访问性问题暴露出来**（正好对着上面那句"框架能力填一部分"——它填的是检测这一环）；但它**处于 alpha，官方直接说预期它的 API 会变**。所以在项目里把它当长期依赖之前，这句提示要一起写进技术选型记录。

## 一、二、四与五的分工

顺带说清一个顺序问题（**这层排序是我的读法，官方没写次序**）：

1. **先做标题**（Page Titles）——因为播报器读的就是标题，标题没区分度，后面那一整套播报都是空的。
2. **确认链接用对了组件**（Links）——这一步同时决定键盘可达与预取行为（442、456）。
3. **补焦点落点**（Focus Management）——skip link 是官方给的第一配方，成本几乎为零。
4. **调滚动**（Scroll Behavior）——只在你改默认行为时才有事做，且要尊重 `prefers-reduced-motion`。
5. **其余归通用实践**（对比度、表单语义、ARIA）——按这一节末尾的资源去查。

## 自查

- 这一节只管导航：色彩对比度、表单语义、ARIA 被官方明写在"Nuxt 无关"那一侧。
- 三个被拿走的默认行为：文档不重载、不播报新页面、焦点不重置；都发生在水合之后。
- 五节的对应关系要记住第一条：播报器读的是 Unhead 渲出的标题，**标题没区分度就等于没播报**。
- `@nuxt/a11y` 是开发期检测工具，官方标注 alpha、API 会变。
- 服务端渲染管首屏 HTML，管不了客户端跳转带来的这些缺口。
