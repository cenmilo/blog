上一篇（311）讲了 `server/` 里"同名工具到底 import 的是哪份"。这一篇把服务端能碰到的**几个 import 面**一次理清：`nuxt/server`、`h3`、`nitropack/runtime`、`#app`/`#imports`——它们各自能用在哪个环境，别引错方向。

## 四个 import 面先分清

- **`#app` / `#imports`**：应用（浏览器 + SSR）那一侧的运行时面，前端组合式、`useFetch` 这些从这来。
- **`nuxt/server`**：Nuxt 给的"可移植服务端工具面"，官方定位——"the import surface for server code that isn't tied to a particular server runtime"，它是 Nuxt 的第二运行时面（和 `nuxt/app`/`#app` 并列）。
- **`h3`**：服务端 HTTP 框架本体，`defineEventHandler` 的原产地。
- **`nitropack/runtime`**：Nitro 引擎特有的能力（storage、缓存、Nitro 插件与钩子）。

`nuxt/server` 里有一批和 h3 **同名**的东西（`defineEventHandler`、`getRouterParams`、`handleCors`、`readValidatedBody` 等），官方点明它不是 h3 的再导出——"These names are not auto-imported from `nuxt/server`"，要用可移植那版必须显式 import（311 讲过）。

## nuxt/server 只能在服务端代码里用

这是方向上的第一道墙。官方 "Server Code Only"：

> Importing `nuxt/server` from a Vue component, a plugin or the `shared/` directory fails the build, and the error points you at `#app`, `#imports`, `$fetch` and `useFetch` instead.

也就是说 `nuxt/server` 只能在 **`server/` 里的代码**用；从组件、Nuxt 插件、`shared/` 引它 → 构建失败，报错会把你指回 `#app`/`#imports`/`$fetch`/`useFetch`（那几个才是 app 侧该用的）。

同节还给了另一条"什么时候即使你在 server 也别用它"：

> `nuxt/server` also only works in code that a server builder bundles ... Code that runs in the Nuxt process, such as `nuxt.config.ts`, a module's `setup` or a function passed to `addDevServerHandler`, has none of these, so don't import `nuxt/server` there: `useRuntimeConfig()` and `useAppConfig()`, for example, return empty objects.

因为 runtimeConfig、appConfig、hooks、in-process fetch 都是**服务端构建器**在背后供的；跑在 Nuxt 进程本身（`nuxt.config.ts`、模块 setup、`addDevServerHandler`）里没有这些，硬用会拿到空对象。

## 需要 Nitro / h3 专有能力：从对应包直接引

`nuxt/server` 只覆盖"跨构建器可移植"的那部分。官方 "Reaching Past the Surface" 说明：要别的就从源头引——

> `nuxt/server` isn't a re-export of h3, so if you need something else that h3 and Nitro offer, such as the server lifecycle (`defineNitroPlugin` and `defineNitroErrorHandler`) or Nitro's own runtime hooks, you would import it directly.

官方 "What Isn't Portable" 把"必须走出 `nuxt/server`"的几块列了出来：

- **Storage**：`useStorage()` 来自 `nitropack/runtime`（驱动配置也是）。
- **Caching**：`defineCachedEventHandler()` / `defineCachedFunction()` 来自 `nitropack/runtime`。
- **Server plugins**：`defineNitroPlugin()` 来自 `nitropack/runtime`；Nitro 自己的钩子（`request`、`beforeResponse`、`error`）来自 `useNitroApp().hooks`。
- **Lazy handlers**：`lazyEventHandler()` 来自 `h3`。

要 h3 独有 helper（`readRawBody`、`readMultipartFormData`、`assertMethod`、`proxyRequest`、`fetchWithEvent`、`writeEarlyHints`，或读 `event.node`/`event.waitUntil()`），官方给的写法是**这个 handler 从 h3 引 `defineEventHandler`**：

```ts [server/api/upload.post.ts]
import { defineEventHandler, readMultipartFormData } from 'h3'

export default defineEventHandler(async (event) => {
  const parts = await readMultipartFormData(event)
  return { received: parts?.length ?? 0 }
})
```

## 方向规矩一句话

把两页的 important 合起来（server 页那条、这一页"Server Code Only"那条是同一堵墙的两面）：

> Do not import Vue app code (components, composables, or other app-only utilities) in your server routes or utilities, and do not import server-only code in your app.

- app 侧：`#app`/`#imports` 的东西。别在 app 里引 `nuxt/server`、`h3`、`nitropack/runtime`。
- server 侧：`nuxt/server`（可移植）、`h3`（要 h3 特性时）、`nitropack/runtime`（要 Nitro 特性时）。别在 server 里引 Vue 组件/组合式。
- `shared/` 两端都不引（312）。

## 模块作者的额外一层

如果你在写模块：官方 "Modules" 一节说运行时代码只要只从 `nuxt/server` 引，就能在任何服务端构建器（v4.6+）下跑，"with no version check and no dependency on h3 or Nitro"。并 tip 打包时把 `nuxt/server` 留作 external（"Leave `nuxt/server` external when you bundle"）。要同时支持 <4.6（没有 `nuxt/server` 可解析）得并排注册两份文件。

## 自查

- `nuxt/server` 只在 `server/` 里用；从组件/插件/shared 引它会构建失败。跑在 Nuxt 进程里的代码（nuxt.config、模块 setup）也别用它，会拿空对象。
- 要 Nitro 专有（storage/缓存/defineNitroPlugin/Nitro 钩子）从 `nitropack/runtime` 引；要 h3 独有 helper 从 `h3` 引。
- app 与 server 代码不许互相 import；shared 两端都不引。
- 写模块要可移植，就只从 `nuxt/server` 引、打包时留 external。
