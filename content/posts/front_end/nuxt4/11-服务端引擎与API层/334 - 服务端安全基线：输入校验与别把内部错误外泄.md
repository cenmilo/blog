前面几篇零散提过几条安全相关的官方约定。这一篇把它们收成一份"服务端安全基线"，每条都对应到文档原句。

## 输入侧：先校验，别信裸数据

`readBody`/`getQuery` 读出来是原始值。官方给的安全做法是接 schema 校验——server 那页两处都建议：

> Alternatively, use `readValidatedBody` / `getValidatedQuery` with a schema validator such as Zod or Valibot for runtime and type safety.

server-imports 的 Validation 节把行为写清了：

> `readValidatedBody` and `getValidatedQuery` take any Standard Schema (Zod, Valibot, ArkType and others) ... Invalid input is rejected with a `400` whose `data.issues` lists what failed. Pass `onError` to reject it with a different error.

基线条目一：**任何进入业务逻辑的 body/query，先过一层 schema 校验**，非法自动 400、`data.issues` 告诉你哪没过。别拿没校验过的输入去拼 SQL、去访问文件路径、去当参数。

## 输出侧：错误信息别把内部细节漏出去

这是本篇最关键的收敛，和 309 那条连上。create-error 那页明写：

> a `message` passed to `createError` on an API route will not propagate to the client.

这条本身就是一种收口——`message` 常来自底层异常原文（可能含 SQL、堆栈、内部路径），Nuxt 默认把它挡在服务端不下发。所以：

基线条目二：**给前端的错误信息，是你显式挑过的 `statusText`（短、可控）或 `data`（结构化、你亲手组），而不是 handler 里那句随手写的 message 自动漏出去。**

紧接着官方那句安全提醒（308/309 都引过）：

> always consider avoiding to put dynamic user input to the message to avoid potential security issues.

基线条目三：**别把用户的动态输入拼进 message / statusText / data**——下发给客户端的字段里不要有没处理过的用户输入。

还有 cause 链：create-error 说 "In production, causes are never included in error responses or in the error page payload."（308、309）。基线条目四：**依赖 cause 保留原始错误只在开发看，生产它不进任何响应**——别指望前端能拿到 cause，也别在开发调试完忘了它不会泄漏。

## 数据保护侧：服务端才护得住数据

292/336 反复立的那句：

> Client-side middleware is helpful for the user, but without server-side protection your data can still be accessed.

基线条目五：**每个碰敏感数据的接口，服务端自己 `requireUserSession(event)` 或等价校验挡一道**（抛 401）。客户端路由中间件守的是体验（326 那条），不是数据。

配套：

- 密钥放 `runtimeConfig` 私有键、只在服务端读（327），别渲染、别传进会进 payload 的 useState（264）。
- `httpOnly`/`secure` cookie（255）——`secure:true` 那句还带 "This can lead to hydration errors"，是安全与水合的权衡点。

## 一张基线清单

| 面 | 基线 | 出处 |
| --- | --- | --- |
| 输入 | body/query 一律过 `readValidatedBody`/`getValidatedQuery` | 305 |
| 输出 | message 不下发；用 statusText/data 主动给；不放用户输入 | 308/309 |
| 输出 | cause 只开发可见、生产不进响应 | 308 |
| 数据 | 服务端 requireUserSession 才护数据 | 292/326 |
| 密钥 | 锁 runtimeConfig 私有键、不进包不进 payload | 264/327 |

## 自查

- 每条接口：进业务的输入有没有先 schema 校验（非法 400 + data.issues）？
- 抛给前端的错误：是不是你显式挑过的 statusText/data，而不是漏出去的 message？里面有没有用户动态输入？
- 敏感接口有没有在服务端挡（requireUserSession / 401），而不是只靠客户端中间件？
- 密钥是不是只在 runtimeConfig 私有键、没进客户端包或 useState？
