先给术语一句人话：跨域（CORS）就是浏览器默认禁止一个网页去请求"另一个域名"的接口，除非服务端在响应里明确写"允许你"。所以处理跨域，本质是**在服务端响应上加对头**。这一篇把 Nuxt 文档里能加这些头的几个点收一起。

## 点一：routeRules 里声明式加

最省事的方式——按路径声明（325 已列 routeRules 属性）：

> `cors: boolean` - Automatically adds cors headers with `cors: true` - you can customize the output by overriding with `headers`.

getting-started/server 的示例就是这么写的：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  routeRules: {
    // Add cors headers on API routes
    '/api/**': { cors: true },
  },
})
```

要精确指定哪些源、哪些方法，就用 `headers` 覆盖：

> `headers: object` - Add specific headers to sections of your site - for example, your assets.

也就是 `cors: true` 给你一套默认跨域头，不满足就自己用 `headers` 写死具体值（比如 `Access-Control-Allow-Origin`）。

## 点二：按请求动态处理用 handleCors

声明式适合"整段路径统一策略"。要按这次请求动态判断（比如根据 origin 白名单决定允不允许），用 helper——server-imports 的 `nuxt/server` 工具表列了它：

> `handleCors` - Apply CORS headers and answer preflight requests.

预检（preflight）就是浏览器在真正发请求前，先用 `OPTIONS` 问一句"能不能跨域"。`handleCors` 负责加跨域头并应答这个预检。它是服务端工具（在 `nuxt/server` / h3 里，313 讲过 nuxt/server 的同名工具要显式 import），用在服务端 handler/中间件里。

## 点三：读入站请求头是另一件事

跨域是"往响应加头"。反过来"从请求读头"是另一个方向，用 315 的那对：

- `useRequestHeader('name')` 读单个头、`useRequestHeaders([...])` 读多个（浏览器分别返回 undefined / 空对象）。
- `useRequestEvent()` 拿整个 event、从 `event.headers` 读。

这三个都只在服务端那一趟有真值（314/315）。别把它们当成"处理跨域"的工具——它们读的是入站头、和"给响应加跨域头"是两回事。

## 一张"跨域相关能落点"的地图

| 你想做的 | 用 | 在哪写 |
| --- | --- | --- |
| 整段路径自动加跨域头 | routeRules `cors: true` | nuxt.config |
| 精确指定跨域头值 | routeRules `headers` | nuxt.config |
| 按请求动态判、应答预检 | `handleCors` | 服务端 handler/中间件 |
| 读入站头（鉴权、代理转发） | `useRequestHeaders` / `useRequestEvent` | 页面/插件/中间件（仅服务端有值） |

## 自查

- 跨域默认走 routeRules：`'/api/**': { cors: true }` 省事，要具体值用 `headers` 覆盖。
- 要"按这次请求判断 + 应答 OPTIONS 预检" → 服务端里用 `handleCors`。
- 读请求头是另一件事，用 useRequestHeaders/useRequestEvent，别和"加跨域头"混为一谈。
- 这些头相关的东西多数只在服务端那一趟生效（307/314/315 同理）。
