## 屏幕上先出现的是两个 count

会员区那一页要摆几个数字，第一个是"这个人登录过几次"。仓库里已经有一张表在记动作，叫 `audit_logs`，它里面正好有一列名字就叫 `count`。于是最顺手的做法是：再建一张表，把那一列抄过来，登录一次就把那列加一。

这一节读的就是两件事：那个 `count` 属于哪张表、它在那里是什么意思；以及"登录过几次"这个数字最后从哪一句话里出来。所有读数都是这一轮跑出来的，跑法在最后一节。

## 两张表并排读一遍

新表只有四列，定义在 `db/tables/meter-events.ts`：

| 列 | 谁给值 | 这一位是干什么的 |
| --- | --- | --- |
| `id` | 库（`bigserial`） | 只是这一行的号，没人按它查 |
| `user_id` | 应用 | 这行动作属于谁 |
| `kind` | 应用 | 做的是哪件事，现在只有 `login` |
| `occurred_at` | 库（`DEFAULT now()`） | 什么时候发生的 |

判据把两张表的列都读出来（`test/unit/meter-shape.test.ts`）：

```
[计量表的列] {"列":["id","user_id","kind","occurred_at"],"计数类列":[]}
[审计表的列] {"列":["id","ts","actor","action","target","count","meta","request_id"],"含count":true}
```

这两行一起读才有意义。审计那行的 `count` 记的是"**这一次动作影响了几行**"——它是对一件事的描述，写进去就不再改；比如管理员把某人所有设备下线，那一行的 `count` 就是当时的设备数。计量这张表**没有**这一列，因为它的每一行本身就是一次动作，数字要靠问。同一个词在两张表里是两个意思，"照抄一份"抄过来的正好是不该带过来的那个意思：一旦有一列存着总数，就有两个地方在说同一件事，而它们会开始不一致。

顺手说一句"这条判据不是扫不到东西"的证明：上面第二行就是它的正控制，`count` 那一位确实在审计表里被读到了。写排除类的判据时，这种"另一侧必须扫得到"的一条要一起写，否则空手也能通过。

## 记一笔那句 SQL 长什么样

服务层的写入口只有一个函数（`server/services/metrics/index.ts` 的 `recordMeterEvent`）。这一轮没有数据库也能看到它真正发出去的那句话：给 `useDb()` 装一个只抄句子的假库，底下用真的 drizzle 实例，于是打印出来的就是数据库将要执行的原文。

```
[计量 INSERT] {"写成功":true,"语句":"insert into \"meter_events\" (\"id\", \"user_id\", \"kind\", \"occurred_at\") values (default, $1, $2, default)","参数":["3f2504e0-4f89-41d3-9a0c-0305e82c3301","login"],"参数个数":2}
```

四个列名都在，但 `values` 里两位写的是 `default`，参数只有两条。**"什么时候发生的"这句话不由应用回答**，它交给库的 `DEFAULT now()`。这一位值得钉：应用和数据库不同机时两套钟会漂，仪表盘按"发生了什么时间"排序时，用应用时钟写的行会跟用库时钟写的行打架。

于是本站做了一个变异：把那次写入补上时间戳——`values({ userId: input.userId, kind: input.kind, occurredAt: new Date() })`，类型完全合法（列就在那儿）。同一趟打印变成：

```
[计量 INSERT] {"写成功":true,"语句":"insert into \"meter_events\" (\"id\", \"user_id\", \"kind\", \"occurred_at\") values (default, $1, $2, $3)","参数":["3f2504e0-4f89-41d3-9a0c-0305e82c3301","login","2026-10-18T00:20:26.782Z"],"参数个数":3}
```

判据红一条：`AssertionError: expected [ …(3) ] to deeply equal [ …(2) ]`。**"库里那一行的时刻是谁给的"这件事，现在是有人看着的了**；改回原样后重新变绿。

## 算一次那句 SQL 长什么样

读侧是同一个文件里的 `metricsForUser(userId, since?)`：

```
[计量 SELECT] {"语句":"select \"kind\", count(*) from \"meter_events\" where \"meter_events\".\"user_id\" = $1 group by \"meter_events\".\"kind\"","参数":["3f2504e0-4f89-41d3-9a0c-0305e82c3301"],"假库回的行":[["login","2"]],"回来的形状":{"total":2,"kinds":[{"kind":"login","count":2}]},"total类型":"number","count类型":"number"}
```

三件事在这一句里看得很清楚：唯一的边界条件是 `where ... = $1`，而且这个人是**参数**不是拼进句子的字符串；计数是 `count(*)` 配 `group by "kind"` 现算的；那张表里没有任何一列存着"2"这个数。所谓"仪表盘的数字与库里数出来的一致"，靠的就是这一句而不是某列的值。

## 给假库喂错形状，数字会静默变成空

上面那条读数里 `假库回的行` 是 `[["login","2"]]`——**数组的数组**。第一眼会觉得别扭：一行数据难道不该是个对象吗？这一轮真的两种都跑了一遍。

```
[桩形状对照] {"给的是对象行":true,"total是不是NaN":true,"JSON序列化后":"{\"total\":null,\"kinds\":[{\"count\":null}]}"}
```

同一条查询，只把假库回的行换成 `[{ kind: 'login', count: '2' }]`，`total` 就成了 NaN，而 NaN 一旦进 JSON 就变成 `null`，一句错误都没有。原因在装上的 drizzle 里，两处可以当场翻：

- `node_modules/drizzle-orm/node-postgres/session.js:61` 那句 `rowMode: "array"`——它要求数据库驱动**按位置**把行交上来；
- `node_modules/drizzle-orm/utils.js:29` 那句 `const rawValue = row[columnIndex]`——组装结果时确实按下标取。

所以对象形状喂进去时，按下标取到的每一位都是 `undefined`，`Number(undefined)` 得 NaN。换成数组形状（顺序等于 `select` 里列的顺序）就是那条绿读数：`{"total":2,"kinds":[{"kind":"login","count":2}]}`。

这一条对读者的用处有两层。第一层是写测试的时候：**假库的形状不是"看着像一行"就行，得跟驱动真会给的那个形状一致**，否则判据跑得越绿、读到的数越假。第二层是排查的时候：接口回 200、`total` 却是 `null`，先别怀疑数据库，先确认是不是映射错位——这一类问题不抛异常，只会让数字凭空消失。判据文件里把这条正控制留着，就是为了下次有人改桩形状时立刻红。

## 外键那一位：两张表方向相反

```
[两种 ON DELETE] {"计量":"cascade","审计":"set null","相反":true}
```

用人话说：`cascade` 是"人被删，他的计量行跟着删"；`set null` 是"人被删，审计行留着，只是'谁干的'那一位空出来"。计量行是这个人自己的东西，留着只会变成谁也对不上的匿名数字；审计行的意义恰恰是"人不在了，痕迹还在"。**两张表都指向 `users`，方向却必须相反**，而这正是照抄最容易做反的一位。

判据两边都读——迁移里那句要执行的 SQL，和 schema 源码里那一处 `onDelete`：

```
[同源] {"计量schema":["cascade"],"计量迁移":"cascade","审计schema":["set null"],"审计迁移":"set null","两处各一处":true}
```

两个变异分别只改一边，红条数不一样，这就是这一节最想要的差别：

| 改哪一边 | 红的判据 | 打印出来的失败 |
| --- | --- | --- |
| 只改迁移里那句 `ON DELETE cascade` → `set null` | 两条 | `expected 'set null' to be 'cascade'`；`expected [ 'cascade' ] to deeply equal [ 'set null' ]`（`Tests 2 failed \| 10 passed (12)`） |
| 只改 schema 源码那一处 → `set null` | 一条 | `expected [ 'set null' ] to deeply equal [ 'cascade' ]`，而 `[两种 ON DELETE]` 那一条**照绿** |

第二行是这个仓库里真实会发生的漂移方向：改了表定义没重新生成迁移，或反过来手工补了一句迁移而源码没跟上。漂移的后果不是当场报错，而是下一次有人跑生成命令时多出一份"改掉外键"的迁移——线上那张表其实一直没变，之后数字从什么时候开始对不上的就没人说得清了。**只盯一边读的检查会放过它。**

## 没配库的时候它不打扰任何人

```
[计量·没配库] {"写成功":false,"发出几条":0}
```

`recordMeterEvent` 先看 `useRuntimeConfig(event).databaseUrl`，没配就一句都不发、回 `false`，登录这件事该成功还是成功。计数丢了不是登录失败的理由——这是记账类的写入口共同的取舍（审计那一条同形）。接口侧"没配库也不许变成 500"是 `test/e2e/metrics-endpoint.spec.ts:19` 管的事，下一站读它。

还有一条本轮量到、留到后面处理的：不传时间窗时那句查询里没有 `occurred_at` 的条件——

```
[计量·全量] {"含occurred_at":false,"参数个数":1}
```

`metricsForUser(userId, since?)` 的第二个参数现在是空着的。要"这周登录几次"，动的是这个参数，**不是**给表加一列。

## 复跑与排错

```
npx vitest run --config vitest.config.ts test/unit/meter-sql.test.ts test/unit/meter-shape.test.ts
```

两份合起来十二条，全绿的尾行是 `Test Files  2 passed (2)`／`Tests  12 passed (12)`；并进整层之后是 `Test Files  37 passed (37)`／`Tests  248 passed (248)`。

| 撞上的现象 | 大概率是哪一位 | 先做什么 |
| --- | --- | --- |
| 接口 200，`total` 却是 `null` | 假库或驱动返回的行形状与按下标取的映射不一致 | 照 `[桩形状对照]` 那条的思路打一行形状出来看，先确认是不是对象形状 |
| 数字与库里手工数出来的对不上，但没错 | 有人加了一列存总数，两处各说一套 | 跑 `[计量表的列]` 那条，它会把多出来的列名点名（本轮变异里打的是 `计数类列:["login_count"]`） |
| `[同源]` 红而 `[两种 ON DELETE]` 绿 | schema 与迁移只改了一边 | 把两处对齐，再跑一次生成命令看有没有多出来的迁移 |
| 想加"这周几次" | 直接去改表 | 别加列，用 `metricsForUser` 那个空着的 `since` 参数；`occurred_at` 已经在表上、且是库的时钟 |
| 登录成功但一条计量都没写 | 没配 `NUXT_DATABASE_URL` | 看 `[计量·没配库]` 那两条读数，这是设计行为；要追责去看那条 `meter_write_failed` 的日志行 |

## 交付前自查

- 两张表的列是并排读的，"不许有计数列"那条配了一条"另一张表里真有 count"的正控制
- 两条 SQL 是这一轮打印的原文，转义都按打印的样子留着，没有手写
- 假库形状那一节给的是错形状时的读数（NaN 与 `null`），不是推测的症状
- 四次变异各有明确的红条数：改时刻一位 1 条、加计数列 1 条、只改迁移 2 条、只改源码 1 条
- 本轮没有连库、没有写库，所以"删用户之后计量行跟着没"这类只有真库能读到的判断，一句都没写进结论
