## 先看一个不会报错的坏改动

上一站读过这张表的形状：一行等于一次动作，`kind` 那一列记的是"哪件事"。现在做一次看起来很安全的改动——把登录那一位的名字从 `login` 改成 `sign_in`，理由是"以后还要记别的动作，名字起得更清楚一点"。

改完之后：登录照常成功、写库照常返回成功、接口照常 200、页面照常渲染。唯一变了的是仪表盘上"登录次数"这一类**从此是 0**，因为库里躺着的新行叫 `sign_in`，而查询按老名字统计。而且这件事在库里查不出来：你去翻 `meter_events`，每一行的 `kind` 都是一个正常的字符串。

这不是假设，`db/tables/meter-events.ts` 与 `server/services/metrics/index.ts` 两处注释早就写着这个代价（那列是 text 而不是 enum，因为动作种类会一路加，枚举每加一个值就是一次建表变更；代价是数据库不拦拼错的值）。**这一站的发现是：注释写得对，而仓库里没有任何东西核对过它。** 下面先补判据，再把它撞三次。

## 五条接线判据，先看基线

`test/unit/meter-write-surface.test.ts`，五条，扫的是生产代码（`server/`、`app/`、`shared/` 三个目录，剥掉注释之后再匹配）：

```
[写入口] {"扫到的文件数":62,"写这张表的文件":["server/services/metrics/index.ts"]}
[手拼 kind] {"现场":[]}
[kind 常量] {"定义处":["server/services/metrics/index.ts"],"取值":{"METER_KIND_LOGIN":"login"}}
[记账调用点] {"文件":["server/api/auth/github/callback.get.ts","server/api/auth/verify.get.ts"],"条数":2}
[名字对账] {"对上的文件数":2,"分家的":[]}
```

各自挡的是：这张表只有一支笔能写（`insert(meterEvents)` 只许出现在服务层那一处）；`kind:` 后面不许出现字符串字面量，只能引常量；常量的定义处唯一、取值集合就是这一份；该记账的动作都记了（调用点清单钉死，少一处就红）；**同一件事在审计表里叫什么，在计量表里也得叫什么**。

第一条读数里"扫到的文件数 62"那一位不是装饰：这类"某样东西不存在"的判据，必须同时打印扫到了多少文件，否则一行没读也能通过。

## 撞第一次：改一个字母，写还是成功

把 `METER_KIND_LOGIN` 的值改成 `sign_in`（不改其它任何一处），`test/unit/meter-sql.test.ts` 里那条打真 SQL 的用例先给出结果：

```
[计量 INSERT] {"写成功":true,"语句":"insert into \"meter_events\" (\"id\", \"user_id\", \"kind\", \"occurred_at\") values (default, $1, $2, default)","参数":["3f2504e0-4f89-41d3-9a0c-0305e82c3301","sign_in"],"参数个数":2}
```

**写成功是 true**——库收了。同趟判据红四条，跨三份文件：

```
[kind 常量] {"定义处":["server/services/metrics/index.ts"],"取值":{"METER_KIND_LOGIN":"sign_in"}}
[名字对账] {"对上的文件数":2,"分家的":["server/api/auth/github/callback.get.ts→sign_in","server/api/auth/verify.get.ts→sign_in"]}
AssertionError: expected 'sign_in' to be 'login' // Object.is equality
AssertionError: expected [ 'sign_in' ] to deeply equal [ 'login' ]
AssertionError: expected [ { …(3) }, { …(3) } ] to deeply equal []
AssertionError: expected [ …(2) ] to deeply equal [ …(2) ]
 Test Files  3 failed | 1 passed (4)
      Tests  4 failed | 18 passed (22)
```

最后那一条 `expected [ …(2) ] to deeply equal [ …(2) ]` 是打真 SQL 那条：参数第二位变了。中间那条 `[名字对账]` 才是这一节的重点：**审计那侧写的是字面量 `action: 'login'`，计量这侧写的是常量，今天相等，但没有任何东西把它们绑在一起**。改名字那天，两张表就开始各说各话——而"事后把登录与计数拼成一条时间线"正是这两张表存在的全部理由。

顺带一条判据自己的弯路：第一版的 `[名字对账]` 只认常量名，遇到手拼的字面量就打印成 `"分家的":["…→"]`，箭头后面是空的，读数看不懂自己在说什么。改成"是常量就换成它的值、不是常量就把原样打出来"之后，同一件事的读数变成能自己解释的。**判据的打印也是给人读的接口**，这一条在这条线上已经是第三次派上用场。

## 撞第二次：第二支笔

仪表盘想多记一类"看过几次"，最自然的做法就是在那个接口里顺手写一行：

```ts
// 临时改动，跑完判据就还原了
await useDb().insert(meterEvents).values({ userId: user.id, kind: 'page_view' })
```

同趟两条红，一份改动两个面：

```
[写入口] {"扫到的文件数":62,"写这张表的文件":["server/api/console/metrics.get.ts","server/services/metrics/index.ts"]}
[手拼 kind] {"现场":["server/api/console/metrics.get.ts"]}
AssertionError: expected [ …(2) ] to deeply equal [ 'server/services/metrics/index.ts' ]
AssertionError: expected [ 'server/api/console/metrics.get.ts' ] to deeply equal []
 Test Files  1 failed (1)
      Tests  2 failed | 3 passed (5)
```

两条判据指向的是同一个决定的两面：**新增一类动作的正确路径是"在服务层加一个常量、在那里写"，而不是"在接口里就地拼一个字符串"**。判据把这条路走死之后，后面的人想加类别就必须经过那唯一一处。

## 失败日志里那句 reason 是别人的话（这一站改了一行代码）

`recordMeterEvent` 的承诺是"落表失败不阻断业务动作"。把假库换成三种会失败的样子（驱动抛 Error、抛一个字符串、抛 `null`），这半句**三种都成立**：都回 `false`、都不把异常交给调用方、都只打一行日志。

问题全在日志那一行。改之前，三种不同的故障打出来的是同一句话：

```
[计量·写失败(Error)] {"返回值":false,"日志条数":1,"那一行":"{\"ts\":\"2026-10-18T01:46:21.261Z\",\"level\":\"error\",\"msg\":\"meter_write_failed\",\"requestId\":\"req-meter-1\",\"kind\":\"login\",\"reason\":\"Failed query: insert into \\\"meter_events\\\" (\\\"id\\\", \\\"user_id\\\", \\\"kind\\\", \\\"occurred_at\\\") values (default, $1, $2, default)\\nparams: 3f2504e0-4f89-41d3-9a0c-0305e82c3301,login\"}"}
[计量·写失败(字符串)] {"返回值":false,"日志条数":1,"那一行":"{\"ts\":\"2026-10-18T01:46:21.271Z\",\"level\":\"error\",\"msg\":\"meter_write_failed\",\"requestId\":\"req-meter-1\",\"kind\":\"login\",\"reason\":\"Failed query: insert into \\\"meter_events\\\" (\\\"id\\\", \\\"user_id\\\", \\\"kind\\\", \\\"occurred_at\\\") values (default, $1, $2, default)\\nparams: 3f2504e0-4f89-41d3-9a0c-0305e82c3301,login\"}"}
[计量·写失败(null)] {"返回值":false,"日志条数":1,"那一行":"{\"ts\":\"2026-10-18T01:46:21.273Z\",\"level\":\"error\",\"msg\":\"meter_write_failed\",\"requestId\":\"req-meter-1\",\"kind\":\"login\",\"reason\":\"Failed query: insert into \\\"meter_events\\\" (\\\"id\\\", \\\"user_id\\\", \\\"kind\\\", \\\"occurred_at\\\") values (default, $1, $2, default)\\nparams: 3f2504e0-4f89-41d3-9a0c-0305e82c3301,login\"}"}
```

三个症状一次齐：真原因一个字没留（`duplicate key…` 与 `pool exhausted` 都不在）；整条语句连参数进了日志文件（这里的参数就是这个人的编号）；**三种故障同一句话**——夜里看到这句的人会去查表约束，而实际是连接池没了。

原因在装上的包里可以直接翻到：`node_modules/drizzle-orm/errors.js:10-19`，那个类的构造函数是 `super(\`Failed query: ${query}\nparams: ${params}\`)`，同时把原始的那个东西挂在 `cause` 上。所以原代码那句 `reason: (error as Error).message.slice(0, 200)` 抄的正是包装那一层。改法是一行，取 `cause`：

```ts
const cause = (error as { cause?: unknown }).cause
reason: (cause instanceof Error ? cause.message : String(cause ?? '(驱动没给原因)')).slice(0, 200),
```

改完同三种形状再跑一遍：

```
[计量·写失败(Error)] {"返回值":false,"日志条数":1,"那一行":"{\"ts\":\"2026-10-18T03:57:15.596Z\",\"level\":\"error\",\"msg\":\"meter_write_failed\",\"requestId\":\"req-meter-1\",\"kind\":\"login\",\"reason\":\"duplicate key value violates unique constraint\"}"}
[计量·写失败(字符串)] {"返回值":false,"日志条数":1,"那一行":"{\"ts\":\"2026-10-18T03:57:15.599Z\",\"level\":\"error\",\"msg\":\"meter_write_failed\",\"requestId\":\"req-meter-1\",\"kind\":\"login\",\"reason\":\"pool exhausted\"}"}
[计量·写失败(null)] {"返回值":false,"日志条数":1,"那一行":"{\"ts\":\"2026-10-18T03:57:15.600Z\",\"level\":\"error\",\"msg\":\"meter_write_failed\",\"requestId\":\"req-meter-1\",\"kind\":\"login\",\"reason\":\"(驱动没给原因)\"}"}
```

判据里除了断言 `reason` 那一位，还加了两位不许出现的：整行不许含 `insert into`、不许含那个用户编号。**"日志里不许出现语句与参数"这件事，靠注释是守不住的**，它是这一节新增的断言之后的新约束。

⚠ 同一形状的写法在 `server/services/audit.ts` 里还有一份（`audit_write_failed` 那一行一模一样）。这一站没测它的行为、也没动它，留给后面审计那条线——两处的判据不该由一条计量用例来管。

## 撞第三次：把修好的那一行退回

判据要能被它自己那个坏法打红，所以把 `reason` 那一行改回原来的写法，跑一次：

```
AssertionError: expected 'Failed query: insert into "meter_even…' to be 'duplicate key value violates unique c…' // Object.is equality
AssertionError: expected 'Failed query: insert into "meter_even…' to be 'pool exhausted' // Object.is equality
AssertionError: expected 'Failed query: insert into "meter_even…' to be '(驱动没给原因)' // Object.is equality
 Test Files  1 failed (1)
      Tests  3 failed (3)
```

三条全红（`Error`、字符串、`null` 各一条），三句 `expected` 左边都是同一句话——那正是上面那个症状本身。改回新写法之后 `Test Files 1 passed (1)`／`Tests 3 passed (3)`，与静态那份合起来 `Tests 8 passed (8)`。（读数里那两处 `…` 是运行器自己截的，不是本文省略。）**这一节是本轮唯一一处应用代码改动。**

## 复跑与排错

```
npm run test:unit -- test/unit/meter-write-surface.test.ts test/unit/meter-write-failure.test.ts
```

八条，两条文件合跑 `Test Files 2 passed (2)`／`Tests 8 passed (8)`；并进整层是 `Test Files 39 passed (39)`／`Tests 256 passed (256)`。

| 撞上的现象 | 大概率是哪一条 | 先做什么 |
| --- | --- | --- |
| 仪表盘上某一类永远是 0，库里却有行 | `kind` 的写入值与统计用的名字分家了 | 跑 `[kind 常量]` 与 `[名字对账]` 那两条，后者会把分家的文件点名 |
| 日志里出现整条 SQL 与参数 | 失败处理器抄的是包装那句 `message` | 抄 `cause`；顺带检查别的 catch 是不是同一形状（`server/services/audit.ts` 里就还有一份） |
| 登录成功但计量少一行 | 落表失败被吞了（设计如此） | 看那条 `meter_write_failed`，它回 `false` 不打扰业务；要找的是为什么失败，而不是为什么没报错 |
| 想加一类新动作 | 在接口里就地 `insert` | 在服务层加常量、由 `recordMeterEvent` 写；判据 `[写入口]` 与 `[手拼 kind]` 会挡住就地拼字符串 |
| 判据一条都没红但你不确定它扫到了东西 | —— | 看 `[写入口]` 读数里的"扫到的文件数"，本轮是 62 |

## 交付前自查

- 五条判据各有现场读数，其中三条各被一个变异打红（常量值改一次、接口里加第二支笔一次）
- 打真 SQL 那份判据把"改名字之后写照样成功"这件事打印出来了：`"写成功":true` 配 `"参数":[…,"sign_in"]`
- 失败日志那一节是**本轮唯一的应用代码改动**，退回原写法能把三条用例全打红
- 审计侧那份同形写法照实记成未处理，没有顺手改、也没有装作看不见
- 本轮依旧没有连库、没有写库：所有"库里真有一行时统计对不对"的判断都不在结论里
