## 五行代码里唯一要紧的那一行

`server/api/console/metrics.get.ts` 的函数体只有三行：

```ts
  const user = requireUser(event)

  const metrics = await metricsForUser(user.id)

  return {
    metrics,
  }
```

它的注释里写着一句很硬的话：`where user_id = ?` 的值不可能由请求里的参数决定——"把 id 放进查询串那种写法，在这里等于把看别人的数字做成一个功能"。前端同学最常见的问题就是这个：`我这边已经有他的编号了，`?userId=…` 传过去不行吗？`

上一站量的是"算错数字"的坏法；这一站量的是**取数的对象换成了谁**。已经有一份判据在管"挂没挂守卫、守卫在不在读参数与任何 `await` 之前"（`test/unit/api-guard-surface.test.ts`），但它管不到这样一件事：守卫照挂、顺序也对，而取数那一步把身份来源换成了请求里的值。那种写法在"顺序"这一层是完美的。

## 新判据六条

`test/unit/metrics-boundary.test.ts`，扫的是源码（剥注释），六条基线：

```
[取数的那一位] {"实参":"user.id","守卫给的变量":"user"}
[从请求里取人] {"出现的写法":[]}
[谁读会话里的人] {"接口自己读":false,"守卫里读":true}
[顺序] {"守卫行":18,"取数行":20,"顺序对":true}
[响应体的键] {"键":["metrics"],"那个块":"metrics,"}
[对照·全端下线] {"权限行":20,"读参数行":26,"用了参数":true,"先过权限":true}
```

最后一条是**正控制**，也是这一节的分界线：后台那条全端下线的接口**确实**读路径参数（`getRouterParam(event, 'userId')`），第 26 行；但它在第 20 行先 `requireAdmin(event)`。所以规矩不是"不许用请求里的参数"，而是**用了就必须先过权限，而权限判定必须在那一行之前**。两条判据的期望值不一样，一份文件里同时钉着，才看得出差别在哪。

第三条那位也是同一个思路：接口里不许自己读 `event.context.user`——要人就调守卫。正控制是"守卫那一层确实读它"，扫得到才说明前面那个 `false` 不是空扫。

## 撞第一遍：把 user.id 换成查询串里的 userId

```ts
  const metrics = await metricsForUser(String(getQuery(event).userId))
```

这一行改动之后，鉴权那一步一个字没动。红的两条：

```
[取数的那一位] {"实参":"String(getQuery(event","守卫给的变量":"user"}
[从请求里取人] {"出现的写法":["getQuery("]}
AssertionError: expected 'String(getQuery(event' to be 'user.id' // Object.is equality
```

而这条照绿：`[顺序] {"守卫行":18,"取数行":20,"顺序对":true}`。**"顺序对"不等于"边界对"**——这一句是本节想留给读者的全部。真按这行上线，后果是每个登录用户都能通过改一个数字拿到别人的计数，而页面层、守卫层、顺序判据三处都看不出异常（这与 773 那站"`requireAdmin` 降级成 `requireUser`"是同一类形状：坏在数据边界，不在导航）。

## 撞第二遍：返回体里顺手多带一份身份

```
[响应体的键] {"键":["metrics","email"],"那个块":"metrics, email: user.email,"}
AssertionError: expected [ 'metrics', 'email' ] to deeply equal [ 'metrics' ]
```

红一条。为什么这一条值得钉：邮箱与角色这些身份字段页面**另有来源**（服务端中间件挂进负载的那一位，第七条线读过），接口再发一份就等于同一件事有两个地方在说，两处会开始对不上——上一站的 `total` 也是同一个道理的另一面。这一位是"少带一份就少一处能出错的地方"。

## 撞第三遍：先取数、再鉴权

```ts
  const user = event.context.user as { id: string, email: string }
  const metrics = await metricsForUser(user.id)
  requireUser(event)
```

三条红跨两份判据文件（新的一份加上上一站那份 `api-guard-surface`）：

```
[谁读会话里的人] {"接口自己读":true,"守卫里读":true}
[顺序] {"守卫行":22,"取数行":20,"顺序对":false}
AssertionError: expected '(没有那句守卫)' to be 'user' // Object.is equality
AssertionError: expected 22 to be less than 20
AssertionError: expected true to be false // Object.is equality
 Test Files  2 failed (2)
      Tests  4 failed | 7 passed (11)
```

注意"实参是不是守卫给的那个人"那条也红了（`'(没有那句守卫)'`）：**这三条判据是从三个不同角度盯同一行的**，所以一处坏改动会同时撞响好几个地方——这不是重复，而是这一层只需要一条规矩的代价（另一种写法：让 `metricsForUser` 自己收 `event` 并读会话，接口就没有可换的来源，代价是那层不再是个纯取数函数）。

## 端到端那一层：带参数到底会看到什么

`test/e2e/metrics-endpoint.spec.ts` 加了一条（产物服务、没有库，`E2E_PORT=3243`，`3 passed (18.0s)`／`3 skipped`）：

```
[metrics anon] {"status":401,"code":"UNAUTHENTICATED"}
[metrics method] {"postNested":{"status":404,"type":"application/json"},"postTop":{"status":404,"type":"application/json"},"getPost":{"status":404,"type":"application/json"}}
[metrics 带参数] {"status":401,"data的键":["code","requestId"],"响应里有那个编号":true,"url那一位":"http://localhost:3243/api/console/metrics?userId=7c9e6679-7425-40de-944b-e07fc1f90ae7"}
```

三条结论：没配库时这个接口对匿名仍是 401 而不是 500；带不带 `?userId=` 对没登录的人是**同一个 401、同一个 `data` 形状**（`['code','requestId']`，一位都不许多）；第三个读数最值得看一眼——框架把**整条地址连查询串**原样回声在 `url` 那一位，所以"响应里出现了那个编号"是 `true`。

这个回声无害：那个编号是调用者自己填的，他本来就知道。但判据要按地址里有没有凭据来选通道，这正是 767 那一站把登录链接的兑换接口改成自己组装响应的原因：那条路由的地址里带的是一次性凭据，框架回声一次就等于把凭据再发回去一遍。同一个站里两种形状，判据不能全站统一。

## 判据自己先红了一次

`[响应体的键]` 那条第一次跑是红的，红在我写的判据上：`return { metrics, }` 用的是**简写键**（没有冒号），而我的正则只认 `键:` 那种写法；闭合括号前还有缩进，`\n\}` 也匹配不到。两处一起改（键位认 `:` 也认 `,`、闭合用 `\n\s*\}`），并把那个块原样打进读数——所以现在读数里能看到 `"那个块":"metrics,"` 这半句，判据读错了也能一眼看出来。

顺带把这份规格文件头的一句过期注释改了：它写着"默认那趟钉的是……照样按方法回 **405**"，而上面 `[metrics method]` 的现量是三种形状全部 **404**。文件头的这句改成现量的形状，"405"那句留给下一站处理（它写在接口自己的注释里）。

**同一份新判据还被类型检查拦了一次**，而且是在它跑绿之后：那条端到端用例打出的就是 `3 passed`，而 `npm run typecheck` 报

```
test/e2e/metrics-endpoint.spec.ts(66,10): error TS18048: 'json.data' is possibly 'undefined'.
```

原因很具体：我把响应体标成 `{ data?: … }`，读的时候先 `json.data ?? {}` 打了读数，断言那行却直接 `json.data.code`——运行时那位确实存在（框架的 401 一定带 `data`），类型上却是"可能是 undefined"。**跑起来了不等于类型也过**：前面几站已经为这句话撞过三次（分别是 `TS2352`、`TS2367`、`TS2783`），本轮又换了一种形状。所以聚合命令里那一步类型检查不能省——改成 `json.data?.code` 之后八项全 ok。

## 复跑与排错

```
npx vitest run --config vitest.config.ts test/unit/metrics-boundary.test.ts test/unit/api-guard-surface.test.ts
E2E_PORT=3243 npm run test:e2e -- --project=site test/e2e/metrics-endpoint.spec.ts
```

| 撞上的现象 | 是哪一位错了 | 先跑哪条 |
| --- | --- | --- |
| 换个数字就能看到别人的计数 | 取数的对象来自请求，不是会话 | `[取数的那一位]` 与 `[从请求里取人]` |
| 顺序判据绿着但接口仍能看别人 | 守卫在前面、取数却换了来源 | 别只看顺序：跑 `[取数的那一位]` |
| 后台能用路径参数、会员区不能 | 两条规矩本来就不同 | `[对照·全端下线]` 给的是"先过权限才许用参数" |
| 页面上邮箱与数字两处显示不一致 | 接口多带了一份身份字段 | `[响应体的键]` 期望就一位 `metrics` |
| 匿名带参数拿到 500 | 没配库时的降级没做好 | `[metrics anon]` 那条端到端 |

## 交付前自查

- 六条判据各有基线读数，三个变异分别打红 2 条、1 条、4 条，红条数与消息逐字贴出
- 与上一站那份顺序判据的分工写明：它管"守卫在不在前面"，这一份管"取数用的是谁"
- 正控制两处：后台那条确实用参数（证明扫得到），守卫那一层确实读会话（证明不是空扫）
- 端到端读到的查询串回声按现量写，无害的原因与"带凭据的那条路由不能这样"的边界都留在正文
- 依旧没有连库：`带会话打这个接口返回本人行数` 那三条仍是 `3 skipped`，本节没写任何"真会话下如何"的结论
