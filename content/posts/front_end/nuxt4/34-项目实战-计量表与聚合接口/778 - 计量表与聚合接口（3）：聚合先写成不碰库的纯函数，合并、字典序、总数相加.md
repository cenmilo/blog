## 页面拿到的是两个数，对不上时谁负责

仪表盘要显示"总共 8 次"，还要显示"登录 3 次、导出 5 次"。这两句话里的数字来自同一次查询，但**加起来对不对**这件事，是应用里某一行代码决定的。`server/services/metrics/index.ts` 里分成两层：

```ts
export async function metricsForUser (userId: string, since?: Date): Promise<MetricsSummary> { … }   // 碰库的那一半
export function summarizeMeterRows (rows: MeterRow[]): MetricsSummary { … }                          // 不碰库的那一半
```

分成两层不是讲究：不碰库的那一半可以在单测里把手写期望值钉死（上一线写过五条），碰库的那一半则一直没被判据看过一眼。**注释里写着三条决定**——同一个 `kind` 出现两次要合并、顺序按 `kind` 字典序排、`total` 是各行相加而不是再查一次 `count(*)`。这一站把这三条一条条撞出来，撞完删掉一句看起来更安全的代码。

## 新判据六条，先看基线

`test/unit/metrics-read.test.ts`。假库按数组形状给行（`rowMode: "array"` 那件事上一站量过），六条读数：

```
[读·乱序] {"假库回的行":[["member","1"],["login","2"]],"回来的形状":{"total":3,"kinds":[{"kind":"login","count":2},{"kind":"member","count":1}]}}
[读·同名] {"假库回的行数":2,"回来的形状":{"total":9,"kinds":[{"kind":"login","count":9}]},"kinds条数":1}
[读·空表] {"回来的形状":{"total":0,"kinds":[]},"total类型":"number"}
[读·不变式] {"total":8,"各行相加":8,"kinds条数":2}
[读·一条语句] {"发出几条":1,"total":7,"各行相加":7}
[读·时间窗] {"语句":"select \"kind\", count(*) from \"meter_events\" where (\"meter_events\".\"user_id\" = $1 and \"meter_events\".\"occurred_at\" >= $2) group by \"meter_events\".\"kind\"","参数":["3f2504e0-4f89-41d3-9a0c-0305e82c3301","2026-10-01T00:00:00.000Z"],"参数个数":2}
```

第一行是"字典序"这条：假库先给 `member` 再给 `login`，交出去的是 `login` 在前。第二行是"合并"：给两行同名，交出去一条、计数相加。第三行是页面能直接渲染的形状——空表回 `{total: 0, kinds: []}` 而不是 `null` 或缺字段。最后一行是那句一直空着的 `since`：传了时间窗，SQL 里就多一位条件，**边界值是应用给的**（参数第二位是那个时刻写成文本交上去的，不是 SQL 里的 `now()`）。

## 撞第一个：把 SQL 的 group by 摘掉

这条最想知道：既然 SQL 里已经 `group by "kind"`，纯函数里那句合并是不是白写？把 `.groupBy(meterEvents.kind)` 摘掉跑一遍：

```
[计量 SELECT] {"语句":"select \"kind\", count(*) from \"meter_events\" where \"meter_events\".\"user_id\" = $1","参数":["3f2504e0-4f89-41d3-9a0c-0305e82c3301"],"假库回的行":[["login","2"]],"回来的形状":{"total":2,"kinds":[{"kind":"login","count":2}]},"total类型":"number","count类型":"number"}
AssertionError: expected 'select "kind", count(*) from "meter_e…' to contain 'group by'
 Test Files  1 failed | 2 passed (3)
      Tests  1 failed | 15 passed (16)
```

**只红一条，红在 SQL 写法那一层；行为层的十五条一条没红**，`[读·同名]` 照样交出 `{total: 9, kinds: [{kind: 'login', count: 9}]}`。这两件事合起来才是答案：`group by` 是今天这句 SQL 的写法，合并是"上游没合并时也不发出两个同名键"的保证——**判据不许假设上游一定是对的**，所以两条都要留着，一条防写法被改，一条防写法失效时数字仍然不自相矛盾。

## 撞第二个：把排序摘掉，顺便撞出"失败消息两边长得一样"

`.sort(...)` 那一行摘掉，两条红：

```
AssertionError: expected { total: 3, kinds: [ { …(2) }, …(1) ] } to deeply equal { total: 3, kinds: [ { …(2) }, …(1) ] }
```

这条消息讲不了话——左右两边打印出来一模一样（运行器把对象内容截成了 `…(2)`），读的人看不出差别在哪。于是给那条断言补一句自己的话（顺序单独断言一次，把实际顺序写进消息）：

```
AssertionError: 输出顺序不是 kind 字典序：member、login: expected [ 'member', 'login' ] to deeply equal [ 'login', 'member' ]
```

同一处坏改动，第二次的消息自己就说清了。**这是这条线上第四次遇到"判据的打印也是接口"**（前三次：点名列出行号、把原值带进失败消息、字面量要原样打出来）。

## 撞第三个：总数改成再查一次

把 `total` 从"各行相加"改成"另发一条 `select count(*)`"——这是最容易说服自己的写法（"让数据库算总数，不是更准吗"）。假库为此备好第二份回包：第一条语句给分项，第二条给一个对不上的数。

```
[读·一条语句] {"发出几条":2,"total":4,"各行相加":7}
AssertionError: 这个问题应当只发一条语句，实际发了 2 条（总数被改成另查一次）: expected 2 to be 1
```

`"total":4` 配 `"各行相加":7`：**屏幕上就是"总共 4 次"与"登录 3、导出 5"并存**。这不是抬杠出来的数字——两次查询之间真插一行时，库里两个时刻的行数本来就不同，页面上就会出现"分项加起来比总数大"这种没人能解释的画面。这一趟共 7 条判据红（`⎯⎯⎯ Failed Tests 7 ⎯⎯⎯`），其中两条是回包错位带来的次生红（`total` 变 `NaN`），一条是那条不变式与"只发一条语句"的正击。

顺带把"什么形状的坏数据会被发现"这件事也撞了一次，见下一节。

## 撞第四个与第五个：那句 `Number(row.n)` 该留还是该删

读侧原来是这一句：

```ts
return summarizeMeterRows(rows.map(row => ({ kind: row.kind, n: Number(row.n) })))
```

`Number(...)` 看着像是必需的（数据库的聚合值在线路上本来就是文本）。**上一站读过另一面**：`test/unit/meter-sql.test.ts` 的读数里写着 `count类型":"number"`——`count()` 自带解码器，交给应用的已经是数字。这一站把它撞实：

```
Test Files  3 passed (3)
      Tests  17 passed (17)
```

把 `Number(...)` 摘掉，**相关十七条判据一条没红**。也就是说那句转换今天不可达，且没有任何判据在保护它。

那它有没有"万一"的价值？再撞一次：让字符串形状真的漏过来（把 `n` 换成文本形状）：

```
AssertionError: expected { total: '002', kinds: [ { …(2) } ] } to deeply equal { total: 2, kinds: [ { …(2) } ] }
AssertionError: expected { total: '00201', …(1) } to deeply equal { total: 3, kinds: [ { …(2) }, …(1) ] }
AssertionError: expected [ { kind: 'login', count: '027' } ] to deeply equal [ { kind: 'login', count: 9 } ]
AssertionError: expected '00502' to be 7 // Object.is equality
      Tests  5 failed | 12 passed (17)
```

`'002'`、`'00201'`、`'00502'`——字符串相加的拼接形状，五条判据立刻红。**结论是反的**：留着 `Number(...)`，这种形状变化会被它悄悄抹平（页面上的数字照样对，判据也不会红，而投影已经被改坏了）；删掉它，形状信号就落在判据上。于是本轮第二处应用代码改动是**删**：

```ts
  // 这里不做任何数值转换：`count()` 自带解码器，交出来的已经是 number
  // （`test/unit/meter-sql.test.ts` 的 `count类型` 那一位钉着）。
  // 写一句 `Number(row.n)` 反而会抹平一个值得看到的信号——哪天投影换成不带动儿的
  // 原始 `sql`，字符串形状会在这里直接撞红（本轮变异量过：总数会变成 `'00201'` 那种拼接）。
  return summarizeMeterRows(rows)
```

改完 `npx vitest run` 六份计量相关判据合跑 `Test Files  6 passed (6)`／`Tests  31 passed (31)`，`npm run typecheck` 也过（drizzle 推出来的行类型 `n` 就是 `number`，所以映射那一步整个省掉了）。

## 复跑与排错

```
npm run test:unit -- test/unit/metrics-read.test.ts test/unit/metrics-summary.test.ts test/unit/meter-sql.test.ts
```

| 撞上的现象 | 是哪条决定失效了 | 本轮对应的变异 |
| --- | --- | --- |
| 页面上"总共 4 次"与"登录 3、导出 5"并存 | 总数被改成另查一次 | 摘掉 `.groupBy` 只红一条；把总数改成另查一次红七条，`[读·一条语句]` 直接把"发了 2 条"报出来 |
| 分项里出现两条同名 | 合并那条被删（或页面自己按行渲染） | 反过来做：摘掉 `group by` 后 `[读·同名]` 仍交出 1 条，证明合并真的在兜底 |
| 分项顺序每次刷新都在变 | 排序被摘或跟着库的返回顺序走 | 摘 `.sort(...)` 红 2 条，消息要自带实际顺序 |
| 数字变成 `'00201'` 那种拼接 | 上游给了文本形状 | 这正是现有断言能看见的形状，所以不要用 `Number()` 把它抹平 |
| 空数据时页面报错 | 空表回的不是 `{total: 0, kinds: []}` | `[读·空表]` 那条钉着可直接渲染的形状 |

## 交付前自查

- 注释里的三条决定各有一个能打红的变异，红条数与读数都逐字贴出
- 两层分工用一次"只红一条"的变异说清了：SQL 写法与行为保证不是同一件事，不能只留一边
- 失败消息两边打印相同这一处当场改掉，并把规矩落成"顺序断言自带实际顺序"
- 本轮的应用代码改动只有一处（删掉那句数值转换）；上一站的日志改动（`reason` 读 `cause`）不在本篇账上，别混着算
- 依旧没有连库：`[读·同名]` 那种"两行同名"是假库喂出来的，真库里今天拿不到（它有 `group by`），这一点照实写
