首页源码里躺着三段外部脚本：统计、客服悬浮窗、地图。功能都在，报告里 INP 红了，主线程上是一串几十毫秒的长任务。

这一篇只讲一件事：**官方文档给了哪几条加载路径**，以及每条的原文范围到哪里。

## 官方怎么定性这件事

Scripts 一节的开头是这句：

> Third-party resources like analytics tools, video embeds, maps, and social media integrations enhance website functionality but can significantly degrade user experience and negatively impact Interaction to Next Paint (INP) and Largest Contentful Paint (LCP) scores.

四类来源被点名（统计、视频嵌入、地图、社媒集成），两个受害指标也点名了。这一节接着推出 Nuxt Scripts，定位是"lets you load third-party scripts with better performance, privacy, security and DX"。

## 路径一：useHead 的 script 数组

`useHead` 是最直接的一条。参数表里那一行是这么写的：

> `script`: `Script[]` - Array of script objects. Each element is mapped to a `<script>` tag, where object properties correspond to HTML attributes.

也就是说：**数组里每个对象变成一个 `<script>`，对象的键就是 HTML 属性名**。官方用法示例给的是内联形式：

```vue [app/app.vue]
<script setup lang="ts">
useHead({
  title: 'My App',
  meta: [
    { name: 'description', content: 'My amazing site.' },
  ],
  bodyAttrs: {
    class: 'test',
  },
  script: [{ innerHTML: 'console.log(\'Hello world\')' }],
})
</script>
```

类型签名里 `script?: Script[]` 与 `noscript?: Noscript[]` 并列存在，这两项都在同一张参数表里。

**这一条路官方只到"怎么把标签写出来"为止**——没有给加载顺序、没有给 defer/async 建议、没有给"什么时候不该用 `useHead` 注脚本"的边界。

紧接着有一条 `::warning`，是这条路上唯一的安全提醒：

> If the data comes from a user or other untrusted source, we recommend you check out `useHeadSafe`.

**内容来自用户或任何不可信来源时，改用 `useHeadSafe`。**

## 路径二：Nuxt Scripts 的三种控制

模块那一节的定位句是：

> Nuxt Scripts provides an abstraction layer on top of third-party scripts, providing SSR support and type-safety and while still giving you full low-level control over how a script is loaded.

三个关键词：**抽象层**、**SSR 支持与类型安全**、**仍然保留对加载方式的低层控制**。官方示例展示的正是这第三种控制：

```ts
const { onLoaded, proxy } = useScriptGoogleAnalytics(
  {
    id: 'G-1234567',
    scriptOptions: {
      trigger: 'manual',
    },
  },
)
// queue events to be sent when ga loads
proxy.gtag('config', 'UA-123456789-1')
// or wait until ga is loaded
onLoaded((gtag) => {
  // script loaded
})
```

把示例里的注释翻成动作，是三种不同意图：

| 写法 | 官方注释 | 意图 |
| --- | --- | --- |
| `scriptOptions: { trigger: 'manual' }` | — | 注册这个脚本但**不由它自己触发加载**，什么时候加载由你决定 |
| `proxy.gtag('config', ...)` | queue events to be sent when ga loads | 先**把事件排进队列**，等脚本加载完再发出去 |
| `onLoaded((gtag) => { ... })` | or wait until ga is loaded | **等脚本就绪**再执行那段逻辑 |

这条路与 `useHead` 的差别不在"能不能注脚本"，而在**有没有一个能排队、能等就绪的时机模型**。示例里那些参数（`id`、`trigger` 的可选值、`proxy` 的完整能力）都不在 Nuxt 核心文档里，官方指向 scripts.nuxt.com。

## 路径三：把它关掉——但范围要说清

`noScripts` 路由规则那句原文是：

> Disables rendering of Nuxt scripts and JS resource hints for sections of your site.

请注意宾语：**Nuxt 脚本与 JS 资源提示**。第三方脚本不在这句话的范围内，文档也没写 `noScripts` 会不会连带影响你自己用 `useHead` 注入的外部脚本——这属于文档未说明，要确认就在开了这条规则的路由上看输出 HTML 里那些外部 `<script>` 还在不在。

顺带两条与脚本注入时机有关的、别处已确认的事实：

- **流式渲染下注册时机有硬边界**。450 讲过：壳冲出去之后才注册的 head 标签会变成"客户端内联脚本打的补丁"，不在 `botRegex` 里的爬虫与 `curl` 完全看不到。用 `useHead` 注脚本时，如果注册发生在 `await` 之后，就落进这一类。
- **head 里的排列由 headNext 处理**。官方在 `experimental.headNext` 那节写它做两件事："Add the capo.js head plugin in order to render tags in of the head in a more performant way" 与 "Uses the hash hydration plugin to reduce initial hydration"，且**默认开启**。

## 官方没给的三件事

- 没有"脚本应该放 `<head>` 还是 `<body>` 末尾"的规定。
- 没有 `async`/`defer`/`type="module"` 的选择建议。
- 没有 Cookie 同意（consent）与脚本加载联动的官方配方——那属于 Nuxt Scripts 模块的能力，核心文档一句未提。

所以照抄任何一篇外部教程里的写法时，要清楚那不是 Nuxt 的规定，而是通用 Web 做法。

## 自查

- 官方把第三方脚本绑在 **INP 与 LCP** 上，点名统计、视频嵌入、地图、社媒四类。
- `useHead` 的 `script` 数组：每个元素一个 `<script>`、对象属性即 HTML 属性；不可信来源改 `useHeadSafe`。
- Nuxt Scripts 那三条能力是"注册但不立刻加载／先排队／等就绪"，这是它和 `useHead` 的真正分工差别。
- `noScripts` 关的是 **Nuxt 自己的脚本与 JS 资源提示**，不含第三方脚本这一说。
- 流式渲染下 `await` 之后注册的脚本标签只对跑了 JS 的客户端可见。
