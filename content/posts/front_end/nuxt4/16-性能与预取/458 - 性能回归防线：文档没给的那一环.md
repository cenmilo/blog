## 先确认缺什么

测试页的整体结构是六块：Installation、Unit Testing、End-To-End Testing、Built-In Mocks、Helpers、Testing in a Browser。在这六块里，`performance`、`budget`、`Lighthouse`、`metric` 四个词**一次都没出现**。

也没有下面这些 API：断言 LCP 数值、断言 bundle 字节数、断言长任务数量。所以任何教程里写的"Nuxt 自带性能预算断言"都不是 4.x 文档的内容——**文档未记载这一层**。

## 文档给的测试能力只有这些

| 能力 | 官方原话要点 |
| --- | --- |
| 定位 | Nuxt 通过 `@nuxt/test-utils` 提供端到端与单元测试的一等支持，这套工具也驱动着 Nuxt 自己的测试与模块生态的测试 |
| 依赖可选 | 运行时环境在 `happy-dom` 与 `jsdom` 之间选；runner 在 `vitest`、`cucumber`、`jest`、`playwright` 之间选；`playwright-core` 只在你想用内置浏览器测试工具且不把 `@playwright/test` 当 runner 时才需要 |
| Unit 环境 | **目前只支持 `vitest`**（官方括注：欢迎贡献其他 runtime） |
| `@nuxt/test-utils/module` | 可选加进 `nuxt.config`，它加的是 **Nuxt DevTools 里的一个 Vitest 集成**，支持在开发时跑单元测试 |
| e2e 上下文 | 每个用到 `@nuxt/test-utils/e2e` helper 的 `describe` 块里要先 `await setup({...})`；`setup` 在 `beforeAll`/`beforeEach`/`afterEach`/`afterAll` 里做环境搭建 |

这套能力的对象是**行为**（渲染出什么、点了之后有什么），不是**快慢**。

## 三个能接上的点（都有原文依据）

**一、把 e2e 打到已部署的版本上。** `host` 选项的官方说明是：

> `host`: If provided, a URL to use as the test target instead of building and running a new server. Useful for running "real" end-to-end tests against a deployed version of your application, or against an already running local server (which may provide a significant reduction in test execution timings).

配套那句还写着这类用法"typically faster than allowing the test framework to rebuild between tests"。这是文档里唯一一处把测试指向**真实部署产物**的入口。

再叠一个 `browser`：

> `browser`: Under the hood, Nuxt test utils uses `playwright` to carry out browser testing. If this option is set, a browser will be launched and can be controlled in the subsequent test suite.

默认 `false`；设了就会真的启动一个浏览器，`browserOptions.type` 可取 `chromium`、`firefox`、`webkit`，`browserOptions.launch` 是传给 Playwright 启动的选项对象。**到这里为止，能起真实浏览器，但文档没给任何取指标的 API。**

**二、`nuxt analyze` 的 CI 行为。** 这条是产物体积能自动化的唯一入口，官方原话在命令页：结果在构建完成后会起本地服务展示，**"unless you pass `--no-serve` or `CI` is set in the environment"**。也就是 CI 里它就是**安静地产出一个 HTML 文件**，落在 `.nuxt/analyze/{name}.html`，`--name` 可以给不同快照（436）。

但要看清边界：**官方没说怎么解析那个 HTML，也没给任何阈值**。"读那个文件里的数字再比较"这一段，文档没有提供方法。

**三、CI 缓存的 key 该含哪些文件。** `experimental.buildCache` 列了一份"改动即全量重建"的清单——`.nuxtrc`、`.npmrc`、`package.json`、`package-lock.json`、`yarn.lock`、`pnpm-lock.yaml`、`tsconfig.json`、`bun.lock`、`bun.lockb`（440）。这份清单正好是**给 CI 缓存算 key 的依据**：这九个文件动了还复用缓存，拿到的就是与本地不同的构建结果，你测到的体积和耗时都会失真。

## 能写与不能写

| 想防的东西 | 文档能力够不够 | 怎么写 |
| --- | --- | --- |
| 首屏 HTML 里那张 hero 图丢了 `loading="eager"` | 够 | e2e 用 `$fetch` 拿路由文档，对 HTML 断言字符串（433 的属性组合作为不变量） |
| 某个第三方脚本被挪回首屏 `<head>` | 够 | 同上，断言那段标签不在其中 |
| 取数被重复执行两次（服务端一次客户端一次） | 够 | 用 `useFetch`/`useAsyncData` 的 payload 转发语义去验（028、235） |
| 主包字节数超阈值 | **不够** | `nuxt analyze` 能产文件，但解析与判定文档没给方法 |
| LCP / INP / CLS 的数值 | **不够** | 属于 457 那三个外部工具，文档不把它们写进测试 |
| 组件初始化耗时 | **不够** | Timeline 面板只在开发期（457） |

按这三行"够"来落防线，得到的其实是**结构不变量测试**——它能挡住"优化被无意撤销"，但挡不住"实现正确但很慢"。这个差别要在团队里讲明白，别让绿勾代替了真实性能。

上面那张表把 e2e 与 HTML 断言组合成回归防线的做法，是**我按文档能力边界做的组合，不是官方配方**；官方只给能力，没给这个用法。

## 时间与产物这两条 CI 口径

跑真实产物的 e2e 会慢，官方给的默认值就是预期：`setupTimeout` 默认 **120000 ms（Windows 上 240000）**——这个超时覆盖的是"可能包含构建或生成文件"的全部准备工作；`teardownTimeout` 默认 **30000 ms**。`build` 默认 `true`，但在 `browser` 或 `server` 被关闭、或提供了 `host` 时是 `false`。`server` 默认 `true`（给了 `host` 就是 `false`），`port` 默认 `undefined`，`runner` 默认 `'vitest'`（可 `jest`/`cucumber`，官方注明目前推荐 Vitest）。

另外两条对排查 CI 里的性能问题有用：`captureServerLogs` 默认 `true`，会把服务端子进程的 stdout/stderr 收起来、通过 `getServerLogs()` 取；要恢复旧的继承 stdio 行为就设 `false`（官方说这在本地调试测试时有用）。`logLevel` 默认 `1`，可用环境变量 `NUXT_TEST_LOG_LEVEL` 覆盖。

## 自查

- 官方测试文档没有任何性能指标断言能力，"把指标写进测试"在 4.x 文档里没有对应条目。
- 能自动化的只有三件：e2e 打 `host`（真实部署）、`browser: true` 起真实浏览器、`nuxt analyze` 在 CI 下只产 HTML 文件。
- 阈值判定与那个 HTML 的解析方法，文档没给——这部分属于外部工具，不是 Nuxt 规定。
- 把"够"的三类写成结构不变量测试，能挡回退，挡不住"正确但慢"。
- CI 时长口径看 `setupTimeout` 120000/240000、`teardownTimeout` 30000、`build` 在三种条件下为 `false`。
- 构建缓存 key 要带上那九个文件，否则测到的不是同一份产物。
