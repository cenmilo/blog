"性能优化"这四个字没法直接开工。你能做的是拿一张检查表逐项对着项目看：哪些框架已经做了、哪些要你启用、哪些只能用工具量出来。官方性能那一节正好就是这么一张表，只是它没自称"清单"。

先补三个词的口径，这一节只点名了这三个指标：

- **LCP**：页面里最大那块内容画出来的时间。
- **CLS**：布局在加载过程中乱跳的程度，跳动越多分越差。
- **INP**：用户操作到下一帧画出来之间的等待。

这一节开头给的分块理由是这样的：

> Nuxt comes with built-in features designed to improve your application's performance and contribute to better Core Web Vitals. There are also multiple Nuxt core modules that assist in improving performance in specific areas.

一句里两件事：**自带的**服务于 Core Web Vitals，**核心模块**管具体某一块。后面就按这两块加"量工具""常见问题"往下排。

## 第一块：框架自带的五项

| 项 | 官方给的动作 | 落到哪 |
| --- | --- | --- |
| 链接 | `<NuxtLink>` 智能预取，默认在链接进入视口或滚动到时预取对应页的 JS | `experimental.defaults.nuxtLink.prefetchOn` |
| 混合渲染 | 按路由给不同缓存规则，决定服务端对新请求怎么响应 | `routeRules` 里的 `prerender`/`swr`/`isr`/`ssr` |
| 组件懒加载 | 组件名前加 `Lazy` 前缀，延迟到需要时才取代码 | 组件名本身，无需配置 |
| 延迟水合 | 控制组件什么时候变可交互，v3.16 加入 | `hydrate-on-visible` 这类属性 |
| 取数 | `useFetch`/`useAsyncData` 保证服务端取过的数据通过 payload 交给浏览器，不再请求一次 | 这两个组合式函数 |

四项里只有"链接"那项官方写了**默认行为**（默认按可见性预取），其余三项都要你主动改写法。混合渲染那段官方给的示例是四条规则同时写：`'/'` 用 `prerender: true`，`'/products/**'` 用 `swr: 3600`，`'/blog'` 用 `isr: 3600`，`'/admin/**'` 用 `ssr: false`，并说明"Nuxt server will automatically register corresponding middleware and wrap routes with cache handlers using Nitro caching layer"。

延迟水合那项还追加了一条上限描述：内容站和营销站如果几乎不需要客户端交互，可以把预渲染、`noScripts` 路由规则、服务端组件和延迟水合组合起来，做到"ship near-zero JavaScript"。

## 第二块：三个核心模块

| 模块 | 官方说它影响哪个指标 | 关键动作 |
| --- | --- | --- |
| Nuxt Image | LCP（"未优化的图片对 LCP 分数有显著负面影响"） | `<NuxtImg>`/`<NuxtPicture>`，按重要性分组加载 |
| Nuxt Fonts | CLS | 五步自动处理，其中"创建度量回退"这条直接对应降低布局跳动 |
| Nuxt Scripts | INP 与 LCP | 第三方脚本（统计、视频嵌入、地图、社媒）会明显拖累体验 |

字体那五项官方列成了编号清单，值得原样记：解析字体（先找 `public/`，再看 Google、Bunny、Fontshare 这些 Web 提供商）、生成 `@font-face` 规则、代理并缓存字体（URL 重写到 `/_fonts`）、创建回退度量、把字体打进构建（哈希文件名并设长缓存头）。

## 第三块：五个量工具，顺序是官方定的

这一节写明了测量次序：

> To improve performance, we need to first know how to measure it, starting with measuring performance during development - on local environment, and then moving to auditing application that are deployed on production.

**先本地，后线上**。工具按这个次序排下来是五个：`nuxt analyze`（生产包体积可视化）、Nuxt DevTools（四个面板：Timeline 记录渲染/更新/初始化耗时，Assets 显示未转换的文件体积，Render Tree 显示组件、脚本、样式之间的连接，Inspect 列出用到的文件及其体积与求值时间）、Chrome DevTools（Performance 面板一打开就显示本地的 LCP 与 CLS，你操作页面后还会抓 INP；Lighthouse 做性能/可访问性/SEO/PWA/最佳实践审计）、PageSpeed Insights（同时给 lab 与 field 数据）、WebPageTest（可选地点、真实浏览器、自定义网络条件）。

## 第四块：五条常见问题

官方这一块的标题是"当你构建更复杂的应用时，大概会碰到下面列出的某些问题"，每条都是一个 Problem 配一个 Solution：

| 问题 | 官方给的解法 |
| --- | --- |
| 插件用太多：插件在水合阶段跑，低效写法会阻塞渲染 | 逐个看插件能不能改成组合式函数或工具函数 |
| 死代码与没用的依赖：功能用不上但占体积 | 检查 `package.json` 的未用依赖，分析未用的 utils/composables/函数 |
| 忘了 Vue 自己的性能建议：这是 Vue 项目 | 用 `shallowRef`、`v-memo`、`v-once` 等 |
| 团队不守同一套模式：人越多越难维持 | 在项目里定规则与模式 |
| 一次把所有东西都加载：没指定顺序就会同时抓全部 | 渐进增强，先把正文核心内容定下来再叠层次 |

这五条里没有一条是"加个配置"，全是改写法或改流程——这也是为什么它单独立一块。

那一节末尾还有三条延伸阅读链接（PRPL 模式、MDN 的感知性能、关键渲染路径），是这一节唯一的外部指向。

## 自查

- 这一节的分块本身就是检查顺序：先看自带的五项有没有被写坏，再看三个模块有没有装，再看量工具，最后对五条常见问题。
- 三个指标各有归属：LCP 对图片、CLS 对字体度量回退、INP 对第三方脚本。
- 自带的只有链接预取是默认开的，其余要主动改。
- 工具次序是本地再到线上，DevTools 四个面板各看一件事，不要混为"看性能"。
- 常见问题的解法全在代码组织层面，配置改不动它们。
