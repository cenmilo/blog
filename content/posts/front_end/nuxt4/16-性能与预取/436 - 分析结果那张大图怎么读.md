第一次跑打包分析的人，卡住的地方不是命令，而是那张图：满屏大小不一的矩形，你不知道哪个矩形值得动手。

官方文档里没有"怎么读图"这一节。但它把读图的原料写在两页上——配置那一页告诉你图的形状和文件在哪，性能那一页给了三条判读规则。合起来就是可执行的办法。

## 图是怎么来的：配置侧三项默认值

`build` 节下的 `analyze` 一句定义：

> Nuxt allows visualizing your bundles and how to optimize them.

然后说用法：设为 `true` 开启包分析，或者传一个选项对象——**选项对象的可用键取决于构建器**，官方给的是 webpack 与 vite 各自工具的选项文档链接（webpack 侧指向 bundle analyzer 的 plugin options，vite 侧指向 rollup visualizer 的 options）。

默认值原样列出来：

```json
{
  "template": "treemap",
  "projectRoot": "/<rootDir>",
  "filename": "/<rootDir>/.nuxt/analyze/{name}.html"
}
```

这三行有三条实际含义：

- **默认模板是 `treemap`**，也就是那张矩形嵌套图。图上矩形面积对应体积，嵌套对应模块归属。
- **结果是一份 HTML 文件**，落在 `.nuxt/analyze/` 下面。它可以被直接用浏览器打开，不必有服务在跑。
- **`{name}` 是占位符**，取的是分析的名字。命令侧 `--name=<name>` 的默认值正好是 `default`，所以默认你会拿到 `.nuxt/analyze/default.html`。想留多份对比，就传不同的 `--name`。

这里有个要提醒的地方：官方给的示例是这么写的——

```ts
export default defineNuxtConfig({
  analyze: {
    analyzerMode: 'static',
  },
})
```

示例把 `analyze` 写在了**顶层**，而这一项的标题在 `build` 节下面。这两处不一致，页面自己没解释，**文档未说明哪个才是当前有效写法**。别猜，用一次构建验证：改完跑 `nuxt build`，看 `.nuxt/analyze/` 里有没有产出文件，两种写法各试一次。

## 命令侧要注意的两件事

命令的完整参数在 043 那篇已经列全了，这里只挑影响读结果的两条：

**这条命令会把 `process.env.NODE_ENV` 设成 `production`**。所以你测的是生产构建的形状，不是开发模式——开发模式下模块没合并，看起来完全是另一回事。

**分析时默认不预渲染路由**。官方给的理由很具体：预渲染会把构建好的应用跑起来，而它跑出来的东西不是你要量的对象。如果你的分析确实需要预渲染，传 `--prerender`。另外结果默认会起一个本地服务展示，除非传 `--no-serve`，或者环境里设了 `CI`。在 CI 里跑，产物就只是那个 HTML 文件。

## 三条判读规则

性能那一页讲工具的那节，除了说这个命令"借助 `vite-bundle-visualizer` 生成包体积的可视化表示，方便找出哪些部分占空间最多"，还把"看到大块之后该干什么"写成了三句。这三句就是读图的规则：

> When you see a large block in the visualization, it often signals an opportunity for optimization—whether by splitting it into smaller parts, implementing lazy loading, or replacing it with a more efficient alternative, especially for third-party libraries.

拆成三条，每条对应图上一种形状：

| 图上看到的 | 官方建议的动作 | 落到代码上 |
| --- | --- | --- |
| 一个大块 | 三种处理方向：拆成更小的部分、实现懒加载、换成更省的实现（尤其第三方库） | 按下面两条细分再决定 |
| 一个大块里面装着多个元素 | 只导入需要的部分，而不是整包导入 | 从 barrel import 改成具名导入、按需引组件 |
| 一个独立成块的大块 | 更适合懒加载，而不是留在主包里 | 加 `Lazy` 前缀、动态 `import()`、按路由切开 |

第三条的边界值得单独说：**独立大块**和**装着许多元素的大块**在图上是两种不同的矩形结构，处理方式正好不同——前者是"别在首屏取它"，后者是"取少一点"。把它们混为一谈，就会出现"明明拆了组件包，主包还是没小"的情况。

## 文档里没有的东西

- **没有体积阈值**。官方通篇没写"主包不能超过多少 KB"，也没给 LCP 对应的毫秒预算。任何具体数字都不是这份文档给的依据。
- **没有 treemap 之外的推荐**。默认模板是 `treemap`，其它模板名归 vite/webpack 各自的工具。
- **没说要按什么顺序处理**。它只说大块"通常意味着优化机会"。

所以"这个包是不是太大了"这个问题，只能自己定基线：先跑一次分析存下 `default.html`，改一处再跑一次存成另一个 `--name`，比对同一条路径上的矩形面积变化。这是文档给的选项能直接支持的做法。

## 自查

- 默认 `template: treemap`，产物在 `.nuxt/analyze/{name}.html`，`{name}` 来自 `--name`，默认 `default`。
- 可传选项由构建器决定，不由 Nuxt 定义；`analyzerMode` 这类键要去 vite/webpack 工具文档查。
- 配置页自身在 `build.analyze` 与顶层 `analyze` 之间不一致，两种写法用一次构建各验一次。
- 命令把 `NODE_ENV` 设为 `production`；默认不预渲染，需要时传 `--prerender`；`CI` 环境下不起服务。
- 三条读图规则：大块 = 机会；内含多元素的大块 = 改按需导入；独立大块 = 改懒加载。
- 没有官方体积阈值，基线只能自己用两次分析建。
