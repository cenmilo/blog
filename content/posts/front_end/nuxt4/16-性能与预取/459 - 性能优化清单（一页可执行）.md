## 第 0 步：先量，别先改

| 动作 | 判据 | 出自 |
| --- | --- | --- |
| 跑一次 `nuxt analyze` 存快照，记下产物 `.nuxt/analyze/default.html` | 默认模板 `treemap`；`--name` 决定文件名 | 436 |
| 看四个面板 | Timeline 组件耗时、Assets **未经转换**的体积、Render Tree 连接、Inspect 文件与求值时间 | 457 |
| Chrome Performance 面板开一次 | 一打开就有本地 LCP 与 CLS 评级，操作后还会抓 INP | 435 |
| 改一处再跑一次分析，用另一个 `--name` | 同一路径矩形面积的变化才是收益证据 | 436 |

次序按官方那句来：**先本地开发环境量，再审计线上应用**。

## 第 1 步：查自带能力有没有被写坏

五项，出自官方性能页 Built-in Features：

| 项 | 检查什么 | 出自 |
| --- | --- | --- |
| `<NuxtLink>` | 站内链接是不是都用它，有没有拿 `<div @click>` 代替；预取触发策略是否只开一种 | 442、456 |
| 混合渲染 | 该缓存的路由有没有配 `routeRules`（`prerender`/`swr`/`isr`/`ssr: false`） | 451 |
| `Lazy` 前缀 | 懒组件有没有配条件渲染——没有就仍然急加载 | 439 |
| 延迟水合 | 首屏不需要交互的块有没有推迟变可交互；**需要交互的组件不能用 `hydrate-never`** | 378、455、456 |
| 取数 | 同一份数据有没有被服务端和浏览器各取一次（`useFetch`/`useAsyncData` 会经 payload 转发） | 435 |

## 第 2 步：三个模块装没装、用没用对

| 模块 | 检查什么 | 出自 |
| --- | --- | --- |
| Nuxt Image | 有没有 `npx nuxt module add image`；首屏图与晚加载图是否按两组属性分开写；`sizes` 是否显式给了 | 423、433、434 |
| Nuxt Fonts | 五步是否落地——尤其第 3 步（URL 重写到 `/_fonts` 自托管，外链请求消失）与第 4 步（回退度量降 CLS） | 453 |
| Nuxt Scripts | 统计/视频/地图/社媒这四类是不是走了 `trigger: 'manual'` + `proxy` 排队 + `onLoaded`；用 `useHead` 注脚本时来源不可信要改 `useHeadSafe` | 454 |

## 第 3 步：按层动手

**JS 加载层**

| 动作 | 官方依据 |
| --- | --- |
| 大块且内含多元素 → 改按需导入 | 436 三条读图规则 |
| 独立大块 → 改懒加载，别留在主包 | 436 |
| 全局注册收窄（`global` 目录或 `.global.vue`，别整目录 `global: true`） | 437（每个全局组件一个 chunk） |
| 手动预热按粒度选：单组件用 `preloadComponents`，整条路由用 `preloadRouteComponents` | 444、445（前者要全局注册＋PascalCase，后者示例**故意不 await**） |

**预取层**

| 动作 | 官方依据 |
| --- | --- |
| 链接密集页改成按交互预取（`prefetchOn: { interaction: true, visibility: false }`） | 442 |
| 别把 `visibility` 与 `interaction` 同开 | 442（重复预取与资源浪费） |
| 用 `custom` 时自己接回 `prefetch`，并先判 `shouldPrefetch` | 442 |
| 跨域预取与提示转发两个开关按需开，先算 CDN 配额 | 443（转发图片请求不带 `Purpose: prefetch`） |

**载荷层**

| 动作 | 官方依据 |
| --- | --- |
| 首屏 HTML 太大 → `payloadExtraction` 从 `true` 试 `'client'`；在意多发一次请求就别用 `true` | 448 |
| 单条取数瘦身 → `serialize: false`、`pick` | 243、448 |
| 已有 `hydrate-never` 组件且内部有取数 → `stripNeverHydratedData`，并检查 prop 会不会变 | 449 |
| 别把 `purgeCachedData` 当体积开关 | 448（它管内存与新鲜度） |

**首字节层**

| 动作 | 官方依据 |
| --- | --- |
| `experimental.ssrStreaming`：开之前确认没有依赖"渲染期间写响应头/状态码"，且 SEO 关键标签都在同步注册 | 450 |
| 缓存与流式互斥：一条路由挂了 `swr`/`isr`/`cache`/`noScripts`/`redirect` 就不流式 | 450、451 |
| `writeEarlyHints` 只在跑 node 服务端时有意义 | 447 |

**构建层**

| 动作 | 官方依据 |
| --- | --- |
| `experimental.buildCache` 只对"同一份代码重复构建"有收益，且 Nitro 永远重建 | 440 |
| CI 缓存 key 要带上那九个文件 | 440、458 |
| 依赖报 ESM 语法错或 E1006 → 登记 `build.transpile`，别忘了它内部导入的包也要登记 | 438 |
| 知道 `optimization.treeShake` 默认从服务端包摇掉十个生命周期钩子 | 441 |

## 第 4 步：验收

- 结构不变量写进 e2e：首屏 HTML 里那张 hero 的属性、外部脚本不在首屏 `<head>`（458，**组合做法**）。
- 指标变化用外部工具读：Lighthouse / PageSpeed Insights（lab+field）/ WebPageTest（457）。
- 流式的视觉结论要在 `nuxt build && nuxt preview` 上看，dev 模式那两条 FOUC 不代表生产（450）。
- 拿掉 JS 的方案（`noScripts` 等）必须**用键盘点一遍**：页面外观不变，但没有任何东西可交互（456）。
- 占位是否防住位移：用 `<ClientOnly>` 的 `#fallback` 插槽而不是 `fallback` 文本（455）。

## 别做

| 别做 | 原因 |
| --- | --- |
| 照任何"官方阈值"填数字 | 文档从未给体积或毫秒预算（436、458） |
| 写 `inlineSSRStyles` | 4.x 无此键，管内联粒度的是 `features.inlineStyles`（427） |
| 用 `ClientOnly` 消水合警告 | 它是给"有意只在客户端渲染"的，代价是默认插槽被 tree-shake 出服务端构建、里面 CSS 可能不内联（455） |
| 为了体积关自动导入 | 官方原话是只用进生产代码的那部分（437） |
| 用 `nuxt analyze --prerender` 去测体积 | 默认不预渲染是因为预渲染跑的是应用、产出的不是被测对象；只有你的分析确实需要预渲染才加 |
| 拿 DevTools 的 Assets 数字当优化后结果 | 它显示的是未经转换的体积（457） |

## 自查

- 顺序不能倒：量 → 自带能力 → 模块 → 分层改 → 验。

- 官方从没给数字，所以本篇也不给数字，只给"用什么读数证明改了"。
