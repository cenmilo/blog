## 那一行为什么会一直停在 `sending`

`downgrade_notices` 是通知状态表，一行代表"某个人的某一期的那封信做到哪一步"。补发的流程是**先抢再发**：一条带条件的 `UPDATE` 把 `failed` 改成 `sending`，抢到的那一趟才真去发信——两个人同时点补做，只该有一封信出去。

抢到手之后进程正常跑完，那一行会被推进成 `sent` 或 `failed`。进程如果正好死在发信中途，它就停在 `sending`：既不算发出去，也不会被下一轮捞进名单，因为补做只挑 `failed`。这是"先抢再发"留下的必然缺口，不是 bug。

捞它只需要一条带条件的写：`status = 'sending'` 且上次写入早于某个界限，改回 `failed`。那个界限是一个时长。整件事就卡在这一个数上。

## 这个时长要问谁

**框架文档。** Nuxt 与 Nitro 那一层管路由渲染、缓存策略、任务注册，不管"一封 SMTP 邮件在途多久"。落空。

**发信库自己的超时。** 本站用的是 `nodemailer@10.1.1`，三个超时写在发信那一层：

```ts [server/services/auth/mailer.ts]
export const SMTP_TIMEOUTS = { connectionTimeout: 5000, greetingTimeout: 3000, socketTimeout: 15000 }
```

去包内把定义读一遍（`nodemailer/dist/cjs/smtp-connection/index.js:129-131`，原话）：

```
greetingTimeout - Time to wait in ms until greeting message is received from the server
connectionTimeout - how many milliseconds to wait for the connection to establish
socketTimeout     - Time of inactivity until the connection is closed
```

前两个只覆盖会话的一个阶段。第三个看着最合适，可它写的是 inactivity：同一份文件里实现用的是 `socket.setTimeout(...)`（`:794`、`:1128`），那是 Node 的空闲计时器，数据一动就重新计时。

于是结论自己出来了：**一次仍在稳步推进的投递，可以在任何有限时长内都不触发这个超时。** 没有任何一个数能区分"这一行还在被慢慢发"与"发它的那个进程已经死了"。抄任何一个数当界限，量的都是另一件事：这三个数的单位是"静默多久关连接"，不是"一封信最多飞多久"。

**站内已有的同类配置键。** 全站的时长常量只剩这一处：`runtimeConfig` 里的 `stripeWebhookToleranceSeconds: 300`。它量的是渠道回调的签名时间窗——早于 5 分钟的事件按过期处理——与"一封邮件在途多久"没有关系。

```
[痕迹面·回收依据] {"有更新列":true,"配置里的时长键":[],"服务里写死的秒":[],"现在能被问出的数":1}
```

`updated_at` 那一列在，所以"多久没落定"读得出来；上面这三段说明"多久**算**死了"没有依据。分子在、分母没有。

## 那就把缺口本身做成能被读出来的东西

决定写进文件头：只报名单、不动状态。服务层加一个只读函数，接口原样交出去。

```ts [server/services/billing/notify.ts]
export async function 列停在发送中 (现在毫秒: number): Promise<停在发送中名单 | null> {
  if (!useRuntimeConfig().databaseUrl) return null
  const 行 = await useDb()
    .select({ 用户id: downgradeNotices.userId, 周期末: downgradeNotices.periodEnd, 上次写入: downgradeNotices.updatedAt })
    .from(downgradeNotices)
    .where(eq(downgradeNotices.status, NOTICE_SENDING))
    .orderBy(asc(downgradeNotices.updatedAt), asc(downgradeNotices.id))
  // …逐行减出 sinceMs；thresholdMs 恒为 null
}
```

四个形状值得单说。

没配库交 `null`，不交空名单。上一站刚立过这条：把"读不出来"折成"结果为空"，界面就会念"没有一位停在发送中"，而真相是没连上库。同一件事换到第二张表上，规矩不变。

"现在"由调用方给。这个函数自己不读钟——测量必须有说得出的一刻，而全站只该有一次"现在"（接口那一层读一次 `Date.now()` 传进来）。

两把排序键。`updated_at` 升序把最久的放前面，`id` 升序把同一刻写入的几行定死。只写一把，顺序由库决定，页面上的名单会闪。

回体里那一格写的是 `thresholdMs: null`，而 `null` 就是它的类型：

```ts [shared/types/task-run.ts]
/** 恒为 `null`：本站没有这个数。 */
thresholdMs: null
```

想改成 300000 的那一天，先编译不过。这一格比注释管用，它把"不许猜"交给了类型检查器。

## 两个问法必须给出不同答案

同一张表上现在有两个读数：`数停在发送中` 问"有几位"（按人去重），`列停在发送中` 问"有哪几行"。它们必须能不相等——同一个人名下有两行时（唯一约束对空值不去重，那一族是"一条订阅行都没有"却被降的人），一个是 1、一个是 2。真库上的读数：

```
[卡住名单·两个问法] {"status":200,"全局":{"rowCount":2,"userCount":1,"thresholdMs":null},
"我的行数":2,"我的有期那行":true,"我的空期那行":true,"我的时长":[7200174,7199999]}
```

断言只在自己的两行之间判，`rowCount` 只判"大于等于 2"：这条地址读的是全库的 `sending` 行，别的规格也会留行——把总数写进期望值，判据就随别人的动作变绿变红。

还有一处藏不住：这一档必须占那把会话级锁。它不批量改任何表，可插进去的两行会让别人的"停在发送中"变高。锁的看守原本只认两族——会造 `member` 的、会跑全库补做的——这一份两族都不命中。"只读不写也串味"的形状是第一次出现，所以看守加了第三族：

```
[收口·锁的看守] {"留发送中的":["retry-window-db.spec.ts","stale-sending-db.spec.ts"],
"发送中没占锁的":["stale-sending-db.spec.ts"]}
```

后面那一位是把锁去掉那一次读到的：报了名字，也说清了是谁。

## 读不出来的时刻不许演成一个较小的数

`updated_at` 有读不出来的可能，而且有两种形状。上一站量过整条链：这一列写 `'infinity'` 时 node-pg 交回来的是数字 `Infinity`（不是 `Date`），而 `new Date(NaN).getTime()` 是 `NaN`。

所以那一行减不出时长时交 `null`，而"最久那一行"的读数必须跟着变 `null`：

```ts
longestMs: 名单[0]?.sinceMs ?? null,
```

这里第一版写的是"找第一个能读出的行"，看着合理其实最坏：屏幕上会念出"最久的 60 秒"，而那行是第二久的——真相是"最久那一行读不出来"，两个说法给的安心相反。

```
[通知·坏值三态] {"第一行":{"user":"u1","periodEnd":null,"sinceMs":null},
"第二行":{"user":"u2","periodEnd":null,"sinceMs":60000},"最久":null,"阈值":null}
```

## 界面上那一句，和那个故意不出现的按钮

句子仍然只有一份，在词表里。这一栏有七种形状：正在读、没登录、不许看、读不出来、没人卡着、有几位卡着、时刻可疑。前四种与 863 那一栏同一套分工（只按 `data.code` 分支），后三种是这张表特有的。真页面上服务端渲出来的字：

```
[卡住名单·页面念法] {"status":200,"状态位":"有几位卡着",
"句子位":"有 1 位停在发送中（2 行），最久的距上次写入 120 分钟。本站没有\"多久算死\"的依据，所以没有去捞。"}
```

后半句是这一站的交付物之一。管理员看到这句的第一反应是"这一栏坏了，该有人处理"，而真相是这里故意不动：理由只写在代码注释里，屏幕上读不到，他就会以为缺的是一个按钮。

时长用领域单位：不到一分钟念秒，超过一分钟念分钟——`0 分钟` 看着像"刚刚发生过"，而它其实说的是"不到 60 秒"。

组件里还有一条判据看着奇怪：

```ts
expect(读数.那一栏有按钮, '这一栏长出了按钮 ⇒ 屏幕上出现了一个没有依据的动作').toBe(false)
```

它防的是最容易发生的那种顺手补全：名单都读出来了，加个"全部重发"很自然。可那个动作的前提是有依据，而这一站整篇都在说没有。

## 判据这一轮自己错了三处

扫描器把 `.vue` 的 HTML 注释当成了代码。新组件的头注释里引了一句服务层路径，于是"应用侧不许绕过接口直接读服务层"那一条报红。红的是形状不是事实：注释不是 import。修法是把注释剥掉——原来的剥注释逻辑只处理 `//` 与 `/* */`，现在补上 `<!-- … -->`，文案一行没改。

一句写进模板的话，在所有形状上都会出现。把"所以没有去捞"直接写进组件，词表那条形状判据红了（句子出现在词表之外），组件那一档同时报"失败态里出现了回收的理由"——读不出来的时候它也念着这句。同一个变异两处红，说的是不同层面的坏味道。

让路的措辞不统一，归族工具就看不见那一族。四条用例各写一句"等不到锁"的理由，其中三句没有那个族认的关键词，读回来是"4 条没归类"。抽成一处 `让路(为什么)` 之后，离线那趟的归族变成要库 92、外部变量 43、内容目录 14、另一趟构建 11、让路 4，没归类 0。`skip` 的数量是环境缺件的读数，读数分不了族就等于没测到。

## 本轮读数与还没闭合的格子

`npm run check` rc=0（八项）；单测 455 条／69 文件（上一站 448）；组件档 71 条／18 文件；端到端不带库 4191 是 260/164/0；带库 4195 是 376/48/0。另一趟 4193 在 `reconcile-write-then-read.spec.ts:149` 卡满 30 秒超时并连带 drain 整批没跑，单跑该文件 4 passed——记为并发与远端慢，不是本站回归。四次变异各撞红：门挪到取数之后、在读名单里写死 5 分钟阈值、句子与按钮写进模板、把这一档的锁去掉。

还欠着的：回收本身仍然欠着，动手那一步要等一个能被验收的出处（不是抄 `socketTimeout`，也不是抄签名时间窗）；"读不出来"那一格在带库这趟问不到，与上一站留下的同一格并着；`/api/_health` 不在本线，这一栏读出名单不等于站点健康，收官那一站逐句判时点名；屏幕只念"最久那一行"，要做整页名单得先谈"给谁看、点进去做什么"——后半件还是做不了。
