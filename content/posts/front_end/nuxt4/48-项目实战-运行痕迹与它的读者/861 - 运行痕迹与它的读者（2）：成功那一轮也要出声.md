## 凌晨那一轮在日志里不存在

排期写的是每天 03:10 跑一轮到期降级。第二天早上有人问："昨晚那轮跑成了没有，几位发信失败？"

你手上有两个地方可以查。数据库里那张每轮一行的表——有行。服务器的输出日志——**一行都没有**。`server/tasks/` 整个目录里一处 `console.` 都找不到，写痕迹那一层只在 INSERT 失败时打 `error`。顺利跑完的那一轮，在 stdout 上不留任何痕迹。

看起来够用：表里有行就够了嘛。问题是这两条证据不是同一条。库会断，而写痕迹那一句是吞掉错误的（打完一行 `error` 就返回 false，不回滚已经降下来的角色，也不抛）。那一刻表里没行、日志也只有一句失败原因——**"这一轮跑过"这件事又变回读不出来**。上一线正是被这一格卡住的：排期能挂上，事后问不出来。

## 框架不出声是分工，不是缺陷

两个词先说清。stdout 是进程的标准输出，你的进程管理器把它接到文件里，就成了运维看到的那份"日志"。结构化日志是另一件事：一行一个 JSON 对象，字段名固定，机器能按字段筛，人也能 grep。

`nuxt task` 那一节讲的是命令：`nuxt task list` 列任务，`nuxt task run <名字>` 跑一个，它"对着为你这个项目跑起来的 `nuxt dev` 服务器说话"，`--url` 可以指向另一台。**它没有规定任务跑成功要输出什么。** 定时执行者也一样——到点跑一轮，成功时一声不响，只有抛错才在 `.catch` 里留一行。

⚠ 那条命令在装好的 CLI 里还问不到（第 853 篇量过：命令表里没有 `task` 这一位）。本站手工触发是直接调任务那一层的 `run()`。

这里有个很容易想歪的地方。命令回的那句"完成"是 CLI 打印的，不是你的任务打印的；它退出码为 0 只说明请求发出去、服务端接了并回了个响应，**不代表库里那一行真多出来了**。框架不出声不是漏了什么，是它不知道你这一轮有意义的数字是哪几个——那一行只能应用自己写。

## 三态，不是一个开关

要出声，第一个决定是分几格。直觉做法是二值：成功打 `log`，失败打 `error`。可这一轮真实存在第三种情况，它是第 856 篇定下的规则：任务跑到一半抛错，但那一行痕迹照样写进了库。

| 这一轮 | `level` | `msg` | 表里有行吗 |
| --- | --- | --- | --- |
| 跑完，没有错 | `info` | `task_run_recorded` | 有 |
| 中途抛错，痕迹写进去了 | `warn` | `task_run_recorded` | 有 |
| 痕迹没写进去（库断了） | `error` | `task_run_write_failed` | 没有 |

压成两态会丢什么？前两格都"有行"，但一格是"这一期一个人都没到该降的时候"，另一格是"读候选名单那一句就炸了，处理到哪一步没人知道"。后者那十五个计数格全是空值（空值与 0 是两件事，写 0 就是编一个读数）。运维读到"跑成功了"会以为数能信——**表里有没有这一行**和**这一行里有没有数**是两个问题，日志的轻重必须能把它们分开。

还有一条更硬：两支互斥。第三格那种情况绝不能同时出成功行，否则日志是在替库里不存在的那一行作证。

上面三种之外还有第四种输入：`databaseUrl` 根本没配。它在函数第一行就返回 false，两支都不走、一行都不打。这是故意的，没配库的部署里这一路不该跑，安静返回比打一句"我没写进去"少一种噪声。代价照实记：那种部署里"跑过一轮"仍然读不出来。

## 出声跟 INSERT 走，不跟任务文件走

放哪一层的判断依据只有一条：谁同时看得见"表里多了一行"和"没多"。任务文件看不见，它只拿到 `写下轮痕迹()` 返回的 true 或 false；真正做 INSERT 的是服务层那一个函数。

所以出声绑在同一个 `try` 里：写成了，在 `return true` 之前打一行；写崩了，在 `catch` 里打另一行。**如果搬到任务文件里**，"根据返回值决定打什么"就成了第二次判断——两处判断迟早漂开。

搬这一层时顺便撞上 Nuxt 的目录规则。自动导入只覆盖 `server/utils/`，官方那一节的原话是你"可以自己往 `~~/server/utils` 目录里加 helper"。本站的 `server/services/` 不在自动导入范围内，跨目录引用必须显式 import：

```ts
// server/tasks/refresh-roles.ts
import { 判触发来源, 写下轮痕迹, type 任务事件 } from '../services/task-run'
```

深层目录里数 `../../` 很烦。4.3 起有 `#server` 别名，指回 `server/` 根，接口层用的就是它：

```ts
// server/api/console/metrics.get.ts
import { metricsForUser } from '#server/services/metrics'
```

它只能在 `server/` 内部用，客户端代码里 import `#server/...` 会直接报错。这条限制正好是同一条边界：痕迹表只有服务端拿得到，页面想读它只能走接口——想抄近路在页面里直接 import 服务层，框架就替你拦住了。

## 那一行长什么样

形状跟着站内已有的两个先例走（每个请求的访问日志、webhook 入账），不自创第三种 logger：

```ts
console.log(JSON.stringify({
  ts: new Date().toISOString(),
  level: 记录.error ? 'warn' : 'info',
  msg: 'task_run_recorded',
  task: 记录.task,
  trigger: 记录.trigger,
  error: 记录.error,
  ...记录.counts,
}))
```

三处细节值得单独说。

`msg` 是一个固定英文短语，不是人话。读日志的人靠它区分两类行；人话会改、会被翻译，`msg` 不动。

`level` 从 `记录.error` 派生，不从"有没有抛错"派生。走到这一行时抛错早已被上面接住，能传下来的信息只剩"这一轮的错误文本是什么"。

`...记录.counts` 展开的是 TypeScript 接口里那十五个驼峰键（`candidates`、`mailFailed`），**不是**数据库列名（`mail_failed`）。列名那一份由 drizzle 的映射负责，日志里再抄一遍就是第二份映射表：改列名时它会漏改，两边悄悄对不上。跑一轮真读一次就能确认，日志里的 `processed` 与任务报回的 `处理行数` 是同一个数。

## 让新判据各红一次

新增的两条断言撞不红就等于没写。同一次改动——在 `catch` 分支开头补一条成功行——两条档各报各的：

```
形状档：expected ['log', 'log', 'error'] to deeply equal ['log', 'error']
行为档：INSERT 没成功却出了成功行 ⇒ 日志在替库里没有的那一行作证
        expected 1 to be 0
```

两条红的原因不一样，这件事值得记下来。形状档读**源码文本**：把那个函数切出来，数里面 `console.` 的调用名。它便宜，不用起服务器就能问，但它只看得到"有几处、是什么级别"。行为档读**跑完一轮之后 spy 收到的调用**，它才回答"这一轮到底出不出声、出了几条、里面那个数对不对"，可它看不见别处偷偷多打的那一行。**两条都要，是因为各自的盲区不重叠。**

顺手加进同一条档的还有"站内成功出声的文件名单"，现在三个：访问日志、webhook 入账、痕迹这一层。名单写死是为了让第四种形状出现时必须被看见——那说明有人又自创了一份格式，该回来统一，而不是各自长。

## 五个容易做错的形状

| 做法 | 为什么会出事 | 改成什么 |
| --- | --- | --- |
| 只在 `catch` 里打日志 | 顺利跑完那一轮读不出发生过什么，"到点自己跑"永远没证据 | 两支各一条 |
| 成功与失败共用一个 `msg` | 分不清"没跑"和"跑了没存下" | 两个具名短语 |
| 三态压成两态 | "跑砸了但证据存下"与"跑成了"看起来一样 | `info`／`warn`／`error` |
| 日志里抄数据库列名 | 两份映射表，改一边漏一边 | 展开 TS 那份驼峰键 |
| 按任务文件的返回值决定打什么 | 两处判断会漂，且看不见写没写进去 | 出声与 INSERT 同一段 |

## 你可以自己量的三件事

- [ ] 你的定时任务顺利跑完一轮，服务器输出里有没有一行说它跑了？没有的话，"跑过"这件事今天靠什么证据？
- [ ] 那行日志的轻重，能不能把"跑成了"和"跑砸了但证据存下了"分开？
- [ ] 你新加的服务层文件在 `server/utils/` 还是别的目录？后者不自动导入，而且客户端拿不到。
