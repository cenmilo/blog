## 四行 YAML 与一份名单

改之前，`.github/workflows/ci.yml` 里跑的是六条命令：

```yaml
- run: npm ci
- run: npm run lint
- run: npm run typecheck
- run: npm run test:unit
- run: npm run build
- run: npm run test:nuxt
```

本地那份 `scripts/check.mjs` 里的名单是同样五项加一道版本判断。**同一份名单写在两个地方**，这就是"本地绿 CI 红"最省事的制造方式：往脚本里加一项（比如将来要加的 `test:e2e` 或者 `check:env`），忘改 YAML，CI 就一直少跑一项，而且没人会注意到——它没有报错，只是没做。

改完是这样，四步：

```yaml [.github/workflows/ci.yml（骨架）]
name: ci

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

on:
  push:
    branches: [main]
  pull_request: {}

jobs:
  check:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '24'
          cache: 'npm'
      - run: npm ci
      - name: check
        run: npm run check
```

拿仓库里的 `js-yaml 4.3.2` 把这份文件读一遍，结构就是我们要的样子：

```text
顶层键: name,concurrency,on,jobs
concurrency: {"group":"ci-${{ github.ref }}","cancel-in-progress":true}
on: {"push":{"branches":["main"]},"pull_request":{}}
job 键: runs-on,timeout-minutes,steps   |   timeout-minutes: 15
steps: 4 → actions/checkout@v4 | actions/setup-node@v4 | run:npm ci | run:npm run check
check.mjs 名单: lint,typecheck,test:unit,build,test:nuxt
workflow 里出现的 npm run 命令: npm run check
名单是否只在一处: 是（workflow 不再抄子项）
```

这么改不是没有代价。**GitHub 的界面里再也不会出现"每一步一个绿勾"**，六步并成一步之后，失败信息全落进同一段日志；换来的是日志末尾那张逐项表和那行 `停止在 <项名>`。上一站量的两趟时长 38851ms 与 38864ms 就是这张表打出来的，信息一点没少，只是位置从 UI 挪进了日志。

## 每个键都得有出处

工作流文件的语法是另一套东西，不在 Nuxt 文档里。这几位的官方说明本轮取到了，直接引：

| 键 | 官方说法（原文摘录） | 这里为什么这么写 |
| --- | --- | --- |
| `concurrency` | A concurrency group ensures only one job/workflow runs at a time；`cancel-in-progress: true` cancels existing pending jobs | 按分支分组。连推三个提交时只留最新一趟，旧的一趟取消，不再占 runner |
| `jobs.<job_id>.timeout-minutes` | Default is 360 minutes. This key sets the maximum allowed time for running a job in minutes | 默认六小时太长。本地量到 `CI=1 npm run check` 是 39688ms，同一条命令不带 CI 是 38864ms（差 824ms），冷缓存机器按十倍留量也才 6.6 分钟 ⇒ 收到 15 |
| `jobs.<job_id>.steps[*].name` | This keyword specifies the name of the step, displayed on GitHub | 合成一步之后，那一步在界面上总得有个名字 |
| `...steps[*].continue-on-error` | If true, the workflow continues to the next step even if the current step fails | **明确不用**：CI 要的就是"红就停"，这句描述的正是我们不想要的行为 |

`on` 这个键名有个众所周知的坑：在 YAML 1.1 方言里 `on` 是布尔字面量（`yes`/`no`/`on`/`off` 那一族），有的解析器会把它读成键 `true`。本轮的复验结果是 js-yaml（按 YAML 1.2）没有这个问题——上面那行 `顶层键: name,concurrency,on,jobs` 里 `on` 还在，也没有多出 `true` 键。但这只证明了一个解析器，所以文件注释里保留了这句提醒，别把"这么写一定没事"当结论。

`actions/checkout@v4` 与 `setup-node@v4` 这两个标签**本轮没能重新取证**（去仓库 README 取当前示例时 `fetch failed`），所以留在原位。之前记录过一次观察：这两个仓库的 README 示例已经写到 `@v7`。升与不升都不影响这份文件说什么，但要升就单独一趟升、看清楚 release notes 再动。

## `node-version: '24'` 是三套口径的交点

上几篇量出来过三个互不相同的版本要求：`nuxt` 包的 `engines` 是 `^22.19.0 || ^24.11.0 || >=26.0.0`，讲 Nuxt CLI 那一节要求 Node v22.21+、v24.11+ 或 v26+，而 `@nuxt/cli` 自己 `package.json` 的 `engines` 松到 `^16.14.0 || >=18.0.0`。依赖树里还有包要求 Node >=24.15。**三套里只有 24.x 的最新版同时满足**，所以取 `'24'`。

引号不是风格问题。这个键值如果不加引号，YAML 会把它当数字：

```text
node-version: 22.10   → 解析成数字 22.1     ← 尾零被吃掉
node-version: 24.10   → 解析成数字 24.1
node-version: '22.10' → 解析成字符串 "22.10"
```

这是拿仓库里的 js-yaml 现测的。写 `'22.10'` 才是"要这个精确版本"，写 `22.10` 是"要 22.1 这个版本"——差一个零，装的运行时就不是你要的那个。

## 不推上去，能验到什么

CI 的真实执行要推上去才知道，但有几件事在本地就能钉死，本轮全做了。

**一，结构。** 就是上面那次 `js-yaml` 读取：文件是不是合法 YAML、四个键在不在、步骤数对不对、名单是不是只剩一处。这一步的意义是"少一项"这种错误能被机器发现，而不是等 CI 绿了才发现它压根没跑测试。

**二，命令本身。** `CI=1 npm run check` 在本地整条跑通，rc=0、39688ms，六项逐项都在表里。它证明的是"这条命令在一个自称 CI 的环境里行为不变"——顺带把 `NODE_ENV`、颜色输出这些差异踩掉一半。另一半没验到：`playwright.config.ts` 里那个 `reuseExistingServer: !process.env.CI` 的差别，要有一个已经在跑的产物服务才看得见，这一轮没有起服务，所以那半句**没取证**，只在注释里写明。

**三，`npm ci` 这一位为什么单列。** 本地没有对应步骤，因为本地的 `node_modules` 是装好状态；云端是干净机器。它的价值在"只按 lockfile 装、装之前先把整个 `node_modules` 删掉"，第一篇量过它的两条脾气：同步时退出码 0、不同步时直接 `EUSAGE` 拒绝。本轮在同一个最小工程里又跑了一次，**8550ms 装完、退出码 0**。这一位也是那份 lockfile 规矩的执行处——不提交 lockfile 的话，CI 装的树和你本地的树是两回事。

**四，产物怎么起。** 端到端那一层不在名单里（它要先构建、还要几百兆的浏览器二进制），但它在这份文件之外。构建出来的 `.output` 按官方讲部署那一节的说法是"默认输出格式"的 Node 服务，入口就一行：

```bash
NODE_ENV=production node .output/server/index.mjs
```

它默认监听 3000，认 `NITRO_PORT` 或 `PORT`、`NITRO_HOST` 或 `HOST`（默认 `0.0.0.0`），那两个 SSL 变量只在测试场景用，正式环境交给反向代理终止 TLS。那一节还有一条 important 值得抄进部署文档：**要设 `NODE_ENV=production` 再起服务**，有些依赖（它点名了 Vue Router）只有在这个值下才会剥掉开发期警告，不设就会在遇到未匹配路由时被 `[Vue Router warn]: No match found…` 刷屏。我们自己的端到端层用的正是同一个入口，端口通过 `PORT` 传（`NUXT_PORT` 对这种直接起法无效，那是第一篇量过的）。

## 改完的末态，以及这份文件还没做的事

改完之后本地再跑一遍确认什么都没坏：`npm run lint` 退出码 0（还是挂着那条 `vue/no-v-html` 的 warning），`CI=1 npm run check` 六项全绿。文件本身从 47 行变成 67 行——行数变多是因为注释写清了每个键的出处，而 `run:` 步骤从 6 条缩到 2 条。

还有几件事这份文件**没有**做，说明白免得被当成漏了：

- 不上传任何测试产物。端到端那套配置里 HTML 报告落在 `playwright-report/`、失败时的附件落在 `.test-report/artifacts`，这些在本轮之前已经躺在本地目录里；CI 上要是不显式加一步上传，红的时候就只能看日志文本。现在端到端不在这个 job 里，所以这一步先欠着，加那一层的时候一起补。
- 不部署。跑完只是"绿"，构建出来的 `.output` 留在 runner 上，任务结束就没了。真要交付，是另一条工作流的事（构建 → 上传 → 交给托管平台），而且部署要用的环境变量属于运行时，不该出现在这份文件的注释或命令里。
- 不跑 `check:env`。上一站说过原因：没配环境变量的干净机器上它必然红，会把"代码能不能构建"和"这台机器配没配库"绑成一件事。
- 不手工管缓存 key。`cache: 'npm'` 交给那个 action 决定，它缓存的是 runner 上的全局包目录，不是 `node_modules`。

## 这一步的自查清单

1. 工作流里不要抄清单。跑 `npm run check`，让 `check.mjs` 是唯一的名单；改检查项只改一个地方。
2. 加 `concurrency`（按分支或 PR 分组）与 `cancel-in-progress`，否则连推几次就是排队跑几趟旧代码。
3. 显式设 `timeout-minutes`：默认是 360 分钟，一条卡住的命令能占 runner 六小时。
4. 版本号一律带引号写，并知道三套版本口径各自的来源；CI 那个 `node-version` 要同时满足依赖树里最严的一条。
5. 每一步的失败都要让整条 job 红，别用 `continue-on-error` 把红灯咽下去。
6. 推上去之前先本地做三件事：解析 YAML 看结构、`CI=1` 跑一遍那条命令、确认 `npm ci` 用的是提交进仓库的 lockfile。

| 现象 | 先查什么 |
| --- | --- |
| CI 全绿但你怀疑它没跑测试 | 看日志里有没有那张逐项表；没有就是它跑的清单和本地不是同一份 |
| 加了新检查项，CI 却不报 | 两处名单只改了一处；合成一步之后这类漏改不会再发生 |
| 装的 Node 不是你要的小版本 | `node-version` 有没有引号 |
| 同一个分支连推三次，跑得越来越慢 | 有没有 `concurrency`；没设就是排队 |
| CI 比本地慢一大截 | 冷缓存：`cache: 'npm'` 缓存的是全局包目录不是 `node_modules`，lockfile 一变就得重装 |

- 工作流语法的四个键（`concurrency` 与其 `cancel-in-progress`、`jobs.<job_id>.timeout-minutes` 默认 360 分钟、step 级 `name`、`steps[*].continue-on-error`）：`https://docs.github.com/en/actions/reference/workflow-syntax-for-github-actions`
- Node.js 服务 preset 是默认输出格式、入口命令 `NODE_ENV=production node .output/server/index.mjs`、默认端口 3000、`NITRO_PORT`/`PORT`、`NITRO_HOST`/`HOST`、SSL 两个变量只用于测试、必须设 `NODE_ENV=production` 那条 important（点名 Vue Router 的开发警告）：`https://nuxt.com/docs/4.x/getting-started/deployment`
- 静态托管的两条路线（`nuxt generate` 预渲染并产出 `200.html`/`404.html`，或 `ssr: false` 的单页应用）与预渲染会产出 `_payload.json`：`https://nuxt.com/docs/4.x/getting-started/deployment`
- CLI 的更新检查在 CI 与非终端环境下跳过（所以这段日志不会污染 CI）：`https://nuxt.com/docs/4.x/api/commands/overview`
- `npm ci` 只按 lockfile 装、不同步时 `EUSAGE` 拒绝、`packageManager` 由 corepack 读：见本系列工程基线第 4 步
