## 三个目录，三种价钱

`Substrate/test/` 下面就是那三个目录，各自的数量与耗时是这一轮跑出来的：

```text
test/unit/   25 个文件 ／ 184 条用例 ／ 2818 ms
test/nuxt/    5 个文件 ／  14 条用例 ／ 3874 ms
test/e2e/    39 个文件 ／ 172 条用例 ／ 25048 ms（119 passed，53 skipped）
```

第一层比第二层快不到一秒，第二层比第三层快一个数量级。为什么这么分、哪些断言只许写在哪一层，靠一句官方定义加一个实验就能说清。

官方讲 `test/` 目录那一节给的是三行定义：**`test/unit/` 是不带 Nuxt 运行时的快速 Node 测试**，**`test/nuxt/` 是需要 Nuxt 运行时环境的测试**，**`test/e2e/` 是对着跑起来的应用做的端到端测试**。同一节还有一句容易忽略的话：Nuxt **不会**像扫 `app/` 和 `server/` 那样扫 `test/`，用什么运行器、怎么摆放都由你自己定。

装的东西也分层。官方那条安装命令是把五件一起装：

```bash
npm i --save-dev @nuxt/test-utils vitest @vue/test-utils happy-dom playwright-core
```

因为 `@nuxt/test-utils` 故意把这些留成可选的对等依赖，好让你自己挑：运行时环境可以在 `happy-dom` 与 `jsdom` 之间选，端到端运行器可以在 `vitest`、`cucumber`、`jest`、`playwright` 之间选，而 `playwright-core` 只有你想用内置的浏览器测试工具、又不拿 `@playwright/test` 当运行器时才需要。单元测试这一层目前**只支持 `vitest`**。本仓库这套的版本：`@nuxt/test-utils 4.3.3`、`vitest 5.0.4`、`@playwright/test 1.64.0`、`happy-dom 21.0.1`、`@vue/test-utils 2.5.1`。

## 文档给一份配置，本项目走三个入口

官方推荐的形状是把三层写进同一个 `test.projects` 数组：

```ts [vitest.config.ts（官方形状）]
import { defineConfig } from 'vitest/config'
import { defineVitestProject } from '@nuxt/test-utils/config'

export default defineConfig({
  test: {
    projects: [
      { test: { name: 'unit', include: ['test/unit/*.{test,spec}.ts'], environment: 'node' } },
      { test: { name: 'e2e', include: ['test/e2e/*.{test,spec}.ts'], environment: 'node' } },
      await defineVitestProject({
        test: { name: 'nuxt', include: ['test/nuxt/*.{test,spec}.ts'], environment: 'nuxt' },
      }),
    ],
  },
})
```

三个项目里只有 `nuxt` 那一层用 `defineVitestProject`——官方那条 note 写得很直接：`defineVitestProject` **只给 Nuxt 环境的测试用**，端到端应当配成一个普通的 `test.environment: 'node'` 项目。挑一层跑用 `npx vitest --project unit` / `--project nuxt`。另外两条 tip：在 vitest 配置里 import `@nuxt/test-utils` 时，`package.json` 必须有 `"type": "module"`，否则要把配置文件改名成 `vitest.config.mts` 这类；测试用的环境变量可以放 `.env.test`。

本项目选的是另一个形状——一层一份配置、一条命令，理由是脚本更好读：

```js [vitest.config.ts（本项目，第一层）]
export default defineConfig({
  test: {
    include: ['test/unit/**/*.test.ts'],
    environment: 'node',
  },
})
```

```ts [test/nuxt/vitest.config.nuxt.ts（第二层）]
export default defineVitestConfig({
  test: {
    include: ['test/nuxt/**/*.test.ts'],
    environment: 'nuxt',
    fsModuleCache: false,
  },
})
```

第二层那个 `fsModuleCache: false` 是这个仓库自己踩出来的：Vitest 5 新加的"把 transform 结果落到 `node_modules/.vitest-cache` 跨进程复用"在 Windows 上会让第二趟崩在 Nuxt 的虚拟入口上（`The argument 'filename' must be a file URL object… 'file:///node_modules/nuxt/dist/app/nuxt-vitest-app-entry.js'`），关掉才能重复跑。

还有一条官方 warning 是这一层的成本所在：**在 Nuxt 环境里跑测试，它们跑在 happy-dom 或 jsdom 上，测试开始前会先初始化一个全局 Nuxt 应用**——包括你在 `app.vue` 里写的代码和注册过的插件。所以官方接着提醒：不要在测试里改全局状态，非要改就事后重置。这也解释了那一秒多的差价：14 条用例本身只花几百毫秒，剩下的都付给"起一个真的运行时"。

## 同一句代码，三种结局

这一站的判据就靠一个实验。把这句代码原样放进三个目录：

```ts
import { useRuntimeConfig } from 'nuxt/app'

expect(typeof useRuntimeConfig()).toBe('object')
```

放进 `test/unit/`，它连加载都没过去：

```text
TypeError: Package import specifier "#build/nuxt.config.mjs" is not defined in package
  …\node_modules\nuxt\package.json imported from …\node_modules\nuxt\dist\app\nuxt.js
Test Files  1 failed (1)
     Tests  no tests          ← 一条用例都没跑起来
退出码 1
```

`#build` 这个别名指向 `.nuxt/` 里的生成物，Node 环境的测试项目没有 Nuxt 的模块解析，于是**运行时不是"不可用"，是"进不了门"**。

放进 `test/nuxt/`，同一句代码通过：

```text
✓ test/nuxt/probe-boundary.test.ts (1 test) 262ms
Test Files  1 passed (1) ／ Tests 1 passed (1)      退出码 0
```

放进 `test/e2e/`，这句代码根本不该出现——这一层的断言方式是"发一次请求，看回来的东西"。同一件事在端到端层的等价写法，是本项目 `landing.spec.ts` 里第一条用例的真读数：

```text
[首屏 HTML] {"status":200,"bytes":5044,"hero":true,"lede":true,"docs":true,"me":true,"announcerInHtml":false}
  ok 1 › 服务端发的首屏 HTML 里就有落地句与入口地址（一行 JS 都没跑）(21ms)
```

于是官方那条 important 的分界线落到实处：**单元测试不该依赖 Nuxt 运行时特性（自动导入、composables）**；只有当测试真的 import 了你的源文件（例如 `~/utils/helpers`）才需要给它加路径别名支持，不是为了让单测能用 Nuxt 的专属能力。默认被纳入 Nuxt 类型上下文的是 `test/nuxt/` 与 `tests/nuxt/`，别的目录要自己往 `typescript.tsConfig.include` 里加——上一篇那条洞就是从这里来的。

## 端到端这一层：`setup()` 的十一个选项

`@nuxt/test-utils/e2e` 的那套 API 要在每个用到它的 `describe` 里先 `await setup({...})`，它背后在 `beforeAll`／`beforeEach`／`afterEach`／`afterAll` 里做一系列准备工作。选项一共十一位，默认值照官方那份列表逐条抄：

| 选项 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `rootDir` | `string` | `'.'` | 被测 Nuxt 应用所在目录 |
| `configFile` | `string` | `'nuxt.config'` | 配置文件名 |
| `setupTimeout` | `number` | `120000`，Windows 上 `240000` | 允许 setup 干完活的时长（可能包含构建） |
| `teardownTimeout` | `number` | `30000` | 拆环境（比如关浏览器）的时长 |
| `build` | `boolean` | `true`；`browser` 或 `server` 关掉、或给了 `host` 时是 `false` | 是否单独跑一次构建 |
| `server` | `boolean` | `true`；给了 `host` 时 `false` | 是否起一个服务响应请求 |
| `port` | `number \| undefined` | `undefined` | 指定测试服务的端口 |
| `host` | `string \| undefined` | `undefined` | 给了就把这个 URL 当被测目标，不自己构建不起服务 |
| `browser` | `boolean` | `false` | 设了就启动浏览器供用例控制 |
| `browserOptions` | `object` | — | `type` 取 `chromium`/`firefox`/`webkit`；`launch` 是传给 Playwright 的启动选项 |
| `runner` | `'vitest' \| 'jest' \| 'cucumber'` | `'vitest'` | 用哪个运行器 |
| `logLevel` | `number` | `1` | 覆盖服务端子进程的日志级别，可用 `NUXT_TEST_LOG_LEVEL` 改 |
| `captureServerLogs` | `boolean` | `true` | 为 `true` 时服务端 stdout/stderr 不打到控制台，改由 `getServerLogs()` 取；`false` 恢复继承 stdio，本地调试时有用 |

配套的 API 六个：`$fetch(url)` 拿服务端渲出的 HTML；`fetch(url)` 拿响应（可以解出 `body` 与 `headers`）；`url(path)` 拼出含端口的完整地址；`getServerLogs()` 返回自上次 `startServer()` 或 `clearServerLogs()` 以来收集到的服务端行；`clearServerLogs()` 清空它们；`createPage(url)` 建一个 Playwright 页面实例。

本项目**没有用这套 `setup()`**，端到端那一层走的是 Playwright 自己的 runner，配置里最关键的是 `webServer`：

```ts [playwright.config.ts（节选）]
webServer: {
  command: 'npm run build && node .output/server/index.mjs',
  env: { ...process.env, PORT: String(PORT) },
  url: BASE_URL,
  reuseExistingServer: !process.env.CI,
  timeout: 180_000,
}
```

为什么宁可自己写：这一层要验的东西——预渲染出来的文件、`last-modified`、缓存响应头、载荷、chunk 字节——**只存在于发布物里**。代价是每一趟都得先 build 一次。

## 三层的耗时怎么读，那 53 条 skipped 算什么

拿本轮的数当基线，但只有前两层能当基线用。端到端那一层单跑同一个 spec 三趟：

```text
18.9s ／ 20.1s ／ 29.2s      同一份代码，同样 7 passed 2 skipped
```

波动超过 50%，比"层与层之间的差价"还大。所以这一层的数字只能用来判断"跑没跑完"，别拿它当回归阈值。

那 53 条 skipped 也不是"测过了"。项目里的规矩是：需要真数据库的用例写成 `test.skip(DATABASE_URL === '', …)`，跑法用 `NUXT_E2E_DB=1 npm run test:e2e -- <点名哪个文件>`。这个开关的存在本身就是判据：产物服务不读 `.env`，有一条断言钉的是"形状对但没配库 ⇒ 503"，如果默认那趟悄悄把连接串带上，那条读数会从 503 变成 401——绿灯换了意思，比红灯更难查。带库跑是另一组数字，不在这一篇里给。

还有一件要交底的：这一轮第一次单跑那条 spec 时退出码是 1，随后三趟都是 0。日志被后一趟覆盖了，没拿到失败的用例名，所以这里不下结论。可疑位置是 `reuseExistingServer: !process.env.CI`——它只看那个 URL 有没有人应答，上一趟正在关闭的服务、或者别的进程占着同一位端口，都会被判成"服务已就绪"（这个仓库确实有过一次 3100 被浏览器当临时出站端口先占走的记录）。**这条没有取证**；要在本地复现那种红，先把这一位改掉再跑。

## 这一步的自查清单

1. 要断言"Nuxt 给不给这个东西"（自动导入、运行时配置、插件写进上下文的状态），就只有 `test/nuxt/` 那一层能测；写成单测会在加载阶段就炸。
2. 纯函数、纯计算、跟框架无关的校验放 `test/unit/`，那一层的价值就是它便宜——184 条用例 2.8 秒。
3. 端到端只留"必须看发布物"的断言：预渲染文件、响应头、缓存位、真实 DOM 交互。别拿它测函数返回值。
4. 三层各自的耗时都跑一次记下来，只有前两层适合当回归基线；端到端记"跑完/没跑完"和失败清单。
5. `skip` 的条数要单独盯，并保证 skip 的条件写在用例里（缺什么就 skip 什么），报告里把"没测"和"测过了"分开列。
6. Nuxt 层的用例别改全局状态；改了就在收尾重置，否则同一次跑里后面的用例会读到脏运行时。

| 现象 | 先查什么 |
| --- | --- |
| 单测里 `import` 一个 composable 就炸 | 这句代码属于 Nuxt 层；挪进 `test/nuxt/` 或改成显式传依赖 |
| Nuxt 层第二趟崩在虚拟入口 | Windows 上关掉 `fsModuleCache`（本项目已关） |
| 端到端用例连不上服务 | `baseURL` 与实际端口对不对；有没有别的进程占着那位 |
| 明明没配库，某条用例却变了行为 | 带库跑的开关被悄悄带上了；按开关与点名的文件跑 |
| 用例越来越多但跑得一样快 | 好事：说明新断言都落在了单测层 |
