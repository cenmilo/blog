## 一条快得可疑的命令

仓库里已经有这条脚本：

```text
$ npm run lint
> eslint .
（没有输出）
退出码 0        耗时 3293 ms
```

三秒、零输出、绿色。它扫了什么、按什么判、以及"退出码 0"这三个字挡不住什么——这一站全部量一遍。装法本身没有悬念：官方讲代码风格那一节推荐用 `@nuxt/eslint` 模块（`npx nuxt module add eslint`），说它会**按你的项目结构**生成配置；启动一次应用之后，项目根会出现 `eslint.config.mjs`，你想改就改它。那一节还有一句给老项目：这套模块是为 ESLint 的新版 flat config 设计的（从 ESLint v9 起 flat config 就是默认格式），还在用旧的 `.eslintrc` 就得手动配，官方建议迁过来。

本机装好的版本：ESLint `10.12.0`、`@nuxt/eslint` 与 `@nuxt/eslint-config` 都是 `1.17.0`。

## 配置是两层，不是一层

根目录那份 `eslint.config.mjs` 只有四行，而且它不写任何规则：

```js [eslint.config.mjs]
// @ts-check
import withNuxt from './.nuxt/eslint.config.mjs'

export default withNuxt(
  // Your custom configs here
)
```

规则全在 `.nuxt/eslint.config.mjs` 里，那是一份**生成物**：51 行、8,076 字节，开头一行注释写着 `// ESLint config generated by Nuxt`。它做三件事。

第一件是把你的项目结构告诉规则集。生成出来的选项里有这么一段：

```js [.nuxt/eslint.config.mjs（节选）]
dirs: {
  pages: ["app/pages"],
  composables: ["app/composables", "app/utils"],
  components: ["app/components"],
  layouts: ["app/layouts"],
  plugins: ["app/plugins"],
  middleware: ["app/middleware"],
  src: ["app"],
}
```

页面在 `app/pages`、组合式函数在 `app/composables` 与 `app/utils`——正因为这样，"哪些目录里的文件该按页面规则判"才不用你手写。这就是官方那句"project-aware"的实际内容。

第二件是把自动导入的名字登记成全局变量。生成配置里有一个名为 `nuxt/import-globals` 的配置对象，把一长串名字以 `readonly` 注册进去。本机这一份的数量是 **397 条、去重后 382 条**，里面既有框架给的 `useFetch`、`useState`、`definePageMeta`，也有**这个项目自己的**自动导入：`useDb`、`requireAdmin`、`apiError`、`readSecretString`、`logAudit`、`safeRedirectTarget`、`normalizeEmail`、`DocPage`、`MeterRow`、`PlanId` 都在表里。这一位解释了为什么 `app/` 里的文件不 import 也能被 lint 放过。

第三件是把你那份接上去：

```js [.nuxt/eslint.config.mjs（节选）]
export function withNuxt (...customs) {
  return configs
    .clone()
    .append(...customs)
    .onResolved(configs => typegen(configs, { dtsPath: r("./eslint-typegen.d.ts"), augmentFlatConfigUtils: true }))
}
```

`append(...customs)` 就是把你在根文件里写的东西**排在最后**。flat config 的合并规则是数组里后面的覆盖前面的，所以"你自己写的那一条一定赢"。

顺带一条会被忽略的依赖关系：把 `.nuxt/eslint.config.mjs` 的修改时间记下来，连跑两次 `nuxt prepare`——

```text
第一次读到的 mtime：2026-10-17T07:08:59.931Z
再跑一次 prepare 后：2026-10-17T07:09:17.502Z     字节数仍是 8,076
```

每次 prepare 都重写它。而根文件是**静态 import** 这个路径的，所以 `.nuxt/` 还没生成时 lint 根本起不来——这就是上一篇那条 `postinstall: nuxt prepare` 存在的理由之一：它不只生成类型，也生成 lint 的配置。

## 一次跑到底扫了什么

把输出切成 JSON 数一下：

```text
npx eslint .        rc=0    耗时 3390 ms
被扫文件数 161        （vue 10 / ts 144 / mjs 7）
error 0    warning 1    可自动修 0
```

那条 warning 是 `app/pages/docs/[slug].vue:89` 的 `vue/no-v-html`——这一条是项目里有意留下的：文档详情页要渲染服务端转义过的 markdown，文件上方就写着前提说明。两种处置都合理：加一行 `eslint-disable-next-line vue/no-v-html` 并附理由，或者让它挂着但知道它在哪。要注意的是判据本身：`--fix` 那次读数里 `2 problems (2 errors, 0 warnings)` 退出码是 1，而这一次 1 条 warning 退出码是 0。**warning 不影响退出码**，所以 `rc=0` 不等于"一条问题都没有"。

再问一件更容易弄错的事：同一个仓库里的不同文件，吃的不是同一套规则。用 `--print-config` 分别问四类文件：

| 这个文件 | 启用的规则数 | 前缀分布 | `no-undef` | 未用变量那条 |
| --- | --- | --- | --- | --- |
| `app/pages/index.vue` | 190 | vue 108、core 47、@typescript-eslint 29、import 4、nuxt 2 | 关 | `@typescript-eslint/no-unused-vars` 开 |
| `nuxt.config.ts` | 83 | 同上家族、少 vue 那一大块 | 关 | 同上 |
| `server/utils/db.ts` | 82 | — | 关 | 同上 |
| `scripts/check-env.mjs` | 69 | 基础那套 | **开** | `no-unused-vars` 开（TS 那条关） |

这张表里最实用的是最后两列：TS 与 Vue 文件里 `no-undef` 是**关掉的**（未定义交给类型系统），所以拼错一个自动导入名，lint 不会响；而 `.mjs` 脚本里 `no-undef` 是开着的，但它用的规则名与 TS 那套不同。**同一个症状在不同文件里报出不同规则名**，看报错时别以为装了两套东西。

## 当场造一次报错，看它红、看修、看回绿

在一个脚本里放三样东西：一个没用的变量、一个 `debugger`、一句只有服务端能用的自动导入：

```js [scripts/lint-probe.mjs]
export function probe () {
  const unused = 1
  debugger
  return useDb()
}
```

```text
$ npx eslint scripts/lint-probe.mjs

Substrate/scripts/lint-probe.mjs
  2:9  error  'unused' is assigned a value but never used  no-unused-vars
  3:3  error  Unexpected 'debugger' statement              no-debugger

✖ 2 problems (2 errors, 0 warnings)
退出码 1
```

带行号、带列号、带规则名、带结论行，这就是"红"应该长成的样子。接下来两件事都值得记：

先试 `--fix`。

```text
$ npx eslint scripts/lint-probe.mjs --fix
（同两条 error，一模一样）
退出码 1
```

**这两条不是格式问题，机器修不了**——`no-unused-vars` 与 `no-debugger` 都要人决定"这个变量本来要拿来干什么"或者"这行是不是还要留着"，自动删掉就是自动改行为。真正能 `--fix` 的是格式与顺序那一类（这一轮格式规则一条都没开，所以下面那段没有可修的东西）。

然后看第四行为什么安静。`useDb()` 是服务端的自动导入，脚本里这样调用是**运行期才炸**的错，可它没报。原因就在这节第二段那张全局表：`useDb`、`requireAdmin` 这些名字被登记成了全局，而那份登记表是**按名字生效、不分文件类型**的——问四类文件都拿到 1,660 个全局名。于是这个位置出现了两条闸门都盖不住的缝：

```text
三份生成的 tsconfig（app / node / server）里，include 中提到 scripts 或 .mjs 的：0 条
```

`.mjs` 不在类型护栏里（那是 lint 的地盘），而 lint 又因为全局表放行了这个名字。**结论：脚本、配置文件这类"不在 app/ 也不在 server/"的文件里，别用自动导入，老老实实写 import**。这条不写在文档里，写在代码审查里，因为它不会报错、只在跑的时候炸。

把探针文件删掉，再跑一次全量：

```text
$ npx eslint .
Substrate/app/pages/docs/[slug].vue  89:7  warning  'v-html' directive can lead to XSS attack  vue/no-v-html
✖ 1 problem (0 errors, 1 warning)
退出码 0     耗时 3293 ms
```

回到基线：只剩那条故意留的 warning。

## 配置文件到底按哪一份：做个对照实验

flat config 是数组、按顺序合并，那当目录里有多份 `eslint.config.*` 时会用哪一份？在仓库里造一个子目录，放一份只关掉 `no-debugger` 的配置和一个带 `debugger` 的文件：

```js [probe-dir/eslint.config.mjs]
export default [
  { rules: { 'no-debugger': 'off' } },
]
```

```text
实验：npx eslint probe-dir/nested.mjs
      → 没有输出，退出码 0                     ← 生效的是 probe-dir 里那份

对照：npx eslint --config eslint.config.mjs probe-dir/nested.mjs
      → 2:3 error Unexpected 'debugger' statement，退出码 1
```

同一份代码、同一条命令，只因谁被找到而结果相反，对照组证明文件本身确实会被扫。**所以 flat config 是从被扫文件所在目录往上找到的第一份 `eslint.config.*`**，子目录里放一份就能改变那一片的规则；`--config` 可以强行指定、绕过这套查找。还有一条同源的坑：命令行里的路径是按当前工作目录解析的，在 `Substrate/` 里写 `Substrate/probe-dir/nested.mjs` 会得到退出码 2 和一句 `Oops! Something went wrong! :(`——它不是在说规则坏了，是说找不到那个文件。

## 格式规则一条都没开（这是个决定，不是遗漏）

四类文件的启用规则里，`style/*` 与 `@stylistic/*` 的数量都是 0。也就是说引号风格、分号、缩进这些现在没人管，`npm run lint:fix` 在格式上也无事可做。生成配置的依赖里能看到它引了 `@stylistic/eslint-plugin` 这个包（`@nuxt/eslint-config/dist/flat.d.mts` 第 3 行），但本机解析出来的规则表里没有格式类条目——要开该往哪一位传选项，这一轮没有取证，所以不写配方。

这个项目现在的取舍是：代码风格跟着仓库里已有的文件写，格式交给编辑器；真要上强制格式，单独开一轮，把要立的规则列成一张表再逐条落地，而不是顺手打开一个会同时改动几百个文件的开关。

## 这一步的自查清单

1. `npm run lint` 绿之前，先确认 `.nuxt/eslint.config.mjs` 存在——它是 prepare 生成的，新克隆的仓库没跑过 `nuxt prepare` 时 lint 起不来。
2. 数一遍扫到了多少文件（`npx eslint . --format json` 数数组长度）。161 个是这仓库现在的数，突然少十几个就说明有目录被忽略掉了。
3. 别把 `rc=0` 读成"没问题"：warning 不进退出码，本项目现在挂着一条 `vue/no-v-html`，那是有意留下的、旁边有说明注释。
4. 红的时候只修报错那几条，不要指望 `--fix` 修逻辑类规则；`--fix` 前后各跑一次，看变化的是哪几条。
5. 不在 `app/`、`server/` 里的文件（`scripts/`、各种 `*.config.*`）显式 import，不用自动导入——lint 的全局表和类型护栏在那儿都盖不住。
6. 想给某个子目录换规则，就在它里面放一份 `eslint.config.mjs`；调试时用 `--config` 强制指定，能分清"规则没生效"和"文件没被扫"。

| 现象 | 先查什么 |
| --- | --- |
| `eslint .` 报找不到配置 | `.nuxt/` 在不在，先 `nuxt prepare` |
| 某目录里的文件一次都没被扫 | 那份目录里是否另有一层配置或 `ignores`；用 `--format json` 数文件数 |
| 未定义的自动导入没报错 | TS/Vue 文件里 `no-undef` 默认关；这类拼错要靠类型检查和运行期 |
| 同一句报错在 `.ts` 和 `.mjs` 里名字不同 | 它们吃的是两套规则家族，看 `--print-config` 的输出 |
| 加了格式规则就一片红 | 那是存量问题，单开一轮处理，别和 function 改动混在同一个提交里 |
