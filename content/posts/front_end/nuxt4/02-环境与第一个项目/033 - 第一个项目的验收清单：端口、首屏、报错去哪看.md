到 032 为止，项目能建、能起、编辑器有类型、环境也能固定在容器里。但"我看到浏览器有东西显示"和"我确认它是对的"是两件事。这一篇给你一张**七项验收清单**，每项都告诉你去哪里读证据，不靠感觉。

## 第 1 项：服务真的起在哪个端口

官方对 `nuxt dev` 的定义里带着地址：

> `dev` 命令启动一个带热模块替换的开发服务器，位于 <http://localhost:3000>

**但"默认 3000"不等于"一定在 3000"。** 端口取自这条优先级（官方原文）：

> 端口和 host 也可以通过 `NUXT_PORT`、`NITRO_PORT`、`PORT`、`NUXT_HOST`、`NITRO_HOST` 或 `HOST` 环境变量来设置。

选项表里写得更细：`-p, --port` 的默认是 `NUXT_PORT || NITRO_PORT || PORT || nuxtOptions.devServer.port`。

验收动作：**以终端面板打出来的那个 URL 为准，不要凭记忆输入 3000。** Windows 用户再叠上 023 那条：地址栏用 `127.0.0.1` 而不是 `localhost`。

## 第 2 项：你是不是开着第二个 dev

这条最容易骗过自己：你以为在验新改动，其实屏幕上还是旧的那个实例。官方的机制是：

> dev 服务器会在你的 [build 目录](https://nuxt.com/docs/4.x/directory-structure/nuxt) 里把自己记录进 `nuxt.lock`，所以同一个项目的第二个 `nuxt dev` **会报告已经运行的那一个，而不是跟它抢端口**。传 `--takeover` 来停掉它并在它的位置启动，或设置 `NUXT_IGNORE_LOCK=1` 依然再跑一个服务器（官方标注 unsupported）。

验收动作：**要换就明确换。** 用 `--takeover`，或者干脆先停掉旧的再起新的。`NUXT_IGNORE_LOCK=1` 官方自己写着"unsupported"，别拿它当解决方案。

## 第 3 项：知道面板上每个键是干什么的

官方描述：

> 在交互式终端里，`nuxt dev` 会渲染一个固定面板：服务器 URL、启动进度、当前状态、一排快捷键，日志折叠在它上方。**当输出不是终端、在 CI 里、附着了调试器，或者终端太小**时，它回退为纯日志流。

那张快捷键表就是你排查时的导航，值得抄在便签上：

| 键 | 作用 |
| --- | --- |
| `r` | 重启 dev 服务器 |
| `shift-r` | 清空缓存后重启 |
| `o` | 在浏览器打开应用 |
| `y` | 复制服务器 URL |
| `i` | 显示版本、URL、二维码与会话信息 |
| `l` | 浏览日志历史 |
| `e` | 打开到最后一条错误处的日志 |
| `n` | 浏览被服务的请求 |
| `p` | 浏览页面与服务端路由 |
| `c` | 清掉日志、请求与控制台 |
| `?` | 显示全部快捷键 |
| `q` | 退出 |

在视图内部还有：`y` 复制选中行，`shift-y` 复制筛选与搜索剩下的所有行（太多放不下时保留最新的）；在 info 视图里 `shift-y` 复制的是 [`nuxt info`](https://nuxt.com/docs/4.x/api/commands/info) 那张表。

**注意你多半用不上这张表**：只要你在 CI 里看日志、或者挂着调试器、或者窗口很窄，面板就退化成纯日志流，官方给退化模式的键是另一组更少的集合：`r` 重启、`o` 打开、`u` 显示 URL、`qr` 二维码、`copy` 复制 URL、`c` 清控制台、`h` 帮助、`q` 退出。

## 第 4 项：报错去哪看，而不是只看终端最后一行

三项按顺序用：

**`e`** —— 直接跳到"最后一条错误"处的日志，不用自己往上翻。

**`l`** —— 浏览日志历史（错误之前的上下文往往才是原因）。

**`n` + `回车`** —— 官方叫"追踪一个请求"：

> 在网络视图（`n`）里，选中一个请求并按 `enter` 来看它的时间花在哪。这条追踪把服务端为那个请求做的一切画在同一张时间线上：**路由中间件、服务端路由处理函数、Nuxt 插件、钩子、数据获取、渲染，以及你的应用向其它服务器发起的请求。** 时间线下面，它列出 Vite 为该请求编译模块花了多久，按 Vite 插件和最慢模块拆分，接着是该请求产生的日志。

这段是整张清单里性价比最高的一项——**"页面慢"到底是渲染慢还是某个取数慢、还是 Vite 编译慢，一张时间线就能分开。**

它靠什么工作，官方也说了：

> 追踪由 Nuxt 与 Nitro 发布的 tracing channel 构建，所以它能显示多少取决于你的版本。`nuxt dev` 会替你打开 `tracingChannel` 选项；在 `nuxt.config` 里设 `tracingChannel: false` 可以退出。

**"取决于你的版本"这句要留意**：看不到某一段，不一定是你配置错了。

## 第 5 项：`p` 与你的路由对得上

`p` 键浏览"页面与服务端路由"。用它核对两件事：你以为存在的页面是不是真的注册上了（回指 025 那个"`<NuxtPage />` 没接"的坑），以及 `server/` 下的接口路径是不是你想的那个。这一屏是**框架实际看到的清单**，比你自己的记忆可靠。

## 第 6 项：改配置后，重启的理由对不对

官方区分两种情况：

> 当 dev 服务器 reload 或 restart 时，它会说明是什么引起的；而 `nuxt.config` 的变化还会**列出真正不同的那些键**，所以由一次只改格式的编辑触发的重启，可以和一次确实改了配置的重启区分开。**reload 原地发生；restart 替换进程**，这是 `nuxt.config` 或已安装依赖的变化所需要的。

验收动作：**看它列出的键。** 如果你只改了空格和换行，而它列不出任何不同的键，说明你的改动确实没影响配置——这能省掉"我明明改了怎么没生效"的自我怀疑。

## 第 7 项：一次收齐环境信息

`nuxt info` 收集什么，官方原话：

> `info` 命令打印当前或指定 Nuxt 项目的信息：它解析到的 **Nuxt、Nitro 与 Vite 的版本、包管理器、它加载的模块，以及配置里的构建模块**。想从脚本里读就用 `--json`。

这一条既是你自己的体检表，也是**下一步报障时的必备附件**（下面就用得上）。

## 附加项：分不清"我不会"还是"框架有 bug"时怎么办

官方在 reporting-bugs 页开头就把这个分界摆出来了：

> 想想你是在寻求帮助，还是认为 Nuxt 本身有 bug。如果是前者，我们很乐意帮你——但最好的方式是**求助**（getting-help），而不是报 bug。

**走求助这条路**（community/getting-help），官方给的渠道是 Discord 与 Nuxters，以及"读文档没读懂"该开 GitHub Discussion。它还给了一条我认为是全套文档里最实用的提问礼仪清单：

> - *说明你的目标是什么，而不只是你面对的问题。* "我需要确保表单输入是可访问的，所以我在尝试让 id 在服务端与客户端之间一致。"
> - *确保你先读过文档并用过搜索引擎。* 用一句话告诉别人，比如"我 Google 过 'nuxt script setup'，但没找到代码示例。"
> - *说明你试过什么。* 告诉大家你实验过哪些方案以及为什么。
> - *分享你的代码。* 别人只看到错误消息或截图大概帮不上忙——但如果你以可复制粘贴的形式分享代码，情况就完全不同了，最好是最小复现的形式。

> 最后，就把问题问出来！没必要"请求允许提问"，也不用等有人回你一句 'hello'。如果你这么做，可能反而得不到回应，因为大家在等完整的问题才开始参与。

**走报 bug 这条路**（community/reporting-bugs），官方页子的四个小节就是四个步骤：先分辨是不是 bug、搜 issues、做最小复现、找准该报给谁。顺序我按页面原文摆：

1. **先分辨。** 开头那段已经给了判据：是"我不会用"就走求助，只有确认是 Nuxt 本身的行为和文档不一致才报 bug。
2. **先搜。** 

> 先搜一遍 [open issues](https://github.com/nuxt/nuxt/issues) 与 [discussions](https://github.com/nuxt/nuxt/discussions)。如果找到看起来是同一个 bug，**在已有线程下评论比新建一个重复的好得多**。

   getting-help 页还补了一句：如果有一个**已关闭**的 issue，请新建一个（别在关闭的下面顶帖）。

2. **做最小复现。**

> 从 Nuxt sandbox 开始，加上**最少**的代码来复现你遇到的 bug。

   官方给的两个入口是 `https://nuxt.new/s/v4`（StackBlitz）与 `https://nuxt.new/c/v4`（CodeSandbox）。
   
   还有一个前置分流：**如果你的问题其实关于 Vue 或 Vite，请先用 Vue SSR starter 试着复现**（官方给了 StackBlitz、CodeSandbox、GitHub 模板三个入口）。

   复现出来之后还要继续删：

   > 一旦你复现了问题，把复现里尽可能多的代码删掉（同时仍能重现 bug）。

3. **找准该报给谁。**

> 在一个 Nuxt 项目里有很多活动部件——从 Nuxt modules 到其它 JavaScript 库。试着**在最相关、最具体的地方**报这个 bug。那很可能是引起问题的某个 Nuxt 模块，或 Nuxt 依赖的上游库。

官方那一节到第四步为止。**多出来的第五步是我加的**：既然 `nuxt info` 一次就能收齐版本、包管理器与模块清单，开 issue 或发帖时直接把它贴进去，省掉别人追问三轮"你什么版本"（042 专门讲这件事）。

## 自查

- [ ] 你现在这个 dev 服务，实际端口是从哪条优先级里算出来的？
- [ ] 你确定屏幕上的是最新那个实例，还是第二个 dev 只是报告了旧实例的存在？
- [ ] 上一次报错，你用的是 `e`、`l` 还是 `n`？看过单请求时间线吗？
- [ ] 终端里那次 restart，它列出的"真正不同的键"是什么？
- [ ] 你遇到的这个，按官方的分界该走求助还是报 bug？报 bug 前你搜过 issues 吗、有最小复现吗？
