  摘要：官方 Installation 页把"从零到看到第一屏"压成了两步：先用 `npm create nuxt@latest <project-name>` 建项目（yarn 是 `yarn create nuxt`、pnpm 是 `pnpm create nuxt@latest`、bun 是 `bun create nuxt@latest`、deno 是 `deno -A npm:create-nuxt@latest`），再用 `npm run dev -- -o` 起开发服务器（yarn `yarn dev --open`、pnpm `pnpm dev -o`、bun `bun run dev -o`、deno `deno run dev -o`），官方承诺此时浏览器会自动打开 http://localhost:3000。这两条命令跑的其实都是 package.json 里的脚本，而脚手架给出的最小 package.json 只有五个脚本：build、dev、generate、preview，以及会在装完依赖后自动执行的 postinstall "nuxt prepare"。

021 已经把 `create nuxt` 的全部参数讲完了，那篇是参数手册视角。这一篇只走最短路径，两条命令，看到第一屏。中途你会看到五个脚本、一个 `-o`、和一个端口号，我把它们一次讲清。

第一步，建项目。官方给的命令，按包管理器分五种写法。

```bash [npm]
npm create nuxt@latest <project-name>
```

```bash [yarn]
yarn create nuxt <project-name>
```

```bash [pnpm]
pnpm create nuxt@latest <project-name>
```

```bash [bun]
bun create nuxt@latest <project-name>
```

```bash [deno]
deno -A npm:create-nuxt@latest <project-name>
```

三个观察点。

yarn 那条没有 `@latest`，其它都有。这不是排版漏了，是官方原样给的写法。

deno 那条完全不同，它写的是包名 `npm:create-nuxt@latest`，前面还挂了个 `-A`。`-A` 的含义这一页没解释，要去查 Deno 的权限参数，照抄即可。

名字 `<project-name>` 换成你的项目目录名。这一步内部发生了什么、模板怎么选，见 021。

建完之后，官方给了两个动作，任选。

```bash [Terminal]
code <project-name>
```

或者从终端进入你的新项目目录。

```bash
cd <project-name>
```

第二步，起开发服务器。同样是五种写法。

```bash [npm]
npm run dev -- -o
```

```bash [yarn]
yarn dev --open
```

```bash [pnpm]
pnpm dev -o
```

```bash [bun]
bun run dev -o

# To use the Bun runtime during development
# bun --bun run dev -o
```

```bash [deno]
deno run dev -o
```

然后官方的那句承诺，做得好，浏览器窗口应该会自动打开 http://localhost:3000。

这里有四件值得说明白的事。

一，那个 `-o` 或 `--open` 就是打开浏览器。从官方把 `-o` 和浏览器窗口应该会自动打开放在同一屏来看，它是打开的意思。`nuxt dev` 的完整开关清单在 034 逐条讲。不加这个参数，服务照样起，只是不会自动弹浏览器。

二，npm 那条为什么多一个 `--`。021 讲过同一件事，`npm create` 或 `npm run` 会把跟在后面的、长得像参数的东西当成 npm 自己的配置吃掉，所以要加一个 `--` 把它后面的原样传下去。yarn、pnpm、bun、deno 是把整条命令行原样转发，所以直接写 `-o`。

三，bun 那两行注释是另一个意思。官方在 bun 的例子里额外写了一行 `bun --bun run dev -o`，注释说要在开发期间使用 Bun 运行时。也就是说默认那条不一定用 Bun 跑，想真正用 Bun 的运行时得加 `--bun`。

四，地址栏用哪个名字。023 里那条 Windows 建议在这就是用的，Windows 上把 `localhost:3000` 换成 `127.0.0.1:3000`。

这两条命令其实都在跑脚本。

`npm run dev` 里没有 `nuxt` 这个词，但它确实在跑 Nuxt。原因在脚手架生成的 `package.json` 里。官方给出的最小形态是这样。

```json [package.json]
{
  "name": "nuxt-app",
  "private": true,
  "type": "module",
  "scripts": {
    "build": "nuxt build",
    "dev": "nuxt dev",
    "generate": "nuxt generate",
    "preview": "nuxt preview",
    "postinstall": "nuxt prepare"
  },
  "dependencies": {
    "nuxt": "latest",
    "vue": "latest",
    "vue-router": "latest"
  }
}
```

对着看就清楚了，`npm run dev` 到 `scripts.dev` 再到 `nuxt dev`。框架的命令都藏在这些脚本里，而不是你手打。

五个脚本各自的时机。`dev` 是开发期间，起带热更新的本地服务，就是上面这一步。`build` 是出生产产物。`generate` 是预渲染出静态站点。`preview` 是构建之后在本地先看一眼。`postinstall` 不用你手动跑，`npm install` 完成后自动执行。

`build`、`generate`、`preview` 三者的关系在 012、029、037 到 039 分别展开。这里只有一行现在就要用上的信息。

`postinstall` 里那句 `nuxt prepare` 意味着你装依赖的那一刻，框架的类型就已经生成过一次了。所以偶尔你只 `npm install` 完、还没跑 `dev`，编辑器就已经不报找不到模块了，不是玄学，是这条脚本干的事，`nuxt prepare` 本身在 035 讲。

另外两个字段也顺便对上前面学过的东西。

`"type": "module"`，015 讲 ESM 时说过，`.js` 默认被当成 CommonJS，除非它的 `package.json` 声明了 `"type": "module"`。脚手架一开始就把这一行写好了。

`"private": true`，这一页只写了字段没解释含义。

`dependencies` 里除了 `nuxt`，还显式列了 `vue` 和 `vue-router`，这是 014 讲核心包各自负责什么时会用到的事实。

官方在这一步末尾留的提示。如果你在用 Docker，或者想让开发环境在多台机器上保持一致，考虑使用 dev container。

这条在 032 单独展开，就两个文件，`.devcontainer/devcontainer.json` 和 `Dockerfile`。现在你只要知道，我这台机器上跑得好好的这类问题，有一条专门的解法，不必硬扛。
