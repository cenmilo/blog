018 立了两条硬规则、029 说过"生产环境没人替你加载 `.env`"。这一篇把 `.env` 这个文件本身讲完：**它有一个明确的读取窗口，窗口外它什么都不是。**

## 官方给的两个定性

> `.env` 文件规定的是你的**构建期 / 开发期**环境变量。
>
> （important）**这个文件应当加入你的 `.gitignore`，以免把密钥推进你的仓库。**

**标题那半句"build/dev-time"就是全篇的钥匙。** 053 抄过的官方 `.gitignore` 清单里那三行也是为它准备的：

```
.env
.env.*
!.env.example
```

## 窗口之内：dev、build、generate

> Nuxt CLI 通过 c12 内置 `.env` 支持，**在开发模式以及运行 `nuxt build` 与 `nuxt generate` 时生效。**
>
> **除了任何进程环境变量之外**，如果你在你的项目根目录有一个 `.env` 文件，它会**在 dev、build 与 generate 时被自动加载**。在那里设置的任何环境变量，都可以在你的 `nuxt.config` 文件与模块里访问到。

```ini [.env]
MY_ENV_VARIABLE=hello
```

**读两句：**

1. **"除了任何进程环境变量之外"——它不是替代，是叠加。** 真实进程环境里已经有的值，仍然在那儿。
2. **能访问到的是 `nuxt.config` 与模块**，也就是**构建期那一侧**（072 讲过 `nuxt.config` 跑在 CLI 进程里）。**这不等于运行时能读到它**——那要靠 `runtimeConfig`（018）。

然后是一条很容易吃暗亏的 note：

> 请注意，**从 `.env` 里删除一个变量、或者把 `.env` 文件整个删掉，都不会取消那些已经被设定过的值。**

**这条的实际后果：**"我把那个变量删了，为什么还在？"——**因为它是被写进 `process.env` 的，删除文件不会反向清除。** 你需要**重启进程**（072 讲过 `.env` 变化会触发完全重启），必要时重启终端/容器。

## 换文件名：`--dotenv`

> 如果你想用一个不同的文件——例如用 `.env.local` 或 `.env.production`——**你可以在使用 Nuxt CLI 时传 `--dotenv` 参数来做到。**

```bash [Terminal]
npx nuxt dev --dotenv .env.local
```

> 在开发模式下更新 `.env` 时，Nuxt 实例会自动重启，以把新的值应用到 `process.env`。

**这两句合起来补了 034/037/039 那张选项表里的 `--dotenv`**：官方那句"可重复传、靠后的文件优先"就适用于这里。

## 官方那条 important：应用代码里别用裸环境变量

> **在你的应用代码里，你应当使用 Runtime Config，而不是普通的环境变量。**

**这一句是整个 `.env` 机制的落脚点。** 应用代码里写 `process.env.X`：

- **在浏览器那一侧没有 `process.env`**（013 讲过两侧执行）；
- 而且按下面的生产规则，`.env` 那时根本不被读。

**所以官方给的正解是 `useRuntimeConfig()` + `NUXT_*` 覆盖**（018 那两条硬规则）。

## 窗口之外：生产不读，理由是"有些环境没文件系统"

> **在你的服务器被构建之后**，你负责在运行服务器时设置环境变量。
>
> 此时你的 `.env` 文件**不会被读取**。怎么做取决于每个环境各不相同。
>
> **做出这个设计决定，是为了确保在各种部署环境之间的兼容性——其中一些环境可能没有传统的文件系统可用，例如 serverless 平台，或者像 Cloudflare Workers 这样的边缘网络。**

**这句理由比规则本身更值得读：它解释的是"为什么不顺手帮你读一下"。** 012 说过 Nitro 的产物是自足的；**自足的另一面就是"不假设旁边有文件"**。

于是官方把动作交给你，并给了三类常见做法：

> 由于 `.env` 文件在生产中不被使用，**你必须用你的托管环境提供的工具与方法显式设置环境变量。** 以下是一些常见途径：
>
> - 你可以通过终端把环境变量作为参数传入：
>   `$ NODE_ENV=production DATABASE_HOST=mydatabaseconnectionstring node .output/server/index.mjs`
> - 你可以在 shell 配置文件里设置环境变量，例如 `.bashrc` 或 `.profile`。
> - 许多云服务提供商（例如 Vercel、Netlify 与 AWS）通过它们的控制台、命令行工具或配置文件提供设置环境变量的界面。

**第一条那个命令你应该觉得眼熟**——029 抄过的生产启动命令就是它（`node .output/server/index.mjs`，默认监听 3000）。

然后是用 important 标的那条前缀规则：

> `runtimeConfig` **在生产里不会接管那些不以 `NUXT_` 开头的环境变量。**

**这就是 018 第一条硬规则在生产侧的表述**：`DATABASE_HOST=...` 这种变量**不会**自动落进 `runtimeConfig.databaseHost`；**要 `NUXT_` 前缀**。

## 本地想看生产行为：`nuxt preview` 是那个例外

> 出于本地生产预览的目的，**我们建议使用 `nuxt preview`，因为使用这条命令时，`.env` 文件会被加载进 `process.env` 以提供便利。请注意这条命令要求在包目录里已经安装了依赖。**

> 或者你可以像上面那样通过终端把环境变量作为参数传入。例如在 Linux 或 macOS 上：

```bash [Terminal]
NODE_ENV=production DATABASE_HOST=mydatabaseconnectionstring node .output/server/index.mjs
```

> 请注意，**对于纯静态站点，在你的项目被预渲染之后，是不可能再设置运行时配置的。**

**这一段有三条判断要用：**

1. **`.env` 在生产不被读，但 `nuxt preview` 会读**——029 我把这条列为"preview 会骗人"的第一条，机制就在这里。
2. **这个便利是有前提的**：`preview` 要求依赖已安装（它跑的是带工具链的那一层）。
3. **纯静态站点没有"运行时配置"这件事**——预渲染完就定了（对照 038 那份 `_payload.json` 与"构建时捕获"）。

## 一条替代方案：`appConfig`

官方在页末用 note 给了一个常常被忽略的选择：

> 如果你想使用在构建期设置、**但并不关心它以后会不会更新的环境变量**（或者只需要在*你的应用内部*对它们作出反应式更新），那么 **`appConfig` 可能是更好的选择。你可以既在 `nuxt.config` 里（使用环境变量）定义 `appConfig`，也可以在你项目里的 `~/app.config.ts` 文件中定义它。**

**这与 055 那条 caution 形成一组对照，判据很清楚：**

| 需求 | 选择 |
| --- | --- |
| 值要能在部署后改 | `runtimeConfig` + `NUXT_*` 环境变量 |
| 值在构建期就定了、之后不改 | `appConfig`（可以是**两侧都在**的那份） |
| 任何情况下都不能进浏览器 | **既不是 `.env` 也不是 `appConfig`** —— 只能是 `runtimeConfig` 顶层的私有键（055：`app.config` 会进客户端包） |

**第三行是我按 055 那条 caution 与本页"构建期"定性给的组合判断**，官方在这一节只写了 `appConfig` 适合"构建期设置、之后不更新"。
