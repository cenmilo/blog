  摘要：这一节把目录结构部分的全部结论压成六张表，查的时候按"目录 → 配置项 → 默认值 → 相对谁 → 改名要核对什么"走。官方的总纲是三句：Nuxt 应用有一套用来组织代码的特定目录结构；根目录就是包含 nuxt.config.ts 的那个目录；app/ 是应用的主目录。基准只有两种——srcDir 与 rootDir，而默认值里带 app/ 前缀的那批（pages、layouts、middleware、plugins、assets）与不带前缀的那批（modules、public、shared）就分在两侧。最容易记错的三条：serverDir 的默认是 /<rootDir>/server，基准是 rootDir 而不是 srcDir，所以只改 srcDir 时服务端目录不动；typesDir 默认取 buildDir 但官方刻意把它与 buildDir 分开，为的是让根 tsconfig.json 引用的那些配置在 Nuxt 到别处构建时仍留在原地；watch 的基准是 srcDir，与前面那四个以 rootDir 为基准的选项不同。另外两个坑：官方把 .nuxt 要求加进 .gitignore，而 nuxt cleanup 删的是"你的构建目录，也就是 .nuxt，除非 buildDir 另有说明"；根目录旁边放独立的 vite.config 或 webpack.config 会撞上 NUXT_B5004，因为 Nuxt 内部管理打包器并忽略这些文件。

目录结构讲到这里，篇目不少了。这一页不引入新东西，只做一件事：把结论排成可以按行查的表。遇到这个文件该放哪、改了为什么没生效，先在这六张表里定位。

表一：官方的三句总纲。

| 官方结论 | 原话要点 |
| --- | --- |
| 结构的存在理由 | Nuxt 应用有一套特定的目录结构用来组织代码，这套结构设计得容易理解、并以一致的方式使用 |
| 根目录 | Nuxt 应用的根目录就是包含 `nuxt.config.ts` 文件的那个目录，该文件用于配置这个 Nuxt 应用 |
| 主目录 | `app/` 是 Nuxt 应用的主目录 |

判断是不是 Nuxt 项目 的官方依据是 `nuxt.config.ts` 在不在，而不是某个目录名。

表二：官方列出的目录与用途。

`app/` 下的八个子目录。

| 目录 | 官方说明 |
| --- | --- |
| `app/assets/` | 由构建工具（Vite 或 webpack）处理的网站资源 |
| `app/components/` | 应用的 Vue 组件 |
| `app/composables/` | 放置你的 Vue 组合式函数 |
| `app/layouts/` | 包裹在你的页面外层、避免页面之间重新渲染的 Vue 组件 |
| `app/middleware/` | 在导航到某个路由之前运行代码 |
| `app/pages/` | 文件式路由，用来在你的 Web 应用里创建路由 |
| `app/plugins/` | 在 Nuxt 应用创建时使用 Vue 插件等 |
| `app/utils/` | 放置贯穿应用、可在组件、组合式函数和页面里使用的函数 |

`app/` 下的三个特定文件。

| 文件 | 官方说明 |
| --- | --- |
| `app/app.config.ts` | 应用内部的响应式配置 |
| `app/app.vue` | 你的 Nuxt 应用的根组件 |
| `app/error.vue` | 你的 Nuxt 应用的错误页 |

`app/` 之外的目录。

| 目录 | 官方说明 |
| --- | --- |
| `public/` | 包含应用的公开文件，这里的文件在根路径提供服务，不被构建过程修改，适合必须保住文件名的（例如 `robots.txt`）或基本不会变的（例如 `favicon.ico`） |
| `server/api/` | 包含应用的 API 路由 |
| `server/routes/` | 包含应用的服务端路由（例如动态的 `/sitemap.xml`） |
| `server/middleware/` | 在服务端路由被处理之前运行代码 |
| `server/plugins/` | 在 Nuxt 服务器创建时使用插件等 |
| `server/utils/` | 放置贯穿你的服务端代码的函数 |
| `shared/` | 包含 Nuxt 应用与 Nuxt 服务器之间的共享代码，Vue 应用和 Nitro 服务端都能用 |
| `test/` | 应用测试（单元、Nuxt 运行时、端到端）的推荐位置 |
| `content/` | 由 Nuxt Content 模块启用，用 Markdown 文件搭文件式 CMS |
| `modules/` | 包含应用的本地模块，模块用于扩展应用功能 |
| `layers/` | 组织并共享可复用的代码、组件、组合式函数与配置，这一层里的 layer 会被自动注册进你的项目 |

三个配置文件。

| 文件 | 官方说明 |
| --- | --- |
| `nuxt.config.ts` | Nuxt 应用的主配置文件 |
| `.nuxtrc` | 配置 Nuxt 应用的另一种语法（对全局配置有用） |
| `.nuxtignore` | 在构建阶段忽略根目录里的文件 |

表三：每个目录由哪个配置项决定。

| 目录 | 配置项 | 默认值 | 官方给的基准 |
| --- | --- | --- | --- |
| 根目录本身 | `rootDir` | `"/<rootDir>"` | 它自己是基准，`nuxt ./my-app/` 会把它设为该路径的绝对路径 |
| 源目录 | `srcDir` | `"app"`（Nuxt 4）/ `"."`（Nuxt 3 配 `compatibilityMode: 3`） | 相对路径相对 `rootDir` |
| `app/` | `dir.app` | `"app"` | `dir` 一节整体 |
| 页面 | `dir.pages` | `"app/pages"` | 同上 |
| 布局 | `dir.layouts` | `"app/layouts"` | 同上 |
| 中间件 | `dir.middleware` | `"app/middleware"` | 同上 |
| 插件 | `dir.plugins` | `"app/plugins"` | 同上 |
| 资源 | `dir.assets` | `"app/assets"` | 同上，构建里别名为 `~assets` |
| 模块 | `dir.modules` | `"modules"` | 同上 |
| 静态 | `dir.public` | `"public"` | 同上 |
| 共享 | `dir.shared` | `"shared"` | 同上 |
| 服务端 | `serverDir`（顶层，不在 `dir` 里） | `"/<rootDir>/server"` | 相对 `rootDir` |
| 构建产物 | `buildDir` | `"/<rootDir>/.nuxt"` | rootDir |
| 生成类型 | `typesDir` | `"/<rootDir>/.nuxt"` | 默认取 `buildDir`，但与之分开，相对 `rootDir` |
| 工作区 | `workspaceDir` | `"/<workspaceDir>"` | Nuxt 会尝试自动检测，可覆盖 |
| 解析用的模块目录 | `modulesDir` | `["<rootDir>/node_modules"]` | 配置路径相对于 `options.rootDir` |

看默认值的前缀就能分出两侧：`dir.pages`、`dir.layouts`、`dir.middleware`、`dir.plugins`、`dir.assets` 五个默认带 `app/`；`dir.modules`、`dir.public`、`dir.shared` 三个不带。`dir` 这一节官方自己的建议是除非必要最好保持默认。

表四：基准只有两个，但记错的都在同一处。

| 记法 | 内容 |
| --- | --- |
| `app/` 那一族 | 认 `srcDir`：改了 `srcDir`，页面、布局、中间件、插件、资源的路径解释跟着变 |
| `server/`、`buildDir`、`typesDir`、`modulesDir` | 认 `rootDir`：改 `srcDir` 对它们没有任何影响 |
| `watch` | 认 `srcDir`（以及各层的 `srcDir`），它和上一行那四个不同基准 |

最典型的一次踩空：把 `srcDir` 改成 `sources`，然后发现 `server/` 还在项目根、`.nuxtignore` 里旧前缀的行全部失效。

表五：别名速查。

| 别名 | 指向 | 依据 |
| --- | --- | --- |
| `~` | `"/<rootDir>/app"` | `alias` 的官方默认值 |
| `~~` | `"/<rootDir>"` | `alias` 的官方默认值，`modules` 数组里的项若在 rootDir 解析则用到 `~~` |
| `~assets` | 资源目录 | `dir.assets` 的官方说明 |
| `#server` | 服务端目录内的任意文件（v4.3） | 只能在 `server/` 内使用，在客户端代码里从 `#server` 导入会报错 |
| `#build` | 虚拟文件系统里的生成物 | 官方构建器指南：入口、路由表、插件与组件注册表等虚拟文件系统在 `#build` 之下 |
| `#imports` | 所有自动导入 | 官方自动导入指南：Nuxt 用 `#imports` 暴露每一个自动导入，可用于显式导入 |
| `#shared` | 共享目录（该别名由 Nuxt 自动配置） | `shared/` 里除自动导入之外的文件必须用 `#shared` 手动导入，例如 `import capitalize from '#shared/capitalize'` |

表六：改名 / 挪位置的代价。

| 你想动的 | 改哪个 | 改完必须核对 |
| --- | --- | --- |
| 源码目录 | `srcDir` | `.nuxtignore` 每行的前缀、`watch` 的基准、`app.config.ts` 的位置 |
| 服务端目录 | `serverDir` | 四类自动注册目录、`/api` 前缀、中间件不得返回、`#server` 能否解析、`server/types` 的自动导入与那条覆盖 server 文件夹的 project reference |
| 构建产物目录 | `buildDir` | `.gitignore` 里那一行 `.nuxt` 盖不住新目录，`nuxt cleanup` 会自动跟随 |
| 生成类型目录 | `typesDir` | 根 `tsconfig.json` 那四条 `./.nuxt/tsconfig.*.json` 引用，实测 `nuxt prepare` 与 `nuxt typecheck` |
| 页面目录 | `dir.pages` | 文件式路由是否还生成（这是官方说最好保持默认的那一项） |

两条根本不该出现在根目录的东西。

一，独立的打包器配置文件。官方错误码 NUXT_B5004 针对的就是它：Nuxt 在 `nuxt.config` 旁边发现独立的 `vite.config` 或 `webpack.config` 时会报出来，因为 Nuxt 内部管理打包器并忽略这些文件。正确做法是把内容移进 `nuxt.config` 对应的键，即 `vite`、`webpack`、`nitro`、`postcss`，然后删掉外部文件。

二，不该被提交的生成目录。`.nuxt` 应当进 `.gitignore`，因为运行 `nuxt dev` 时整个目录会被重新创建，同理，`.output` 是构建输出，也不属于源码。
