052 看了开发期的生成目录 `.nuxt`，这一篇看另一个：`.output`。两者的差别一句话就能说完——一个是给开发用的中间物，一个是你要真的拿去部署的东西。

顺便把 `.gitignore` 那节的官方清单抄下来，因为这两个目录都靠它才不被误提交。

官方给 `.output` 的那一节非常短，拢共四句话，每句都有用。Nuxt 在为生产构建你的应用时创建 `.output/` 目录。这个目录应当加入你的 `.gitignore` 文件，以避免把构建输出推送到你的仓库。用这个目录把你的 Nuxt 应用部署到生产。还有那句熟悉的老话：你不应触碰其中的任何文件，因为运行 `nuxt build` 时整个目录会被重新创建。

对照 052 的 `.nuxt` 那一节，结构一模一样：谁创建它、加 `.gitignore`、别碰里面。差别就在"重建"那个词上——`.nuxt` 的 warning 写的是跑 `nuxt dev` 时重建，`.output` 写的是跑 `nuxt build` 时。两个目录各自跟着自己的命令重生，这就是它们的分工。

可执行的入口在哪。`.output` 那一节自己没往下拆，但另一节早给过答案。Server Engine 一节讲 Nitro：它产出一个独立于 `node_modules` 的服务器 dist，Nuxt 在跑 `nuxt build` 时把它生成到 `.output` 目录。而部署页给了入口文件的完整启动命令，029 抄过：

```bash [Terminal]
NODE_ENV=production node .output/server/index.mjs
```

"独立于 `node_modules`"是 `.output` 最值钱的性质：部署时不用带着整个仓库和依赖目录走，带这一份产物就够了。029 里那个提醒也是从这儿来的——`.env` 在生产运行阶段不会被读取，因为那时跑的只是这个自足产物。

静态托管那边也有入口。038 讲 `ssr: false` 时，官方说的是 `.output/public/index.html` 入口与 JS 包，要上传的就是 `.output/public`。

把两个目录放一起看。官方定位上，`.nuxt` 是开发时用来生成 Vue 应用的，`.output` 是为生产构建时创建、拿去部署的。生成命令也不同：`.nuxt` 由 `nuxt dev`、`nuxt build`、`nuxt prepare` 三条生成，`.output` 只有 `nuxt build`。重建的触发器分别是 `nuxt dev` 和 `nuxt build`。里面值得认识的，`.nuxt` 有四份 tsconfig 和 `nuxt.lock`，052 讲过；`.output` 有 `server/index.mjs`，029 讲过，还有 `public/index.html`，038 讲过。

共同点也一样重要：两个都不能当输入改，它们都是输出；两个都在 `nuxt cleanup` 的删除清单上，040 那份。所以清完之后，开发要重新 `nuxt prepare`，想验产物得重新 `nuxt build`，两边都不是顺手就能恢复的。

`.gitignore` 那一节给了一份可直接抄的最小清单，官方措辞是"至少包含以下条目"：

```bash [.gitignore]
# Nuxt dev/build outputs
.output
.data
.nuxt
.nitro
.cache
dist

# Node dependencies
node_modules

# Logs
logs
*.log

# Misc
.DS_Store

# Local env files
.env
.env.*
!.env.example
```

对着分组读一遍。

开发与构建输出那六项，前两行你已经认识了——`.nuxt` 是 052 的，`.output` 是本篇。后面四项 `.data`、`.nitro`、`.cache`、`dist`，官方没在这一节解释含义，我不替它们编定义，照抄清单。不过这份清单对 040 有个直接价值：cleanup 清的五项里就有 `dist` 和 `.cache` 这两族名字。哪些目录是生成物，官方在这两处给的是同一批名字，这个对照是两份清单并排看才发现的。

`node_modules` 没什么好说的。030 讲锁文件时说过，一个项目只该有一种锁文件，而依赖目录永远不该进仓库。日志两项，`logs` 和 `*.log`。

最值得停一下的是最后三行：`.env`、`.env.*`、`!.env.example`。前两行忽略所有本地环境文件——`.env` 和任何 `.env.xxx`；第三行那个 `!` 是把 `.env.example` 排除在忽略之外。这个写法表达的是个很常见的工程习惯：环境变量的键清单要提交，让同事知道该配哪些；值绝不提交。这和 018、029 讲的是同一件事的三个面——runtimeConfig 的默认值写在 `nuxt.config`，可提交；真实值走环境变量，不可提交；`.env.example` 是那份可提交的键清单。

最后提醒一下新手最容易踩的两个坑，正好一边一个。

改 `.nuxt` 里的文件想让行为变？052 那条 warning 已经封死了这条路，dev 一跑就重建。

改 `.output` 里的文件想让线上变？本篇这条 warning 同样封死了。而且更糟：你改的那份产物根本不会被推上仓库——它在 `.gitignore` 里，部署时构建出来的还是原始代码的产物。

两条路最后都指向同一个动作：改源码，或者改配置。生成物只是结果。
