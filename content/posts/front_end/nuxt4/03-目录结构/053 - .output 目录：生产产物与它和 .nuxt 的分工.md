052 看了开发期的生成目录 `.nuxt`。这一篇看另一个：`.output`。**两者的差别就一句话——一个是给开发用的中间物，一个是你要真的拿去部署的东西。**

顺便把 `.gitignore` 那页官方清单抄下来，因为这两目录都靠它才不被误提交。

## 官方给 `.output` 的四句原话

这一页非常短，但四句每句都有用：

> **Nuxt 在为生产构建你的应用时创建 `.output/` 目录。**
>
> （important）**这个目录应当加入你的 `.gitignore` 文件，以避免把构建输出推送到你的仓库。**
>
> **用这个目录把你的 Nuxt 应用部署到生产。**
>
> （warning）**你不应触碰其中的任何文件，因为运行 `nuxt build` 时整个目录会被重新创建。**

对照 052 里 `.nuxt` 那一页，你会发现**两页的结构是一样的**：都是"谁创建它 + 加 `.gitignore` + 别碰里面"。

**差别在触发时机那句**：`.nuxt` 页的 warning 写的是"运行 `nuxt dev` 时整个目录会被重新创建"，而 `.output` 页写的是"**运行 `nuxt build` 时**"。**这就是两个目录的分工——它们各自跟着自己的命令重生。**

## `.output` 里那个可执行的入口

这一页自己没往下拆目录，但另一页已经给了那个路径。**Server Engine 那一页讲 Nitro 的"独立服务器 dist"（standalone server dist）：**

> Nitro 产出一个**独立于 `node_modules`** 的服务器 dist。
>
> Nuxt 在运行 `nuxt build` 时把它生成到 `.output` 目录。

而部署页给的就是那个入口文件的完整启动命令（029 抄过）：

```bash [Terminal]
NODE_ENV=production node .output/server/index.mjs
```

**"独立于 `node_modules`"这半句是 `.output` 最有价值的性质**：部署时你不需要带着整个仓库和依赖目录走，带这一份产物就够了。这也是 029 里那个提醒的来源——**`.env` 在生产运行阶段不会被读取**，因为那时跑的只是这个自足产物。

产物侧的另一个入口也在这里：038 讲 `ssr: false` 时，官方说的是"`.output/public/index.html` 入口与 JS 包"——**静态托管要上传的就是 `.output/public`**。

## 一张对照表：`.nuxt` 与 `.output`

| | `.nuxt` | `.output` |
| --- | --- | --- |
| 官方定位 | 开发时用来生成你的 Vue 应用 | 为生产构建时创建；用它部署到生产 |
| 谁生成 | `nuxt dev`、`nuxt build`、`nuxt prepare` | `nuxt build` |
| "别碰"的理由 | 跑 `nuxt dev` 时整个目录重建 | 跑 `nuxt build` 时整个目录重建 |
| 里面值得认识的东西 | 四份 tsconfig、`nuxt.lock`（052） | `server/index.mjs`（029）、`public/index.html`（038） |
| 能不能当输入改 | 不能，它是输出 | 不能，它也是输出 |
| 被 `nuxt cleanup` 删 | 是（构建目录那一项） | 是（清单第二项） |

**这张表有一条实用推论**：`nuxt cleanup` 一次删掉两个（040 那份清单），**所以清完之后开发要 `nuxt prepare`、要验产物得重新 `nuxt build`**——两边都不是"顺手就能恢复"的。

## 官方给的 `.gitignore` 最小清单

`.gitignore` 那一页给的是一份可直接抄的清单，官方措辞是"**至少**包含以下条目"：

```bash [.gitignore]
# Nuxt dev/build outputs
.output
.data
.nuxt
.nitro
.cache
dist

# Node dependencies
node_modules

# Logs
logs
*.log

# Misc
.DS_Store

# Local env files
.env
.env.*
!.env.example
```

对着分组读，四组各有各的理由：

**一、开发/构建输出六项。** 前两行你已经认识了：`.nuxt`（052）、`.output`（本篇）。**后面四项官方同样没在本页解释含义**——`.data`、`.nitro`、`.cache`、`dist`，我只照清单原样给你，不替它们编定义。

**但这条清单对 040 有个直接价值**：`nuxt cleanup` 清的五项里就有 `dist` 与 `.cache` 这两族名字——**"哪些目录是生成物"这件事，官方在这两处给的是同一批名字**（这个对照是我把两页清单并排看出来的）。

**二、`node_modules`。** 030 讲锁文件时说"一个项目只该有一种锁文件"，而 `node_modules` 本身永远不该进仓库。

**三、日志两项。** `logs` 与 `*.log`。

**四、本地环境变量文件三行——这一组最值得停一下：**

```
.env
.env.*
!.env.example
```

**前两行是忽略所有本地环境文件（`.env` 与任何 `.env.xxx`），第三行那个 `!` 是把 `.env.example` 排除在忽略之外。** 官方这个写法表达的是一个很常见的工程习惯：**环境变量的"清单"要提交（让同事知道要配哪些键），而"值"绝不提交。**

**这条和 018、029 讲的是同一件事的三个面**：runtimeConfig 的默认值写在 `nuxt.config`（可提交）、真实值走环境变量（不可提交）、`.env.example` 是那份可提交的键清单。

## 别把两个目录的作用弄反

新手最容易犯的两种错，正好各对应一个目录：

**错误一：改 `.nuxt` 里的文件想让行为变。** 052 那条 warning 已经封死了这条路——`nuxt dev` 会重建它。

**错误二：改 `.output` 里的文件想让线上变。** 本篇那条 warning 同样封死了——`nuxt build` 会重建它。**而且更要命的是：你改的那份产物根本不会被推上仓库**（它在 `.gitignore` 里），部署时构建出来的还是原始代码的产物。

**两边都指向同一个动作：改源码，或者改配置。** 生成物只是结果。
