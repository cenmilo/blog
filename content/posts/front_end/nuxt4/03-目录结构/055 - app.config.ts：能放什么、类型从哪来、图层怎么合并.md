`nuxt.config` 管构建与运行怎么配，018 讲过。`app.config.ts` 管的是另一件事：运行时可改、浏览器和服务端都能读到的那份配置。

这一页信息不少，值得留意的是三处：一条 caution 的安全限制、一段容易让人误判的类型规则、一个只对数组生效的图层合并机制。

官方的用法：Nuxt 提供一个 `app/app.config.ts` 配置文件，用来在应用里暴露响应式配置——你可以在生命周期内或用 nuxt 插件在运行时更新它，也可以靠 HMR 直接编辑。扩展名可以是 `.ts`、`.js` 或 `.mjs`。

```ts [app/app.config.ts]
export default defineAppConfig({
  foo: 'bar',
})
```

这三个性质各有用途：响应式意味着改了能生效；运行时可更新对应下面的 `updateAppConfig`；HMR 可编辑意味着开发时改它不必重启。

然后是全篇最硬的一条 caution：不要把任何密钥放进 `app.config` 文件，它会暴露进用户的客户端包。

这条要和 018 那两行硬规则放在一起才看得清。`runtimeConfig` 的顶层键只在服务端能读，该放密钥和 token；`runtimeConfig.public` 两侧能读，会进每个页面的 payload，放前端需要的公开配置；`app.config.ts` 也是两侧能读、进客户端包，放主题、UI 开关这类应用配置。判据很清楚：凡是不能让浏览器看到的东西，都不属于这里。

位置也提一句。官方用 note 写了句和 051 直接相关的话：配置了自定义 `srcDir` 时，记得把 `app.config` 文件放在新 srcDir 的根部。`srcDir` 默认值是 `app`，所以文档里写 `app/app.config.ts`；你把它改成别的名字，这个文件就得跟着搬。这条改动很安静，但搬错了的表现是配置整个读不到。

用法上，官方举的例子是主题色。

```ts [app/app.config.ts]
export default defineAppConfig({
  theme: {
    primaryColor: '#ababab',
  },
})
```

官方原话：现在我们可以在服务端渲染页面时与浏览器里都用 `useAppConfig` 组合式函数访问 `theme`。

```vue [app/pages/index.vue]
<script setup lang="ts">
const appConfig = useAppConfig()

console.log(appConfig.theme)
</script>
```

运行时更新用另一个工具。

```vue [app/pages/index.vue]
<script setup>
const appConfig = useAppConfig() // { foo: 'bar' }

const newAppConfig = { foo: 'baz' }

updateAppConfig(newAppConfig)

console.log(appConfig) // { foo: 'baz' }
</script>
```

注意示例注释里的顺序：`appConfig` 这个引用没换，`updateAppConfig` 之后打印它已经是 `{ foo: 'baz' }` 了。这就是开头那句"响应式、运行时更新"的落地写法。009 提到 `updateAppConfig` 属于官方列出的更新手段，就是这一条。

类型那节最让人困惑。Nuxt 会尝试自动从你提供的 app config 生成 TypeScript 接口，所以你不必自己写类型。但完整的推断类型只在应用代码里可用——组件、组合式函数、插件这些。在服务端路由、`shared/` 目录以及 `nuxt.config` 里，`app.config` 文件中定义的键类型是 `unknown`。官方给的理由：在那儿给它们定型，需要在应用上下文之外对你的应用代码做类型检查，而那里没有 app 自动导入。

相比之下，写在 `nuxt.config` 的 `appConfig` 选项里内联定义的键，在所有地方都有类型。想覆盖 `unknown`，就扩展 `SharedAppConfig` 接口——增强文件的位置决定哪些上下文能看到它，放在 `shared/` 目录下的 `.d.ts` 文件，能覆盖应用代码、共享代码与服务端路由。

读成几句话就是：别把服务端路由里 `appConfig.xxx` 是 `unknown` 当 bug，官方的理由就是上下文限制；想让某个键到处有类型，内联写进 `nuxt.config` 的 `appConfig` 选项；想覆盖 `unknown`，扩展 `SharedAppConfig`，`.d.ts` 放进 `shared/`。

还有个容易混的点：`useAppConfig()` 的返回类型在 app 内外不是同一个。官方在 App Config Output 一节写得很清楚——在应用代码里给调用结果定型，扩展的是 `AppConfig`；在应用代码之外（服务端路由、`shared/`、`nuxt.config`），它返回的是 `SharedAppConfig`，要扩展就扩展那个接口。

然后官方给两个扩展目标各一份代码。`AppConfigInput` 面向模块作者，声明设置 app config 时合法的输入选项，不影响 `useAppConfig()` 的类型：

```ts [index.d.ts]
declare module 'nuxt/schema' {
  interface AppConfigInput {
    /** Theme configuration */
    theme?: {
      /** Primary app color */
      primaryColor?: string
    }
  }
}

// It is always important to ensure you import/export something when augmenting a type
export {}
```

`AppConfig` 是给 `useAppConfig()` 的结果定型的：

```ts [index.d.ts]
declare module 'nuxt/schema' {
  interface AppConfig {
    // This will entirely replace the existing inferred `theme` property
    theme: {
      // You might want to type this value to add more specific types than Nuxt can infer,
      // such as string literal types
      primaryColor?: 'red' | 'blue'
    }
  }
}

export {}
```

但这段之前挂着 warning：给 `AppConfig` 写类型时要小心，因为你会覆盖掉 Nuxt 从你实际定义的 app config 推断出来的类型。示例里那行注释说得更直接——这将完全替换已有的被推断出的 `theme` 属性。

两份示例里都有那行 `export {}`，官方给的注释是：增强类型时，务必确保你 import 或 export 了某个东西。少了这一行，模块增强不生效——这是它出现在两份示例里的原因。

图层合并这部分只对数组生效。官方原话：Nuxt 对你应用各图层里的 `AppConfig` 使用一种自定义合并策略，通过一个 Function Merger 实现，它可以为 `app.config` 中每个值属于数组的键定义自定义合并策略。

例子是图层定默认值、再用函数覆盖：

```ts [layer/app/app.config.ts]
export default defineAppConfig({
  // Default array value
  array: ['hello'],
})
```

```ts [app/app.config.ts]
export default defineAppConfig({
  // Overwrite default array value by using a merger function
  array: () => ['bonjour'],
})
```

不过同一页上有条 note 和第二个文件的标法对不上：这个 function merger 只能用在被继承的图层里，不能用在项目的主 `app.config` 中。示例第二个文件写的是 `app/app.config.ts`，看着像项目那一份，note 却说函数只能待在图层里。这两处我合不成一句无矛盾的结论，遇到时以你自己的实际运行为准，016 讲过这类文档与行为不一致该怎么报。用的时候记住两个限定就够了：只有值为数组的键有这个能力，以及那条 note 的存在。

已知限制那节说的是这个文件被 Nitro 共用。自 Nuxt v3.3 起，`app.config.ts` 与 Nitro 共享，带来两个限制：不能在 `app.config.ts` 里直接导入 Vue 组件；一些自动导入在 Nitro 上下文里不可用。原因在于 Nitro 处理 app config 时没有完整的 Vue 组件支持。

官方还提了个不推荐的绕法——在 Nitro 配置里用 Vite 插件——跟着就是 warning：可能导致意外行为与 bug，而且 Vue 插件只是众多在 Nitro 上下文里不可用的插件之一。"众多之一"这四个字值得留意，说明这不是补一个插件就能解决的事。

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitro: {
    vite: {
      plugins: [vue()],
    },
  },
})
```

结尾官方给了预期：Nitro v3 将通过移除对 app config 的支持来解决这些限制。所以这类问题的长期解法不是绕，而是别把需要 Vue 上下文的东西放进 `app.config.ts`——后半句是我的建议，官方给的是 Nitro v3 会移除支持。
