`nuxt.config` 管"构建与运行怎么配"（018）。`app.config.ts` 管另一件事：**运行时可改、并且浏览器和服务端都能读到的那份配置。**

这一页有三块内容值得逐块读：一条安全限制、一段让人困惑的类型规则、一个图层合并机制。

## 官方定义与三个性质

> Nuxt 提供一个 `app/app.config.ts` 配置文件，用来在你的应用里暴露**响应式**配置，并具备**在生命周期内或使用一个 nuxt 插件于运行时更新它**、以及**用 HMR（热模块替换）编辑它**的能力。
>
> 你可以很容易地用 `app.config.ts` 文件提供运行时的应用配置。**它可以是 `.ts`、`.js` 或 `.mjs` 扩展名。**

```ts [app/app.config.ts]
export default defineAppConfig({
  foo: 'bar',
})
```

三个性质对应三个用途：**响应式**（改了能生效）、**运行时可更新**（见下面的 `updateAppConfig`）、**HMR 可编辑**（开发时改它不必重启）。

## 一条 caution：这里不能放密钥

官方用的是 caution 级别，只有一句话：

> **不要把任何密钥放进 `app.config` 文件。它会被暴露进用户的客户端包。**

**这一条要和 018 那两行硬规则放在一起才成立**：

| 配置位置 | 谁能读到 | 该放什么 |
| --- | --- | --- |
| `runtimeConfig` 的顶层键 | **只在服务端** | 密钥、token |
| `runtimeConfig.public` | 两侧（会进每个页面的 payload） | 前端需要的公开配置 |
| `app.config.ts` | 两侧（**进客户端包**） | 主题、UI 开关这类应用配置 |

**判据很清楚：凡是"不能让浏览器看到"的东西，都不属于这里。**

## 位置：`srcDir` 改了要跟着挪

官方用 note 提醒了一句和 051 直接相关的话：

> **当配置了自定义的 `srcDir` 时，请确保把 `app.config` 文件放在那个新 `srcDir` 路径的根部。**

也就是 `srcDir` 的默认值是 `app`，所以文档里写 `app/app.config.ts`；**你把 `srcDir` 改成别的名，这个文件就要跟着搬。** 这条很静，但搬错了表现是"配置整个读不到"。

## 用法：`useAppConfig` 与 `updateAppConfig`

官方给的例子是主题色：

```ts [app/app.config.ts]
export default defineAppConfig({
  theme: {
    primaryColor: '#ababab',
  },
})
```

> 现在我们可以在**服务端渲染页面时**与**浏览器里**都用 [`useAppConfig`](https://nuxt.com/docs/4.x/api/composables/use-app-config) 组合式函数访问 `theme`。

```vue [app/pages/index.vue]
<script setup lang="ts">
const appConfig = useAppConfig()

console.log(appConfig.theme)
</script>
```

运行时更新用另一个工具：

```vue [app/pages/index.vue]
<script setup>
const appConfig = useAppConfig() // { foo: 'bar' }

const newAppConfig = { foo: 'baz' }

updateAppConfig(newAppConfig)

console.log(appConfig) // { foo: 'baz' }
</script>
```

**注意示例注释给出的顺序**：`appConfig` 这个引用没换，但 `updateAppConfig` 之后打印它已经是 `{ foo: 'baz' }`——**这就是官方开头那句"响应式"与"运行时更新"的落地写法**（009 提到 `updateAppConfig` 属于官方列出的更新手段，就是这一条）。

## 类型那一节：app 内外不是同一种类型

这是本页最容易让人误判的部分，我把官方那段拆开：

> Nuxt 会尝试**自动从你提供的 app config 生成一个 TypeScript 接口**，所以你不必自己写类型。
>
> **完整的推断类型只在应用代码里可用**（组件、组合式函数、插件等）。**在服务端路由、`shared/` 目录里的代码以及 `nuxt.config` 里，`app.config` 文件中定义的键其类型是 `unknown`** —— 因为在那儿给它们定型，需要在应用上下文之外对你的应用代码做类型检查，而那里**没有 app 自动导入**。
>
> **在 `nuxt.config` 的 `appConfig` 选项里内联定义的键，在所有地方都有类型。** 如果你需要在应用代码之外让其它键也有类型，可以按下述方式扩展 `SharedAppConfig` 接口。**增强文件的位置决定哪些上下文能看到它：放在 `shared/` 目录下的一个 `.d.ts` 文件，覆盖应用代码、共享代码与服务端路由。**

把这段变成四条可执行结论：

1. **别把"服务端路由里 `appConfig.xxx` 是 `unknown`"当 bug。** 官方给的理由是上下文限制（那里没有 app 自动导入，无法类型检查应用代码）。
2. **想让某个键在所有上下文都有类型**：把它内联写进 `nuxt.config` 的 `appConfig` 选项——官方明说"内联定义的键到处都有类型"。
3. **想覆盖 `unknown`**：扩展 `SharedAppConfig`，并把 `.d.ts` 放进 `shared/`（官方给的覆盖范围：app 代码 + 共享代码 + 服务端路由）。
4. **注意 `useAppConfig()` 的返回类型在 app 内外不同**：官方在"App Config Output"一节写得很清楚——

> 如果你想在**应用代码**里给调用 [`useAppConfig()`](https://nuxt.com/docs/4.x/api/composables/use-app-config) 的结果定型，那你要扩展的是 `AppConfig`。**在应用代码之外（服务端路由、`shared/` 目录与 `nuxt.config`），`useAppConfig()` 返回的是 `SharedAppConfig`，所以请改为扩展那个接口。**

然后官方给两个扩展目标各一份代码，并留下一条 warning。

**`AppConfigInput`（声明合法输入，不影响输出类型）**——官方说它面向模块作者：

```ts [index.d.ts]
declare module 'nuxt/schema' {
  interface AppConfigInput {
    /** Theme configuration */
    theme?: {
      /** Primary app color */
      primaryColor?: string
    }
  }
}

// It is always important to ensure you import/export something when augmenting a type
export {}
```

> `AppConfigInput` 可能被模块作者用来声明设置 app config 时**合法的输入选项**是什么。**这不会影响 `useAppConfig()` 的类型。**

**`AppConfig`（给 `useAppConfig()` 的结果定型）**：

```ts [index.d.ts]
declare module 'nuxt/schema' {
  interface AppConfig {
    // This will entirely replace the existing inferred `theme` property
    theme: {
      // You might want to type this value to add more specific types than Nuxt can infer,
      // such as string literal types
      primaryColor?: 'red' | 'blue'
    }
  }
}

export {}
```

官方在这段之前挂了 warning：

> **给 `AppConfig` 写类型时要小心，因为你会覆盖掉 Nuxt 从你实际定义的 app config 推断出来的类型。**

而示例里那行注释写得更狠："这将**完全替换**已有的被推断出的 `theme` 属性"。

**两段都有那句共同的要求：`export {}`。** 官方给它的注释是"增强类型时，务必确保你 import 或 export 了某个东西"——**少了这一行，模块增强就不生效**（这是它出现在两份示例里的原因）。

## 图层合并：Function Merger 只给数组用

> Nuxt 对你应用**各图层**里的 `AppConfig` 使用一种自定义合并策略。
>
> 这一策略是通过一个 **Function Merger** 实现的，它可以为 `app.config` 中**每一个值属于数组的键**定义自定义合并策略。

官方给的例子是"图层定默认值、用函数覆盖它"：

```ts [layer/app/app.config.ts]
export default defineAppConfig({
  // Default array value
  array: ['hello'],
})
```

```ts [app/app.config.ts]
export default defineAppConfig({
  // Overwrite default array value by using a merger function
  array: () => ['bonjour'],
})
```

**但同一页上还有一条 note，与上面第二个文件的标法读起来对不上：**

> 这个 function merger **只能用在被继承的图层里，而不能用在项目的主 `app.config` 中。**

**我没有办法把这两处并成一句无矛盾的结论**——示例的第二个文件写的是 `app/app.config.ts`（看起来是项目那一份），而 note 说函数只能待在图层里。**遇到这一项时请以你自己的实际运行为准**（016 讲过这类"文档与行为不一致"该怎么报障）。

要用的时候记住官方给的两个限定：**只有值为数组的键有这个能力**，以及那条 note 的存在。

## 已知限制：这个文件被 Nitro 共用

官方用一个小节写了这件事，起点是一个版本说明：

> **自 Nuxt v3.3 起，`app.config.ts` 文件与 Nitro 共享**，这带来以下限制：
>
> 1. **你不能在 `app.config.ts` 里直接导入 Vue 组件。**
> 2. **一些自动导入在 Nitro 上下文里不可用。**
>
> 这些限制之所以存在，是因为 **Nitro 处理 app config 时没有完整的 Vue 组件支持**。

官方还提了一个它**不推荐**的绕法：

> 虽然可以在 Nitro 配置里使用 Vite 插件作为绕法，但**这种做法不被推荐**：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitro: {
    vite: {
      plugins: [vue()],
    },
  },
})
```

> （warning）**使用这个绕法可能导致意外行为与 bug。Vue 插件只是众多在 Nitro 上下文里不可用的插件之一。**

这一句"只是众多之一"很重要：**它说明这不是补一个插件就解决的事。**

结尾官方给了预期：

> Nitro v3 将通过**移除对 app config 的支持**来解决这些限制。

**所以这类问题的长期解法不是绕，而是别把需要 Vue 上下文的东西放进 `app.config.ts`。**（后半句是我的建议；官方给的是 Nitro v3 会移除支持。）
