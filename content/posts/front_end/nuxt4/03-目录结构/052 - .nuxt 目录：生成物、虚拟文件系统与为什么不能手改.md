050 那张地图上没有一个位置是 `.nuxt`——**因为它不是你的代码，是框架的产物。** 但你在报错里见到它的次数，可能比任何目录都多。这一篇就讲这一个人目录：**它什么时候被生成、里面值得认识的东西有哪几样、以及为什么官方用 warning 级别写着别碰它。**

## 官方给的定位：只有一句话

> Nuxt **在开发时**使用 `.nuxt/` 目录来生成你的 Vue 应用。

紧接着是这一页唯一的 important 块：

> **这个目录应当被加入你的 [`.gitignore`](https://nuxt.com/docs/4.x/directory-structure/gitignore) 文件，以避免把开发构建产物推送到你的仓库。**

**"在开发时"这三个字要连着读**：053 会看到生产产物住在 `.output`，两个目录的分工就是"开发期生成物"与"发布期产物"。

## 它什么时候被生成

035 抄过官方那句判据，这里作为本篇的时间线：

> Nuxt 项目依赖自动生成的类型才能正常工作。这些类型**存放在 `.nuxt` 目录里，在你运行开发服务器或构建应用时生成**。你也可以通过运行 `nuxt prepare` 手动生成这些文件。

三条路径：

| 你跑什么 | `.nuxt` 会怎样 |
| --- | --- |
| `nuxt dev` | 生成，而且**整个目录会被重新创建**（下面第 4 节） |
| `nuxt build` | 生成 |
| `nuxt prepare` | 专门用来只生成它（035：CI 或 `postinstall` 场景） |

**脚手架 `package.json` 里那句 `postinstall: "nuxt prepare"` 就是把这三条的第一条与第三条接上了**（024）：装完依赖，`.nuxt` 就有了一份。

## 里面值得认识的三类东西

`.nuxt` 里的文件多到不必逐一看，但有三类你迟早要主动去找它们。

**一、四份 tsconfig。**

031 抄过这份清单，它们是本篇的主角：

- `.nuxt/tsconfig.app.json`
- `.nuxt/tsconfig.node.json`
- `.nuxt/tsconfig.server.json`
- `.nuxt/tsconfig.shared.json`

036 那四查里的第二查（"`.nuxt` 里有没有这四份"）就落在这里。**编辑器没类型、`typecheck` 结果诡异，第一件事是确认这个目录存在。**

**二、别名指向的位置。**

051 那张默认别名表里，有两条直接指进 `.nuxt`：

```json
{
  "#build": "/<rootDir>/.nuxt",
  "#internal/nuxt/paths": "/<rootDir>/.nuxt/paths.mjs"
}
```

**这是"生成物可以被子路径解析到"的官方入口**——`#build` 是一个能写进 import 的别名，而不只是一个你能在文件管理器里看到的文件夹。031 从 TypeScript 那一页也见过同一件事的另一种说法：生成的 tsconfig 里包含"像 `#imports`、`~/file`、`#build/file` 这样的路径别名"。

**三、`nuxt.lock`。**

033、034、041 反复出现的那个文件，就住在这里（官方措辞：**dev 服务器把自身记录进"[构建目录](https://nuxt.com/docs/4.x/directory-structure/nuxt)里的 `nuxt.lock`"**）。

它的作用链条你已经会用三条了：

| 谁 | 拿它做什么 |
| --- | --- |
| 第二个 `nuxt dev` | 报告"已有一个在运行"，而不是抢端口（033） |
| `nuxt curl` | 找到要请求的 dev 服务器（041） |
| `nuxt task` | 找到要通信的 dev 服务器（041） |

**040 讲 `nuxt cleanup` 时会看到这条链的副作用**：cleanup 删掉构建目录，`.nuxt` 没了，锁也就没了——"明明有进程还在、命令却说没有"就是这么来的。

## 那句 warning：为什么不能手改

官方的措辞非常干脆：

> **你不应当触碰里面的任何文件，因为运行 `nuxt dev` 时整个目录会被重新创建。**

这条 warning 的实际含义，比"别乱改"三个字强得多：

1. **改了等于没改。** 你的修改会在下一次 `nuxt dev` 时被整体重建覆盖掉。
2. **改坏了还会连累别人。** 031 抄过另一页的同一立场（针对根目录那份 `tsconfig.json`）："不建议直接修改，**因为这样做可能覆盖 Nuxt 或其它模块依赖的重要设置**"。
3. **正确入口在配置里。** 想扩展类型配置，走 `typescript.tsConfig` 与那四个按上下文的选项（036 逐条讲过它们的例外规则）；想改生成目录本身，走 `buildDir`（051）。

**一句话记住：`.nuxt` 是输出，不是输入。**

## 那一句 VFS：你在磁盘上看到的不是全部

这是本篇我认为最该被注意到、却最容易被略过的一句：

> **Nuxt 还为模块提供了一个虚拟文件系统（VFS），让模块可以把模板添加到这个目录里而不必写到磁盘上。**

**它推翻了"我在 `.nuxt` 里找不到那个文件，所以它不存在"这个直觉。** 按这句定义，模块注入的东西**可能只在 VFS 里**——磁盘上看不见，但框架能读到。

于是官方紧接着给了唯一可行的查看方式：

> **你可以通过在开发模式打开 [Nuxt DevTools](https://devtools.nuxt.com) 并切到 Virtual Files 标签页，来浏览这些生成的文件。**

**这就是"想确认某个模块到底给我生成了什么"的官方工具路径。** 047 已经出现过 DevTools 的另一个标签（Payload tab，用来看取数转发到客户端的数据），本篇这个是 **Virtual Files**——**两个标签对应两类完全不同的问题：一份是运行时的数据，一份是构建期的生成物。**

（VFS 的模块侧写法在 067、P23 那几篇；本篇只到"它有这个机制、用 DevTools 看得到"为止。）

## 改名之后：`buildDir` 会让上面全部失效

051 抄过官方那句很实用的说明：

> 许多工具假定 `.nuxt` 是一个隐藏目录（因为它以 `.` 开头）。如果那会造成问题，**你可以用这个选项来避免它。**

```ts
export default defineNuxtConfig({
  buildDir: 'nuxt-build',
})
```

**改了这一行，本篇前面所有写着 `.nuxt` 的地方都要跟着换算**：`.gitignore` 里的条目（官方这条 important 的本意是"把构建目录加进去"，不是特指那个名字）、040 那张清单里"构建目录"那一项（它按 `buildDir` 的实际值走）、以及 `#build` 别名指向的位置。
