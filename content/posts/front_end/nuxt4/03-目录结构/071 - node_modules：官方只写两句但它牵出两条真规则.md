这一节是全套目录文档里最短的一节，两句话。但 `node_modules/` 牵出的两条规则，一条能解释自动导入为什么时灵时不灵，一条能在 monorepo 里救你。

官方给的全部两句。包管理器，`npm` 或 `yarn` 或 `pnpm` 或 `bun` 或 `deno`，创建这个目录来存放你项目的依赖。这个目录应当加入你的 `.gitignore` 文件，以避免把依赖推送进你的仓库。

这一节自己不讲任何 Nuxt 行为，它只是把这个目录不属于你这件事写清楚。

053 抄过的那份官方 `.gitignore` 推荐清单里，它是单独一组。

```bash [.gitignore]
# Node dependencies
node_modules
```

同页另一组 Nuxt dev/build outputs 里有 `.output`、`.data`、`.nuxt`、`.nitro`、`.cache`、`dist`，052、053 各讲了前两个。两组理由不同，一组是产物可重建，一组是依赖可重装。

第一条真规则，`modulesDir` 与 monorepo。这条配置项的原文值得完整读，用于设置做路径解析时使用的 modules 目录，例如 webpack 的 `resolveLoading`、`nodeExternals` 与 `postcss`。配置路径相对于 `options.rootDir`，默认是当前的工作目录。如果你的项目组织成 yarn workspace 风格的 monorepo，设置这个字段可能是必要的。

官方给的默认值是 `["/<rootDir>/node_modules"]`。

三句各对应一个可操作的事实。

一，它的用途是路径解析，不是多扫一处模块来源。官方举的三个例子，webpack 的 `resolveLoading`、`nodeExternals`、`postcss`，全都在构建器与工具链那一层，088 会讲 `builder` 可切换，这条就是切换后依赖去哪儿找的坐标。

二，基准是 `rootDir`，且默认是当前工作目录。这与 051 讲的 `srcDir` 与 `serverDir` 同基准，080 那节会再确认一次 `rootDir` 可被 `nuxt ./my-app/` 覆盖，048 也提过。

三，monorepo 场景官方直接点名，可能需要设置它。也就是说，在 workspace 结构里出现依赖明明装了却解析不到时，这是官方指的那个配置项。症状与配置项的对应关系是按官方可能是必要的这句给的判断方向。

类型是 `array`，它可以给多个目录，不是单值。

第二条真规则，自动导入不为 `node_modules` 启用。这一条不在 `node_modules` 页，而在模块结构那一节，它解释了自动导入为什么有时不生效这个高频困惑。

已发布的模块不能为自己的 runtime 目录里的资源利用自动导入。相反，它们必须从 `#imports` 或类似位置显式导入。自动导入不会为 `node_modules` 里的文件启用，那正是已发布模块最终所在的位置，这是出于性能考虑。

读出三层含义。

一，这是一条性能取舍，不是 bug。官方写的理由是 for performance reasons，扫描依赖树做自动导入的代价太高。

二，它划出了 063、066 那两节的边界。你在 `app/composables/`、`shared/utils/` 里享受的自动导入，同一个文件在页面里不用写 import，到了 `node_modules` 里就没有。

三，它对本地模块与发布模块给出两种写法。项目里的 `modules/`，067 讲过，能用自动导入，官方在 067 那个示例里直接用 `addServerHandler`、`createResolver`，runtime 里的文件按 `runtime/app/` 组织以便类型正确。发布成 npm 包，住进 `node_modules`，不能，必须显式 `import ... from '#imports'`。

这正好解释了一类在我本地项目里好好的、发成包就报找不到名字的现象，同一个 runtime 文件从 `modules/` 搬到 npm 包里，自动导入这项能力就没了，得改成显式导入。017 讲约定的代价时提的就是这一族问题。

`#imports` 这个别名是这里的解法入口，051 那张表里 `#shared`、`#server`、`#build` 同族，官方在类型那节也说过生成的 tsconfig 里包含 `#imports` 这类别名。

这个目录里的 Nuxt 缓存，被 040 一条命令收走。`node_modules/` 不只有依赖，框架的本地缓存在它下面。

`node_modules/.vite` 是 Vite 的缓存，040 的清单。`node_modules/.cache` 是各类工具缓存，040 的清单。`node_modules/.cache/nuxt/preview` 是 preview 记录本项目已有一个在跑的地方，029、039 讲过。

这张表把 040 那条提醒闭环了，`nuxt cleanup` 删的是构建目录加 `.output` 加 `dist` 加这两处缓存。所以清完之后，依赖解析与 Vite 预构建要重来，首次启动变慢，属正常，preview 的接管判断失去记录，039 说的那个明明有进程还在、命令却说没有。

而依赖本身不会被 `nuxt cleanup` 删除，它的清单里没有 `node_modules` 这一项。要重装依赖得走包管理器，030 那张锁文件表、044 的 `--force` 才是干这件事的。
