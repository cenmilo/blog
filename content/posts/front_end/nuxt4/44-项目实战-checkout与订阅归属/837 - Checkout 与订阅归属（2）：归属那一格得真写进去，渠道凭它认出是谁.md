## 两端各读各的，中间那一格一直没人写

上一站读到的送出去的正文，末尾长这样（少了一格）：

```text
mode=subscription&success_url=…&cancel_url=…
&line_items%5B0%5D%5Bprice%5D=price_REPLACE_ME&line_items%5B0%5D%5Bquantity%5D=1
```

而入账那一路读的是哪儿？`server/services/billing/payload.ts:131` 那一行写着 `用户id: 取串(元数据?.userId)`——它读的是事件载荷里 `data.object.metadata.userId`。

**一位是写、一位是读，中间那一格从来没被写过。** 渠道对这个编号没有任何理解，`metadata` 就是它替我们保管的一小份附件：你塞什么它存什么，送回来时原样还你。之所以要塞，是因为事件里只有渠道自己的编号（`cus_…`、`sub_…`），本站的用户 id 不在里面——不塞，回来就没人知道这是谁的订阅。

## 写进去的形状

`组会话单` 多收一位参数，返回的单子里那一格不再是空的：

```ts
metadata: { userId: 输入.用户Id, priceId: 价格 },
```

摊成表单之后是这两位（键名的方括号会被编码成 `%5B` 与 `%5D`，这是渠道那种表单写法要求的）：

```text
metadata%5BuserId%5D=0fba18db-3668-4289-9c58-ef4e81c6a192
metadata%5BpriceId%5D=price_REPLACE_ME
```

值从哪儿来只有一条路：接口里 `requireUser` 的返回值。

```ts
const 用户 = requireUser(event)
const 单 = 组会话单({ 计划Id: 解析.planId, 用户Id: 用户.id, 站点地址: … })
```

上一站这一行是裸调 `requireUser(event)`——只管让不让你进，返回值没人要。这一站它得往下传。**请求体里那位同名的 `userId` 一律不读**：读了就等于把"给谁下单"交给调用方，会员区那条老规矩（先确认是谁在问，再动手）在这里是同一条。

判据里专门有一档试这个：请求体里塞一个别人的编号（一个固定的假 uuid），断交出去的仍是会话主人，且请求里那位连影子都不在单子里。

```text
[结账·归属来源] {"会话主人":"7b352646-2c80-4b8c-9fb6-631b275c6081",
"交出去那位":"7b352646-2c80-4b8c-9fb6-631b275c6081","请求里塞的那位还在不在":false}
```

## 闭环那一档：交出去的那一位，正是回来时读的那一位

单看这一站，判据只能说到"我们递了一个 uuid 出去"；单看上一线，入账只能说到"载荷里有 `metadata.userId` 就认得出人"。**这两句是不是同一件事，两边各自都判不了**。所以有一档把三步接起来跑，全在本机：

1. 下一单，从本机假 provider 记下的正文里**读回**本站真写出去的那一位；
2. 用那一个值造一份 `checkout.session.completed` 的载荷（`data.object.metadata.userId`），拿本地密钥签好，发进入账那一路；
3. 读 `subscriptions` 那一行的 `user_id`。

```text
[结账·闭环] {"交出去那位":"9cdd3353-c8af-4ab4-9779-590afb7477c0","回调状态":200,
"库里归属":"9cdd3353-c8af-4ab4-9779-590afb7477c0","状态":"active","事件行":{"处理过":true}}
```

三个读数同时成立才算闭上：交出去的那一位等于库里那一行的归属；订阅行建成了 `active`（渠道送回来的会话对象不带订阅状态，状态由事件类型决定）；事件表那一行盖了处理完的标记。

**假 provider 在这一档里仍然只证明"本站自己写的东西自己读得回来"**。真实渠道会不会把这一格原样带回来、`metadata` 在会话对象里的层级是不是这样，缺一次真投递——这条账从上一线就挂着，这一站没把它清掉。

## 翻一条判据，翻出两个缺陷

上一站那条判据是 `expect(读数.有归属).toBe(false)`，注释写着"下一站会把它翻成 `true` 并断出那个 uuid"。翻的时候先红了一次，两次都不是实现的问题：

**第一个缺陷在判据自己身上。** `有归属` 是这么算的：`正文.includes('metadata[')`。可正文是 URL 编码过的，实际长成 `metadata%5BuserId%5D=`——**那个未编码的串永远找不到**。上一站读到 `false` 是两件事叠在一起：确实没写，而且判据本来就找错了字符串。改成找 `metadata%5B` 之后，这一位第一次给出可信的读数。

一条判据的"红"与"绿"要能解释为什么会是这个值。解释不了的那一位，等于没判。

**第二个缺陷在实现里，是变异撞出来的。** 把写进去的格名从 `userId` 换成 `user`（另一种"写错格名"的真实形状），入账那一读就是空，接口回 200 而订阅行不建——这符合预期。但同一趟里，判据读不到那一位、退化成把字符串 `(读不到)` 当成用户编号塞进载荷，于是撞出一条没准备的错误：

```text
[WebServer] [request error] [unhandled] [POST] http://localhost:…/api/billing/webhook
 H3Error: Failed query: insert into "subscriptions" ("id", "user_id", …) values (…)
 params: sub_c837_1792448401,(读不到),cus_c837_1792448401,active,price_REPLACE_ME,,false,…
```

**入账那一路只挡了"这一位没有"，没挡"这一位本站不认识"。** `user_id` 那一列是外键，指着一个不存在的用户就是这条未处理错误：渠道送回来一个本站查不到的编号（删过的账号、别的账号体系、别人测试环境的事件），这个回调就 500。它会一直重试，而那条事件永远处理不完。这一条进未闭合清单，修法是入账前先认一次用户、认不到就留痕不建行——不属于这一站的活，但这一站把它读出来了。

两处变异的红各是几档也记一下：格名写错红三档端到端（`⑦⑧⑨`）加两档单测；归属改从请求体取只红一档端到端（⑨）加一档静态判据。**红几档不是运气，是判据定位准不准的读数。**

## 同一批判据在三趟里的样子

| 这一趟 | 跑了几档 | skip 几档 | skip 的是什么 |
| --- | --- | --- | --- |
| 不带库也不配密钥 | 2 | 7 | 要真会话与要 provider 的全部 |
| 带库、不配下单密钥 | 5 | 4 | ⑥⑦⑧⑨（都要假 provider 收正文） |
| 带库、两个密钥齐、渠道指向本机 | 8 | 1 | 只有"本站没配密钥"那一档 |

第三趟里"本站没配密钥"那一档反过来必须 skip——它要的就是密钥留空。skip 不是测过：这个文件里的九个档位，不带库那一趟只跑了两条，闭环那三步一条都没走。

全站这一趟是 **257 passed／98 skipped**，跳过分档 要库 46／要外部服务变量 28／内容目录读得到 14／要另一趟构建的开关 10，没有一条归不进类。

## 撞上的三件事

| 症状 | 为什么 | 怎么办 |
| --- | --- | --- |
| 正文里明明有归属，读数却说没有 | 判据找的是未编码的 `metadata[`，表单里是 `metadata%5B` | 找编码后的形状；顺带把这一档翻成"断出具体那一位"而不只看有没有 |
| 同一趟里第二档读到上一档那一发 | 假 provider 收到的是一串数组，`find` 取第一条命中的 | 按本次探针那一位筛，并从末尾往前找；探针 id 本来就各发不同 |
| 入账那一路 500，栈里是一条 insert 语句 | 载荷里的用户编号本站查不到，外键拒了 | 入账前先认用户；认不到就留痕不建行（这条进未闭合） |

## 下一站

下一站谈落地地址：`success_url` 与 `cancel_url` 都由本站拼，请求里没有任何一处能把它们换成外站地址——这一格的边界要单独打红一次，顺便把"为什么渠道回调那边豁免那道双提交校验、这边不豁免"两条路放一起讲清。
