## 先在地址上确认它不存在

上一线收尾时留了一句话：`metadata.userId` 是本站创建订阅时写进渠道对象的，渠道本身不知道你是谁。可现在没有一处代码往里写过——因为本站还没有"发起一次订阅"这件事。

先看屏幕上有什么。这一路的地址还不存在，三种方法读回来是同一个答案：

```text
[结账·引入前] [{"方法":"get","状态":404,"正文字节":262,"allow头":"(没有这一位)"},
{"方法":"put","状态":404,"正文字节":262,"allow头":"(没有这一位)"},
{"方法":"post","状态":404,"正文字节":262,"allow头":"(没有这一位)"}]
```

正文 262 字节是那份通用错误页（上一线量到的是 258，差在地址长度上，所以这条判据不钉字节数，只钉状态码与"没有 `allow` 头"）。

## 这一站的顺序与上一线相反

上一线那道门是签名：调用方是渠道服务器，它没有本站 cookie，也永远填不出 `x-csrf-token`，所以那一站把"本站没准备好"放在最前面，密钥留空连请求头都不看。

这一路的调用方是**本站登录用户**。于是顺序换成另一头：

```text
门（是谁在问）→ CSRF（这请求是不是页面自己发的）→ 形状（内容对不对）
→ 可售（这计划卖不卖）→ 有没有配置（本站准没准备好）→ 才交出去
```

两条规矩都合理，因为问的不是同一件事：渠道回调那句"你签名不对"没有意义（它按规矩签，不通过就是有人在试）；而用户的请求里，"你是谁"永远比"本站配没配好"更该先答。

这个先后不是审美。它由一句话钉着：**没配密钥那一趟，形状错的请求读到的是 400 而不是 503**。把配置检查往前挪一格，这一档就红。

## 六道判断各读一次

带库那一趟（真会话由判据自己建、自己删），不配密钥：

```text
[结账·方法门] {"未注册":[{"方法":"get","状态":404,"allow头":"(没有这一位)"},
{"方法":"put","状态":404,"allow头":"(没有这一位)"}],
"POST":{"状态":401,"码":"UNAUTHENTICATED","请求号":true}}
[结账·CSRF] {"只有会话":{"状态":403,"码":"CSRF_MISMATCH","请求号":true},
"只有头":{"状态":403,"码":"CSRF_MISMATCH","请求号":true},
"两位不等":{"状态":403,"码":"CSRF_MISMATCH","请求号":true},"三种同码":true}
[结账·校验] {"密钥在这一趟":"(没配)","数字":{"状态":400,"码":"CHECKOUT_PLAN_INVALID"},
"缺这一位":{"状态":400,"码":"CHECKOUT_PLAN_INVALID"},
"免费":{"状态":400,"码":"CHECKOUT_PLAN_NOT_SELLABLE"},
"不认识":{"状态":400,"码":"CHECKOUT_PLAN_NOT_SELLABLE"}}
[结账·没配置] {"状态":503,"码":"CHECKOUT_NOT_CONFIGURED","请求号":true}
```

四件事在这批读数里各自站得住：

- **文件名后缀就是方法门**。`checkout.post.ts` 只接 POST，GET／PUT 仍是 404，POST 已经不是 404——这一档上一线也改过一次，同样是登记新事实而不是把红灯抹掉。
- **401 与 503 是两个世界**。匿名请求读到的是"你还没登录"，不是"本站没准备好"。上一线那句"没配置与签名不对要分开"在这里有个镜像。
- **三种缺 CSRF 的写法同码**。只交会话、只交头、两边不等，全都回 403 `CSRF_MISMATCH`。告诉对方差在哪一位，等于替他省一次尝试。
- **两个 400 分得开**。形状不对（`planId` 是数字、或者压根没这一位）是一个码；形状对但这个计划不卖（`free`、或表里没登记）是另一个码。前者是按钮发错了请求，后者是本站的价格表与页面对不上——排查方向完全不同。

配上密钥、并把渠道根地址指到本机自己起的假 provider，就能读到放行那一档：

```text
[结账·放行] {"状态":200,"体":{"url":"http://127.0.0.1:3411/c/cs_local_836"}}
[结账·送出去] {"路径":"/v1/checkout/sessions","有归属":false,
"正文":"mode=subscription&success_url=http%3A%2F%2Flocalhost%3A3000%2Fconsole
&cancel_url=http%3A%2F%2Flocalhost%3A3000%2F&line_items%5B0%5D%5Bprice%5D=price_REPLACE_ME
&line_items%5B0%5D%5Bquantity%5D=1"}
```

**这个 200 不代表接过渠道。** 那个地址是本机假 provider 回的，那串 `price_REPLACE_ME` 是占位符——本站没有渠道账号。假 provider 唯一能证明的是"本站确实交出去了一份什么东西、形状长这样"；真渠道认不认这份东西，缺一次真投递。

## 交出去的那份东西，为什么不是 JSON

渠道那一侧要的是表单编码，嵌套位靠 `line_items[0][price]` 这种键名表达。直接 `JSON.stringify` 发过去，参数会被当成一个字符串字段，读回来永远是"缺少 mode"。

`success_url` 与 `cancel_url` 都由本站拼：付完款回会员区那一栏，取消回首页。请求里没有任何一处能把它们换成别的地址——这一格的边界下一站专门钉。

`metadata` 这一位现在是空的 `{}`，判据也照着钉（`有归属:false`）。这不是遗漏，是这一站的靶子：**下一站往这一格写本站用户 id，那条判据要从 `false` 翻成 `true`**，并断出那个 uuid。

## 一次当场改掉的实现错

默认那份送信一开始写的是 `fetch(地址, …)`，然后读 `响应.status()`。端到端一跑，两条档 500，服务端 stderr 里是：

```text
TypeError: 响应.status is not a function
    at 默认送信 (.output/server/chunks/routes/api/billing/checkout.post.mjs:82:39)
```

**产物里的全局 `fetch` 不是原生那一个。** 框架把它换成了自家那套取数工具：默认直接返回解析后的响应体（所以上面那个 `响应` 其实是 `{url: …}` 这个对象），而且非 2xx 会抛。这两条正好打掉本函数要读的东西——状态码，以及"渠道回了 400 也要原样带回来"。

改法是走 `node:http`／`node:https`，不用全局 `fetch`；`发会话单` 再补一种失败原因 `渠道连不上`（DNS、拒绝、超时都归它），三种渠道侧的坏都不抛、只回原因。判据里加了一条静态档盯着这件事：服务层不许出现裸 `fetch(`，必须引那两个 node 模块。

顺带一处契约表的补洞：`apiError` 那张状态短语表里没有 502，会兜成 `'Error'`，于是自回出口与 throw 出口在同一个状态码上发出两种短语——补了 `502: 'Bad Gateway'`。

## 三条判据被证伪的经过

变异一，**把配置检查挪到形状校验前面**（写法是在前面再加一处）：

```text
[结账·顺序] {"门":228,"CSRF":249,"形状":502,"可售":725,"配置":332,"送出":1186,"配置检查处数":2}
[结账·校验] {"数字":{"状态":503,"码":"CHECKOUT_NOT_CONFIGURED"},…}
1 failed / 4 passed / 2 skipped
```

端到端那档红在预期 `400` 与实际 `503` 上——这正是这条判据要防的：坏请求拿到的码把"本站没配密钥"这件事说了出去，运维也分不清该去配 env 还是该去改按钮。

但**静态那条顺序判据整条没红**。原因值得记：它读的是 `if (!密钥)` 第一次出现的位置，而这次变异是"再加一处"，原来那一处还在原位，位置读出来还是正确的顺序。⇒ 补了一条判据：配置检查**只能有一处**。只有一处，位置才等于顺序。这条补上之后，同一份变异立刻红在 `expected 2 to be 1`。

变异二，**去掉 CSRF 那一句**：三种缺法的输入全部读到 503 `CHECKOUT_NOT_CONFIGURED`，而另外三档（门、方法门、形状）照旧绿。红一处而不是全红，说明这几道判断各归各的判据管。

## 不带库那一趟读到什么

同样七个档位，不带库也不配密钥：

```text
5 skipped
2 passed (32.0s)
```

不靠会话也能读的两位是方法门与匿名那一档。剩下五档是 skip——**skip 不等于测过**：那一趟里 403、400、503、200 全都没发生。全站端到端这一趟是 257 passed／96 skipped，分档 要库 46／要外部服务变量 26／要内容目录 14／要另一趟构建的开关 10，没有一条归不进类。这一线新加的五条里，③④⑤ 落在"要库"，⑥⑦ 落在"要外部服务变量"（它们两个条件都要，脚本按第一条命中归类——读表时要说明这一点）。

## 撞上的三件事

| 症状 | 为什么 | 怎么办 |
| --- | --- | --- |
| 放行那两档 500，日志里 `TypeError: 响应.status is not a function` | 产物里的全局 `fetch` 是框架换过的，返回解析后的正文 | 默认送信走 `node:http`／`node:https`；把这件事钉成一条静态判据 |
| `Invalid character in header content ["x-csrf-token"]` | 判据给的头值里写了中文 | 进请求头的字符串一律 ASCII；换成本机才用的英文名再跑 |
| 静态顺序判据在变异下不红 | 变异是"再加一处检查"，原来那一处没挪走 | 判位置之前先判"这一处只出现一次"，否则位置不代表顺序 |

## 下一站

这一站只把入口立起来。下一站还那句欠了四站的账：把本站用户 id 写进 `metadata.userId`，让事件回来认得出是谁——`payload.ts` 现在读的就是这一格。再往后是落地地址的边界、同一条订阅在两处都拿到 id 时谁建行，以及会员区那一栏真读订阅表。
