## 库里有那一列，屏幕上没有那件事

`users` 表里有一列 `banned_at`（`db/tables/users.ts:19`）。后台那一页（`app/pages/admin/index.vue`）有两栏，读的都是任务的运行痕迹与停在发送中的名单。也就是说：这一列既没人往里写，也没人往外读，屏幕上更没有任何一个地方能让人"被禁"。

这一站不写功能。它做两件后面每站都要靠住的事：把"有没有人动它"量成读数，以及把"真要动它，动哪一层"这个决定定下来并钉住。第二个才是难的那个——因为它有三种都能跑起来的写法，而它们的症状完全不同。

## 判"做没做"分三层，别只看表结构

一列在库结构里存在，容易让人以为功能做了一半。真正要问的是三件事：那一列在不在、有没有代码写它、有没有代码读它。上一线收官时已经用这三层量过一次，本站把同一把尺子往"门"那一路再插一层——门每收到一个带会话号的请求，到底从库里读哪几列。

这件事只有读那条 SQL 才作数。门那一路只有四行：

```ts [server/services/auth/session.ts]
const rows = await useDb()
  .select({ id: users.id, email: users.email, role: users.role })
  .from(sessions)
  .innerJoin(users, eq(sessions.userId, users.id))
  .where(and(eq(sessions.id, sid), gt(sessions.expiresAt, new Date())))
```

新写的判据把假库接上真函数跑了一次，读回来是这样：

```json
{ "读回来的键": ["email", "id", "role"], "语句里有没有那一列": false, "查了几次": 1, "自证计数": 1 }
```

三份现状数一起说明一件事：这个人是谁、他有什么角色、他的会话有没有过期——门知道这三样；他被没被封，门不知道。（`查了几次` 与 `自证计数` 那两位是防"顺手加一次查询"的，第 ⑦ 档专管这件事。）

## 同一个需求，三种能跑的写法，三种症状

决定写在这里，后面五站照着走：**那一列由 `loadSessionUser` 读出来，由 `requireUser` 判，页面那一层只负责弹。**

为什么不是别的写法——三种被否掉的方案，各自的症状是这样的：

**方案 A：门直接把被封禁的人读成"没有这个人"（返回 `null`）。** 代码最短，症状最坏。`null` 在本站只有一个含义：会话不存在或已过期，于是接口回 401、页面层的门把他弹回登录页。而他手里那枚 cookie 是有效的——登录页再发链接、再进来、再被弹。验收那句要的是 403（"你是谁"已经确认，缺的是许可），这种写法把两件事折成了一件。

**方案 B：把封禁写成 `role = 'free'`。** 那是降级唯一的写入路径（上一线的任务在动它），"会员期结束"和"被人踢下线"会共用同一列：解禁时无从恢复原来的角色，审计里两条动作看起来还是同一件事。

**方案 C：封禁＝调用那条"把他的会话全删掉"的地址。** 那叫全端下线，不是封禁：他重新点一次登录链接就又能进来。它今天确实存在、也确实有用，只是回答的是另一个问题。

还有一个必须写下来的边界：**页面那一层给不出状态码**。路由中间件跑在 Vue 那一侧，官方那节直接给出返回值的语义——`return navigateTo('/')`，服务端那一路把重定向码设成 302。所以 `app/middleware/admin-auth.ts` 与 `console-auth.ts` 里 `403` 出现的次数必须是 0；谁把"403"搬进页面层，谁就在替接口层承诺它没做的事。这一条也被写成了判据（④）。

## 八档怎么分：六条看代码形状，两条真跑到门口

新文件 `test/unit/admin-surface-baseline.test.ts` 一共八档。分两类看：

- 看代码形状的六条：类型里的键清单、两道门各自写出的状态码、页面层两份中间件里 `403` 与 `navigateTo` 的计数、全站改 `users` 的地址清单、那条"下线"地址不许顺手写 `users`。
- **真跑到门口的两条**：① 假库接上 `loadSessionUser` 调一次，看那条 SQL 里到底有没有那一列；⑥ 把①读回来的那个人挂上 `event.context.user`，真调 `requireUser`。

⑥ 是这一站最贵的一条。它的输入不是手敲的一个 `banned: true` 对象——那个键在类型里根本不存在，敲出来就编译不过。它的输入是从那条真实查询路径里走出来的那个人：那条语句只问三列，所以无论库里那一列写着什么，能走到门口的形状里都没有它。把这样一个人挂上 `event.context` 交给 `requireUser`，读数是这样：

```json
{ "是不是null": false, "有没有抛": false, "键": ["id", "email", "role"] }
```

`有没有抛: false` 就是"他进了门"。这一档断言的消息写着"今天他进了门——这条变红说明 868 做完了"。它和 ① 是同一件事的两半：① 证明语句没问那一列，⑥ 证明因此没人拦他。

与上一线同一条纪律：**形状档顶不掉行为档**——看代码只知道"没人写这一列"，"这样的人今天进得来"只有把门跑一遍才知道。

## 判据的第一版红在我自己的传话上

第三档（两道门的状态码）第一版写成"管理员门里应该有 `[401, 403]`"。跑下去红了：那个文件里只有 `403`。

那句话是从 `require-admin.ts` 的头注释里读来的——注释写"没登录走 `requireUser` 那一句"，讲的是委托，不是这个文件里真有一个 401。那一位 401 由 `requireUser` 抛，在另一个文件里。于是这一档改成钉两件事：这个文件自己写出哪些码（`[403]`），以及它有没有委托拿人（`true`）。

**注释里那句"这段逻辑做了 X"也是一条待验断言**——这条纪律本站是第十八次撞上，每次都是自己写的注释绊自己。

## 五个变异，各撞红一处

零实现的站也要能证伪，否则判据就是第二份注释。五个变异各改一处、验完即回：

- 把那一列加进门的那条 `select` → ① 红（读回来的键多一位、SQL 里出现了那列名）与 ⑦ 红（列数 3 变 4）。
- 往共用类型里加一位封禁 → ② 红。这里有个细节值得单独讲：探针变量名第一次写的是中文，那个扫键的式子 `^\s{2}(\w+)\??\s*:` 里的 `\w` **不认汉字**，于是加了一列而读数仍是那三键——绿灯照旧，判据什么也没看见。把两种写法各演一遍这个匹配就看得清楚：中文键名读回 `["id","email","role"]`，ASCII 的 `bannedProbe` 读回四个并把封禁位认出来。汉字不是单词字符这件事上一线为它红过一次，这次是靠"预期会红的那条没红"把它发现的。
- 在页面层的门里加一句 `navigateTo('/403')` → ④ 红。
- 在"下线"那条地址里塞一句带 `.update(users)` 的字符串 → ⑤ 与 ⑧ 同时红（写 `users` 的名单多了一个、而且那个在后台目录里）。
- 把新线账本里那份档案的期望档数从 8 改成 99 → ⑪ 红，报的是 `8 < 99`。

删干净这件事这次有两条独立的路：一是把五个探针的名字在全仓搜一遍（命中 0），二是重跑八档＋十一档全部绿。上一站漏删一次探针是被 lint 拦下的，这一站把"grep＋重跑"变成固定动作。

## 这一趟的读数

聚合检查八项全过：单测 466 条／70 文件（比上一站多 9 条、多 1 个文件，正是新加的那八档与账本那一档），组件档 71 条／18 文件。

端到端要跑两趟，因为第一趟不干净。不带库那一趟（端口 4200）是 257 passed／164 skipped／**1 failed**，红的还是 `landing.spec.ts:179` 那一条预取用例——这是它第 10 次闪红，单独把这份文件跑一遍是 7 passed；同一趟里另有 2 条因为依赖它而 `did not run`。换端口 4203 重跑整趟：260／164／0。带库那一趟（4201）同样被这一条拖累：372／49／1 failed；换 4204 重跑是 **377 passed／47 skipped／0 failed**，那 47 条分族是要外部服务变量 17、要内容目录读得到 14、要另一趟构建的开关 11、要库 5。

多出来的那一条 skip 落在 `role-refresh-db` 的 ①，同一份文件里其余几档都在跑；分族的名字取自那份文件里第一条 skip 条件，所以被记成"要库"，真实触发点在这一行看不出来。这一条只记成"两趟之间环境放行不同"，不写成"这一档没测到东西"。本线三份带库文件那 15 档，重跑这一趟全部跑到。
