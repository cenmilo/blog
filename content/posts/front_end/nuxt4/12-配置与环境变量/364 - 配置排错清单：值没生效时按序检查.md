配置没生效，最容易犯的错是"想到哪查到哪"。其实它有一小撮固定成因，按顺序排比乱翻快得多。下面这条清单从前到后走，绝大多数情况在第 1 到第 4 关就解决了。

## 第 1 关：键名对不对、有没有类型提示

先确认配置项名字没拼错、缩进没错。官方建议 `nuxt.config` 用 `.ts` 扩展名正是为此：

> You don't have to use TypeScript to build an application with Nuxt. However, it is strongly recommended to use the `.ts` extension for the `nuxt.config` file. This way you can benefit from hints in your IDE to avoid typos and mistakes while editing your configuration.

`.ts` 下写错键名，编辑器会划线。`.js`/`.mjs` 没这层保护，拼错了只能静默不生效。

## 第 2 关：放对了文件吗

配了不生效的第二大成因，是把东西写进了一个 Nuxt 根本不读的文件。

- **Nitro / Vite / PostCSS / webpack 的独立配置文件不再被读取**（`nitro.config.ts`、`vite.config.ts`、`postcss.config.js`、`webpack.config.ts` 官方表里都划了删除线）——必须写进 `nuxt.config` 对应的 `nitro` / `vite` / `postcss` / `webpack` 键（见 347、错误码 B5004）。
- 但 `tsconfig` / eslint / prettier / stylelint / tailwind / vitest 这些**仍各自留文件**，别搬进 nuxt.config（见 347）。
- 客户端可见、构建期定死的公开配置（主题、标题）在 `app.config.ts`，不在 nuxt.config 顶层随手塞（见 348）。

## 第 3 关：是不是被更高优先级盖掉了

同一个键多处在配，合并有固定顺序（见 345）：

```
nuxt.config  >  项目 .nuxtrc  >  全局 ~/.nuxtrc
```

高层压过低层。如果你在项目 `.nuxtrc` 里配了某个键、又在 `nuxt.config` 配了同名键，生效的是 `nuxt.config`。反过来想改全局默认、却发现项目级把它盖住了，也在这关。运行时环境变量只覆盖 `runtimeConfig` 的值（另一维度，见 342），不参与这条链。

## 第 4 关：runtimeConfig 的映射对不对

取不到某个 `runtimeConfig` 值，八成在映射规则上（见 342、343）：

- **键必须先在 `nuxt.config` 声明**，没声明的环境变量不会凭空出现。
- **环境变量名要对得上**：全大写、`NUXT_` 前缀、`_` 分层级；public 层的键名里要带 `PUBLIC`（`apiBase` → `NUXT_PUBLIC_API_BASE`）。
- **别把默认值指向异名的 `process.env.X`**：官方明说这样"只在构建期有效、运行时会坏"（见 343）。给普通默认，靠对得上的 `NUXT_` 变量运行时覆盖。
- **destr 的类型转换坑**：`NUXT_MY_VAR=4848e0` 会被转成数字 `4848`，要保字符串得给值加引号（见 342）。
- **服务端路由里要用 `useRuntimeConfig(event)`**，不传 event 拿不到运行时覆盖值（见 341）。

## 第 5 关：改了要不要重启

改完配置页面纹丝不动，先看改的是哪类文件（见 362）：

- 改 `nuxt.config` / `.env` / `.nuxtignore` / `.nuxtrc` → Nuxt 是**整重启**，不是热更；确认它真的重启完了再看。
- 改 `app.config` → 支持 HMR，能即时生效。
- 改 `runtimeConfig`（默认值或环境变量喂进来的）→ **不热更**，得靠重启生效。

## 第 6 关：`--envName` 选没选

多环境覆盖块（见 363）里，`$production`/`$development` 自动挑，自定义的 `$env.staging` **不点名不生效**。预发配了不生效，先确认命令带了 `nuxt build --envName staging`。另外 `.env` 只在 dev/build/generate 读，产物跑起来时不读——线上变量得部署平台设（见 073、349）。

## 第 7 关：真看不清就上调试工具

前六关排完还定位不到，就用 debugging 那页给的工具把范围缩小：

- **sourcemaps**：服务端构建默认开、客户端在 dev 开；要精确控制：

  ```ts
  export default defineNuxtConfig({
    sourcemap: { server: true, client: true },
  })
  ```

- **Node Inspector**：`nuxt dev --inspect` 起带调试器的 dev，Chrome DevTools 出现 Node 图标就能 attach。官方有硬限制：

  > Note that the Node.js and Chrome processes need to be run on the same platform. This doesn't work inside of Docker.

- **IDE 断点**：VS Code 用 launch 配置（`client: chrome` + `server: nuxt` + `fullstack: nuxt` compound），注意 `webRoot` 要指到你的 `srcDir`（默认 `app`）；JetBrains 系在项目根建 `nuxt.run.xml` 贴三段配置。

## 按序走完（速查）

| 顺序 | 检查 | 典型结论 |
| --- | --- | --- |
| 1 | 键名/`.ts` 提示 | 拼错且没开 TS 类型保护 |
| 2 | 放对文件 | 写进了 nitro/vite/postcss/webpack 独立文件 |
| 3 | 优先级 | 被 nuxt.config 或高层 .nuxtrc 盖住 |
| 4 | runtimeConfig 映射 | 键没声明 / `NUXT_` 名不对 / 异名 process.env / destr 转数字 |
| 5 | 生效时机 | 该重启的没重启（nuxt.config、.env、runtimeConfig） |
| 6 | env 选择 | `$env.staging` 没配 `--envName`；生产还在指望 `.env` |
| 7 | 调试工具 | sourcemap、`--inspect`（非 Docker）、IDE 断点 |

## 自查

- 排错顺序：键名 → 文件对不对 → 优先级 → runtimeConfig 映射 → 生效时机 → envName → 调试工具。
- 前四关（拼错、放错文件、被覆盖、映射不对）占"没生效"的绝大多数。
- 拿不准是不是重启问题，对照"四类文件整重启、app.config 热更、runtimeConfig 不热更"。
- 实在看不清才上 `--inspect`，且记着它不在 Docker 里能用。
