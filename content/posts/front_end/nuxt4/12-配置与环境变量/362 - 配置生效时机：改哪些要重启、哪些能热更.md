`nuxt dev` 跑着，你改了个配置，浏览器里没变化，于是开始怀疑是不是热更坏了、要不要手动重启。其实 Nuxt 早就规定死了：改哪类文件决定它是"整个重启""热更一下"还是"根本没门路生效"。搞混这条线，就会把"本来就该重启"当成 bug，也会把"改 `runtimeConfig` 指望它热更"当成配置没读对。

## 重启、热更分别指什么

**重启**：Nuxt 把当前这个开发实例关掉重来，进程重新初始化。你等的是一次完整的重新启动（首页重新构建），期间端口会短暂断开。

**热更（HMR，hot-module-replacement）**：不重启进程，只把改动的那块模块换掉、页面局部更新，几乎是即时的。

两者的区别决定了你改完配置要等多久、要不要刷新——但更重要的是，**哪些文件根本走不到热更这条路**。

## 会触发整重启的四个文件

`nuxt.config.ts` 那一节（目录结构里的）讲得最直接：

> To ensure your configuration is up to date, Nuxt will make a full restart when detecting changes in the main configuration file, the `.env`, `.nuxtignore` and `.nuxtrc` dotfiles.

也就是说改下面这四个之一，Nuxt 是**整重启**，不是热更：

1. 主配置文件 `nuxt.config`
2. `.env`
3. `.nuxtignore`
4. `.nuxtrc`

`.env` 那一节又把同一个事实说了一遍，还补了为什么：

> When updating `.env` in development mode, the Nuxt instance is automatically restarted to apply new values to the `process.env`.

因为 `.env` 的变量是加载进 `process.env` 的，进程环境变了只能重启才能重读——所以它不可能热更，改了它必然伴随一次自动重启。

## 能热更的是 app.config

`app.config.ts` 那一节开篇就点明它的能力：

> Nuxt provides an `app/app.config.ts` config file to expose reactive configuration within your application with the ability to update it at runtime within lifecycle or using a nuxt plugin and editing it with HMR (hot-module-replacement).

`app.config` 是**响应式**的，支持 HMR：改了它、或在运行期用 `updateAppConfig` 改，都能即时生效，不用重启。

这也是 `.env` 那一节给的一个建议的落点——如果你想用构建期定的环境变量的值、又希望它之后能在应用里被反应式更新，`appConfig` 比 `env` 更合适：

> If you want to use environment variables set at build time but do not care about updating these down the line (or only need to update them reactively *within* your app) then `appConfig` may be a better choice.

## 不热更的是 runtimeConfig

`getting-started/configuration` 里那张 `runtimeConfig` vs `app.config` 对照表，最后有一行专门讲这个：

| Feature | `runtimeConfig` | `app.config` |
| --- | --- | --- |
| Client-side | Hydrated | Bundled |
| Environment variables | ✅ Yes | ❌ No |
| Reactive | ✅ Yes | ✅ Yes |
| Types support | ✅ Partial | ✅ Yes |
| Configuration per request | ❌ No | ✅ Yes |
| Hot module replacement | ❌ No | ✅ Yes |
| Non-primitive JS types | ❌ No | ✅ Yes |

关键两行：**Hot module replacement** 上 `runtimeConfig` 是 ❌ No、`app.config` 是 ✅ Yes。所以改了 `runtimeConfig`（不管是 `nuxt.config` 里的默认值，还是环境变量喂进去的值），别指望它在运行中的实例里热更——默认值在 `nuxt.config` 里，那属于上面"整重启"那一档；环境变量那档在 dev 里也是靠 `.env` 变更触发重启来生效。

另外表里 "Configuration per request" `runtimeConfig` 也是 ❌ No：它是全局一份、构建/启动时定的，做不到"每个请求不同"。

## 热更到底怎么发生的

顺带说清热更的机制，来源是 builders 那一节。开发期 builder 除了打包还要负责起 dev server、改动时重载：

> **Reloads** are signalled by calling `nuxt.server.reload()` when a compilation finishes. The official builders emit a `compiled` hook (for example `vite:compiled`, `webpack:compiled`) that the server integration listens to in order to reload.

即一次重新编译完成，builder 触发 `nuxt.server.reload()`，Nuxt 的服务端集成监听着这个 `compiled` 钩子去重载。这解释的是"应用代码改了怎么热重载"这一层——和上面"配置文件走重启"是两码事：配置文件不参与模块图的热替换，只能整重启。

## 生产环境：env 不再被读、静态渲染后改不了

`.env` 那一节的 Production 段划了条硬边界：

> **After your server is built**, you are responsible for setting environment variables when you run the server. Your `.env` files will not be read at this point.

构建完、跑 `.output` 时，`.env` 文件不再被读取；环境变量要由部署环境（启动参数、`.bashrc`、云平台面板等）显式给。它还提醒 `runtimeConfig` 在生产里只认 `NUXT_` 开头的环境变量。

纯静态另有一档：

> Note that for a purely static site, it is not possible to set runtime configuration config after your project is prerendered.

站点已经预渲染成静态 HTML 了，渲染之后再想改 `runtimeConfig` 就无能为力——这也是为什么 `app.config`（打包进产物、构建期定）和 `runtimeConfig`（运行时可覆盖）要分清。

## 自查

- 改 `nuxt.config` / `.env` / `.nuxtignore` / `.nuxtrc` → **整重启**，不是热更，等它重启完再看效果。
- 改 `app.config` → 支持 **HMR**，即时生效。
- 改 `runtimeConfig`（默认值或环境变量喂进来的）→ **不热更**；它靠重启生效，且非按请求可配。
- 生产：构建后 `.env` 不再被读，环境变量得部署侧给；`runtimeConfig` 生产只认 `NUXT_` 前缀。
- 纯静态预渲染后改不了 `runtimeConfig`；要构建期定又能反应式更新的值，用 `app.config`。
