## 一处写了类型实参，一处没写

内容区那两处（`app/pages/docs/index.vue`、`app/pages/docs/[slug].vue`）都长这样：

```ts
const { data: docs } = await useAsyncData('docs:list', () => $fetch<DocSummary[]>('/api/docs'))
```

会员区那一处只有地址，没有任何类型实参：

```ts
const { data: consoleMetrics } = await useConsoleMetrics('/api/console/metrics')
```

两边后面都能直接写 `consoleMetrics.metrics.total`、`docs.map(item => item.slug)` 而不报错。**那个类型是谁给的**——这个问题不能靠抄声明文件回答，得让编译器自己说。

## 量法：把类型赋给一个数字

故意的错赋值是最便宜的读数机器：`const 检查: number = 那一位`，TS 会把**它自己推出的那个类型**原样印在错误消息里。五探针一次跑完，`npm run typecheck` 的五行输出（原样，未截断）：

```
test/nuxt/fetch-type-sources.test.ts(13,9): error TS2322: Type 'Simplify<SerializeObject<{ error: boolean; url: string; statusCode: number; statusMessage: string; message: string; data: { requestId?: string | undefined; code: string; }; }> | SerializeObject<...>[]> | undefined' is not assignable to type 'number'.
test/nuxt/fetch-type-sources.test.ts(14,9): error TS2322: Type 'DocSummary[]' is not assignable to type 'number'.
test/nuxt/fetch-type-sources.test.ts(15,9): error TS2322: Type 'Simplify<SerializeObject<{ error: boolean; url: string; statusCode: number; statusMessage: string; message: string; data: { requestId?: string | undefined; code: string; }; }> | SerializeObject<...>[]>' is not assignable to type 'number'.
test/nuxt/fetch-type-sources.test.ts(16,9): error TS2322: Type 'unknown' is not assignable to type 'number'.
test/nuxt/fetch-type-sources.test.ts(17,9): error TS2322: Type 'unknown' is not assignable to type 'number'.
```

第 13 行是 `useFetch('/api/docs')` 的 `data.value`，第 14 行是 `$fetch<DocSummary[]>('/api/docs')`，第 15 行是 `$fetch('/api/docs')`（不写泛型），第 16、17 行是把地址换成一个不存在的 `/api/docs-typo` 之后同样的两位。四件事一次读清：

**一、认得地址就真的会推。** 讲 `useFetch` 那一节写的正是这件事：它"按服务端路由给地址提示，并推断接口返回类型"。推出来的类型是 `SerializeObject<…>` 那一大坨——服务端返回体经过 `JSON.stringify` 之后再被 Nuxt 尽量还原的形状。

**二、推出来的那一位里带着错误体。** 注意联合的两支：一支是列表本体，另一支是 `{ error, url, statusCode, statusMessage, message, data: { requestId?, code } }`。这不是我加的，是本站那条接口错误契约的响应形状被路由类型原样带出来的——所以**模板里判一句"取到了没有"不是防御性摆设，那个分支真的在类型里存在**。上一条线（接口错误契约第五步）立的"客户端按 `code` 分支、别匹配人话"，在这一位上也照样要判，因为类型会把它一起推给你。

**三、写了显式泛型，就以你写的为准。** 第 14 行干净得只有一个 `DocSummary[]`：错误体那一支**不会**进来。内容区那两处靠这一位把形状钉成"只有成功体"，代价是失败那一支得自己用 `error` 那一位处理——它们的代码也正是这么写的（服务端取数失败要赶在发 SEO 标签之前抛 503）。

**四、地址写错不报错。** 第 16、17 行是最该记住的一条：`/api/docs-typo` 没让类型检查失败，只是**两位都塌成 `unknown`**。所谓"写错地址谁先报错"这个提法本身就是错的——两条口子都不报，第一次真去用那个值的时候才炸。所以"编译期有保护"这件事要收窄成一句：**它保护的是"类型对得上"，不保护"地址存在"**。

把第一、三、四条合起来读，还有一句分工上的结论：**类型这件事与"选哪条口子"无关**。第 15 行证明不写泛型的 `$fetch` 也认得本站地址，第 13 行证明 `useFetch` 走的是同一套路由类型——会员区那个出口没写任何类型实参却照样推得出形状，靠的就是这一位（它拿到的是 `server/api/console/metrics.get.ts` 那份响应体，形状与错误体一起进来）。所以真正需要关心的只有一件事：这条口子最终发出的地址，是不是 `server/api/` 里存在的那一支。是，类型白拿；不是，全部塌成 `unknown`，而编译器不会替你喊。哪天会员区这份数改成从第三方接口来（今天没有），类型就从"白拿"变成"自己声明"，那时候要改的也不是换成哪条口子，而是加一层自己的类型。

## 那第三方接口怎么办

讲 data fetching 那一节给的就是这个场景：数据来自 CMS 或第三方自带查询层时，`useFetch` 不合适，改用 `useAsyncData` 包住你自己的调用，照样拿到去重、负载转发这些好处。代价就是今天量到的另一面——**没人给你推类型**，返回形状得自己写（`$fetch<…>` 那种显式实参，或者自己声明函数的返回类型）。

本站今天没有第三方查询层，所以类型来源实际只有一条：`server/api/` 下那些路由。两处内容区之所以看起来"多写了泛型"，是因为它们要的形状与推出来的联合不同（第三条），不是因为它们走的是另一条口子。

顺带一句版本线：讲 `createUseFetch` 的那一节里有一个 `routes` 的写法，可以给"不是本站服务端路由"的一批地址声明出类型（配 `routeTypedFetch`／`strictRouteTypes` 才拒绝表里没有的路径与方法）。那一档写的是 4.6 起，本仓库装的是 4.5.2，**用不上**，本文只标版本线、不给用法结论。

## 判据怎么常驻

上面那五行是拆掉用的临时错赋值；留在仓库里的那份是编译期断言（`test/nuxt/fetch-type-sources.test.ts`，1 条 4 断言）：

```ts
expectTypeOf(从地址来.data.value).not.toBeAny()
expectTypeOf(写了泛型).toEqualTypeOf<DocSummary[]>()
expectTypeOf(没写泛型).not.toBeAny()
expectTypeOf(地址写错.data.value).toBeUnknown()
```

那个函数**从不在运行时被调用**（只 `void` 引用它）：在 Nuxt 上下文外面调 `useFetch` 本身就会抛，而这一位要检查的是类型。`npm run typecheck` 会跑这些断言，vitest 那趟只是确认它没把运行时搞坏（`Tests 1 passed (1)`）。

能红吗？把第 2 条改成 `toEqualTypeOf<DocSummary>()`（少写一对中括号）：

```
test/nuxt/fetch-type-sources.test.ts(22,36): error TS2344: Type 'DocSummary' does not satisfy the constraint '{ [x: number]: … tags: "Expected: ..., Actual: never"; …
```

改回来 `npm run check` 八项全 ok。⇒ 类型断言不是装饰，写错形状 `npm run check` 就拦。

## 撞上了去哪里看

| 撞上的现象 | 大概率是哪一位 | 先看哪里 |
| --- | --- | --- |
| 取回来的值是 `unknown`，用不了 | 地址不在 `server/api/` 路由里 | 那一位是不是 `unknown`（本文第四件） |
| 类型里莫名多出一个错误体联合 | 让 `useFetch` 自己推 | 想要干净形状就写显式泛型，并自己处理失败分支 |
| 接了第三方后类型全靠手 | 路由类型只覆盖本站接口 | `useAsyncData` 包调用 ＋ 自己声明返回类型 |
| `expectTypeOf` 那一条看着没跑 | 它是编译期断言 | `npm run typecheck`，不是 vitest |

## 交付前自查

- 类型来源是**让编译器印出来的**（错赋值法），五行读数原样贴，没有抄声明文件
- 那条"推出来的类型带错误体那一支"与上一条线的错误契约对上，并说明模板判空不是摆设
- 推翻了一个想当然：地址写错不会在类型检查报错，只是塌成 `unknown`
- 常驻判据是可红的（少写一对中括号 ⇒ TS2344），且不在运行时调 `useFetch`
- `routes` 那一档标了 4.6 版本线、本机 4.5.2 用不上，没给用法结论
