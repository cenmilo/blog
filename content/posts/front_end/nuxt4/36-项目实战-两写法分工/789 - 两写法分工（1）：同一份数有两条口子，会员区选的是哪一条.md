## 仓库里现在就摆着两种写法

会员区那一处（`app/pages/console/index.vue`）是一行调用出口：

```ts
const { data: consoleMetrics, status: metricsStatus } = await useConsoleMetrics('/api/console/metrics')
```

内容区那一处（`app/pages/docs/index.vue:15`）长得不一样：

```ts
const { data: docs, status, error } = await useAsyncData('docs:list', () => $fetch<DocSummary[]>('/api/docs'))
```

一个是"给个地址，其余交给框架"，一个是"给个键，再给一个自己写的取数函数"。上一条线（页面取数与键）量的是**同一份数怎么被读出来、读几趟**；这一条线问的是前面那一步：**为什么这两处选了不同的口子**。

## 官方给的分工是三句话

讲 data fetching 那一节开头就有一段"in a nutshell"：`$fetch` 是发一次网络请求最简单的方式；`useFetch` 是包在 `$fetch` 外面的一层，作用是让数据在通用渲染（服务端先渲一份 HTML、客户端再接手）里**只取一次**；`useAsyncData` 与 `useFetch` 类似，但提供更细的控制。同一节里还有一句更直白的等价式：

> `useFetch(url)` is nearly equivalent to `useAsyncData(url, () => event.$fetch(url))`. It's developer experience sugar for the most common use case.

也就是：`useFetch` 就是"最常见那一用例的糖"，糖心里那层是 `useAsyncData` 加上一个会自己发请求的函数。

两条口子中只用 `$fetch` 是不够的，那一节写得很明白：只在 setup 里裸用 `$fetch`，同一份数据可能被取两次（服务端一次为了渲 HTML、客户端一次为了水合），会带来水合问题、推迟可交互时间；`useFetch` 与 `useAsyncData` 解决这件事的办法是**服务端取到的那份会随负载送到客户端**。所以那一节的建议是：`$fetch` 留给"只从浏览器发起的请求"（比如点按钮时），初始数据要么 `useFetch`，要么 `useAsyncData` 包住取数函数。

那节还点了什么时候该换另一条口子：当数据来自 CMS 或者第三方自带的查询层时，`useFetch` 不合适，就用 `useAsyncData` 把你的调用包起来，照样拿到它给的那些好处。

## 第一位不同：键在 `useAsyncData` 那里是位置参数

这是这一站能量清、也最容易踩的一位。讲 `useFetch` 与 `useAsyncData` 的那两节写的是同一件事：`useFetch` 的键由"地址＋选项＋调用点在源码里的位置"生成；`useAsyncData` **第一位如果是字符串就拿它当键**，如果直接给函数则自动生成。而那节另一处 `::note` 给了建议：**永远自己写键**，理由是自动键只认调用位置——尤其"当你在做一个包住 `useAsyncData` 的自定义 composable 时"。

两条口子各跑一次，读数原样（`useAsyncData` 这边数的是那个取数函数被叫了几次）：

```
[两口子·带键] {"跑了几次":1,"每趟":["甲调用点#1"]}
[两口子·不写键] {"跑了几次":2,"每趟":["甲#1","乙#2"]}
[两口子·useFetch不写键] {"跑了几次":2,"每趟":["useFetch#1","useFetch#2"]}
[两口子·同一调用点] {"跑了几次":1,"每趟":["同一点#1"]}
```

四行读起来是两句话。**写了同一个字符串键，两处不同调用点也只跑一次**，而且第二处连那个函数都没被叫；**不写键就各跑一次**，`useFetch` 与 `useAsyncData` 在这一条上表现一样。第四行是给第三行划边界的：自动键按调用位置算，所以"同一个位置跑两遍"仍然只跑一次——不写键不等于一定多跑，跑几趟取决于**几行代码**。

这也说明上一条线那个出口为什么值得存在：把键写死在唯一一处，比"每个调用点都要记得写键"更耐磨。

## 清单钉住：现在谁走哪条口子

判据不评好坏，只把现状钉死，免得"哪种写法在管哪份数"只能靠人记。`test/unit/data-fetch-surface.test.ts` 两条读数：

```
[useAsyncData 的键位] [{"文件":"app/pages/docs/index.vue","第一位":"'docs:list', () => $fetch<DocSummary[]>('/api/docs'))","是键吗":true},{"文件":"app/pages/docs/[slug].vue","第一位":"`docs:${slug}`, () => $fetch<DocPage>(`/api/docs/${slug}`),","是键吗":true}]
[口子清单] {"出口调用":["app/components/ConsoleMetricsPanel.vue","app/pages/console/index.vue"],"就地Fetch":[],"用AsyncData":["app/pages/docs/[slug].vue","app/pages/docs/index.vue"]}
```

三位信息：全站 `useAsyncData` 的调用点只有内容区那两处，且**第一位都是写死的键**（一个是常量串、一个把路由参数拼进键里）；**没有任何一处就地写 `useFetch`**（会员区两处走的是出口）；出口那两处就是页面与面板。

把内容区那个键摘掉试一次，判据立刻红，报的是文件名连着那一段原文：`app/pages/docs/index.vue 那个调用点没写键：() => $fetch<DocSummary[]>('/api/docs')): expected false to be true`。改回来就绿——这条判据的价值不在于"必须写键"这个品味，而在于**有人省键时你会立刻知道**。

顺带标一位后面要用的形状：内容区那两处都给 `$fetch` 写了显式类型实参（`$fetch<DocSummary[]>`、`` $fetch<DocPage> ``）。会员区那条出口没有这一位也能有类型——**类型从哪来**这件事是这一条线后面一步的题。

## 分工还没证明，只是把现状量清

需要说明一句：这一站没有证明"内容区那个选择是对的"。那两处代码的注释各自写着理由（大意是这份正文以后要同时走"服务端渲一次"和"客户端导航再取一次"两条路，所以取数交给 `useAsyncData` 包着 `$fetch`）。可这个理由在 `useFetch` 那条口子上同样成立——上一条线量过的那四档就是同一件事：两条口子在服务端都会等取数落定再渲。所以那句理由成不成立，是下一站要判的动作，不在这里先替它背书。

## 撞上了去哪里看

| 撞上的现象 | 大概率是哪一位 | 先看哪里 |
| --- | --- | --- |
| 同一份数据被取了两遍 | 两处各自写键、或干脆没写键 | `[两口子·不写键]` 那条形状：几行代码就是几个自动键 |
| 包了一层自定义 composable，结果每处调用各取一次 | 自动键只认调用位置 | 把键写死在唯一一处（出口那种做法） |
| setup 里裸 `$fetch`，页面数字闪一下才对 | 没有负载转发与去重 | 换成 `useFetch` 或 `useAsyncData` 包住 |
| 判据忽然报"某个调用点没写键" | 有人省了第一位的键 | 那一条静态判据 |

## 交付前自查

- 两条口子的差别量在**可判的位**上（键在第一位还是选项里、跑几趟），没有停在"一个更高层一个更底层"这种说法
- 四条读数各管一件事，其中"同一调用点只跑一次"是给"不写键就多跑"划边界的
- 静态判据被一次真实坏改动验过（摘掉键 ⇒ 红，且消息带文件与原文）
- 内容区那句选择理由**没有**被本站当成结论，明确留给下一站判
- 应用代码零改动，两条口子都是仓库里原有的写法
