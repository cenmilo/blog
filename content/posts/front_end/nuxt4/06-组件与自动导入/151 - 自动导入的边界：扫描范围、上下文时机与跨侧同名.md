自动导入带来的困惑基本是三类："我明明写了这个文件，为什么导不进来"、"`Nuxt instance is unavailable` 是什么意思"、"这个名字在服务端指向的是同一个东西吗"。三类各有一条官方边界，这一篇一次划完。

## 边界一：扫描范围是列出来的，不是"目录里所有文件"

`shared/` 那一节把这条讲得最细，因为它的规则是**只认两个子目录**：

> Only files in the `shared/utils/` and `shared/types/` directories will be auto-imported. Files nested within subdirectories of these directories will not be auto-imported unless you add these directories to `imports.dirs` and `nitro.imports.dirs`.

官方直接给了带注释的目录树，我认为这是整篇最省话的一张图：

```bash [Directory Structure]
-| shared/
---| capitalize.ts        # Not auto-imported
---| formatters
-----| lower.ts           # Not auto-imported
---| utils/
-----| lower.ts           # Auto-imported
-----| formatters
-------| upper.ts         # Not auto-imported
---| types/
-----| bar.ts             # Auto-imported
```

四行 `Not auto-imported` 的分布说明了两件事：**`shared/` 根下的文件不算**，**`shared/utils/` 的下层子目录也不算**。

被扫的那两个目录，扫描方式与 app 侧同源：

> The way `shared/utils` and `shared/types` auto-imports work and are scanned is **identical to** the `app/composables/` and `app/utils/` directories.

不在范围内的，官方给的出口是别名而不是配置：

> Any other files you create in the `shared/` folder **must be manually imported using the `#shared` alias** (automatically configured by Nuxt):

```ts [Importing From #shared]
// For files directly in the shared directory
import capitalize from '#shared/capitalize'

// For files in nested directories
import lower from '#shared/formatters/lower'

// For files nested in a folder within utils
import upper from '#shared/utils/formatters/upper'
```

> This alias ensures consistent imports across your application, regardless of the importing file's location.

**两条出口要分清**：想真的进入自动导入，得把目录同时加进 `imports.dirs` **和** `nitro.imports.dirs`（两个都要写，这是官方原话里的并列）；只想跨侧共用一个函数，用 `#shared` 显式导更省事，也不改变扫描范围。

类型是同样的分侧规则：

> Types that are only used in one context can live next to that context instead: `app/types/` is auto-imported in the Vue app only, and `server/types/` is auto-imported in the Nitro server only. Use `shared/types/` when a type is needed in both.

`shared/` 那条禁令也在这张图旁边（066 已立过）：

> Code in the `shared/` directory cannot import any Vue or Nitro code.

官方还专门警告"看起来能用"的那种错觉：

> `import type` is erased at compile time and does not pull runtime code into the other bundle, so importing only types across the boundary **may appear to work**. Even so, keep shared types (such as API response types) in `shared/types/`, where they are auto-imported in both contexts.

## 边界二：调用位置与时机（这条最容易在运行时报错）

`auto-imports` 那一节的 "Vue and Nuxt Composables" 小节，是这一类问题的官方解释，三段都在讲同一件事：

> When you are using the built-in Composition API composables provided by Vue and Nuxt, be aware that many of them rely on being called in the right *context*.

> During a component lifecycle, Vue tracks the temporary instance of the current component (and similarly, Nuxt tracks a temporary instance of `nuxtApp`) via a global variable, **and then unsets it in the same tick**. This is essential when server rendering, both **to avoid cross-request state pollution (leaking a shared reference between two users)** and to avoid leakage between different components.

机制句里"同一个 tick 内被清掉"就是全部原因：**它不是常驻全局，是一个转瞬即逝的登记**。所以：

> That means that (with very few exceptions) **you cannot use them outside a Nuxt plugin, Nuxt route middleware or Vue setup function**. On top of that, **you must use them synchronously** - that is, you cannot use `await` before calling a composable, except within `<script setup>` blocks, within the setup function of a component declared with `defineNuxtComponent`, in `defineNuxtPlugin` or in `defineNuxtRouteMiddleware`, **where we perform a transform to keep the synchronous context even after the `await`**.

这句长话拆成三格：

| 限制 | 官方给的口径 |
| --- | --- |
| 位置 | 只有三处：Nuxt 插件、Nuxt 路由中间件、Vue setup 函数 |
| 时机 | 必须同步——`await` 之后不能再调 composable |
| 例外 | 四个场合可以跨 `await`：`<script setup>`、`defineNuxtComponent` 的 setup、`defineNuxtPlugin`、`defineNuxtRouteMiddleware`；原因是框架"perform a transform"保住了同步上下文 |

报错怎么读，官方只给了一句，但方向很明确：

> If you get an error message like `Nuxt instance is unavailable` then it probably means you are calling a Nuxt composable **in the wrong place in the Vue or Nuxt lifecycle**.

官方给的正反两例，差别只在调用的位置：

```ts [composables/example.ts]
// trying to access runtime config outside a composable
const config = useRuntimeConfig()

export const useMyComposable = () => {
  // accessing runtime config here
}
```

```ts [composables/example.ts]
export const useMyComposable = () => {
  // Because your composable is called in the right place in the lifecycle,
  // useRuntimeConfig will work here
  const config = useRuntimeConfig()

  // ...
}
```

**第一个文件的错不在语法，在"模块顶层就调用了"**：文件被导入的那一刻并没有组件上下文。把调用挪进函数体，等调用者带着上下文进来时才执行。

还有一条针对非 SFC 组件的补充：

> When using a composable that requires the Nuxt context inside a non-SFC component, you need to wrap your component with `defineNuxtComponent` instead of `defineComponent`

真要打破这套同步限制，官方指了一个实验开关：`asyncContext`（read-more 指向 `experimental-features#asynccontext`），"Checkout the `asyncContext` experimental feature to use Nuxt composables in async functions."——它是实验特性，不是免费的逃生舱（162 会讲 `defineNuxtComponent` 本身）。

## 边界三：同名的东西在两侧可能不是同一个

### app.config.ts：一部分自动导入在 Nitro 侧不存在

`app.config.ts` 会被 Nitro 一起处理，官方列了两条限制：

> As of Nuxt v3.3, the `app.config.ts` file is shared with Nitro, which results in the following limitations:
>
> 1. You cannot import Vue components directly in `app.config.ts`.
> 2. **Some auto-imports are not available in the Nitro context.**

原因也给了：

> These limitations occur because Nitro processes the app config without full Vue component support.

官方确实提到一个 workaround，但**立刻把它标成不推荐**：

> While it's possible to use Vite plugins in the Nitro config as a workaround, this approach is not recommended:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitro: {
    vite: {
      plugins: [vue()],
    },
  },
})
```

> Using this workaround may lead to unexpected behavior and bugs. **The Vue plugin is one of many that are not available in the Nitro context.**

**"注意第二句的范围词"**：Vue 插件只是"许多不可用之一"的一个例子，不是全部。别把这段读成"加上 vue 插件就没事了"。

类型侧同一条边界也出现过：

> Outside app code (server routes, the `shared/` directory and `nuxt.config`) `useAppConfig()` returns `SharedAppConfig`, so extend that interface instead.

（三个接口怎么用是 108 的事，这里只取"app 之外是另一个类型"这一格。）

### 服务端：自动导入的同名函数是 h3 的

`nuxt/server` 这一层（官方注明"**`nuxt/server` ships from Nuxt 4.6**"）把跨侧同名讲得最直接：

> These names are **not auto-imported from `nuxt/server`**. In server code, **the auto-imported names of the same spelling are h3's own helpers**, which take the h3 event and **behave differently in places** (`defineEventHandler`, `handleCors`, `getRouterParams` and `readValidatedBody` among them), **so import from `nuxt/server` explicitly**. That includes `defineEventHandler`: the `nuxt/server` helpers read the event it hands the handler.

四个被点名的例子就是最容易"写法一样、行为不同"的那批。会话那四个名字更狠，官方专门给了一条 note：

> h3 ships session helpers of the same names, and under `@nuxt/nitro-server` those are what the auto-imported `useSession`, `getSession`, `updateSession` and `clearSession` resolve to, so import these from `nuxt/server` explicitly. **They are a separate implementation and are not interchangeable**: h3 defaults to the `h3` cookie name rather than `nuxt-session`, takes its own configuration, and a session one of them issues **will not unseal with the other**.

**"一边发的会话另一边解不开"**——这是跨侧同名能造成的最实际故障：表现是"用户每次刷新都被登出"，而不是报错。

### 反方向：nuxt/server 不能在 app 侧导入，也不能在 Nuxt 进程里用

> Importing `nuxt/server` from a Vue component, a plugin or the `shared/` directory **fails the build**, and the error points you at `#app`, `#imports`, `$fetch` and `useFetch` instead. **Its types still resolve in those contexts**, which is what lets `$fetch` know what your server routes return.

第二句有个正向用途：**类型能解析**，所以 `$fetch` 的返回类型仍然知道你的服务端路由返回什么——构建失败的是运行时导入，不是类型。

另一半限制针对"跑在 Nuxt 进程里"的代码：

> `nuxt/server` also only works in code that a server builder bundles, because the builder supplies the runtime config, app config, hooks and in-process fetch behind it. Code that runs in the Nuxt process, such as `nuxt.config.ts`, a module's `setup` or a function passed to `addDevServerHandler`, has none of these, **so don't import `nuxt/server` there**: `useRuntimeConfig()` and `useAppConfig()`, for example, **return empty objects**. Read `nuxt.options` instead.

这条的症状最难查：不报错，**返回空对象**。我按官方结论记住这个分工：模块与配置层读 `nuxt.options`，被服务端构建器打包的代码才用 `useRuntimeConfig()`。

### 撞名时的裁决：priority

两侧都靠 `imports` 机制，撞名规则官方写在参数表里：

| 字段 | 官方定义 |
| --- | --- |
| `priority` | "Priority of the import; **if multiple imports have the same name, the one with the highest priority will be used.**" |
| `disabled` | "If this import is disabled." |

服务端侧对应的 kit 函数是 `addServerImports`（"Add imports to the server. **It makes your imports available in Nitro without the need to import them manually.**"）与 `addServerImportsDir`（"Add a directory to be scanned for auto-imports by Nitro."，`opts.prepend` 为 true 时"the directory is added to **the beginning of the scan list**"）。这两个函数的完整用法 153 讲，这里只取一条硬性警告——**跨侧共用的工具必须两边同源**：

> If you want to provide a utility that works in both server and client contexts and is usable in the `shared/` directory, the function must be imported **from the same source file** for both `addImports` and `addServerImports` and **should have identical signature**. That source file **should not import anything context-specific** (i.e., Nitro context, Nuxt app context) or else it might cause **errors during type-checking**.

四个要求：同源文件、同签名、不导入上下文相关代码、否则类型检查报错。

## 三类症状对应三类边界

| 症状 | 是哪条边界 | 先看哪一句 |
| --- | --- | --- |
| 明明有文件，名字却用不了 | 范围 | 它在不在 `shared/utils`、`shared/types`、`app/composables`、`app/utils`、`server/utils` 这些**被列出的目录**里，有没有再套一层子目录 |
| `Nuxt instance is unavailable` | 上下文 | 调用点是否在插件/路由中间件/setup 里，`await` 之后有没有再调 composable |
| 类型检查阶段报错、两侧行为不一致 | 侧别（跨侧共用） | 那个文件是不是同时喂 `addImports` 与 `addServerImports`，签名是否一致，有没有引用上下文相关代码 |
| 服务端同名函数行为奇怪 | 侧别（h3 同名） | 需不需要从 `nuxt/server` 显式导入（尤其会话相关四个名字） |
| `useRuntimeConfig()` 在模块里返回空 | 侧别（Nuxt 进程） | 换成读 `nuxt.options` |
| 模板里 ref 显示成对象 | 范围那一节的 warning | 自动导入的 `ref`/`computed` 在模板中不解包（150） |
