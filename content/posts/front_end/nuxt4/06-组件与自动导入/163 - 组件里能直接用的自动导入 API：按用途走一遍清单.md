You can find a reference for auto-imported components, composables and utilities in the API section.**"；范围承诺是："Nuxt auto-imports functions and composables to perform **data fetching**, get access to the **app context** and **runtime config**, manage **state** or **define components and plugins**."，Vue 那一半是："**Vue exposes Reactivity APIs like `ref` or `computed`, as well as lifecycle hooks and helpers that are auto-imported by Nuxt.**"。三件事最容易记错：**其一，服务端不共享这份名单**——`nuxt/server` 那一节明写"**These names are not auto-imported from `nuxt/server`**"，服务端同名的是 h3 的 helper；**其二，编译器宏不是自动导入的普通函数**——`definePageMeta` 与 `defineLazyHydrationComponent` 都是宏（后者官方定位："a compiler macro that helps you create a component with a specific lazy hydration strategy"），有各自的书写限制；**其三，`node_modules` 里的文件不享受自动导入**（"Auto-imports are not enabled for files within `node_modules` ... for performance reasons."），所以模块作者要显式从 `#imports` 导。出口在别名：`#imports` 覆盖"**every auto-import**"、组件的对应出口是 `#components`、`shared/` 用 `#shared`。

写到这我开始需要一张"能直接用的名字"的表：不是记不记得住的问题，而是每次要确认"这个是不是自动导入的、它在服务端有没有"。这一篇把前面几篇证实过的名字按用途归一次类，末尾给三条判定办法。

## 先给判定标准，别背清单

官方在自动导入页写了一句可以直接当判据用：

> In the docs, **every function that is not explicitly imported is auto-imported by Nuxt** and can be used as-is in your code. You can find a reference for auto-imported components, composables and utilities in the API section.

所以判"能不能不写 import"只需要三步：

| 步 | 问什么 | 依据 |
| --- | --- | --- |
| 1 | 这个文件在 `app/` 侧还是 `server/` 侧？ | 两份名单是分开的（151、153） |
| 2 | 它在不在 `node_modules` 里？ | "**Auto-imports are not enabled for files within `node_modules`** ... for performance reasons."（154） |
| 3 | 它是编译器宏还是普通函数？ | 宏有额外限制（下下面第二节） |

清单会随版本变，这三条判据不会——**这张表我用来得分，用来核对；真正确认还是靠这三条**。

## app 侧：按用途分组

| 用途 | 能直接写的名字 | 出处（文档那一节） |
| --- | --- | --- |
| 取数据 | `useFetch`、`useAsyncData` | 自动导入页 "data fetching" 那一组链接 |
| 状态 | `useState` | 同上 "manage state" |
| 应用上下文 | `useNuxtApp` | 同上 "app context" |
| 运行时配置 | `useRuntimeConfig` | 同上 "runtime config"（服务端那一侧见下一节） |
| 路由与导航 | `useRoute`、`useRouter`、`navigateTo`、`abortNavigation`、`preloadRouteComponents` | 120-127、145 |
| 页面定义 | `definePageMeta`（宏）、`setPageLayout` | 117、139 |
| 中间件与插件 | `defineNuxtRouteMiddleware`、`defineNuxtPlugin`、`addRouteMiddleware` | 130-132、061 |
| 错误 | `createError`、`useError`、`clearError`、`showError` | 111、095 |
| 组件相关 | `defineNuxtComponent`、`defineLazyHydrationComponent`（宏） | 162、166 |
| 反馈通道 | `useLoadingIndicator`、`useRouteAnnouncer`、`useAnnouncer` | 144、146 |
| 应用配置 | `useAppConfig`、`updateAppConfig` | 108 |
| 组件预热 | `preloadComponents`、`prefetchComponents` | 168 |
| Vue 那一半 | `ref`、`computed`、`watch` 等响应式 API，以及 `onMounted` 这类**生命周期钩子与工具** | "Vue exposes Reactivity APIs like `ref` or `computed`, as well as **lifecycle hooks and helpers** that are auto-imported by Nuxt." |
| 你自己写的 | `app/composables/`、`app/utils/`、`shared/utils/`、`shared/types/` 里的导出 | 150、151 |

Vue 那一组的范围词别只看举例：**官方句子里除了 `ref`/`computed` 还包含"lifecycle hooks and helpers"**，也就是 `onMounted`、`onBeforeUnmount`、`nextTick` 这类同批到位——149 那条"SSR 阶段不跑 `onMounted`"的限制正是在这批名字上成立的。

## 编译器宏：形状不同，限制也不同

上面表里标了"宏"的两个，跟普通函数**不是一套规则**：

| 宏 | 官方定位 | 特殊限制 |
| --- | --- | --- |
| `definePageMeta` | 编译器宏，元数据被提到组件之外 | 参数只能是纯函数与导入绑定；`title, // do not do this` 这类变量写法拿不到值（117、143） |
| `defineLazyHydrationComponent` | "a **compiler macro** that helps you create a component with a specific lazy hydration strategy" | "**To ensure that the compiler correctly recognizes this macro, avoid using external variables.**"（167 展开） |

**共同点**：它们的参数会被**编译期读取**，所以"能求值出结果的写法"才是有效写法。这一类出问题时的症状通常是"选项像没写一样"，而不是报错。

## 服务端那一侧：另一份名单

`server/` 里能直接写的只有这一条来源，官方一句话限定：

> In the `server` directory, Nuxt auto-imports **exported functions and variables** from `server/utils/`.

其余都要显式导入。`nuxt/server` 那一节给了完整的可用清单（**它不自动导入**，`import` 得自己写）：

| 领域 | 名字 |
| --- | --- |
| 事件与错误 | `defineEventHandler`、`createError`、`isNuxtError` |
| 请求信息 | `getRequestURL`、`getRequestHost`、`getRequestProtocol`、`getRequestHeader`、`getRequestHeaders`、`getRouterParam`、`getRouterParams`、`getRequestIP` |
| 查询与请求体 | `getQuery`、`getValidatedQuery`、`readBody`、`readValidatedBody` |
| Cookie | `getCookie`、`parseCookies`、`setCookie`、`deleteCookie` |
| 响应 | `setResponseStatus`、`handleCors`、`sendRedirect` |
| 内部取数 | `serverFetch` |
| 会话与密钥 | `useSession`、`getSession`、`updateSession`、`clearSession`、`deriveSecret` |
| 规则与配置 | `getRouteRules`、`matchRouteRules`、`useRuntimeConfig`、`useAppConfig`、`useServerHooks` |

官方那句提醒是这一节的核心："**These names are not auto-imported from `nuxt/server`.** In server code, the auto-imported names of the same spelling are **h3's own helpers**, which take the h3 event and **behave differently in places** (`defineEventHandler`, `handleCors`, `getRouterParams` and `readValidatedBody` among them), **so import from `nuxt/server` explicitly.**"

**`useRuntimeConfig` 在两侧都出现，但拿法不同**：app 侧无参、可移植的服务端侧无参、而 nitro2 那条路上是 `useRuntimeConfig(event)`（154 的例子）。这是"同名不同物"最典型的样本。

不在 `nuxt/server` 覆盖范围内的（storage、caching、server plugins、lazy handlers、tasks）官方另给一张表，要从 `nitropack/runtime` 或 `h3` 直接导入（171 那条线附近我引过）。

## 三个别名出口

| 别名 | 覆盖 | 官方句 |
| --- | --- | --- |
| `#imports` | **每一份自动导入** | "Nuxt exposes **every auto-import** with the `#imports` alias" |
| `#components` | 组件（绕过自动导入） | "explicitly import components from `#components` ... to **bypass Nuxt's auto-importing functionality**" |
| `#shared` | `shared/` 里没被扫到的文件 | "Any other files you create in the `shared/` folder must be manually imported using the `#shared` alias" |

用 `#imports` 的三种必写场合（发布模块、关掉自动导入、服务端 legacy 文件）在 154 那篇。
