You can also generate these files manually by running `nuxt prepare`."**

组件与自动导入这一段写了二十多篇，最后我需要一个能回答"这个名字为什么用不了"的东西——不是清单，是一张**顺序图**。下面这五步，就是我在项目里查这类问题时实际走的顺序。

## 全景：一个标签名经过的五步

```
① 构建期生成名单   imports:sources / imports:extend / imports:dirs / imports:context
                   components:dirs / components:extend
        ↓
② 决定"谁有资格进名单"  目录范围 + 开关 + 第三方 presets
        ↓
③ 决定"它叫什么名"  路径拼接 / pathPrefix / prefix / (分组) / normalizeComponentNames
        ↓
④ 撞名裁决  priority（同名字段两处同句）与目录数组顺序
        ↓
⑤ 能不能被调用  位置与时机（上下文）+ 类型是否已生成（prepare）
```

每步的失败方式不同，我把它们分开写。

## 第 ① 步：名单是构建期生成的

这六个钩子都在官方"Nuxt Hooks (Build Time)"表里，逐行原话：

| Hook | Arguments | Description（原文） |
| --- | --- | --- |
| `imports:sources` | `presets` | Called at setup allowing modules to extend sources. |
| `imports:extend` | `imports` | Called at setup allowing modules to extend imports. |
| `imports:context` | `context` | Called when the unimport context is created. |
| `imports:dirs` | `dirs` | Allows extending import directories. |
| `components:dirs` | `dirs` | Called within `app:resolve` allowing to extend the directories that are scanned for auto-importable components. |
| `components:extend` | `components` | Allows extending new components. |

底座官方也点名了："These utilities are powered by `unimport`, which provides the underlying auto-import mechanism used in Nuxt."

**这一步的失败方式：名单根本没被写入。** 典型原因有两个——模块的 `setup` 没跑（模块没装、或 `modules` 顺序问题），或者你改的是配置文件却没重启：**这四个钩子都在构建期**。

## 第 ② 步：谁能进名单（三条范围 + 三个开关）

三条范围，各是一句原话：

| 来源 | 官方原话 |
| --- | --- |
| app 侧三个目录 | "Thanks to its opinionated directory structure, Nuxt can auto-import your `app/components/`, `app/composables/` and `app/utils/`." |
| 服务端 | "In the `server` directory, Nuxt auto-imports exported functions and variables from `server/utils/`." |
| shared | "Only files in the `shared/utils/` and `shared/types/` directories will be auto-imported." |

再加两条隐含范围：**嵌套子目录不算**（要同时加进 `imports.dirs` 与 `nitro.imports.dirs`）、**`node_modules` 里的文件不算**（"Auto-imports are not enabled for files within `node_modules` ... for performance reasons."）。

三个开关的作用范围不同，很容易配错对象：

| 开关 | 关掉什么 | 关不掉什么 |
| --- | --- | --- |
| `imports.autoImport: false` | 自动导入机制本身（`#imports` 仍可用） | 组件自动注册 |
| `imports.scan: false` | 扫 `app/composables/` 与 `app/utils/`（框架与模块注册的名字仍在） | 组件；**副作用是破坏 layers 覆盖** |
| `components.dirs: []` | 你自己的 `~/components` 与 `~/components/global` | 模块添加的组件 |

**失败方式：能用一半。** 最常见的读错是把 `imports.*` 当成也管组件（官方那句"configured separately"就是为此写的）。

## 第 ③ 步：它叫什么名

组件侧的生成规则一句话："the component's name will be based on its own path directory and filename, **with duplicate segments being removed**."

三种人为干预，改的是不同段（158）：

| 手段 | 改动 |
| --- | --- |
| `pathPrefix: false` | 去掉全部路径段（"the same strategy as used in Nuxt 2"） |
| `prefix: 'Xxx'` | 给这条规则匹配到的全部组件前加一段 |
| `(分组)` 目录 | 只让这一段不出现在名字里 |

名字还有**第二个体系**：Vue 内部认识的组件名（`normalizeComponentNames` 把它与自动导入名对齐，v4 起生效）与页面的 `__name`（`normalizePageNames`，要 `future.compatibilityVersion: 5`）。

**失败方式：解析成功但不是你要的那个。** 症状通常是"模板里写的标签没报错、渲染出来的却是另一个文件"或"测试里 `findComponent({ name })` 找不到"。前者查第 ④ 步，后者查这一格的"两个体系"。

## 第 ④ 步：撞名时谁赢

官方唯一一句裁决规则重复出现在三张参数表里（`addImports`、`addServerImports`、`addComponent`）：

> if multiple imports (components) have the same name, **the one with the highest priority will be used**.

第二套机制是顺序，官方在三处写了方向：目录数组"they are scanned **in order**"、"nested directories need to be added first"、覆盖规则那条宽目录"**comes last**"，以及模块侧的 `opts.prepend`（`unshift()` 而非 `push()`）。

**"更早扫到"与"`priority` 更高"谁更强，官方没写成一张表**——这一条我始终只按实测结论写（159 给了测法）。

## 第 ⑤ 步：名字对了，还是调不动

这一步属于函数而非组件，两个条件都在官方那句长规则里：

> That means that (with very few exceptions) **you cannot use them outside a Nuxt plugin, Nuxt route middleware or Vue setup function**. On top of that, **you must use them synchronously**...

失败信息官方连读法都给了：`Nuxt instance is unavailable` → "you are calling a Nuxt composable in the wrong place in the Vue or Nuxt lifecycle"。

组件也在这一步有对应失败：**注册了却没在渲染路径上**（`Lazy` 前缀不带 `v-if` 时"still load eagerly"），以及编译期特性只对 SFC 生效（延迟水合那四条限制）。

## 类型这一层：它不在五步里，但会让五步都"看起来失败"

> Nuxt projects rely on auto-generated types to work properly. These types are stored in the `.nuxt` directory and are **generated when you run the dev server or build your application**. You can also generate these files manually by running `nuxt prepare`.

**为什么单独提**：新加一个自动导入目录后，编辑器里的红线不是"名单没生效"，而是"类型还没重新生成"。这两件事的处置完全不同——前者改配置，后者跑一次 `prepare`。同理，**类型增强要放对目录**（`app/`、`server/`、`shared/` 三个上下文）。

## 一张排错入口表

| 症状 | 先查第几步 | 细读篇目 |
| --- | --- | --- |
| 编辑器提示"找不到名字"，但运行时正常 | ⑤ 之后的类型层 | 155 |
| 名字有、类型也对，运行时报 `Nuxt instance is unavailable` | ⑤ | 151 |
| 明明写了文件，名字却用不了 | ② | 150、151、152 |
| 组件标签解析不出来 | ②③ | 156、157、161 |
| 解析出来的是另一个组件 | ④ | 159 |
| 模板里的标签能写，DevTools/测试里名字对不上 | ③ 的两个体系 | 157 |
| 服务端同名函数行为奇怪 | ②（两侧名单分离） | 151、163 |
| 模块 runtime 里所有名字都报错 | ② 的 `node_modules` 例外 | 154 |

## 这一段最该留下的三句判据

1. **"没写 import"是文档的默认约定**："every function that is not explicitly imported is auto-imported by Nuxt"——遇到不确定的名字，先查它在 API 那一大节的哪一层。
2. **两侧是两套名单**：app 与 Nitro 各自注册、同名不同物；跨侧共用必须同源同签名。
3. **编译期特性只对特定写法生效**：`.client`/`.server` 后缀、`Lazy` 前缀、延迟水合、`resolveComponent` 字面量、宏的参数——**它们的失效都是静默的**。

## 自查

1. 五步分别是什么？每步典型的失败方式各说一句。
2. 六个构建期钩子分别暴露什么参数？其中哪个直接给出 unimport 实例？
3. 三条范围原话各自覆盖哪些目录？两条"隐含范围"是什么？
4. 三个开关各自关不掉什么？哪个开关会连带破坏 layers 覆盖？
5. 组件名的"两个体系"指什么？哪个测试 API 会因此踩坑？
6. 撞名裁决的两套机制分别是什么？哪一部分官方没有定义、需要实测？
7. "编辑器红线"与"名单没生效"怎么区分？各自的处置是什么？
8. 三句判据里，哪几条失效是静默的？
