"这个组件只在服务端渲染"听起来永远划算——少发 JS 怎么会是坏事。但官方那一页里有一段专门讲**客户端导航时每个岛屿要发一次请求**，读完我改变了默认答案：岛屿不是免费的优化，它换走的是别的东西。

## 官方论证的是哪种浪费

开篇不是在介绍功能，而是在算一笔账：

> Nuxt renders your app on the server by default, but then it ships the JavaScript for every component to the browser and hydrates the whole page. For content-heavy components (markdown rendering, syntax highlighting, CMS output) **that never change on the client**, this is **wasted work**: the user downloads, parses and executes code whose only job is **to reproduce HTML that is already on the page**.

> Server components (also called island components) invert this. A server component is rendered on the server, its HTML is embedded in the page, and **none of its JavaScript is sent to the client**. Its dependencies (a markdown parser, a highlighting library) **stay on the server too**.

**两个条件同时成立才值得用**：内容在客户端不会变、且它的依赖体积可观。官方举的三类正是这种（markdown 渲染、语法高亮、CMS 输出）。一个只渲染 `<div>文本</div>` 的组件改成岛屿，省下的是几行 JS，换来的是下面所有代价。

## 换来的是什么：客户端导航的往返

> On the initial server-rendered page load, islands are rendered inline and **there is no extra request**. On **client-side navigation**, however, **each island on the destination page must be fetched from the server** (you can see these requests in the network tab). This has real costs:

官方列的两条代价：

> - islands **block on a network round trip during navigation**, unless you pass the `lazy` prop (with a `#fallback` slot) to render them non-blockingly
> - an app with **many islands per page makes many requests per navigation**

然后是那两句判断，我把它们当作选不选岛屿的标准：

> Islands work best on pages that are reached by **full page loads** (content and marketing pages) or when their **number per page is small**. **If a component needs to update frequently on the client, an island is probably the wrong tool.**

第二条尤其要连 166/167 一起读：**需要频繁更新的组件用延迟水合（JS 仍下发、只是延后交互）都比做成岛屿合适**，因为岛屿每次更新都要重新请求服务端渲染 HTML。

官方也给了"props 变化"的真实代价，在机制那节：

> Changing an island's props triggers **a network request** that re-renders the component on the server and updates its HTML in place.

### 缓解手段与它的边界

> When a `<NuxtLink>` to a [server-only page] is **prefetched**, its island response is prefetched too, so the round trip happens **before** the user navigates rather than during the navigation. The prefetched response is cached against the island's **name, props and context**, which is the same key the island uses when it mounts. **A failed prefetch is not fatal: the island is fetched again on mount.**

紧接着那条 note 划掉了乐观解读：

> This applies to **the island that renders a whole `.server.vue` page**. **Islands used within a page are still fetched when they mount.**

**读法**：预取只救"整页就是一个服务端页面"的那种情况；页面里内嵌的岛屿仍然在挂载时各自发请求。所以我不能拿"链接会预取"来给多岛屿页面辩护。

（这也接上 147 那张预取表：`<NuxtLink>` 预取的东西包括 payload，而岛屿响应的缓存键正是 name/props/context。）

## 岛屿看不见你的页面：三条隔离后果

106 讲过隔离机制（独立 Vue app、island context、插件重跑），这里只留与"能不能用"相关的三条：

> - you **cannot share state** (provide/inject, Pinia, `useState`) between the page and the island; **pass data via props instead**
> - `useRoute()` inside an island **reflects the island's own request**, not the page the user is on. If an island needs route information, pass it in explicitly, either as props or via the `context` prop on `<NuxtIsland>` (read inside the island from `nuxtApp.ssrContext.islandContext`)
> - **route middleware does not run** when rendering islands

官方把隔离的原因归到缓存键上，这句是我最喜欢的一个"为什么"：

> Note that island responses being keyed only on **name, props and context** is exactly what keeps them **cacheable independently of the page** they appear on; this is also why **they cannot see the current route**.

**"可缓存"与"看不见路由"是同一件事的两面**——接受岛屿，就接受这份信息切断。

## 官方列的当前限制（十条里我记三条）

> Server components are experimental, and some rough edges are tracked in open issues:

| 原文 | 我在意它的理由 |
| --- | --- |
| "Most features for server-only and island components, such as **slots and `nuxt-client` components**, are **only available for single file components**." | 与 167 那条 SFC 限制同形：**编译期特性只认 SFC** |
| "**Using islands can significantly increase the number of chunks generated at build time**" | 岛屿多 → 构建产物分块数膨胀，这是构建侧的代价 |
| "**`inject`/`provide` does not cross the island boundary**, so injecting from the page into a standalone server component does not work" | 依赖 provide 的库（UI 主题、上下文组件）进岛屿会静默失效 |
| "Server components rendered via the auto-generated wrapper **do not expose load and error events**; use `<NuxtIsland>` directly if you need its `error` event and `refresh()` method" | 要错误处理就得下沉到 `<NuxtIsland>`（107 的 `error` 事件与 `refresh()`） |
| "Each **nested island** adds extra overhead, so be careful when nesting islands within other islands" | 嵌套不是免费叠加 |
| "With webpack and Rspack, scoped `:slotted()` styles in server component slots can fail because server and client builds may generate different scope IDs" | 插槽样式在特定构建器下有已知问题 |
| "Template refs cannot reference elements inside a server component from the parent" | 父组件拿不到岛屿内部 DOM |
| "`useId` has known limitations inside islands" | 107 展开过（无解的重复 id 场景） |

另外"服务端组件与岛屿必须有单根元素（HTML 注释也算元素）"这条结构要求反复出现在两页（161 也记了）。

**最上面那句"Server components are experimental"要连着这条 read-more 读**："Server components are still marked experimental. You can follow the roadmap on GitHub."——这套能力官方自己标的是实验状态。

## 与另外三种"少发 JS"的手段放一起

| 手段 | JS 是否下发 | 交互 | 主要代价 |
| --- | --- | --- | --- |
| `.server.vue` 岛屿 | **不下发** | 静态（除非 `nuxt-client`，见 171） | 每次挂载/prop 变化一个网络往返；状态与路由被切断 |
| 延迟水合（166、167） | 下发 | 延后可用 | 代码仍在包里；四条限制 |
| `hydrate-never` | 下发 | **永不交互** | prop 一变仍会水合（167） |
| `noScripts` 路由规则（141） | 页面脚本不下发 | 全无 | 该路由永不水合，交互都失效 |
| `ssr: false`（165） | 全下发 | 全部 | 首屏 HTML 与服务端渲染的 SEO 收益 |

**这张表我的用法**：先问"要省的是下载、执行，还是首屏空白"，再决定用哪一行。**岛屿省的是下载 + 执行，但代价是运行时往返**——这也是它只适合"整页加载到达的内容页"的原因。

## 一个常被忽略的替代：成对写法

> You can also pair a `.server.vue` component with a `.client.vue` component of the same name for separate server and client implementations. **In that case the component is not an island: the client half hydrates normally.**

这句很关键：**成对写法（165 引过）得到的不是岛屿**。它能避开状态/路由切断与网络往返，代价是两份实现都要维护。所以我判断"到底要不要岛屿"时的第一问其实是：**我是不是只需要"服务端简单版 + 客户端交互版"？** 如果是，成对写法比岛屿便宜。
